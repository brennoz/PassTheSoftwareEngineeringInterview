HashMap — from Concept to Distributed KV

Algorithms Data Structures Lesson 01 ~20 min Java · C · System Design

HashMap is the data structure interviewers probe most often — and not just "what is it?" They want to know how it works inside (Java), how you'd build it without a standard library (C), and how the same idea scales to a distributed system (Redis Cluster, DynamoDB). This lesson covers all four layers.

1. Core concept — what a HashMap is

A HashMap solves the lookup problem: given a key, find the associated value in O(1) average time. The trick is a hash function that converts any key into an integer bucket index. 

hash("name") = 7429
7429 % 16   = 5          // bucket index
buckets[5]  = {key="name", value="Alice"}

What it gives you

  • O(1) average get, put, remove
  • Key-value association (dictionary / map)
  • Flexible key types (any object with hashCode)

What it doesn't give you

  • Ordering — keys have no sequence
  • Sorted range queries (use TreeMap)
  • O(1) worst-case (use a tree for that)

2. Java HashMap internals

The data structure

class HashMap<K,V> {
    Node<K,V>[] table;         // array of bucket heads
    int size;
    float loadFactor = 0.75f;  // resize when size > capacity * 0.75

    static class Node<K,V> {
        final int hash;
        final K key;
        V value;
        Node<K,V> next;        // linked list for collisions
    }
}

Java's hash spread function

static final int hash(Object key) {
    int h = key.hashCode();
    return (h == 0) ? 0 : (h ^ (h >>> 16));
}
// bucket = hash & (capacity - 1)   ← bit-mask, not %
Why XOR with the high 16 bits? Small tables (capacity 16–32) only use the low bits of the hash. Without mixing, keys that differ only in high bits would all collide. The XOR spreads entropy across the full width.

Collision: chain → tree

Two keys with the same bucket index collide. Java uses separate chaining: each bucket is a linked list. A chain longer than 8 nodes (and table ≥ 64 buckets) is converted to a Red-Black Tree for O(log n) lookup in that bucket.

Interview trap — "HashMap is O(1)". True on average, false in the worst case. A hashCode() that returns a constant puts all keys in one bucket → O(n) lookup. hashCode() quality is load-bearing.

The hashCode() / equals() contract

// Two-step lookup in HashMap.get():
// Step 1 — find bucket via hashCode()
// Step 2 — walk chain, compare via equals()

// Java spec rule:
// If a.equals(b) → a.hashCode() == b.hashCode()
// (same hash does NOT imply equal — that's a collision)

// Classic bug:
class Order {
    String id;
    @Override public boolean equals(Object o) { ... } // ✓
    // hashCode() NOT overridden                       // ✗ — silent bucket miss
}
Order o1 = new Order("X"), o2 = new Order("X");
map.put(o1, "data");
map.get(o2);  // → null — different hashCode, different bucket!

// Fix: Java record auto-generates both:
record Order(String id) {}

3. Building a HashMap in C

What a struct is

C has no classes. A struct is a named block of fields laid out contiguously in memory. typedef struct X X lets you write X instead of struct X everywhere. 

struct Node {
    char *key;         // pointer to string — 8 bytes on 64-bit
    char *value;       // pointer to string — 8 bytes
    struct Node *next; // pointer to next node — 8 bytes
};                     // total: 24 bytes, contiguous in RAM

typedef struct Node Node;  // drop the "struct" keyword

Pointer operators

Node  val;         // value on the stack
val.key = "hi";   // dot   = direct field access

Node *ptr = &val; // pointer to the node
ptr->key  = "hi"; // arrow = (*ptr).key — dereference then access
(*ptr).key = "hi";// same thing, long form

Heap allocation

Node *n = (Node *) malloc(sizeof(Node)); // allocate 24 bytes on heap
if (!n) { /* OOM — always check NULL */ }
n->key = strdup("hello"); // heap-copies the string; caller must free()
free(n->key);
free(n);

Full HashMap implementation

/* Entry: one key-value pair with chaining */
typedef struct Entry {
    char *key;
    char *value;
    struct Entry *next;
} Entry;

typedef struct {
    Entry **buckets; // array of Entry* pointers
    int capacity;
} HashMap;

/* djb2 hash — fast, good distribution for strings */
unsigned int djb2(const char *str) {
    unsigned int h = 5381;
    int c;
    while ((c = *str++))
        h = ((h << 5) + h) + c; // h*33 + c
    return h;
}

HashMap* hm_create(int cap) {
    HashMap *m = malloc(sizeof(HashMap));
    m->buckets = calloc(cap, sizeof(Entry*)); // calloc zeros all pointers
    m->capacity = cap;
    return m;
}

void hm_put(HashMap *m, const char *k, const char *v) {
    int idx = djb2(k) % m->capacity;
    Entry *e = m->buckets[idx];
    while (e) {
        if (strcmp(e->key, k) == 0) { // strcmp: 0 = equal
            free(e->value);
            e->value = strdup(v);
            return;
        }
        e = e->next;
    }
    // prepend new entry (head-insert = O(1))
    Entry *ne = malloc(sizeof(Entry));
    ne->key   = strdup(k);
    ne->value = strdup(v);
    ne->next  = m->buckets[idx];
    m->buckets[idx] = ne;
}

char* hm_get(HashMap *m, const char *k) {
    int idx = djb2(k) % m->capacity;
    Entry *e = m->buckets[idx];
    while (e) {
        if (strcmp(e->key, k) == 0) return e->value;
        e = e->next;
    }
    return NULL;
}
C pitfalls to know: a == b compares pointer addresses, not string content — always use strcmp. strdup heap-allocates; you must free it. calloc zeroes memory; malloc does not.

4. Distributed KV Store — the same idea at scale

A single-machine HashMap is bounded by RAM. At millions of keys you spread the hash table across N machines. The core problem is identical: given a key, find which bucket owns it — but now a "bucket" is a whole server.

Consistent hashing

Naive sharding (serverIndex = hash(key) % N) breaks every time you add or remove a node — all keys remap. Consistent hashing fixes this:

  1. Map all servers AND all keys onto a ring (integers 0 → 2³²)
  2. A key is owned by the first server clockwise from its hash position
  3. Adding a node only remaps ~1/N keys; removing one only remaps its direct successor's keys

Virtual nodes

A plain ring with 3 servers puts each server at one fixed point — load is uneven if keys cluster. Virtual nodes (vnodes): each physical server appears at K positions on the ring (e.g. K=150). DynamoDB and Cassandra both use this.

N / W / R quorums

VariableMeaning
NReplication factor (e.g. 3 replicas)
WWrite quorum — ACKs required before success
RRead quorum — responses required

W + R > N guarantees you read at least one node that saw the latest write (strong consistency). W=1, R=1 is fastest but allows stale reads.

The analogy

Real systems
  • Redis Cluster: 16 384 hash slots, CRC16(key) % 16384
  • DynamoDB: consistent hashing with vnodes; R/W quorums per table
  • Cassandra: tunable consistency per query (QUORUM, ONE, ALL)
