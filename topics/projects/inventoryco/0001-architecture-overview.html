Architecture Overview

Layered modular monolith · docker-compose stack · actual vs. suggested infrastructure

System map

The solution is a Spring Boot 3.5 / Java 21 backend organised as a single modular monolith (packages frame, web, config, observability, health) rather than a set of separate services, paired with a React + TypeScript + Vite frontend. MariaDB is the only datastore — there is no separate cache, search index, or message broker anywhere in the running stack. The entire system starts with one command, docker compose up --build, and exposes the frontend on :3000, the backend API on :8080, and MariaDB on :3306 (loopback-only).

Controllers depend on services, services own transaction boundaries and domain logic, and repositories are plain Spring Data JPA interfaces plus one hand-written Specification class (FrameSpecifications) for the search query. This is a standard layered boundary inside one Maven module — not something a microservices framework imposes, and not a separate deployable per layer. The frame package is the single bounded context; web, observability, config, and health are cross-cutting concerns that sit outside it.

Actual vs. originally-suggested infrastructure

The original exercise's docker-compose.yml was explicitly a starting point, not a requirement, and explicitly told candidates to pick one of two datastore options and delete the other. Here is what changed between the original file and the solution's file:

The original compose file said, in a comment above the service definitions: pick ONE of mongodb or mariadb-primary for domain data, and remove the one you don't use so the stack reflects the design actually built. MariaDB was picked because frames are structured, validated, relational data — a frame create/update needs an atomic multi-table write (the frame row plus its revision row), which is exactly what a relational database with real transactions gives for free and a document store does not give without extra coordination. That reasoning is recorded as the decision in ADR 0001. The backend's depends_on also tightened from a plain service-start dependency on three services to a condition: service_healthy gate on MariaDB alone, and a new backend healthcheck (curl against /actuator/health/readiness) means the frontend only starts once the backend is actually able to serve traffic, not merely running.

Why this reads as "boring" on purpose

One datastore, no message broker, no search engine, for a roughly 1,000-row inventory built in a one-day exercise. That is the deliberate shape, not a shortcut taken under time pressure. Later pages in this guide (What If: OpenSearch, What If: Kafka) explore exactly what would need to change if scale or requirements demanded a broker or a search index — but this page describes what was actually built and why that was the right call for the constraints given, not a claim that this is a settled-forever architecture.
