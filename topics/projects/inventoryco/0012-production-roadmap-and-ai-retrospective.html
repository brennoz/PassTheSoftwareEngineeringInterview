Production Scale-Up Roadmap & AI-Collaboration Retrospective

Prioritized production gaps · honest Entire/Codex checkpoint-capture account

This closing page has two unrelated jobs. First, it takes the README's flat "Current limitations" list and turns it into a prioritized production roadmap — what actually breaks first, and where the fix is already discussed elsewhere in this study guide. Second, it gives an honest account of the exercise's own required deliverable that was not met: the Entire checkpoints branch capturing the Codex sessions behind this solution. That gap is real, it is documented in the solution repo itself, and it is not glossed over here.

Production scale-up roadmap

Ordered by consequence, not by the order the README happens to list them in. Row 1 is most damaging because it blocks the application from being usable by more than one trusted person at all. Row 2 blocks a core delivered feature — CSV import — for any realistically large file, not just at extreme scale. Row 3 ranks above row 4 deliberately: a single-instance deployment is a hard availability failure mode — any one container crashing takes the whole app down for every user, regardless of load — while row 4's search limitation is a README-declared intentional scope decision that degrades gradually as the catalogue grows, not a defect present today. An outright single point of failure outranks a deliberately-scoped feature limitation. Row 5 is least damaging because it isn't a confirmed problem at all — it's an open question, flagged honestly rather than papered over with an invented number.

What Entire was supposed to capture

The original exercise instructions (INSTRUCTIONS.md §5, "Additional Requirements") are specific about what the Entire CLI is for:

INSTRUCTIONS.md §5 "Entire hooks into the candidate's git workflow and, on every push, captures the Codex agent sessions that produced the changes and links them to the corresponding commits as checkpoints. The result is a searchable record of how the solution was actually built: the prompts used, the iterations the candidate went through, the suggestions they accepted, and — just as important — the ones they rejected or refined."

§6, "Submission," makes this a hard requirement of what gets handed back, not an optional nicety:

INSTRUCTIONS.md §6 The public repository must include "The Entire checkpoints branch with the captured Codex sessions linked to commits, so we can review the AI collaboration alongside the code."

What actually happened

It did not happen. The implementation journal's own "Entire outcome" section states this without hedging:

implementation-journal.md — Entire outcome "Entire installed repository settings, Codex lifecycle-hook declarations, and local Git hooks. However, the Codex hooks were not trusted in the client used during implementation, so no session became active and no checkpoint was linked to a commit. Consequently:
— entire checkpoint list reports zero checkpoints on main.
— Existing commits contain no Entire-Checkpoint trailers.
— The remote exposes no entire/checkpoints/v1 branch.
— The earlier sessions cannot be reconstructed as a genuine Entire transcript."

This is not a minor detail to smooth over. The exercise instructions frame Entire capture as the mechanism for judging "how the candidate works with AI tooling," and the submission requirement names the checkpoints branch explicitly as something the reviewer needs "to review the AI collaboration alongside the code." A submission with zero checkpoints, no trailers, and no remote checkpoints branch is a real, documented shortfall against that explicit assessment criterion — not a cosmetic gap. Stating it plainly here is more useful than burying it in a limitations footnote.

The substitute evidence that does exist

What survives instead is the git history itself, plus two curated retrospective documents reconstructed after the fact — the implementation journal and the conversation record. Neither claims to be a verbatim session transcript; both say so directly. The most fact-checkable artifact of the three is the commit timeline, reproduced here exactly as it appears in implementation-journal.md:

Why this is a real, if imperfect, substitute signal: the gate structure itself — implement, stop, provide manual verification steps, wait for approval, only then commit — is direct evidence of a review discipline independent of whether Entire recorded it. More concretely, two commits are explicitly labelled as review-fix gates rather than feature gates: 43c9b39 ("Gate 2 review fixes") and 714d2e4 ("Gate 3 review fixes"). Each exists only because a separate review pass found boundary issues in the preceding feature commit and those issues were fixed and re-committed on their own, rather than folded silently into the original. That is direct evidence of AI-generated output being reviewed and corrected, not accepted wholesale — exactly the signal Entire was meant to make searchable, just captured the harder way, through the commit graph instead of a checkpoint transcript.

If doing this again

The implementation journal does not just note the failure — it states what capture actually requires next time, and that guidance should be quoted exactly rather than paraphrased:

implementation-journal.md — Entire outcome "Future capture requires starting the interactive Codex CLI from this repository, approving the project hooks there, confirming entire doctor is clean, and accepting checkpoint linkage when committing. Because the repository is public, any pushed checkpoint transcript should be reviewed for sensitive information first."

The conversation record adds the specific root cause behind why approval never happened: the four Codex lifecycle hooks — SessionStart, UserPromptSubmit, PostToolUse, and Stop — require interactive approval through /hooks inside the Codex terminal UI, and the session instead ran through an app/chat surface where that approval prompt was never reachable. The fix is procedural, not architectural: start the next session from the interactive Codex CLI, approve the hooks before the first commit, and verify with entire doctor before doing any real work.

Across twelve pages it followed one solution from its actual architecture (page 0001) through domain model, CRUD, audit history, search, and CSV import, into two deliberately counterfactual "what if" detours (OpenSearch, Kafka) that exist to show where the real design choices would change, and finally back to what remains unfinished and what the AI-collaboration record does and does not show. The throughline was the same on every page: verify every claim against the actual source before writing it down, including — especially — the parts that are not flattering.
