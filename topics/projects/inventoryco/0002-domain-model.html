Domain Model

Frame entity · FrameData value object · legacy CSV mapping decisions

INSTRUCTIONS.md §4 describes the legacy export in six loose groupings and is explicit that "the legacy column names and groupings are not prescriptive" — the candidate is meant to design the model that best fits the four features in §3 (add/update, search, CSV bulk upload, history), not mirror the CSV 1:1. The table below checks the solution's actual Frame.java field list against that brief, grouping by grouping.

Reading the gaps honestly

Every "dropped" field above is a field data/inventory_frame.csv's header row actually contains (verified against the real CSV: frame_id, type_classic_digital, format, environment, created_date, modified_date, postcode, site_no, inventory_site_no, location, postcode_area, postcode_district, postcode_sector, postcode_unit, address, region, country_code, town, illumination_type_id, number_of_slots, status, status_reason, longitude, latitude, distance_to_closest_school, panel_number, station, size_code, size_group_code, impact_weight, production_rate_card, airport, price_entity_id, broadsign_display_unit_id, broadsign_frame_id, broadsign_domain_id, linked_frame_ids, aspect_ratio_code, pixel_height, pixel_width, location_id, t_size, premium, production_rate_card_legacy, pricing_grade). The CSV import feature (page 0006) still has to parse and either map or ignore these columns row by row — the domain model's job is to decide which of them earn a place in Frame/FrameData, and this table is the record of that decision.

The Frame entity

Frame is the JPA aggregate root — it has identity (frameId) and a lifecycle (created, updated, versioned). Its field block:

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/Frame.java:14-90
@Entity
@Table(name = "frames")
public class Frame {

    @Id
    @Column(name = "frame_id", length = 64, nullable = false, updatable = false)
    private String frameId;

    @Enumerated(EnumType.STRING)
    @Column(name = "media_type", length = 16, nullable = false)
    private MediaType mediaType;

    @Column(name = "format", length = 100, nullable = false)
    private String format;

    @Enumerated(EnumType.STRING)
    @Column(name = "environment", length = 32, nullable = false)
    private FrameEnvironment environment;

    @Column(name = "site_number", length = 64)
    private String siteNumber;

    @Column(name = "station", length = 150)
    private String station;

    @Column(name = "address", length = 500)
    private String address;

    @Column(name = "region", length = 100)
    private String region;

    @Column(name = "country_code", length = 8, nullable = false)
    private String countryCode;

    @Column(name = "town", length = 150)
    private String town;

    @Column(name = "postcode", length = 16)
    private String postcode;

    @Column(name = "longitude", precision = 11, scale = 8)
    private BigDecimal longitude;

    @Column(name = "latitude", precision = 10, scale = 8)
    private BigDecimal latitude;

    @Enumerated(EnumType.STRING)
    @Column(name = "status", length = 32, nullable = false)
    private FrameStatus status;

    @Column(name = "status_reason", length = 255)
    private String statusReason;

    @Column(name = "number_of_slots")
    private Integer numberOfSlots;

    @Column(name = "distance_to_closest_school")
    private Integer distanceToClosestSchool;

    @Column(name = "pixel_height")
    private Integer pixelHeight;

    @Column(name = "pixel_width")
    private Integer pixelWidth;

    @Column(name = "premium", nullable = false)
    private boolean premium;

    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;

    @Version
    @Column(name = "version", nullable = false)
    private long version;

frameId is a natural key (a String, not a generated UUID/surrogate) because the legacy system already assigns stable, meaningful frame identifiers — reusing them keeps CSV bulk-import round-trips (import → export → re-import) referencing the same ID instead of minting a parallel identity scheme the legacy system knows nothing about.

updatable = false on frameId enforces immutability at the JPA mapping level, not just by convention or by omitting a setter — Hibernate will not include that column in any generated UPDATE statement even if something upstream mistakenly tries to change it, so the guarantee holds regardless of what application code does above the persistence layer.

@Version wires JPA's built-in optimistic-locking column: every UPDATE Hibernate issues includes a WHERE version = ? check and bumps the value, so a write against a stale row fails instead of silently overwriting a concurrent edit. The full mechanics — how a stale write surfaces as StaleFrameVersionException and a 409 — are covered in depth in the next page, "Frame CRUD & Optimistic Concurrency"; here it's enough to know what the field is for.

FrameData — the value object that makes diffing possible

Frame (the JPA entity) and FrameData (a plain record) are deliberately two separate types carrying largely the same fields. Frame has identity and a lifecycle; FrameData has neither — it's an immutable snapshot of "everything about a frame except which frame it is and when it changed."

Notice the field list is the same "domain" subset of Frame minus frameId, createdAt, updatedAt, and version — exactly the fields that belong to identity/lifecycle stay on Frame, and everything a caller could legitimately want to change in one edit lives on FrameData. Also note premium is boxed (Boolean) here versus primitive (boolean) on Frame — a record field can be null mid-construction from a partially-filled CSV row or request DTO in a way the entity's persisted column never should be.

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/Frame.java:95-141
public static Frame create(String frameId, FrameData data, Instant now) {
    Frame frame = new Frame();
    frame.frameId = frameId;
    frame.apply(data);
    frame.createdAt = now;
    frame.updatedAt = now;
    return frame;
}

public List<FrameFieldChange> update(FrameData data, Instant now) {
    List<FrameFieldChange> changes = data.changesFrom(data());
    if (!changes.isEmpty()) {
        apply(data);
        updatedAt = now;
    }
    return changes;
}

public FrameData data() {
    return new FrameData(
        mediaType, format, environment, siteNumber, station, address, region, countryCode,
        town, postcode, longitude, latitude, status, statusReason, numberOfSlots,
        distanceToClosestSchool, pixelHeight, pixelWidth, premium
    );
}

private void apply(FrameData data) {
    mediaType = data.mediaType();
    format = data.format();
    environment = data.environment();
    siteNumber = data.siteNumber();
    station = data.station();
    address = data.address();
    region = data.region();
    countryCode = data.countryCode();
    town = data.town();
    postcode = data.postcode();
    longitude = data.longitude();
    latitude = data.latitude();
    status = data.status();
    statusReason = data.statusReason();
    numberOfSlots = data.numberOfSlots();
    distanceToClosestSchool = data.distanceToClosestSchool();
    pixelHeight = data.pixelHeight();
    pixelWidth = data.pixelWidth();
    premium = data.premium();
}

data() and apply() are the two directions of the round trip: data() reads the entity's current column values into a fresh FrameData snapshot (entity → value), and apply() writes a FrameData's values back onto the entity's fields (value → entity). Neither method touches anything JPA-specific — no @Version, no frameId, no Instant timestamps.

That separation is what makes update() work: it calls data.changesFrom(data()) — comparing the incoming FrameData against a snapshot of the entity's current state — entirely as two plain records being diffed field-by-field, with no Hibernate session, no database round trip, and no risk of the comparison itself triggering a lazy load or a dirty-checking side effect. changesFrom()'s own mechanics (how each FrameFieldChange becomes an audit revision row) are covered in depth in the later "Audit History" page — flagged here only as the reason this two-type split exists in the first place.

Enums

Three fields are modelled as closed Java enums rather than free strings, each backed by @Enumerated(EnumType.STRING) on Frame.

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/FrameStatus.java:3-8
public enum FrameStatus {
    LIVE,
    PENDING,
    MAINTENANCE,
    BLOCKED
}

Drives the "Lifecycle" grouping from §4 — a frame's status is the field the audit-history feature (§3 feature 4) most exists to track, since status transitions are the changes an inventory operator most needs a trail for.

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/FrameEnvironment.java:3-8
public enum FrameEnvironment {
    UNDERGROUND,
    RAIL,
    ROADSIDE,
    AIRPORT
}

This is the out-of-home (OOH) site-type classification straight out of §4's "Site & position" grouping ("station, underground, roadside, airport, etc.") — closing it to a fixed enum rather than a free-text CSV column also makes it usable as an exact-match search filter (page 0005) and gives closed-set validation on any future or unknown input, rather than silently accepting whatever string a caller sends.

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/MediaType.java:3-6
public enum MediaType {
    CLASSIC,
    DIGITAL
}

The classic-vs-digital split called out explicitly in §4's "Format" grouping. It's the field that determines whether pixelHeight/pixelWidth are meaningful for a given frame (a classic paste-up panel has no pixel dimensions; a digital screen does) — the model doesn't enforce that correlation, but it's the reason both fields stay nullable on Frame.
