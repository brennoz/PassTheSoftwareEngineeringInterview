What If: OpenSearch for Search

Counterfactual · explicitly not what was built · see CLAUDE.md
This is not what was built

OpenSearch and OpenSearch Dashboards were present in the original suggested docker-compose.yml for this exercise, alongside MariaDB and MongoDB, and were deliberately removed. The actual solution runs on MariaDB alone, with search implemented as a JPA Specification over case-insensitive SQL LIKE — see the Search page for the real implementation. Everything below is a "what if scale, fuzzy matching, or geospatial discovery became material" exploration, in the exact words of docs/adr/0001-relational-persistence-and-sql-search.md's closing line. Nothing on this page exists in the codebase.

What would actually change in the code

The current search path is one call: FrameQueryService.search() hands a query string and three exact-match filters to FrameSpecifications.matching(), which builds a single JPA Specification and MariaDB does the rest in one round trip. The free-text branch of that specification OR's a case-insensitive LIKE across exactly seven fields — frameId, siteNumber, station, address, town, postcode, format (see Search for the full breakdown). Introducing OpenSearch means FrameQueryService would gain an OpenSearch client call for the free-text portion of a search — the query parameter, against those same seven fields re-indexed as an OpenSearch document — while the status/environment/mediaType exact-match filters have a real choice to make: stay as MariaDB predicates, or move into the OpenSearch query as term filters.

OptionTrade-off
OpenSearch does everything — text and the three exact-match filters, in one query DSL request One round trip, one result set, no merging logic. But every filter combination that exists today in FrameSpecifications has to be re-implemented against OpenSearch's query DSL (term filters, bool queries) instead of Criteria API predicates — the filtering logic effectively lives twice, once conceptually and once as two different query languages, and any future filter has to be added in the DSL, not just the specification.
OpenSearch does only free text; MariaDB still applies status/environment/mediaType and remains the source of result data Smaller blast radius — FrameSpecifications' exact-match predicates are untouched, only the free-text branch of matching() is replaced by an OpenSearch lookup that returns matching frame IDs, then MariaDB filters/paginates/fetches within that ID set. But now there are two queries to combine (an ID-list intersection or an IN clause), and pagination has to be coordinated across both instead of relying on a single Pageable.

Either way, this is additive to the existing relational model, not a replacement of it — ADR 0001 is explicit that a search projection "can be added without replacing MariaDB as the source of truth."

Why NOT a naive dual-write

The obvious-looking approach is to write to MariaDB and then write to OpenSearch in the same request handler — inside the same FrameCommandService method that creates or updates a Frame. That's wrong, because the two writes are not atomic. They're two separate systems with two separate commit protocols, and nothing ties their success together:

illustrative pseudocode — not from the codebase
frameRepository.save(frame);        // MariaDB transaction commits here
// --- process crashes / times out / OpenSearch is unreachable here ---
openSearchClient.index(frame);      // never runs

If the process dies, the pod is killed, or the OpenSearch call simply times out anywhere after the MariaDB commit, the relational row exists but the search index entry never gets created. Nothing detects this — there's no automatic reconciliation, no retry, no error surfaced to a caller (the HTTP response for the original write may well have already returned 200 before the second call even runs). MariaDB and the OpenSearch index now silently disagree, and they stay disagreeing until something notices — a customer searching for a frame that demonstrably exists but doesn't show up in results, discovered by accident rather than by any system-level signal.

The outbox-based alternative

This does not exist in the actual solution. It's a sketch of the pattern ADR 0001 names by name in its closing line: "That projection should be populated through a transactional outbox rather than dual writes."

  1. The same transaction that writes a Frame and its FrameRevision today would also insert a row into a new outbox_events table — frame ID, event type (e.g. FRAME_CREATED, FRAME_UPDATED), a payload, and a nullable processed_at column. All three writes — Frame, FrameRevision, outbox_events — commit atomically, because they're the same database transaction against the same MariaDB instance. There is no window where one exists and the others don't.
  2. A separate poller/projector process — not part of the request path, running independently — reads unprocessed outbox_events rows (processed_at IS NULL), indexes each one into OpenSearch, and marks it processed once the index write succeeds.
  3. If the projector crashes mid-batch, the unprocessed rows are simply retried on restart: processed_at is still NULL for anything it didn't finish, so the next run picks them up again. That gives at-least-once delivery into the search index — a row might get indexed twice, which is safe because indexing is idempotent by frame ID, but it can never be silently lost the way the dual-write's second step could be. MariaDB stays the single source of truth throughout; OpenSearch is a derived, eventually-consistent projection of it, never authoritative on its own.

When this would actually be justified

Nothing here is "OpenSearch is more sophisticated, therefore better" — that's not a justification the ADR makes, and it isn't one to invent. The concrete triggers, grounded in ADR 0001's own language, are:

  • Fuzzy / typo-tolerant matching. The current LIKE '%query%' approach requires an exact substring — a misspelled station name or postcode simply won't match. OpenSearch's text analysis (edit-distance fuzziness, tokenization, stemming) handles that class of query natively; SQL LIKE cannot.
  • Geospatial "frames near this point" queries. The domain model already carries longitude/latitude as BigDecimal fields on every frame (see Domain Model) — but nothing today queries on them; search is purely substring text. "Show frames within 500m of this location" is a geo-distance query, a first-class OpenSearch query type with a dedicated geo-point index; doing the equivalent in SQL means either a bounding-box approximation or reaching for a database extension MariaDB doesn't ship with by default.
  • A dataset size where the leading-wildcard scan becomes measurable. ADR 0001 is explicit that LIKE '%query%' "cannot fully use ordinary B-tree indexes and may scan as data grows" — see the Search page's breakdown of why a leading wildcard defeats a B-tree. At the ~1,000-row scale this solution targets, that full scan costs nothing worth optimizing for. If the inventory grew by orders of magnitude and search latency became measurable and user-visible, that's the point the trade-off actually flips — not before.
