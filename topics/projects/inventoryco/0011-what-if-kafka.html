What If: Kafka & Event-Driven Patterns

Counterfactual · explicitly not what was built · see CLAUDE.md
This is not what was built

Kafka was never part of the original suggested docker-compose.yml for this exercise — unlike MongoDB and OpenSearch, which were present in that file (alongside MariaDB) and deliberately removed by the actual solution, Kafka never appeared in the suggested stack at all. There was nothing to remove. The original INSTRUCTIONS.md does mention a "message broker" — but only generically, as one example in a list of infrastructure the candidate was free to swap in: "The candidate is free to swap any of these services for tooling they prefer (a different database, search engine, message broker, hosting model, etc.)." It names the category, not Kafka specifically, and the candidate was never nudged toward introducing one. The actual solution runs entirely without a broker: CSV import is a synchronous request (see CSV Import and ADR 0002) and revisions are written in the same transaction as the frame they describe (see Audit History and ADR 0003) — no queue, no consumer, no asynchronous hop anywhere in the request path. Everything below is a "what if this needed to decouple or scale asynchronously" exploration, grounded in ADR 0002's own closing lines. Nothing on this page exists in the codebase.

Where it would go #1: async CSV import

ADR 0002's closing line names the shape directly: "A future large-volume design should persist an import job, publish it through a transactional outbox, process bounded batches asynchronously, and expose progress and retry state." That's a design sketch, not a design — here is what it would concretely mean for FrameImportService:

  1. POST /api/frames/import would, in one transaction, write an import_job row (status=PENDING, filename, row count) and an outbox event — then return 202 Accepted with the job ID immediately, instead of the current design's behaviour of holding the request open for the whole file. ADR 0002 names that current behaviour directly in its Consequences: "Request duration grows with row count and the client must remain connected" — that's exactly the constraint this design removes. The synchronous, whole-request nature of today's import is covered on the CSV Import page, though the request-duration consequence itself is ADR 0002's framing, not that page's.
  2. A consumer would pick up the outbox event, read the stored file, and process rows in bounded batches — reusing the exact same per-row REQUIRES_NEW upsert logic already covered on the Frame CRUD & Optimistic Concurrency page's "CSV upsert path" section. The batching unit changes — a background consumer working through chunks instead of one HTTP thread walking the whole file — but the upsert mechanism itself (upsertImportedFrame(), one row, one independent transaction, three failure types counted rather than fatal) would not need to change at all.
  3. Job status and progress would be queryable via GET /api/frames/import/{jobId}, replacing the current design's single synchronous response with a pollable resource — the aggregate counts (created/updated/unchanged/ failed) and the truncated error list from CSV Import's "Bounded, honest error reporting" section would live on that resource instead of in one final response body.
  4. A stuck or crashed consumer could resume from the last committed batch rather than the client having to re-upload and restart the whole file from row one.

Step 1's transaction, sketched out, is the same shape as the outbox write on the OpenSearch page — one more row alongside the domain write, committed atomically because it's the same database transaction:

illustrative pseudocode — not from the codebase
@Transactional
public ImportJobResponse startImport(MultipartFile file) {
    ImportJob job = ImportJob.pending(file.getOriginalFilename(), countRows(file));
    importJobRepository.save(job);                                   // import_job row
    outboxRepository.save(OutboxEvent.of(job, "IMPORT_JOB_CREATED", storeFile(file)));
    return ImportJobResponse.accepted(job.getId());                  // both rows committed together
}                                                                     // controller returns 202

import_job and outbox_events commit or roll back together because they're the same transaction against the same MariaDB instance — there is no window where a job record exists without a corresponding outbox event, or vice versa. The controller returns 202 Accepted as soon as this method returns, not after the file has actually been processed; the consumer described in step 2 above does that part later, out of band, reading the outbox row this method wrote.

The honest trade-off, named directly rather than glossed over: this adds a job-state table, a consumer process, and a polling or WebSocket UX for progress — real, ongoing operational complexity. ADR 0002 explicitly judged that not worth paying for a 5,000-row / 2 MB bound that completes synchronously in seconds: "At this scale, background infrastructure would add operational and consistency costs without improving the user workflow." Everything in this section is what would flip that judgement, not a claim that it should flip today.

Where it would go #2: revision fan-out

Audit History already covers the actual mechanics: every Frame mutation computes a field-level diff via changesFrom() and, if that diff is non-empty, writes a FrameRevision (plus its child FrameRevisionChange rows) in the same database transaction as the frame update itself — no revision for a no-op, no window where one exists without the other. That mechanism isn't repeated here. What it enables, hypothetically, is fan-out: after that same transaction commits, an outbox row could carry the revision event onward to Kafka, letting downstream systems consume frame changes as they happen instead of polling the frames API for them. INSTRUCTIONS.md §1 names exactly the systems that would plausibly want that feed — "every downstream process (planning, pricing, booking, reporting) depends on" the inventory being accurate.

Worth naming explicitly: this reuses the identical outbox mechanism already sketched on the What If: OpenSearch for Search page — the same transaction that writes the domain row also writes one more row into an outbox_events table, and a separate process reads unprocessed rows and delivers them onward, retrying safely on crash because delivery is idempotent and at-least-once rather than exactly-once. One additional table, one pattern, two different consumers of it: a search projector reading the outbox to keep OpenSearch in sync, and a Kafka publisher reading the same kind of outbox row to keep downstream systems in sync. Same problem shape — "reliably get an event out of a transaction that already committed" — solved once.

"A broker alone would not make the write atomic"

ADR 0002's exact words: "A broker alone would not make the database write and message publish atomic." Expanded: publishing directly to Kafka from inside the same code path that writes the database row has the identical dual-write problem the OpenSearch page walks through for a naive frameRepository.save(frame); openSearchClient.index(frame); sequence — two separate systems, two separate commit protocols, and nothing tying their success together. A crash between the DB commit and the Kafka publish either loses the event entirely (if the crash lands after the commit but before the publish call) or risks double-publishing it (if a naive retry re-sends after a publish that actually succeeded but whose acknowledgement was lost) — which failure mode you get depends on exactly where the crash lands and how retries are implemented, and neither is something application code can reliably avoid by being more careful with try/catch blocks.

The outbox table is what turns "publish an event" into "write one more row in the same transaction." That row commits or rolls back atomically with the Frame and FrameRevision rows it describes, because it's the same MariaDB transaction — no network call, no second system, nothing that can succeed independently of the write it's supposed to describe. The Kafka publish itself happens later, out of band, driven by a separate consumer reading unprocessed outbox rows — which is exactly why it can be retried safely without threatening the atomicity of the original write.

What wasn't reached for, and why that's fine

Worth closing on what a broker would not have fixed here, because it's easy to read a "what if Kafka" page as implying Kafka is a missing piece. It isn't, for this build. A broker would not have fixed the correctness of the per-row upsert logic — that's optimistic locking: the @Version check and the ObjectOptimisticLockingFailureException catch that closes the race between two concurrent writers of the same frame. It would not have fixed search relevance — that's the OpenSearch page's subject, a text-analysis and query-capability problem, not a decoupling problem. Kafka solves asynchronous decoupling: letting a producer and a consumer of the same event not have to be up, fast, or even alive at the same moment. At this exercise's actual scale — 5,000-row-bounded CSV files completing synchronously in seconds, a single-instance deployment, no real downstream consumers actually waiting on a frame-change feed — there was no decoupling problem yet to solve. That's not a gap in the solution; it's ADR 0002's trade-off working as intended.
