API Contracts, Error Handling & Observability

RFC 9457 ProblemDetail · request correlation · readiness · container hardening

The Frame CRUD page introduced Frame.version and StaleFrameVersionException, and deferred one question: how does a plain RuntimeException subclass with no HTTP annotations actually turn into a 409 Conflict on the wire? The answer is a single class, ApiExceptionHandler, which every controller in the app shares.

ProblemDetail, not ad-hoc error JSON

RFC 9457 ("Problem Details for HTTP APIs") standardizes one JSON shape for error responses: type (a URI identifying the problem category), title (a short human-readable summary), status (the HTTP status code, repeated in the body), detail (specifics for this occurrence), and instance (optionally, which request triggered it). Spring's ProblemDetail class is a typed builder for exactly that shape. The alternative — each controller method catching its own exceptions and hand-rolling a JSON error map — means every endpoint can drift to a slightly different field name or status convention. A single @RestControllerAdvice class instead maps every exception type the app throws to a consistent problem body once, and every controller gets it for free without importing anything.

src/backend/src/main/java/com/global/ct/frameinventory/web/ApiExceptionHandler.java:27-67
    @ExceptionHandler(FrameNotFoundException.class)
    ProblemDetail handleNotFound(FrameNotFoundException exception) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, exception.getMessage());
        problem.setTitle("Frame not found");
        problem.setType(URI.create("urn:problem:frame-not-found"));
        return problem;
    }

    @ExceptionHandler(DuplicateFrameException.class)
    ProblemDetail handleDuplicate(DuplicateFrameException exception) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, exception.getMessage());
        problem.setTitle("Frame already exists");
        problem.setType(URI.create("urn:problem:duplicate-frame"));
        return problem;
    }

    @ExceptionHandler({StaleFrameVersionException.class, ObjectOptimisticLockingFailureException.class})
    ProblemDetail handleStaleVersion(RuntimeException exception) {
        String detail = exception instanceof StaleFrameVersionException
            ? exception.getMessage()
            : "The frame was modified by another request; reload it and try again";
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, detail);
        problem.setTitle("Frame was modified");
        problem.setType(URI.create("urn:problem:stale-frame-version"));
        return problem;
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail handleInvalidFrame(MethodArgumentNotValidException exception) {
        Map<String, String> errors = new LinkedHashMap<>();
        exception.getBindingResult().getFieldErrors().forEach(error ->
            errors.putIfAbsent(error.getField(), error.getDefaultMessage())
        );
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST, "One or more frame fields are invalid"
        );
        problem.setTitle("Invalid frame");
        problem.setType(URI.create("urn:problem:invalid-frame"));
        problem.setProperty("errors", errors);
        return problem;
    }

This confirms the page 0003 deferral directly: StaleFrameVersionException is caught by handleStaleVersion alongside Spring Data's own ObjectOptimisticLockingFailureException (the exception JPA throws natively when an @Version mismatch is detected at flush time — the app's own exception is thrown from a narrower, more deliberate check earlier in FrameCommandService, but both paths converge on the same handler and the same status). Both become 409 Conflict. Note that DuplicateFrameException is also 409, not 400 — Spring Data-flavoured REST conventions treat "this ID already exists" as a conflict with existing state, not a malformed request. Validation failures (MethodArgumentNotValidException, thrown by @Valid on the request body) become 400 Bad Request with a errors property mapping each invalid field to its message — a shape the frontend can render directly next to each form field without string-parsing a generic detail message.

Request correlation

Every request gets a request ID: the caller's own X-Request-ID header if it's present and matches a safe pattern, otherwise a freshly generated UUID. Either way the ID goes onto the response header and into SLF4J's MDC (Mapped Diagnostic Context) so every log line the request produces — anywhere in the call stack, not just in this filter — carries it automatically via the logging pattern's %X{requestId}.

src/backend/src/main/java/com/global/ct/frameinventory/observability/filter/RequestObservabilityFilter.java:24-56
    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String requestId = requestId(request.getHeader(REQUEST_ID_HEADER));
        response.setHeader(REQUEST_ID_HEADER, requestId);
        MDC.put(REQUEST_ID_MDC_KEY, requestId);
        long startedAt = System.nanoTime();

        try {
            filterChain.doFilter(request, response);
        } finally {
            long durationMillis = (System.nanoTime() - startedAt) / 1_000_000;
            logRequest(request, response, durationMillis);
            MDC.remove(REQUEST_ID_MDC_KEY);
        }
    }

    private String requestId(String suppliedRequestId) {
        if (suppliedRequestId != null && SAFE_REQUEST_ID.matcher(suppliedRequestId).matches()) {
            return suppliedRequestId;
        }
        return UUID.randomUUID().toString();
    }

    private void logRequest(HttpServletRequest request, HttpServletResponse response, long durationMillis) {
        if (request.getRequestURI().startsWith("/actuator/health")) {
            LOGGER.debug("HTTP request method={} path={} status={} durationMs={}",
                request.getMethod(), request.getRequestURI(), response.getStatus(), durationMillis);
            return;
        }
        LOGGER.info("HTTP request method={} path={} status={} durationMs={}",
            request.getMethod(), request.getRequestURI(), response.getStatus(), durationMillis);
    }

Confirmed directly from the code, not just the README: a client-supplied ID is only trusted if it matches SAFE_REQUEST_ID (letters, digits, ., _, -, 1–64 chars) — an attacker can't inject a newline or a log-forging payload through this header and have it echoed straight into the log line. Every log line records method, path (via getRequestURI() — the path only, no query string), status, and durationMs; the request ID itself isn't in the log message text because it's already in the MDC and therefore already in every line's prefix (the application.yml logging pattern is "%5p [requestId=%X{requestId:-}]"). What's deliberately absent: request or response bodies, and query parameter values — logRequest never touches either. Health-check traffic under /actuator/health logs at DEBUG instead of INFO, so a 10-second polling interval from Compose's healthcheck doesn't flood production logs at normal levels.

Readiness vs. liveness

Liveness answers one question: is the process alive and its main loop still responding — not deadlocked, not stuck? Readiness answers a different, stricter question: can this specific instance actually serve a real request right now, including everything it depends on? A JVM can be perfectly alive while its database connection pool is exhausted or MariaDB itself is still starting — liveness would say "fine," readiness should say "not yet."

src/backend/src/main/java/com/global/ct/frameinventory/health/controller/HealthController.java:11-24
@RestController
@RequestMapping("/api")
@CrossOrigin(origins = "*")
public class HealthController {

    @GetMapping("/health")
    public Map<String, Object> health() {
        return Map.of(
            "status", "UP",
            "service", "frame-inventory-backend",
            "timestamp", Instant.now().toString()
        );
    }
}

This is not the readiness probe — it's a separate, deliberately CORS-open (@CrossOrigin(origins = "*")) endpoint at /api/health, distinct from the Actuator's /actuator/... namespace, sized for a browser client to poll and confirm basic connectivity. It answers "is the backend reachable at all," with no dependency check — closer to a liveness signal than a readiness one, and it never claims to be more than that.

src/backend/src/main/resources/application.yml:25-36
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState,db
  endpoints:
    web:
      exposure:
        include: health,info

The actual readiness probe, /actuator/health/readiness, comes from Spring Boot Actuator, not from application code — this configuration is what makes it real. probes.enabled: true turns on the Kubernetes-style /actuator/health/liveness and /actuator/health/readiness groups; the readiness group is then explicitly widened past the bare readinessState availability flag to also include: ... db — a live connection check against MariaDB via the configured DataSource. That's why the Compose healthcheck shown on the Architecture Overview page (page 0001) targets /actuator/health/readiness specifically rather than /actuator/health or a liveness endpoint: it needs the frontend to wait not just for the JVM to boot, but for the backend to actually be able to talk to the database before Compose reports it healthy and lets dependent services start. endpoints.web.exposure.include: health,info is its own small hardening choice — only those two Actuator endpoints are exposed over HTTP at all, not the full default set (env, beans, mappings, etc.) that would leak internal configuration detail.

Container hardening

Neither safeguard here claims production-grade container security — this is a local demo stack — but both are real, deliberate choices rather than defaults left untouched.

src/backend/Dockerfile:8-15
FROM eclipse-temurin:21-jre
WORKDIR /app
RUN groupadd --system app \
    && useradd --system --gid app --home-dir /app --shell /usr/sbin/nologin app
COPY --from=build --chown=app:app /workspace/build/libs/*.jar app.jar
USER app
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

This is the second stage of a multi-stage build — the first stage (eclipse-temurin:21-jdk, not shown here) compiles the jar with Gradle and never ships; the runtime image starts from the smaller JRE-only base and copies in just the built artifact. On top of that, a dedicated system group and user (app, no login shell) is created explicitly so the process does not run as the image's default root. The jar is chown'd to app:app at copy time and USER app switches the effective user before ENTRYPOINT runs — so a container escape or a dependency RCE inside the JVM doesn't hand an attacker root inside the container. Paired with the MariaDB port binding already shown on page 0001 (127.0.0.1:3306:3306, loopback-only rather than bound to all interfaces), the pattern across this stack is consistent: small, concrete safeguards sized to a local demo, not a claim of hardened production posture.
