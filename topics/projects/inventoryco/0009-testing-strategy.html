Testing Strategy

Why integration-heavy first · where unit tests were added · what was scoped out

Why integration tests first

The implementation journal states the reasoning directly, and it's worth quoting rather than paraphrasing:

docs/implementation-journal.md — Testing strategy

"Integration tests were emphasized initially because the highest-risk behavior crosses Spring MVC validation, transactions, JPA mappings, Flyway schema, MariaDB semantics, optimistic locking, and HTTP ProblemDetail responses. Testcontainers keeps those tests representative of the production database."

The mechanics live in a small shared base class. Every backend integration test that needs a real database extends it rather than repeating container setup:

src/backend/src/test/java/com/global/ct/frameinventory/DatabaseIntegrationTest.java:1-16
package com.inventoryco.ct.frameinventory;

import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.containers.MariaDBContainer;

public abstract class DatabaseIntegrationTest {

    @ServiceConnection
    static final MariaDBContainer<?> MARIA_DB = startMariaDb();

    private static MariaDBContainer<?> startMariaDb() {
        MariaDBContainer<?> container = new MariaDBContainer<>("mariadb:11.4");
        container.start();
        return container;
    }
}

This isn't the class-level @Testcontainers/@Container JUnit extension pattern — it's the newer Spring Boot 3.1+ style: @ServiceConnection on a manually-started static field. Spring Boot inspects the field, recognizes it's a MariaDBContainer, and auto-wires the container's JDBC URL, username, and password into the application context — no @DynamicPropertySource boilerplate needed. Because the field is static and the container starts once per JVM, every @SpringBootTest class that extends DatabaseIntegrationTest (like FrameControllerIntegrationTest below) shares the same running MariaDB 11.4 instance, keeping total suite runtime reasonable while still exercising the real engine.

One representative test from FrameControllerIntegrationTest shows what that buys. This test drives two concurrent updates against the same frame through MockMvc, using real virtual threads racing against the real database:

src/backend/src/test/java/com/global/ct/frameinventory/frame/controller/FrameControllerIntegrationTest.java:270-288
    @Test
    void allowsOnlyOneOfTwoConcurrentUpdatesWithTheSameVersion() throws Exception {
        CountDownLatch start = new CountDownLatch(1);
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var first = executor.submit(() -> performUpdateAfter(start, "Concurrent A"));
            var second = executor.submit(() -> performUpdateAfter(start, "Concurrent B"));
            start.countDown();

            assertThat(List.of(first.get(), second.get())).containsExactlyInAnyOrder(200, 409);
        }

        mockMvc.perform(get("/api/frames/FRAME-001/history"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$", hasSize(1)));
        mockMvc.perform(get("/api/frames/FRAME-001"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.station").value(anyOf(equalTo("Concurrent A"), equalTo("Concurrent B"))))
            .andExpect(jsonPath("$.version").value(1));
    }

Two virtual threads wait on a shared latch, then both fire a PUT against the same frame at version 0 the instant it releases. The assertion is that exactly one request wins (HTTP 200) and the other loses (HTTP 409 from the optimistic-lock conflict), only one history revision gets written, and the surviving frame is at version 1 with whichever station name actually committed.

A mocked-repository unit test could not have exercised this. With a mocked JpaRepository, the test author would have to script the mock's behavior for each call — decide in advance which invocation "wins" and stub the exception on the other — which only proves that FrameCommandService's flush-catch block rethrows ObjectOptimisticLockingFailureException as StaleFrameVersionException, or (mocking one layer up) that the centralized ApiExceptionHandler's @ExceptionHandler maps that exception to a 409. Neither confirms the real @Version check-and-increment is actually atomic under genuine concurrent MariaDB transactions — that two real connections racing a real UPDATE ... WHERE version = ? against the real frames table really does serialize into exactly one winner. That's a lost-update race condition, and only a real database enforcing the version predicate at commit time can confirm it's closed.

Where focused unit tests made more sense

Not every test needs a database. The CSV import row-count guard is validated purely in-memory, with Mockito standing in for both collaborators:

src/backend/src/test/java/com/global/ct/frameinventory/frame/service/FrameImportServiceTest.java:48-55
    @Test
    void rejectsMoreThanFiveThousandRowsBeforeWritingAnyFrame() {
        assertThatThrownBy(() -> importService.importCsv(csvWithRows(5_001)))
            .isInstanceOf(InvalidCsvException.class)
            .hasMessageContaining("5,000");

        verifyNoInteractions(commandService);
    }

FrameCsvMapper and FrameCommandService are both @Mocks here — FrameImportServiceTest never spins up a Spring context or a container. The test builds a 5,001-row CSV in memory and asserts importCsv throws InvalidCsvException before a single row reaches commandService, confirmed by verifyNoInteractions(commandService). That's exactly the shape of behavior that doesn't benefit from Testcontainers: the 5,000-row cap is evaluated by counting CSV records before any persistence call is made, so a real MariaDB instance would add container startup latency to every test run without adding any confidence — there's no database interaction on this code path to verify.

Frontend testing

On the frontend, component tests cover rendering and API-client interaction without a running backend. CreateFramePage.test.tsx mocks the API module wholesale and drives the form through Testing Library:

src/frontend/src/pages/CreateFramePage.test.tsx:1-35
import { fireEvent, render, screen } from '@testing-library/react'
import { MemoryRouter, Route, Routes } from 'react-router-dom'
import { describe, expect, it, vi } from 'vitest'
import { createFrame } from '../api/frames'
import { ApiError } from '../api/http'
import { CreateFramePage } from './CreateFramePage'

vi.mock('../api/frames', () => ({ createFrame: vi.fn() }))

describe('create frame', () => {
  it('exposes required fields to assistive technology', () => {
    render(<MemoryRouter initialEntries={['/frames/new']}><Routes><Route path="/frames/new" element={<CreateFramePage />} /></Routes></MemoryRouter>)

    expect(screen.getByLabelText(/^Frame ID/)).toBeRequired()
    expect(screen.getByLabelText(/^Media type/)).toBeRequired()
    expect(screen.getByLabelText(/^Format/)).toBeRequired()
    expect(screen.getByLabelText(/^Environment/)).toBeRequired()
    expect(screen.getByLabelText(/^Status \*/)).toBeRequired()
    expect(screen.getByLabelText(/^Country code/)).toBeRequired()
  })

  it('explains how to recover when the frame ID already exists', async () => {
    vi.mocked(createFrame).mockRejectedValue(new ApiError('Frame FRAME-1 already exists', 409, {
      title: 'Frame already exists', type: 'urn:problem:duplicate-frame',
    }))

    render(<MemoryRouter initialEntries={['/frames/new']}><Routes><Route path="/frames/new" element={<CreateFramePage />} /></Routes></MemoryRouter>)
    fireEvent.change(screen.getByLabelText(/Frame ID/), { target: { value: 'FRAME-1' } })
    fireEvent.change(screen.getByLabelText(/Format/), { target: { value: 'D6' } })
    fireEvent.click(screen.getByRole('button', { name: 'Create frame' }))

    expect(await screen.findByText('A frame with this ID already exists. Choose another ID.')).toBeInTheDocument()
    expect(createFrame).toHaveBeenCalledWith(expect.objectContaining({ frameId: 'FRAME-1', format: 'D6' }))
  })
})

Two things are covered together here, both without a backend process running. The first test renders CreateFramePage and checks that the required form fields (Frame ID, Media type, Format, Environment, Status, Country code) are exposed as required to assistive technology — an accessibility assertion, not a happy-path smoke test. The second mocks createFrame to reject with the same ApiError shape the real API client would surface for a 409 conflict, fills in the form, submits it, and asserts both that the specific recovery copy ("Choose another ID") renders and that the outgoing payload matched what the user typed. It's a component test plus an API-client-mocking test in one file — form behavior and error-message wiring verified in isolation from any server.

What was deliberately left out

The README is explicit that browser automation never happened:

README.md — Current limitations

"Frontend workflows have component tests and manual responsive verification, but no browser automation suite."

The journal frames this as a scoping decision tied to the exercise's time budget, not an oversight: "Browser automation remained out of scope for the one-day exercise; frontend workflows were covered by component tests, build/lint checks, and manual responsive verification." Playwright or Cypress end-to-end coverage would have added real value — catching regressions across the full render → API → MariaDB round trip in a real browser — but standing up and maintaining a browser-automation suite inside a single day was judged a worse use of the available time than deepening backend Testcontainers coverage and adding the frontend component/unit tests above. The gap is named directly rather than silently absent.
