Frame CRUD & Optimistic Concurrency

Create/update flow · JPA @Version · conflict handling · concurrent-write sequence diagram

The Domain Model page introduced Frame.version — a JPA @Version column — and deferred its mechanics here: how a stale write is actually caught, and what happens when two clients edit the same frame at the same time. All three write paths in this page live in FrameCommandService.

Create

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameCommandService.java:44-65
    @Transactional
    public FrameResponse create(CreateFrameRequest request) {
        if (frameRepository.existsById(request.frameId())) {
            throw new DuplicateFrameException(request.frameId());
        }

        Instant now = now();
        Frame frame = Frame.create(request.frameId(), request.toData(), now);
        try {
            frameRepository.saveAndFlush(frame);
        } catch (DataIntegrityViolationException exception) {
            throw new DuplicateFrameException(request.frameId());
        }

        List<FrameFieldChange> changes = new ArrayList<>();
        changes.add(new FrameFieldChange("frameId", null, frame.getFrameId()));
        changes.addAll(frame.data().changesFrom(null));
        revisionRepository.save(FrameRevision.record(
            frame, RevisionAction.CREATED, ChangeSource.MANUAL, MANUAL_ACTOR, now, changes
        ));
        return FrameResponse.from(frame);
    }

There are two separate defenses against the same duplicate-ID problem here, and only one of them is load-bearing. The existsById check (line 46) is a fast, readable early exit for the common case — it lets most duplicate-create attempts fail with a clean error before any write is attempted. But existsById-then-save is itself a check-then-act race: two concurrent create() calls for the same frameId can both pass the existsById check before either one has committed, because reading "does this row exist" and later writing it are not atomic with each other. The real guarantee is the database's own primary-key constraint on frame_id, surfaced here as the try/catch around saveAndFlush (lines 52-56): if both requests reach the insert, exactly one of them succeeds and the other gets a DataIntegrityViolationException, which this method translates back into the same DuplicateFrameException the fast-path check would have thrown. The existsById call is an optimization for the overwhelmingly common non-racing case, not the correctness mechanism — the unique constraint is.

Update and the version check

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameCommandService.java:67-90
    @Transactional
    public FrameResponse update(String frameId, UpdateFrameRequest request) {
        Frame frame = frameRepository.findById(frameId)
            .orElseThrow(() -> new FrameNotFoundException(frameId));
        if (frame.getVersion() != request.version()) {
            throw new StaleFrameVersionException(frameId);
        }

        Instant now = now();
        List<FrameFieldChange> changes = frame.update(request.toData(), now);
        if (changes.isEmpty()) {
            return FrameResponse.from(frame);
        }

        try {
            frameRepository.flush();
        } catch (ObjectOptimisticLockingFailureException exception) {
            throw new StaleFrameVersionException(frameId);
        }
        revisionRepository.saveAndFlush(FrameRevision.record(
            frame, RevisionAction.UPDATED, ChangeSource.MANUAL, MANUAL_ACTOR, now, changes
        ));
        return FrameResponse.from(frame);
    }

This method has two independent layers of defense against a lost update, and they close different halves of the race window.

Layer 1 — the explicit check (lines 71-73): frame.getVersion() != request.version() compares the version this request's client last read against the version currently in the freshly-loaded entity. If they differ, it fails immediately with a clear StaleFrameVersionException, before touching frame.update() or opening a write at all. This makes the common case — a client editing a genuinely stale copy — fast and cheap to reject.

Layer 2 — the JPA flush-catch (lines 81-85): the explicit check above reads frame.getVersion() at the start of this transaction, but that value can itself go stale before this transaction commits, if a second concurrent request also passes its own version check and commits first. @Version means every UPDATE Hibernate issues carries a WHERE version = ? clause; if the row's version changed underneath this transaction between the read and the flush(), zero rows match, Hibernate raises ObjectOptimisticLockingFailureException, and this method rethrows it as the same StaleFrameVersionException. Layer 1 exists to make the common case fast and give a clean, early rejection; layer 2 is what actually closes the race for the rare case where two requests both pass layer 1 before either one's transaction has committed — the database's row-level version guarantee is the real correctness mechanism, exactly the same relationship as existsById vs. the unique constraint in create() above.

One more branch worth flagging without fully explaining it here: if frame.update() (line 76) computes an empty change list — the request's values match what's already stored — the method returns early at line 78 and never writes a revision. Why revisions are diff-driven, and what "no-op" means at the field level, is the subject of the next page, Audit History.

CSV upsert path

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameCommandService.java:92-117
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public FrameImportOutcome upsertImportedFrame(String frameId, FrameData data) {
        Frame frame = frameRepository.findById(frameId).orElse(null);
        Instant now = now();
        if (frame == null) {
            frame = Frame.create(frameId, data, now);
            frameRepository.saveAndFlush(frame);
            List<FrameFieldChange> changes = new ArrayList<>();
            changes.add(new FrameFieldChange("frameId", null, frameId));
            changes.addAll(data.changesFrom(null));
            revisionRepository.saveAndFlush(FrameRevision.record(
                frame, RevisionAction.CREATED, ChangeSource.CSV, "csv-import", now, changes
            ));
            return FrameImportOutcome.CREATED;
        }

        List<FrameFieldChange> changes = frame.update(data, now);
        if (changes.isEmpty()) {
            return FrameImportOutcome.UNCHANGED;
        }
        frameRepository.flush();
        revisionRepository.saveAndFlush(FrameRevision.record(
            frame, RevisionAction.UPDATED, ChangeSource.CSV, "csv-import", now, changes
        ));
        return FrameImportOutcome.UPDATED;
    }

@Transactional(propagation = Propagation.REQUIRES_NEW) (line 92) means every call to this method opens its own, fully independent database transaction — suspending whatever transaction (if any) is active on the calling thread rather than joining it. For CSV import, this is called once per row. Because each row's write is its own transaction with its own commit point, one bad row failing partway through does not roll back any row already committed earlier in the same import — those commits already happened, in their own transactions, and are unaffected by a later row's failure. This is the concrete mechanism behind the CSV import ADR's partial-success guarantee (some rows created, some updated, some rejected, all in the same import run). The full import pipeline — validation, row limits, error reporting, and why per-row transactions were chosen over parallelizing across virtual threads — is covered in depth on the later CSV Import page; here it's enough to see that this is the same optimistic-lock machinery as manual update() above, reused for the bulk path via frame.update() and a plain flush() (no explicit version argument — CSV import upserts unconditionally by frameId, it does not carry a client-supplied version to compare against).

StaleFrameVersionException → 409

src/backend/src/main/java/com/global/ct/frameinventory/frame/exception/StaleFrameVersionException.java:1-7
package com.inventoryco.ct.frameinventory.frame.exception;

public class StaleFrameVersionException extends RuntimeException {
    public StaleFrameVersionException(String frameId) {
        super("Frame '" + frameId + "' was modified by another request; reload it and try again");
    }
}

Worth being precise here rather than assuming: this class is a plain RuntimeException subclass with a constructor that builds a human-readable message. It carries no @ResponseStatus annotation and no HTTP-specific code anywhere in the file — nothing in this class itself says "409." The mapping from this exception to an HTTP 409 Conflict response therefore has to happen somewhere else in the request pipeline, almost certainly in ApiExceptionHandler (in the web package, visible in the package layout on the Architecture Overview page) — but that file is this guide's later API Error Handling & Observability page's subject, not read for this page, so its exact mechanism (a @ExceptionHandler method, an RFC 9457 ProblemDetail body, or something else) is deliberately left unstated here rather than guessed.

Diagram B — two clients racing to update the same frame

Both clients below have already read the frame independently and both hold version=3. Both send a PUT with that version at roughly the same time. Spring handles requests concurrently on separate threads — nothing at the backend level queues one request behind the other. The diagram below shows one possible interleaving: Client A's request runs fully to commit, including its UPDATE ... WHERE version = ?, before Client B's explicit version check (Layer 1, above) even runs — so Layer 1 alone is enough to catch the conflict here. It is row-level locking at commit time in the database, not backend request ordering, that ultimately serializes the two competing UPDATE statements. A tighter interleaving is also possible: if both requests' Layer-1 checks read version=3 before either transaction commits, Layer 1 would let both through, and it would be Layer 2 — the flush() / ObjectOptimisticLockingFailureException catch — that catches the loser instead. The diagram shows the Layer-1-catches-it case only; it does not depict that tighter race.

Ordering is not deterministic — either client could "win" depending on which request's transaction commits first; the point is that at most one of them ever does.
