CSV Import

Validate-before-write · per-row REQUIRES_NEW · partial-success reporting

FrameImportService accepts a multipart CSV upload and upserts each row through the same command path used by the manual create/update endpoints. ADR 0002 (docs/adr/0002-synchronous-transactional-csv-import.md) frames the whole design as one choice: run the import synchronously, inside the request, with the file validated as a whole before any row is written — deliberately rejecting a background-job/outbox design as overkill for a 5,000-row, 2 MB bound. That trade-off shapes every method below.

Validate the whole file before writing anything

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameImportService.java:74-82
    private void validateFile(MultipartFile file) {
        if (file == null || file.isEmpty()) {
            throw new InvalidCsvException("A non-empty CSV file is required");
        }
        String filename = file.getOriginalFilename();
        if (filename != null && !filename.toLowerCase(Locale.ROOT).endsWith(".csv")) {
            throw new InvalidCsvException("The uploaded file must have a .csv extension");
        }
    }
src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameImportService.java:92-112
    private void validateStructureAndRowCount(MultipartFile file) {
        try (CSVParser parser = openParser(file)) {
            validateHeaders(parser);
            int rowCount = 0;
            for (CSVRecord record : parser) {
                rowCount++;
                if (rowCount > MAX_IMPORT_ROWS) {
                    throw new InvalidCsvException("A CSV file may contain at most 5,000 data rows");
                }
                if (!record.isConsistent()) {
                    throw new InvalidCsvException(
                        "CSV row " + (record.getRecordNumber() + 1) + " has an unexpected number of columns"
                    );
                }
            }
        } catch (IOException | UncheckedIOException exception) {
            throw new InvalidCsvException("The CSV file could not be read", exception);
        } catch (IllegalArgumentException exception) {
            throw new InvalidCsvException("The CSV structure is invalid", exception);
        }
    }

importCsv() calls validateFile() then validateStructureAndRowCount() before it opens the parser it will actually import from. Note what that means: the file gets parsed over in full twice — once here, purely to check the header set, the MAX_IMPORT_ROWS = 5,000 row-count cap, and per-row column-count consistency (record.isConsistent(), guarding against a row with a stray or missing comma), and again in importCsv()'s main loop for the actual upsert pass. No row is upserted until this first pass has walked every row and returned cleanly.

That's a deliberate trade-off, not an oversight: doubling the parse cost (cheap — CSV parsing is linear, and the file is capped at 2 MB / 5,000 rows) buys "the file is either structurally valid as a whole, or nothing gets written." Without this pre-pass, a header typo or a ragged row wouldn't surface until whatever row number it happens to sit at — potentially after 4,000 good rows have already been committed to the database, with no way to undo just the parse failure without also undoing legitimate writes.

One row, one transaction

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameImportService.java:141-155
    private void importRecord(CSVRecord record, ImportCounts counts, List<FrameImportErrorResponse> errors) {
        long rowNumber = record.getRecordNumber() + 1;
        String frameId = frameId(record);
        try {
            FrameImportRow row = mapper.map(record);
            FrameImportOutcome outcome = commandService.upsertImportedFrame(row.frameId(), row.data());
            counts.record(outcome);
        } catch (InvalidCsvRowException | DataIntegrityViolationException |
                 ObjectOptimisticLockingFailureException exception) {
            counts.failed++;
            if (errors.size() < MAX_REPORTED_ERRORS) {
                errors.add(new FrameImportErrorResponse(rowNumber, frameId, safeMessage(exception)));
            }
        }
    }

commandService.upsertImportedFrame() — walked through in the CRUD & optimistic concurrency page's "CSV upsert path" section — is annotated @Transactional(propagation = Propagation.REQUIRES_NEW). Called from inside the per-row loop, that means every row gets its own independent database transaction, committed or rolled back on its own, rather than all rows sharing one transaction for the whole file. One bad row rolling back does not touch the rows already committed before it or the rows still to come.

The catch clause names three distinct failure shapes, all handled identically — counted as failed, not fatal to the rest of the file:

  • InvalidCsvRowException — a row-level validation failure raised by FrameCsvMapper (missing required field, unparseable decimal/integer, or a value that doesn't match one of the MediaType/FrameEnvironment/FrameStatus enums).
  • DataIntegrityViolationException — a database constraint violation (Spring's translated form of whatever the JDBC driver reports).
  • ObjectOptimisticLockingFailureException — an optimistic-lock failure. This one is worth calling out specifically: it means a CSV import row can itself lose a race against a concurrent manual edit to the same frame made through the UI while the import is running. It is not treated as special or fatal — it's counted and reported exactly like a validation error, so the rest of the file keeps importing.

Bounded, honest error reporting

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameImportService.java:172-185
    private static final class ImportCounts {
        private int created;
        private int updated;
        private int unchanged;
        private int failed;

        private void record(FrameImportOutcome outcome) {
            switch (outcome) {
                case CREATED -> created++;
                case UPDATED -> updated++;
                case UNCHANGED -> unchanged++;
            }
        }
    }

MAX_REPORTED_ERRORS = 100 caps only the detailed row-error list (errors) returned to the client — importRecord() stops appending to errors once it holds 100 entries. counts.failed, the aggregate total, is never capped: it increments on every failing row regardless of whether that row's detail made it into the list.

errorsTruncated = counts.failed > errors.size() then makes the gap between those two numbers explicit in the response. If a file has 340 failing rows, the client gets failed: 340, exactly 100 entries in errors, and errorsTruncated: true — so "we stopped listing errors" is a field the client can check, not something it has to infer from an error list that's shorter than the failure count would suggest.

What the demo file actually demonstrates

data/gate4c_mixed_import.csv is a header row plus exactly 4 data rows. The README (README.md) describes it as: "first import the full inventory and then upload gate4c_mixed_import.csv. On that baseline, its first run returns one created, one updated, one unchanged, and one intentionally failed row." That's a claim worth checking rather than repeating — the outcome depends on a specific baseline, so I cross-referenced the mixed file against data/inventory_frame.csv (the "full inventory" the README refers to — 1,000 data rows, header includes the same frame_id/status/status_reason/etc. field names FrameCsvMapper reads by name):

Rowframe_idIn baseline inventory?OutcomeWhy
1 1234604983 Yes — baseline has status=LIVE, empty status_reason Updated Mixed-file row sets status=MAINTENANCE, status_reason=Gate 4C demo update — a real diff from the baseline row, so FrameData.changesFrom() is non-empty.
2 1234605591 Yes — baseline row matches on every mapped field Unchanged status=LIVE, empty status_reason, and every other mapped field (site_no, station, address, coordinates, slot count, distance, pixel dimensions, premium) is identical between the two files.

Verified, not assumed The 1-created / 1-updated / 1-unchanged / 1-failed claim checks out — but only given the specific baseline the README names. It is not a property of gate4c_mixed_import.csv in isolation: row 2's "unchanged" outcome only holds because inventory_frame.csv already contains an identical row for that frame ID, and row 1's "updated" outcome only holds because the baseline's version of that row differs. Import gate4c_mixed_import.csv against an empty database, or a database that was seeded differently, and the create/update/unchanged split would come out differently — only the failed row (RETIRED is not a valid FrameStatus) is guaranteed regardless of what's already in the database.

This is also a compact illustration of "one row, one transaction" from the section above: row 4's failure is a mapping-level InvalidCsvRowException raised before any database call is made for that row, and it has no effect on rows 1–3, which commit independently.
