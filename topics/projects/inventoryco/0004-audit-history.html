Audit History

Field-level diffing · transactional revisions · no-op suppression

The Frame CRUD page showed FrameCommandService.update() calling frame.update(request.toData(), now) and getting back a List<FrameFieldChange>, then deferred what that diff actually is and how it becomes a persisted FrameRevision. This page covers both: how FrameData compares two snapshots of itself field by field, and how the result gets turned into an append-only revision row in the same transaction as the mutation it describes.

Diffing two FrameData snapshots

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/FrameData.java:30-61
    public List<FrameFieldChange> changesFrom(FrameData previous) {
        List<FrameFieldChange> changes = new ArrayList<>();
        compare(changes, "mediaType", previous, FrameData::mediaType);
        compare(changes, "format", previous, FrameData::format);
        compare(changes, "environment", previous, FrameData::environment);
        compare(changes, "siteNumber", previous, FrameData::siteNumber);
        compare(changes, "station", previous, FrameData::station);
        compare(changes, "address", previous, FrameData::address);
        compare(changes, "region", previous, FrameData::region);
        compare(changes, "countryCode", previous, FrameData::countryCode);
        compare(changes, "town", previous, FrameData::town);
        compare(changes, "postcode", previous, FrameData::postcode);
        compare(changes, "longitude", previous, FrameData::longitude);
        compare(changes, "latitude", previous, FrameData::latitude);
        compare(changes, "status", previous, FrameData::status);
        compare(changes, "statusReason", previous, FrameData::statusReason);
        compare(changes, "numberOfSlots", previous, FrameData::numberOfSlots);
        compare(changes, "distanceToClosestSchool", previous, FrameData::distanceToClosestSchool);
        compare(changes, "pixelHeight", previous, FrameData::pixelHeight);
        compare(changes, "pixelWidth", previous, FrameData::pixelWidth);
        compare(changes, "premium", previous, FrameData::premium);
        return changes;
    }

    private <T> void compare(List<FrameFieldChange> changes, String fieldName, FrameData previous,
                             Function<FrameData, T> getter) {
        T oldValue = previous == null ? null : getter.apply(previous);
        T newValue = getter.apply(this);
        if (!equivalent(oldValue, newValue)) {
            changes.add(new FrameFieldChange(fieldName, display(oldValue), display(newValue)));
        }
    }

FrameData is a record with nineteen components, and a first pass at this would naturally reach for nineteen hand-written if blocks — one per field, each calling Objects.equals(previous.mediaType(), this.mediaType()) and its neighbours. That is nineteen near-identical blocks differing only in which accessor they call and which field name string they attach to the result, which is exactly the shape of duplication that hides a bug: get one field's accessor wrong in one of the nineteen copies and nothing catches it, because each block is independently "correct" boilerplate that nobody re-reads carefully after the first three.

The private compare() helper collapses all nineteen into one generic method parameterized on Function<FrameData, T> getter, called nineteen times with a different method reference each time (FrameData::mediaType, FrameData::format, and so on). Each call site is now a single line that reads as "compare this field" rather than a four-line block that has to be visually diffed against its neighbours to confirm it does what it claims. This is a deliberate DRY choice made for correctness, not tidiness that happened to fall out of refactoring: collapsing to one implementation means there is exactly one place where the "what counts as changed" logic (in equivalent(), below) and the "what does a changed value look like in the audit trail" logic (in display()) can be wrong, instead of nineteen.

Note the previous == null branch inside compare(): when changesFrom(null) is called for a brand-new frame (see the "Recording a revision" section below), every field's old value is treated as absent rather than the method throwing on a null receiver, so a CREATED revision naturally records every field as a "changed from nothing" entry using the same code path as an ordinary update diff.

Why BigDecimal fields need special-cased equality

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/FrameData.java:63-68
    private boolean equivalent(Object oldValue, Object newValue) {
        if (oldValue instanceof BigDecimal oldDecimal && newValue instanceof BigDecimal newDecimal) {
            return oldDecimal.compareTo(newDecimal) == 0;
        }
        return Objects.equals(oldValue, newValue);
    }

longitude and latitude are BigDecimal, and BigDecimal.equals() is scale-sensitive: new BigDecimal("10.0") and new BigDecimal("10.00") represent the identical numeric value but are not .equals() to each other, because equals() compares both unscaled value and scale, not just numeric value. Objects.equals() on two BigDecimals therefore inherits that same scale-sensitivity — it delegates straight to BigDecimal.equals().

This matters here specifically because a coordinate can pick up a different scale on a round trip without its value actually changing — for example, a value read back from the database, or a value re-serialized from a form submission, gaining or losing a trailing zero. Left to plain Objects.equals(), that round trip would register as a "changed" field and generate a phantom FrameFieldChange entry for a coordinate that never moved. equivalent() special-cases the BigDecimal pair with a type pattern (oldValue instanceof BigDecimal oldDecimal && newValue instanceof BigDecimal newDecimal) and compares with compareTo() == 0 instead, which is numeric-value equality regardless of scale. Every other field type — String, the various enums, Integer, Boolean — falls through to the Objects.equals() branch, where scale isn't a concern in the first place.

Recording a revision

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameCommandService.java:58-63
        List<FrameFieldChange> changes = new ArrayList<>();
        changes.add(new FrameFieldChange("frameId", null, frame.getFrameId()));
        changes.addAll(frame.data().changesFrom(null));
        revisionRepository.save(FrameRevision.record(
            frame, RevisionAction.CREATED, ChangeSource.MANUAL, MANUAL_ACTOR, now, changes
        ));

This is the call site inside FrameCommandService.create() — unchanged from how it appeared on the Frame CRUD page, re-verified here against the current source rather than assumed. MANUAL_ACTOR is the literal string "demo-user", declared as a private static final constant at the top of FrameCommandService. The parallel call inside upsertImportedFrame() passes ChangeSource.CSV and the literal "csv-import" in the same actor position instead.

src/backend/src/main/java/com/global/ct/frameinventory/frame/model/FrameRevision.java:54-64
    public static FrameRevision record(Frame frame, RevisionAction action, ChangeSource source,
                                       String actor, Instant occurredAt, List<FrameFieldChange> fieldChanges) {
        FrameRevision revision = new FrameRevision();
        revision.frame = frame;
        revision.action = action;
        revision.source = source;
        revision.actor = actor;
        revision.occurredAt = occurredAt;
        fieldChanges.forEach(change -> revision.changes.add(FrameRevisionChange.create(revision, change)));
        return revision;
    }

record() is a static factory on FrameRevision — the only way to construct one, since the no-arg constructor is protected (for JPA's benefit) and there is no public constructor at all. Its parameter order matches the call site exactly: frame, then action (RevisionAction.CREATED or UPDATED), then source (ChangeSource.MANUAL or CSV), then the actor string, then the timestamp, then the list of field changes. Inside, it builds the parent FrameRevision row and, in the same call, converts every FrameFieldChange value object into a child FrameRevisionChange JPA entity via FrameRevisionChange.create(revision, change) — this is where the plain in-memory diff result from changesFrom() becomes persistence-ready rows, one FrameFieldChange in, one FrameRevisionChange entity out, field name and old/new value strings carried across unchanged.

ChangeSource.MANUAL vs. ChangeSource.CSV records which write path produced a revision — API call vs. bulk import — but the actor field is the harder gap: today it can only ever be one of two fixed constants, demo-user or csv-import, because no authentication provider exists in this build. Every manual write, regardless of who is actually driving the API, is attributed to the same literal string. ADR 0003 is explicit that this is a known, temporary limitation rather than a design choice being defended: "When authentication is introduced, actor values should come from verified identity claims." Until then, the audit trail answers what changed, when, and via which path (manual vs. CSV) — it does not answer who, beyond that one bit.

No revision for a no-op

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameCommandService.java:76-79
        List<FrameFieldChange> changes = frame.update(request.toData(), now);
        if (changes.isEmpty()) {
            return FrameResponse.from(frame);
        }

If a client re-submits a PUT with exactly the values already stored — a form resubmitted without edits, a retried request that already succeeded, a script that always sends the full object whether or not anything changed — frame.update() runs changesFrom() internally and gets back an empty list: nothing failed equivalent(), so nothing was appended to changes. This method checks that directly and returns the current state without ever reaching the revisionRepository.saveAndFlush(FrameRevision.record(...)) call further down — no FrameRevision row, no child FrameRevisionChange rows, nothing written at all beyond the read.

The consequence is that frame_revisions is a record of actual changes to a frame's data, not a record of every HTTP call that happened to hit the update endpoint. A frame that gets re-PUT ten times with identical values shows zero history entries for those ten calls, which is the intended reading of the audit trail: scan it and every row means something on the frame genuinely moved. The same changes.isEmpty() short-circuit appears again in upsertImportedFrame(), returning FrameImportOutcome.UNCHANGED for a CSV row that upserts to identical values — same suppression, same reasoning, reused for the bulk path.

Same transaction, always

ADR 0003 states the rule directly: "Perform the frame mutation and its field-level revision in the same database transaction." The Frame CRUD page already showed the concrete mechanism — the @Transactional annotations on create(), update(), and upsertImportedFrame() — so it isn't re-pasted here. What this page adds is what actually happens inside that one transaction: the diff computed by changesFrom() decides whether a revision gets written at all, and if it does, FrameRevision.record() turns that diff into rows that commit or roll back together with the frame row they describe. There is no window where a frame's data changes and its history doesn't, or vice versa — and, per the no-op rule above, no window where an update that changed nothing leaves a misleading trace that it did.
