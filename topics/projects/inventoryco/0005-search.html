JPA Specification pattern · LIKE-wildcard escaping · pagination

The Specification pattern

Frame search combines up to four independent filters — a free-text query plus three exact-match enum filters — and any subset of them can be present or absent on a given request. Rather than building this with a hand-assembled JPQL string and conditional concatenation (a common source of missing-space bugs and accidental SQL injection when done carelessly), the solution uses Spring Data JPA's Specification<T> pattern: a functional interface that receives the JPA Criteria API's root, criteriaQuery, and builder, and returns a single composed Predicate.

src/backend/src/main/java/com/global/ct/frameinventory/frame/repository/FrameSpecifications.java:14-52
public final class FrameSpecifications {

    private static final char LIKE_ESCAPE = '\\';

    private FrameSpecifications() {
    }

    public static Specification<Frame> matching(String query, FrameStatus status,
                                                FrameEnvironment environment, MediaType mediaType) {
        return (root, criteriaQuery, builder) -> {
            List<Predicate> predicates = new ArrayList<>();

            if (query != null && !query.isBlank()) {
                String pattern = "%" + escapeLike(query.trim().toLowerCase(Locale.ROOT)) + "%";
                List<Predicate> textMatches = new ArrayList<>();
                for (String field : List.of("frameId", "siteNumber", "station", "address", "town", "postcode", "format")) {
                    Expression<String> value = builder.lower(root.get(field).as(String.class));
                    textMatches.add(builder.like(value, pattern, LIKE_ESCAPE));
                }
                predicates.add(builder.or(textMatches.toArray(Predicate[]::new)));
            }
            if (status != null) {
                predicates.add(builder.equal(root.get("status"), status));
            }
            if (environment != null) {
                predicates.add(builder.equal(root.get("environment"), environment));
            }
            if (mediaType != null) {
                predicates.add(builder.equal(root.get("mediaType"), mediaType));
            }

            return builder.and(predicates.toArray(Predicate[]::new));
        };
    }

    private static String escapeLike(String value) {
        return value.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
    }
}

matching() is a predicate-builder: each active filter — text query, status, environment, media type — appends zero or more Predicates to a mutable list, and everything left in the list at the end is AND'd together with builder.and(...). Absent filters (a null status, a blank query) simply never add a predicate, so the specification degrades gracefully to "no filter" without any branch needing to build a different SQL string by hand. Inside the text-query branch, the seven candidate fields are OR'd together first (builder.or(textMatches...)) and that OR group is then one of the AND'd top-level predicates — so a query for "deptford" combined with status=ACTIVE reads as (frameId LIKE ... OR siteNumber LIKE ... OR ...) AND status = 'ACTIVE', not a flat OR of everything.

One thing worth being precise about: root.get("fieldName") takes a plain String field name. This is not compile-time type-safe — a typo like root.get("frmeId") compiles fine and only fails at query-execution time. JPA's Criteria API has a static metamodel mechanism (generated Frame_ classes with typed SingularAttribute fields, giving root.get(Frame_.frameId) compile-time checking) that would close this gap, but this codebase doesn't use it — no metamodel generator is configured, and every field reference here is a bare string. So the Specification pattern buys composability over string-concatenated JPQL, not type safety over it.

Escaping LIKE wildcards

src/backend/src/main/java/com/global/ct/frameinventory/frame/repository/FrameSpecifications.java:49-51
private static String escapeLike(String value) {
    return value.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
}

SQL LIKE treats % as "any sequence of characters" and _ as "any single character." Without escaping, a user typing a literal 50% — entirely plausible if searching a format string, a percentage-based media spec, or any free-text field that happens to contain a percent sign — would have that % interpreted as a wildcard by the database, silently matching far more rows than the user intended (anything starting with 50 followed by anything, rather than the literal string 50%). That's a real correctness bug, not just a hardening nicety: the search box would quietly return wrong results with no error and no obvious cause. escapeLike() neutralizes this by backslash-escaping % and _ before the pattern is wrapped in the caller's own wildcard bookends (the "%" + escapeLike(...) + "%" in matching()), and it escapes the backslash itself first so a literal backslash in the input doesn't accidentally un-escape a following character. The escape character is registered with the query via the three-argument builder.like(value, pattern, LIKE_ESCAPE), so the database, not just application code, knows \ is the escape marker. This is exactly the injection-adjacent shape the project's own code-review rubric flags elsewhere (string concatenation into a query without escaping) — here it's handled correctly, at the LIKE-pattern level rather than the SQL-string level, since Criteria API parameter binding already prevents classic SQL string injection.

Seven fields, one OR

The loop builds one LIKE predicate per field and OR's all seven together, so a single free-text query box matches if any of the seven fields contains the substring. Every field is lower-cased on both sides (builder.lower(...) against a lower-cased query) for case-insensitive matching. The field list — frameId, siteNumber, station, address, town, postcode, format — is exactly the set of identifying, human-readable attributes an out-of-home (OOH) advertising operator would plausibly type into one search box without knowing which field the value lives in: they might remember the frame's internal ID, the site number from a spreadsheet, the station or town it's near, a fragment of the street address or postcode, or the physical format (e.g. a panel size code). Fields that don't belong in free-text search — status, environment, mediaType — are deliberately excluded from this loop and handled as separate exact-match enum predicates instead, because a partial substring match on an enum name isn't a meaningful user intent the way it is for an address or postcode.

Pagination and controller wiring

src/backend/src/main/java/com/global/ct/frameinventory/frame/controller/FrameController.java:53-63
@GetMapping
public PageResponse<FrameResponse> search(
    @RequestParam(required = false) String q,
    @RequestParam(required = false) FrameStatus status,
    @RequestParam(required = false) FrameEnvironment environment,
    @RequestParam(required = false) MediaType mediaType,
    @RequestParam(defaultValue = "0") @Min(0) int page,
    @RequestParam(defaultValue = "25") @Min(1) @Max(100) int size
) {
    return queryService.search(q, status, environment, mediaType, page, size);
}

The controller method is annotated @Validated at the class level (line 37), which is what makes the method-parameter constraints @Min(0) on page and @Min(1) @Max(100) on size actually enforced — Spring runs them through a method-validation interceptor and rejects out-of-range values with a ConstraintViolationException before the method body ever executes. This is the concrete answer to "where is the page-size cap enforced": in the controller's request-parameter annotations, not in FrameQueryService or the repository layer — neither of those re-checks the bound. page defaults to 0 (zero-based, matching Spring Data's PageRequest.of(page, size, ...) convention) and size defaults to 25, capped at 100.

src/backend/src/main/java/com/global/ct/frameinventory/frame/service/FrameQueryService.java:19-36
private static final Sort DEFAULT_SORT = Sort.by(
    Sort.Order.desc("updatedAt"),
    Sort.Order.asc("frameId")
);

private final FrameRepository repository;

public FrameQueryService(FrameRepository repository) {
    this.repository = repository;
}

@Transactional(readOnly = true)
public PageResponse<FrameResponse> search(String query, FrameStatus status, FrameEnvironment environment,
                                          MediaType mediaType, int page, int size) {
    var pageRequest = PageRequest.of(page, size, DEFAULT_SORT);
    var frames = repository.findAll(FrameSpecifications.matching(query, status, environment, mediaType), pageRequest);
    return PageResponse.from(frames, FrameResponse::from);
}

FrameQueryService.search() is the seam between the controller's already-validated raw parameters and the query itself: it builds a Spring Data PageRequest from the (now-bounded) page/size plus a fixed DEFAULT_SORT, and passes both the Specification and the PageRequest into JpaSpecificationExecutor.findAll(spec, pageable). The sort is stable — updatedAt DESC then frameId ASC as a tiebreaker — which matters because updatedAt alone isn't unique (two frames can update in the same millisecond); without the frameId tiebreaker, rows with equal updatedAt could shuffle order between pages as new writes land, which would let a row appear twice or not at all across consecutive page requests.

The leading-wildcard limitation

ADR 0001 — Consequences

"Leading-wildcard searches cannot fully use ordinary B-tree indexes and may scan as data grows."

The pattern built in matching() is always "%" + escapeLike(query) + "%" — a wildcard on both sides of the search term, because the requirement is substring matching (find "deptford" anywhere in the address, not just at the start). A standard B-tree index is built by sorting values and letting the database binary-search the sorted structure by prefix: given LIKE 'deptford%' (a trailing-only wildcard), the engine can jump straight to where values starting with "deptford" begin and stop once they end — because everything in a B-tree is ordered left-to-right by leading characters, a known prefix narrows the search range immediately. LIKE '%deptford%' has no known prefix at all — the match could start anywhere in the string — so there is no starting point in the sorted index to jump to, and the database falls back to scanning every row's value and testing the substring by hand. At the ~1,000-row scale this solution targets (per ADR 0001's Context section), that full scan is cheap enough not to matter; the ADR calls this out explicitly as a known, accepted limitation rather than something worked around. This gap — leading-wildcard search not being index-friendly at growing scale — is the exact seed for a later "What If: OpenSearch" page in this study guide, which explores what changes if search moves off substring-LIKE entirely.
