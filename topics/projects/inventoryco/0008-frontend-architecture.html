Frontend Architecture

React file layout · design-system usage · stale-edit and partial-import UX

The frontend is a small Vite + React 19 single-page app (React Router 7, TypeScript, Vitest + Testing Library). No state library, no CSS framework — plain fetch, component-local useState, and hand-written CSS. Six route pages sit under one AppShell layout; everything else is a thin support layer around those pages.

File layout

src/frontend/src/ ├── api/ frames.ts (typed API functions), http.ts (fetch wrapper + ApiError), frames.test.ts ├── assets/ fonts/ (Inter TTFs), vite.svg ├── components/ │ ├── frame/ FrameForm.tsx (the one form shared by create + edit), frameFormModel.ts │ ├── layout/ AppShell.tsx (rail nav, topbar, breadcrumbs, mobile menu) │ └── ui/ FeedbackState.tsx, FieldValue.tsx, LoadingTable.tsx, StatusBadge.tsx ├── hooks/ useRemoteData.ts (fetch-on-mount + retry, used by every read page) ├── pages/ CreateFramePage, EditFramePage, FrameDetailPage, FrameHistoryPage, │ FrameImportPage, FrameInventoryPage (+ colocated *.test.tsx) ├── types/ frame.ts (Frame, FrameSearch, FrameImportResult, FrameRevision, ...) ├── utils/ inventoryNavigation.ts (safe "back to filtered list" return path) ├── App.tsx route table, wraps every page in AppShell ├── App.css component styles (tables, forms, banners, nav rail) ├── index.css CSS custom properties + @font-face, global reset └── main.tsx entry point — mounts App inside StrictMode + BrowserRouter
FolderResponsibility
api/Two files: http.ts wraps fetch into getJson/sendJson/sendForm helpers and turns a non-2xx response into a thrown ApiError (carrying status, title, and per-field fieldErrors parsed from a Problem Detail body); frames.ts is a thin set of typed functions (searchFrames, getFrame, createFrame, updateFrame, getFrameHistory, importFrames) that call those helpers against /api/frames. No other file in the app calls fetch directly.
types/One file, frame.ts — the frontend's mirror of the backend's DTOs: Frame (including version for optimistic locking), FrameSearch/PageResponse for the list, CreateFrameRequest/UpdateFrameRequest write payloads, FrameRevision/FrameChange for history, and FrameImportResult/FrameImportError for CSV import results.
pages/One component per route: list/search (FrameInventoryPage), read-only detail (FrameDetailPage), create and edit (CreateFramePage, EditFramePage — both just supply FrameForm with different mode/submit logic), audit trail (FrameHistoryPage), and CSV import (FrameImportPage).
components/frame/The one non-trivial shared component: FrameForm.tsx renders all writable fields, does client-side validation, and shows server-side fieldErrors/notice/conflict passed in as props. frameFormModel.ts converts between the wire-shaped Frame (numbers, nullable strings) and form-shaped FrameFormValues (everything is a string, since HTML inputs only produce strings).
components/ui/Generic, page-agnostic pieces: FeedbackState (error/empty state with optional retry button), FieldValue (label/value pair that falls back to "Not provided"), LoadingTable (skeleton rows), StatusBadge (colored dot + label for a FrameStatus).
components/layout/Just AppShell.tsx — the persistent chrome (brand bar, breadcrumbs, collapsible nav rail, mobile menu) that every route renders inside via <Outlet />.
hooks/useRemoteData.ts — the one data-fetching hook in the app. Wraps a loader function in loading/success/error state, aborts the in-flight request on dependency change or unmount via AbortController, and exposes a retry() that bumps an internal counter to re-run the effect.
utils/inventoryNavigation.ts — a single guard function, inventoryReturnPath, that only trusts a location.state.returnTo value if it points back at /frames or /frames?..., otherwise falls back to /frames. Used so "Back to frames" links preserve the caller's search/filter/page query string without accepting an arbitrary redirect target.

Design system usage

design-system/README.md describes a product-scoped design system extracted from the Frame Inventory prototype, built on a "Global Design System (Global Next theme — Inter type, blue/cyan palette)". It ships as source files rather than a package: tokens.css (CSS custom properties only), styles.css (component styles built on those tokens), shell.jsx (app chrome — rail nav, topbar, breadcrumbs, icon set), and reference JSX shapes (master-data.jsx, direction-a.jsx, direction-b.jsx). It specifies concrete visual rules: Inter at 13px body size, cool-blue primary (--blue-1000 #046AC4) on near-white --gray-50 surfaces, no drop shadows on resting surfaces, 4px/8px/999px radii, an 8px spacing base, and hand-rolled 1.8px-stroke SVG icons (no icon CDN).

The frontend does not import any design-system file directly — there is no reference to design-system/ anywhere under src/frontend/src/, and no build-time copy step for it either. What it does instead is hand-copy a subset of the same token values into its own src/index.css: the frontend's --gray-50 (#f7f9fa) and --blue-1000 (#046ac4) are byte-identical to design-system/tokens.css's --gray-50 and --blue-1000, and --radius: 4px matches too — but the frontend keeps its own smaller, differently-named token set (it drops most of the design system's grays and adds its own --muted/--primary/--shadow aliases) rather than loading tokens.css as-is. In practice this is "inspired by the design system's palette," not "consumes the design system."

This is the frontend's entire design-system footprint at the token/import level: one hand-maintained token block. Every color, radius, and shadow used across App.css and the page components resolves back to a var(--...) defined here, and the hex values line up with design-system/tokens.css's primary/neutral scale — but there is no shared file, so a palette change in the design system would need to be copied over by hand rather than picked up automatically.

So the influence is real and structural — a layout blueprint that was followed — even though it was reimplemented from scratch in TSX/CSS rather than imported as a file.

Stale-edit recovery

Per ADR 0003 (docs/adr/0003-optimistic-concurrency-and-transactional-audit-history.md), the backend uses JPA @Version optimistic locking: a client must echo back the version it read, and a stale write throws StaleFrameVersionException → HTTP 409 Conflict. EditFramePage.tsx is the only page that sends a version, and its submit handler is where the 409 is caught:

src/frontend/src/pages/EditFramePage.tsx:25-36
  async function submit(_frameId: string, payload: FrameWritePayload) {
    if (frame.status !== 'success') return
    setSubmitting(true); setNotice(undefined); setConflict(false); setFieldErrors({})
    try {
      const updated = await updateFrame(frameId, { version: frame.data.version, ...payload })
      navigate(`/frames/${encodeURIComponent(updated.frameId)}`, { replace: true, state: { returnTo } })
    } catch (error) {
      if (error instanceof ApiError) {
        setFieldErrors(error.fieldErrors); setNotice(error.message); setConflict(error.status === 409)
      } else setNotice('An unexpected error occurred while saving the frame.')
    } finally { setSubmitting(false) }
  }

The version sent on the request is frame.data.version — whatever useRemoteData loaded when the page mounted, not a value the user can edit. On any ApiError the handler always sets notice to the server's message and stores per-field errors; it additionally flips conflict to true only when error.status === 409, which is the only signal that distinguishes "someone else saved first" from an ordinary validation failure.

conflict and notice are passed straight through as props to FrameForm, which is where the banner actually renders:

src/frontend/src/components/frame/FrameForm.tsx:80
      {notice && <div className={`form-notice ${conflict ? 'conflict' : 'error'}`} role="alert"><AlertCircle /><div><strong>{conflict ? 'This frame has changed' : 'Frame could not be saved'}</strong><span>{notice}</span></div>{conflict && onReload && <button type="button" className="button secondary" onClick={onReload}>Reload latest</button>}</div>}

The banner heading swaps between "This frame has changed" and "Frame could not be saved" purely on the conflict flag, and only the conflict case renders a "Reload latest" button. That button's onClick is onReload, which EditFramePage wires to its own reload() — clearing notice/conflict/fieldErrors and calling frame.retry() from useRemoteData to re-fetch the current row. The form itself is remounted with key={frame.data.version} once the reload lands, so stale in-progress edits are discarded rather than silently merged with the new version.

Partial CSV import results

Per ADR 0002, CSV import upserts each row in its own transaction rather than the whole file, so a single import can produce a mix of created/updated/unchanged/failed rows — the response is a summary count plus a capped list of row-level errors (backend caps detail at 100 rows; total failed stays accurate even when the list is truncated). FrameImportPage.tsx renders that shape directly:

src/frontend/src/pages/FrameImportPage.tsx:82-100
function ImportResult({ result }: { result: FrameImportResult }) {
  const hasErrors = result.failed > 0
  return (
    <section className={`import-result ${hasErrors ? 'partial' : 'success'}`} aria-live="polite">
      <header><CheckCircle2 /><div><h2>{hasErrors ? 'Import completed with row errors' : 'Import completed'}</h2><p>{hasErrors ? 'Valid rows were imported successfully.' : 'All rows were processed successfully.'}</p></div></header>
      <dl className="import-counts">
        <div><dt>Created</dt><dd>{result.created}</dd></div>
        <div><dt>Updated</dt><dd>{result.updated}</dd></div>
        <div><dt>Unchanged</dt><dd>{result.unchanged}</dd></div>
        <div><dt>Failed</dt><dd>{result.failed}</dd></div>
      </dl>
      {result.errors.length > 0 && <div className="import-errors">
        <h3>Row errors</h3>
        <div className="table-scroll"><table><thead><tr><th>Row</th><th>Frame ID</th><th>Reason</th></tr></thead><tbody>{result.errors.map((error) => <tr key={`${error.rowNumber}-${error.frameId ?? ''}`}><td>{error.rowNumber}</td><td>{error.frameId ?? 'Not provided'}</td><td>{error.message}</td></tr>)}</tbody></table></div>
        {result.errorsTruncated && <p className="truncated-errors"><AlertCircle />Only the first 100 row errors are shown.</p>}
      </div>}
    </section>
  )
}

All four counts (created/updated/unchanged/failed) render unconditionally in a <dl> regardless of outcome — there's no "hide the zero rows" logic, so an all-success import still shows Failed 0 next to the others. The row-error table only mounts when result.errors.length > 0, keyed per row on rowNumber + frameId (falling back to an empty string when frameId is null, since a row can fail before an ID is even parsed). The errorsTruncated flag — set by the backend once more than 100 row errors exist — renders a fixed "Only the first 100 row errors are shown" notice; it does not recompute how many were actually omitted, since the summary failed count already carries the true total.
