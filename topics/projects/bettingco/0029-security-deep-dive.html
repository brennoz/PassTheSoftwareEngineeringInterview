Security Deep Dive

Functional security (what the system does) · Non-functional security (how the system resists attack)
The distinction that matters at Opayo Interviewers at a payment platform will probe security harder than most. The key distinction: functional security = features you built (authentication, authorisation, tenant isolation). Non-functional security = properties of the system (no PAN in logs, encrypted at rest, least-privilege pod permissions). Confusing the two is a red flag. Knowing both — and honestly knowing where the gaps are — is the senior answer.

Functional Security — What ARM BettingCo Does

1. JWT Authentication — JwtAuthenticationTokenFilter

// Every request passes through JwtAuthenticationTokenFilter
// Extends OncePerRequestFilter — Spring guarantees single execution per request

public class JwtAuthenticationTokenFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                Claims claims = jwtService.parseToken(token);
                Long tenantId = claims.get("tenantId", Long.class);
                String role = claims.get("role", String.class);

                // Validate tenant exists — prevents JWT with deleted tenant
                tenantService.validateTenant(tenantId);

                UsernamePasswordAuthenticationToken auth =
                    new UsernamePasswordAuthenticationToken(tenantId, null,
                        List.of(new SimpleGrantedAuthority("ROLE_" + role)));
                SecurityContextHolder.getContext().setAuthentication(auth);
            } catch (JwtException e) {
                res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
                return;
            }
        }
        chain.doFilter(req, res);
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        // Login and health endpoints skip authentication
        String path = request.getRequestURI();
        return path.startsWith("/login") || path.startsWith("/actuator/health");
    }
}
Why OncePerRequestFilter not a regular Filter? Spring's filter chain can invoke a filter multiple times per request in some configurations (forward, include). OncePerRequestFilter guarantees exactly one invocation per logical request — essential for authentication to prevent double-processing or bypass. This is the correct base class for any security filter in Spring Boot.

2. Multi-Tenant Isolation — Data Layer Enforcement

// Tenant isolation is NOT enforced at the service deployment level —
// all tenants share pods. Isolation is at the data layer: every query scoped by tenantId.

@Repository
public interface BetRepository extends JpaRepository<Bet, Long> {
    // tenantId injected from SecurityContext in service layer
    List<Bet> findByEventIdAndTenantId(Long eventId, Long tenantId);

    // Service extracts tenantId from SecurityContext — never trusts request body
    // A tenant cannot query another tenant's bets even with a valid JWT
}

@Service
public class BetService {
    public List<Bet> getBetsForEvent(Long eventId) {
        Long tenantId = SecurityContextHolder.getContext()
            .getAuthentication().getPrincipal();  // from JWT claim, not request
        return betRepository.findByEventIdAndTenantId(eventId, tenantId);
    }
}

5. Secret Management

# Secrets managed via HashiCorp Vault (not plain K8s Secrets)
# ARM uses the Vault Secrets Operator: VaultStaticSecret CRD syncs secrets
# from Vault into K8s Secrets, then mounted into pods via envFrom.
# Protected by:
# - Vault policy: only authorised service accounts can read specific paths
# - K8s RBAC: only correct namespace service accounts can access synced secrets
# - GitLab CI: Vault tokens injected as env vars, never committed to git

# Helm chart pattern (vault-static-secrets.yaml + deployment.yaml):
# 1. VaultStaticSecret CRD creates a K8s Secret from Vault kv-v2 path:
apiVersion: secrets.hashicorp.com/v1beta1
kind: VaultStaticSecret
spec:
  path: secrets/bet-manager-service/db
  type: kv-v2
  mount: secrets
  refreshAfter: 60s    # auto-rotates without pod restart
  destination:
    create: true
    name: bet-manager-service-secrets

# 2. Deployment consumes via envFrom (bulk inject all keys from secret):
spec:
  containers:
  - name: bet-manager-service
    envFrom:
    - secretRef:
        name: bet-manager-service-secrets

# AWS MSK access: IAM role assigned to EKS service account (IRSA)
# Pod inherits AWS permissions from the role — no static AWS keys in the pod

Non-Functional Security — How ARM Resists Attack

1. No PII in Logs

// ARM logs are shipped to Datadog — accessible to multiple engineers.
// Rule: no user-identifiable data in logs at INFO or above.

// BAD: logs tenant name, bet amount (financial data)
log.info("Processing bet for tenant {} amount {}", tenant.getName(), bet.getAmount());

// GOOD: log IDs and operational context only
log.info("Processing bet betId={} tenantId={} eventId={}",
    bet.getId(), bet.getTenantId(), bet.getEventId());

// Why this matters at Opayo:
// PCI-DSS requires PAN never appears in logs.
// GDPR requires PII (name, email, account number) never in cleartext logs.
// Same principle ARM uses (tenant name = PII) applies to cardholder name at Opayo.

2. Kubernetes Pod Security

# ARM Helm chart — pod security context
# Note: the base values.yaml leaves securityContext as {} (empty) by default.
# These hardening fields are the recommended additions for a payment platform.
# In production, resource limits are service-specific (not a global default):
spec:
  securityContext: {}     # base chart default — override per service in practice
  containers:
  - name: event-service
    securityContext: {}   # base chart default — hardening applied per service

# Recommended hardening (apply per service, not global default):
# securityContext:
#   runAsNonRoot: true          # container cannot run as root
#   runAsUser: 1000             # explicit non-root UID
#   readOnlyRootFilesystem: true   # container filesystem is read-only
#   allowPrivilegeEscalation: false
#   capabilities:
#     drop: ["ALL"]           # drop ALL Linux capabilities (including NET_RAW)

# JVM memory control via JAVA_OPTS (actual ARM config):
JAVA_OPTS: "-XX:+UseContainerSupport -XX:+ExitOnOutOfMemoryError -XX:MaxRAMPercentage=75"
# UseContainerSupport: JVM reads cgroup limits (respects K8s memory limit)
# ExitOnOutOfMemoryError: pod crashes cleanly instead of hanging zombie
# MaxRAMPercentage=75: heap = 75% of container memory limit

3. Network Policies — Namespace Isolation

# arm-dev pods CANNOT reach arm-prod pods (different namespaces, NetworkPolicy)
# Prevents a dev environment compromise from accessing prod data

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: arm-dev-isolation
  namespace: arm-dev
spec:
  podSelector: {}    # applies to all pods in arm-dev
  policyTypes: ["Ingress", "Egress"]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          environment: dev    # only accept traffic from dev namespace
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          environment: dev    # only send traffic to dev namespace
    - ipBlock:
        cidr: 0.0.0.0/0      # allow external (MSK, ECR, etc.)
        except:
        - 10.0.0.0/8          # block internal prod VPC CIDR

4. Rate Limiting on External Feed Ingestion

// resilience4j RateLimiter on WOODS cluster consumers
// Prevents a misbehaving feed handler from overwhelming the internal BETTINGCO cluster

@Component
public class BetfairFeedHandler extends AbstractFeedHandler {

    private final RateLimiter rateLimiter;

    public BetfairFeedHandler(RateLimiterRegistry registry) {
        this.rateLimiter = registry.rateLimiter("betfair-ingestion");
        // config: 1000 events/second, refresh every 1 second
    }

    @Override
    public void onMessage(FeedMessage message) {
        RateLimiter.waitForPermission(rateLimiter);  // blocks if over limit
        super.processMessage(message);
    }
}

Honest answer: what ARM didn't have (and what you'd add at Opayo) No mTLS between services — internal traffic is plain HTTP. At a payment platform you'd add Istio or Linkerd service mesh for mTLS, providing encryption and mutual authentication between every service. Secrets rotation: ARM uses HashiCorp Vault with a 60-second refresh interval on VaultStaticSecret — better than static K8s Secrets, but not automatic rotation triggered on compromise. At Opayo you'd add Vault dynamic secrets with lease revocation for true rotation. No WAF (Web Application Firewall) in front of the ingress — at Opayo, AWS WAF with rate rules and OWASP ruleset would be mandatory. No runtime security scanning (Falco) — at Opayo, container runtime anomaly detection would be expected for PCI-DSS compliance. No pod security hardening in the base chart (securityContext defaults to empty) — at Opayo, readOnlyRootFilesystem and capability dropping would be enforced via Pod Security Admission. Being honest about these gaps and knowing how to close them is a stronger answer than claiming the platform was perfectly secure.

Quiz

Q1. An Opayo interviewer asks: "What's the difference between functional and non-functional security? Give me an example of each from your project." What's the correct answer?

  • Functional security = unit tests that test security logic. Non-functional security = penetration testing and vulnerability scans done after deployment.
  • Functional security = the security features users interact with (login, logout, password reset). Non-functional security = TLS encryption and HTTPS enforcement. Functional is user-facing; non-functional is infrastructure.
  • Functional security = features I built to implement security requirements: JWT authentication filter (OncePerRequestFilter), role-based @PreAuthorize, tenant isolation enforcing tenantId on every DB query. Non-functional security = properties that make the system resistant to attack regardless of whether a security feature is used: no PII in logs, readOnlyRootFilesystem on pods, network policies preventing arm-dev from reaching arm-prod, rate limiting on feed ingestion to prevent cascade. Functional answers "what security does the system provide?" Non-functional answers "how hard is the system to attack?"
  • Functional security = authentication and authorisation. Non-functional security = everything else including HTTPS and encryption.
The correct distinction: functional security = security requirements expressed as features (auth, authz, data isolation, audit log). Non-functional security = systemic properties that make the system harder to attack or compromise regardless of application-level security (least-privilege pods, no PII in logs, network isolation, runtime scanning). Both are required for a complete security posture. Option B is incomplete — HTTPS is a non-functional property but not the full picture. Option D conflates authentication with functional security (auth is one category of functional security, not the whole definition).

Q2. ARM BettingCo's JWT contains the tenantId claim. A malicious actor signs their own JWT with tenantId=999 (a different client's tenant). Why does this fail, and what's the defence?

  • Two defences make this fail: (1) JWT signature verification — the JWT is signed with a server-side secret (HS256). A self-signed JWT with a different key produces a signature that doesn't verify against the server's secret — JwtAuthenticationTokenFilter throws JwtException → 401. (2) Even if a valid JWT were obtained (e.g. stolen token), TenantService.validateTenant(tenantId) checks the claimed tenantId against the DB and verifies the authenticated user belongs to that tenant. Tenant data is also always scoped by tenantId at query level — a valid JWT for tenant 1 cannot retrieve tenant 2's data even if the DB query ran. Multiple layers, each independently failing closed.
  • The JWT is encrypted so the tenantId cannot be read or forged by an attacker
  • HTTPS prevents the JWT from being intercepted, so a malicious JWT cannot reach the server
  • The K8s network policy blocks requests from unknown IP addresses before they reach the JWT filter
JWT is typically signed (not encrypted) — the payload is base64-encoded and readable, but the signature makes it tamper-proof. An attacker can read the claims in an intercepted JWT but cannot modify them without invalidating the signature. A self-crafted JWT with a different signing key produces a signature that fails verification. The second defence layer — tenantId scoped DB queries — provides defence-in-depth: even a valid-looking JWT (e.g. if the secret were compromised) can only access data for the claimed tenant.

Q3. Opayo asks: "How would you ensure no card data (PAN) ever appears in your application logs?" What is the complete answer?

  • Use DEBUG log level only in production — lower log verbosity reduces the chance of PAN appearing in logs
  • Encrypt all log output using AES-256 — even if PAN appears in a log line, it cannot be read without the decryption key
  • Configure Logback to mask any string matching a card number regex before writing — a regex pattern on all log output catches accidental PAN logging without requiring every developer to remember to mask manually
  • Three layers: (1) Never log PAN — code review checklist item, static analysis rule (Checkstyle custom rule: flag log statements containing cardNumber/pan/cvv variables). (2) Tokenise on ingestion — PAN enters the system at one point, is immediately tokenised (PAN → token), and the token is what flows through the rest of the system. No downstream code ever has PAN to accidentally log. (3) Log masking as safety net — Logback PatternLayout with a custom converter that detects and masks 13-16 digit sequences matching Luhn algorithm before writing to any appender. Defence in depth: policy + architecture + tooling.
Tokenisation is the architectural answer — it removes PAN from the data flow entirely so downstream services never have it to log. This is the PCI-DSS preferred approach. But tokenisation alone doesn't cover the initial ingestion point (the gateway controller that first receives the card number). That's where code review rules and static analysis apply. Log masking as a safety net catches accidental logging in any layer. Using only log level control (option A) doesn't prevent PAN logging — it just reduces log volume. Encryption (option B) doesn't prevent compliance issues — PCI-DSS requires PAN not be stored unmasked, even in encrypted logs, because the encryption key becomes a compliance scope expander.
