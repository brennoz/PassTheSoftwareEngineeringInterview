pricing-service — Deep Dive (Odds Calculation + Redis Caching)

Category: Projects · Topic: ARM BettingCo · Est. time: 20 min · Lesson 5 of 13 · Deep Dive

Role

pricing-service receives raw odds from feed handlers (via Kafka), runs ARM's pricing algorithm to produce adjusted odds (factoring overround and liability exposure), and caches the results in Redis for sub-millisecond reads by sportsbook-service. It is the computation engine of the platform — turning raw bookie data into ARM's official prices.

Redis Caching Strategy

The Redis cluster has 6 nodes (3 primaries + 3 replicas, bitnami/redis-cluster in local dev, AWS ElastiCache in production). Consistent hashing distributes keys across the three primaries. Replica per primary means the cluster survives one node failure with automatic promotion.

Why Redis over PostgreSQL for live odds? sportsbook-service pushes price updates to thousands of WebSocket subscribers on every odds change. During the Grand National, that could be tens of thousands of connected clients, each needing the current odds on every tick. A PostgreSQL query per subscriber per update would collapse the database under this read load. Redis reads are O(1) and sub-millisecond — the only viable path for live odds at racing scale.

Odds Calculation — Conceptual

pricing-service receives raw bookie odds for the same runner from multiple feed handlers simultaneously (e.g. Betfair 3.50, SIS 3.60, Tote 3.40 for the same horse). The ARM pricing algorithm:

  1. Weight prices by bookie reliability and trading volume
  2. Calculate overround — the sum of (1/price) for all runners in a race. A value above 100% represents the bookmaker's margin (e.g. 110% = 10% margin)
  3. Adjust for ARM's own liability exposure (from liability-scheduler-service via Kafka — limits how much ARM owes on any one runner)
  4. Publish the final ARM-adjusted price to event-service, which fans it out via Kafka

Consumer Group and Kafka Partition Design

Consumer group: test-local-arm.pricing-service-armdev. Kafka distributes topic partitions across all pods in the consumer group.

Scenario: 4 Kafka partitions, 4 pricing-service pods Pod 1 → Partition 0 Pod 2 → Partition 1 Pod 3 → Partition 2 Pod 4 → Partition 3 (full parallelism — each pod processes independently) Scenario: 4 Kafka partitions, 3 pods (HPA hasn't scaled yet) Pod 1 → Partitions 0, 1 Pod 2 → Partition 2 Pod 3 → Partition 3 (one pod handles 2 partitions — still works, slightly less even throughput) Scenario: 4 Kafka partitions, 6 pods (HPA over-scaled) Pod 1–4 → one partition each Pod 5, 6 → idle (Kafka cannot assign more consumers than partitions) (scaling beyond partition count wastes resources)
Partition count limits horizontal scaling You cannot scale a Kafka consumer group beyond the number of topic partitions. If arm-dev.event-service.json has 4 partitions, adding a 5th pricing-service pod gives you nothing — the 5th pod sits idle. Partition count must be planned in advance (Kafka does not support reducing partitions). Always set partition count to the maximum expected consumer scale.

Java Reactive Streams — Live Pricing Pipeline

pricing-service uses RxJava 3 (io.reactivex.rxjava3) to model the live odds computation pipeline as a reactive event stream. Every GPS update, every race state change, every ARM platform notification flows through an observable chain — giving the service non-blocking, backpressure-aware processing without a thread-per-request model.

RxJava 3, not Spring WebFlux Spring WebFlux (Project Reactor: Flux/Mono) targets reactive HTTP request/response pipelines. pricing-service does not serve reactive HTTP — it consumes Kafka messages and runs a computation pipeline internally. RxJava 3 provides richer stream-composition operators (buffer(boundary), groupBy(), replay()) and per-stream backpressure strategies, making it a better fit for an event-processing engine. Both are Java Reactive Streams-compliant (JDK java.util.concurrent.Flow / org.reactivestreams.Publisher), but the operator vocabulary differs.

Hot Observables — the pricing job bus

Two PublishSubject instances form the backbone of the in-running pipeline:

// PricingService constructor — actual source code
pricingJobSubject = PublishSubject.create();     // receives GPS position jobs
pricingTriggerSubject = PublishSubject.create(); // ad-hoc trigger (faller detected, etc.)

// replay() buffers the last 3 seconds for late-joining subscribers
pricingJobObservable = pricingJobSubject
    .replay(3000, TimeUnit.MILLISECONDS)
    .refCount();

PublishSubject is a hot observable: it emits regardless of whether anyone is subscribed. The replay(3000ms) operator adds a sliding window buffer — if a pod restarts or a new race subscription is created slightly late, it can receive the last 3 seconds of GPS jobs rather than starting cold. refCount() makes the multicast connection reference-counted: the shared upstream activates when the first subscriber joins and tears down when the last leaves, preventing threads from running indefinitely with no consumers.

Per-race buffering — the 1-second pricing window

GPS position updates arrive many times per second. Each pricing computation is expensive (calls the in-play algorithm service over HTTP). The service batches GPS jobs over a 1-second window and processes them together:

// setupJob() — called once per race on transition to in-running
pricingJobObservable
    .filter(job -> paRaceId == job.paRaceId())   // isolate this race's stream
    .retry()                                      // resubscribe on error
    .buffer(observer -> setupTrigger(paRaceId, observer)) // custom boundary
    .observeOn(Schedulers.from(pricingPool))      // offload to thread pool
    .subscribe(jobs -> processJobs(race, jobs), ...);
// setupTrigger() — emits a boundary signal every 1s AND on ad-hoc events
private void setupTrigger(long paRaceId, Observer<? super Long> observer) {
    CompositeDisposable sub = new CompositeDisposable();
    // fixed 1-second timer closes the current buffer window
    sub.add(Observable.interval(0L, 1000L, TimeUnit.MILLISECONDS)
                      .subscribe(observer::onNext));
    // event-driven trigger closes the window early on a faller/event change
    sub.add(pricingTriggerSubject
        .subscribeOn(Schedulers.newThread())
        .filter(id -> paRaceId == id)
        .subscribe(observer::onNext));
    observer.onSubscribe(sub);
}

buffer(boundaryIndicator) collects all upstream items between consecutive emissions from setupTrigger into a List<Job>, then delivers the list downstream. The result: processJobs() receives every GPS snapshot that arrived in the last second and uses the freshest data — trading up to 1 second of latency for a dramatic reduction in algorithm service calls. Without this buffering, every GPS tick (potentially 10+ per second) would fire a separate HTTP round-trip to the in-play model.

Why buffer(), not window() or debounce()? window() emits an inner observable per period — correct semantics but heavier allocation when you only need the collected list. debounce() waits for a quiet period — wrong here because GPS updates arrive continuously during a race; debounce would fire only when the race ends. buffer(boundary) fires on a fixed clock regardless of upstream traffic: predictable 1-second price ticks with bounded latency.

BackpressureStrategy.LATEST — race state subscriptions

Each race has a PublishSubject<RaceInfo> that emits whenever race state changes (start signal received, suspension, faller update). PricingService.subscribeToRace() subscribes to it:

raceInfoSubject
    .toFlowable(BackpressureStrategy.LATEST) // if slow, keep only newest
    .retry()
    .observeOn(Schedulers.from(raceProcessorPool))
    .subscribe(this::processRace, ...);

BackpressureStrategy.LATEST: if the downstream processor (processRace) is slower than upstream emissions, all queued items are dropped and only the most recent survives. This is safe here because RaceInfo is a complete snapshot — each emission carries the full current state of the race, not an incremental delta. Processing a stale snapshot after a newer one has arrived would produce incorrect pricing decisions (e.g. treating a resumed race as still suspended). Contrast with BUFFER (queue everything — wrong: memory grows unbounded during a burst) or DROP (discard the newcomer — wrong: the newest snapshot is the most important one).

ARM update sharding — RaceService

When pricing-service writes price updates back to the ARM platform, it cannot block the pricing thread (a REST call to eventsApi.patchEventInplay() can take tens of milliseconds). RaceService serialises these writes through a reactive pipeline with parallel sharding:

// RaceService constructor — actual source code
armUpdateSubject
    .observeOn(Schedulers.from(armUpdateExecutor))
    .filter(dto -> dto.getId() != null)
    .groupBy(dto -> dto.getId() % 997)          // hash event ID into 997 shards
    .toFlowable(BackpressureStrategy.MISSING)
    .flatMap(group ->
        group.toFlowable(BackpressureStrategy.MISSING)
             .onBackpressureBuffer(
                 1,                             // one pending update per shard
                 () -> logfmt().info(log, "Skip oldest dto"),
                 BackpressureOverflowStrategy.DROP_OLDEST
             )
             .observeOn(Schedulers.io(), false, 1) // prefetch=1, bound memory
             .doOnNext(dto ->
                 eventsApi.patchEventInplay(dto.getId(), dto))
    )
    .retry()
    .subscribe();
Design choiceWhy
groupBy(id % 997) Events for the same ARM event ID always land in the same shard → sequential ordering within a race. Different races use different shards → concurrent ARM calls. 997 is prime to minimise hash collisions across the typical event ID range.
onBackpressureBuffer(1, DROP_OLDEST) Each shard buffers at most 1 pending update. If a new price arrives before the previous REST call completes, the old one is dropped. Correct for pricing: the latest odds are always the right ones to send; a stale price dispatched 50ms late is wrong.
observeOn(Schedulers.io(), false, 1) prefetch=1 keeps at most one item in-flight per shard thread, preventing the scheduler from pulling ahead and buffering stale prices in memory.

Disposable lifecycle — per-race resource management

Every reactive subscription returns a Disposable. Leaking disposables means threads and memory are held for finished races. pricing-service tracks them explicitly per-race:

// On race going in-running — register subscriptions
jobSubscriptions.computeIfAbsent(paRaceId, this::setupJob);
raceInfoSubjectSubscriptions.computeIfAbsent(paRaceId,
    id -> raceInfoSubject.toFlowable(BackpressureStrategy.LATEST)
                         .retry()
                         .observeOn(Schedulers.from(raceProcessorPool))
                         .subscribe(this::processRace, ...));

// On race finishing — dispose all resources atomically
subscription.dispose();
raceInfoSubjectSubscription.dispose();
raceService.getRaceInfoSubjects().remove(paRaceId);
inPlayAlgorithmService.removeRaceApiService(paRaceId);
stickyPricingService.cleanUp(paRaceId);

The close() method (implementing java.io.Closeable) disposes all remaining subscriptions on shutdown — important for graceful pod termination in Kubernetes, where SIGTERM must allow in-flight price calculations to complete before the pod is removed from the load balancer.

The dumySubscription (a dummy subscriber kept alive on pricingJobObservable) doubles as a health signal: the HealthIndicator implementation checks whether it has been disposed or has terminated with an error. If so, the pod reports DOWN and Kubernetes removes it from service discovery until it recovers.

Quiz

Q1. websocketEventMessageCache has a 15-minute TTL. Why not 1 minute (fresher) or 1 hour (fewer cache misses)?

  • 15 minutes is the Redis cluster default TTL and cannot be changed
  • 1-min TTL causes frequent cache misses — each expiry forces re-serialisation of the same event for thousands of subscribers; 1-hour risks serving stale odds during a live race where prices change every few seconds; 15 min is the practical balance
  • Redis cannot store serialised STOMP messages for longer than 15 minutes
  • 15 minutes matches the average duration of a horse race
TTL design is a tradeoff between cache freshness (low TTL) and cache hit rate (high TTL). For live race data, odds change every few seconds — a 1-hour TTL would serve wrong prices. For the pre-serialised STOMP cache specifically, the payload IS refreshed on every odds update (cache is invalidated and re-written), so 15 min is a fallback expiry, not the actual refresh interval. It protects against memory leaks from orphaned cache keys for events that ended.

Q2. pricing-service has 3 pods and the Kafka topic has 4 partitions. What happens to partition assignment?

  • Kafka queues the 4th partition until a 4th pod joins the consumer group
  • One pod is assigned 2 partitions and processes them concurrently; the other two pods get 1 partition each — all messages are still consumed, just with slightly uneven load distribution
  • Kafka drops all messages on the 4th partition
  • A 4th pod is automatically created by HPA to handle the unassigned partition
Kafka consumer group rebalancing distributes all partitions across available consumers. With 4 partitions and 3 consumers, one consumer gets 2 partitions. This consumer processes both partitions with slightly more load — not a problem unless the partition with 2 is consistently higher-volume. To get 1:1 partition-to-pod mapping, scale to exactly 4 pods or change the partition count (which requires topic recreation).

Q3. Why does pricing-service cache odds in Redis rather than having sportsbook-service query PostgreSQL directly for each odds update?

  • PostgreSQL is deployed in a different AWS VPC and is unreachable from sportsbook-service
  • Redis reads are O(1) sub-millisecond; a PostgreSQL query per WebSocket subscriber per odds tick would collapse the database under live race traffic — Redis is the only viable path at scale
  • sportsbook-service is not allowed to have a JDBC connection in the hexagonal architecture
  • PostgreSQL cannot handle concurrent reads from more than 100 connections
Consider the scale: 10,000 WebSocket subscribers × every odds change (every few seconds during a live race) × a PostgreSQL query each = tens of thousands of queries per second to a single DB. PostgreSQL connection pools are measured in hundreds. Redis handles millions of O(1) GET/SET operations per second. The caching layer is not an optimisation — it's required for the system to function at racing scale.

Q4. pricing-service uses RxJava 3 (PublishSubject, buffer, groupBy) rather than Spring WebFlux (Flux/Mono). What is the primary reason?

  • Spring WebFlux is not compatible with Spring Boot 3.x and cannot be used in this project
  • pricing-service is an internal event-processing engine — it consumes Kafka messages through a computation pipeline, not HTTP requests. RxJava 3 provides stream-composition operators (buffer with custom boundary, groupBy sharding, replay window) better suited to this model than WebFlux's request/response abstractions
  • RxJava 3 is faster than Project Reactor for all use cases in Spring Boot services
  • Spring WebFlux requires a reactive database driver and PostgreSQL does not have one
Both RxJava 3 and Project Reactor implement the Reactive Streams specification (Publisher/Subscriber contract), so they are interoperable at the boundary. The distinction is purpose: WebFlux (Reactor) is optimised for reactive HTTP pipelines — request in, response out. RxJava 3 has a richer operator vocabulary for event-driven computation pipelines: buffer(boundary) for batching, groupBy() for parallel sharding with per-key ordering, replay() for late-subscriber buffering. pricing-service needs all three of these; WebFlux Flux doesn't have direct equivalents for all of them without composition overhead.

Q5. The raceInfoSubject.toFlowable(BackpressureStrategy.LATEST) call in subscribeToRace() means that if the downstream processor is slow, intermediate race state emissions are dropped and only the most recent is kept. Why is this safe, and what would go wrong with BackpressureStrategy.BUFFER?

  • LATEST is safe because race state events are immutable; BUFFER would be safe too but is avoided for performance reasons
  • LATEST is safe because Kafka guarantees that each RaceInfo emission carries only the delta change; BUFFER would replay all deltas and cause double-processing
  • Each RaceInfo emission is a complete snapshot of the current race state, not a delta — processing an older snapshot after a newer one arrived would produce stale pricing decisions. BUFFER would allow unbounded memory growth during a burst of state changes (e.g. rapid start + faller + suspension signals during a chaotic race start)
  • LATEST is only safe when the RaceInfo object is thread-safe; BUFFER is the correct choice when RaceInfo contains mutable state
RaceInfo is a snapshot — every emission is a complete picture of the race at that moment. If processRace() is slow and 5 RaceInfo snapshots queue up, you only care about snapshot 5 (the current truth). Snapshots 1–4 are stale and processing them would trigger pricing logic based on outdated state. BUFFER (queue everything) would process all 5 sequentially — the first four produce wrong decisions, and memory grows without bound if the backpressure builds. DROP (discard the newcomer) is also wrong: the latest snapshot is the most important one. LATEST is the correct semantic for state-snapshot streams.
