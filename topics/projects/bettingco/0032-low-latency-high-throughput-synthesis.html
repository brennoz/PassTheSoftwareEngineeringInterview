Low Latency & High Throughput — How ARM Actually Did It

Synthesis across pricing-service, feed-handler-betfair, event-service, MSK/Kafka config, Helm values · every claim below cites a real file · cross-refs: 0005 · 0008 · 0009 · 0011 · 0030
Why this question gets asked as one question, not five "How did you achieve low latency and high throughput?" is the single most common technical-deep-dive question for a real-time risk/pricing system. A weak answer lists buzzwords (Kafka, Redis, caching). A strong answer names the specific tradeoff made at each layer, why it was correct for this domain (live odds must reflect the newest state, stale data is actively dangerous), and is honest about what wasn't built. This lesson assembles that answer from verified source, not from a generic system-design template.
The one-sentence version ARM didn't chase raw speed — it chose freshness over completeness everywhere on the hot path (drop stale data rather than queue it), and used ordering guarantees to avoid needing horizontal scale on the core pricing pipeline (keyed Kafka partitions instead of more replicas).
1
Kafka ordering via event-ID keying, not partition count
lib-events/Broadcaster.java:131-133

Every event/odds update is published with the event's own ID as the Kafka key:

var key = String.valueOf(eventDto.getId());
kafkaEventsTemplate.send(topic, key, message);

Kafka guarantees ordering only within a partition. Keying by eventId means every update for one race always lands on the same partition and is consumed in the order it was produced — without a lock, a sequence number, or a distributed coordinator. This is the single load-bearing decision that makes the rest of the architecture possible: because ordering is solved per-event by the key, most topics only need 1-4 partitions (arm-config/prod/msk/topics.tf:12-192). The one outlier is arm-prod.bet-builder-service.simulations at 128 partitions (topics.tf:77-82) — an embarrassingly-parallel Monte-Carlo-style workload with no per-race ordering requirement, so it gets brute-force parallelism instead.

WHAT BREAKS WITHOUT THIS Round-robin partitioning (no key) spreads one race's updates across all partitions. Two consumers could then process "runner scratched" and "race suspended" out of order — the UI briefly shows a scratched runner as active, or a bet gets accepted on a suspended market. In a betting platform that's not a display bug, it's a liability.
2
Producer tuned for latency, not durability
application.yml — pricing-service, sportsbook-service, event-service-odds-matrix, feed-handler-betfair

KAFKA_PRODUCER_ACKS: 1 (not all) and KAFKA_PRODUCER_ENABLE_IDEMPOTENCE: false, set consistently across the hot-path services. acks=1 only waits for the partition leader to write the record — not for in-sync replica acknowledgement — which is faster but means a leader crash before replication can lose the last unreplicated message.

No linger.ms, batch.size, or compression.type override was found anywhere in the repo — these run on Kafka client defaults. Throughput here comes from partitioning and consumer-side batching (technique 3), not producer-side batching. That's a deliberate structural choice: batching on the producer trades per-message latency for fewer, bigger requests; ARM instead keeps producer latency low and does the batching downstream, closer to where CPU-heavy processing happens anyway.

WHY THIS IS DEFENSIBLE, NOT SLOPPY A momentary live-odds message loss is self-healing — the next GPS/price tick a fraction of a second later supersedes it (see technique 5, freshness-over-completeness). A payments platform would make the opposite tradeoff (acks=all, idempotent producer) because a lost payment event is not self-healing. Naming this contrast is exactly the kind of domain-aware answer a senior interview is listening for.
3
Consumer batching sized per feed criticality
feed-handler-betfair/application.yml:24-31,124 · event-service-woods/application.yml:73-74

concurrency: 3                 # concurrent listener threads per pod

# event-service-liability-multiplier — lower volume, tuned down accordingly

This isn't one blanket config copy-pasted everywhere — max-poll-records ranges from 25 (racecards handler) to 50,000 (Betfair/woods exchange feeds), matched to actual per-feed message volume. All three ConcurrentKafkaListenerContainerFactory beans in feed-handler-betfair/config/KafkaConsumerConfiguration.java:48-105 use setBatchListener(true) — the listener receives a List<ConsumerRecord>, not one record at a time, which is what makes technique 4 possible.

4
Squashing — freshness over completeness on ingest
feed-handler-betfair/kafka/AbstractSquashingListener.java:32-124

Given a batch of Betfair records, the listener groups by event → market → runner and keeps only the last record per runner before processing ("Squashed {} messages to 1", line 85). A runner can emit many price ticks per second during a live race; only the newest one matters for pricing. Each surviving event-group is then dispatched via CompletableFuture.supplyAsync(..., taskExecutor) — fork/join over a bounded pool, not reactive streams.

WHAT BREAKS WITHOUT THIS Processing every tick serially means the pricing pipeline falls permanently behind during a busy race — by the time tick #40 is priced, tick #200 has already arrived. Squashing guarantees the pipeline is always working on the latest known state, even under load, at the cost of intentionally discarding intermediate ticks that were already stale by the time they'd be processed.
5
RxJava backpressure inside pricing-service — same principle, different layer
pricing-service — see 0005 for full source

Technique 4 squashes at the Kafka-consumption boundary. Inside pricing-service the identical philosophy repeats one layer deeper, using RxJava 3:

  • buffer() collects GPS ticks into a fixed 1-second window before running the (expensive, HTTP-bound) pricing algorithm — trading up to 1s of latency for a large cut in algorithm-service calls.
  • Race-state snapshots use BackpressureStrategy.LATEST — if the processor falls behind, queued snapshots are dropped and only the newest survives, because each snapshot is a complete state (processing a stale one after a newer one arrived would be actively wrong, e.g. treating a resumed race as still suspended).
  • Writes back to the ARM platform are sharded by groupBy(id % 997) (prime, minimises collisions) with onBackpressureBuffer(1, DROP_OLDEST) per shard and prefetch=1 — at most one pending, always-freshest update per event in flight at a time.

Full source walkthrough with the design-choice table (why buffer() not debounce() or window()) is in 0005-pricing-service.html. The point to make in an interview: this is the same architectural decision made twice, at the transport layer (Kafka squashing) and the compute layer (RxJava backpressure) — a consistent, repeated principle, not two unrelated tricks.

6
Near-cache: Caffeine (L1) + Redis (L2) + Kafka-broadcast invalidation
lib-utils/caching/CompositeRedisCacheWriter.java:23-131

CompositeRedisCacheWriter wraps Spring's Redis cache writer with a Caffeine layer in front. Reads check Caffeine first, fall back to Redis on miss and warm the local cache. Every write (put/remove/clean) calls evictLocalCache(...), which publishes an eviction event through CompositeCacheBroadcaster onto a dedicated Kafka topic (arm-prod.local-cache, arm-config/prod/msk/topics.tf:194-196) — so a write on one pod invalidates every other pod's Caffeine copy without sticky routing or a shared-lock scheme.

This is a genuinely different pattern from the Caffeine-only websocket caches covered in 0030/0011 — those are single-pod, short-TTL, eventually-stale-is-fine caches. This one is a coherent cross-pod near-cache for config/pricing lookups where staleness after a write would actually be wrong.

7
Redis as shared live state, not just a cache
liability-scheduler-service/processor/impl/LiabilityCacheBetProcessor.java:22-89

Individual bet DTOs are written into a Redis hash keyed per event (liabilityBetsCache::<eventId>, field = betId) via opsForHash().put/.delete. Every pod reads and incrementally updates the same canonical, low-latency liability-exposure structure — instead of recomputing total exposure from Postgres on every bet. This is the throughput technique for a write-heavy, cross-instance-shared number (total exposure per outcome), as distinct from technique 6's read-heavy config lookups.

8
Java 21 virtual threads for I/O fan-out; fixed pools for CPU/DB work
event-service/config/ThreadConfig.java:20-95 · sportsbook-service/config/AppConfig.java:35-55

Virtual threads (VirtualThreadTaskExecutor) are used specifically for I/O-bound fan-out work: participantNameUpdateExecutor, eventExecutor, betRecommendationExecutor, liabilityMultiplierExecutor. Meanwhile CPU/DB-bound work stays on tuned fixed-size ThreadPoolTaskExecutors (feeds-pricing-executor, in-running-executor, transaction-executor) with externalised core-size config. This is the correct split — virtual threads help when a thread spends most of its life blocked waiting on I/O; they don't help (and can even hide) CPU-bound contention, so ARM didn't blanket-apply them.

A custom ArmExecutor abstraction (lib-utils/execution/ArmExecutor.java:16-111) wraps CompletableFuture fan-out with a config-driven on/off switch — ops can force synchronous execution in an incident without a redeploy. Notably: no Spring WebFlux / Project Reactor anywhere in the repo — the HTTP stack is blocking Spring MVC; reactive-style processing is confined to pricing-service's internal RxJava pipeline (technique 5), not the web layer.

9
Container-aware JVM sizing + fast cold start
arm-chart/values.yaml:137 · sportsbook-service/Dockerfile:6,14,18
JAVA_OPTS: "-XX:+UseContainerSupport -XX:+ExitOnOutOfMemoryError -XX:MaxRAMPercentage=75"

Heap is 75% of whatever the container's memory limit is — not a fixed -Xmx — so heap scales automatically when a service's Helm values change memory limits, with no separate JVM config to keep in sync. ExitOnOutOfMemoryError fails the pod fast on OOM rather than degrading silently through GC thrashing; Kubernetes just restarts it. No explicit GC algorithm flag is set anywhere (implicit G1 on the base JRE image) — only heap fraction and OOM behaviour are tuned explicitly.

Separately, several services use AppCDS (Class Data Sharing): -XX:ArchiveClassesAtExit=./application.jsa at build time, -XX:SharedArchiveFile=application.jsa at runtime. This cuts JVM cold-start time — not a steady-state throughput win, but directly relevant to technique 10 below, where some hot-path services run at exactly one replica and a slow-starting rolling restart is a real availability risk.

10
The core pricing pipeline does NOT horizontally scale in prod
pricing-service, event-service-odds-matrix, feed-handler-betfair — .helm/values-prod.yaml

This is the fact most candidates would not guess, and the one worth leading with in an interview because it shows you understand your own system's real constraints rather than reciting "just add more pods":

pricing-service:            autoscaling.minReplicas: 1, maxReplicas: 1
event-service-odds-matrix:  autoscaling.minReplicas: 1, maxReplicas: 1
feed-handler-betfair:       autoscaling.minReplicas: 1, maxReplicas: 1
feed-handler-betting-world: minReplicas: 1 (maxReplicas inherits chart default = 5)
sportsbook-service:         no autoscaling override — inherits min:1 max:5 @ 80% CPU

The chart default (arm-chart/values.yaml:165-170) supports scaling to 5 replicas. Every hot pricing/odds/feed service explicitly overrides that down to a pinned single replica in prod. pdb.enabled: false is also set on these — no PodDisruptionBudget protects the single pod during a node drain, a real availability tradeoff being made deliberately, not by omission.

Why this is coherent rather than a mistake: technique 1 (event-ID keyed ordering) means correctness already depends on one consumer owning one partition at a time per race. Adding replicas to a service pinned to consume the same low-partition-count topics wouldn't increase throughput — it would just add idle pods, or require re-partitioning (an operationally expensive, hard-to-reverse change, per 0005's partition-planning note). Instead, throughput headroom comes from vertical sizing + in-process concurrency (techniques 3, 4, 5, 8). The one hot-path service that does scale — sportsbook-service — is the client-facing WebSocket fan-out layer, where load is proportional to connected browsers, not to race-event count, so horizontal replicas behind the RabbitMQ STOMP relay (0009) genuinely help.

WHAT THIS COSTS A single pricing-service pod is a single point of failure for the entire live-pricing pipeline during its own restart window (mitigated by AppCDS fast startup, technique 9, and rolling-update maxUnavailable settings — but not eliminated). This is a real, named tradeoff to be honest about in the interview, not glossed over.
11
Postgres: pooled + batched, not sharded or replicated
application.yml HikariCP + Hibernate blocks, near-identical across services
# HikariCP — repeated pattern across services
maximum-pool-size: 20-30      # varies by service
minimum-idle: 5
cachePrepStmts: true
prepStmtCacheSize: 250
useServerPrepStmts: true
leak-detection-threshold: 60000ms

# Hibernate — write-throughput tuning
hibernate.jdbc.batch_size: 30
order_inserts: true
order_updates: true
connection.handling_mode: DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION

DELAYED_ACQUISITION_AND_RELEASE_AFTER_TRANSACTION holds the physical DB connection for the minimum necessary window, freeing it back to the (bounded, 20-30 connection) Hikari pool faster under concurrent load — important because every pod has its own pool and Postgres has a hard max_connections ceiling shared across all of them.

HONEST GAP No read-replica configuration exists anywhere in the repo (verified by repo-wide search). Read throughput scaling relies entirely on the cache tiers (techniques 6, 7), not on offloading reads to a replica. Worth naming unprompted: it shows you know where the actual scaling ceiling is, not just where the caching is.
12
Domain-level circuit breakers instead of resilience4j
FeedPriceService.java:82-87 · Broadcaster.java:111-119 · LatencyService.java:86-117

No resilience4j, @CircuitBreaker, or @TimeLimiter exists anywhere in the codebase (verified). What ARM built instead are three domain-shaped substitutes that protect latency/throughput at the point where staleness or redundancy would otherwise propagate:

  • Feed staleness cutoff — if an incoming market snapshot's snapshotTime is older than now - maxFeedAge (default PT2S), the odds are discarded entirely rather than priced. Protects downstream risk logic from acting on data that's already too old to trust.
  • Revision-based dedup — before broadcasting an event update, Broadcaster compares the event's revision against the last-broadcast revision; if not newer, the send is skipped. Prevents redundant/out-of-order broadcasts from re-triggering downstream pricing recomputation on every subscriber.
  • Latency-triggered auto-suspension — a scheduled job compares ARM-received time vs. upstream time per event; if the gap exceeds a configured threshold, the event's markets are automatically suspended (StatusReason.LATENCY_ARM_PROCESS). This is the closest thing in the repo to a hard SLA-breach circuit breaker, and it's wired directly into the domain risk model rather than being a generic library.

What ARM does have from a library is narrower: Spring Retry (@Retryable, not resilience4j) on the STOMP broadcast path and one named outbound client, plus a shared Kafka consumer exponential-backoff auto-configuration (maxRetries=5) applied to every listener container — retry-with-backoff substitutes for a circuit breaker on the consume side. An aggressive connect-timeout: PT1S on the internal arm.template HTTP client (pricing-service → event-service) is also notable: fail fast rather than hang on a down dependency.

HONEST GAP A generic resilience4j circuit breaker around synchronous inter-service REST calls (e.g. settlement-service → bet-manager, described in 0030) is genuinely absent from the code the repo actually contains — 0030's circuit-breaker section describes the correct pattern to use, not a verified-present one. If asked directly, the honest answer is "we relied on tight timeouts + Kafka backoff + domain-level staleness checks; a formal circuit breaker on the synchronous settlement call would have been the next resilience investment."
13
JSON over the wire, no schema registry
verified via repo-wide grep — zero avro/schema-registry hits

Every Kafka message uses Spring Kafka's JsonSerializer/JsonDeserializer. No Avro, no Protobuf, no schema registry anywhere in lib-events or pa-model — confirmed by repo-wide search, not just an omission from what was read. This explains the deliberately large max.message.bytes overrides (2-3MB) on event/odds topics: JSON payloads carrying full event/market/runner trees are bigger than an equivalent binary encoding would be. Schema/contract enforcement instead happens at the REST/SDK layer via the separate arm-interface-contracts/*-api OpenAPI modules, not at the event-streaming layer.

HONEST GAP JSON is human-debuggable and fast to iterate on (a real advantage during incident response — you can read a message off a topic without a schema registry lookup), but offers no compile-time or registry-enforced compatibility checking. A schema registry (Avro/Protobuf + Confluent/AWS Glue Schema Registry) would be the natural next investment if payload size or accidental breaking changes became a problem.
60-second interview answer "Our biggest single decision was keying every Kafka message by event ID — that gave us per-race ordering for free, which meant we didn't need horizontal scale-out on the core pricing pipeline; pricing-service actually runs pinned at one replica in production. Throughput instead came from consumer-side batching tuned per feed volume, and squashing — dropping superseded price ticks and keeping only the latest, both at the Kafka-consumption layer and again inside pricing-service with RxJava backpressure. For state, we ran a two-tier cache — Caffeine locally, Redis as source of truth, invalidated across pods over a dedicated Kafka topic — plus a separate Redis hash for shared, incrementally-updated liability exposure. On the honesty side: we didn't have a formal circuit breaker library, we leaned on tight timeouts, Kafka retry-with-backoff, and domain-specific staleness cutoffs instead — and we never added Postgres read replicas or a Kafka schema registry, both of which would be the next investments if the platform kept scaling."

Quiz

Q1. Why can pricing-service run at exactly one replica in production without becoming a throughput bottleneck, when the chart default supports scaling to 5?

  • Kubernetes automatically load-balances a single pod across all available CPU cores, so one replica is functionally equivalent to five smaller ones
  • Kafka messages are keyed by event ID, so ordering per race already requires one consumer per partition at a time — adding replicas without re-partitioning wouldn't add usable parallelism, so throughput instead comes from consumer batching, squashing, and in-process concurrency on that one pod
  • pricing-service doesn't do any CPU-bound work, so replica count is irrelevant to its performance
  • Redis handles all the actual pricing computation, so pricing-service itself is just a thin proxy that doesn't need to scale
The event-ID keying (technique 1) is what makes this coherent rather than an oversight: ordering correctness already depends on single-consumer-per-partition-per-race semantics. Given that, more replicas consuming the same low-partition-count topics would sit mostly idle rather than add throughput — you'd need to increase partition count first, which is an expensive, hard-to-reverse operation. ARM instead invested in vertical sizing and in-process concurrency (virtual threads, tuned thread pools, large consumer poll batches, RxJava backpressure) to get throughput out of the one pod it does run.

Q2. The Betfair feed handler's squashing listener collapses a batch of price ticks down to one record per runner before processing, discarding the rest. Why is this the correct tradeoff for live-odds pricing specifically, rather than a risky shortcut?

  • Discarding messages is always fine because Kafka's acks=1 setting means message loss is expected and already tolerated everywhere in the system
  • Betfair sends duplicate messages by design, so squashing is really just deduplication with no information loss at all
  • It reduces network bandwidth costs, which was the primary motivation according to the code comments
  • Each price tick for a runner is a complete snapshot of that runner's current odds, not an incremental delta — so once a newer tick has arrived, every older tick for that runner is already stale and acting on it would produce an outdated price. Discarding superseded ticks and processing only the latest keeps the pipeline working on current information even under high message volume, which matters more for correctness than processing every historical tick would
This is the same principle as RxJava's BackpressureStrategy.LATEST in pricing-service (technique 5) — both rely on messages being full-state snapshots rather than deltas. If Betfair ticks were incremental deltas (e.g. "odds moved +0.1"), squashing would silently corrupt state by skipping intermediate changes. Because they're full snapshots, only the newest one is ever needed, and discarding older ones is free correctness-wise while being a large throughput win under load.

Q3. ARM's Kafka producers use acks=1 and no idempotence, while a payments platform would typically use acks=all with an idempotent producer. What domain difference justifies ARM's choice, and would it still be correct at a payments company like Opayo?

  • ARM's choice is justified specifically because live odds are self-healing — a lost price-update message is superseded by the next tick a fraction of a second later, so the brief inconsistency has no lasting effect. That reasoning does not transfer to payments: a lost payment or settlement event is not self-healing, there is no "next tick" that corrects a missed charge, so a payments platform needs acks=all and idempotent producers to guarantee no event is silently dropped
  • The choice is purely a performance micro-optimisation with no domain justification either way — Opayo should copy the exact same producer settings for consistency
  • ARM's choice is a mistake that should be fixed regardless of domain, since acks=all is strictly better in every scenario
  • acks=1 only affects consumer-side read performance, not producer durability, so the comparison to payments durability requirements doesn't apply
This question tests whether you can articulate *why* a tradeoff was correct for one domain and would be wrong for another — the exact framing a payments-company interviewer is listening for when they ask about a betting-platform project. The technical mechanism (acks=1 = leader-only ack, faster but can lose the last unreplicated message on a leader crash) is domain-neutral; whether that's acceptable is entirely about whether the data is self-correcting.
