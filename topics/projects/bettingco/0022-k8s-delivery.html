Kubernetes Delivery — Zero-Downtime Deployments

Gap Topic — Interview depth expected at Senior level · ARM BettingCo examples throughout

Senior engineers are expected to explain not just what Kubernetes resources exist but how they interact during a deployment: how rolling updates work, what liveness vs readiness probes actually do, why PodDisruptionBudgets matter, and how to diagnose a failed deployment from the command line. ARM BettingCo runs 43+ services on two EKS clusters — this lesson uses that real infrastructure as the anchor.

1. Rolling Update — Step by Step

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1   # at most 1 pod can be unavailable during update
    maxSurge: 1         # at most 1 extra pod can be created above desired count

# For ARM's event-service with replicas: 3:
# Step 1: K8s creates a new pod (v2) → now 4 pods (3 old + 1 new)
# Step 2: New pod passes readiness probe → K8s adds it to Service endpoints
# Step 3: K8s sends SIGTERM to one old pod → pod drains in-flight requests
#          (preStop hook runs; terminationGracePeriodSeconds=30)
# Step 4: Old pod removed from Service endpoints (no new requests sent)
# Step 5: Old pod terminates → back to 3 pods (2 old + 1 new)
# Repeat for remaining old pods.
# Zero downtime: at least 2 old + 1 new serving traffic throughout.
The gap that causes request drops during rolling update Kubernetes removes a pod from Service endpoints immediately on SIGTERM, but iptables rules on nodes update asynchronously — there's a window where traffic still reaches the terminating pod. Fix: add a preStop hook with a short sleep (2-5s) to give iptables time to propagate before the pod actually stops accepting connections. 
# ARM Helm chart — graceful shutdown configuration
spec:
  containers:
  - name: event-service
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 5"]
    # sleep 5s before SIGTERM → gives iptables time to drain new connections
    terminationGracePeriodSeconds: 60
    # 60s total: 5s preStop + 55s for in-flight requests to complete

2. Liveness vs Readiness vs Startup Probes

ProbeFailure actionPurposeARM config
Liveness Restart the pod Detect deadlock / hung process — JVM frozen, infinite loop. If failing, pod is unhealthy beyond recovery. GET /actuator/health (ARM default) · initialDelaySeconds=60 (JVM warmup) · periodSeconds=30 · failureThreshold=3
Readiness Remove from Service endpoints (no restart) Detect not-yet-ready state — still connecting to DB, cache warming, Kafka consumer group rebalancing. Pod stays alive but gets no traffic. GET /actuator/health/readiness · initialDelaySeconds=30 · periodSeconds=10 · failureThreshold=3
Startup Kill pod if startup times out Give slow-starting services (Kafka consumer group join, Liquibase migration) time to start without the liveness probe killing them prematurely. GET /actuator/health · failureThreshold=30 · periodSeconds=10 → allows 5min startup 
livenessProbe:
  httpGet:
    path: /actuator/health        # ARM default — checks full health indicator chain
    port: 8081
  initialDelaySeconds: 60   # wait 60s before first check (JVM startup + Spring Boot init)
  periodSeconds: 30
  failureThreshold: 3       # restart after 3 consecutive failures (90s of failure)
  timeoutSeconds: 5

readinessProbe:
  httpGet:
    path: /actuator/health/readiness  # ARM uses /readiness subpath for readiness only
    port: 8081
  initialDelaySeconds: 30
  periodSeconds: 10
  failureThreshold: 3       # remove from LB after 30s of failure
  successThreshold: 1       # add back after 1 success

# ARM Helm chart defaults (arm-chart/values.yaml):
# livenessProbe path  → /actuator/health (full health check; restarts pod if DOWN)
# readinessProbe path → /actuator/health/readiness (readiness group: DB + Redis + Kafka)

3. HPA — How Autoscaling Works in ARM

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: event-service-hpa
  namespace: arm-dev
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: event-service
  minReplicas: 1
  maxReplicas: 5
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80    # scale up when avg CPU > 80%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60   # wait 60s before scaling up (avoid thrash)
    scaleDown:
      stabilizationWindowSeconds: 300  # wait 5min before scaling down (avoid flapping)
HPA limitation for Kafka consumers — the interview improvement point CPU-based HPA works for request-driven services. For Kafka consumers (bet-manager-service's settlement consumer), CPU may be low while consumer lag is high — more messages waiting than the pod can process, but CPU not yet saturated. Better metric: Kafka consumer lag from the External Metrics API (KEDA — Kubernetes Event-Driven Autoscaling). ARM uses CPU HPA; a senior candidate should flag this and know KEDA exists.

4. PodDisruptionBudget — Zero-Downtime Node Drains

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: event-service-pdb
  namespace: arm-prod
spec:
  selector:
    matchLabels:
      app: event-service
  minAvailable: 2    # at least 2 pods must be available at all times

# Effect: during node drain (kubectl drain / cluster upgrade), Kubernetes
# will not evict a pod if doing so would bring available pods below 2.
# Without PDB: a node drain could kill all 3 event-service pods simultaneously.
# With PDB: only 1 pod evicted at a time, ensuring 2 always available.

# Related: TopologySpreadConstraint ensures pods spread across AZs:
spec:
  topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: event-service
# Prevents all 3 pods landing in eu-west-1a (single AZ failure = full outage)

5. Debugging a Failed Deployment — The Commands You Need

# 1. Check rollout status
kubectl rollout status deployment/event-service -n arm-dev
# "Waiting for deployment event-service rollout to finish: 1 out of 3 new replicas have been updated"

# 2. Describe the deployment to see events
kubectl describe deployment event-service -n arm-dev
# → shows: "ReplicaSet event-service-7f9d8b67c4 is progressing"
# → OOMKilled, ImagePullBackOff, CrashLoopBackOff etc.

# 3. List pods and their status
kubectl get pods -n arm-dev -l app=event-service
# NAME                            READY   STATUS             RESTARTS   AGE
# event-service-7f9d8b67c4-xk2p9  0/1     CrashLoopBackOff   5          3m

# 4. Get logs from crashing pod
kubectl logs event-service-7f9d8b67c4-xk2p9 -n arm-dev --previous
# --previous: logs from the previous container run (the one that crashed)

# 5. Describe the failing pod for K8s events
kubectl describe pod event-service-7f9d8b67c4-xk2p9 -n arm-dev
# → Events section: OOMKilled, FailedMount, Unhealthy (probe failed)

# 6. If the pod is Running but misbehaving, exec into it
kubectl exec -it event-service-7f9d8b67c4-xk2p9 -n arm-dev -- /bin/sh
# → check env vars, test DB connectivity, inspect /tmp

# 7. Check HPA status
kubectl describe hpa event-service-hpa -n arm-dev
# → shows current/desired replicas, last scale event, metric values

# 8. Rollback a broken deployment instantly
kubectl rollout undo deployment/event-service -n arm-dev
# → reverts to previous ReplicaSet (Kubernetes keeps history)
CrashLoopBackOff — how to diagnose Pod starts, crashes, restarts, crashes again. Kubernetes applies exponential backoff (10s → 20s → 40s → ... → 5min). Step 1: kubectl logs <pod> --previous — get the crash log. Step 2: check for OOM (kubectl describe pod → "OOMKilled"). Step 3: check for missing env vars or secrets (application.yml property ${KAFKA_BOOTSTRAP_SERVERS} not set → startup exception). Step 4: check readiness probe configuration — if probe fires before Spring Boot finishes starting, pod gets killed before it's ready.

6. Helm Chart Structure in ARM

# ARM uses a single Helm chart for all services (arm-chart/)
# Values files per environment:
#   values-dev.yaml    → arm-dev namespace, lower resource limits, ECR dev
#   values-int.yaml    → arm-int namespace
#   values-prod.yaml   → arm-prod namespace, higher limits, ECR prod

# Helm upgrade command from GitLab CI:
helm upgrade --install event-service ./arm-chart \
    --namespace arm-dev \
    --values values-dev.yaml \
    --set image.tag=${CI_COMMIT_SHA} \    # pin image to exact commit SHA
    --set replicaCount=2 \
    --wait \                              # wait for rollout to complete
    --timeout 5m                          # fail CI if not ready in 5 minutes

# --install: create if not exists, upgrade if exists (idempotent)
# --wait: blocks until Deployment rollout is complete and pods are ready
# --timeout: CI job fails if pods don't become ready within 5 minutes

Quiz

Q1. ARM's event-service has a readiness probe on /actuator/health/readiness and a liveness probe on /actuator/health (not /liveness — ARM's Helm chart uses the full health endpoint for liveness). During a deployment, a new pod fails its readiness probe 3 times in a row because it's still waiting for Kafka consumer group assignment. What does Kubernetes do?

  • Kubernetes restarts the pod and tries again with a fresh JVM instance
  • Kubernetes keeps the pod running but does not add it to the Service endpoints. No traffic is routed to it. The pod stays alive, waiting to become ready. When Kafka consumer group assignment completes and the readiness probe passes, Kubernetes adds it to endpoints and it starts receiving traffic.
  • Kubernetes marks the deployment as failed and rolls back automatically
  • Kubernetes kills the pod and does not schedule a replacement during the rolling update
Readiness probe failure → removed from Service endpoints (no traffic) but pod stays running. Liveness probe failure → pod restarted. This distinction is critical: a pod that is slow to start should fail readiness (not liveness) so it doesn't get killed during warmup. ARM's readiness probe hits /actuator/health/readiness (which includes DB + Redis + Kafka indicators) while liveness hits /actuator/health (general health). The initialDelaySeconds=30 on readiness gives the pod 30 seconds before the first check — enough for Spring Boot to start but not enough for Kafka rebalancing. A startup probe with a longer window would be more appropriate.

Q2. ARM's prod cluster is being upgraded (node drained). Without a PodDisruptionBudget, what risk exists for sportsbook-service (3 replicas, 1 pod per node)?

  • HPA will prevent all pods from being evicted by scaling up new pods first
  • K8s rolling update strategy (maxUnavailable=1) prevents simultaneous eviction
  • All 3 pods could be evicted simultaneously if all 3 nodes are drained concurrently. Each pod is on a separate node; each node drain evicts its pod immediately. Without a PodDisruptionBudget, Kubernetes has no constraint preventing all 3 pods from being unavailable at once. PDB with minAvailable=2 would prevent the second eviction until the first pod is rescheduled and healthy.
  • K8s always keeps at least 1 pod running during any cluster operation without PDB
Rolling update strategy (maxUnavailable) only applies to Deployments controlled by a rollout. Node drains are voluntary disruptions — they honour PodDisruptionBudgets, not Deployment rolling update constraints. Without a PDB, kubectl drain (or the cluster autoscaler removing nodes) can evict all pods simultaneously. PDB is the correct mechanism to guarantee minimum availability during node maintenance, cluster upgrades, and cluster autoscaler scale-down.

Q3. A new version of bet-manager-service is deployed but the rollout is stuck at "1 out of 3 new replicas have been updated" for 5 minutes. What are the most likely causes and how do you investigate?

  • The HPA has hit maxReplicas and cannot create new pods — scale up maxReplicas
  • The new pod is stuck because: (a) its readiness probe is failing (DB or Kafka connection issue in new version), (b) it's CrashLoopBackOff (startup exception — new config/env var missing), or (c) image pull failure (wrong ECR tag). Investigate: kubectl get pods -n arm-dev → check STATUS. kubectl logs <new-pod> --previous → see startup exception. kubectl describe pod <new-pod> → see K8s events including probe failures and image pull errors.
  • The PodDisruptionBudget is blocking the rollout — temporarily delete the PDB
  • Kubernetes is waiting for the deployment timeout to expire before proceeding
A stuck rolling update almost always means the new pod isn't becoming Ready. The Deployment controller waits for the new pod to pass its readiness probe before terminating an old one (per maxUnavailable). If the new pod never becomes Ready, the rollout stalls. kubectl get pods shows CrashLoopBackOff or 0/1 READY. kubectl logs --previous shows the crash reason. Common causes in real incidents: missing secret/ConfigMap in new version, DB migration failed (Liquibase), new Kafka topic doesn't exist in this environment, or increased memory usage causing OOMKill before readiness.
