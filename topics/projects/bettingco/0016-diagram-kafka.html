ARM BettingCo — Kafka Data Flow

Category: Projects · Topic: ARM BettingCo · Diagram 2 of 4 · Kafka Topics & Consumer Groups

ARM uses two isolated Kafka clusters. The WOODS cluster receives raw bookmaker feeds from 18 external sources — it is intentionally quarantined from internal systems. The BETTINGCO cluster (AWS Managed Streaming for Kafka) carries all internal service-to-service events. No service consumes directly from WOODS except the feed handlers, which normalise and re-publish to BETTINGCO.

Why two Kafka clusters instead of one? WOODS isolates third-party instability. If Betfair sends a burst of malformed messages or goes offline, only the WOODS cluster is affected. Internal BETTINGCO MSK stays clean. Feed handlers act as the bridge — they consume from WOODS, normalise to the ARM canonical model, and publish to BETTINGCO. If a feed handler crashes, no other service is affected — it simply stops publishing on its topic.
at-least-once delivery + idempotency Kafka guarantees at-least-once: a message may be replayed on consumer restart. bet-manager-service prevents duplicate slip placement via a SELECT pre-check on (sportsbookTenantId, sportsbookRef) before INSERT — if a matching row exists, it returns the existing slip ID without creating a new bet. The Broadcaster in event-service tracks a revision per event to prevent out-of-order publishes — if a message arrives with revision N but the current revision is N+1, it is discarded.
