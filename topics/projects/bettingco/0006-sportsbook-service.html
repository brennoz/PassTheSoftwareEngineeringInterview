sportsbook-service — Kafka→STOMP Bridge

Category: Projects · Topic: ARM BettingCo · Est. time: 25 min · Lesson 6 of 30 · Deep Dive

Role

sportsbook-service (port 8082) is the real-time bridge between ARM's internal Kafka event stream and browser clients. It consumes five Kafka topics, applies per-topic change-detection caching, and pushes updates to connected browsers via STOMP over WebSocket. Tenant authorisation is enforced on every STOMP SUBSCRIBE frame. In production the STOMP broker is backed by RabbitMQ; in development Spring's in-memory SimpleBroker is used.

Kafka Consumers — Five Topics, Batch Mode

All five listeners are in batch mode (setBatchListener(true) in KafkaConfig) and conditionally enabled via @ConditionalOnProperty. A GenericConsumerInterceptor propagates JWT/tenant context from Kafka message headers into the thread-local MDC.

Listener classListener IDDefault topicPayload
EventServiceKafkaListener arm-events-sportsbook arm-dev.event-service.json MessageDto — full event/market/outcome updates
EventServiceKafkaListener arm-events-sportsbook-inplay arm-dev.event-service-inplay.json MessageDto — in-running price updates only
BetSettlementKafkaListener arm-bets-sportsbook arm-dev.bet-updates.json BetDto — bet status changes (placement, settlement)
BetRecommendationKafkaListener arm-bet-recommendation-sportsbook test-local.arm-dev.bet-recommendations BetRecommendationDto

Consumer group: test-local-arm.sportsbook-service-armdev (dev profile overrides to test-local.roberto.arm.sportsbook-service-armdev).

WebSocket / STOMP — Dual Broker Mode

sportsbook-service supports two broker modes, controlled by the ws.simple-broker property (default: true):

Dev default: SimpleBroker (in-memory), NOT RabbitMQ When ws.simple-broker=true (the default in application.yml), Spring's in-memory SimpleBroker handles message routing. RabbitMQ relay only activates when ws.simple-broker=false is injected via env var in production. Running locally you are NOT using RabbitMQ for STOMP.

SimpleBroker mode (dev, default)

Spring's built-in broker routes messages in-process. Heartbeat and destination prefix config is still applied. No external dependency.

RabbitMQ relay mode (production)

When ws.simple-broker=false:

registry.enableStompBrokerRelay("/topic", "/queue")
        .setRelayHost("rabbitmq-ha")
        .setRelayPort(61613)
        .setVirtualHost("/")
        .setClientLogin(...)
        .setClientPasscode(...)

The STOMP relay sends frames from Spring's message broker to RabbitMQ's STOMP plugin, which manages durable queue bindings, routing, and delivery to connected clients. This enables true fan-out at scale: multiple sportsbook-service pods can all relay to the same RabbitMQ cluster.

STOMP endpoint config (both modes)

  • Endpoint: /ws with withSockJS()
  • Heartbeat: server=10000ms, client=10000ms
  • Heartbeat scheduler: ThreadPoolTaskScheduler named wss-heartbeat-thread-, pool size 1
  • Application destination prefix: /app
  • HttpHandshakeInterceptor — captures client IP from X-Forwarded-For header on SockJS handshake (used in access logs / audit)
  • MarshallingMessageConverter added alongside default Jackson converter (XML marshalling for certain feed formats)

TopicSubscriptionInterceptor — Per-SUBSCRIBE Authorisation

Every STOMP SUBSCRIBE frame passes through TopicSubscriptionInterceptor (a ChannelInterceptor registered via configureClientInboundChannel) before reaching the broker:

STOMP SUBSCRIBE frame received │ ├─ Extract JWT from Authorization header → authenticate │ ├─ topicService.needsAuthorization(destination)? │ NO → allow through │ YES ↓ │ ├─ Validate JWT tenant exists ├─ topicService.hasAccess(tenant, destination)? │ NO → throw MessageDeliveryException (connection rejected) │ YES ↓ │ ├─ Validate tenant.deliveryMethod == WEBSOCKET │ (HTTP/FTP tenants cannot subscribe) │ └─ Set x-queue-name native STOMP header: authenticated → "{tenantId}_{tenantName}_{topic}_{UUID}" anonymous → "{topic}_{UUID}"

The x-queue-name header tells the RabbitMQ STOMP plugin which queue to use for this subscription — ensuring each tenant gets its own isolated queue on the RabbitMQ broker rather than sharing a queue across all subscribers to the same topic destination.

Change-Detection Cache — Three Caches, Not Serialisation

The previous description of this cache was wrong. The cache is NOT for pre-serialisation of STOMP messages. It is a deduplication / change-detection layer to suppress unnecessary broadcasts.

WebsocketMessageDeliveryService.hasChanged():

// Stores the EventDto Java object in cache keyed by:
// "{topicName}-{streamId}-{eventId}-{raceCardLevel}"
// If the cached object .equals() the incoming one → return false (skip)
// If different (or not cached) → cache it and return true (broadcast)
cache.put(cacheKey, incomingDto);
return !incomingDto.equals(cachedDto);

When hasChanged() returns false, the broadcast is skipped entirely — no serialisation, no convertAndSend() call. Spring's SimpMessagingTemplate handles the single serialisation internally when a broadcast does happen; it does not serialise per-subscriber.

Cache nameTTLWhat's storedPurpose
websocketEventMessageCache 15 min (PT15M) EventDto object per event/stream/level Horse-racing event deduplication
websocketDogRacingMessageCache configured DogRacingDto object Greyhound racing event deduplication
websocketBetRecommendationMessageCache configured BetRecommendationDto object Bet recommendation deduplication
Default cache manager is Caffeine, not Redis Redis is only used when REDIS_CACHE_ENABLED=true (default: false). In local development all three caches are backed by Caffeine (in-process). Redis (Lettuce, cluster mode) is the production cache manager.

WebsocketBroadcaster — Retry on Delivery Failure

When hasChanged() returns true, WebsocketBroadcaster.broadcast() sends the STOMP frame via SimpMessagingTemplate. The method carries @Retryable:

@Retryable(
    value = MessageDeliveryException.class,
    maxAttempts = BROADCAST_ATTEMPTS_MAX + 1,  // 6 total attempts
    backoff = @Backoff(delay = 500, multiplier = 1.5)
)
public void broadcast(String destination, Object payload, Map<String, Object> headers) {
    // adds "uuid" native STOMP header to every message
    // adds custom headers: arm_timestamp, sport, etc.
    SimpMessageHeaderAccessor accessor = SimpMessageHeaderAccessor.create(SimpMessageType.MESSAGE);
    headers.forEach(accessor::setNativeHeader);
    accessor.setNativeHeader("uuid", UUID.randomUUID().toString());
    template.convertAndSend(destination, payload, accessor.getMessageHeaders());
}

6 attempts with exponential backoff (500ms → 750ms → 1125ms → ...) handles transient RabbitMQ relay disconnections or in-memory broker overload without dropping the message immediately.

sportsbook-publisher — STOMP Client, Not RabbitMQ Producer

sportsbook-publisher (port 8099) is a separate Spring Boot service that acts as a STOMP client, not a server. It connects to sportsbook-service's /ws endpoint and re-delivers messages to external tenant systems via HTTP or FTP.

sportsbook-publisher startup (ApplicationReadyEvent) 1. loginApi.login() → get JWT from auth-service 2. websocketApi.getWsTopics() → get topic list from sportsbook-service REST (/ws-topics) 3. WebSocketStompClient (StandardWebSocketClient + SockJsClient) .connect("{sportsbook-service.url}/ws") 4. afterConnected(): subscribe to each topic (ack: client-individual) Per received STOMP frame: MessageProcessor.processMessage(bytes, headers) → lookup tenant by name → DeliveryMethod == HTTP → HttpMessageSender.send() (REST POST to tenant URL) → DeliveryMethod == FTP → FtpMessageSender.send() NOT RabbitMQ. External tenants are reached via HTTP or FTP.

@Retryable on processMessage(): max 15 attempts per tenant message. Up to 50 reconnection attempts for the WebSocket connection itself. Metrics: rmq_websocket_message_consuming_timings timer per queue/type (the metric name reflects the historical implementation; the transport is now STOMP, not RabbitMQ AMQP).

Quiz

Q1. In the default (application.yml) configuration of sportsbook-service, which WebSocket broker mode is active, and what does that mean for RabbitMQ?

  • RabbitMQ relay is always active; ws.simple-broker defaults to false
  • Spring's in-memory SimpleBroker is active by default (ws.simple-broker=true); RabbitMQ relay is only used when this property is set to false via env var in production — running locally you are not connecting to RabbitMQ for STOMP routing
  • Both modes run simultaneously; messages are fan-out to both the SimpleBroker and the RabbitMQ relay
  • RabbitMQ relay is always required; the property only controls which queue type (/topic vs /queue) is used
The ws.simple-broker flag (default true in application.yml) is a hard branch: when true, enableSimpleBroker() is configured; when false, enableStompBrokerRelay() is configured. They are mutually exclusive. RabbitMQ relay is the production configuration, injected via env var override. Local and dev environments use SimpleBroker with no RabbitMQ dependency.

Q2. What does websocketEventMessageCache actually store, and what is its primary purpose?

  • Pre-serialised STOMP byte arrays — avoids serialising the same message N times for N subscribers
  • STOMP frame strings keyed by destination — Spring's SimpMessagingTemplate reads from this cache instead of serialising
  • EventDto Java objects used for change-detection — if the incoming EventDto equals the cached one, the broadcast is skipped entirely; otherwise the cache is updated and the broadcast proceeds
  • Redis pub/sub channel IDs — maps event IDs to the RabbitMQ routing keys used for fan-out
The cache stores EventDto objects (not serialised bytes). WebsocketMessageDeliveryService.hasChanged() compares the incoming DTO to the cached one via .equals(). If identical, the broadcast is suppressed — zero STOMP frames sent, zero serialisation. This prevents thundering-herd on high-frequency in-running price ticks where many consecutive updates carry the same data. There are three such caches: websocketEventMessageCache, websocketDogRacingMessageCache, and websocketBetRecommendationMessageCache.

Q3. A new external tenant needs to receive ARM odds updates. Their system accepts HTTP POST requests. Which service delivers those updates, and via what mechanism?

  • sportsbook-service pushes directly to the tenant HTTP endpoint via a RestTemplate call inside BetSettlementKafkaListener
  • sportsbook-publisher connects to sportsbook-service as a STOMP client, subscribes to the relevant topics, and when a STOMP frame arrives, HttpMessageSender POSTs the payload to the tenant's endpoint; @Retryable with 15 attempts handles transient failures
  • RabbitMQ delivers messages directly to the tenant HTTP endpoint via a Shovel plugin configuration
  • The tenant must connect directly to sportsbook-service's /ws WebSocket endpoint; HTTP delivery is not supported
sportsbook-publisher is a separate Spring Boot service (port 8099) that acts as a STOMP client. On startup it logs into auth-service, fetches the topic list from sportsbook-service's /ws-topics REST endpoint, then connects to /ws and subscribes. Each received frame is dispatched by MessageProcessor based on the tenant's DeliveryMethod: HTTP → HttpMessageSender, FTP → FtpMessageSender. It does NOT push to RabbitMQ — the historical metric name rmq_websocket_message_consuming_timings is a legacy artefact.
