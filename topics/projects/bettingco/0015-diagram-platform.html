ARM BettingCo — Platform Architecture

Category: Projects · Topic: ARM BettingCo · Diagram 1 of 4 · Platform Overview

ARM BettingCo comprises 43+ Spring Boot 3.5 / Java 21 microservices organised into six bounded contexts. Each context owns its data model, its Kafka topics, and its service(s). External bookmaker feeds arrive on the isolated WOODS Kafka cluster; all internal communication uses BETTINGCO MSK (AWS Managed Streaming for Kafka).

Key Design Decisions

DecisionWhatWhy
WOODS cluster isolationExternal feeds on separate Kafka brokers3rd-party instability (Betfair outages, malformed messages) cannot cascade into internal BETTINGCO MSK
One pod per bookmaker18 independent feed-handler servicesIndependent scaling, failure isolation, independent deployment — Betfair outage doesn't stop SIS feed
lib-events shared libraryEvent, Race, Market as JPA @Entity in JAROne canonical model across all services; avoids duplicate entity definitions; traded hexagonal purity for pragmatic reuse
RabbitMQ for WebSocket relaySTOMP over RabbitMQ, not Kafka directKafka has no concept of "subscriber sessions"; RabbitMQ STOMP relay manages per-connection subscriptions natively
Caffeine (in-process) vs RedisAll caches use Caffeine by default; REDIS_CACHE_ENABLED=false in production values — local composite cache is the hot read pathZero network hop; Redis cluster exists for other use cases (Redisson locks, tenant cache) but the websocket change-detection and price caches stay in-process
Vault for secretsHashiCorp Vault + VaultStaticSecret CRD (not AWS Secrets Manager); 60s refresh, injected via envFrom secretRefGitOps-friendly; secrets as K8s CRDs synced automatically; 60s TTL means rotated credentials propagate without pod restart
Interview talking point: bounded context → no cross-DB reads Each bounded context owns its PostgreSQL schema. bet-manager-service never reads the events table directly — it calls event-service REST API or consumes Kafka events. This anti-corruption layer means the event schema can change without breaking bet-manager. The cost: eventual consistency and network calls instead of SQL JOINs.
