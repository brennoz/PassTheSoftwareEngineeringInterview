bet-manager-service — Deep Dive (Slip Placement, Liability, Settlement)

Category: Projects · Topic: ARM BettingCo · Est. time: 30 min · Lesson 4 of 30 · Deep Dive

Role

bet-manager-service runs on port 8084 (HTTP_PORT:8084) and owns the complete bet lifecycle: slip-based bet placement with idempotency, combinatorial bet explosion, liability tracking, settlement execution, and Kafka publishing. It is the authoritative service for bet state — every bet in ARM flows through it.

Core responsibilities:

  • Slip placement — accepts POST /slips from operators/sportsbooks, validates, persists, and publishes
  • Liability management — tracks per-outcome/market/tenant exposure and suspends markets when thresholds are exceeded
  • Settlement execution — consumes settlement instructions from settlement-service and marks bets won/lost
  • Multi-tenancy — all data scoped to sportsbookTenantId via lib-tenants

The Slip Abstraction

The primary placement endpoint is POST /slips handled by SlipController.createSlip(). A Slip is the container that holds one or more Bet objects. This separation exists because a single customer action (placing a Yankee on four horses) produces one Slip with eleven Bet objects after combinatorial explosion.

Slip (container, one per customer placement request) └── Bet[] (one per combination after BetExplosionService) └── Leg[] (one per selection) └── Part[] (WIN part, PLACE part for each-way) └── eventDetails (market, outcome, price at time of placement)

BetController handles a separate concern: operator confirmation (confirmBet()), status queries, cashout requests, and settlement — not initial placement. Do not confuse the two controllers.

BetType vs LegType/PartType — common confusion WIN, PLACE, and EACH_WAY are not BetType values. They are LegType or PartType values — they describe what a single selection is staked on (win market, place market, or both). BetType describes the combinatorial structure across multiple selections.

Domain Model — Bet Entity

The Bet entity uses a Long primary key with @GeneratedValue(strategy = GenerationType.IDENTITY), not UUID. Market and runner information is not stored as direct foreign keys on Bet — it lives in the Leg → Part → eventDetails hierarchy. Customer ownership goes via Slip.customer (ManyToOne).

// Bet entity — key fields (abbreviated)
@Entity
@NamedEntityGraph("bet-graph")           // avoids N+1 when loading legs/parts
@EntityListeners(MetricsMonitoringService.class)  // wires Prometheus metrics via JPA lifecycle
public class Bet {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    private Slip slip;                   // customer lives on Slip, not directly on Bet

    private BetType betType;             // SINGLE, YANKEE, LUCKY_63, etc.
    private BetStatus betStatus;         // PENDING → APPROVED | DECLINED | CANCELLED
    private SportsbookBetStatus sportsbookBetStatus; // ACTIVE, PARTIALLY_CASHED_OUT, etc.

    private BigDecimal stakeAmount;
    private BigDecimal freeStakeAmount;
    private BigDecimal winningsAmount;
    private BigDecimal potentialWinningAmount;

    @OneToMany private Set<Leg> legs;
    @OneToMany private Set<BetAdjustment> betAdjustments;

    // Rule 4 deductions (horse-racing non-runner withdrawals)
    @OneToMany private Map<BetDeductionType, BetDeduction> betDeductions;

    private String sportsbookRef;        // operator's own reference — part of idempotency key
    private Long recommendedBetId;       // set for BetBuilder / recommendation engine bets
    private Boolean inRunning;
    private boolean earlySettled;
    private boolean resettlementEligible;
}

BetStatus and SportsbookBetStatus — Dual Status

Each bet carries two status fields. They track different concerns:

FieldValuesWhat it tracks
betStatusPENDING, APPROVED, DECLINED, CANCELLED, SETTLED, PARTIALLY_CASHED_OUT, FULLY_CASHED_OUTARM's internal view of the bet outcome
sportsbookBetStatusACTIVE, CANCELLED, PARTIALLY_CASHED_OUT, FULLY_CASHED_OUTThe operator's / sportsbook's view of cashout state
ACCEPTED does not exist. VOID does not exist. The approved state is called APPROVED, not ACCEPTED. There is no VOID status — bets are CANCELLED or DECLINED. Confusing these in an interview signals you are guessing from generic knowledge rather than reading the source.

Placement Flow — SlipService.createSlip()

The full synchronous sequence on POST /slips:

POST /slips (JWT, slip payload with sportsbookRef per bet) │ ▼ SlipController.createSlip() │ ▼ SlipService.createSlip() 1. Resolve tenant → securityService.getPrincipal().getTenantId() 2. Idempotency pre-check (SELECT, not INSERT-then-catch): Optional<Slip> existing = slipRepository.findBySportsbookId(tenantId, sportsbookRef); if (existing.isPresent()) return slipMapper.toDto(existing.get()); ← early return 3. BetExplosionService.explode(slip) ← expand combinatorial BetTypes into individual Bets 4. For each Bet: BetService.populateBet() a. bet.setBetStatus(BetStatus.PENDING) b. betValidator.validate(bet) ← adds errors to bet object if invalid 5. slip.updateBetStatus() └─ bet.updateBetStatus(): if sportsbookBetStatus == CANCELLED → bet.status = CANCELLED else if bet has errors → bet.status = DECLINED else → bet.status = APPROVED 6. slipRepository.save(slip) ← persists slip + all bets in one transaction 7. betMessenger.send(bet, eventCache) ← publishes to Kafka (per approved bet) │ └──▶ Return SlipDto (synchronous — APPROVED/DECLINED status is in the same HTTP response)
Idempotency — SELECT first, not INSERT then catch The idempotency key is a composite of (sportsbookTenantId, sportsbookRef) — the operator's own reference for their slip. Before any write, slipRepository.findBySportsbookId(tenantId, sportsbookRef) checks for an existing record. If found, the existing Slip DTO is returned immediately. There is no idempotency_key UUID column. There is no DataIntegrityViolationException catch. The duplication check is a plain SELECT.

Note that PENDING → APPROVED (or DECLINED) happens synchronously on the same HTTP request, not asynchronously. The status in the response is the final accepted or declined status.

Operator Confirmation — BetController.confirmBet()

After placement, operators can call BetController.confirmBet() to set operatorStatus and optionally update operatorAcceptedOdds per part. This is a separate step from initial slip creation — it models the operator manually reviewing and confirming a bet before it becomes live.

Code: BetSettlementListener

// Source: bet-manager-service/.../kafka/BetSettlementListener.java
@Slf4j
@Component
@RequiredArgsConstructor
@ConditionalOnProperty(name = "kafka.consumer.settlement.enabled", havingValue = "true")
public class BetSettlementListener {

    private static final String ARM_BET_SETTLEMENT = "arm-bet-settlement";  // listener ID, not topic

    private final SettlementService settlementService;
    private final SecurityService securityService;

    @KafkaListener(id = ARM_BET_SETTLEMENT,
                   idIsGroup = false,
                   clientIdPrefix = "${kafka.default.client-id}-${kafka.consumer.settlement.topic}",
                   topics = "${kafka.consumer.settlement.topic}",  // → test-local.arm-dev.bet-settlement
                   containerFactory = "settlementContainerFactory")
    public void consumeBets(final List<BetStatusDto> bets) {
        var eventCache = new EventCache();
        var principal = securityService.getPrincipal();  // tenant from Kafka header via GenericConsumerInterceptor

        bets.forEach(bet -> settleBet(bet, principal, eventCache));
    }

    private void settleBet(BetStatusDto bet, SecurityUserDetails principal, EventCache eventCache) {
        try {
            if (Boolean.TRUE.equals(bet.getSettle())) {
                settlementService.settleBetEarlyResult(bet.getId(), principal,
                        Boolean.TRUE.equals(bet.getIsForEarlySettlement()), eventCache);
            } else if (Boolean.FALSE.equals(bet.getSettle())) {
                settlementService.unsettleBet(bet.getId());
            }
        } catch (Exception e) {
            logfmt().error(log, "Error settling bet {}", bet.getId(), e);  // fail-safe: log and continue
        }
    }
}
// @ConditionalOnProperty lets settlement be disabled per env —
// e.g. dev pods running only pricing logic skip settlement entirely

Liability Management

LiabilityService (500+ lines) is a core responsibility of bet-manager-service, absent from most surface-level descriptions. It tracks per-outcome, per-market, per-tenant, per-channel, and per-currency exposures in the singles_liability table.

The flow after a bet is approved:

slipRepository.save(slip) ← bet persisted with APPROVED status │ └──▶ liabilityService.update(explodedBet) ← @Async on "liability-executor" thread pool │ accumulates stake exposure per outcome │ └── if global liability > win/place limit threshold: suspensionService.suspendEvent(eventId, StatusReason.EXCEEDED_LIABILITY) → market automatically suspended (no more bets accepted on that event)
Why @Async for liability? Liability tracking does not need to block the HTTP response. The bet is already saved and confirmed. Running it on the dedicated "liability-executor" thread pool keeps placement latency low and isolates liability calculation failures from the critical path. The suspension check happens asynchronously — there is a small window where a few bets over the threshold could still be accepted, which is an accepted trade-off for throughput.

LiabilitiesController exposes the current liability data via REST for operator dashboards and risk management tools.

Rule 4 Deductions — Horse-Racing Non-Runner Withdrawals

In UK horse racing, when a horse is withdrawn (non-runner) after bets are placed, Rule 4 of the Rules of Racing mandates a deduction from winning payouts. Rule4Listener consumes test-local.arm-dev.event-rule4-update and applies the deduction to affected bets:

Rule4MessageDto arrives on test-local.arm-dev.event-rule4-update │ ▼ Rule4Listener.consume() │ ▼ PotentialWinningAmountService.updatePotentialWinningAmountOnRule4s() │ recalculates potentialWinningAmount for each affected bet │ └──▶ BetDeduction entity persisted (type = BetDeductionType, amount = deduction %) stored in bet.betDeductions map

BetDeduction entities record each deduction applied, keyed by BetDeductionType. Multiple deductions can accumulate on a single bet if multiple non-runners are declared before the race starts.

Redis — Two Mechanisms

bet-manager-service uses Redis in two distinct ways, both conditionally enabled:

MechanismTechnologyPurposeDefault
Spring Cache (@Cacheable)Lettuce client (cluster mode)Cache tenant data fetched from event-service; enabled by property REDIS_CACHE_ENABLEDfalse
Distributed lockRedisson (RedissonClient)RedissonLockService.lockAndGet() used in CustomerService.createOrUpdateCustomerWithLock() — prevents concurrent upserts of the same customer record; enabled by BET_MANAGER_R_LOCK_ENABLEDfalse
Lettuce vs Redisson — why two Redis libraries? Lettuce is Spring's default reactive Redis client — wired into Spring Cache automatically. Redisson is a higher-level Redis client that provides distributed Lock, Semaphore, and Queue abstractions on top of Redis primitives. Spring Cache can cache data; it cannot provide a distributed lock. Both clients connect to the same Redis cluster but serve different purposes.

Spring Retry — @Retryable Scope

@Retryable appears in one place only: RetryableQuantBetBuilderClient, which calls the Quant BetBuilder (an ML pricing and simulation engine for BetBuilder bets). It is not used for advisory-service (which does not exist in the placement call path) or for event-service.

// Source: bet-manager-service/.../client/RetryableQuantBetBuilderClient.java
@Component
@RequiredArgsConstructor
public class RetryableQuantBetBuilderClient {

    @Retryable(retryFor = BetBuilderRetryableException.class,
               maxAttemptsExpression = "${app.bet-builder.retry.max-attempts}",
               backoff = @Backoff(delayExpression = "${app.bet-builder.retry.backoff-delay}"))
    public BetBuilderPricesDto getPrices(final Long eventId, ...) {
        return getWithRetry(() -> betBuilderApi.getPrices(eventId, ...));
    }

    private <T> T getWithRetry(final Supplier<T> getSupplier) {
        try {
            return getSupplier.get();
        } catch (final RestClientException e) {
            // only retry the specific transient simulation-count error
            if (e.getMessage() != null
                    && e.getMessage().contains("simulations to fulfill request but only have")) {
                throw new BetBuilderRetryableException(e);
            }
            throw e;  // all other errors propagate immediately
        }
    }
}
Why retry only BetBuilderRetryableException? Retrying all exceptions is dangerous — a 400 Bad Request (invalid bet) must not be retried. The BetBuilder engine returns a recoverable error when it does not yet have enough Monte Carlo simulations ready to price a bet. That specific transient case is wrapped in a retryable exception. Every other failure (timeout, 5xx, bad request) propagates immediately. Max attempts and backoff delay are externalised to config so they can be tuned per environment without redeploying.

Multi-tenancy via lib-tenants

ARM serves multiple betting operators from one deployment. Tenant identity flows via JWT:

  • JWT contains tenantId claim; JwtAuthenticationTokenFilter extracts it into SecurityUserDetails.tenantId
  • Services call securityService.getPrincipal().getTenantId() to get the current tenant
  • TenantService.getTenant(tenantId) fetches full tenant config from event-service, cached in Redis with @Cacheable(cacheManager = REDIS_CACHE_MANAGER_BEAN)
  • Kafka consumers receive tenant context via GenericConsumerInterceptor, which propagates the JWT from Kafka message headers into SecurityService

Quiz

Q1. A sportsbook submits POST /slips with sportsbookRef="SLIP-999". The network drops the response before the client receives it. The client retries with the same payload and sportsbookRef. What does bet-manager-service do on the second call?

  • A second Slip is created; duplicate bets are placed on both slip records
  • SlipService.createSlip() runs slipRepository.findBySportsbookId(tenantId, "SLIP-999") before any write; the existing Slip is found and its DTO is returned immediately — no second insertion occurs
  • The INSERT fails on a UNIQUE constraint on idempotency_key; DataIntegrityViolationException is caught and the original record is returned
  • The second request returns HTTP 409 Conflict and the client must use a different sportsbookRef
Idempotency in bet-manager-service is a pre-check SELECT on (sportsbookTenantId, sportsbookRef). If a Slip with that composite key already exists, the existing DTO is returned immediately and the method returns early. There is no UUID idempotency_key column, no UNIQUE constraint catch, and no 409 response. The client can retry safely any number of times.

Q2. A customer places a YANKEE bet (4 selections). How many Bet rows are persisted after BetExplosionService runs?

  • 1 — one Bet with 4 Legs
  • 4 — one Bet per selection
  • 11 — 6 doubles + 4 trebles + 1 fourfold
  • 15 — every combination including singles
A YANKEE covers all doubles, trebles, and the fourfold from 4 selections: C(4,2)=6 doubles + C(4,3)=4 trebles + C(4,4)=1 fourfold = 11 combinations. BetExplosionService creates one Bet entity per combination, each with its own Legs, stakes, and status. A PATENT would give 7 (adds 3 singles); a LUCKY_15 would give 15 (PATENT + fourfold).

Q3. After a bet is approved and saved, liability tracking runs @Async on the "liability-executor" thread pool. What happens if the accumulated liability exceeds the configured win threshold for an event?

  • The last approved bet is rolled back and its status changed to DECLINED
  • A Kafka event is published to bet-updates.json asking settlement-service to void affected bets
  • LiabilityService throws an exception that bubbles up to the HTTP response as HTTP 429
  • suspensionService.suspendEvent(eventId, StatusReason.EXCEEDED_LIABILITY) is called, automatically suspending the market so no further bets are accepted on that event
Liability tracking is asynchronous — it runs after the HTTP response is sent, so it cannot modify the response or roll back the transaction. Instead, when global liability for an event exceeds the threshold, suspensionService.suspendEvent() is called. This suspends the market going forward. Bets already accepted remain valid; only new bets on that event are blocked until the operator reviews and re-opens the market.
