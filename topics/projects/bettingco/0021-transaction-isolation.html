Transaction Isolation Levels

Gap Topic — Interview depth expected at Senior level · ARM BettingCo examples throughout

Transaction isolation is one of the most probed senior-level topics. Interviewers expect you to name the four levels, know which anomalies each prevents, give a concrete example of where each matters, and explain how Spring's @Transactional maps to database isolation. ARM BettingCo provides real examples: bet placement races, idempotency key conflicts, and settlement consistency.

1. The Four Isolation Levels and Their Anomalies

LevelDirty ReadNon-Repeatable ReadPhantom ReadWhen to use
READ UNCOMMITTED possible possible possible Almost never. No guarantees. Useful only for approximate aggregate queries on bulk analytics data.
READ COMMITTED
PostgreSQL default		 prevented possible possible Standard OLTP: ARM BettingCo's default. Each statement sees committed data at statement start time.
REPEATABLE READ prevented prevented possible* Read-heavy workflows needing consistent snapshot: settlement queries, reporting. *PostgreSQL's MVCC also prevents phantom reads at this level (stronger than SQL standard).
SERIALIZABLE prevented prevented prevented Financial critical sections: double-spend prevention. High overhead — serialization failures retry-able. Use sparingly.

2. Anomalies — Concrete Definitions

Dirty Read

-- Transaction A updates a bet but has NOT committed:
T1: UPDATE bets SET status='SETTLED', payout=150 WHERE id=42;
-- (T1 has not committed yet)

-- READ UNCOMMITTED: Transaction B can read T1's uncommitted data:
T2: SELECT payout FROM bets WHERE id=42;  -- returns 150 (dirty read)

-- T1 rolls back. T2 acted on data that never existed.
-- PostgreSQL never allows this — minimum is READ COMMITTED.

Non-Repeatable Read

-- Scenario: settlement-service reads bet status twice in same transaction
T1: SELECT status FROM bets WHERE id=42;  -- returns 'PENDING'
-- (between T1's two reads, T2 updates and commits)
T2: UPDATE bets SET status='CANCELLED' WHERE id=42;  COMMIT;
T1: SELECT status FROM bets WHERE id=42;  -- returns 'CANCELLED' (changed!)

-- T1 sees different values for the same row in the same transaction.
-- READ COMMITTED allows this (each statement sees fresh committed data).
-- REPEATABLE READ prevents it (T1 sees snapshot taken at transaction start).

Phantom Read

-- Scenario: settlement-service counts PENDING bets for an event
T1: SELECT COUNT(*) FROM bets WHERE event_id=100 AND status='PENDING';  -- returns 47

-- T2 places a new bet and commits:
T2: INSERT INTO bets(event_id, status, ...) VALUES (100, 'PENDING', ...);  COMMIT;

T1: SELECT COUNT(*) FROM bets WHERE event_id=100 AND status='PENDING';  -- returns 48!

-- T1 sees a "phantom" row that appeared during its transaction.
-- REPEATABLE READ prevents re-reading changed rows but allows new rows (phantoms).
-- SERIALIZABLE prevents phantoms.
-- Note: PostgreSQL's MVCC makes REPEATABLE READ also phantom-safe in practice.

3. Spring @Transactional Isolation

// Default: uses database default (READ COMMITTED for PostgreSQL)
@Transactional
public void settleBet(Long betId) { ... }

// Explicit isolation for settlement — consistent snapshot across all reads
@Transactional(isolation = Isolation.REPEATABLE_READ)
public SettlementResult settleBets(Long eventId) {
    // All SELECTs see the same snapshot even if concurrent INSERTs happen
    List<Bet> bets = betRepository.findPendingByEventId(eventId);
    bets.forEach(this::calculatePayout);
    betRepository.saveAll(bets);
    return buildResult(bets);
}

// Read-only flag: hint to JPA (Hibernate flushes less), hint to DB driver
@Transactional(readOnly = true)
public List<Bet> getRecentBets(Long tenantId) { ... }
// readOnly=true: Hibernate skips dirty checking on loaded entities
// PostgreSQL: no effect on isolation, but Spring can route to read replica
PostgreSQL default is READ COMMITTED — not REPEATABLE READ MySQL defaults to REPEATABLE READ. PostgreSQL defaults to READ COMMITTED. This is the most common interview trap. In ARM BettingCo's bet-manager-service, the default @Transactional gives READ COMMITTED. If settlement-service needs a consistent snapshot across multiple reads, it must explicitly set isolation = Isolation.REPEATABLE_READ.

4. Optimistic vs Pessimistic Locking

Optimistic Locking — @Version

// JPA optimistic locking: version column prevents lost updates
// Used when conflicts are RARE but must be detected
@Entity
public class Bet {
    @Id private Long id;
    @Version private Long version;  // JPA increments on every UPDATE
    private BetStatus status;
    private BigDecimal payout;
}

// When two threads try to settle the same bet:
// Thread A: SELECT id=42, version=1 → UPDATE bets SET version=2 WHERE id=42 AND version=1 → OK
// Thread B: SELECT id=42, version=1 → UPDATE bets SET version=2 WHERE id=42 AND version=1
//           → 0 rows affected (version is now 2) → JPA throws OptimisticLockException
//           → caller catches and retries or returns error

// No DB lock held between SELECT and UPDATE — high throughput

Pessimistic Locking — SELECT FOR UPDATE

// Pessimistic locking: hold a DB lock for the duration of the transaction
// Used when conflicts are LIKELY and you need to prevent concurrent access
@Repository
public interface BetRepository extends JpaRepository<Bet, Long> {

    // JPQL with pessimistic write lock
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT b FROM Bet b WHERE b.id = :id")
    Optional<Bet> findByIdWithLock(@Param("id") Long id);
}

// Generates: SELECT ... FROM bets WHERE id=? FOR UPDATE
// Thread B's SELECT FOR UPDATE blocks until Thread A commits or rolls back.
// Prevents phantom reads and lost updates but reduces throughput.
// Risk: deadlock if two transactions lock rows in different orders.

5. ARM BettingCo's Idempotency Strategy (SELECT Pre-Check)

// bet-manager-service (SlipService) uses a SELECT pre-check for idempotency.
// Before inserting a new slip, it queries for an existing one with the same
// sportsbook reference — if found, it returns the existing result immediately.

// Java: SELECT pre-check pattern
@Transactional
public SlipDto placeSlip(SlipDto slipDto) {
    // Idempotency pre-check: has this sportsbook reference already been processed?
    Optional<Slip> existing = slipRepository.findBySportsbookId(
        slipDto.getSportsbookTenantId(), slipDto.getSportsbookRef());

    if (existing.isPresent()) {
        // Duplicate request — return the already-processed result
        return slipMapper.toDto(existing.get());
    }

    // First time: proceed with validation and save
    Slip slip = buildAndValidate(slipDto);
    slipRepository.save(slip);
    return slipMapper.toDto(slip);
}
// The sportsbook reference (sportsbookRef + tenantId) acts as the idempotency key.
// Pre-check before INSERT avoids a unique-violation exception on retry.
// Trade-off: SELECT pre-check has a small TOCTOU race under extreme concurrency,
// but is simpler and avoids exception-driven control flow.
Interview answer: when to use each strategy SELECT pre-check: idempotency (bet placement) — query for existing record before inserting; simple, avoids exception-driven control flow. UNIQUE constraint + catch: high-concurrency idempotency where the race window matters — DB enforces uniqueness atomically, catches violation in application layer. Optimistic lock (@Version): low-contention updates where conflicts are rare — e.g., updating user profile settings. Pessimistic lock (SELECT FOR UPDATE): high-contention, must-not-lose scenarios — e.g., decrementing a shared counter where multiple threads race. SERIALIZABLE isolation: complex invariants spanning multiple rows/tables — financial close, allocation across accounts.

6. Lost Update Problem — The Classic Interview Scenario

-- Two concurrent bet placements on same wallet balance:
-- Both read balance=£1000. Both deduct £600. Both commit → balance=£400.
-- Correct answer: balance=£1000 - £600 - £600 = -£200 (overdraft — should be rejected)

-- READ COMMITTED does NOT protect against this:
T1: SELECT balance FROM wallets WHERE id=1;  -- reads 1000
T2: SELECT balance FROM wallets WHERE id=1;  -- reads 1000 (T1 not committed)
T1: UPDATE wallets SET balance=400 WHERE id=1;  COMMIT;
T2: UPDATE wallets SET balance=400 WHERE id=1;  COMMIT;  -- ← lost T1's update!

-- Fix option A: Pessimistic lock
SELECT balance FROM wallets WHERE id=1 FOR UPDATE;  -- T2 blocks until T1 commits

-- Fix option B: Atomic SQL update (no read needed)
UPDATE wallets SET balance = balance - 600 WHERE id=1 AND balance >= 600
-- single statement = atomic in READ COMMITTED; returns rows_affected=0 if insufficient funds

-- Fix option C: @Version optimistic lock
-- T2 finds version mismatch → OptimisticLockException → retry or reject

Quiz

Q1. ARM BettingCo runs PostgreSQL with default isolation. Two settlement-service instances simultaneously query SELECT COUNT(*) FROM bets WHERE event_id=100 AND status='PENDING' then attempt to insert a settlement record. What anomaly could occur, and what isolation level prevents it?

  • Dirty read — prevented by READ COMMITTED (PostgreSQL default already prevents this)
  • Non-repeatable read — prevented by REPEATABLE READ isolation on the count query
  • A phantom read — both instances read 47 bets, then a new bet is inserted between their reads. REPEATABLE READ (or SERIALIZABLE) prevents this by giving each transaction a consistent snapshot that excludes rows inserted after the transaction starts.
  • Lost update — prevented by SELECT FOR UPDATE on the bets table
Phantom read: transaction T1 sees a set of rows matching a condition (47 PENDING bets). Between T1's reads, T2 inserts a new PENDING bet. T1's second read sees 48 rows — a "phantom" appeared. READ COMMITTED allows this. REPEATABLE READ (PostgreSQL's implementation via MVCC) takes a snapshot at transaction start — T1 consistently sees 47 even if T2 commits. This is why settlement queries should use REPEATABLE READ or SERIALIZABLE.

Q2. bet-manager-service uses @Version on its Bet entity. Under high load, two requests try to update the same bet simultaneously. Request A succeeds. What happens to Request B?

  • Request B's update silently overwrites Request A's update (last write wins)
  • JPA throws OptimisticLockException on Request B. The version column in the database has been incremented by Request A's commit. Request B's UPDATE statement finds 0 rows matching (id=X AND version=old_version) and JPA detects this as a concurrent modification. The caller must catch this and decide: retry or return a conflict error.
  • Request B blocks until Request A completes, then retries automatically
  • PostgreSQL throws a serialization failure and both transactions retry
Optimistic locking never blocks. Both transactions read the same version=1. Request A updates and sets version=2. Request B then tries "UPDATE bets SET version=2 WHERE id=X AND version=1" — the WHERE finds no matching rows (version is already 2). JPA interprets 0 rows updated as a concurrent modification and throws OptimisticLockException. The application catches this and typically retries the operation from scratch (re-read → re-compute → re-attempt update).

Q3. ARM's idempotency uses a SELECT pre-check on the sportsbook reference before inserting a slip. Two identical POST /bets requests arrive at two different pods simultaneously (network retry). What is the expected outcome?

  • Both requests execute their SELECT pre-check and find no existing slip. Both proceed to INSERT, creating two identical slips — the small race window in the SELECT-then-INSERT pattern. In practice ARM mitigates this at the API gateway / sportsbook layer, and the risk window is very narrow under normal retry patterns.
  • The second request's SELECT pre-check finds the first request's committed slip and returns its result — no duplicate created. This is the normal case: the first request completes before the second's SELECT runs.
  • PostgreSQL automatically detects the duplicate and rolls back one INSERT
  • The second request blocks at the DB level until the first commits
ARM uses a SELECT pre-check pattern (SlipService.findBySportsbookId). In the common case — where the first request commits before the second's pre-check — the second finds the existing record and returns immediately. There is a theoretical TOCTOU (Time-Of-Check-Time-Of-Use) race if both requests run their SELECT simultaneously before either commits, but network retry patterns make this extremely unlikely. A UNIQUE constraint + catch approach would eliminate this race entirely at the cost of exception-driven control flow.
