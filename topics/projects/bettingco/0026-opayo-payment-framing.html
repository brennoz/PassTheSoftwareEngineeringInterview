ARM BettingCo → Opayo Payment Platform

Interview framing: how every ARM pattern transfers to payment domain · Opayo-specific context

Opayo (formerly SagePay, part of Elavon / US Bancorp) is a UK payment gateway: merchants send card authorisation requests through Opayo, Opayo routes them to card schemes (Visa/Mastercard), and the response flows back within ~200ms. The same technical challenges you solved in ARM BettingCo — idempotency, exactly-once, Saga, distributed tracing, Kafka fan-out, Redis atomics — are the exact same problems at higher stakes in payment processing. This page shows how to present ARM experience at a payment platform interview.

The core interview pitch "At ARM I built a real-time platform processing thousands of concurrent bet placements and live odds updates. The technical constraints are almost identical to payment processing: you cannot double-process a transaction, you need sub-100ms latency under load, you need exactly-once event delivery, and a single bug can cause financial loss. The patterns I used — idempotency keys at DB level, outbox for event delivery, Kafka for settlement choreography, Redis for atomic state — these are the same patterns a payment gateway needs."

2. Payment-Specific Extensions — What ARM Didn't Need

PCI-DSS (Payment Card Industry Data Security Standard)

// PCI-DSS rules ARM didn't face but Opayo must follow:

// Rule 1: PAN (Primary Account Number = card number) NEVER in logs
// ARM: bet amounts and odds can be logged freely
// Opayo: card number, CVV, expiry date NEVER appear in application logs

// Bad (PCI violation):
log.info("Processing payment for card: " + request.getCardNumber());

// Good (PCI compliant):
log.info("Processing payment for masked card: {}", maskPan(request.getCardNumber()));
// maskPan: "4111111111111111" → "411111******1111"

// Rule 2: CVV never stored (not even encrypted)
// Can be used for authorisation check, must be deleted immediately after
// ARM equivalent: nothing — betting platforms don't have CVV-equivalent data

// Rule 3: PAN encrypted at rest (AES-256) or tokenised
// Opayo: PAN stored as token in vault service, actual PAN never in application DB
// ARM: no equivalent (bet slips don't have equivalent sensitive field)

// Rule 4: Audit log for every card data access
@Transactional
public PaymentResult authorise(PaymentRequest request) {
    auditLog.record(AuditEvent.PAYMENT_AUTHORISATION_ATTEMPT,
        request.getMerchantId(), maskPan(request.getPan()));
    // ... process payment
    auditLog.record(AuditEvent.PAYMENT_AUTHORISATION_RESULT,
        request.getMerchantId(), result.getStatus());
}
PCI-DSS interview question — the right answer "How do you handle card data?" Answer: Tokenisation. The real PAN touches the system only during authorisation, is immediately tokenised via a vault service (e.g. Stripe Vault, Braintree, or own PCI-compliant vault), and the token is what gets stored in your DB. All subsequent operations (capture, refund, recurring) use the token. The PAN never appears in logs, never in application DB, never in Kafka messages. ARM BettingCo didn't need this but the same defence-in-depth thinking — idempotency at DB level, audit logging on every mutation — directly applies.

// Opayo sits between merchant and card scheme network:
// Merchant → Opayo (gateway) → Card Scheme (Visa/MC) → Issuing Bank
//                             ← auth response           ← approve/decline

// The Opayo flow (simplified):
// 1. Merchant POST /authorise {pan_token, amount, currency, merchantId, idempotencyKey}
// 2. Opayo validates: merchant credentials, amount limits, idempotency check
// 3. Opayo calls Visa/MC ISO 8583 protocol (or ISO 20022 for newer networks)
// 4. Issuing bank returns: approved / declined / referral
// 5. Opayo stores result, returns to merchant
// 6. Merchant later POST /capture to actually settle the funds
//    (authorise = reserve funds; capture = move funds — two-step)

// ARM analogy:
// bet-manager-service (merchant) → advisory-service check → bet confirmed
// advisory-service = Opayo's fraud/authorisation check
// bet confirmation = Opayo's authorisation response
// settlement-service = Opayo's capture/settlement flow

// Key difference: Opayo's external call (card scheme) is ISO 8583 binary protocol
// not a REST call. The ARM equivalent is the WOODS cluster STOMP relay to bookmakers.
// Both: external protocol, must handle timeout, retry, idempotency.

// Timeout handling:
// ARM: advisory-service has 500ms SLA; circuit breaker opens after 3 failures
// Opayo: card scheme call has 30s hard timeout; timeout = decline (conservative)
//        A declined transaction never double-charges; an unclear timeout might.

Exactly-Once Payment Settlement

// The hardest Opayo problem: settle money exactly once
// Even if the settlement Kafka consumer crashes mid-way

// ARM approach (choreography saga):
// ARM_BET_SETTLEMENT → settlement-service marks bets SETTLED → publishes payout event
// If crash between "mark SETTLED" and "publish payout": on restart, consumer replays
// → idempotency_key prevents double-settlement
// → outbox pattern ensures payout event is not lost

// Opayo equivalent:
// settlement-topic → settlement-service debits merchant → credits acquirer → publishes receipt
// Same pattern: idempotency_key on each settlement record, outbox for receipt event

// Outbox pattern in payment context:
@Transactional
public void processSettlement(SettlementCommand cmd) {
    // 1. Apply state change
    Payment payment = paymentRepo.findById(cmd.getPaymentId());
    payment.settle(cmd.getAmount());  // sets status=SETTLED, stores amount
    paymentRepo.save(payment);

    // 2. Atomically write outbox event (same transaction)
    OutboxEvent event = new OutboxEvent(
        "PAYMENT_SETTLED",
        cmd.getPaymentId().toString(),
        objectMapper.writeValueAsString(new PaymentSettledEvent(payment))
    );
    outboxRepo.save(event);

    // 3. Outbox poller (separate thread) publishes to Kafka and deletes row
    // If crash before outbox publish: transaction committed, outbox row survives,
    // poller retries → at-least-once Kafka delivery → consumer deduplicates by paymentId
}
// This is the same ARM outbox pattern from lesson 0004-bet-manager-service.html
// Applied to payment: same code, different domain object (Payment not Bet)

3. Where ARM Is HARDER Than Opayo

Use this to show depth — ARM was not a simple project Some ARM challenges are harder than equivalent Opayo ones. Mentioning this in interview shows architectural maturity: you understand the relative difficulty of problems, not just that you solved them.

Latency SLA Sub-100ms for in-play bet acceptance. Odds change every second during live races. Stale odds = financial exposure. 200ms for card authorisation. This is a hard requirement but the auth call is to an external network — Opayo can't control issuer latency.
Fan-out concurrency 50,000 concurrent WebSocket clients all receiving the same odds update simultaneously. RabbitMQ STOMP + Redis pub/sub to manage this. Merchant dashboard WebSocket: hundreds or thousands of connections, not 50k. Lower cardinality, same pattern.

4. Interview Answer Templates — Opayo-Framed

"Tell me about a time you handled idempotency in a financial system"

// Structure: situation → problem → solution → outcome → how it applies here

"At ARM BettingCo, a real-money betting platform, we had a classic payment-style
idempotency problem: a client places a £100 bet, the network drops, the client
retries — does the backend place two bets and deduct £200?

We solved it at the service layer: before every bet INSERT, the service performs
a SELECT pre-check on (sportsbookTenantId, sportsbookRef). If a row already
exists with that reference, the service returns the original bet result rather
than inserting again. No double stake deduction, no lock contention.

  // In BetManagerService:
  Optional<Bet> existing = betRepo.findBySportsbookTenantIdAndSportsbookRef(
      cmd.getSportsbookTenantId(), cmd.getSportsbookRef());
  if (existing.isPresent()) {
      return BetResult.from(existing.get());  // return original, do not reprocess
  }

At Opayo, the same idempotency goal applies to payment authorisation, though
a payment gateway can additionally enforce a UNIQUE constraint on the
idempotency_key column for a harder atomic guarantee. The merchant sends a
unique reference per payment attempt. A duplicate request gets the original
authorisation response — merchant sees success, no double-charge, no ambiguity."

"How have you dealt with distributed transaction consistency?"

"ARM BettingCo's settlement saga is the payment settlement equivalent:
a race finishes → event triggers a multi-step saga across three services:
settlement-service marks 300 bets as won/lost, advisory-service confirms odds
were valid, wallet-service credits winners.

If step 3 fails after step 2 succeeded, we need to compensate — put the bets
back to PENDING and retry. We used Kafka choreography: each service publishes
the next event only after its step succeeds. If it fails, it publishes a
compensating event upstream.

At Opayo, the equivalent is a capture + ledger saga: authorise reserves funds,
capture actually moves money, ledger records the debit, merchant payout is
scheduled. If capture succeeds but ledger fails, the compensating action is
a reversal to the card scheme. The saga structure — event triggers step,
step failure triggers compensation — is identical.

The pattern is called Saga choreography. It avoids a distributed transaction
coordinator (2PC) which would become a bottleneck at payment volume."

"How would you ensure a payment processes exactly once?"

"Three layers, each covering a different failure mode:

Layer 1 — Client deduplication: unique bet reference on every API call.
At ARM, a SELECT pre-check on (sportsbookTenantId, sportsbookRef) before INSERT.
At Opayo, this is backed by a DB UNIQUE constraint on idempotency_key — a harder
atomic guarantee than a pre-check alone.

Layer 2 — Kafka producer idempotency: enable.idempotence=true on the Kafka
producer. The broker deduplicates within a session using producer ID + sequence
number. If the producer retries after a network partition, the broker discards
the duplicate — exactly-once to Kafka.

Layer 3 — Consumer deduplication: before applying any state change, check if
this eventId has already been processed. At ARM, the SettlementEngine in
bet-manager-service checks current bet status before applying SETTLED — if a
bet is already SETTLED, skip processing. At Opayo, a UNIQUE constraint on
settlement records gives a stronger atomic guard.

The core lesson from ARM: Layer 1 alone is insufficient. A Kafka consumer crash
mid-processing replays the message even with the original reference. Layer 3
catches what Layer 1 misses."

Quiz — Opayo Interview Scenarios

Q1. Opayo's authorisation service receives the same payment request twice (merchant retry after network timeout). The first request succeeded (funds reserved at issuing bank). The second arrives 3 seconds later with the same idempotency key. What should happen, and what is the implementation?

  • Both requests should be processed — the merchant may have genuinely intended two payments; idempotency only applies to exact duplicates detected within 100ms
  • The second request should return the result of the first authorisation — same authorisation code, same reserved amount, no second charge to the cardholder. Implementation: Redis lookup by idempotency key first (fast, 24h TTL), return cached response if found. DB UNIQUE constraint on authorisations(idempotency_key) as durable backup. The card scheme is NOT called a second time — calling the scheme twice could result in two authorisation holds on the cardholder's account.
  • The second request should return 409 Conflict — the client should use a different idempotency key if it genuinely wants a new payment
  • Opayo should call the card scheme with the duplicate and let the scheme deduplicate using its own protocol
Idempotency means: same key = same result, always. The merchant retried because it didn't get a response — it doesn't know if the first request succeeded. Opayo must return the same authorisation response (authorisation code, amount, status) without calling the card scheme again. Two scheme calls = two authorisation holds = cardholder sees double charge pending. The Redis + DB approach: Redis (fast, 24h) for the hot path, DB UNIQUE constraint (durable) as the safety net for cache miss. ARM BettingCo uses exactly this pattern for bet placement.

Q2. Opayo processes a card payment. The capture step succeeds (funds move from cardholder to Opayo). The ledger write then fails (DB timeout). The consumer restarts and replays the Kafka message. How do you ensure the ledger write doesn't double-record the debit?

  • Use a Kafka transaction — wrap the capture and ledger write in a single Kafka transaction so both succeed or both fail atomically
  • Use SERIALIZABLE isolation on the ledger write transaction — this prevents phantom reads and ensures exactly-once recording
  • Add a paymentId UNIQUE constraint to the ledger_entries table. When the consumer replays, the INSERT fails with a duplicate key violation. Catch DataIntegrityViolationException, fetch the existing ledger entry, and continue. This is the same pattern ARM BettingCo uses for bet settlement: idempotency_key UNIQUE on bets prevents double-settlement on consumer replay. The ledger is append-only (never UPDATE posted entries) so the UNIQUE constraint on paymentId is the correct guard.
  • Set enable.idempotence=true on the Kafka producer — this prevents the message from being delivered twice
Kafka producer idempotency (option D) prevents duplicate delivery within a single producer session — it doesn't help when the consumer crashes and replays an already-delivered message. SERIALIZABLE isolation (option B) prevents phantom reads but doesn't prevent double recording if the same INSERT runs twice. Kafka transactions (option A) can wrap producer operations but can't include an external DB write atomically. The correct answer is consumer-side deduplication via UNIQUE constraint on the natural identifier (paymentId). This is the exact pattern from ARM's bet settlement. Ledger entries must be immutable (no UPDATE on posted rows) — audit trail and accounting correctness require this.

Q3. Opayo needs to log every payment authorisation attempt for PCI-DSS compliance. A junior engineer writes: log.info("Authorising card: {}, amount: {}", request.getCardNumber(), request.getAmount()). What is wrong and what are the consequences?

  • This is a PCI-DSS violation: the Primary Account Number (PAN — the card number) appears in plain text in application logs. Consequences: (1) Logs are often shipped to Splunk/ELK/Datadog — the PAN is now in those systems, each of which must be PCI-compliant if they hold card data. (2) Log files may be accessible to engineers without PCI clearance — data exposure. (3) A PCI audit would flag this as a Level 1 violation, potentially resulting in loss of card processing rights (existential for Opayo). Fix: log.info("Authorising masked card: {}, amount: {}", maskPan(request.getCardNumber()), request.getAmount()) where maskPan returns "411111******1111".
  • The log format is incorrect — SLF4J requires using %s not {} for string formatting
  • The log level should be DEBUG not INFO — payment data should not appear at INFO level
  • There is no issue — card numbers are already encrypted by HTTPS so logging them is safe
HTTPS encrypts data in transit — it has nothing to do with what gets stored in log files on disk. PCI-DSS Requirement 3.4 states PAN must be rendered unreadable anywhere it is stored. Requirement 10 requires log integrity and access controls. A PAN in a log file violates both. The fix is masking at the point of logging — never log the full PAN, always log masked ("411111******1111"). In ARM BettingCo, there's no equivalent sensitive field, but the same principle applies to any PII (user email, date of birth): mask before logging at system boundaries, never log raw at INFO or above. A senior Opayo engineer would catch this in code review immediately.

Q4. You are designing Opayo's merchant-facing API for payment capture. The API must handle: (1) a merchant capturing a previously authorised payment, (2) the merchant retrying the capture request because they didn't get a response, (3) a merchant accidentally calling capture twice on the same authorisation (days apart). How do you handle all three cases?

  • Use a distributed lock (Redis SETNX) to prevent concurrent capture calls on the same authorisation — lock for 30 seconds, reject if already locked
  • Three layers: (1) Authorisation state machine: authorisation has states AUTHORISED → CAPTURED → REFUNDED. Capture is only valid from AUTHORISED — reject with 409 if already CAPTURED (case 3). (2) Idempotency key on the capture request: merchant provides a unique capture reference. Redis + DB UNIQUE constraint. Same reference = same response (case 2). (3) Optimistic lock (@Version) on the authorisation entity: prevents two simultaneous captures racing to the same AUTHORISED state (concurrent case). These three layers together cover all three scenarios: state machine for business rule, idempotency key for retries, optimistic lock for races.
  • Put a UNIQUE constraint on authorisations(id) — duplicate captures on the same authorisation_id are rejected at DB level
  • Require merchants to poll for authorisation status before capturing — if status is already CAPTURED, they skip the capture call
A UNIQUE constraint on authorisations(id) (option C) doesn't prevent capturing twice — the authorisation row exists once; what changes is its state. Polling (option D) creates a race condition — both polls could see AUTHORISED before either capture completes. Redis lock (option A) prevents concurrent calls but doesn't handle the case where both calls are sequential (days apart). The full solution is all three layers: state machine catches the business logic violation (double-capture is invalid regardless of timing), idempotency key handles retries (same reference = same response without re-processing), optimistic lock handles the concurrent race. This layered approach is the same defence-in-depth ARM uses for bet placement + settlement.
