ARM BettingCo — Infrastructure & Kubernetes Topology

Category: Projects · Topic: ARM BettingCo · Diagram 4 of 4 · K8s / AWS / CI-CD

ARM runs on two AWS Elastic Kubernetes Service (EKS) clusters — one shared dev/integration cluster and a dedicated production cluster — both in eu-west-1. All services share a single Helm chart with environment-specific values files. Deployments are triggered by GitLab CI/CD pipelines that build Docker images, push to ECR (Elastic Container Registry), and run helm upgrade. Kubernetes Horizontal Pod Autoscaler (HPA) manages scale automatically against CPU load.

Production debugging — how you investigate an incident 1. Datadog APM: find the failing trace — every HTTP request and Kafka message is traced with distributed trace IDs. 2. Kafka consumer group lag: kafka-consumer-groups.sh --describe — if lag is growing, consumer is behind. 3. Pod logs: kubectl logs -n arm-prod <pod> --previous for crashed pods. 4. HPA events: kubectl describe hpa -n arm-prod — shows scale-up/down events. 5. Redis memory: redis-cli INFO memory — check eviction policy if cache is full. This is the hands-on debugging depth expected at senior level.
API evolution without downtime New API versions are deployed via helm upgrade as a rolling update: Kubernetes spins up new pods (v2) while old pods (v1) still serve traffic. During the rollout, the Service load balances across both versions. Only once all new pods pass their readiness probe (/actuator/health/readiness) does Kubernetes terminate old pods. For Kafka: consumers use consumer group IDs — adding a new consumer group for a new version allows both old and new consumers to process messages in parallel until the old version is drained and removed.
