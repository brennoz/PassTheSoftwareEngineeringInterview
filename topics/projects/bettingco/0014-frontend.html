ARM BettingCo — Frontend Architecture

Category: Projects · Topic: ARM BettingCo · Est. time: 20 min · Lesson 14 of 14

ARM has two frontends serving two audiences: cerberus-ui, the trader/operator tool for managing race meetings, and sportsbook, the customer-facing betting interface. They share the same backend services but differ dramatically in tech stack — cerberus-ui is a modern Next.js 15 application written in 2024, sportsbook is a legacy React 16 Redux application from 2019.

Why two different stacks? sportsbook predates cerberus-ui by 4+ years. Rewriting it in Next.js would be a multi-month project with no new business value. ARM kept sportsbook stable and built all new trader tooling in cerberus-ui. Legacy and modern apps coexist behind the same backend — a common pattern when a platform outlives its original frontend.

cerberus-ui — Trader Interface (Next.js 15)

Routes

Three Next.js App Router pages:

  • /login — JWT authentication, writes auth_token cookie
  • /meetings — list of race meetings for today, real-time status via WebSocket
  • /meetings/[id] — single meeting detail: races, runners, odds, market controls

State Architecture — Jotai + TanStack Query

cerberus-ui separates two kinds of state cleanly:

  • Server state — TanStack Query (React Query v5). Fetches race meetings, tracks, topics from the REST API. Handles caching, background refetch, loading/error states automatically.
  • Client state — Jotai atoms. Only three atoms: healthCheckStatusAtom, oddsFormatAtom, roleAtom. Tiny global state — no Redux boilerplate.
// Source: cerberus-ui/src/store/atoms.ts
export const healthCheckStatusAtom = atom<'good' | 'warning' | 'disconnected'>('good')
export const oddsFormatAtom = atom<OddsFormat>(OddsFormat.Fractional)
export const roleAtom = atom<Role[]>([])

// rolePersistenceAtom: derived atom — reads roleAtom, writes roleAtom AND cookie
export const rolePersistenceAtom = atom(
  (get) => get(roleAtom).length ? get(roleAtom) : [],
  (get, set, payload: { roles: Role[]; exp?: number }) => {
    set(roleAtom, payload.roles)
    setCookie(COOKIE_ROLES_KEY, JSON.stringify(payload.roles), {
      expires: payload.exp ? dayjs.unix(payload.exp).toDate() : undefined
    })
  }
)
Jotai vs Redux — why atoms win for small global state Redux requires actions, reducers, selectors, and a store for every piece of state. Jotai: const [value, setValue] = useAtom(myAtom) — same API as useState but shared globally. For three pieces of global state (health, format, role), Redux would be 100+ lines of boilerplate. Jotai is 15 lines. TanStack Query eliminates the need for Redux async actions (thunks) by owning server state directly.

ApiClient.interceptors.request.use((config) => {

Code: Real WebSocket — useWebsocket Hook

STOMP over SockJS, with exponential backoff reconnect and dynamic topic subscription from the API:

// Source: cerberus-ui/src/infrastructure/hooks/useWebsocket.tsx
export const useWebsocket = () => {
  const { data: topics = [] } = useListTopicsApi()  // topics fetched from REST API
  const [reconnections, setReconnections] = useState(0)
  const setStatus = useSetAtom(healthCheckStatusAtom)
  const { onUpdate: onOptimisticUpdate } = useOptimisticUpdateTrack()

  useEffect(() => {
    function reconnect() {
      // Exponential backoff: 1s, 2s, 4s, 8s... capped at 30s
      const delay = Math.min(1000 * Math.pow(2, reconnections), 30000)
      setTimeout(() => setReconnections(reconnections + 1), delay)
    }

    const client = Stomp.client(apiUrl)
    client.configure({
      webSocketFactory: () => new SockJS(`${apiUrl}/ws`),   // SockJS fallback
      onDisconnect: () => reconnect(),
      onWebSocketClose: (event) => { if (event.code > 1000) reconnect() },

      onConnect: () => {
        const headers = { Authorization: `Bearer ${apiToken}` }  // JWT on STOMP SUBSCRIBE (per-subscription header)

        topics.forEach((topic) => {
          switch (topic.type) {
            case TopicType.CERBERUS_MEETINGS:
              // Live meeting update → directly mutate React Query cache
              client.subscribe(topic.name, (msg) => {
                const meeting: Meeting = JSON.parse(msg.body)
                onOptimisticUpdate({ meetingId: meeting.id, payload: meeting })
              }, headers)
              break
            case TopicType.HEALTH_CHECK:
              client.subscribe(topic.name, (msg) => {
                // msg.body: "UP" or "DOWN" — update global health atom
                setStatus(msg.body === 'DOWN' ? 'disconnected' : 'good')
              }, headers)
              break
          }
        })
      },
    })
    client.activate()
    return () => { client.deactivate() }
  }, [topics, reconnections])
}
Optimistic updates without HTTP — the key pattern When a STOMP message arrives with a meeting update, useOptimisticUpdateTrack calls queryClient.setQueryData() directly — it writes into the TanStack Query cache without making an HTTP request. The UI re-renders instantly with the new odds. This is the critical path: Kafka → sportsbook-service → STOMP → browser cache update — no round-trip REST call on the hot path.

Code: Optimistic Cache Update

// Source: cerberus-ui/src/infrastructure/hooks/useOptimisticTrackUpdate.hook.ts
export const useOptimisticUpdateTrack = () => {
  const queryClient = useQueryClient()

  const onUpdate = useCallback(({ meetingId, payload }: Update) => {
    queryClient.setQueryData(
      [TRACK_API_KEYS.LIST, meetingId],   // same key as useQuery — updates the cache
      (prevMeeting: Meeting) => {
        if (!prevMeeting) return
        const { races = [], ...rest } = payload
        return {
          ...prevMeeting,
          ...rest,
          races: prevMeeting.races.map((currentRace) => {
            const race = races.find((r) => r.id === currentRace.id)
            return {
              ...currentRace,
              ...(race && {
                ...race,
                ...(race.runners && {
                  runners: sortBy(race.runners, 'trapNumber'),  // always sort by trap number
                }),
              }),
            }
          }),
        }
      }
    )
  }, [queryClient])

  return { onUpdate }
}

Auth Guard — Next.js Middleware

Route protection runs at the Edge — before the page is served, Next.js middleware checks the auth_token cookie and redirects unauthenticated users to /login:

// Source: cerberus-ui/src/middleware.ts
export function middleware(req: NextRequest) {
  const token = req.cookies.get('auth_token')?.value
  const roles = JSON.parse(req.cookies.get(COOKIE_ROLES_KEY)?.value ?? '[]')
  const { pathname } = req.nextUrl

  if (!token && pathname.startsWith('/')) {
    return NextResponse.redirect(new URL('/login', req.url))  // no token → login
  }
  if (token && pathname === '/login') {
    return NextResponse.redirect(new URL(getRedirectPath(roles), req.url))  // already authed
  }
  if (token && pathname === '/' && isObserverRole(roles)) {
    return NextResponse.redirect(new URL('/meetings', req.url))
  }
  return NextResponse.next()
}

export const config = {
  matcher: ['/', '/login$'],  // only run middleware on these paths
}
Why JWT in a cookie, not localStorage? localStorage is accessible via JavaScript — an Cross-Site Scripting (XSS) attack can read it and steal the token. A cookie with HttpOnly flag cannot be read by JavaScript at all. For an operator trading tool handling live odds and positions, token theft would allow impersonation. The cookie approach adds one layer of protection against the most common frontend token-theft vector.

sportsbook — Customer Interface (React 16 / Redux)

sportsbook is a legacy Redux application. It predates TanStack Query and Jotai. All async operations go through a custom Redux middleware (ApiMiddleware) that wraps axios and dispatches typed action triplets: REQUEST / SUCCESS / FAILURE.

// Source: sportsbook/src/api/ApiMiddleware.ts
// Redux middleware pattern: intercepts { type: 'API' } actions and makes HTTP calls
const ApiMiddleware: Middleware = ({ dispatch }) => next => (action) => {
  if (action.type !== 'API') { next(action); return; }

  const { payload: request } = action
  dispatch({ type: request.actions.REQUEST, request })  // loading state

  api[request.method.toLowerCase()](request.url, request.body).then(
    response => dispatch({ type: request.actions.SUCCESS, request, response }),
    error    => dispatch({ type: request.actions.FAILURE, request, error })
  )
}
// Typed action creators: asyncActionType('FETCH_EVENTS') →
//   { REQUEST: 'FETCH_EVENTS', SUCCESS: 'FETCH_EVENTS_SUCCESS', FAILURE: 'FETCH_EVENTS_FAILURE' }

Odds Display — Fractional to Probability

cerberus-ui shows odds in fractional format (e.g. 5/2) by default. For display purposes, fractional odds are converted to implied probability:

// Source: cerberus-ui/src/infrastructure/utils/odds.ts
export const getOddsProbability = (odds: string): number => {
  const [numerator, denominator] = odds.split('/').map(Number)
  if (!numerator || !denominator) return 0
  // Formula: probability = denominator / (numerator + denominator)
  // Example: 5/2 → 2 / (5 + 2) = 0.286 = 28.6% implied probability
  return denominator / (numerator + denominator)
}

Quiz

Q1. cerberus-ui uses TanStack Query for REST data and Jotai for client state. What specific problem does this separation solve compared to putting everything in Redux?

  • Redux cannot handle asynchronous actions without additional libraries
  • Server state (REST responses) has its own lifecycle: caching, background refetch, stale/fresh state. TanStack Query manages this automatically. Client state (health status, odds format) is synchronous and tiny — Jotai handles it in 3 atoms. Mixing both in Redux requires writing actions, reducers, and selectors for every API call
  • Jotai is required for Next.js App Router — Redux is not compatible with Server Components
  • TanStack Query cannot coexist with Redux in the same application
The key insight: server state and client state have fundamentally different properties. Server state is asynchronous, can become stale, needs caching and background refresh. Redux treats it like client state — you have to manually invalidate, refetch, and manage loading/error states. TanStack Query owns this automatically. Jotai then only needs to manage the three pieces of true client state: health indicator, odds format preference, and current user role — all synchronous, all small.

Q2. When a live odds update arrives via STOMP WebSocket in cerberus-ui, how does the UI update without making an HTTP request?

  • The browser reloads the page on each WebSocket message to get fresh data
  • useOptimisticUpdateTrack calls queryClient.setQueryData() — writing directly into the TanStack Query cache with the same key as useQuery. React Query detects the cache change and re-renders the component immediately, no HTTP round-trip needed
  • WebSocket messages are stored in localStorage and read by a polling interval every 100ms
  • Redux dispatches a WEBSOCKET_UPDATE action; a reducer merges it into the store; React re-renders
TanStack Query's cache is keyed by the queryKey array (e.g. ['tracks', meetingId]). setQueryData() writes a new value at that key. Any component subscribed to useQuery with the same key immediately receives the update and re-renders. This eliminates the HTTP round-trip on the hot path: the live odds update path is Kafka → sportsbook-service → RabbitMQ → STOMP → browser cache → re-render, with no REST call in the middle.

Q3. cerberus-ui stores the JWT in a cookie rather than localStorage. What security risk does this mitigate?

  • localStorage does not persist across browser sessions; cookies do
  • localStorage is accessible to any JavaScript running on the page — a Cross-Site Scripting (XSS) attack can read it and exfiltrate the JWT. An HttpOnly cookie cannot be read by JavaScript at all, preventing this class of token theft
  • The JWT is too large to fit in localStorage (4KB limit)
  • Next.js middleware can only read cookies, not localStorage, so there is no alternative
XSS (Cross-Site Scripting) is one of the most common frontend vulnerabilities — injected malicious JavaScript can call document.cookie and localStorage. HttpOnly cookies are invisible to JavaScript; only the browser includes them in HTTP requests. For a trading platform where token theft = impersonating a trader with live market access, this is a meaningful protection layer. Note: cookies are still vulnerable to CSRF attacks, mitigated separately by SameSite=Strict and CSRF tokens.

Q4. SockJS is used as the WebSocket factory in cerberus-ui instead of connecting to a raw WebSocket URL directly. What does SockJS add?

  • SockJS compresses WebSocket frames to reduce bandwidth usage
  • SockJS negotiates the best available transport: WebSocket if the browser and network support it, falling back to XHR-streaming or long-polling. This makes the connection work through corporate proxies and firewalls that block WebSocket upgrades
  • SockJS is required by the STOMP protocol — @stomp/stompjs cannot connect without it
  • SockJS adds message authentication on top of the WebSocket connection
Corporate networks and some browsers block WebSocket upgrades (the HTTP → WS protocol switch). SockJS starts with a /info endpoint probe to detect what the network supports, then selects the best transport: native WebSocket, XHR-streaming (chunked HTTP), or long-polling (repeated HTTP). To the application layer (STOMP), the transport is transparent. For a B2B trading tool used in financial services offices with strict network controls, SockJS connectivity is important.
