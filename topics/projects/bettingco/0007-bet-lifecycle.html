ARM BettingCo — End-to-End Bet Lifecycle

Category: Projects · Topic: ARM BettingCo · Est. time: 25 min · Lesson 7 of 30

The Slip Abstraction

The entry point for bet placement is POST /slips, handled by SlipController.createSlip(). A Slip is the container that holds one or more Bet objects. This distinction matters: a single customer submission — say, a Lucky 15 — explodes into 15 individual Bet records (4 singles + 6 doubles + 4 trebles + 1 fourfold). BetController handles queries against existing bets; it plays no role in placement.

BetType is not just SINGLE/WIN/PLACE. The full set includes: SINGLE, DOUBLE, TREBLE, ACCUMULATOR4 through ACCUMULATOR25, TRIXIE, YANKEE, CANADIAN, HEINZ, SUPER_HEINZ, GOLIATH, PATENT, LUCKY_15, LUCKY_31, LUCKY_63. BetExplosionService is responsible for expanding combinatorial bet types into their constituent individual bets for liability tracking.

Phase 1: Placement — Idempotency

Idempotency is enforced at the Slip level using a composite deduplication key: (sportsbookTenantId, sportsbookRef). At the very start of SlipService.createSlip(), before any validation or persistence:

Optional<Slip> optional = slipRepository.findBySportsbookId(tenantId, sportsbookRef);
if (optional.isPresent()) {
    return slipMapper.toDto(optional.get());
}

If the HTTP response is lost and the client retries with the same sportsbookRef, the SELECT finds the already-persisted Slip and returns it immediately. No duplicate Bet is created. There is no idempotency_key field, no UNIQUE constraint on the bets table, and no DataIntegrityViolationException to catch — the deduplication is a pre-check SELECT, not an exception-driven pattern.

Why pre-check SELECT beats UNIQUE constraint here A UNIQUE constraint is reactive — it lets the INSERT happen and catches the collision. A pre-check SELECT is proactive — it avoids the INSERT entirely and returns the original object without touching the database constraint machinery. The tradeoff: if two requests race with the same sportsbookRef in the same millisecond, both may pass the SELECT before either commits. In practice, sportsbookRef is generated by the upstream sportsbook from its own transaction, so true concurrent duplicates are extremely rare. The SELECT pattern is simpler and avoids error-path complexity.

Phase 2: BetStatus State Machine

The full BetStatus enum has seven values. Each Bet also carries a second field, sportsbookBetStatus, reflecting the sportsbook's view of the bet.

betStatusSet byWhen
PENDINGSlipServiceInitial state, before validation
APPROVEDbet.updateBetStatus()Synchronously during POST /slips — all checks pass
DECLINEDbet.updateBetStatus()Synchronously during POST /slips — validation failure
CANCELLEDbet.updateBetStatus()Synchronously during POST /slips — market suspended or selection removed
SETTLEDSettlementEngine.settle()After payout calculated in bet-manager-service
PARTIALLY_CASHED_OUTSettlementEngine / cashout flowCustomer partially cashed out before result
FULLY_CASHED_OUTSettlementEngine / cashout flowCustomer fully cashed out before result
Key fact: PENDING→APPROVED is synchronous The transition from PENDING to APPROVED (or DECLINED/CANCELLED) happens inside the same HTTP request as POST /slips, within bet.updateBetStatus(). There is no async advisory-service approval step. The HTTP response returned to the browser already contains the final APPROVED/DECLINED status. SETTLED, PARTIALLY_CASHED_OUT, and FULLY_CASHED_OUT are set later by SettlementEngine inside bet-manager-service — NOT by a separate settlement-service.

The dual status fields serve different audiences: betStatus is the ARM-internal lifecycle state. sportsbookBetStatus mirrors the sportsbook's categorisation — values: ACTIVE, CANCELLED, PARTIALLY_CASHED_OUT, FULLY_CASHED_OUT — used when syncing state back to the originating sportsbook.

settlement-service is a router, not a payout calculator settlement-service never touches winnings amounts. Its job is: consume the results feed — identify which bets are eligible for settlement — batch them — publish the list to test-local.arm-dev.bet-settlement. All payout calculation happens in SettlementEngine inside bet-manager-service after consuming that topic. This split keeps payout logic co-located with the Bet domain model, and gives settlement-service a single, small responsibility.

The Kafka message key is bet.getId() (Long). There is no correlationId field in BetDto. The uuid that appears in MDC (Mapped Diagnostic Context) logs within settlement-service comes from the incoming event-feed message — it identifies the event update, not the bet placement.

Phase 4: What settlement-service Actually Does

EventServiceKafkaListener (listener ID: arm-events-settlement) consumes arm-dev.event-service.json. DataService.handleMessage() inspects each market outcome in the event update and applies these rules:

  • resultConfirmed=true AND result != NOT_SET → settle=true
  • resultConfirmed=false AND result == VOIDED → settle=true (void path)
  • resultConfirmed=false AND result == NOT_SET → unsettle=true

Deduplication is handled by marketOutcomeResultInspectorCache, a ConcurrentHashMap that tracks the last-seen result per outcome. If the incoming result is identical to the cached value, the message is skipped — no redundant settlement broadcasts.

OutcomeSettlerService.settle() then calls betsApi.getBetStatusesForOutcome(outcomeId) via REST to retrieve eligible bets from bet-manager-service. Eligible statuses: APPROVED, FULLY_CASHED_OUT, PARTIALLY_CASHED_OUT, SETTLED. Bets are batched (default 100/batch) and published to test-local.arm-dev.bet-settlement via SettlementBroadcaster.broadcast(). If that REST call throws a RestClientException, the method returns early — there is no retry.

Phase 5: Payout Calculation in SettlementEngine

When BetSettlementListener in bet-manager-service receives the List<BetStatusDto>:

  • betStatusDto.settle == true → settlementService.settleBetEarlyResult(betId, ...)
  • betStatusDto.settle == false → settlementService.unsettleBet(betId) → reverts status to APPROVED

SettlementEngine.settle() runs the following steps:

  1. If earlySettled=true → mark resettlementEligible=true, skip (will be re-settled when the final result arrives).
  2. If betStatus not in {APPROVED, FULLY_CASHED_OUT, PARTIALLY_CASHED_OUT} → skip.
  3. If cast (forecast or tricast) → delegate to castSettler.settle().
  4. Otherwise: settleWinBet() → resultBet() assigns a LegResult (WON, LOST, or VOID) to each leg → calculatePayout().
  5. After payout: updateBet() writes winningsAmount, freeWinningAmount, pushedAmount, refundedAmount, betStatus=SETTLED, settledTime, settledReason, settledBy.
  6. betRepository.save(bet).
  7. betMessenger.send(bet) → publishes settled BetDto to test-local.arm-dev.bet-updates.json.

Payout Complexity

The payout calculation is not a simple stake x win_price. Several adjustments apply, tracked as BetAdjustment entities:

ScenarioHow it is handled
AccumulatorOdds multiply across all legs; a single LOST leg voids the accumulator winnings
Each-wayunitStake = stake / oddsMap.size() — split between WIN and PLACE PartTypes; winnings calculated per PartType
Best Odds Guaranteed (BOG)Two parallel payouts: at LP (price taken at placement) vs min(SP, LP). The larger wins, subject to BOG_CAP config. Tracked as BetAdjustment of type BOG
Rule 4 deductionsNon-runner withdrawal tax applied via BetDeduction entities of type BetDeductionType
Void legsStake for voided legs flows into refundedAmount
CashoutTracked as BetAdjustment of type CASHOUT; does not override winningsAmount
ResettlementIf resettlementEligible=true, SettlementService.resettleBets() re-runs payout; may add FPTP / FREE_FPTP adjustments

Full BetAdjustment type set: BOG, FREE_STAKE_BOG, CASHOUT, FREE_STAKE_CASHOUT, FPTP, FREE_FPTP, BOOST. Every monetary value — stake, winningsAmount, refundedAmount, pushedAmount — is BigDecimal. Never double or float.

Void and Unsettle

Voiding a bet is not a separate status — it goes through the SETTLED path. SettlementEngine.voidBet() sets betStatus=SETTLED and sets refundedAmount=stakeAmount, with winningsAmount=ZERO. The bet is considered settled (not pending), but the customer receives their stake back rather than a payout.

Unsettling reverses a prior settlement: settlementService.unsettleBet(betId) sets betStatus back to APPROVED, clears the payout fields, and saves. This happens when settle==false arrives from BetSettlementListener — typically triggered by a results amendment or a data correction.

Error Handling — No Dead Letter Queue

In BetSettlementListener.settleBet(), exceptions per individual bet are caught and logged but not re-thrown:

catch (Exception e) {
    logfmt().error(log, "Error settling bet {}", bet.getId(), e);
}

This means one failed bet in a batch does not block settlement of the remaining bets in that batch. Processing continues. There is no explicit Dead Letter Queue (DLQ) configuration visible in the codebase. Similarly, in settlement-service, a RestClientException on the betsApi.getBetStatusesForOutcome() call causes the OutcomeSettlerService.settle() method to return early with no retry — the failed outcome would need to be re-triggered by a subsequent event-feed message.

No @Retryable on settlement — intentional The @Retryable annotation is present only in bet-manager-service, on RetryableQuantBetBuilderClient.getPrices() and getMultiplePrices() — the REST calls to the ML BetBuilder engine used during placement price retrieval. It does not appear in the settlement path. There is no advisory-service REST call at placement either; that flow does not exist.

Quiz

Q1. The browser times out on POST /slips and retries with the same request. How does ARM prevent creating a duplicate bet?

  • The client generates an idempotency_key UUID; a UNIQUE constraint on the bets table catches the duplicate INSERT and returns the original bet
  • SlipService.createSlip() starts with a SELECT via findBySportsbookId(tenantId, sportsbookRef); if a Slip already exists for that composite key it is returned immediately before any INSERT occurs
  • The load balancer pins the retry to the same pod, which caches the response in memory and returns it without touching the database
  • BetController deduplicates incoming requests using the JWT subject claim and rejects the second submission
The idempotency mechanism is a pre-check SELECT on the composite key (sportsbookTenantId, sportsbookRef). There is no idempotency_key field, no UNIQUE constraint on the bets table, and no DataIntegrityViolationException to catch. The SELECT-first approach means the deduplication is proactive and avoids inserting at all on a retry, rather than relying on exception handling. BetController plays no role in placement — that is SlipController's responsibility.

Q2. After a race result is declared, settlement-service publishes List<BetStatusDto> to test-local.arm-dev.bet-settlement. What does bet-manager-service do when it receives a BetStatusDto where settle==true?

  • It publishes the BetStatusDto directly to arm-dev.bet-updates.json so sportsbook-service can update the browser UI
  • It calls betsApi.getBetStatusesForOutcome() to retrieve the full bet details from settlement-service
  • SettlementEngine.settle() runs: resultBet() assigns LegResult per leg, calculatePayout() computes winningsAmount (BigDecimal, with BOG/Rule4/each-way adjustments), betStatus is set to SETTLED, betRepository.save() persists, and betMessenger.send() publishes the settled BetDto
  • It forwards the BetStatusDto to advisory-service for risk reconciliation before updating the bet record
bet-manager-service owns all payout calculation. settlement-service is purely a router: it reads the results feed, identifies eligible bets via REST, and publishes batches. The actual SettlementEngine.settle() execution — LegResult assignment, BOG comparison, Rule 4 deduction, each-way stake split, BigDecimal payout, betRepository.save() — all happens inside bet-manager-service after consuming test-local.arm-dev.bet-settlement. There is no advisory-service involvement at settlement time.

Q3. A PENDING bet transitions to APPROVED during the POST /slips request. When and where does the transition to SETTLED occur?

  • SettlementEngine.settle() inside bet-manager-service sets betStatus=SETTLED after consuming test-local.arm-dev.bet-settlement and completing payout calculation — this is asynchronous, triggered by the race result arriving in the event feed
  • settlement-service sets betStatus=SETTLED synchronously when it receives the race result from event-service
  • The PENDING→APPROVED transition is asynchronous; advisory-service sets APPROVED, then settlement-service sets SETTLED
  • sportsbook-service sets betStatus=SETTLED after consuming arm-dev.bet-updates.json and pushing the STOMP notification to the browser
PENDING→APPROVED (or DECLINED/CANCELLED) is synchronous inside the POST /slips request — bet.updateBetStatus() is called before slipRepository.save(). The transition to SETTLED is asynchronous and happens much later: race result → event-service publishes → settlement-service routes eligible bets → bet-manager-service BetSettlementListener consumes → SettlementEngine.settle() sets betStatus=SETTLED and saves. settlement-service never writes to the bets table; sportsbook-service only reads from arm-dev.bet-updates.json and pushes to the browser.
