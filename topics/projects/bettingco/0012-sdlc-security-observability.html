ARM BettingCo — How It Was Built, Secured, and Monitored

Category: Projects · Topic: ARM BettingCo · Est. time: 20 min · Lesson 12 of 14

This lesson covers the non-functional aspects: architecture process, coding standards, testing strategy, deployment workflow, security design, and observability toolchain — all the "how did you build it?" interview questions.

Architecture Process

ARM was architected using Domain-Driven Design (DDD) to identify bounded contexts: Feed Ingestion, Event Management, Pricing and Risk, Bet Lifecycle, Real-time Push. Kafka events act as the anti-corruption layer between contexts — each context owns its own data model and communicates only through published events, never through direct database access.

Services use a standard Spring Boot layered architecture — controller → service → JPA repository. Domain entities are JPA @Entity classes shared across services via the lib-events shared library. Cross-cutting concerns (security, tenant resolution, Kafka publish, logging) are handled by shared libraries (lib-security, lib-tenants, lib-events) rather than by per-service abstraction layers.

Coding Standards

  • Language: Java 21 — records for DTOs (eliminates boilerplate), sealed classes for event type hierarchies, var for local type inference, text blocks for SQL strings
  • Build: Gradle 8.5 multi-module, one root build.gradle, one module per service and per shared library
  • Code style: Intellij-code-style.xml committed to the repository root — enforced in IntelliJ IDE, consistent formatting across all 43 services and 50+ developers
  • Shared libraries: lib-security, lib-utils, lib-events, lib-tenants, lib-sportsbook-utils, lib-feed-handlers, lib-woods — prevent code duplication across services and ensure consistent behaviour for cross-cutting concerns

Pull Request Quality — Danger → Slack

dangerfile.js at the repository root is executed by Danger (a code review automation tool) on every GitLab Merge Request. It checks:

  • PR size — flags very large diffs as hard to review
  • Test coverage changes — warns if tests were not added/modified alongside new code
  • Missing JIRA ticket reference in the MR description
  • Database migrations that are not accompanied by corresponding code changes

When rules are violated, Danger posts an automated comment on the GitLab Merge Request AND sends a Slack alert to the team's #arm-code-review channel. This catches common mistakes before human review begins — saving reviewer time and enforcing standards at scale across a large team.

No @SpringBootTest — by design Spring context startup adds 15–30 seconds per test class. With 43 services and hundreds of test classes, @SpringBootTest would make the CI pipeline unusably slow. WireMock stubs external bookie APIs in unit tests.

Security — Functional and Non-Functional

Authentication and Authorisation

  • JWT tokens: lib-security provides a shared Spring Security filter chain. All REST endpoints require a valid JWT in the Authorization: Bearer header. JWT_SECRET is a Kubernetes Secret injected as an env var.
  • Role-Based Access Control (RBAC): auth-service manages user accounts and authorities. @PreAuthorize("hasRole('TRADER')") on sensitive controllers.
  • Server-to-server auth: Internal service calls use VALID_API_KEYS (also a Kubernetes Secret) instead of JWTs — avoids JWT expiry issues for machine-to-machine calls.
  • CORS: Configurable via CORS_ORIGINS env var. Default * in dev; locked to specific origins in prod.

Code: Real JWT Authentication Filter

JwtAuthenticationTokenFilter in lib-security is the concrete implementation. It extends Spring's OncePerRequestFilter — guaranteed to run exactly once per request, even through forward chains:

// Source: lib-security/.../filter/JwtAuthenticationTokenFilter.java
@Component
@RequiredArgsConstructor
public class JwtAuthenticationTokenFilter extends OncePerRequestFilter {

    protected final JwtTokenManager jwtTokenManager;
    protected final JwtHeaderManager jwtHeaderManager;
    protected final SecurityService securityService;

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        final String token = jwtHeaderManager.getAuthorizationHeader(request);

        if (token != null) {  // not all resources require auth — carry on if missing
            try {
                authenticateToken(request, token);
            } catch (JwtTokenUnauthorizedException e) {
                response.sendError(HttpStatus.UNAUTHORIZED.value(), e.getMessage());
                return;
            }
        }
        filterChain.doFilter(request, response);
    }

    private void authenticateToken(HttpServletRequest request, String token) {
        JwtTokenAttributes tokenAttributes = jwtTokenManager.parseToken(token);
        boolean isNotYetAuthenticated = securityService.getAuthentication() == null;

        if (isNotYetAuthenticated && jwtTokenManager.isTokenStillValid(tokenAttributes)) {
            final SecurityUserDetails user = build(tokenAttributes, token);
            MDC.put(TENANT_ID_LABEL, Objects.toString(user.getTenantId())); // logfmt logging
            final var auth = new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
            auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        return ignoredPaths.matches(request);  // /login bypasses the filter
    }
}

Non-Functional Security

  • No secrets in code: JWT_SECRET, DB passwords, Redis auth, API keys are all Kubernetes Secrets. Terraform provisions IAM roles for pod-level AWS access (ECR image pull, MSK connection) — no hardcoded AWS credentials.
  • Audit trail: audit-service records every state-changing operation immutably via ARM_AUDIT_CHANGE_EVENTS Kafka topic. Required for gambling regulatory compliance.
  • Not PCI-DSS scope: ARM is a pricing and risk platform, not a payment processor. No card data is stored or processed — this was a deliberate architectural boundary.
  • TLS: MSK and Redis connections use TLS in production. Internal Kubernetes service-to-service communication uses the cluster network (no mTLS in this version).

Observability — Datadog + Prometheus → Slack

Metrics

Every service exposes /actuator/prometheus. Spring Boot Actuator auto-exports JVM metrics, HTTP request metrics, Kafka consumer lag, and custom application metrics (WebSocket sessions, bet placement rate). Prometheus scrapes all services on a 15-second interval.

Datadog APM

Datadog APM agent runs as a sidecar in each pod. It instruments Spring Boot automatically, capturing distributed traces across service boundaries. A trace started at the POST /slips HTTP request propagates through sportsbook-service → bet-manager-service → advisory-service, visible as a single trace in Datadog.

Datadog Monitors → Slack Alerts

Datadog monitor definitions live in arm-config/dev/datadog_monitors/ and arm-config/prod/datadog_monitors/ as Terraform resources. Each monitor defines a metric threshold and a notification target.

ARM Services │ /actuator/prometheus metrics endpoint ▼ Prometheus (scrape every 15s) │ ▼ Datadog APM + Metrics │ ├── Dashboard: Kafka consumer lag per service, bet placement rate, │ WebSocket connection count, error rate per endpoint │ └── Monitors (Terraform-managed in arm-config) ├── Kafka consumer lag > 1000 messages │ → @slack-arm-alerts: "arm-dev kafka lag spike: sportsbook-service" ├── Service error rate > 5% │ → @slack-arm-alerts + PagerDuty on-call page ├── Pod OOMKilled │ → @slack-arm-alerts: "pod event-service OOMKilled in arm-prod" └── Redis memory > 80% → @slack-arm-alerts: "Redis cluster approaching memory limit"
Why Terraform-managed monitors? Monitor definitions in Terraform are version-controlled, code-reviewed, and reproducible. A manually configured Datadog monitor is undocumented and ephemeral — it can be accidentally deleted or misconfigured. With Terraform: monitor changes require a PR, get reviewed, are applied by CI, and can be rolled back like any other infrastructure change. Dev and prod monitors are defined separately but share the same structure.

Quiz

Q1. dangerfile.js detects a Merge Request with 450 changed lines and no new tests. Where do the alerts go?

  • Danger blocks the merge automatically until the author adds tests
  • Danger posts a comment directly on the GitLab Merge Request AND sends a Slack alert to #arm-code-review — human reviewers make the final decision on whether to merge
  • The GitLab CI pipeline fails and the MR cannot proceed to the build stage
  • Danger sends an email to the developer's manager
Danger is an advisory tool, not a gate. It surfaces violations for human judgment — a 450-line PR without tests might be a large refactor where new tests aren't applicable. Danger informs rather than blocks. The two notification channels (MR comment + Slack) ensure the reviewer sees the flag before approving, even if they miss the MR comment. The team culture decides how strictly to follow Danger's recommendations.

Q2. ARM has no @SpringBootTest integration tests. How is real infrastructure (Redis, RabbitMQ, Kafka) verified?

  • Tests run against the production environment with a special test flag
  • Manual testing via docker-compose up (local 6-node Redis + 3-node RabbitMQ + Kafka) and the arm-dev Kubernetes namespace post-deploy — WireMock stubs external APIs in unit tests
  • Testcontainers integration tests run in a separate nightly CI pipeline
  • Infrastructure is not verified — only business logic is tested
The tradeoff is explicit: @SpringBootTest startup cost (15-30s per class × hundreds of classes) makes CI too slow for a team of 50+ engineers iterating rapidly. The team accepted that infrastructure correctness is verified through: (1) local docker-compose before PR, (2) arm-dev deployment post-merge, (3) arm-int before prod. WireMock stubs bookie APIs so unit tests exercise the feed handler normalisation logic without real external connections.

Q3. Datadog monitor definitions live in arm-config Terraform instead of being configured manually in the Datadog UI. Why?

  • The Datadog UI does not support threshold-based alerting for MSK metrics
  • Terraform-managed monitors are version-controlled, code-reviewed, auditable, and reproducible — manual UI config is ephemeral, undocumented, and can diverge between dev and prod without anyone noticing
  • Terraform is required by Datadog's enterprise licensing terms for the ARM account
  • The Datadog UI cannot connect to AWS MSK metrics directly
Infrastructure as code applies to monitoring as much as to compute. If a monitor is deleted accidentally in the Datadog UI, there is no rollback — it just disappears. With Terraform: the monitor definition is in git, changes require a PR, application is by CI, rollback is a git revert. Dev and prod share the same monitor structure but can have different thresholds (e.g. prod error rate alert fires at 2%, dev at 10%). The Terraform state tracks current state and diffs changes.

Q4. A prod deployment causes the error rate to spike to 12%. What is the fastest rollback path?

  • Revert the code, push to trunk, wait for the full CI pipeline to build and deploy
  • Re-run the previous pipeline's "Deploy to Prod" stage in GitLab CI — this re-executes helm upgrade with the previous image tag, replacing pods in minutes without a new build
  • Scale down to 0 replicas in Kubernetes to stop traffic immediately
  • Restore the prod PostgreSQL database from the pre-deployment snapshot
The previous GitLab CI pipeline is still available with its exact artifact (Docker image SHA). Re-running the "helm-deploy" stage with the previous values re-executes: helm upgrade arm-chart values-prod.yaml --set image.tag={previous-sha}. Kubernetes does a rolling update, replacing pods one by one. No new build required — the previous Docker image is already in ECR. This is the fastest path: typically 2-5 minutes to full rollout vs 10-15 minutes for a new CI build cycle.
