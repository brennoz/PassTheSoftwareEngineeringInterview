ARM BettingCo — System Architecture Overview

Category: Projects · Topic: ARM BettingCo · Est. time: 20 min · Lesson 1 of 14

What is ARM BettingCo?

ARM (Automated Risk Management) is a real-time sports betting risk platform for horse and dog racing at BettingCo. It receives racecards from 18 external bookmakers, calculates risk and pricing for each race, and publishes live odds to internal frontends. The platform comprises 43+ Spring Boot 3.5 / Java 21 microservices deployed on AWS Elastic Kubernetes Service (EKS), spread across dev and production clusters in the eu-west-1 region. Every second of a race meeting, odds from multiple external sources are ingested, reconciled against internal liability positions, and pushed to trader UIs and consumer-facing sportsbook frontends — all without perceptible latency.

The 6 Bounded Contexts

ARM BettingCo is organised into six Bounded Contexts (from Domain-Driven Design (DDD)). Each context owns its data model, its Kafka topics, and its service(s). No context reaches into another's database.

The six bounded contexts are: Feed Ingestion (one handler per bookmaker, 18 total), Event Management (canonical racecard owned by event-service:8081), Pricing & Risk (probability calculations, liability exposure, algorithm models), Bet Lifecycle (acceptance, validation, settlement), Real-time Push (sportsbook-service:8082 — WebSocket relay to browsers), and Authentication (auth-service:8080 — JWT issuance and validation). The bet-recommendation-service:8100 sits across pricing and bet lifecycle, consuming odds to suggest lay/back positions to traders.

Technology Choices

The technology stack is chosen to meet the latency and reliability requirements of live sports betting: odds must reach trader UIs within hundreds of milliseconds of a bookie feed update, at volumes that spike sharply around major race meetings like the Grand National or Cheltenham Festival.

Kubernetes EKS + Helm Orchestration Helm parameterises dev/int/prod with one chart; Horizontal Pod Autoscaler (HPA) auto-scales on CPU

AWS Deployment Topology

All production and development infrastructure lives in the AWS eu-west-1 (Ireland) region. Two separate Elastic Kubernetes Service (EKS) clusters are used: one for development workloads (with two namespaces: arm-dev and arm-int) and one for production. Elastic Container Registry (ECR) accounts are also kept separate to prevent a dev image from being accidentally promoted to prod.

AWS eu-west-1 VPC ├── EKS dev-2-eu-west-1 │ ├── Namespace: arm-dev (development) │ └── Namespace: arm-int (integration) ├── EKS prod-eu-west-1 │ └── Namespace: arm-prod ├── MSK: msk-broker-1,2,3.dev.bettingcosport.com:9092 ├── ElastiCache Redis: 6-node cluster, eu-west-1 ├── ECR dev: 471627132520.dkr.ecr.eu-west-1.amazonaws.com └── ECR prod: 168953832003.dkr.ecr.eu-west-1.amazonaws.com

The Helm chart uses a single parameterised values file per environment. The Horizontal Pod Autoscaler (HPA) default: minReplicas=1, maxReplicas=5, targetCPUUtilizationPercentage=80. Production (values-prod.yaml) overrides to minReplicas=2, maxReplicas=3 — ensuring two pods always run for availability while capping cost. No behavior stabilization block is configured.

Communication Patterns

  • Async (Kafka): External bookmakers (Betfair, SIS, etc.) publish to the WOODS Kafka cluster (192.168.26.101-103:9092). ARM feed handlers consume from WOODS, normalise data into FeedRaceDto, and produce to the BETTINGCO MSK cluster (topic test-local.arm-dev.prices). Downstream ARM services consume from BETTINGCO MSK. Durable, at-least-once delivery.
  • Sync (REST): sportsbook-service calls auth-service, bet-manager, and event-service for query-side reads. All calls use internal Kubernetes DNS: http://service-name:8080. No external network hop.
  • Push (STOMP over WebSocket): sportsbook-service consumes odds updates from Kafka, then pushes to browser clients via STOMP over WebSocket. In production: RabbitMQ STOMP relay (ws.simple-broker=false), allowing multiple pods to fan-out via shared broker. In local dev: embedded Spring SimpleBroker (ws.simple-broker=true) with no RabbitMQ dependency. SockJS fallback for WebSocket-blocked networks.
Why two Kafka clusters? WOODS cluster (192.168.26.101-103:9092) is owned by external bookmakers (Betfair, SIS, etc.) — ARM has no control over its reliability. Feed handlers consume from it; if it goes down or sends garbage, only the ingestion layer is affected. The internal BETTINGCO MSK cluster (msk-broker-1,2,3.dev.bettingcosport.com:9092) is ARM-managed and reliable — downstream services only ever connect here.

This blast-radius isolation is a key resilience design decision. If Betfair’s Kafka brokers become slow or unavailable, only the WOODS consumer layer stalls. BETTINGCO MSK and all downstream ARM services continue operating normally with the last good data in cache. The feed handler is the firewall between external unreliable infrastructure and internal reliable infrastructure.

Quiz

Q1. Why does ARM use RabbitMQ for WebSocket push instead of Kafka directly to browsers?

  • Kafka is too expensive for high-frequency push scenarios
  • Browsers have no Kafka client; RabbitMQ provides STOMP on port 61613 that browsers reach via WebSocket/SockJS
  • RabbitMQ is faster than Kafka for all message types
  • Kafka messages are too large to send over WebSocket connections
Browsers have no Kafka client library. RabbitMQ exposes STOMP on port 61613 (or WebSocket port 15674). sportsbook-service acts as the bridge: consumes from Kafka, relays to STOMP topics, and the browser StompClient subscribes. This is a standard pattern for real-time push in Java microservice stacks.

Q2. What is the purpose of the WOODS Kafka cluster separate from BETTINGCO MSK?

  • One cluster handles horse racing, the other handles dog racing feeds
  • WOODS receives unreliable 3rd-party bookie feeds — isolating them prevents their instability from cascading into internal ARM services on BETTINGCO MSK
  • WOODS is used for dev environments only; BETTINGCO MSK is used for production
  • WOODS is a read-only replica cluster for consumer group scaling
External bookmaker Kafka brokers (Betfair, SIS, etc.) can be slow, unreliable, or send malformed messages. WOODS cluster absorbs this without affecting the internal MSK cluster that all ARM services depend on. This is a blast-radius isolation pattern: 3rd-party failures stay contained in the ingestion layer.

Q3. Helm HPA is configured with maxReplicas=5 and targetCPU=80%. A Grand National race causes a 10x traffic spike. What happens?

  • The overloaded pod crashes and Kubernetes restarts it, causing brief unavailability
  • Kubernetes schedules additional pods up to 5 total as CPU exceeds 80%; services must be stateless (shared state in Redis/Kafka) for this to work correctly
  • HPA disables itself to prevent pod thrashing during sustained high load
  • Traffic is rerouted to the prod EKS cluster's spare capacity
HPA (Horizontal Pod Autoscaler) monitors CPU metrics via the Kubernetes metrics server. When CPU exceeds 80%, it creates additional pods up to maxReplicas=5. All state must be external (Redis for live odds cache, Kafka for the event log) — no in-memory state per pod — otherwise a new pod would start cold with no data and serve stale or missing odds.
