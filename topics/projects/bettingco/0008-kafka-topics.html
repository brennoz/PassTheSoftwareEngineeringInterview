Topic Naming Convention

Internal ARM topics follow the pattern {env}.{service}.{type}. Examples: arm-dev.event-service.json, arm-dev.bet-updates.json. External topics use the bookie name: betfair.odds.horse.uk. All-caps strings such as ARM_BET_SETTLEMENT and ARM_BET_MANAGER_SERVICE_EVENT are Java constants that name @KafkaListener container IDs — they are not Kafka topic names. The actual topic names are always the lowercase dotted strings resolved from application.yml.

Consumer Group ID Pattern

There is no single uniform pattern — group IDs vary by service. Common forms seen in source:

  • test-local-arm.sportsbook-service-armdev (sportsbook-service)
  • test-local-arm-dev.bet-manager-service (bet-manager-service)
  • test-local-arm-dev.settlement-service (settlement-service)
  • test-local.{spring.application.name}-armdev (advisory-service — uses Spring property interpolation)
  • test-local-arm.event-service-armdev (event-service main consumer)

The test-local- or test-local. prefix makes it clear which environment owns the group; multiple environments can coexist on the same Kafka cluster with separate consumer groups and independent offsets. The exact group ID is controlled by the KAFKA_GROUP_ID environment variable per service.

At-Least-Once Delivery

Kafka commits consumer offsets after processing (not before). If a pod crashes mid-processing, the next pod picks up from the last committed offset — the message is redelivered. This means every consumer must be idempotent: processing the same message twice must produce the same result as processing it once.

Why at-least-once, not exactly-once? Kafka's exactly-once semantics (Kafka transactions) require the producer and consumer to share a transactional context. In ARM, each service has its own PostgreSQL database and its own transaction manager — there is no distributed transaction spanning the Kafka consume, DB write, and Kafka produce. At-least-once delivery + service-level idempotency (idempotency_key, check-before-process) is the pragmatic and correct choice for this architecture.

Quiz

Q1. sportsbook-service and pricing-service both consume arm-dev.event-service.json. How does Kafka ensure both receive every message?

  • event-service publishes each message twice, once per consumer service
  • Each service belongs to a different consumer group; Kafka delivers the full topic independently to every consumer group — no message sharing between groups
  • They share one consumer group and a load balancer routes messages between them
  • event-service maintains separate topic copies for each consumer
Kafka's consumer group model: consumers in the same group share partitions (each message processed once). Consumers in different groups each get every message independently. sportsbook-service and pricing-service have separate group IDs (test-local-arm.sportsbook-service-armdev vs test-local-arm.pricing-service-armdev), so both receive every event published to arm-dev.event-service.json.

Q2. bet-manager-service crashes while processing a test-local.arm-dev.bet-settlement message from settlement-service. The offset was not yet committed. What happens?

  • The message is permanently lost — it was already acknowledged by the broker
  • Kafka redelivers the message to the next available bet-manager-service pod; bet-manager-service must be idempotent (check if the bet is already SETTLED before processing)
  • Kafka sends the message to a configured dead-letter topic automatically
  • The pod auto-restarts and processes the message from its in-memory buffer
At-least-once delivery: Kafka only advances the committed offset when the consumer explicitly commits after processing. A crash before commit means the message will be redelivered to the next consumer. bet-manager-service (the consumer of test-local.arm-dev.bet-settlement) must handle this: if bet.status is already SETTLED, skip the redelivered message without writing duplicate settlement records or paying the customer twice.

Q3. Why are external bookie feeds on the WOODS cluster rather than the BETTINGCO MSK cluster?

  • AWS MSK does not support connections from external IP addresses
  • External bookmaker brokers can be unreliable (slow, unavailable, malformed messages); isolating them on WOODS prevents their failures from cascading into the internal BETTINGCO MSK cluster that all ARM services depend on
  • WOODS cluster is cheaper to run than MSK for external data volumes
  • Betfair requires all consuming clients to use their own Kafka brokers
Failure isolation is the core reason. If Betfair's Kafka brokers become slow or unavailable, WOODS absorbs the impact. Feed handlers bridge WOODS → BETTINGCO MSK after normalisation. Internal services (event-service, pricing-service, sportsbook-service) only connect to the reliable, ARM-managed BETTINGCO MSK cluster. The design contains 3rd-party unreliability behind the feed handler boundary.
