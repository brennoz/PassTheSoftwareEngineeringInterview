Story A — The composite local cache on the WebSocket broadcast path

Performance · Collaboration · Distributed systems
Per-pod Caffeine cache with Kafka-driven cross-pod invalidation, instead of shared Redis reads
Grounded in: sportsbook-service/.../config/CacheConfig.java (websocketEventMessageCache, websocketDogRacingMessageCache beans) · sportsbook-service/.../app/service/WebsocketBroadcaster.java (retry config) · lib-utils/.../config/kafka/KafkaCompositeCacheConfig.java (Kafka-backed cache invalidation) · lib-utils/.../config/cache/service/CaffeineCacheService.java (evictCachesByPrefix / evictCacheByKey) · application.yml: composite-local-cache.topic=test-local.local-cache, WEBSOCKET_EVENT_MESSAGE_CACHE_TTL default PT15M
Ssportsbook-service pushes live event/price updates to connected clients over STOMP via WebsocketBroadcaster.broadcast(). The messages it broadcasts are read from a set of named Caffeine caches (websocketEventMessageCache, websocketDogRacingMessageCache, a bet-recommendation cache, a stream-outcome-prices cache) rather than hitting the database or a shared cache on every push. TRunning one Caffeine cache per pod is fast, but naively it means every pod's view can drift the moment the underlying data changes — a stale local cache serving an old price after an update is a real correctness problem, not just a performance nuance, on a live-odds path. AThe pattern the codebase actually uses to solve that is a "composite local cache": each pod keeps its own Caffeine cache for speed, but cache mutations get published to a dedicated internal Kafka topic (test-local.local-cache), and every pod runs a Kafka listener that consumes those events and evicts the matching key from its own local cache (CaffeineCacheService.evictCacheByKey / evictCachesByPrefix). So reads stay local-cache-fast — no network hop to a shared store on the broadcast hot path — but a write on any one pod still propagates an eviction to every other pod within one Kafka round-trip, instead of relying on a short TTL and just hoping nobody reads stale data in the meantime. RThat's a genuinely nice trade: you get the latency profile of a local, in-process cache, and the consistency guarantee of "every pod's cache gets told the moment something changed" instead of "every pod's cache is stale for up to N minutes." The 15-minute TTL on the websocket caches is really a safety net for the case where an eviction message is somehow missed, not the primary consistency mechanism.
websocketEventMessageCache TTL: 15 min (safety net, not primary consistency mechanism) Broadcast retry: 6 attempts total (5 retries), 500ms × 1.5 backoff on MessageDeliveryException Cache invalidation: dedicated internal Kafka topic, one hop to reach every pod

If pushed on the disagreement angle

The natural pushback here is "why not just read from Redis directly and skip the complexity of a composite cache?" The honest answer is a genuine trade-off, not a strictly better option either way: a direct shared-Redis read is simpler to reason about (one source of truth, no eviction-propagation logic to get wrong) but puts a network hop and a shared resource directly on the highest-traffic path in the platform — exactly where you don't want a single point of contention. The composite-cache approach accepts more moving parts (a Kafka topic, an eviction listener on every pod) in exchange for keeping that hot path fully local. Worth being honest in an interview that this is a real complexity cost, not a free lunch — the payoff only makes sense because that broadcast path is disproportionately hot compared to everything else in the service.

Story B — The idempotency check that's inconsistent with itself

Technical problem-solving · System design
SlipService.createSlip() has a real race window — and the codebase already has the fix pattern, just not applied here
Grounded in: bet-manager-service/.../app/service/SlipService.java (createSlip(), the idempotency SELECT) · bet-manager-service/.../app/service/RedissonLockService.java (lockAndGet()) · bet-manager-service/.../app/service/CustomerService.java (createOrUpdateCustomerWithLock() — the real usage of the lock, on the same (tenantId, sportsbookRef) key shape)
SSlipService.createSlip() is @Transactional and starts with a genuine idempotency check — the code comment says it directly: "If this slip has already been placed, then send it straight back so that this service is idempotent." It does a slipRepository.findBySportsbookId(tenantId, sportsbookRef) lookup, and if a match exists, returns it instead of creating a duplicate. TThat's a SELECT-then-INSERT pattern with nothing enforcing atomicity between the two — two near-simultaneous requests with the same reference can both pass the SELECT before either commits its INSERT, and both create a slip. On a betting platform that's a duplicate stake deduction on a real account, not a cosmetic bug. AWhat makes this a good story is that the fix pattern already exists in the same codebase, just applied to a different entity: CustomerService.createOrUpdateCustomerWithLock() wraps the exact same "find-or-create keyed by (tenantId, sportsbookRef)" shape in RedissonLockService.lockAndGet(lockKey, () -> ...) — a distributed lock via Redisson, keyed on tenant+reference, held for the duration of the check-then-write. SlipService.createSlip() doesn't use it. So the options aren't theoretical: option one is wrap the slip idempotency check the same way CustomerService already wraps customer creation — smallest possible change, reuses an existing, already-tested utility, no schema migration. Option two is a DB-level unique constraint on (sportsbookTenantId, sportsbookRef) with catch-and-return-existing on conflict — more "correct" in the sense of being enforced by the database itself regardless of application code, but a schema change on the bets table is a bigger, riskier piece of work to get signed off. Option three — leave it — isn't reasonable once you've seen the same race already got fixed one service over. RThe Redisson-lock option is the one I'd push for as the immediate fix, precisely because the pattern, the dependency, and the tests for it already exist in the codebase — it's applying an established internal solution consistently, not introducing something new. The unique-constraint version is the better long-term answer and worth tracking separately, but doesn't need to block closing the actual race.

Why this is a strong technical-problem-solving story

It's not "I found a bug," it's "I found an inconsistency between two services solving the identical problem two different ways, one of them safely and one of them not" — that's a more senior-reading observation than a generic bug report, and it comes with a genuinely low-risk fix because the pattern to copy is sitting right there in the same codebase.

Story C — Settlement as a choreographed flow, and why advisory stays off the placement path

Distributed systems · Event-driven architecture · System design
18 external feeds normalised into one contract; settlement owned by the service that owns the bet's state
Grounded in: arm-backend/feed-handler-* — 18 separate feed-handler services (betfair, sis, tote, matchbook, ladbrokes-coral, and 13 others), all built on lib-feed-handlers · bet-manager-service/.../app/settlement/SettlementEngine.java (settle(Bet, SettledReason, String username), BOG_CAP platform config, BetAdjustmentType.BOG / FREE_STAKE_BOG, BetDeduction/BetDeductionType for non-runner price adjustments, isEachWay() handling) · settlement-service (router) vs bet-manager-service (calculator) split
SThe platform doesn't talk to one external odds source — it talks to 18, each a separate feed-handler-* service (Betfair, SIS, Tote, Matchbook, Ladbrokes Coral, and more), each consuming a different external Kafka cluster we don't control, each normalising into one shared internal contract before anything downstream — pricing, event-service, sportsbook — has to care which bookmaker a price came from. TOnce a race finishes, settlement has to work out every affected bet's payout — including Best-Odds-Guaranteed adjustments, non-runner deductions, and each-way terms — without either blocking bet placement or letting two services both think they own the authoritative bet state. AThe split that matters: bet placement itself stays synchronous and minimal — idempotency check, insert, done. Advisory (risk signals on the bet) is deliberately NOT a synchronous gate on placement — it's published to Kafka and picked up asynchronously, because advisory is informational for a risk team, not something a customer should wait on. Settlement is a genuine two-service choreography, not one service doing everything: settlement-service consumes race-result events and calls back to bet-manager over REST to fetch the affected bets, then publishes that list to a dedicated settlement topic — but the actual payout math (SettlementEngine.settle(), applying BOG_CAP, resolving deduction types for non-runners, each-way legs) runs inside bet-manager-service, because that's the service that owns the bet row. Settlement-service triggers; bet-manager-service decides and writes. RPlacement latency never depends on how much advisory or settlement work is queued. And nothing downstream has to ask "did someone else already touch this bet's status" — because only one service is ever allowed to.
18 external feed handlers, one shared internal contract SettlementEngine: BOG (+ FREE_STAKE_BOG variant), BOG_CAP config, non-runner deductions, each-way settlement-service = router/trigger; bet-manager-service = calculator/owner

The one-line version, if time is short

"We kept the customer-facing path — placing a bet — completely decoupled from the two things that don't need to happen in real time: risk advisory and settlement. And within settlement, the service that triggers the payout calculation isn't the same service that's allowed to actually change the bet's state — that split is deliberate, not incidental."

Story D — Genuine interest in sports/betting/probability

Personal framing — not a technical story, keep it short and honest
Why this domain specifically

This is the one question where a rehearsed STAR structure reads as fake — answer it more like you'd actually talk.

What pulled me in wasn't the sport side first, it was realising how much genuinely fiddly engineering sits underneath something that looks simple from the outside — a price on a screen. Working on SettlementEngine meant actually implementing Best-Odds-Guaranteed logic, non-runner deductions, each-way terms — rules that sound simple stated out loud and are genuinely unforgiving to get right in code, because a rounding or ordering mistake there is someone's real payout, not a cosmetic bug. That combination — real-time systems, a domain with hard, precise rules, and money on the line so correctness isn't optional — is what keeps it interesting for me beyond just "I like sport." I'd rather work on a system where getting a settlement calculation wrong is a felt, real problem than one where correctness is more of an academic nicety.
