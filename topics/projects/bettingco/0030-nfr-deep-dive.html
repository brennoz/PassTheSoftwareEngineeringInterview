Non-Functional Requirements — 5 Pillars

Performance · Scalability · Availability · Resilience · Observability · ARM numbers + Opayo equivalents
Why NFRs matter at a payment platform interview Most candidates cover functional requirements well (what the system does). Senior engineers are expected to demonstrate they thought about the system's operational properties: how fast, how many, how often it fails, how quickly it recovers, how you know it's healthy. At Opayo, every one of these pillars maps to a merchant SLA or a card scheme requirement. ARM BettingCo gives you concrete numbers for all five.

P
Performance
Target: sub-100ms in-play · p99 <200ms on event-service

Performance in a real-time system is not about raw speed — it's about latency under load. A response that takes 50ms on a quiet server but 800ms on a race day with 5,000 concurrent requests is not a performant system. ARM's performance work focused on two areas: eliminating unnecessary DB round-trips (Redis caching) and eliminating slow queries (indexed lookups).

# Three-layer latency strategy in ARM:

# Layer 1 — Local in-memory cache (ARM uses LOCAL_CACHE_ENABLED=true in prod)
# Note: REDIS_CACHE_ENABLED=false in prod — ARM uses local composite cache not Redis
# for the hot read path. Redis cluster is present (redis.svc.cluster.local) but
# the Spring cache abstraction uses local cache in production config.
# websocketEventMessageCache: event state cached locally per pod
# streamOutcomePricesCache: prices cached locally (slower to invalidate across pods)
# Cache hit = no DB query = sub-1ms response

# Layer 2 — Indexed PostgreSQL queries (1-5ms)
# Partial index on active events only:
# CREATE INDEX CONCURRENTLY idx_events_active ON events(id) WHERE status='ACTIVE';
# 500k total events, 12k active → index scan on 12k not seq scan on 500k

# Layer 3 — Async Kafka writes (don't block the response path)
# Publishing to Kafka is fire-and-forget on the response path:
# 1. Request arrives → validate → update DB → respond 200
# 2. Kafka publish happens asynchronously in a @TransactionalEventListener
# The client gets the 200 before Kafka publish completes.
# Kafka durability is guaranteed by the outbox pattern — not by blocking the response.
WHAT BREAKS WITHOUT THIS Without in-process (Caffeine) caching: every odds update on 50,000 WebSocket clients triggers a DB query. At 5 updates/second per race = 250,000 DB queries/second. PostgreSQL connection pool exhausted → 503s. Without partial index: event-service GET /events/active scans 500k rows → 1.5s response → p99 SLA breach on every race meeting.
OPAYO EQUIVALENT Card auth response must be <200ms to merchant. Merchant SLA violation causes chargebacks. Performance strategy: in-memory or Redis cache for merchant config (routing rules, fee rates — Opayo would use Redis as a shared distributed cache across pods, unlike ARM's local cache), indexed PostgreSQL for payment lookup, async Kafka write for audit log (not in response path). Same layered approach: cache first, indexed DB second, async for non-blocking work.
S
Scalability
HPA: dev max=1, prod min=2 max=3, at 80% CPU · Kafka partition = consumer concurrency

Scalability means adding capacity horizontally without architectural change. ARM uses two mechanisms: Kubernetes HPA for request-driven services, and Kafka partition count for event-driven consumers. The key insight is that these are different scaling dimensions: HPA scales request processing, Kafka partitions scale event processing — you need both.

## HPA — scales request-driven services (event-service, sportsbook-service)
## Default (dev): min=1 max=1. Default base chart: min=1 max=5.
## Production override: min=2 max=3 (conservative — stability over burst capacity)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 1     # base default; prod overrides to 2
  maxReplicas: 5     # base default; prod overrides to 3
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80   # scale up before saturation
  # Note: no behavior/stabilizationWindowSeconds configured in ARM's HPA template.
  # Kubernetes default stabilization: 0s scaleUp (immediate), 300s scaleDown (5min).
  # This means ARM scales up immediately on CPU spike — no artificial delay.
  # If thrashing is observed, adding scaleUp.stabilizationWindowSeconds: 60 is the fix.

## Kafka — scales event-driven consumers (settlement, pricing)
# Consumer concurrency = number of partitions (one thread per partition per consumer group)
# ARM_BET_SETTLEMENT topic: 6 partitions → max 6 concurrent settlement consumers
# To scale settlement throughput: increase partition count to 12 → max 12 concurrent consumers
# Rule: partition count is the ceiling of consumer concurrency — set it once, hard to change later

## What HPA can't do:
# HPA scales on CPU/memory. A Kafka consumer with 10,000 message lag may have LOW CPU
# (messages process fast but queue is large). HPA won't trigger a scale-up.
# Solution: KEDA (Kubernetes Event-Driven Autoscaling) — scales on Kafka consumer lag.
# ARM uses CPU HPA. KEDA would be the improvement for settlement-service.
WHAT BREAKS WITHOUT THIS Without HPA: event-service handles race day traffic with 1 pod → CPU 100% → thread starvation → timeouts → 503s to all clients simultaneously. Without Kafka partition planning: settlement topic has 2 partitions → max 2 concurrent settlement consumers → settlement lag grows linearly with bet volume during large race meetings.
OPAYO EQUIVALENT Black Friday payment volume can spike 100× in minutes (midnight shopping, payday events). HPA on the authorisation service with pre-warming (manual scaling before known traffic events) plus Kafka partition count on the settlement topic sized for peak volume. Same KEDA improvement applies: scale settlement consumers on lag, not CPU.
A
Availability
Multi-AZ · PodDisruptionBudget · Rolling update zero-downtime · RTO <2min

Availability is measured as the percentage of time the system correctly handles requests. ARM targets 99.9% (8.7h downtime/year budget). This requires that no single failure — pod crash, node failure, AZ outage, deployment — causes an outage. Three mechanisms work together: multi-AZ scheduling, PodDisruptionBudget, and rolling updates.

## Multi-AZ topology — pods spread across availability zones
spec:
  topologySpreadConstraints:
  - maxSkew: 1                           # at most 1 pod difference between AZs
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule    # scheduler refuses to create an unbalanced pod
    labelSelector:
      matchLabels:
        app: event-service
# Result: 3 pods → 1 per AZ. AZ-a fails → 2 pods remain in AZ-b and AZ-c.
# Service continues with 66% capacity. No outage.

## PodDisruptionBudget — prevents all pods evicted during node drain
apiVersion: policy/v1
kind: PodDisruptionBudget
spec:
  selector:
    matchLabels:
      app: event-service
  minAvailable: 2   # at least 2 pods always up during voluntary disruption
# Node drain (cluster upgrade): K8s evicts pods one at a time.
# Without PDB: all 3 pods on 3 nodes drained simultaneously → full outage.
# With PDB(minAvailable=2): only 1 pod evicted at a time → 2 always serving.

## Rolling update — zero-downtime deployment
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1   # at most 1 pod down during update
    maxSurge: 1         # 1 extra pod created before old one removed

## RTO (Recovery Time Objective) — time to restore after failure
# Pod crash → K8s replaces immediately (liveness probe fails → restart)
# Bad deployment → kubectl rollout undo → previous ReplicaSet active in ~90s
# Node failure → pods rescheduled on healthy nodes → ~2-3 minutes (PVC attachment adds time)
WHAT BREAKS WITHOUT THIS Without multi-AZ: all 3 pods land in eu-west-1a. AZ-a failure (AWS has had AZ-level failures) → full event-service outage. Without PDB: cluster upgrade drains all nodes simultaneously → complete platform outage during maintenance window. Without rolling update: deployment requires taking the service down to update → planned downtime every release.
OPAYO EQUIVALENT Card scheme SLAs require Opayo to maintain 99.95%+ availability. Multi-AZ is non-negotiable. PDB ensures cluster maintenance doesn't create outages during which merchants can't process payments. Rolling update means deployments are invisible to merchants — no planned downtime windows. RTO <2min via rollback is required to minimise merchant impact during a bad deployment.
R
Resilience
Circuit breaker · @Retryable · Dead Letter Queue · Saga compensation

Resilience is the ability to continue operating correctly when dependencies fail. In a distributed system, failure of any single dependency (external feed, advisory service, DB) should not cascade into a full platform failure. ARM uses three resilience mechanisms: circuit breaker for synchronous calls, retry for transient failures, and Dead Letter Queue for events that cannot be processed.

// Circuit Breaker — settlement-service calling bet-manager REST API
// settlement-service calls betsApi.getBetStatusesForOutcome() synchronously
// to fetch bets for a race outcome before publishing to the settlement topic.
// Pattern: if bet-manager fails 3 times in a row, open circuit for 60s.
// During open circuit: fail-fast (immediate exception, don't wait for timeout).
// After 60s: allow 1 probe request. If successful, close circuit. If not, stay open.

// NOTE: advisory-service is NOT called synchronously at bet placement.
// Advisory notifications are sent asynchronously via Kafka (ARM_BET_MANAGER_SERVICE_EVENT
// topic) from bet-manager-service — the bet is accepted without waiting for advisory.

@Component
public class BetManagerApiClient {
    private final CircuitBreaker circuitBreaker;
    private final BetsApi betsApi;  // generated SDK client

    public List<BetStatusDto> getBetStatusesForOutcome(String outcomeId) {
        return CircuitBreaker.decorateSupplier(circuitBreaker, () ->
            betsApi.getBetStatusesForOutcome(outcomeId)
        ).get();
    }
    // CircuitBreakerConfig: failureRateThreshold=50%, waitDurationInOpenState=60s,
    // slidingWindowSize=10 (last 10 calls determine open/closed state)
}

// Retry — Kafka consumer transient failures (DB timeout, momentary unavailability)
@KafkaListener(id = ARM_BET_SETTLEMENT, ...)
@Retryable(maxAttempts = 3, backoff = @Backoff(delay = 1000, multiplier = 2))
public void consumeBets(List<BetStatusDto> bets) {
    settlementService.processBatch(bets);
}
// Attempt 1 → wait 1s → Attempt 2 → wait 2s → Attempt 3 → send to DLQ

// Dead Letter Queue — bets that fail all 3 retries
// Configured in Kafka consumer properties:
spring.kafka.consumer.properties.spring.json.trusted.packages=*
spring.kafka.listener.ack-mode=manual  # don't auto-commit until processed
# DLQ topic: arm-dev.bet-settlement.DLT
# Monitoring: Datadog alert on DLQ partition lag > 0 → immediate investigation
WHAT BREAKS WITHOUT THIS Without circuit breaker: advisory-service slow (30s timeout per call). 100 concurrent bet placements → 100 threads blocked for 30s each → thread pool exhausted → bet-manager-service 503 for all new requests → full bet placement outage. Without retry: a 500ms DB timeout causes one settlement message to fail permanently → 1 bet never settled → customer complaint + manual fix. Without DLQ: a message that cannot be processed blocks the consumer → entire settlement topic stops processing → all bets unsettled.
OPAYO EQUIVALENT Circuit breaker on card scheme call: Visa/MC network hiccup should not cause Opayo's authorisation service to exhaust its thread pool. Circuit opens after 3 failures → fail-fast with "try again" response to merchant → merchant retries via a different payment method. DLQ for settlement events: a payment that cannot be settled after 3 retries goes to DLQ → operations team investigates → manual resolution → no automated money movement on ambiguous state.
O
Observability
Datadog APM · Kafka lag alerts · p99 dashboards · Log correlation

Observability is the ability to understand what the system is doing from its external outputs — without adding new instrumentation. A system is observable if you can diagnose any failure using only its existing metrics, traces, and logs. The three pillars are metrics (what happened in aggregate), traces (what happened for a specific request), and logs (why it happened).

## Metrics — aggregated system state
# Spring Boot Actuator + Micrometer → Prometheus scrape → Datadog
# Key ARM metrics:
# http.server.requests (rate, p50, p95, p99 per endpoint)
# kafka.consumer.fetch-manager.records-lag (consumer lag per partition)
# hikaricp.connections.active (pool utilisation)
# jvm.memory.used (heap before OOM)
# resilience4j.circuitbreaker.state (open/closed/half-open)

# Datadog monitors (alert conditions):
# - p99 latency on event-service > 500ms for 5 minutes → PagerDuty
# - Kafka consumer lag > 1000 messages → Slack warning
# - Kafka consumer lag > 10000 messages → PagerDuty
# - Error rate > 1% for 3 minutes → PagerDuty
# - HikariCP active connections > 80% pool for 2 minutes → PagerDuty

## Traces — individual request journey
# Datadog APM auto-instruments Spring Boot (no manual span creation needed for HTTP/Kafka)
# Trace shows: HTTP handler time → service method time → DB query time → Kafka publish time
# Correlation: traceId in logs → trace in Datadog APM → full request journey
# ARM pattern: log traceId with every business event
log.info("Bet settled betId={} traceId={}", betId, MDC.get("dd.trace_id"));

## Logs — structured, searchable
# All services use SLF4J + Logback → JSON format → Datadog Log Management
# Fields in every log line: service, host, environment, traceId, tenantId (no PII)
# Datadog log correlation: click a trace → see all log lines for that trace → exact error
# Log-level change without restart:
# POST /actuator/loggers/com.bettingcosports.settlement {"configuredLevel":"DEBUG"}
# → enable DEBUG for settlement package in production for 10 minutes, revert to INFO
WHAT BREAKS WITHOUT THIS Without traces: a slow request takes 2s. You see it in Datadog error count. But which service? Which DB query? Which Kafka topic? You're guessing. Fix takes 4 hours instead of 20 minutes. Without Kafka lag monitoring: settlement consumer crashes silently. No alert fires. Users call support reporting unsettled bets 2 hours later. Without structured logs: you can't search logs by tenantId → you can't isolate a specific client's issue in 2 minutes → support SLA breached.
OPAYO EQUIVALENT Same three pillars + payment-specific additions: settlement reconciliation metric (expected settled vs actual settled — any gap = a missing payment), fraud detection false positive rate (too high = merchants angry; too low = fraud losses), PCI audit log completeness metric (all card data access logged — automated daily check), and authorisation decline rate by issuer (sudden spike in declines from one bank = their system is down, not Opayo's fault).
Interview answer: "How do you know the system is healthy?" Senior answer covers all five pillars in 60 seconds: "Datadog shows me p99 latency per endpoint (performance), pod count vs desired (scalability), rolling update status and PDB violations (availability), circuit breaker state and DLQ lag (resilience), and distributed traces for any request that took over 500ms (observability). If all five are green, the system is healthy. If any one is degraded, I know exactly where to look."

Quiz

Q1. A downstream service that bet-manager-service calls synchronously is failing intermittently (30% of calls returning 500). With a 3-second timeout and no circuit breaker, what happens to bet-manager-service under 200 concurrent bet placements?

  • 30% of bet placements fail with a 500 error — only the calls that fail are affected, other bets continue normally
  • The JVM's thread pool absorbs the load — Java 21 virtual threads mean each request gets its own lightweight thread with no contention
  • Thread pool exhaustion: 30% of 200 concurrent calls (60 threads) are waiting 3 seconds for the downstream timeout. Those 60 threads are blocked. New bet placement requests queue behind them. If the pool is 100 threads and 60 are blocked for 3 seconds, only 40 are available for new requests. At 200 concurrent requests, the queue fills faster than threads free up — bet-manager-service starts returning 503 for all new bets, including those where the downstream call would have succeeded. A 30% dependency failure rate causes 100% bet placement failure. This is cascading failure. Circuit breaker prevents it: after 3 failures, fail-fast in 1ms instead of blocking for 3 seconds.
  • Kafka absorbs the pressure — failed downstream calls are published to a retry topic and reattempted asynchronously
This is the classic cascading failure pattern. The downstream service failure doesn't just fail 30% of bets — it ties up threads for 3 seconds each (the timeout duration). Thread exhaustion means the service can't serve even the 70% of requests that would have succeeded. The circuit breaker's key property is fail-fast: instead of waiting 3 seconds for a timeout, it fails in 1ms when the circuit is open. 60 threads × 3 seconds = 180 thread-seconds consumed. 60 threads × 1ms (fail-fast) = 0.06 thread-seconds — a 3000× difference in thread consumption. Virtual threads (Java 21) help with blocking I/O but don't eliminate the timeout problem — a virtual thread waiting 3 seconds is still a virtual thread not serving another request.

Q2. ARM's settlement-service has Kafka consumer lag alerts at 1,000 messages (warning) and 10,000 messages (critical). The warning fires at 2pm on a race day. What do you do in the first 5 minutes?

  • Immediately scale up the settlement-service HPA maxReplicas from 5 to 10 — more pods = more consumers = faster processing
  • Check if there was a recent deployment — rollback if yes, wait for lag to clear naturally if no
  • Restart the settlement-service pods — consumer group rebalance often clears transient lag
  • Step 1: kubectl get pods -l app=settlement-service -n arm-prod — are pods Running and Ready? Step 2: kafka-consumer-groups.sh --describe → which partition has the lag? Is 1 consumer dead (CrashLoopBackOff)? Step 3: check Datadog APM for settlement-service error rate — is it processing but slow, or not processing at all? Step 4: check recent deployments in GitLab CI — any deploy in the last 30 minutes? Step 5: based on findings: dead pod → check kubectl logs --previous for crash reason. Slow processing → check DB query time in traces. Recent deploy → prepare rollback. Do NOT scale HPA maxReplicas blindly — the lag may be caused by a bug that more pods will repeat faster.
A lag warning requires diagnosis before action. Scaling up with a bug in the processing code just means the bug runs on more pods simultaneously — potentially causing more damage (e.g., if the bug causes a DB connection leak, more pods = faster pool exhaustion). Restarting pods (option C) may help if the cause is a stuck consumer, but could also delay diagnosis by clearing evidence. The systematic approach: diagnose first (is the consumer alive? is it erroring? is it just slow?), then act with targeted response. The lag warning threshold (1,000 messages) is designed to fire early enough that you have 10-15 minutes before it becomes critical — use that time for diagnosis, not panic actions.

Q3. Opayo asks: "If we get 10× our normal payment volume tomorrow morning (a Black Friday event), what fails first in your ARM BettingCo architecture, and how do you prepare for it?"

  • First failure point: HikariCP connection pool on event-service (or whichever service has the most DB read traffic). Pool is sized for normal load — 10× load exhausts it. HPA scales pods to 5 (maxReplicas) but each pod has its own connection pool — total connections = 5 × pool-size. PostgreSQL max_connections is a hard limit. Fix: pre-scale pods manually before the event (kubectl scale —replicas=4), verify DB connection headroom in pg_stat_activity, enable read replica for GET /events queries. Second failure point: Kafka settlement consumer at maxReplicas=5 with 6 partitions — at 10× volume the lag grows. Fix: pre-set maxReplicas to 6 (matches partition count) so HPA can use all partitions. Preparation checklist: review HPA settings, check DB connection limits, review Kafka partition headroom, run load test in arm-int at 5× normal, set Datadog alerts to lower thresholds for the event window.
  • Nothing fails — HPA automatically scales all services to handle 10× load, and Kafka absorbs the extra messages without any manual intervention required
  • The Redis cache fails first because 10× read traffic exhausts Redis connection limits and causes cache evictions that cascade to DB overload
  • The Kubernetes cluster runs out of nodes — each pod requires a new node and AWS takes 5 minutes to provision new EC2 instances, creating a cold-start delay under sudden load spikes
HPA can scale pods but it has two limits: maxReplicas (config ceiling) and node capacity (infrastructure ceiling). At 10× load, if maxReplicas=5 is hit, HPA can't scale further. Connection pool exhaustion happens when 5 pods × 10-connection pool = 50 connections, but the service needs 100 for 10× load. The preparation checklist is the key senior answer: you don't just say "HPA handles it" — you identify the specific constraints (maxReplicas, DB connections, Kafka partition ceiling) and take proactive steps before the event. Pre-scaling is valid: set replicas to 4 manually before the event so HPA starts from a higher baseline. Load testing at 5× in arm-int tells you where the real bottleneck is — it's almost never where you expect.
