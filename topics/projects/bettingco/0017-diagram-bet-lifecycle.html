ARM BettingCo — Bet Lifecycle (End-to-End Sequence)

Category: Projects · Topic: ARM BettingCo · Diagram 3 of 4 · Sequence Diagram

A slip (wrapping one or more bets) travels through five services across two protocols (REST and Kafka) before the customer receives their settlement push via WebSocket. The sequence maps every step from browser POST to STOMP push — including the asynchronous race result trigger from the feed handler. Note: there is no advisory-service REST call at placement — advisory consumes bet events asynchronously via Kafka after placement completes.

Idempotency: SELECT pre-check, not UNIQUE constraint bet-manager-service prevents duplicate slips via a SELECT pre-check: slipRepository.findBySportsbookId(tenantId, sportsbookRef). If a row already exists, the existing SlipDto is returned immediately with no INSERT. There is no UNIQUE constraint involved — no exception is caught. This is deliberate: a UNIQUE constraint would still INSERT before failing, creating a brief lock; the SELECT pre-check avoids that entirely.
No advisory REST call at placement bet-manager-service has zero advisory-service imports. Advisory-service consumes the ARM_BET_MANAGER_SERVICE_EVENT Kafka topic asynchronously after the slip is persisted. This is a common misconception in architectural diagrams — advisory is async risk monitoring, not a synchronous gate at placement.
Settlement-service role: router, not calculator settlement-service does NOT calculate payouts. It calls betsApi.getBetStatusesForOutcome() (REST to bet-manager) to get the list of bets to settle, then publishes that batch to Kafka. The actual payout calculation happens in bet-manager's SettlementEngine inside BetSettlementListener — BOG parallel path, Rule 4 deductions, each-way stake splits, BetAdjustment application. Kafka batch consumer decouples the load so settlement-service releases quickly without holding a DB connection.
