Behavioural Interview Questions

Opayo interview prep · STAR skeleton + model answer · 10 questions
How to use this page Each question has a STAR skeleton — four bullet-point anchors to structure your spoken answer. Study the skeleton first; it's what you personalise and deliver naturally. Click "Show model answer" to read a full written version and check you're hitting the right themes. The key phrases are what the interviewer is listening for — land at least two per answer.
STAR format reminder Situation — set the scene briefly (1-2 sentences). Task — what was your specific responsibility. Action — what YOU did (not "we" — own it). Result — measurable outcome + what you learned. Target 90-120 seconds per answer. Silence at the end is fine — don't fill with hedging.

I'm a backend software engineer specialised in distributed, event-driven systems on the JVM. Q3
Tell me about a significant technical challenge you overcame.
SDuring a major race meeting, settlement-service Kafka consumer started lagging — 10,000 messages behind. Bets were not being settled. Financial exposure growing with every minute. TMy responsibility: diagnose root cause, restore settlement, prevent recurrence — without losing any messages or double-settling. AUsed kafka-consumer-groups.sh to confirm consumer dead (CrashLoopBackOff). kubectl logs --previous revealed OOMKill from oversized batch (5,000 records, 512Mi limit). Reduced batch size to 200 via ConfigMap change (no redeploy needed). Consumer recovered and cleared lag in ~10 minutes. Root cause: environment-specific batch size not caught in arm-int (lower volume). Added consumer lag Datadog monitor + memory alert at 80% heap. RZero messages lost (Kafka guaranteed delivery). Zero double-settlements (SettlementEngine checks current bet status before applying SETTLED — replayed messages are skipped). Incident resolved in 22 minutes. Monitor now fires before OOM recurs.
Key phrases to land kafka-consumer-groups.sh OOMKill diagnosis zero messages lost idempotency prevented double-settlement monitor to prevent recurrence
During a major race meeting, I was paged because our settlement-service Kafka consumer was 10,000 messages behind. Every unprocessed message was a bet not settled — direct financial exposure for the platform.

My first step was to confirm the consumer was actually dead, not just slow: kafka-consumer-groups.sh --describe --group ARM_BET_SETTLEMENT showed the consumer ID as blank — the pod had crashed. kubectl logs --previous revealed a Java heap space OOMKill. The batch size had been set to 5,000 for a performance experiment and never reverted — fine in our lower-volume arm-int environment, lethal on race day with real load.

I changed the batch size from 5,000 to 200 via a ConfigMap update — no redeploy, just a rolling restart. The consumer reconnected, started processing at 200 messages per poll, and cleared the lag in 9 minutes.

Zero messages were lost because Kafka guaranteed at-least-once delivery from committed offsets. Zero double-settlements because bet-manager's SettlementEngine checks current bet status before writing SETTLED — if a message is replayed to an already-settled bet, the engine skips it without reprocessing. After the incident I added two Datadog monitors: Kafka consumer lag threshold and JVM heap usage at 80%. Both would have fired 15 minutes before the OOM on that day. — ~145 words, ~95 seconds
Q4
Tell me about a time you disagreed with a technical decision.
STeam was debating how to implement cross-cutting cache invalidation in TenantService. The proposed approach used a plain this reference for @Cacheable — which silently bypasses Spring's proxy and makes caching a no-op. TI disagreed: the proposed approach looked correct but would fail silently in production. Needed to convince the team without blocking the sprint. AI wrote a failing unit test that proved the no-proxy issue — the cache was never populated when called via this. Then proposed the self-injection pattern: inject the Spring proxy as a constructor dependency. Showed it in a spike branch. Walked the team through WHY Spring proxies work this way (CGLIB subclass, method interception only on external calls). RTeam adopted self-injection. Test became part of CI. Later caught another instance of the same anti-pattern in a different service. The test-first approach meant the disagreement was settled by evidence, not opinion.
Key phrases to land test as evidence not opinion failing silently in production spike branch to prove the point
We were implementing Redis caching on TenantService — a hot path called on every authenticated request. A colleague proposed calling the cached method directly as this.getTenant(id) within the same class. That looks correct but silently bypasses Spring's CGLIB proxy — @Cacheable only intercepts external method calls through the proxy, not internal this calls. The cache would never be populated, and we'd never see an error — just Redis never being used.

Rather than arguing in a PR comment, I wrote a unit test that demonstrated the bug: mock the Redis cache, call the method via this, assert cache was never populated. The test failed, proving the point without rhetoric. I then created a spike branch with the self-injection fix: inject the bean's own Spring proxy as a constructor dependency and call through that. Ran the test again — green.

The team adopted the pattern. The test lives in CI. Three months later it caught the same anti-pattern in a different service before it reached production. My lesson: technical disagreements should be resolved by evidence. A five-minute spike that proves the bug beats three rounds of back-and-forth in PR comments. — ~150 words, ~100 seconds
Q5
Tell me about a time you influenced without formal authority.
SARM BettingCo had inconsistent idempotency across services — some had it, some didn't. No cross-team standard. Multiple services were at risk of duplicate processing on retry. TI wasn't the tech lead. I had no mandate to change other services. But the risk was real and the fix was teachable. AWrote an internal one-pager: "Idempotency at ARM — pattern, why, implementation." Shared it in the engineering Slack channel. Built a reference implementation in bet-manager-service (SELECT pre-check on the natural business key before any state-changing INSERT). Offered to pair-review PRs in other services that added the same pattern. Within one sprint, three other services adopted it independently. RPattern became de facto standard. Added to our PR review checklist under "write endpoints." No authority used — just a clear explanation of the risk, a working example, and availability to help.
Key phrases to land one-pager + reference implementation made it easy to adopt, not mandatory PR checklist as lasting artefact
Idempotency handling across ARM BettingCo was inconsistent — bet-manager had it, but three other services processing financial writes didn't. Any of those services could double-process on a Kafka consumer replay. I wasn't the tech lead and had no mandate to enforce changes in other teams' code.

My approach was to make the correct thing easy and the incorrect thing visible. I wrote a short internal doc: the problem (what double-processing looks like in production), the pattern (SELECT pre-check on the natural business key before any state-changing INSERT — if a record with that key already exists, return the existing result rather than inserting again), and a working implementation in bet-manager-service that anyone could copy. I shared it in our Slack engineering channel, not as a mandate but as "here's what I built and why." I offered to pair on PRs for anyone adding the pattern to their service.

Within a sprint, three services had adopted it — not because I told them to, but because the reference implementation was clear and the risk was explained concretely. We added "idempotency check: does this write endpoint check for an existing record before inserting?" to our PR review checklist, so the standard lives in the process now, not in my memory. — ~145 words, ~95 seconds
Q6
Tell me about a failure and what you learned.
SI deployed a change to pricing-service that removed a Redis TTL from a cache configuration — a one-line change I considered trivial, didn't flag for extra review. TNo immediate error. Four hours later Redis memory was full — 2.4 million keys with no expiry. Cache eviction started, pricing slowed, error rate climbed. ADiagnosed via redis-cli INFO memory — maxmemory nearly reached, eviction rate high. Found the missing TTL in the diff. Reverted the configuration and purged the keyspace with redis-cli --scan | xargs DEL. Service recovered in under 5 minutes. Wrote postmortem: root cause, why review didn't catch it, action items. RAdded a startup integration test that asserts TTL is set on all cache configs. Added Redis eviction rate alert. The lesson: "trivial" changes to infrastructure configuration deserve the same review rigour as logic changes — the blast radius is often larger.
Key phrases to land postmortem with action items test to prevent recurrence trivial changes deserve full review
I deployed a one-line change to a Redis cache configuration: a TTL duration was accidentally set to zero — no expiry. I considered it a trivial config change and didn't flag it for extra scrutiny. No tests failed, no alerts fired immediately.

Four hours later, pricing-service started degrading. Redis memory was at 99% — 2.4 million cache keys had accumulated with no expiry. The LRU eviction policy was evicting live pricing data to make room, causing cache misses, which caused DB load, which caused latency spikes on bet placement during an active race meeting.

Diagnosis took about 8 minutes: redis-cli INFO memory showed the problem clearly. The fix was straightforward — revert the config, purge the keyspace. Recovery in under 5 minutes.

The learning wasn't just "test your configs." It was that "trivial" is a judgment call I made without evidence. Infrastructure config changes have potentially larger blast radius than logic changes — a wrong TTL affects every cached key, silently, with a 4-hour delay before symptoms appear. I wrote a postmortem and added a startup test that asserts TTL is non-zero on all cache configurations. That test has caught two other misconfigurations since. — ~155 words, ~105 seconds

SA new bookmaker client required integration by a contractually fixed date — 3 weeks. Their feed format was undocumented and inconsistent. Two other engineers were occupied with a live incident at the start of the window. TDeliver a working feed handler in 3 weeks, solo for the first week, with no formal spec. We had a contractually fixed deadline to integrate a new bookmaker's feed. The format was undocumented and their integration team's responses were slow. The first week I was working largely solo because two colleagues were dealing with a separate live incident.

My first move was to capture 48 hours of live feed traffic to a file before writing any parsing code. This gave me real data to test against — not invented examples. I built the parser TDD-style against those samples. In the process I found three inconsistencies: message types that appeared in the live feed but weren't in the rough spec they'd shared. Rather than waiting to discover these at integration time, I wrote them up concisely and emailed their team with specific examples from the captured data. They responded in two days with clear answers — weeks faster than if I'd raised them verbally and waited.

I delivered a working, tested integration on day 18 — three days early. The first 30 days of live operation had zero feed-related incidents. Q8
Tell me about a time you had to deal with significant ambiguity.
SARM was moving to multi-tenancy — same platform serving multiple bookmaker clients. The requirement was "isolate tenants" but no one had defined what isolation meant: data, config, rate limits, or all three. TDesign the tenancy model before three services started building on it — without waiting for requirements to be fully specified. AListed every dimension of isolation (data, cache, Kafka topic, rate limits, config) and asked the product owner to prioritise which were needed for the first client. Got answers in a 30-minute session. Designed the minimum viable model: tenantId in JWT, DB rows scoped by tenantId, Redis keys prefixed per tenant, shared Kafka topics (no partition-per-tenant). Documented the explicit decisions and what was deferred — so the team knew what was intentional scope and what was debt. RThree services built against the model without conflict. Deferred items (per-tenant rate limits) were correctly scoped as future work, not surprises. The process — enumerate dimensions, prioritise, document decisions explicitly — is now how we handle ambiguous architectural requirements.
Key phrases to land enumerate dimensions before deciding document what's deferred — intentional not forgotten minimum viable model
ARM was expanding to serve multiple bookmaker clients on the same platform. The requirement was "tenants must be isolated" — but isolation is a spectrum. It could mean isolated data (different rows), isolated caches, isolated Kafka topics, isolated rate limits, or fully isolated deployments. No one had defined which.

Rather than waiting for clarity or guessing, I enumerated every isolation dimension I could think of — nine in total — and took them to the product owner in a 30-minute prioritisation session. Which ones were hard requirements for the first client? Which were nice-to-have? Which were deferred? In 30 minutes we had a concrete list: tenantId in JWT, all DB queries scoped by tenantId, Redis keys prefixed, shared Kafka topics (no per-tenant partitions). Per-tenant rate limits and config overrides were explicitly deferred.

I documented this as an Architecture Decision Record — what we chose, what we didn't, and why. Three services built against this model in the same sprint without stepping on each other. The deferred items became a backlog ticket, not technical debt discovered by surprise. The process itself — enumerate, prioritise, document explicitly — is now how we handle ambiguous architectural requirements. — ~155 words, ~103 seconds
Q9
Tell me about a time you improved a process or made a team more efficient.
SARM was losing Kafka events occasionally when a service crashed between DB write and Kafka publish. The team was patching it service-by-service with ad hoc retry logic — each patch slightly different, none reliable. TEstablish a consistent, reliable approach across all write services — without mandating a big rewrite. AIntroduced the outbox pattern: DB transaction atomically writes both the domain record and an outbox row; a separate poller publishes to Kafka and deletes the row on success. Built a shared OutboxPublisher library (one class, three methods) that any service could drop in. Ran a 1-hour workshop showing the before/after. Added an outbox row count alert to catch publishing failures. RThree services migrated in two sprints. Zero lost events in the subsequent 3 months. The library abstracted the pattern so junior engineers could use it correctly without understanding the internals. Reduced incident rate from "occasional lost event" to zero for those services.
Key phrases to land outbox pattern shared library not repeated pattern workshop to accelerate adoption
Several services in ARM were losing Kafka events occasionally when a pod crashed between the DB write and the Kafka publish call — the two operations weren't atomic. Each team was patching it differently: some added retry loops, some added manual checks, none of them reliable. It was the same root cause solved five different ways, none correctly.

I proposed the outbox pattern: write the domain record and an outbox event row in the same DB transaction — atomically. A separate polling thread then publishes the outbox rows to Kafka and deletes them on success. The key insight is that the DB commit is the guarantee — if the service crashes before Kafka publish, the outbox row survives and gets processed on restart.

I built a small shared OutboxPublisher — one class, three methods — that any service could drop into their Spring context. Ran a 1-hour walk-through with the team, not to mandate it, but so everyone understood what problem it solved. Three services migrated in two sprints. In the three months after, those services had zero lost event incidents. Making the correct approach easy to adopt mattered more than explaining the pattern. — ~155 words, ~105 seconds
Q10
How do you approach code quality and technical debt?
SNot a STAR question — a philosophy question. Answer reveals how you think about engineering hygiene and prioritisation. TQuality: Correct code that fails silently is worse than loud code that fails clearly. I'd rather have a test that proves the behaviour than a comment explaining it. Constructor injection over field injection — it forces dependencies to be explicit and makes testing trivial. ADebt classification: Not all debt is equal. Blocking debt (idempotency missing on financial write) → fix before next sprint. Slowing debt (copy-paste HikariCP config in every service) → schedule, quantify the sprint cost. Cosmetic debt (method naming) → fix opportunistically. RReview: PR review is outcome-focused: correctness under concurrency, production failure modes, missing observability. Not style. Style is Checkstyle's job. My review comments are always about what breaks in production, not what looks wrong to me.
Key phrases to land debt classified by impact not by smell test proves behaviour, comment explains it PR review: what breaks in production
My approach to code quality starts with what I care about in a PR review — and it's not style. Style is Checkstyle and a formatter's job. What I look for is: will this break in production under concurrent load? What happens if this external call times out? Where's the idempotency guard? Those questions reveal quality issues that matter.

On technical debt: I classify it by impact, not by how unpleasant the code looks. Blocking debt — where the absence of a pattern creates real risk (missing idempotency on a financial write endpoint) — gets fixed before the next sprint regardless of other priorities. Slowing debt — copy-paste config across every service that costs us 2 hours per new service — gets scheduled with a measured cost argument. Cosmetic debt — method names that could be clearer — gets fixed opportunistically when I'm already in that file.

On testing: I write tests to prove behaviour, not to satisfy coverage metrics. A test that proves "duplicate request returns existing result, not a new record" is worth more than five tests that assert the happy path five different ways. I default to unit tests with Mockito because they run in milliseconds and cover the domain logic. Real infrastructure gets verified manually via docker-compose — not because integration tests are bad, but because the marginal value of a Testcontainers test over a manual smoke test is low compared to the maintenance cost. — ~195 words, ~130 seconds — trim if over time
