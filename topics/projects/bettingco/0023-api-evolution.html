API Evolution — Versioning, Compatibility, Schema Change

Gap Topic — Interview depth expected at Senior level · ARM BettingCo examples throughout

Interviewers probe whether senior engineers understand the full cost of API changes: client impact, deployment coordination, Kafka schema compatibility, and how to evolve without big-bang releases. ARM BettingCo has both REST APIs (consumed by cerberus-ui and sportsbook) and Kafka topics (consumed by multiple services) — both require careful evolution strategies.

1. REST API Versioning Strategies

2. What Changes Break Backward Compatibility

// SAFE changes (backward compatible — existing clients unaffected):
// ✓ Add new optional field to response
// ✓ Add new optional request parameter
// ✓ Add new endpoint
// ✓ Change error message text (if clients don't parse it)
// ✓ Add new enum value (if clients use default/unknown handling)

// BREAKING changes (require version bump):
// ✗ Remove a field from response
// ✗ Rename a field
// ✗ Change field type (string → integer)
// ✗ Remove an endpoint
// ✗ Make an optional field required
// ✗ Change the meaning of a field (same name, different semantics)
// ✗ Change status codes (200 → 201 for the same operation)
// ✗ Remove an enum value that clients depend on

// ARM example: event-service adds 'inPlayOdds' field to Event response:
// V1 response (existing clients):
{
  "id": 12345,
  "status": "IN_RUNNING",
  "races": [...]
}
// V2 response (new field — backward compatible, no version bump needed):
{
  "id": 12345,
  "status": "IN_RUNNING",
  "races": [...],
  "inPlayOdds": { "win": "3/1", "place": "1/1" }   // ← additive, not breaking
}
// V2 breaking (requires bump): rename 'status' → 'eventStatus'
// Existing clients reading 'status' would get null — silent failure
Robustness Principle (Postel's Law) — the interview talking point "Be conservative in what you send, liberal in what you accept." Clients should ignore unknown fields (Jackson does this by default with DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES = false). Servers should accept requests missing optional fields. This makes additive changes always backward compatible. ARM's generated SDK clients use Jackson with unknown properties ignored — adding new fields to event-service responses is safe without client updates.

3. Deprecation — How to Remove an API Field Properly

// Phase 1: Add new field alongside old one (parallel period)
public class EventResponse {
    @Deprecated  // will be removed in 2026-Q3
    public String status;         // old name

    public String eventStatus;    // new canonical name — same value for now
}

// Phase 2: Document sunset in OpenAPI:
// @ApiResponse(headers = {
//   @Header(name = "Sunset", description = "2026-09-30"),
//   @Header(name = "Deprecation", description = "2026-06-01")
// })

// Phase 3: Emit Sunset and Deprecation HTTP response headers:
@GetMapping("/api/v1/events/{id}")
public ResponseEntity<EventResponse> getEvent(@PathVariable Long id) {
    return ResponseEntity.ok()
        .header("Sunset", "Sat, 30 Sep 2026 00:00:00 GMT")    // RFC 8594
        .header("Deprecation", "Mon, 01 Jun 2026 00:00:00 GMT")
        .body(buildResponse(id));
}

// Phase 4: After sunset date — remove old field, return 410 Gone from v1 endpoint
// Track which clients still use v1 via access logs BEFORE removing

4. Kafka Schema Evolution — The Hard Problem

Kafka messages are immutable once published. Consumers that were offline when you changed the schema will replay old messages with the new consumer. This is the hardest API evolution problem.

// Strategy A: Tolerant reader (no schema registry — ARM's approach)
// Consumers use Jackson ObjectMapper with FAIL_ON_UNKNOWN_PROPERTIES=false
// and handle missing fields with Optional or defaults.

// SAFE Kafka changes (no consumer code change needed):
// ✓ Add new field with default value
// ✓ Make a required field optional (consumers use default if absent)

// UNSAFE Kafka changes (require coordinated consumer update):
// ✗ Remove a field consumers read
// ✗ Rename a field
// ✗ Change field type

// ARM example: event-service adds 'meetingId' to EventUpdateEvent:
// Old message: {"eventId": 100, "status": "ACTIVE"}
// New message: {"eventId": 100, "status": "ACTIVE", "meetingId": "M42"}
// sportsbook-service (consumer): @JsonIgnoreProperties(ignoreUnknown=true)
// → old consumers silently ignore meetingId — safe

// Strategy B: Avro + Schema Registry (not used in ARM, but the standard approach)
// Schema Registry enforces compatibility rules:
// BACKWARD: new schema can read old messages (new consumer, old messages)
// FORWARD: old schema can read new messages (old consumer, new messages)
// FULL: both — safest, most restrictive

5. Strangler Fig — Migrating Legacy Services

// Pattern: incrementally replace a legacy service by routing traffic
// through a proxy that redirects some paths to the new service.

// ARM scenario: migrating sportsbook-service to a new event-streaming-service
// that handles the Kafka fan-in and WebSocket relay more efficiently.

// Step 1: Deploy new service alongside old one
// Step 2: Proxy routes /api/v2/stream/* to new service, all else to old
nginx:
  location /api/v2/stream {
    proxy_pass http://event-streaming-service:8085;
  }
  location / {
    proxy_pass http://sportsbook-service:8082;  # old service still handles rest
  }

// Step 3: Migrate clients endpoint by endpoint
// Step 4: Shadow mode — new service receives copies of traffic, results compared
// Step 5: Once validated, flip all traffic to new service
// Step 6: Decommission old service

// Advantage: no big-bang cutover; rollback is just updating the proxy.
// Zero downtime: both services run simultaneously during transition.
// Key metric: compare response bodies between old and new in shadow mode.
Interview question: "How would you deprecate an internal API used by 5 microservices?" Senior answer: 1) Add the new API alongside the old, announce sunset date. 2) Add Deprecation + Sunset response headers. 3) Monitor which services still call the old API via access logs / Datadog. 4) Work with each team to migrate, in order of their sprint cadence. 5) After all consumers migrated and verified in prod, remove the old endpoint. 6) Keep the old endpoint returning 410 Gone for 30 days as a safety net for any missed consumers. Never remove silently — always 410, never 404.

6. ARM BettingCo — Real API Evolution Example

// event-service REST API versioning (Spring Boot)
@RestController
@RequestMapping("/api")
public class EventController {

    // V1: original endpoint — still supported
    @GetMapping("/v1/events/{id}")
    public ResponseEntity<EventResponseV1> getEventV1(@PathVariable Long id) {
        return ResponseEntity.ok()
            .header("Deprecation", "2026-06-01")
            .header("Sunset", "2026-12-31")
            .body(mapper.toV1(eventService.getEvent(id)));
    }

    // V2: new endpoint with expanded response (meetingId, inPlayOdds)
    @GetMapping("/v2/events/{id}")
    public ResponseEntity<EventResponseV2> getEventV2(@PathVariable Long id) {
        return ResponseEntity.ok()
            .body(mapper.toV2(eventService.getEvent(id)));
    }
}

// EventResponseV2 is a superset of V1 — all V1 fields present plus new ones.
// cerberus-ui uses V2. sportsbook (legacy) uses V1 until migrated.

Quiz

Q1. event-service renames the JSON field "status" to "eventStatus" in its response. ARM's cerberus-ui (Next.js) and sportsbook (React 16) both consume this API. What happens to each client if the change is deployed without a version bump?

  • Both clients work fine — JavaScript is duck-typed and ignores missing fields
  • Both clients fail with a parse error — JSON fields must match exactly
  • cerberus-ui silently breaks — it reads response.status, which is now undefined (the field is gone). sportsbook also silently breaks the same way. No exception thrown — the event status just displays as undefined/null everywhere. This is the worst kind of breaking change: silent data loss. A version bump to /api/v2/events with a parallel deprecation period on v1 is required.
  • JavaScript automatically maps "eventStatus" to "status" because field names are strings
Renaming a JSON field is a breaking change. JavaScript (and Jackson) look up fields by exact name. response.status returns undefined when the server sends "eventStatus". No exception is thrown — the UI silently renders nothing or "undefined" where the event status should appear. This breaks user-visible functionality without any error log. The correct approach: add "eventStatus" alongside "status" (backward compatible additive change), deprecate "status" with a sunset header, migrate clients to read "eventStatus", then remove "status" after the sunset date.

Q2. ARM adds a new "meetingId" field to all Kafka messages on arm-dev.event-service.json. sportsbook-service is the consumer. It hasn't been updated yet and uses @JsonIgnoreProperties(ignoreUnknown=true). What happens?

  • sportsbook-service silently ignores the new "meetingId" field and continues processing normally. @JsonIgnoreProperties(ignoreUnknown=true) tells Jackson to skip unknown fields without error. Once sportsbook-service is updated to use meetingId, it can start reading it. This is the "tolerant reader" pattern — additive Kafka schema changes are safe when consumers ignore unknown fields.
  • sportsbook-service throws a JsonMappingException and stops consuming from the topic
  • Kafka rejects the message because the schema changed without a registry update
  • sportsbook-service processes the message but loses all existing fields due to deserialization failure
@JsonIgnoreProperties(ignoreUnknown=true) is the key safety mechanism for tolerant reader. Without it, Jackson would throw UnrecognizedPropertyException on any unexpected field. With it, new fields are ignored until the consumer is updated to read them. This is why ARM can add fields to Kafka messages without coordinating consumer deployments — producers deploy first, consumers update at their own pace. The only requirement: new fields must have sensible defaults (null or empty) so old consumers don't break on their absence.

Q3. ARM needs to remove the "legacyOdds" field from its Event Kafka messages — 3 services currently read it. What is the correct migration process?

  • Remove the field immediately and patch all 3 consumers in the same deployment
  • 1) Add the replacement field "odds" with the new format alongside "legacyOdds". 2) Deploy producer. 3) Update each of the 3 consumers to read "odds" instead of "legacyOdds" — deploy each independently. 4) Verify all 3 consumers have migrated in production (grep access logs / metrics). 5) Remove "legacyOdds" from producer. 6) Remove "legacyOdds" reading code from consumers. Note: Kafka retains old messages — after removal, replaying old messages won't have the field, so consumers must handle its absence gracefully.
  • Publish a new Kafka topic with the new schema and migrate consumers to the new topic
  • Use Avro schema registry to enforce the field removal and force consumer updates
Field removal from Kafka is the riskiest schema change because old messages in Kafka still won't have the field — even if you run consumers backwards through history. The correct sequence is: add new field → migrate consumers → verify all consumers use new field → remove old field. The verification step is critical: check that no consumer still reads legacyOdds by searching code and monitoring error rates. Removing a field before all consumers migrate causes silent null/default values in those consumers, potentially corrupting business data (e.g., odds displayed as null during a live race).
