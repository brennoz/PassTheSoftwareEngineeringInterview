ARM BettingCo — Feed Handler Pattern (18 External Integrations)

Category: Projects · Topic: ARM BettingCo · Est. time: 15 min · Lesson 2 of 14

What Are Feed Handlers?

Feed handlers are 18 Spring Boot microservices, one per external bookmaker or exchange. Each handler connects to a bookie API (REST, WebSocket, FTP, or proprietary protocol), receives odds and racecard updates in that bookie's specific format, normalises the data into the ARM canonical event model, then publishes to Kafka. Feed handlers are the ingestion layer of the platform — all data about races and odds enters ARM through them. Without feed handlers, there is no data to price, and no odds to show to customers.

lib-feed-handlers — The Shared Component Library

All 18 handlers share a common library: lib-feed-handlers. This library provides two injectable Spring components — FeedRaceBroadcaster (Kafka publish) and MessageBuilder (message envelope builder). There is no abstract base class; each handler service uses these components by composition (dependency injection).

lib-feed-handlers (shared library) FeedRaceBroadcaster ← @Service — publishes FeedRaceDto to Kafka publishFeedRace(dto) key = "{feedName}:{feedCode}" ← same race always → same partition kafkaTemplate.sendDefault(key, dto) MessageBuilder ← @Component — builds KafkaMessage envelope build(feed, message, messageType) → KafkaMessage { timestamp, uuid, feed, entityType, message } feed-handler-betfair (Spring Boot service) @Autowired FeedRaceBroadcaster broadcaster @Autowired MessageBuilder messageBuilder // connects to Betfair REST API, normalises → FeedRaceDto, calls broadcaster.publishFeedRace() feed-handler-sis (Spring Boot service) @Autowired FeedRaceBroadcaster broadcaster // connects to SIS SFTP feed, normalises → FeedRaceDto, publishes
OOD Pattern: Composition over Inheritance Each feed handler service injects FeedRaceBroadcaster and MessageBuilder rather than extending an abstract superclass. This is the Strategy pattern (via dependency injection): the shared publishing algorithm is a concrete Spring @Service, not a Template Method to override. Adding bookmaker 19: a new Spring Boot service that injects the same two components — zero changes to lib-feed-handlers. Open/Closed Principle achieved through composition, not inheritance.

Kafka: WOODS Consumer → BETTINGCO MSK Producer

Feed handlers consume from the WOODS cluster. External bookmakers (Betfair, etc.) are the producers to WOODS — they publish their own Kafka topics. The actual WOODS topic names (verified from application.yml):

  • exchange.betfair.horse_racing — Betfair horse racing prices (UK/IRE)
  • exchange.betfair.greyhound_racing — Betfair greyhound prices
  • exchange.betfair.uk_ire.horse_racing.avgwgtodds — Betfair WOODS average weighted odds
  • exchange.betfair.uk_ire.horse_racing.market_info — UK/IRE racecard market info
  • exchange.betfair.au.horse_racing.market_info — AU racecard (similar pattern per region)

After consuming and normalising, every handler produces to the BETTINGCO MSK cluster (bootstrap: msk-broker-1,2,3.dev.bettingcosport.com:9092) on topic test-local.arm-dev.prices (configured via KAFKA_TOPIC_PRICES_NAME), publishing a normalised FeedRaceDto.

The flow: external Betfair brokers → WOODS Kafka → feed-handler-betfair (consumer + normaliser) → BETTINGCO MSK (test-local.arm-dev.prices) → downstream ARM services.

Why isolate WOODS from BETTINGCO MSK? 3rd-party Kafka brokers (Betfair, SIS, etc.) can be slow, unavailable, or send malformed messages — failures outside ARM's control. Keeping external feeds on the separate WOODS cluster means their instability cannot cascade into the internal BETTINGCO MSK cluster that all ARM services depend on. Feed handlers act as both a translation layer (format normalisation) and an isolation layer (failure containment).

Why 18 Separate Services?

Each feed handler is its own Spring Boot service with its own Kubernetes pod(s). This gives each handler:

  • Independent scaling — Betfair may need 3 pods at peak, a smaller bookie needs 1
  • Failure isolation — Betfair downtime does not stop SIS feeds or any other handler
  • Independent deployment — update one handler's parsing logic without touching others
  • Independent Kafka connection — each handler connects to WOODS cluster independently

Quiz

Q1. 18 different bookmakers use different data formats. What OOD pattern allows ARM to add a new bookie without modifying existing handler code?

  • Factory Pattern — a factory creates the correct handler type at runtime based on bookie name
  • Composition — lib-feed-handlers provides FeedRaceBroadcaster and MessageBuilder as injectable components; new bookie = new Spring Boot service that injects them, zero changes to the library
  • Observer Pattern — new bookies register as observers of the ARM event stream
  • Singleton — one shared handler class manages all bookmaker connections
lib-feed-handlers provides FeedRaceBroadcaster (Kafka publish) and MessageBuilder (message envelope) as injectable @Service/@Component. Each feed handler service injects them and uses them directly — composition over inheritance. Adding a 19th bookmaker means a new Spring Boot service that injects FeedRaceBroadcaster; lib-feed-handlers is unchanged. Open/Closed Principle is achieved through composition: the shared component is closed for modification, new consumers extend behaviour by creating new services.

Q2. Which Kafka cluster do feed handlers consume from, and which do they publish to?

  • Read from BETTINGCO MSK, write to WOODS (for external bookie consumers)
  • Read from WOODS cluster (192.168.26.101-103:9092, external bookies), write to BETTINGCO MSK (msk-broker-1,2,3.dev.bettingcosport.com:9092, internal ARM)
  • Read and write both on BETTINGCO MSK — WOODS is only for monitoring
  • Use RabbitMQ, not Kafka, for feed ingestion
Feed handlers bridge WOODS (external, 3rd-party, unreliable) to BETTINGCO MSK (internal, AWS-managed, reliable). This isolation means external Kafka instability — latency spikes, broker restarts, malformed messages — cannot affect internal ARM services consuming from BETTINGCO MSK.

Q3. Why are there 18 separate Spring Boot services instead of one monolith with 18 handler classes?

  • Java does not support more than one protocol handler per JVM application
  • Each handler has independent scaling requirements, failure isolation, and deployment lifecycle — Betfair downtime must not stop SIS feeds, and each can be updated and scaled independently
  • Each bookmaker requires a separate public IP address by contract
  • GitLab CI pipelines can only deploy one service per bookmaker integration
Microservice isolation means one handler crashing, lagging, or being redeployed does not affect others. Each scales independently (high-volume Betfair vs low-volume boutique bookies). Each can be deployed independently — no coordination required. In a monolith, a Betfair parsing bug would require redeploying all 18 handlers simultaneously.
