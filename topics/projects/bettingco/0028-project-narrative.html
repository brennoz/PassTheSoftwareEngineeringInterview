Project Narrative — The 3-Minute Pitch

Opayo interview prep · Architecture → Coding → Testing → Deployment · Timed blocks
How to use this page The interview will open with "tell me about the project." This is your moment to set the frame. Read through each timed block, internalise the key points, and practise speaking them aloud — not memorising verbatim. The script examples show the tone and vocabulary, not lines to recite. Aim for 3 minutes total — interviewers start probing questions after ~3 minutes regardless.
~30s Block 1 — What is it / why does it matter

Key points

  • Real-money platform — financial consequences of bugs
  • Real-time + multi-tenant (multiple bookmaker clients)
  • Scale: live races, thousands of concurrent bets

Key phrases

  • real-money, real consequences
  • multi-tenant SaaS
  • live events, sub-100ms
  • 40+ microservices
SPOKEN EXAMPLE
"ARM BettingCo is a real-time sports betting risk platform — it processes live odds from 18 bookmakers, handles bet placement for multiple client operators simultaneously, and pushes live price updates to thousands of concurrent WebSocket connections. The core constraint is that it's real money: a duplicate bet means a double stake deduction, a bad settlement means a wrong payout. That stakes level defines every engineering decision."
~60s Block 2 — Architecture

Key points

  • 6 bounded contexts, each its own service(s)
  • Two Kafka clusters: WOODS (external feeds, on-prem) → BETTINGCO MSK (internal, AWS)
  • Feed handlers normalise 18 formats → canonical events
  • event-service: source of truth for events/races/markets
  • Real-time push: RabbitMQ STOMP + Redis pub/sub → WebSocket clients
  • All on AWS EKS, two clusters (dev + prod), multi-AZ

Key phrases

  • bounded contexts
  • event-driven choreography
  • two Kafka clusters (external bridge)
  • STOMP over RabbitMQ
  • EKS multi-AZ
SPOKEN EXAMPLE
"The architecture is event-driven with six bounded contexts — feed ingestion, event management, pricing, bet lifecycle, real-time push, and auth. External bookmaker feeds come in over a dedicated Kafka cluster we call WOODS, where feed handlers normalise 18 different formats into a single canonical event schema. Those events flow into our internal Kafka cluster on AWS MSK and fan out to downstream services.

The event-service is the source of truth for all live events, races, and markets — it owns the PostgreSQL schema and publishes state changes. Real-time odds updates reach clients via a RabbitMQ STOMP relay that maintains WebSocket connections — about 50,000 concurrent during peak. The whole platform runs on two EKS clusters — dev and prod — each multi-AZ, managed with Helm."
~45s Block 3 — Coding standards and testing

Key points

  • Java 21: records, sealed classes, pattern matching — less boilerplate
  • Spring Boot 3.5: constructor injection everywhere, @Conditional for environment-specific beans
  • TDD: red → green → refactor, 2-4 tests per class (behaviour, not coverage)
  • No Testcontainers, no @SpringBootTest — unit tests + Mockito only
  • Real infra verified manually via docker-compose — deliberate tradeoff

Key phrases

  • TDD red→green→refactor
  • behaviour not coverage
  • deliberate no-integration-test choice
  • Java 21 records reduce boilerplate
SPOKEN EXAMPLE
"We use Java 21 throughout — records for immutable value types, sealed classes for domain state machines like EventStatus, and pattern matching to reduce instanceof boilerplate. Spring Boot 3.5 with strict constructor injection — no field injection — which keeps beans testable without Spring context.

Testing is TDD: failing test first, minimum code to pass, refactor. We write 2-4 tests per class covering the core behaviour and the one meaningful failure mode — not exhaustive edge cases. We deliberately don't use Testcontainers or @SpringBootTest. The tradeoff is: unit tests run in 3 seconds, real infrastructure is verified manually via docker-compose during development. The marginal value of an integration test suite didn't justify the maintenance overhead for our team size."
~45s Block 4 — Deployment and delivery

Key points

  • GitLab CI: 6 stages — build → unit-test → docker push ECR → helm deploy dev → (release/*) helm deploy int → manual gate → prod
  • Each service pinned to exact commit SHA — no "latest" tags
  • Helm chart: rolling update, HPA min=1 max=5 CPU 80%, PodDisruptionBudget
  • Zero-downtime: preStop sleep + terminationGracePeriodSeconds=60
  • Rollback: kubectl rollout undo — 2 minutes, no code change

Key phrases

  • commit SHA pinning
  • manual gate to prod
  • rolling update + PDB
  • 2-minute rollback
  • HPA CPU 80%
SPOKEN EXAMPLE
"GitLab CI has six stages. Commits to trunk auto-deploy to the dev environment. Release branches go to integration automatically, then require a manual approval gate before production. Every deployment pins to the exact commit SHA — no mutable tags.

On Kubernetes: each service deploys with a rolling update strategy, PodDisruptionBudget ensuring minimum availability during node drains, and HPA scaling between 1 and 5 replicas at 80% CPU. We add a 5-second preStop sleep before SIGTERM to let iptables drain — that's what makes the rolling update genuinely zero-downtime. If something goes wrong, kubectl rollout undo reverts to the previous ReplicaSet in under 2 minutes — no hotfix branch required."
Transition phrase after the pitch After ~3 minutes, pause and say: "That's the high level — I'm happy to go deeper on any of those areas." This hands control back to the interviewer and signals you know there's more. It's more confident than trailing off or asking "does that make sense?"

Likely Follow-up Probing Questions

After the pitch, interviewers typically pick one area and go deep. Click each to see the 2-3 sentence answer starter.

Why Kafka and not RabbitMQ for the internal event bus?
Kafka gives us durable, replayable event log — critical for settlement. If the settlement consumer crashes, it replays from the last committed offset with zero data loss. RabbitMQ (which we do use for WebSocket relay) deletes messages after delivery — you can't replay. For anything that touches financial state we need Kafka's durability guarantee. RabbitMQ's strength is low-latency fan-out to WebSocket clients — that's why it handles the STOMP layer.
Why no integration tests — isn't that a risk?
The tradeoff is explicit, not accidental. Unit tests with Mockito cover domain logic in 3 seconds. Real infrastructure behaviour — Kafka consumer group rebalancing, Redis cluster failover, PostgreSQL transaction isolation — can't be reliably tested with Testcontainers anyway: the test environment doesn't match production topology. We verify those manually via docker-compose during development and in arm-int with real load. The risk we accept: bugs that only appear under real infrastructure. The benefit: test suite that's fast, stable, and doesn't break when Testcontainers version bumps.
How do you handle a bad deployment to production?
kubectl rollout undo deployment/<service> -n arm-prod — that's the first move. It reverts to the previous ReplicaSet, which Kubernetes already has cached. Rolling restart, usually complete in under 2 minutes. We also have Datadog monitors on error rate and consumer lag — if either spikes within 5 minutes of a deploy, that's a strong signal to rollback before investigating root cause. Fix forward is only the option if the rollback would make things worse (e.g. schema migration already applied).
What was the hardest technical problem you faced on this project?
Getting exactly-once bet settlement right. Kafka gives at-least-once delivery. A consumer crash mid-processing causes replay. Without idempotency, a replayed settlement message means double-payout. The solution is three layers: (1) SELECT pre-check on the natural bet reference before any INSERT or state change — if the bet is already SETTLED, skip; (2) outbox pattern for event publishing — atomic with the DB write, so no lost events on pod crash between DB commit and Kafka publish; (3) consumer-side status check before re-applying settlement — SettlementEngine reads current bet status and skips if already SETTLED. Any one layer alone is insufficient — you need all three because each covers a different failure mode.
How does multi-tenancy work technically?
JWT carries the tenantId claim. The JwtAuthenticationTokenFilter extracts it and stores it in the SecurityContext. Every JPA repository method takes a tenantId parameter — all queries include WHERE tenant_id = ?. Redis cache keys are prefixed with tenantId. TenantService validates the JWT claim against the tenants DB before processing any request — an invalid tenant gets 401, not a query with null tenantId. The important property is that tenant isolation is enforced at the data layer, not at the service deployment layer — all tenants share the same pods but data never crosses.
What would you do differently if starting again?
Add a schema registry for Kafka messages earlier. We use @JsonIgnoreProperties(ignoreUnknown=true) as a tolerant reader, which works for additive changes, but removing a field requires manually checking every consumer — that's error-prone. Avro + Schema Registry would enforce compatibility at the producer side. I'd also add KEDA for Kafka consumer autoscaling instead of CPU-based HPA — a consumer with high lag but low CPU won't scale up with the current setup, which was the root cause of a settlement lag incident we had.
