Production Debugging — 5 Scenarios

Gap Topic — Interview depth expected at Senior level · ARM BettingCo examples throughout

Interviewers expect senior engineers to describe a systematic debugging approach — not "I looked at logs until I found it." The expected answer has structure: observe → hypothesise → confirm → fix → prevent. This lesson runs five realistic ARM BettingCo incidents with the exact tools and commands used at each step.

The Systematic Approach

1. OBSERVE   — what is the symptom? (alert, user report, metric spike)
2. SCOPE     — which service? which region? which endpoint? since when?
3. HYPOTHESISE — what could cause this? (list 2-3 candidates)
4. CONFIRM   — use data to confirm/eliminate each hypothesis
5. FIX       — smallest change that resolves the issue
6. PREVENT   — what alert/test/monitor catches this before users see it next time?

Scenario 1: High Latency on GET /events — Users Report Slow Page Loads

Alert: Datadog monitor fires — p99 latency on event-service GET /events exceeds 2000ms for 5 minutes.

# Step 1: Datadog APM — find the slowest trace
# → trace shows: HTTP handler 2100ms total
#   → eventService.getActiveEvents() 2050ms
#     → eventRepository.findByStatus() 1980ms  ← SQL query is the bottleneck
#     → (no other significant spans)

# Step 2: Get the slow query — pg_stat_statements in production
kubectl exec -it postgres-pod -n arm-prod -- psql -U arm -d arm_prod -c "
SELECT substring(query,1,100), calls, round(mean_exec_time::numeric,1) AS avg_ms
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 5;"

# Output:
# SELECT * FROM events WHERE status = $1     | 847 | 1980.2ms

# Step 3: EXPLAIN ANALYZE on the exact query
EXPLAIN ANALYZE SELECT * FROM events WHERE status = 'ACTIVE';
# → Seq Scan on events (actual time=0.04..1940.3 rows=12450 loops=1)
#   Filter: (status = 'ACTIVE')
#   Rows Removed by Filter: 488000
# 500k rows scanned to return 12k active events → missing index

# Step 4: Fix — add partial index (no downtime, CREATE INDEX CONCURRENTLY)
CREATE INDEX CONCURRENTLY idx_events_status_active
ON events(status) WHERE status = 'ACTIVE';
# CONCURRENTLY = table remains readable during build (takes longer, no lock)

# Step 5: Verify — p99 drops to <50ms within minutes of index creation

# Prevent: Add to CI a query plan check — fail if new queries use Seq Scan
# Add Datadog monitor on pg_stat_statements mean_exec_time per query

Scenario 2: Kafka Consumer Lag Growing — Settlement Delayed

Alert: Datadog monitor fires — Kafka consumer group lag on the bet settlement consumer group exceeds 10,000 messages.

# Step 1: Check consumer group lag directly
# Consumer group ID is configured via KAFKA_GROUP_ID env var (e.g. arm-dev.bet-manager-service)
kafka-consumer-groups.sh \
    --bootstrap-server msk-broker-1.dev.bettingcosport.com:9092 \
    --describe --group arm-dev.bet-manager-service

# Output:
# TOPIC                   PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG     CONSUMER-ID
# arm-dev.bet-settlement  0          45230           55890           10660   bet-manager-...-0
# arm-dev.bet-settlement  0          45230           55890           10660   -           ← CONSUMER DEAD

# Step 2: Consumer dead — check bet-manager-service pods
kubectl get pods -n arm-prod -l app=bet-manager-service
# NAME                           READY  STATUS             RESTARTS
# bet-manager-service-7f9d-xk2  0/1    CrashLoopBackOff   8

kubectl logs bet-manager-service-7f9d-xk2 -n arm-prod --previous
# → java.lang.OutOfMemoryError: Java heap space
#   at com.bettingcosports.bet.kafka.BetSettlementListener.consumeBets(...)
#   Processing batch of 5000 bets — too large for heap

# Step 3: Root cause — batch size too large for memory limit
# kafka.consumer.settlement.batch-size=5000 (previous deployment changed this)
# Pod memory limit: 512Mi → OOM on large batch

# Fix A: Reduce batch size to 200 (immediate — ConfigMap change, rolling restart)
# Fix B: Increase pod memory limit from 512Mi to 1Gi (requires Helm upgrade)

# Deploy Fix A immediately to clear lag:
kubectl set env deployment/bet-manager-service \
    KAFKA_SETTLEMENT_BATCH_SIZE=200 -n arm-prod
# → triggers rolling restart with new env var

# Step 4: Monitor lag decrease after fix
# → consumer reconnects, starts processing at 200 messages/poll
# → lag decreases at ~500 msg/s

# Prevent: Add Datadog monitor on Kafka consumer lag threshold
# Add memory usage alert before OOM (at 80% heap usage)
# Add batch size validation in application startup

Scenario 3: 500 Errors on POST /bets — Intermittent, 2% of Requests

Alert: Datadog monitor fires — error rate on bet-manager-service POST /bets exceeds 1%.

# Step 1: Datadog APM — find 500 traces
# → trace shows: HTTP 500 from bet-manager-service
# → span error: NullPointerException in TenantService.getTenant()
# → stack trace: TenantService.java:47

# Step 2: Check logs for context
kubectl logs deployment/bet-manager-service -n arm-prod \
    --since=10m | grep "NullPointerException" | head -5
# → 2026-06-25 14:23:11 ERROR [traceId=8f2a3b1c...] TenantService - NPE
# → com.bettingcosports.tenant.TenantService.getTenant(TenantService.java:47)
# → TenantsApi.getTenant returned null for tenantId=9999

# Step 3: Reproduce — what is tenantId=9999?
SELECT * FROM tenants WHERE id = 9999;
# → 0 rows — tenant doesn't exist

# Root cause: a client is sending a JWT with tenantId=9999 (deleted/invalid tenant)
# TenantService calls external TenantsApi which returns null for unknown tenant
# Code at line 47: return tenantsApi.getTenant(tenantId) — no null check

# Fix:
public TenantDto getTenant(final long tenantId) {
    TenantDto tenant = tenantsApi.getTenant(tenantId);
    if (tenant == null) {
        throw new TenantNotFoundException("Unknown tenant: " + tenantId);
        // → maps to 401 Unauthorized via @ExceptionHandler
    }
    return tenant;
}

# Why intermittent: only clients with invalid JWT tenantId trigger this path
# (2% of requests from a specific integration partner with bad token config)

# Prevent: Input validation on JWT tenantId claim before any service call
# Add test: mock TenantsApi returning null, assert 401 not 500

Scenario 4: Redis Connection Exhaustion — Cache Misses Spiking

Alert: Datadog monitor fires — Redis connection count on pricing-service exceeds 90% of pool.

# Step 1: Check Redis metrics
redis-cli -h redis-cluster.arm-prod -p 6379 INFO clients
# connected_clients: 490
# blocked_clients: 12
# maxclients: 500    ← approaching limit

redis-cli INFO stats | grep evicted
# evicted_keys: 142000   ← high eviction rate → keys expiring faster than expected

# Step 2: Which keys are being evicted?
redis-cli INFO memory
# maxmemory_policy: allkeys-lru    ← evicts least recently used when full
# used_memory_human: 7.92G
# maxmemory_human: 8.00G    ← Redis memory is full

# Step 3: What's using memory?
redis-cli --scan --pattern 'streamOutcomePricesCache:*' | wc -l
# → 2,400,000 keys    ← 10x expected (expected ~240,000 active races)

# Root cause: TTL not being set correctly on cache keys
# @Cacheable cacheManager=REDIS_CACHE_MANAGER_BEAN — check bean config
# → RedisCacheConfiguration.defaultCacheConfig().entryTtl(Duration.ZERO)
# ← Duration.ZERO = NO EXPIRY — bug introduced in last deployment

# Fix: restore TTL configuration
@Bean
public RedisCacheManager redisCacheManager(RedisConnectionFactory factory) {
    return RedisCacheManager.builder(factory)
        .cacheDefaults(RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(1)))     // default 1min
        .withCacheConfiguration("streamOutcomePricesCache",
            RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofHours(12)))  // 12h for price history
        .build();
}

# Clear the keys without TTL:
redis-cli --scan --pattern 'streamOutcomePricesCache:*' | \
    xargs redis-cli DEL

# Prevent: Integration test verifying TTL is set on cache keys after startup
# Alert on evicted_keys rate growing faster than expected baseline

Scenario 5: Distributed Trace — Slow End-to-End Request Across Services

Alert: User reports bet placement taking 8 seconds. Datadog APM trace ID available from browser developer tools (X-B3-TraceId header).

# Step 1: Find trace in Datadog APM by trace ID
# → Trace view shows waterfall:
#   sportsbook-service (200ms) → bet-manager-service (7800ms total)
#     → event-service call (200ms) — fast
#     → event-details save (7400ms) ← THIS IS THE BOTTLENECK
#       (saves racing event data to DB before emitting Kafka messages)
#     → DB insert (100ms)

# Note: advisory-service in ARM communicates via Kafka only — async.
# It does NOT appear as a synchronous span in bet-placement traces.
# If you see a long span, it is typically: event-details save, DB write,
# or an external odds-feed call — not advisory-service.

# Step 2: Why is the event-details save slow?
kubectl exec -it postgres-pod -n arm-prod -- psql -U arm -d arm_prod -c "
SELECT pid, now() - pg_stat_activity.query_start AS duration, query
FROM pg_stat_activity
WHERE state = 'active' ORDER BY duration DESC LIMIT 5;"
# → Long-running INSERT on event_details — contention or missing index

# Step 3: Check bet-manager-service CPU/memory
kubectl top pods -n arm-prod -l app=bet-manager-service
# NAME                        CPU    MEMORY
# bet-manager-service-7f9-abc1   980m   1.8Gi   ← near CPU limit (1000m)

kubectl describe hpa bet-manager-service-hpa -n arm-prod
# Current replicas: 3, Desired replicas: 3 (maxReplicas reached)
# Current CPU: 94% (target: 80%)

# HPA at maxReplicas — can't scale further with current config

# Fix A: Increase maxReplicas from 3 to 6 (immediate, no code change)
kubectl patch hpa bet-manager-service-hpa -n arm-prod \
    --type='merge' \
    -p '{"spec":{"maxReplicas":6}}'
# → HPA triggers scale-up → more pods → CPU drops

# Fix B (root cause): profile the slow service
kubectl exec -it bet-manager-service-7f9-abc1 -n arm-prod -- \
    jcmd 1 JFR.start duration=60s filename=/tmp/profile.jfr
kubectl cp arm-prod/bet-manager-service-7f9-abc1:/tmp/profile.jfr ./profile.jfr
# Open in JDK Mission Control → find hot method

# Prevent: Set maxReplicas conservatively higher than expected peak
# Add Datadog alert on HPA at maxReplicas with high CPU (signals need to tune)
# Load test bet-manager-service in arm-int before prod deploy

Quiz

Q1. Datadog fires: error rate on sportsbook-service POST /bets is 3% and growing. You check Datadog APM and see all 500 errors share the same stack trace: HikariPool-1 - Connection is not available, request timed out after 30000ms. What is happening and what are the two most likely root causes?

  • The PostgreSQL server is down — restart the RDS instance immediately
  • HikariCP connection pool is exhausted. Root cause A: too many slow queries holding connections (connection_timeout fires while waiting for a pool connection). Investigate with pg_stat_activity to see long-running queries. Root cause B: pool size too small for current traffic (maximum-pool-size=10 but 15 concurrent requests need DB). Investigate with kubectl top and request rate metrics. Immediate fix: increase pool size or kill long-running queries. Long-term fix: fix slow queries or scale DB read replicas.
  • Kafka consumer lag is causing sportsbook-service to slow down, backpressuring the connection pool
  • Redis is unavailable — sportsbook-service falls back to direct DB calls exhausting the pool
HikariPool connection exhaustion means all pool connections are in use and new requests are waiting up to connection-timeout (30s) for one to become available. This causes cascading slow responses and eventually timeouts. Root cause A is slow queries holding connections for seconds each (a connection busy with a 5s query can't serve other requests). Root cause B is pool undersized for traffic spike. Diagnose with: SELECT * FROM pg_stat_activity WHERE wait_event_type='Client' (queries waiting) and SELECT count(*) FROM pg_stat_activity WHERE state='active'.

Q2. A user reports their bet settlement amount is wrong — they bet £10 at 5/2 odds and expected £35 payout (£25 winnings + £10 stake) but received £25. You need to trace this through ARM BettingCo. What is your first step and how do you correlate the request across services?

  • Check the bets table directly with a SELECT query for the user's account
  • Reproduce the issue in arm-int environment and add debug logs to settlement-service
  • Get the bet ID and trace ID from the user (or look up by their account ID in Datadog). Use the trace ID to find the full distributed trace in Datadog APM — see the exact spans for the settlement-service calculation. Then check the ARM_BET_SETTLEMENT Kafka message payload for that betId in the Kafka broker logs or Datadog log correlation. If the Kafka message had the wrong payout, the bug is in settlement-service. If the Kafka message was correct but bet-manager-service stored the wrong value, the bug is in bet-manager's consumer logic.
  • Restart settlement-service to clear any in-memory state corruption
Correct debugging follows the data: get the bet ID → find the settlement trace → inspect each step's data. The payout bug could be in: (1) settlement-service calculation (odds parsed incorrectly, e.g. "5/2" read as 5.2 decimal = 53 not 35 payout), (2) the Kafka message payload, or (3) bet-manager's consumer applying the payout. Each service leaves a trace span — find where the number first becomes wrong. This is the value of distributed tracing: you follow the exact execution path, not grep logs hoping to find the right entry.
