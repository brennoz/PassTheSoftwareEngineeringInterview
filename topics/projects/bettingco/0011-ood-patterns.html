ARM BettingCo — OOD and Architecture Patterns

Category: Projects · Topic: ARM BettingCo · Est. time: 20 min · Lesson 11 of 14

1. Standard Spring Boot Layered Architecture

ARM services use a standard Spring Boot layered architecture. All layers — controllers, services, repositories — use Spring annotations throughout. Domain entities are JPA @Entity classes, not pure Java. There is no hexagonal (Ports and Adapters) split.

ARM service architecture (actual pattern) HTTP request │ ▼ ┌─────────────────────────────────────────────────────┐ │ @RestController (e.g. EventController) │ │ Receives HTTP, validates, calls service │ └────────────────────────┬────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────┐ │ @Service (e.g. EventService, StatusService) │ │ Business logic, @Transactional boundaries │ │ Calls repositories and Broadcaster │ └──────────┬────────────────────────┬─────────────────┘ │ │ ▼ ▼ ┌──────────────────┐ ┌────────────────────────────┐ │ Spring Data JPA │ │ Broadcaster (lib-events) │ │ MarketRepository│ │ KafkaTemplate<String, │ │ (interface) │ │ MessageDto> → Kafka topic │ └──────────────────┘ └────────────────────────────┘ │ ▼ PostgreSQL Domain entities (Event, Race, Market) live in lib-events — they are JPA @Entity classes with @Column, @ManyToOne, @OneToMany annotations. No port interfaces. No use-case classes. Spring throughout.
Why pragmatic layered instead of hexagonal? Hexagonal architecture (Ports and Adapters) protects domain logic from infrastructure by keeping domain pure Java with no framework dependencies. ARM uses a pragmatic layered approach instead: domain entities are JPA @Entity classes shared across services via the lib-events library. This reduces code duplication (one entity model across all consuming services) at the cost of tighter coupling to JPA. For an internal trading platform where the team controls all services, this trade-off is reasonable.

2. Feed Handler Shared Library (lib-feed-handlers)

lib-feed-handlers is a shared library providing two components used by all 18 feed handler services: FeedRaceBroadcaster (publishes normalised race data to Kafka) and MessageBuilder (builds a timestamped KafkaMessage envelope). There is no abstract Template Method superclass — each feed handler service includes this library as a dependency and calls these components directly.

// Source: lib-feed-handlers/.../broadcaster/FeedRaceBroadcaster.java
@Slf4j
@Service
@RequiredArgsConstructor
public class FeedRaceBroadcaster {

    private final KafkaTemplate<String, FeedRaceDto> kafkaTemplate;

    public void publishFeedRace(final FeedRaceDto dto) {
        // key = "{feedName}:{feedCode}" — all messages for one race to same partition
        final var key = String.format("%s:%s", dto.getFeedName(), dto.getFeedCode());
        kafkaTemplate.sendDefault(key, dto)
                     .whenComplete((result, ex) -> processFeedRace(dto, result, ex));
    }
}

// Source: lib-feed-handlers/.../builder/MessageBuilder.java
@Component
public class MessageBuilder {
    public KafkaMessage build(final String feed, final String message, String messageType) {
        final KafkaMessage msg = new KafkaMessage();
        msg.setTimestamp(DateUtils.format(Instant.now(armClock())));
        msg.setUuid(UUID.randomUUID());
        msg.setFeed(feed);
        msg.setEntityType(messageType);
        msg.setMessage(message);
        return msg;
    }
}
Composition over inheritance Each feed handler service injects FeedRaceBroadcaster and MessageBuilder rather than extending an abstract superclass. This is the Strategy pattern (dependency injection variant): the publishing algorithm is a shared @Service component. Adding bookmaker 19: new Spring Boot service, same two injected components — no base class to modify. Open/Closed Principle via composition, not Template Method inheritance.

3. Saga Choreography

The bet placement lifecycle is a distributed saga implemented via choreography. No central orchestrator — each service reacts to Kafka events and publishes its own events. Compensating transactions handle failures.

Saga steps (choreography): bet-manager-service → ARM_BET_MANAGER_SERVICE_EVENT topic → advisory-service (async, non-blocking) event-service → arm-dev.event-service.json → bet-manager-service (event state changes) bet-manager-service → arm-dev.bet-updates.json → sportsbook-service (bet status push) settlement-service → test-local.arm-dev.bet-settlement → bet-manager-service (applies SETTLED) Note: ARM_BET_MANAGER_SERVICE_EVENT and ARM_BET_SETTLEMENT are Java @KafkaListener container IDs (private static final String) — the actual topic names come from application.yml (e.g. ${KAFKA_TOPIC_BET_SETTLEMENT_NAME:test-local.arm-dev.bet-settlement}). Advisory is ASYNC Kafka only — bet-manager sends no synchronous REST call to advisory-service at bet placement. The bet proceeds to APPROVED/DECLINED immediately; advisory is a parallel risk notification, not a gate in the placement flow. Compensating transaction on failure: If settlement fails → retry via Kafka redelivery (at-least-once) If bet-manager crashes mid-settle → SELECT pre-check on redelivery prevents double-settlement
Choreography vs Orchestration An orchestrator (e.g. AWS Step Functions, a dedicated saga service) knows the full workflow and commands each service. Choreography: each service knows only its own step and reacts to events. ARM chose choreography: no single orchestrator pod = no single point of failure, looser coupling, easy to add new steps. Cost: harder to trace the full workflow without correlation IDs and aggregated logging.

4. Command Query Responsibility Segregation (CQRS) — Implicit

ARM separates write and read models without a formal CQRS framework:

  • Write model: event-service owns authoritative state (PostgreSQL). All mutations go here.
  • Read model: sportsbook-service maintains denormalised views in in-process Caffeine caches (websocketEventMessageCache, websocketDogRacingMessageCache, websocketBetRecommendationMessageCache). REDIS_CACHE_ENABLED=false in production — Redis is not the backing store for these caches; they are local to each pod.
  • Sync mechanism: event-service publishes Kafka events; sportsbook-service consumes them, compares with the cached EventDto via .equals() (change-detection), and broadcasts only if changed — avoiding redundant WebSocket pushes.

Why: write throughput (odds updates) and read throughput (WebSocket queries) have completely different scaling profiles. In-process Caffeine gives zero-latency reads for the hot websocket path; Redis is reserved for cross-pod shared state (tenant data in lib-tenants). Separating read and write models lets each scale independently.

5. Multi-tenancy — lib-tenants

ARM serves multiple betting operators (tenants) from one deployment. lib-tenants provides TenantService and PermissionsService. The tenant identity flows via the JWT token and is resolved at the service layer, not via ThreadLocal.

  • JWT contains tenantId claim; JwtAuthenticationTokenFilter extracts it into SecurityUserDetails.tenantId
  • Services call SecurityService.getPrincipal().getTenantId() to get the current tenant
  • TenantService resolves full tenant data via the event-service REST SDK, cached in Redis with @Cacheable(cacheManager = REDIS_CACHE_MANAGER_BEAN)
  • Tenant data (stream config, competition groups, feed permissions) lives in event-service's database; lib-tenants services query it over HTTP, results cached in Redis
// Source: lib-tenants/.../service/TenantService.java
@Service
@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)  // self-injection for @Cacheable proxy
public class TenantService {

    private final TenantsApi tenantsApi;  // generated REST client for event-service

    @Cacheable(cacheNames = TENANTS_SDK_CACHE, key = "#tenantId",
               cacheManager = REDIS_CACHE_MANAGER_BEAN)
    public TenantDto getTenant(final long tenantId) {
        return tenantsApi.getTenant(tenantId);  // HTTP call to event-service
    }

    @Cacheable(value = ALL_TENANTS_CACHE, cacheManager = REDIS_CACHE_MANAGER_BEAN)
    public List<TenantDto> getAllTenants() {
        return tenantsApi.getTenants(null, true, true, true);
    }
}
@Scope(proxyMode = TARGET_CLASS) — the self-injection trick @Cacheable is implemented via AOP proxy: a method calling another method on this bypasses the proxy and skips the cache. The @Scope(proxyMode = TARGET_CLASS) annotation combined with injecting TenantService self forces calls through the Spring proxy, ensuring the Redis cache is always consulted. This is a standard Spring pattern for self-calling @Cacheable methods.

6. Publisher-Subscriber via Kafka

ARM uses Kafka as a pub/sub backbone. pricing-service publishes odds without knowing that sportsbook-service exists. sportsbook-service subscribes without knowing pricing-service exists. New consumers (e.g. a new monitoring service) can subscribe to arm-dev.event-service.json without any change to event-service. Producers and consumers are fully decoupled through the event log.

Quiz

Q1. lib-tenants' TenantService uses @Scope(proxyMode = TARGET_CLASS) and injects TenantService self. Why is this necessary for @Cacheable to work?

  • @Scope(TARGET_CLASS) makes the bean a singleton, which is required for Redis caching
  • Spring @Cacheable works via AOP proxy — a method calling another method on this bypasses the proxy and skips the cache. Injecting self forces calls through the proxy so Redis is consulted
  • Without proxyMode = TARGET_CLASS, the service is not visible to other Spring beans
  • TARGET_CLASS tells Spring to use CGLIB rather than JDK proxy — required because TenantService implements no interface
Spring AOP proxies intercept method calls on the Spring-managed bean reference, not on internal this references. When getTenant() calls another method internally via this.X(), the proxy is bypassed and @Cacheable is never triggered — the Redis cache is skipped every time. The fix: inject the Spring proxy reference as self and route internal calls through it. This is one of the most common Spring @Cacheable gotchas.

Q2. The bet Saga uses choreography. advisory-service never receives a message from test-local.advisories.messages due to a network partition. What happens to the bet in progress?

  • The bet is automatically confirmed without the advisory check after a timeout
  • The bet stays PENDING; Kafka redelivers when connectivity recovers (at-least-once); if advisory-service remains unavailable, a compensating transaction voids the bet and refunds the customer's stake
  • The customer is charged and the bet is accepted without advisory processing
  • settlement-service handles the missing advisory event during settlement
Saga choreography requires compensating transactions for failure paths. A bet in PENDING state with no advisory confirmation after a defined timeout triggers the compensating transaction: bet status → VOID, stake refunded. Kafka at-least-once redelivery means the advisory event eventually arrives if the service recovers — the idempotency check prevents double-processing. Saga correctness relies on both mechanisms.

Q3. ARM resolves tenant context via SecurityContextHolder (Spring Security), not a raw ThreadLocal. A developer adds @Async to a service method inside bet-manager-service. What data integrity risk appears?

  • SecurityContextHolder is stored per thread and works correctly in all Java execution contexts including @Async
  • @Async runs on a Spring task executor thread that does not inherit the caller's SecurityContext; calls to SecurityService.getPrincipal() return null, tenant_id is missing from queries, and JPA could return or write data without tenant scoping — a data bleed risk between operators
  • @Async is incompatible with Spring Security and throws AuthenticationException at startup
  • SecurityContextHolder automatically propagates to child threads managed by Spring
Spring's SecurityContextHolder uses a strategy (default: MODE_THREADLOCAL) that stores the SecurityContext per-thread. The HTTP request thread has the authenticated principal (including tenantId). @Async creates or borrows a thread from a pool — that thread's SecurityContext is empty. SecurityService.getPrincipal() returns null, breaking any code that calls getPrincipleTenantId(). The fix: configure SecurityContextHolder to use MODE_INHERITABLETHREADLOCAL, or explicitly propagate the SecurityContext into the @Async task via DelegatingSecurityContextExecutor.
