Agile Ownership — Senior Engineer Responsibilities

Gap Topic — Interview depth expected at Senior level · ARM BettingCo examples throughout

Interviewers probe agile ownership to understand whether you see your role as "code writer" or "outcome owner." Senior engineers at Opayo or any payment/fintech platform are expected to drive delivery end-to-end: from shaping tickets, through code review, incident response, and production monitoring, to measuring their team's delivery health. This lesson uses ARM BettingCo's GitLab CI, Datadog, and delivery patterns as examples.

1. Senior vs Junior — The Ownership Spectrum

Junior engineer's scope

  • Takes a ticket, implements it, opens PR
  • Fixes what reviewers comment on
  • Asks "is this done?" when code merges
  • Escalates incidents to someone else
  • Follows the Definition of Done (DoD) checklist
  • Waits for performance issues to be reported

Senior engineer's scope

  • Shapes tickets before they're picked up
  • Asks "is this the right thing to build?"
  • Checks production metrics after deploy
  • Owns incidents from detection to postmortem
  • Defines the Definition of Done for the team
  • Proactively monitors and alerts on regressions
The interview differentiator A junior says "I implemented the feature and it passed all tests." A senior says "I implemented the feature, deployed it to arm-int, verified with a sample of real traffic, set up a Datadog monitor for the new endpoint, and confirmed p99 latency was within SLA before signing off." The difference is outcome ownership, not just task completion.

2. Definition of Done — Opayo/Payment Platform Version

A strong DoD at a payment platform goes beyond "tests pass and PR merged." At Opayo, processing payments, every item on this list is a compliance and reliability concern:

Definition of Done — ARM BettingCo payment/fintech context:
☐ Unit tests written and passing (relevant behaviour, not every edge case)
☐ No new Sonar/Checkstyle violations introduced
☐ Reviewed by ≥1 other engineer (architecture review for cross-service changes)
☐ Deployed to arm-int (integration environment) and smoke-tested manually
☐ Idempotency verified for any write operation (double-submit safe)
☐ Datadog monitor created or updated for the changed endpoint/consumer
☐ Runbook updated if incident response changes (alert → action mapping)
☐ Database migration: tested rollback scenario, added CONCURRENTLY index if needed
☐ API change: backward compatible OR version bump + deprecation header + date
☐ Kafka schema change: producers deployed before consumers, old fields kept during transition
☐ Security: no secrets in logs, no user PII in exception messages
☐ Load tested if adding a new hot path (post load-test results in PR description)
Payment platform specific — idempotency is not optional At Opayo, every POST endpoint that creates or modifies money state must be idempotent. The DoD must include: "idempotency_key enforced at DB level (UNIQUE constraint), duplicate detected and handled gracefully (not 500)." This is a design requirement, not an afterthought. A senior engineer at a payment platform raises this in ticket refinement, not in a post-incident review.

3. Tech Debt — When to Tackle It

// Tech debt classification (ARM BettingCo examples):

// Type A: Blocking — stop work until fixed
// → BetSettlementListener missing idempotency_key check → double settlement risk
// → action: P0, fix before next sprint, no new work on bet-manager until done

// Type B: Slowing — costing time each sprint, fix soon
// → No shared HTTP client → every new service copy-pastes HikariCP config
// → action: schedule in next sprint, create lib-http-client module

// Type C: Cosmetic — code quality without functional impact, fix opportunistically
// → EventRepository method names not following Spring Data naming conventions
// → action: fix while in the file for another reason

// Senior engineer's role in tech debt:
// 1. Name and track it: create a Jira/GitLab issue with measured impact
//    ("HikariCP copy-paste costs ~2h per new service = ~10h/quarter")
// 2. Prioritise by impact: cost × frequency × risk, not by smell
// 3. Propose the fix scope: don't refactor everything, fix the bottleneck
// 4. Get sign-off: tech debt isn't free — get PM agreement on sprint allocation

4. DORA Metrics — Measuring Delivery Health

DORA (DevOps Research and Assessment) metrics are the standard way to measure engineering team performance. A senior engineer should know all four, what ARM BettingCo's GitLab CI pipeline contributes to each, and how to improve them.

MetricDefinitionARM pipeline contributionElite threshold
Deployment Frequency How often code deploys to production GitLab CI auto-deploys trunk to arm-dev; release/* triggers arm-int; manual gate to arm-prod. Each service deploys independently. Multiple times per day
Lead Time for Changes Commit to production time build+test+deploy-dev: ~8min. arm-int: manual trigger, ~5min. arm-prod: manual gate. Fastest path: ~30min commit-to-prod. Under 1 hour
Change Failure Rate % of deployments causing incidents arm-int smoke tests catch most issues. Helm --wait ensures rollout completes before CI passes. kubectl rollout undo for instant rollback. Under 5%
Mean Time to Restore (MTTR) Time to recover from incident kubectl rollout undo takes ~2min. Datadog alerts fire within 1min of error rate spike. Good runbooks → clear action. Under 1 hour

5. PR Review — What a Senior Engineer Looks For

// Code review at senior level is not grammar-checking. It's:

// ✓ Correctness under concurrent load
//   "This UPDATE doesn't handle the case where two threads run simultaneously.
//    The balance subtraction needs SELECT FOR UPDATE or optimistic @Version."

// ✓ Production failure modes
//   "What happens if TenantsApi returns null? I see you call .getTenant(id)
//    without null-checking. This will throw NPE in production on unknown tenant."

// ✓ Idempotency for write paths
//   "POST /bets creates a new bet on every call. What happens on client retry?
//    Add idempotency_key parameter and UNIQUE constraint."

// ✓ Schema evolution risk
//   "You're removing the 'legacyOdds' field from EventUpdateEvent. We have 3
//    consumers that read this field. Are they all deployed before this change?"

// ✓ Missing observability
//   "New endpoint added — no Datadog monitor. What alert fires if this starts
//    returning 500s at 3am? Add a monitor before this merges."

// ✓ Performance hot paths
//   "This loops over all bets to find pending ones. With 500k bets per event,
//    this is O(n). You need an index on (event_id, status) with WHERE status='PENDING'."

// ✗ NOT: "This variable should be called 'betAmount' not 'amount'"
// ✗ NOT: "Add a comment explaining this method"
// ✗ NOT: Stylistic preferences already handled by checkstyle/formatter

6. Incident Ownership — From Alert to Postmortem

// ARM BettingCo incident response playbook (senior engineer owns all of this):

// Phase 1: Detection (minutes 0-5)
// → Datadog alert fires: error rate > 1% on bet-manager-service
// → Check: what broke? which service? since when? which env?
// → Datadog APM: find service, find failing traces, find error type
// → Communicate: post in #incidents Slack channel:
//   "bet-manager-service: 3% 500 error rate since 14:23 UTC. Investigating."

// Phase 2: Triage (minutes 5-15)
// → Is it a deployment? Check GitLab CI: last deploy was 14:18 → likely culprit
// → Rollback decision: if clear causal link → kubectl rollout undo immediately
//   "Rolling back bet-manager-service to v2.3.1 (deployed 14:18)"
// → If unclear: gather more data before rollback (might not help)

// Phase 3: Resolution (minutes 15-60)
// → Fix deployed or rollback confirmed
// → Verify: error rate drops to baseline, lag clears, no customer impact
// → Communicate: "Resolved 14:52 UTC. Root cause: missing null check on TenantsApi.
//    Customers affected: ~400 bets failed. All retried successfully by client retry logic."

// Phase 4: Postmortem (within 48h)
// Template:
// - Timeline (when detected, when fixed, duration)
// - Root cause (technical cause + contributing factors)
// - Impact (how many users, what data, any financial impact)
// - Why we didn't catch it (what test/monitor was missing)
// - Action items (who fixes what by when — no vague "improve monitoring")

// A good postmortem action item:
// "Add unit test: TenantsApi returns null → expect 401, not 500. Owner: @roberto, Done by: 2026-06-30"
// A bad postmortem action item:
// "Improve error handling in TenantService" (no owner, no date, no definition of done)
The blameless postmortem principle Incidents are system failures, not individual failures. A postmortem that names a person as the cause ("João made a mistake") doesn't prevent the next incident — the system allowed that mistake to reach production. A good postmortem asks "what system property allowed this to happen?" (missing test, missing monitor, missing review checklist item) and fixes the system. This is the senior engineer's job to model and enforce.

7. Ticket Refinement — Senior Engineer's Pre-Sprint Role

// Questions a senior engineer asks in refinement (before a ticket is accepted into sprint):

// On a new feature ticket:
// 1. "What is the expected throughput? 1 req/s or 1000 req/s? This affects indexing."
// 2. "Is this a one-way door or two-way door? Can we roll this back if users hate it?"
// 3. "Which services does this touch? Do we need a Kafka schema change? DB migration?"
// 4. "What's the rollout strategy? Feature flag, canary, or full deploy?"
// 5. "What does the incident runbook look like for this feature?"

// On a bug ticket:
// 1. "Can we reproduce this in arm-int before fixing it? Fixes without reproduction risk re-opening."
// 2. "Is this a data corruption issue? Do we need a one-off data fix script?"
// 3. "How do we verify the fix is working in production? What metric proves it's gone?"

// Signs a ticket isn't ready for sprint:
// - "Add caching" without specifying what data, TTL, invalidation strategy
// - "Fix performance" without a measured baseline and target
// - "Integrate with Opayo's payment API" without API docs or sandbox credentials

Quiz

Q1. You merged a feature to production at 10am. At 2pm, Datadog fires: settlement-service error rate 4%. No other deploys happened between 10am and 2pm. How do you determine whether your deploy caused this, and what do you do first?

  • Immediately roll back your deploy — the 4-hour gap is suspicious but it's the only change
  • Check Datadog APM for the 2pm trace errors. Look at which endpoint/flow is failing. Check GitLab CI — was there another deploy in another service between 10am and 2pm? Check if the error pattern matches code paths your feature touched. If error traces reference your new code paths, rollback is likely correct. If errors are in unrelated services, gather more data before rolling back. Communicate in #incidents either way.
  • Wait for more data — 4% error rate might be transient and could resolve itself
  • Ask the on-call engineer to investigate — you're off shift at 2pm
A 4-hour gap doesn't exclude your deploy — some bugs only surface under specific conditions (time of day, specific race meeting starting, specific tenant). The correct sequence: (1) check traces to understand what's failing, (2) check if your code is in the failure path, (3) check if other deploys happened (other services, infra changes), (4) decide: if your code is clearly in the error path → rollback immediately, (5) communicate in #incidents. "Wait and see" on a 4% error rate at a payment platform is never correct — at 4%, ~1 in 25 transactions is failing.

Q2. In sprint refinement, a PM proposes: "Add a fee calculation endpoint — POST /fees/calculate, takes bet amount and odds, returns fee." No further detail. What questions must be answered before this goes into a sprint?

  • Questions needed: (1) Fee rules — where are they stored? DB? Config? Per-tenant? (2) Expected throughput — called on every bet placement? If yes, what's peak bet/s? (3) Caching — can fee rules be cached, or are they dynamic per-bet? (4) Idempotency — POST that reads (no write) is fine, but does it create any record? (5) Rounding — fees involve money. BigDecimal not double. Which rounding mode (HALF_UP for customer-facing)? (6) Audit — does a fee calculation need to be logged for PCI-DSS? (7) Integration point — does this call an external Opayo API or is it internal logic? Without these, the estimate is fiction.
  • Ask the PM which sprint this is for — if it's Sprint 3 we have time to figure it out later
  • Accept the ticket and start implementation — the questions will answer themselves as you code
  • Ask only about the API format — the business logic is the PM's responsibility to define
Fee calculation at a payment platform is a compliance-critical path. BigDecimal vs double alone is a source of real financial bugs — Java double arithmetic loses precision in the 14th decimal place, which over millions of transactions becomes material. Rounding mode matters: HALF_UP (standard for customer-facing finance) vs HALF_EVEN (banker's rounding, statistically unbiased). These aren't architecture questions — they're requirements that must be locked before any code is written. A senior engineer's job in refinement is to surface all these so the ticket has a real acceptance criterion, not just "POST /fees/calculate works."

Q3. Your team's Lead Time for Changes is 3 days (DORA elite is under 1 hour). What are the three most likely bottlenecks and what does a senior engineer do about each?

  • The team needs more developers — 3-day lead time means insufficient staffing, hire two more engineers
  • The CI pipeline is too slow — optimize test execution time with parallel test runners
  • Three likely bottlenecks: (A) Long-lived feature branches — PRs open for 2+ days. Fix: mob PR reviews, smaller tickets (1-day chunks), pair programming. (B) Manual approval gates — waiting for QA or management sign-off. Fix: automate smoke tests in arm-int, remove manual gate if test suite is trustworthy. (C) Large batch sizes — big PRs take 3 days to review. Fix: break features into vertical slices deployable independently (feature flags for in-progress work). Senior engineer's action: measure each step (commit → PR → review → merge → deploy), find the longest wait, eliminate it first. Lead time is about flow, not speed.
  • The team should adopt Kanban instead of Scrum — sprint boundaries are causing the delay
3-day lead time almost always points to batch size and handoff delays, not pipeline speed. The root cause is usually: (1) PRs sit in review for 1-2 days because no one has time or context, (2) deployment requires manual steps or approvals, (3) tickets are too large (week-long branches). A senior engineer diagnoses with data: plot the time at each stage (writing code, waiting for review, waiting for deploy, waiting for approval). The longest box is the bottleneck. Kanban vs Scrum rarely changes lead time — reducing batch size (smaller tickets, frequent merges, feature flags) is the highest-leverage change for lead time.
