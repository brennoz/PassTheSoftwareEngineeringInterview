Spring Boot Internals

Gap Topic — Interview depth expected at Senior level · ARM BettingCo examples throughout

Senior engineers are expected to explain Spring Boot beyond "it auto-configures things". Interviewers probe the mechanism: how does autoconfiguration decide what to create, what happens between your main() call and first request, how does the Security filter chain work, and what does Actuator actually expose. This lesson covers each with ARM BettingCo code as the anchor.

1. Autoconfiguration — How It Actually Works

When Spring Boot starts it reads META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (Spring Boot 2.7+) — a flat list of hundreds of configuration classes. Each class carries @Conditional annotations that decide whether it fires.

main() │ └─ SpringApplication.run() │ ├─ load spring.factories / AutoConfiguration.imports │ → list of ~150 AutoConfiguration classes │ ├─ evaluate @Conditional on each class │ @ConditionalOnClass(DataSource.class) → only if DataSource on classpath │ @ConditionalOnMissingBean(DataSource.class) → only if YOU haven't defined one │ @ConditionalOnProperty("spring.datasource.url") → only if property set │ ├─ instantiate passing configurations │ → creates beans: DataSourceAutoConfiguration │ KafkaAutoConfiguration │ SecurityAutoConfiguration │ ActuatorAutoConfiguration │ ... │ └─ application context ready → first request accepted
Why this matters in interview "Spring Boot auto-configures your application" is a junior answer. Senior answer: "Spring Boot reads AutoConfiguration.imports, evaluates @Conditional annotations on each class, and only creates beans that aren't already user-defined. @ConditionalOnMissingBean is what lets you override defaults — define your own DataSource bean and Spring Boot's auto-configured one is skipped entirely."

2. Bean Lifecycle — The Full Sequence

1. Instantiate → constructor called 2. Populate → @Autowired / constructor injection filled 3. BeanNameAware.setBeanName() (if implemented) 4. BeanFactoryAware.setBeanFactory() (if implemented) 5. BeanPostProcessor.postProcessBeforeInitialization() ← @Cacheable proxy wired HERE 6. @PostConstruct method ← your init logic 7. InitializingBean.afterPropertiesSet() 8. Custom init-method (if declared) 9. Bean is READY — in use ...application running... 10. @PreDestroy method ← cleanup: close connections, drain queues 11. DisposableBean.destroy() 12. Custom destroy-method
Step 5 is the one interviewers trip candidates on BeanPostProcessor runs BEFORE @PostConstruct. This is where Spring AOP proxies are created. If TenantService has @Cacheable, the proxy wraps the real bean at step 5. Calling this.getTenant() directly bypasses the proxy — which is why ARM's TenantService self-injects (TenantService self) to route calls through the proxy and hit the cache.

ARM BettingCo — Self-Injection for @Cacheable Proxy

// TenantService.java — self-injection is the correct solution when @Cacheable
// must apply to an internal call (calling 'this.method()' bypasses the AOP proxy)
@Service
@Scope(proxyMode = ScopedProxyMode.TARGET_CLASS)
public class TenantService {
    private final TenantsApi tenantsApi;
    private final TenantService self;  // injected proxy, not 'this'

    public TenantService(TenantsApi tenantsApi, TenantService self) {
        this.tenantsApi = tenantsApi;
        this.self = self;
    }

    @Cacheable(cacheNames = TENANTS_SDK_CACHE, key = "#tenantId",
               cacheManager = REDIS_CACHE_MANAGER_BEAN)
    public TenantDto getTenant(final long tenantId) {
        return tenantsApi.getTenant(tenantId);  // cache miss → real HTTP call
    }

    public void doSomethingThatNeedsTenant(long tenantId) {
        TenantDto t = self.getTenant(tenantId); // ← goes through proxy → cached
        // NOT: this.getTenant(tenantId) ← bypasses proxy, no cache
    }
}

3. Spring Security Filter Chain

Spring Security inserts a DelegatingFilterProxy into the Servlet filter chain. It delegates to a Spring-managed FilterChainProxy, which routes requests to the matching SecurityFilterChain. Each chain contains ordered filters.

HTTP Request │ ▼ [Servlet Container filter chain] │ ├─ DelegatingFilterProxy (Spring Security entry point) │ │ │ └─ FilterChainProxy │ │ │ └─ SecurityFilterChain (matches /api/**) │ │ │ ├─ SecurityContextPersistenceFilter │ ├─ UsernamePasswordAuthenticationFilter (form login — if configured) │ ├─ JwtAuthenticationTokenFilter ← ARM custom (extends OncePerRequestFilter) │ │ reads Authorization: Bearer header │ │ validates JWT │ │ sets SecurityContextHolder │ ├─ ExceptionTranslationFilter │ └─ FilterSecurityInterceptor (authorization check) │ ▼ DispatcherServlet → @RestController

ARM BettingCo — Real JWT Filter

// JwtAuthenticationTokenFilter.java
// OncePerRequestFilter guarantees exactly one execution per request
// (Servlet spec allows multiple dispatches — FORWARD, ERROR, etc.)
public class JwtAuthenticationTokenFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        final String header = req.getHeader("Authorization");

        if (header != null && header.startsWith("Bearer ")) {
            final String token = header.substring(7);
            // validate → extract claims → build SecurityUserDetails
            final SecurityUserDetails user = tokenProvider.validateAndBuild(token);
            final var auth = new UsernamePasswordAuthenticationToken(
                user, null, user.getAuthorities());
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        chain.doFilter(req, res);  // always continue chain
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest req) {
        return req.getServletPath().startsWith("/login");  // bypass for login endpoint
    }
}

4. @Transactional — What Interviewers Probe

PropagationBehaviourARM use case
REQUIRED (default)Join existing tx; create new if noneMost service methods — ensures DB ops in same tx
REQUIRES_NEWSuspend current tx; create new independent txAudit logging — must commit even if outer tx rolls back
MANDATORYMust run in existing tx; throw if noneInternal helpers that must not be called outside a tx
NOT_SUPPORTEDSuspend tx; run non-transactionallyRead-only Redis lookups — don't need tx overhead
NEVERThrow if tx existsCache-only reads that must not be in a tx
The most common @Transactional bug in interviews Calling a @Transactional method from within the same class bypasses the proxy — the transaction never opens. Example: serviceA.methodA() calls this.methodB() where methodB is @Transactional. The this call goes to the real object, not the proxy. Fix: inject the service into itself (same self-injection pattern as @Cacheable above), or restructure.

Quiz

Q1. TenantService uses self-injection to route calls through the @Cacheable proxy. What happens if you remove the self field and call this.getTenant(tenantId) instead?

  • The cache still works because @Cacheable intercepts at the method level regardless of caller
  • The cache is bypassed entirely — this refers to the real object, not the Spring AOP proxy. Every call hits the external API, with no Redis lookup. The @Cacheable annotation has no effect on direct internal calls.
  • Spring throws an exception at startup because self-injection is required for @Cacheable
  • The cache works only for the first call, then expires immediately
Spring AOP proxies work by wrapping the bean. When code outside the class calls getTenant(), the call goes through the proxy and @Cacheable fires. When code inside the class calls this.getTenant(), it goes directly to the real object — the proxy is bypassed. Self-injection works because Spring injects the proxy (not this), so calls through self go through the proxy and hit @Cacheable.

Q2. In production, bet-manager-service is throwing NullPointerExceptions sporadically under load. You need to enable DEBUG logging for com.bettingcosports.bet without restarting the pod. How?

  • Edit application.yml and trigger a config reload via @RefreshScope
  • POST to /actuator/loggers/com.bettingcosports.bet with body {"configuredLevel":"DEBUG"}. No restart needed. Resets when pod restarts.
  • Increase log level in the Helm chart values.yml and run helm upgrade
  • SSH into the pod and edit the logback.xml file directly
Spring Actuator's /loggers endpoint accepts POST requests to change log levels on a running JVM. This is a critical production debugging tool — you can enable verbose logging for a specific package without restarting the service (which would lose the NPE context). The change is in-memory only and resets on pod restart.

Q3. @ConditionalOnMissingBean is on Spring Boot's DataSourceAutoConfiguration. What does this mean for ARM BettingCo services that define their own DataSource bean?

  • Spring Boot throws a conflict exception — you cannot have two DataSource beans
  • Both beans are created; Spring uses the one with @Primary annotation
  • Spring Boot's auto-configured DataSource is skipped entirely. @ConditionalOnMissingBean means: only create this bean if the application context does not already contain a bean of that type. Your custom DataSource takes precedence.
  • The auto-configured bean is created first; your custom bean overrides it at runtime
@ConditionalOnMissingBean is the mechanism that makes Spring Boot's autoconfiguration "overridable by convention." Define your own bean of the same type and the autoconfiguration class evaluates the condition as false — its bean factory method is never called. This is how you customise HikariCP settings, add SSL to a DataSource, or configure a read-replica routing DataSource without modifying framework code.

Q4. BetSettlementListener uses @ConditionalOnProperty(name = "kafka.consumer.settlement.enabled", havingValue = "true"). In the arm-int namespace, this property is false. What is the effect at runtime?

  • The BetSettlementListener bean is never registered in the application context. No Kafka consumer is started for the settlement topic in arm-int. Settlement messages queue up unconsumed in Kafka — consumer group lag grows, but no processing error occurs.
  • Spring throws a BeanCreationException at startup because the Kafka topic still exists
  • The listener registers but immediately throws an exception on first message
  • Settlement messages are silently dropped by the Kafka broker
@ConditionalOnProperty is evaluated at application context startup. If the condition is false, the bean is never created — no listener is registered, no consumer group joins the topic. Messages accumulate in the Kafka partition and consumer group lag grows. When the property is set to true (e.g., in prod), the consumer starts and processes messages from its last committed offset. This lets ARM run integration tests without triggering settlement side-effects.
