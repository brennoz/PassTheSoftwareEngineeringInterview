event-service — Deep Dive (Port 8081)

Category: Projects · Topic: ARM BettingCo · Est. time: 25 min · Lesson 3 of 14 · Deep Dive

Role

event-service is the single source of truth for all racing events in the ARM platform. It owns all data about race meetings (horse and dog racing), individual races within a meeting, runners (horses/dogs), betting markets, and outcomes (odds). All consumers — sportsbook-service, pricing-service, event-monitoring — read from this service via its Kafka output topics or via REST. No other service stores the authoritative event state.

PostgreSQL Schema

The database is called events. Each developer works in a named schema (e.g. roberto, vladimir, suranga) to avoid conflicts. Migrations are managed by Liquibase, applied automatically on service startup from changelogs in src/main/db/changelog/.

Why BigDecimal, not double, for prices? Floating-point arithmetic (double/float) cannot represent 0.1 exactly in binary. A price of 3.50 might be stored as 3.4999999999999996. Multiplied across millions of payout calculations, the rounding error adds up to real money. Regulatory audits in gambling catch this. BigDecimal uses exact decimal arithmetic — 3.50 is exactly 3.50. Never use double for money.

Code: Real EventStatus enum (generated from OpenAPI spec)

Event and market statuses are Java enums generated from the OpenAPI specification at build time. They live in common-enums-api. The six status values reflect the lifecycle of a race meeting in the real platform:

// Source: workspace/build/common-enums-api/generated-resources/src/main/java/
//         com/bettingcosports/common/enums/EventStatus.java
public enum EventStatus {
    ACTIVE,      // meeting is live and accepting odds updates
    DELETED,     // removed from the platform
    DORMANT,     // created but not yet taking feeds
    FINISHED,    // race is over, settlement pending
    IN_RUNNING,  // race is in progress (in-play)
    SUSPENDED    // temporarily halted (e.g. stewards inquiry)
}

// MarketStatus adds one extra value for infrastructure failures:
public enum MarketStatus {
    ACTIVE, DELETED, DORMANT, FINISHED, IN_RUNNING, SUSPENDED,
    MARKET_SERVICE_FAILED  // downstream pricing service error
}

Code: StatusService — real status transition logic

StatusService in com.bettingcosports.eventservice.app.service.status is the service that drives status changes. It uses @Transactional, reads the event from EventService, computes a StatusOptions object, and updates the event and its markets before broadcasting via Kafka:

// Source: event-service/.../service/status/StatusService.java
@Slf4j
@Service
@RequiredArgsConstructor
public class StatusService {

    private final Broadcaster broadcaster;           // Kafka publish to arm-dev.event-service.json
    private final EventService eventService;         // reads authoritative event state
    private final MarketRepository marketRepository; // Spring Data JPA
    private final StatusOptionsService statusOptionsService; // computes next allowed status

    @Transactional
    public void updateEvent(final long eventId) {
        final Optional<Event> optional = eventService.findEventById(eventId)
                                                     .filter(Predicate.not(Event::isCompleted));
        if (optional.isPresent()) {
            final Event event = optional.get();
            final var options = statusOptionsService.build(event);
            updateEvent(event, options);  // applies status changes, saves, broadcasts
        }
    }
}

Code: Real Kafka Publisher — Broadcaster

Broadcaster in lib-events is the shared Kafka publisher for event-service. After every status change, it publishes the full event state as a MessageDto to arm-dev.event-service.json. The key is the event ID — all updates for one event go to the same Kafka partition, guaranteeing ordering:

// Source: lib-events/.../kafka/Broadcaster.java
@Transactional
public void broadcast(KafkaOperation operation, Changes changes) {
    DtoCache dtoCache = new DtoCache();
    String timestamp = DateUtils.format(Instant.now(armClock()));

    changes.getEvents()
           .forEach(e -> send(kafkaTopic, timestamp, e, operation,
                              changes.getPriorityForEvent(e), dtoCache));
}

private UUID send(String topic, String timestamp, EventDto eventDto,
                  KafkaOperation operation, KafkaMessagePriority priority, int revision) {
    var messageId = UUID.randomUUID();

    // Revision cache: skip if a newer version was already broadcast (prevents out-of-order publishes)
    if (eventRevisionCacheEnabled) {
        int latestRevision = eventRevisionCacheService.getLatestCacheRevision(eventDto.getId());
        if (shouldSkipBroadcast(revision, latestRevision)) {
            log.warn("Skipping broadcast: eventId={}, rev={}, latest={}",
                     eventDto.getId(), revision, latestRevision);
            return null;
        }
        eventRevisionCacheService.setLatestCacheRevision(eventDto.getId(), revision);
    }

    MessageDto message = new MessageDto();
    message.setUuid(messageId.toString());
    message.setTimestamp(timestamp);
    message.setOperation(operation);   // KafkaOperation: UPDATE, DELETE, etc.
    message.setEventDto(eventDto);
    message.setPriority(priority);

    var key = String.valueOf(eventDto.getId());  // event ID as partition key → ordering
    kafkaEventsTemplate.send(topic, key, message);
    return messageId;
}
// @Transactional on broadcast(): Kafka send is part of the same TX as the DB update
// that triggered it — if DB commit fails, Kafka send does not happen (via KafkaTransactionManager)

Quartz Scheduler

event-service uses Quartz (not Spring @Scheduled) to manage timed tasks: automatically suspending markets at race start time, triggering resulted-event processing when a race finishes, archiving old events overnight.

Why Quartz over @Scheduled? Spring's @Scheduled is in-memory — if the pod restarts, scheduled jobs are lost. Quartz persists job state to the database (PostgreSQL). If event-service crashes mid-race and Kubernetes reschedules it, Quartz picks up exactly where it left off. For a live betting platform where a missed market suspension means customers can bet at wrong odds, this persistence is critical.

Standard Spring Boot Layered Architecture

event-service uses a standard Spring Boot layered architecture — not hexagonal. All layers use Spring annotations throughout. Domain entities are JPA @Entity classes and live in the shared lib-events library alongside the Kafka publisher and JPA repositories.

No hexagonal architecture — no use-case classes Classes like CreateEventUseCase, UpdateOddsUseCase, or EventRepository as a domain port interface do not exist. Domain entities are Spring JPA @Entity classes. Services use @Service and @Transactional throughout. The architecture is pragmatic layered Spring Boot: controller → service → JPA repository → PostgreSQL.

Spring Annotations Used

  • @KafkaListener(topics = "arm-dev.commands.json") — consumes internal commands
  • @RestController — all three controllers
  • @Transactional — service methods that modify state (e.g. StatusService.updateEvent(), MarketService)
  • @Entity — JPA entities in the infrastructure layer
  • @DisallowConcurrentExecution — Quartz annotation preventing concurrent job runs
  • @EnableJpaRepositories — activates Spring Data JPA
  • Liquibase auto-applied on startup via Spring Boot autoconfiguration

Quiz

Q1. event-service uses Quartz scheduler instead of Spring @Scheduled. Why does this matter in a Kubernetes environment?

  • @Scheduled consumes more CPU than Quartz under load
  • Quartz persists job state to the database — if the pod is killed and rescheduled, jobs resume; @Scheduled is in-memory and loses all scheduled tasks on pod restart
  • Quartz is always faster than @Scheduled for high-frequency tasks
  • @Scheduled does not support cron expression syntax
In Kubernetes, pods can be killed and rescheduled at any time (rolling deployments, OOMKills, node failures). @Scheduled jobs vanish when the pod dies. For a live betting platform, a missed market suspension means customers can place bets after a race starts — real money at stake. Quartz stores job state in PostgreSQL and resumes correctly after restarts.

Q2. The outcomes table stores win_price as BigDecimal. What is the concrete risk of using double instead?

  • double cannot represent negative numbers, causing issues for place bets
  • Floating-point binary cannot represent 0.1 exactly — 3.50 may become 3.4999999999; multiplied across millions of payout calculations, the rounding error loses real money and fails regulatory audits
  • PostgreSQL does not natively support the double type in Java JDBC
  • double is too slow for the high-throughput odds update volume
Binary floating-point (IEEE 754) cannot represent most decimal fractions exactly. 0.1 + 0.2 = 0.30000000000000004 in double arithmetic. For odds and payouts, multiply this error across millions of bets and you get a measurable discrepancy. UK Gambling Commission audits require exact payout calculations. BigDecimal uses base-10 arithmetic — 3.50 is exactly 3.50.

Q3. sportsbook-service and pricing-service both consume arm-dev.event-service.json. How does Kafka ensure both services receive every message independently?

  • event-service sends each message twice, once per consumer
  • Each service belongs to a different consumer group — Kafka delivers the full topic to every consumer group independently; messages are not shared between groups
  • They share one consumer group and alternate processing messages
  • event-service publishes to two different topic names, one per consumer
Kafka's consumer group model: all consumers in the same group share the topic (each message processed once by one consumer). Consumers in different groups each get every message independently. sportsbook-service group: test-local-arm.sportsbook-service-armdev; pricing-service group: test-local-arm.pricing-service-armdev — both receive every event update.

Q4. The PriceScheduleCacheConfig in event-service uses Caffeine, not Redis, for its internal price cache. What does this mean operationally?

  • Caffeine is slower than Redis but cheaper to operate in Kubernetes
  • Caffeine is an in-process heap cache — each pod has its own independent copy. If two event-service pods run, their price caches are not shared. Redis (external cluster) would be shared across all pods
  • Caffeine uses the Redis wire protocol, so it can be replaced with Redis transparently
  • Caffeine stores data on disk; Redis stores data in memory — Caffeine is safer for large price schedules
Caffeine (com.github.ben-manes.caffeine) is an in-JVM cache — zero network hops, nanosecond reads. The event-service price schedule cache is read very frequently from the same service, so local memory beats Redis for latency. The trade-off: if event-service scales to multiple pods, each pod caches independently (no consistency guarantee across pods). Redis would give a shared, consistent cache at the cost of a network call per read. event-service accepts per-pod divergence for the price schedule because the data is refreshed frequently from the authoritative database.
