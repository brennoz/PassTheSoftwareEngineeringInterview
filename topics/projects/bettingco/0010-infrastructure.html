AWS Topology

AWS Region: eu-west-1 VPC ├── EKS Cluster: dev-2-eu-west-1 │ ├── Namespace: arm-dev (development environment) │ └── Namespace: arm-int (integration / pre-prod environment) │ ├── EKS Cluster: prod-eu-west-1 │ └── Namespace: arm-prod (production) │ ├── MSK (Managed Streaming for Kafka) │ Brokers: msk-broker-1.dev.bettingcosport.com:9092 │ msk-broker-2.dev.bettingcosport.com:9092 │ msk-broker-3.dev.bettingcosport.com:9092 │ ├── ElastiCache Redis │ 6-node cluster: 3 primary + 3 replica │ Prod endpoint: a1dca3a16ce804620ad4e91fc2a56c34-895886155.eu-west-1.elb.amazonaws.com:6379 │ ├── ECR (Elastic Container Registry) │ Dev: 471627132520.dkr.ecr.eu-west-1.amazonaws.com │ Prod: 168953832003.dkr.ecr.eu-west-1.amazonaws.com │ └── EFS (Elastic File System) Persistent volumes for stateful services
Why two EKS clusters (not two namespaces in one cluster)? Two separate clusters provide blast radius reduction: a catastrophic failure in dev (misconfigured HPA, runaway pod, misconfigured network policy) cannot affect prod. They also allow different node group configurations (dev can use cheaper instances). The cost is duplicate cluster management, which Terraform IaC and Helm make manageable.

Helm Chart — arm-chart

All 43+ services are deployed from a single Helm chart (arm-chart), parameterised with environment-specific values files:

arm-chart/
  Chart.yaml
  templates/
    deployment.yaml    ← {{ .Values.image.tag }} injected by CI
    service.yaml
    configmap.yaml
    hpa.yaml
  values-dev.yaml     ← dev-specific: low replica counts, debug logging
  values-int.yaml     ← int: closer to prod settings
  values-prod.yaml    ← prod: full replica counts, prod endpoints

Horizontal Pod Autoscaler (HPA) — dev defaults (values-dev.yaml):

minReplicas: 1
maxReplicas: 5
targetCPUUtilizationPercentage: 80

Production override (values-prod.yaml): minReplicas: 2, maxReplicas: 3. Two replicas always running ensures availability; capped at 3 to control cost. No behavior stabilization block is configured in the Helm chart.

Why Helm over raw Kubernetes YAML? 43 services × 3 environments = 129 sets of nearly-identical Deployment/Service/ConfigMap YAML files if done raw. Helm templates parameterise the differences (image tag, replica count, environment variables, endpoints) while sharing a single template definition. helm upgrade arm-chart values-prod.yaml --set image.tag=latest-sha deploys the right configuration for prod in one command.

GitLab CI/CD Pipeline

GitLab CI Stages (defined in .gitlab-ci.yml) Stage 1: build └── ./gradlew build -x test ← Gradle 8.5, compiles all modules Stage 2: unit-tests └── ./gradlew test ← JUnit 5 unit tests, fail fast on failure docker-test.sh ← frontend tests (Jest/Vitest) in Docker Stage 3: docker-push └── docker build -t {ECR_URL}/{service}:{date}-{branch}-{sha} docker push {ECR_URL}/{service}:{date}-{branch}-{sha} Stage 4: helm-deploy └── helm upgrade arm-chart ./helm/arm-chart \ -f values-{env}.yaml \ --set image.tag={sha} Branch rules: trunk (main) → auto-deploy to arm-dev namespace release/* → conditional deploy to arm-int + manual gate for arm-prod feature/* → build + test only, no deploy
Why manual gate for production? Every production deployment is a deliberate decision. The GitLab CI pipeline pauses at the helm-deploy stage for prod and requires a human to click "Deploy". This prevents accidental deployments (merged PRs accidentally triggering prod), ensures QA has validated in arm-int first, and creates a clear audit trail of who approved each production release.

Secrets Management — HashiCorp Vault

Secrets (DB credentials, Kafka TLS certs, JWT signing keys) are managed by HashiCorp Vault via the Vault Secrets Operator (VSO). The Kubernetes CRD VaultStaticSecret declares which Vault path to sync; VSO writes the values into a Kubernetes Secret every 60 seconds. Services consume the Secret via envFrom.secretRef in the Helm Deployment — no AWS Secrets Manager, no hardcoded credentials.

Ingress

ARM uses nginx ingress variants rather than AWS Application Load Balancer (ALB) Ingress Controller:

  • nginx-cloudflare — public traffic via Cloudflare proxy
  • nginx-public — public endpoints without Cloudflare
  • nginx-internal — internal service-to-service traffic
  • nginx-protected — authenticated internal routes

Route 53 DNS → nginx ingress → K8s Service → pods. No ALB in the ingress path.

Terraform — arm-config

All AWS infrastructure is managed as Terraform code in the arm-config repository:

  • ECR repositories (one per service)
  • EKS node groups and IAM roles
  • VPC, subnets, security groups
  • EFS volumes for persistent storage
  • MSK cluster configuration
  • Route53 DNS records (prod only)
  • Datadog monitors (alert thresholds as code)

Separate Terraform state per environment. Changes to infrastructure go through the same GitLab CI review process as application code.

Local Development

Local dev uses docker-compose (in arm-utils/local-env/) to start:

  • Redis cluster: 6 containers (3 primary + 3 replica, bitnami/redis-cluster)
  • RabbitMQ cluster: 3 nodes + HAProxy for STOMP relay
  • Kafka + Zookeeper (local replacement for MSK)
  • PostgreSQL (local, schema per developer)

Quiz

Q1. ARM uses one Helm chart (arm-chart) for all 43+ services with different values files per environment. What is the primary benefit?

  • Helm is significantly faster at deploying containers than raw kubectl apply
  • One parameterised chart avoids duplicating 43 Deployment/Service/ConfigMap YAML files per environment; env differences are localised to values files; image tags are injected by CI at deploy time as a single --set argument
  • Helm automatically compresses Docker images before pushing to ECR
  • Kubernetes requires Helm charts for services that use HPA
Without Helm: 43 services × 3 envs × ~3 YAML files each = 387 YAML files to maintain. Change the HPA target CPU: update in 387 places. With Helm: one template, one values file per env. Change HPA target: edit the template once. The parameterisation is the value — not speed or compression.

Q2. GitLab CI deploys automatically to arm-dev on every trunk merge but requires manual approval for arm-prod. Why the asymmetry?

  • arm-prod uses a different AWS account that requires separate credentials
  • Manual gate ensures every production deployment is a deliberate, auditable decision; dev is a sandbox for rapid iteration where auto-deploy accelerates feedback; prod affects real customers and requires QA validation in arm-int first
  • GitLab CI does not support automatic deployments to production namespaces
  • Terraform manages prod deployments, not GitLab CI helm-deploy
Auto-deploy to dev = fast feedback on every merge. Manual gate to prod = every production change is a conscious decision with a human accountable for it. The audit trail (who clicked "Deploy", when, which SHA) matters for post-incident reviews and regulatory compliance in the gambling industry. arm-int bridges the gap: it gets the automatic deploy from release/* branches, giving QA a stable pre-prod environment before manual prod promotion.

Q3. A new service needs a Kafka topic. Terraform manages MSK in arm-config. What is the correct process?

  • Create the topic manually in the AWS MSK console — Terraform doesn't support topic management
  • Add the topic definition to arm-config's Terraform MSK module, submit for code review, and apply via GitLab CI — infrastructure changes are version-controlled and reviewed like application code
  • The service creates the topic automatically on startup using Kafka AdminClient
  • Kafka topics don't need to be pre-provisioned — they are created on first publish
Infrastructure as code means all infrastructure changes — including Kafka topics — go through the same review and CI pipeline as application code. Manual console changes are untracked (no audit trail, no rollback, no reproducibility). Auto-create on publish is disabled in production MSK to prevent accidental topic creation with wrong partition counts or retention settings. Terraform plan → review → apply is the correct path.
