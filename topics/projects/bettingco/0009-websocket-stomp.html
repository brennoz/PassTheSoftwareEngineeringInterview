ARM BettingCo — WebSocket, STOMP, and Real-time Push

1. Architecture Overview — Three Distinct Services

The real-time push layer in ARM BettingCo is not a single service. There are three separate components with distinct roles:

Kafka topics │ arm-dev.event-service.json │ arm-dev.bet-updates.json │ arm-dev.bet-recommendations │ arm-dev.event-service-inplay.json │ arm-dev.event-service.cerberus-meeting-update │ ├──────────────────────────────────────┐ ▼ ▼ sportsbook-service:8082 internal-websocket-service:8086 WebSocket hub for BROWSERS WebSocket hub for INTERNAL TOOLS (cerberus-ui, sportsbook) (arm-risk tooling) STOMP endpoint: /ws STOMP endpoint: /ws JWT + tenant auth JWT auth, CSRF disabled Change-detection cache (3) In-memory EventService map WebsocketBroadcaster ArrayDeque bet ticker queue Kafka batch consumers (5) Kafka batch consumers (2) │ │ STOMP subscription (client) ▼ sportsbook-publisher:8099 STOMP CLIENT (not a server) Connects to sportsbook-service /ws Subscribes to event/bet topics Re-publishes to external TENANTS via HTTP or FTP per tenant config
Common misconception sportsbook-publisher is often described as a RabbitMQ producer. It is not. It is a STOMP client that connects to sportsbook-service via WebSocket, receives STOMP frames, and forwards them to external tenant endpoints via HTTP or FTP. RabbitMQ is only involved as the production broker relay inside sportsbook-service — it is never directly touched by sportsbook-publisher.

2. sportsbook-service — Dual Broker Mode

sportsbook-service supports two broker backends, selected at runtime by the property ws.simple-broker:

Simple Broker Mode (default — ws.simple-broker=true)

Uses Spring's built-in SimpleBroker with in-memory message routing. This is the default for local development. No external infrastructure is required. Fan-out is limited to subscribers connected to the same JVM instance.

// Simple broker config (dev default)
registry.enableSimpleBroker("/topic", "/queue")
        .setHeartbeatValue(new long[]{10000, 10000})
        .setTaskScheduler(heartbeatScheduler());  // ThreadPoolTaskScheduler
                                                  // name: "wss-heartbeat-thread-"
                                                  // pool size: 1

RabbitMQ Relay Mode (ws.simple-broker=false — production only)

Uses enableStompBrokerRelay(), which opens a STOMP TCP connection from each sportsbook-service pod to RabbitMQ. All pods share one external broker — so a message published by pod A is delivered to subscribers on pods B and C. This solves the multi-pod fan-out problem.

// RabbitMQ relay config (production)
registry.enableStompBrokerRelay("/topic", "/queue")
        .setRelayHost("rabbitmq-ha")     // HAProxy load-balancing 3 RabbitMQ nodes
        .setRelayPort(61613)             // STOMP protocol port (not AMQP 5672)
        .setVirtualHost("/")             // configurable
        .setClientLogin("...")
        .setClientPasscode("...");
Why RabbitMQ relay solves the multi-pod problem WebSocket sessions are stateful — each client maintains a persistent connection to exactly one pod. HAProxy round-robins new connections, spreading subscribers across pods. In SimpleBroker mode, pod A only knows about its own subscribers. With relay mode, all pods publish to the same RabbitMQ exchange; RabbitMQ fan-out delivers to every subscriber on every pod.

3. STOMP Endpoint Config

Both sportsbook-service and internal-websocket-service expose a STOMP endpoint at /ws with SockJS:

registry.addEndpoint("/ws")
        .setAllowedOriginPatterns("*")
        .withSockJS();   // WebSocket -> xhr-streaming -> xhr-polling -> jsonp fallback chain

Heartbeat is set symmetrically to 10 000 ms in both directions. The heartbeat scheduler is a dedicated ThreadPoolTaskScheduler named wss-heartbeat-thread- with a pool size of 1 — a single thread is sufficient because heartbeats are low-frequency and non-blocking.

Two additional channel customisations are registered on sportsbook-service:

  • configureClientInboundChannel — registers TopicSubscriptionInterceptor (see section 4)
  • configureMessageConverters — adds MarshallingMessageConverter (XML support alongside Jackson JSON)

Additionally, HttpHandshakeInterceptor captures the connecting client's IP address from the X-Forwarded-For header during the SockJS HTTP handshake, storing it as a session attribute for audit and rate-limiting purposes.

4. TopicSubscriptionInterceptor — Per-SUBSCRIBE Authorization

Every STOMP SUBSCRIBE frame passes through TopicSubscriptionInterceptor before the subscription is registered. This is how sportsbook-service enforces per-topic, per-tenant access control without a separate HTTP gate:

STOMP SUBSCRIBE frame arrives | v TopicSubscriptionInterceptor.preSend() | +-- 1. Extract JWT from "Authorization" native STOMP header | authenticate user (throws exception if invalid) | +-- 2. topicService.needsAuthorization(destination) | Does this topic require tenant-level auth? | | NO --> anonymous path | | x-queue-name = "{topic}_{UUID}" | | subscription proceeds | | | YES --> authorized path | +-- validate tenant JWT | +-- topicService.hasAccess(tenantId, destination) | +-- validate DeliveryMethod == WEBSOCKET | +-- x-queue-name = "{tenantId}_{tenantName}_{topic}_{UUID}" | v x-queue-name set as native STOMP header on the subscription (used by RabbitMQ to create a named durable queue for this subscriber)

The x-queue-name header format is significant: in RabbitMQ relay mode it instructs the broker to create a named queue for this subscriber rather than an anonymous transient queue. This makes reconnections cheaper — the subscriber can rejoin the same named queue and receive any messages buffered during the disconnect.

Change-detection cache — three caches, not one

Before broadcasting a STOMP message, WebsocketMessageDeliveryService.hasChanged() checks whether the incoming payload differs from the last broadcast. This is deduplication, not serialisation — the cache stores EventDto Java objects and compares them with .equals(). If the cached object equals the incoming object, the broadcast is skipped entirely.

Cache nameTTLContent
websocketEventMessageCache15 minHorse racing events (EventDto)
websocketDogRacingMessageCache15 minGreyhound racing events (EventDto)

The default cache manager is Caffeine — a local in-process cache. Redis is only used when REDIS_CACHE_ENABLED=true (default: false). In a multi-pod deployment with Caffeine, each pod maintains its own independent cache — a pod that has not yet seen a given event will broadcast it even if another pod already filtered it. Redis mode aligns all pods but adds a network round-trip to every delivery path.

WebsocketBroadcaster — retry and header enrichment

After the change-detection check passes, WebsocketBroadcaster sends the STOMP message to the broker:

  • @Retryable: maxAttempts=6, exponential backoff starting at 500 ms with multiplier 1.5, retries on MessageDeliveryException
  • Adds a uuid native STOMP header to every outbound message (enables idempotency / deduplication by receivers)
  • Adds custom headers (arm_timestamp, sport, and others) sourced from the delivery service
  • Uses SimpMessageHeaderAccessor to construct the STOMP header map before calling messagingTemplate.convertAndSend()

7. internal-websocket-service (port 8086)

internal-websocket-service is a completely separate Spring Boot application — not a module of sportsbook-service. Its audience is internal ARM tooling such as arm-risk, not browser clients.

Kafka consumers

Listener classConsumer IDTopicMessage type
BetServiceKafkaListenerarm-bets-websocketarm-dev.bet-updates.jsonBetDto
EventKafkaListenerarm-events-websocketarm-dev.event-service.jsonMessageDto

Consumer group: test-local-arm.websocket-service-armdev.

Topic naming

TopicService.formatTopicName() builds destination strings from environment and topic name: {topicPrefix}/{topicEnv}{topicName}. Examples: /topic/test_local_events, /topic/test_local_bets. The environment segment prevents topic collisions when multiple environments share the same RabbitMQ instance.

In-memory event store

EventService maintains a ConcurrentHashMap<Long, EventDto> of all non-finished events. When a Kafka event message arrives, updateEvent() adds the entry or removes it when EventStatus.FINISHED. This map is the source of truth for bet enrichment — it avoids a database round-trip per broadcast.

Bet ticker queue

UpdatedBetsQueueService maintains an ArrayDeque<BetDto> capped at retainSize (default: 100). When a client reconnects, it calls GET /bet-tickers (BetTickerController.repopulateBetTickers()) to retrieve the last 100 bets and catch up on activity missed during the disconnect. Settled bets are filtered out before broadcast.

Why ArrayDeque and not LinkedList? ArrayDeque is backed by a resizable array — O(1) amortised add-to-tail and remove-from-head, better cache locality than a node-linked structure, and no per-node pointer overhead. A capped deque is the canonical bounded First In, First Out (FIFO) structure for this reconnect-replay pattern.

Bet enrichment

Before broadcasting a BetDto, each PartDto inside the bet is enriched with event, market, and outcome data looked up from the in-memory EventService map. This ensures consumers receive fully resolved objects rather than bare IDs.

No change-detection cache

Unlike sportsbook-service, internal-websocket-service broadcasts directly — there is no deduplication layer. Internal tooling (arm-risk) needs every update, not a deduplicated stream.

Security

  • JwtAuthenticationTokenFilter — HTTP-level JSON Web Token (JWT) validation filter
  • WebsocketSecurityConfig extends AbstractSecurityWebSocketMessageBrokerConfigurer — Cross-Site Request Forgery (CSRF) protection is explicitly disabled via sameOriginDisabled()=true. This is required for STOMP over SockJS, which cannot embed CSRF tokens in the STOMP CONNECT frame
  • /ws/** is whitelisted in SecurityConfig to allow the SockJS HTTP handshake through before the JWT filter intercepts
  • RemoteAuthenticationProvider — calls authenticationApi.login() on auth-service to authenticate credentials, maps the result to SecurityUserDetails

8. sportsbook-publisher (port 8099) — STOMP Client, Not Server

sportsbook-publisher's role is tenant delivery: it connects to sportsbook-service as a STOMP client, subscribes to event and bet topics, and forwards each message to external tenant systems via HTTP or File Transfer Protocol (FTP).

STOMP client configuration

sportsbook-publisher uses Spring's server-side WebSocketStompClient — not the browser @stomp/stompjs library. The transport stack is StandardWebSocketClient wrapped in SockJsClient, configured in StompConfig with a MappingJackson2MessageConverter for JSON deserialisation of incoming frames.

Startup flow — EventsStompController

On ApplicationReadyEvent:

ApplicationReadyEvent fired | v 1. loginApi.login() POST to auth-service --> receive JWT | v 2. websocketApi.getWsTopics() GET list of STOMP topic destinations to subscribe | v 3. WebSocketStompClient.connect("{sportsbook-service.url}/ws", ...) | v 4. afterConnected() callback for each topic: stompSession.subscribe(topic, frameHandler, headers: { ack: "client-individual" }) // client-individual = each frame must be ACKed individually // prevents silent message loss on crash

Frame handling and tenant delivery

When a STOMP frame arrives, handleFrame() passes the raw bytes and headers to MessageProcessor.processMessage(). The processor resolves the tenant from the topic name, then dispatches based on the tenant's configured DeliveryMethod:

  • HTTP → HttpMessageSender — REST POST to the tenant's webhook endpoint
  • FTP → FtpMessageSender — writes the message to the tenant's FTP drop location

@Retryable wraps processMessage() with a maximum of 15 attempts per tenant message. The STOMP connection itself retries up to 50 times on connection failure before alerting.

Metrics

A Micrometer Timer named rmq_websocket_message_consuming_timings records the end-to-end processing time per frame, tagged by queue name and message type.

Why not connect sportsbook-publisher directly to Kafka? sportsbook-publisher needs the enriched, deduplicated, change-filtered stream that sportsbook-service already produces. Subscribing to raw Kafka topics would require duplicating all the change-detection cache logic and bet-enrichment logic in a second service. Consuming the STOMP stream from sportsbook-service gives sportsbook-publisher a clean, tenant-ready feed for free.

Quiz

Q1. In production, sportsbook-service has 3 pods. A Kafka event arrives at pod A. Which subscribers miss the STOMP broadcast — and what prevents this in production?

  • All subscribers on all pods receive the broadcast because STOMP protocol replicates automatically across pods
  • HAProxy sticky sessions ensure all subscribers connect to the same pod, so no subscriber ever misses a message
  • Only subscribers connected to pod A receive the broadcast in SimpleBroker (dev) mode; in production, RabbitMQ relay mode (ws.simple-broker=false) centralises fan-out so all pods' subscribers receive the message regardless of which pod consumed the Kafka event
  • internal-websocket-service handles multi-pod fan-out for sportsbook-service automatically
In SimpleBroker mode, each pod has its own in-memory broker — pod A's broadcast never reaches pods B and C. The fix is ws.simple-broker=false, which switches to enableStompBrokerRelay(). All pods open a STOMP TCP connection to the shared RabbitMQ cluster (host: rabbitmq-ha, port: 61613). Pod A publishes to RabbitMQ; RabbitMQ fan-out delivers to every subscriber on every pod. This is why SimpleBroker is only safe in single-instance local development.

Q2. A STOMP SUBSCRIBE frame arrives at sportsbook-service for a tenant-protected topic. What does TopicSubscriptionInterceptor do before the subscription is registered?

  • TopicSubscriptionInterceptor only validates the JWT — topic-level access control is handled by a separate REST call after the subscription is registered
  • TopicSubscriptionInterceptor extracts the JWT from the Authorization STOMP header, authenticates it, calls topicService.needsAuthorization(destination), and if yes: validates the tenant JWT, calls topicService.hasAccess(), confirms DeliveryMethod == WEBSOCKET, then sets x-queue-name to "{tenantId}_{tenantName}_{topic}_{UUID}" as a native STOMP header before the subscription proceeds
  • TopicSubscriptionInterceptor rejects the SUBSCRIBE frame and sends a STOMP ERROR — subscriptions to protected topics always require a prior HTTP handshake
  • Authorization only applies to the CONNECT frame; once connected, any subscription destination is permitted
TopicSubscriptionInterceptor intercepts at the STOMP protocol layer, inside configureClientInboundChannel, before Spring registers the subscription. The JWT is a native STOMP header (not an HTTP header). For anonymous topics x-queue-name is simply "{topic}_{UUID}". For authorized topics the tenant ID and name prefix allows RabbitMQ to create a named durable queue per subscriber, enabling reconnect buffering.

Q3. sportsbook-service has three change-detection caches. What do they store, and what happens on a cache hit?

  • The three caches (websocketEventMessageCache, websocketDogRacingMessageCache, websocketBetRecommendationMessageCache) store EventDto Java objects. When hasChanged() finds the cached object .equals() the incoming object, the broadcast is skipped entirely — no STOMP message is sent
  • The caches store serialised STOMP message bytes; a cache hit means the bytes are served directly to subscribers without re-serialising
  • There is only one change-detection cache; the three names are environment-scoped aliases for the same underlying cache
  • The cache stores the UUID of the last message per topic; a hit means the same UUID arrived twice and the message is deduplicated at the Kafka consumer layer before reaching the broadcaster
The caches hold EventDto objects (Java heap), not serialised bytes. hasChanged() calls .equals() between the cached dto and the incoming dto — if identical, no STOMP broadcast occurs. The cache manager is Caffeine by default (in-process, per-pod). Redis is optional via REDIS_CACHE_ENABLED=true. With Caffeine across multiple pods, each pod has its own cache — a pod that hasn't seen a given event yet will broadcast it even if another pod already suppressed it. Redis mode eliminates this per-pod inconsistency at the cost of a network round-trip per delivery.

Q4. What does sportsbook-publisher actually do, and why is describing it as a RabbitMQ producer incorrect?

  • sportsbook-publisher is a RabbitMQ producer: it consumes Kafka events and publishes them as AMQP messages to RabbitMQ exchanges, which then routes them to tenant queues
  • sportsbook-publisher is a Kafka consumer that transforms events and pushes them directly to tenant REST APIs without touching WebSocket
  • sportsbook-publisher is a Spring WebSocket server that external tenants connect to with their own STOMP clients
  • sportsbook-publisher is a STOMP client (WebSocketStompClient + SockJsClient) that connects to sportsbook-service /ws, subscribes to event/bet topics, receives STOMP frames, and re-delivers each message to external tenant systems via HTTP or FTP based on tenant DeliveryMethod config — it never touches RabbitMQ directly
The "publisher" in the name refers to publishing to tenants, not to a message broker. sportsbook-publisher runs Spring's server-side WebSocketStompClient. On ApplicationReadyEvent it logs in, fetches the topic list, connects to sportsbook-service /ws, and subscribes with ack: client-individual. In handleFrame() it calls MessageProcessor.processMessage(), which dispatches to HttpMessageSender (REST POST) or FtpMessageSender based on tenant config. RabbitMQ is only involved inside sportsbook-service as the broker relay — sportsbook-publisher only consumes the already-delivered STOMP stream.
