PairingCo Pairing Round — Format & Rubric

PairingCo 2nd stage — technical pairing  ·  Live refactor exercise, ~45–60 min · Lesson 1 of 3

This round pairs you with a senior engineer and a tech lead on an existing Java codebase seeded with code smells. You are driving, but the framing is explicit: treat the two engineers as junior developers you are mentoring through the change. Finishing the refactor is not the goal — how you read unfamiliar code, decide what to change, and explain it while changing it, is.

1. What Actually Gets Graded

Sourced from the task brief plus public signal on this specific PairingCo exercise (2nd-stage technical pairing, Kotlin codebase, code-smell refactor, less about syntax and more about thought process):

AxisWhat they're watching for
Technical communicationYou narrate before you type. You name the pattern/technique you're applying and why. You justify each step, not just the end state.
Balanced engineeringYou improve the code without over-engineering it — no speculative abstraction, no gold-plating a class nobody asked you to touch.
PrioritizationYou find the highest-impact smell first and say why it's highest-impact, instead of refactoring top-to-bottom or chasing whatever you noticed first.
Reading unfamiliar codeYou have a visible strategy for orienting in code you've never seen — not silent scrolling.
Leading safelyYou protect behaviour before changing it (tests), take the smallest safe step, and treat the two engineers as people to bring along, not an audience.
The non-goal, stated plainly "Finishing the task is not the goal." A candidate who ships a fully refactored file having narrated nothing loses to a candidate who safely improves one thing and explains it well. Don't race the clock.

2. Predicted Domain

PairingCo is a supply-chain / ethical-trade compliance platform (100k+ businesses, supply-chain sustainability data). Expect domain nouns in the codebase like Site, Supplier, Buyer, Audit, SAQ (self-assessment questionnaire), Membership, Rating/RiskScore. If a class or method name is unfamiliar, that's domain vocabulary, not a language gap — ask what it means rather than guessing.

3. Predicted Code Smells

These map directly to categories you already have planted examples for in code-review/ in this repo — useful raw material for drills (see Lesson 2's roleplay block):

  • God class / God method — one class or function doing orchestration, validation, and persistence
  • Feature envy — a method that mostly reaches into another object's data
  • Primitive obsession — String/int standing in for a domain concept (e.g. a raw String for an audit status instead of an enum)
  • Duplicated logic across two near-identical code paths
  • Missing or thin tests around the exact area you're asked to touch
  • Mutable shared state / non-data class DTOs with unclear ownership
  • Magic numbers/strings standing in for named business rules

4. Predicted Session Shape

  1. Orient (~5 min) — scan the file(s), ask what the code is for, ask if there's an existing test suite to run first.
  2. Pick a target together — state 2–3 smells you see, rank them, say which you'd fix first and why. Invite their opinion — this is the "mentoring junior" signal.
  3. Protect current behaviour — write or point at a characterization test before touching logic with weak coverage.
  4. Smallest safe step — one extract/rename/introduce-abstraction at a time, run tests, narrate as you go.
  5. Repeat or stop — either continue to the next smell or explicitly park remaining ones ("I see X too, not fixing it today, here's why").
  6. Wrap — summarise what changed, what you deliberately left, what you'd do next with more time.

5. Do / Don't

DO

  • Think aloud before typing
  • Name the pattern + one rejected alternative
  • Ask "what would you two do here?" at least once
  • Add/verify a safety-net test before a risky change
  • State the tradeoff out loud, even if you proceed anyway
  • Watch the clock — stop cleanly rather than half-finish two things

DON'T

  • Type silently for more than ~30 seconds
  • Big-bang rewrite the whole file
  • Introduce an abstraction the current code doesn't need yet
  • Ignore an existing test that starts failing
  • Correct a "junior" suggestion bluntly without explaining why
