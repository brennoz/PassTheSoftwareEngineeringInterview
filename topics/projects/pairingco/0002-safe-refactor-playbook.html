Safe Refactor Playbook

PairingCo Technique  ·  The repeatable loop to run live · Lesson 2 of 3

One loop, run on every smell you touch. The loop itself is the deliverable — interviewers are watching whether you have one, not whether you memorised a catalogue of refactorings.

Understand→ Protect→ Smallest safe step→ Verify→ Narrate→ Repeat

1. Understand Before Touching

Read the method/class fully before proposing anything. State out loud what it currently does — not what's wrong with it yet. This separates "I understand this" from "I'm pattern-matching on smells I've seen before," which is exactly what a rubric on reading unfamiliar code is checking.

Script "Before I change anything — let me say back what this does, so you can correct me if I've misread it: it takes a <X>, does <Y>, and returns <Z>. Is that right?"

2. Protect Current Behaviour

If there's no test covering the path you're about to touch, that's the first thing to fix — before the "real" refactor. This is a characterization test: a test that pins down what the code currently does (bugs included), not what it should do. It's your rollback net.

Why this matters more than the refactor itself A candidate who refactors confidently but breaks untested behaviour looks worse than one who writes one characterization test and makes a smaller change. "Leading safely" is graded explicitly — this is the single highest-leverage move in the whole session.

Fast pattern (say it, don't just do it)

// 1. Call the method with realistic inputs, assert on whatever it currently returns
// 2. Run it, read the actual output, paste that as the expected value
// 3. Now you have a net — any refactor that changes behaviour goes red immediately
@Test
void pinsCurrentBehaviourBeforeRefactor() {
    BigDecimal result = auditService.calculateRiskScore(sampleAudit);
    assertEquals(0, EXPECTED_CURRENT_VALUE.compareTo(result));  // captured from a real run, not derived
}

3. Smallest Safe Step

Don't plan the end-state and type toward it. Take one mechanical, low-risk step, run tests, then decide the next step based on what you now see. Typical order of moves, cheapest/safest first:

  1. Rename — free, zero behaviour risk, immediately improves readability for everyone watching
  2. Extract method — pull a cohesive chunk out, no logic change
  3. Extract class / introduce parameter object — group data that's always passed together (fixes primitive obsession)
  4. Replace magic value with named constant/enum
  5. Replace conditional with polymorphism / strategy — only once you've seen the same if/when branch shape repeat at least twice
Script when picking a step "I could jump straight to a Strategy pattern here, but I only have one real branch in front of me right now — I'll extract the method first and see if a second case shows up before I introduce that abstraction."

4. Verify, Every Step

Re-run the test(s) after every mechanical step, not just at the end. Say the result out loud even when it passes — silence after a change reads as uncertainty, not confidence.

5. Prioritization Framework

When you see 3+ smells at once (you will), rank instead of going top-to-bottom in the file:

FactorQuestion
ImpactIs this code hot (touched often / bug-prone) or cold (rarely changes)?
RiskHow much blast radius if this breaks — one caller or twenty?
RelevanceDoes fixing this unblock whatever the "task" in front of you actually asks for?
Script for parking something "I also see <smell Y> over here — I'm not touching it today because it's not on the path of what we're changing and it's low-risk as-is. Flagging it, not fixing it."

6. The Over-Engineering Line

"Balanced engineering" is graded explicitly — the failure mode isn't just under-refactoring, it's building an abstraction the current code doesn't justify.

YAGNI check, said out loud "I could make this generic over any status type, but I only have one caller and no evidence a second is coming — I'll keep it concrete and leave a comment on why, rather than build the abstraction now."

7. When You're Wrong Mid-Session

It will happen. The recovery, not the mistake, is what's graded.

Script "Actually — that assumption doesn't hold, I can see it breaks <case>. Let me back that last step out and take a smaller one."
