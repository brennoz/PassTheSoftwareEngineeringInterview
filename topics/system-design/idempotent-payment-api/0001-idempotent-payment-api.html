Lesson 01 — Idempotent Payment API

Category: System Design · Domain: Payments/Fintech · Difficulty: Medium-Hard · Est. time: 20 min

Networks fail. Clients retry. Without idempotency, a retry creates a second charge. This lesson covers the complete server-side pattern for making a payment API safe to retry without ever processing the same payment twice.

After this lesson you can: Design an idempotency layer from scratch, handle the concurrent-duplicate race condition, wire the Outbox Pattern for reliable event publishing, and explain every component to an interviewer.

1. The problem — why retries cause double charges

Client API Server DB │ │ │ │── POST /payments ────────►│ │ │ {amount: 100, │── INSERT payment ────►│ │ idempotencyKey: "k1"} │ │ │ │ ← 500 / timeout ────│ ← server crashed after write │ [client sees no response]│ │ │ │ │── POST /payments ────────►│ ← RETRY │ {amount: 100, │── INSERT payment ────►│ ← DOUBLE CHARGE │ idempotencyKey: "k1"} │ │

The client cannot tell if the first request succeeded or not. If it retries without protection, the payment is processed twice. Idempotency key: a client-generated unique token attached to every mutating request. The server uses it to detect and suppress duplicates.

2. Idempotency key — rules

RuleDetail
Who generates itClient — UUID v4 before the first attempt. Never the server.
ScopePer operation + per client. Same key = same payment. Different key = new payment.
HeaderIdempotency-Key: <uuid> — industry standard (Stripe, Adyen use this header)
Sent withEvery retry of the same request — identical payload + same key
Time-to-live24 hours typical. After TTL, same key treated as a new request.
Missing keyReturn 400 Bad Request — never process a payment without one

4. Database schema

-- Idempotency records table
CREATE TABLE idempotency_records (
    key         VARCHAR(64)   NOT NULL,
    client_id   VARCHAR(64)   NOT NULL,
    status      VARCHAR(16)   NOT NULL,   -- PROCESSING | COMPLETED | FAILED
    request_hash VARCHAR(64)  NOT NULL,   -- SHA256 of request body
    response    TEXT,                     -- serialised JSON of first response
    expires_at  TIMESTAMPTZ   NOT NULL,
    created_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),
    PRIMARY KEY (key, client_id)
    -- unique constraint enforces exactly-once INSERT at DB level
);

-- Payments table
CREATE TABLE payments (
    id              UUID PRIMARY KEY,
    idempotency_key VARCHAR(64)  NOT NULL,
    amount          NUMERIC(19,4) NOT NULL,   -- never FLOAT
    currency        CHAR(3)      NOT NULL,
    status          VARCHAR(16)  NOT NULL,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- Outbox table (Outbox Pattern — same transaction as payment)
CREATE TABLE payment_outbox (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    payload     JSONB        NOT NULL,
    published   BOOLEAN      NOT NULL DEFAULT false,
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);

5. The concurrent duplicate race condition

Two retries arrive simultaneously — both find the key absent at step 2, both try to INSERT. Without protection, both proceed and the payment is charged twice.

Race window Thread A: SELECT → not found → [context switch] → Thread B: SELECT → not found → both INSERT → double charge.

Fix: DB unique constraint + handle duplicate key exception

-- The PRIMARY KEY (key, client_id) gives us a unique constraint for free.
-- Two concurrent INSERTs: one wins, the other gets a unique violation.

@Transactional
public PaymentResult process(String idempotencyKey, String clientId, PaymentRequest req) {

    try {
        // Attempt to claim the slot — throws on duplicate
        idempotencyRepo.insertProcessing(idempotencyKey, clientId, hash(req));

    } catch (DataIntegrityViolationException e) {
        // Another thread (or retry) already claimed this key
        IdempotencyRecord record = idempotencyRepo.findByKey(idempotencyKey, clientId);

        if (record.isProcessing()) {
            // First request still in flight — tell client to retry later
            throw new ConflictException("Payment is already being processed");
        }
        // First request completed — return stored result
        return deserialize(record.getResponse());
    }

    // We own the key — execute the payment
    PaymentResult result = paymentService.charge(req);

    // Update record to COMPLETED + store response (same transaction)
    idempotencyRepo.markCompleted(idempotencyKey, clientId, serialize(result));

    return result;
}
Why unique constraint beats SELECT FOR UPDATE SELECT FOR UPDATE locks the row — only works when the row exists. On first insert there is no row to lock. Unique constraint on INSERT is the correct tool: exactly one thread wins; the loser gets an exception to handle gracefully.

6. Outbox Pattern — reliable event publishing

After charging, you need to publish a PaymentCompleted event to Kafka/SNS for downstream services (fraud detection, notifications, ledger). Publishing after commit risks losing the event if the broker is down. Publishing before commit risks publishing an event for a transaction that rolls back.

❌ Wrong — event lost if Kafka is down after commit: BEGIN TX → charge account → COMMIT → publish to Kafka ← can fail here ❌ Wrong — ghost event if TX rolls back: BEGIN TX → charge account → publish to Kafka ← event sent → ROLLBACK ✅ Correct — Outbox Pattern: BEGIN TX → charge account → INSERT INTO payment_outbox (payload) ← same transaction COMMIT [Outbox relay polls outbox table] → publish to Kafka → UPDATE payment_outbox SET published = true
-- Outbox relay (runs every 100ms, or triggered by DB LISTEN/NOTIFY)
SELECT * FROM payment_outbox WHERE published = false ORDER BY created_at LIMIT 100;
-- publish each to Kafka
-- on ack: UPDATE payment_outbox SET published = true WHERE id = ?
At-least-once + Kafka consumer deduplication Outbox relay may publish the same event twice on crash/restart (before marking published=true). Kafka consumers must deduplicate using the payment ID as the deduplication key. Kafka idempotent producer (enable.idempotence=true) prevents producer-side duplicates.

7. Request hash — guard against key reuse with different payload

A misbehaving client might send the same idempotency key with a different amount. Store a SHA-256 hash of the original request body. On retry, compare hashes. If they differ → return 422 Unprocessable Entity ("Idempotency key already used for a different request"). 

String requestHash = sha256(objectMapper.writeValueAsString(request));

if (existingRecord != null && !existingRecord.getRequestHash().equals(requestHash)) {
    throw new UnprocessableEntityException(
        "Idempotency key '" + key + "' was already used for a different request");
}

DynamoDB conditional write (no SQL unique constraint)

// Atomic "insert if not exists" — replaces the SQL unique constraint
dynamoDB.putItem(PutItemRequest.builder()
    .tableName("IdempotencyRecords")
    .item(Map.of(
        "pk",     AttributeValue.fromS(clientId + "#" + idempotencyKey),
        "status", AttributeValue.fromS("PROCESSING"),
        "ttl",    AttributeValue.fromN(String.valueOf(Instant.now().plusSeconds(86400).getEpochSecond()))
    ))
    .conditionExpression("attribute_not_exists(pk)")   // ← atomic check-and-set
    .build());
// ConditionalCheckFailedException = duplicate → handle same as DataIntegrityViolationException

What breaks at scale without idempotency

  • Mobile clients on flaky connections retry aggressively → duplicate charges at scale
  • Load balancer health-check retries → payment service auto-retry → double debit
  • Kafka consumer at-least-once delivery → downstream ledger double-posts
  • Blue/green deploy mid-request → old pod dies, new pod retries the queued request

9. Retrieval quiz

Q1. Who should generate the idempotency key — client or server?

  • A) Client — generated before the first attempt, sent with every retry of the same request
  • B) Server — generated after validating the request, returned to the client in the response
  • C) Either — it does not matter as long as it is unique
  • D) The API Gateway — it adds a correlation ID header automatically
The client must generate the key before the first attempt. If the server generated it, the client would need a round-trip before the first request — and the very first request could still be retried without a key. Client-generated UUID: the client knows the key before any network call happens, so every retry can include the same key from the start.

Q2. Two concurrent retries arrive simultaneously with the same key. The DB shows no existing record. What prevents a double charge?

  • A) The server checks a Redis lock before inserting — only one request proceeds
  • B) The API Gateway deduplicates requests with the same header before they reach the service
  • C) A unique constraint (or DynamoDB conditional write) on the idempotency key — one INSERT wins, the other gets a duplicate key exception and returns the cached result
  • D) SELECT FOR UPDATE locks the idempotency record row before processing begins
SELECT FOR UPDATE only locks an existing row — on first insertion there is no row to lock. Redis lock adds a separate system to keep consistent. Unique constraint is atomic at the DB level: exactly one concurrent INSERT succeeds; the loser handles the exception. DynamoDB conditional write (attribute_not_exists) is the equivalent without SQL.

Q3. Why store the payment event in an outbox table in the same transaction as the payment, rather than publishing directly to Kafka after commit?

  • A) Kafka does not support direct writes from a Spring Boot service
  • B) Publishing after commit: if Kafka is down, event is lost and the payment has no audit trail. Outbox: event is atomically saved with the payment — relay publishes when Kafka recovers
  • C) The outbox pattern is only needed when using SQS, not Kafka
  • D) Publishing before commit is always safe because Kafka has its own rollback mechanism
Dual-write problem: you cannot atomically commit to two separate systems (DB + Kafka) without a distributed transaction. Outbox solves this by writing only to the DB (one system), then a relay publishes to Kafka asynchronously. If Kafka is down: payment is safe in DB, outbox relay retries until Kafka recovers. No lost events, no ghost events.

Q4. A client sends the same idempotency key but with a different request body (different amount). What should the server return?

  • A) 200 OK — process the new amount, the key is reused legitimately
  • B) 409 Conflict — the key is already PROCESSING so the new request is rejected
  • C) 200 OK with the cached result from the first request, ignoring the new amount
  • D) 422 Unprocessable Entity — idempotency key was already used for a different request payload (detected via request hash mismatch)
Silently processing a different amount (A) is dangerous — client bug causes wrong charge. Returning the first result silently (C) is also wrong — the client thinks they charged a different amount but got the old result. The correct response is 422 with a clear error: "idempotency key already used for a different request." The request hash (SHA-256 of body) stored on first use enables this check.
