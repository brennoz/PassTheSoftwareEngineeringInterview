Tesco Store System — Bounded Context Overview

Tesco Interview Prep · Tier 2 — Worked Example · File 3 of 12
What Tesco actually said (paraphrased, uncertain — from 2nd interview conversation) There's a machine in each store, likely connected to the cashier terminals. They mentioned heavy use of WebSockets. Infrastructure is dockerized, running on Kubernetes, hosted on Azure. Backend services are Spring Boot microservices. That's the complete list of real recalled hints — everything else in this file and the rest of the folder is a plausible design built to be consistent with those hints, not a claim about Tesco's actual system.

This file sketches the shape of a hypothetical Tesco store system consistent with those hints: a WebSocket-connected in-store machine implies a local compute layer near the cashier terminals (not everything routing straight to the cloud); Docker/K8s/Azure implies containerised services, likely split between a lightweight cluster in-store and a larger one centrally; Spring Boot microservices implies bounded-context service boundaries rather than one monolith.

1. Why local compute exists at all — the question that shapes everything else

The most important design decision in this whole system, and the one worth stating out loud first in an interview, is this: why does a shop with a good internet connection need a local machine at all, instead of every cashier terminal just calling a central cloud API directly? Three answers, and any one of them alone would justify it:

  1. Latency. A checkout scan-to-price-display round trip needs to feel instant. A local hop is single-digit milliseconds; a round trip to a central region can be 50–150ms even on a good link, and queues form during peak trading (Christmas Eve, Boxing Day) exactly when you can least afford slow tills.
  2. Availability under network partition. A supermarket cannot stop selling because its WAN link to head office drops. Card payments and stock lookups need to keep working, degraded if necessary, off a local cache — this is the strongest argument and the one to lead with (file 0010 goes deep on this).
  3. Fan-out cost and blast radius. Thousands of stores hammering one central API for every single scan is both expensive and a single point of failure for the entire estate. Local compute turns "3,000 stores calling central per-scan" into "3,000 stores syncing periodically" — a fundamentally cheaper and safer traffic shape.

The boundary rule worth stating explicitly in the interview Every store-edge service except Store-Sync must be able to keep functioning with zero connectivity to central. That's a deliberate architectural rule, not an accident — it's what makes the "why local compute" argument in Section 1 actually true rather than aspirational. If Pricing Service's read path required a live central call, the WAN-outage story falls apart. Naming this rule out loud is a strong signal — it shows the design decision was followed through consistently, not just used to justify drawing an edge box.
