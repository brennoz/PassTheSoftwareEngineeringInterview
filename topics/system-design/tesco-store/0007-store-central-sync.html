Store ↔ Central Sync

Tesco Interview Prep · Tier 2 — Worked Example · File 7 of 12

This is where "thousands of stores" scale actually bites (file 0005 explicitly isn't this problem). Two directions of flow, each with a different consistency story.

1. Two directions, two different rules

DirectionWhat flowsWho's the writer
Central → StorePrice/promo updates, occasional stock-master correctionsCentral is the SOLE writer; every store is a read-only subscriber/cache
Store → CentralSales transactions, local stock decrements, loyalty point eventsEach store is the sole writer for ITS OWN store's events; central aggregates from all stores
Why there's no real write-conflict to resolve Both directions are single-writer per piece of data — central owns prices, each store owns its own sales/stock events. That's a deliberate design choice, not luck: partitioning ownership this way means "conflict resolution" reduces to "handle staleness," which is a much easier problem than true concurrent-write conflict resolution (no CRDTs or last-writer-wins tie-breaking needed anywhere in this flow).

2. Central → Store: price/promo propagation

Central Pricing Service updates a price │ ▼ Publishes change event to Azure Service Bus topic │ ▼ Each store's local Pricing Service subscribes, applies to its local cache │ (if a store is offline, the message waits in Service Bus — or the store catches up via a periodic full-sync pull on reconnect, whichever is simpler to reason about for staleness bounds)

A store offline for an hour during a price change means that store sells at the OLD price for up to that hour once reconnected and caught up — an accepted, bounded business risk, not a bug to design away entirely. The interesting design question is bounding HOW stale: cap it with a "last synced at" timestamp shown to store ops staff, and/or a maximum acceptable offline duration after which the store manager is alerted to intervene manually (file 0010 covers the WAN-down operating mode in full).

3. Store → Central: the outbox pattern

Sale completes at till │ ▼ Store-Sync Service writes event to LOCAL outbox table (same local transaction as the sale itself — atomic, survives a reboot) │ ▼ Background process reads outbox, attempts to publish to Azure Service Bus │ ├─ WAN up: publish succeeds → mark outbox row as sent │ └─ WAN down: publish fails → row stays pending, retried with backoff the STORE KEEPS SELLING regardless (file 0010) — the outbox just grows until connectivity returns

This is the standard outbox pattern: writing the "sale happened" fact and queuing the central-sync event happen in the same local transaction, so a crash between "sale recorded" and "event queued" can't happen — either both happened or neither did. Publishing to Service Bus is a separate, retryable step decoupled from the sale itself, which is exactly what makes the store's checkout flow independent of WAN health.

Idempotency — a detail worth having ready A retried publish after a flaky reconnect could send the same event twice. Central's consumer must dedupe by an idempotency key (e.g. a UUID generated when the outbox row is first written, not regenerated per retry) — otherwise a single sale could get double-counted in central reporting/stock decrement. This is the same idempotency-key pattern used anywhere "at-least-once delivery + a system that must behave exactly-once" meet — worth naming by name if asked, since it signals you've hit this class of problem before, not just this specific scenario.

4. Transport choice: Service Bus vs Event Hubs

OptionFit
Azure Service Bus (queue/topic)Recommended for this sync path — ordered delivery per store, reliable at-least-once, dead-letter queue for poison messages, moderate volume (sales events, not high-frequency telemetry)
Azure Event HubsBetter fit for pure high-throughput streaming — if this were also carrying, say, fine-grained clickstream/telemetry data at much higher volume, Event Hubs' partition-based consumer-group model would be the right pick instead. Worth naming as the alternative and why it loses here (this sync doesn't need that throughput, but DOES need the reliable delivery guarantees Service Bus gives more directly)

5. Why local stock accuracy and central stock accuracy have different bars

A subtlety worth stating explicitly if probed: a store's OWN local stock count must be accurate in real time locally, because the checkout can't sell what the shelf doesn't have and the local Inventory Service is the thing preventing that. But CENTRAL's aggregate view across all 3,000 stores can lag by minutes without real business harm — a warehouse replenishment decision made on 5-minute-old aggregate stock data is fine; a single till selling based on 5-minute-old LOCAL stock data risks overselling an already-empty shelf. Same word ("stock accuracy"), two different consistency requirements depending on which system is asking.
