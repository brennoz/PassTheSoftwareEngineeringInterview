K8s/Azure Infrastructure Topology

Tesco Interview Prep · Tier 2 — Worked Example · File 8 of 12

Zooming out from individual services to the full infra picture: central AKS, the store-edge fleet, and — the genuinely hard part of this domain — how you deploy and observe configuration across thousands of independently-running edge clusters without either a central bottleneck or losing visibility into which store is running what.

1. Central AKS

ConcernChoiceWhy
Cluster topologyMulti-AZ within a region, one primary region + a warm secondary for DRA single-AZ central outage would be a genuinely bad failure mode given every store's sync path depends on central being reachable eventually — file 0010 covers exactly how bad
IngressAzure Application Gateway Ingress Controller (or Azure Front Door if central serves any public-facing traffic too)WAF capability at the edge of central, TLS termination, path-based routing to services
Namespace layoutOne namespace per bounded context (pricing, inventory, promotions, loyalty, reporting)Mirrors the service boundaries from file 0006 — RBAC and network policy naturally scope to the same boundary, no separate mental model needed
AutoscalingHPA per service on CPU/custom metric (e.g. queue depth for consumers), cluster autoscaler for node poolsCentral load is spikier than any single store (aggregates all 3,000 stores' sync traffic) — needs to breathe with trading patterns (Christmas Eve peak vs a quiet Tuesday)

3. Store connectivity — how a store actually reaches central

OptionTrade-off
Azure ExpressRoute per storeMost reliable, private, predictable latency — but expensive per site at ~3,000 locations; the "gold standard" answer if cost weren't a constraint
SD-WAN / site-to-site VPN over public internet, mTLS end to end (recommended default)Pragmatic middle ground — standard broadband/leased line per store, encrypted tunnel, far cheaper at fleet scale, and the whole design already assumes WAN can be unreliable (file 0007, 0010), so it doesn't need ExpressRoute-grade guarantees to work correctly
The framing that ties this together Because every store-edge service except Store-Sync is designed to tolerate WAN loss (file 0003's boundary rule), the connectivity choice becomes a cost/reliability trade-off rather than a correctness requirement — a cheaper, less reliable link is an acceptable choice specifically BECAUSE the architecture was already built to not depend on it being perfect. That's worth saying explicitly: it shows the infra decision follows from the application design, not the other way around.
