Reusable Azure CI/CD Template

Tesco Interview Prep · Tier 1 — Transferable Method · File 2 of 12

The prompt says: "you may be asked to go into more detail and provide some examples of CI/CD." That's not a maybe — treat it as guaranteed. The goal of this file is a pipeline shape you can sketch and narrate in under 15 minutes for any system you've just designed, not something invented live under pressure.

1. The generic pipeline skeleton

Developer pushes to feature branch │ ▼ [CI trigger: Azure DevOps Pipelines / GitHub Actions] │ ├─► Build (compile, e.g. Maven for Spring Boot) ├─► Unit + integration tests ├─► Static analysis / dependency scan (SonarQube, Dependabot/Snyk) │ ▼ [Build container image] ──► [Push to Azure Container Registry (ACR)] │ ▼ Merge to main triggers CD │ ▼ [CD: deploy to AKS — dev → staging → prod, gated] │ ├─► dev: auto-deploy on every merge ├─► staging: auto-deploy + smoke tests, mirrors prod config └─► prod: manual approval gate, then progressive rollout (rolling update / canary — Section 4) │ ▼ [Azure Monitor / Application Insights] watches error rate, latency │ └─► breach threshold → automatic or one-click rollback (Section 5)

This is the skeleton regardless of what you designed in the previous 70 minutes. What changes per-system is which services get their own pipeline (one per bounded context, same boundary as your microservices — never one pipeline building everything), and how aggressive the rollout gating needs to be (a payment service warrants stricter gates than an internal reporting service).

3. Environments and promotion

Three environments is the standard default and defensible without over-explaining: dev (auto-deploy every merge, fast feedback, expect breakage), staging (mirrors prod configuration and scale ratio, runs smoke/contract tests, this is where you'd catch a config drift before it reaches real stores), prod (manual approval gate — a human decides when, even if everything upstream is green).

Trunk-based vs long-lived branches Default to trunk-based development with short-lived feature branches merged behind feature flags, not long-lived develop/release branches. It's the more senior-signalling answer, and it sidesteps a common follow-up trap ("how do you handle a hotfix while a release branch is in flight?") that long-lived branching strategies invite.

4. Deployment strategy — and the fleet-rollout problem specific to this domain

For a single-cluster service, standard AKS rolling update (readiness probes gate traffic cutover, maxUnavailable/maxSurge control pace) is enough to mention, with canary (Argo Rollouts or Flagger) as the upgrade if you want zero-risk progressive traffic shift for something high-stakes like a payment service.

But the Tesco-store domain has a genuinely harder version of this problem, worth raising proactively if your design includes an edge cluster per store (file 0004, 0008): you're not deploying to one cluster, you're deploying to a fleet of thousands. A central CI/CD pipeline trying to kubectl apply against 3,000 store clusters synchronously is fragile — one flaky store network connection blocks or half-completes the whole rollout.

Push-based (naive, doesn't scale to a fleet): [CD pipeline] ──kubectl apply──► Store 1 ──kubectl apply──► Store 2 ──kubectl apply──► Store 3,000 ← one bad connection stalls the batch Pull-based GitOps (Flux/Argo CD, scales to a fleet): [Git repo: desired state per store-group] ▲ │ each store's agent polls independently, on its own schedule │ Store 1 agent Store 2 agent Store 3,000 agent (pulls when (pulls when (pulls when ready, retries ready) ready — one store's on its own) outage doesn't block others)

With GitOps, each store-edge cluster runs a lightweight agent that pulls its desired config from Git on its own schedule and reconciles continuously — rather than a central system pushing to thousands of targets and needing all of them reachable at once. A staged rollout then becomes a Git-level concept: merge the new version to a "canary store group" branch/path first (e.g. 10 pilot stores), watch Azure Monitor for a defined bake period, then promote the same config to the next ring (a region), then all stores — the same progressive-rollout idea as canary deployment, just expressed at fleet scale instead of pod-replica scale.

5. Rollback strategy

TriggerResponse
Automatic — error rate / latency SLO breach detected by Azure Monitor during a canary bake windowAutomatic halt + revert to previous Git-tracked state (GitOps makes this a revert commit, not a manual kubectl rollback)
Manual — human notices an issue post-rollouthelm rollback or Git revert + re-sync; both are fast because the previous known-good state is already versioned, not reconstructed by hand
Store-specific issue (one store misbehaving, not a systemic bug)Roll back just that store's ring/group in the fleet model — this is exactly why per-store-group Git paths matter, so a bad rollout doesn't force an all-or-nothing revert across every store

6. The 90-second verbal answer

Say roughly this when asked "walk me through CI/CD for this" "Each service gets its own pipeline, one per bounded context. On push: build, test, static analysis, then a container image gets built and pushed to Azure Container Registry. Merge to main promotes through dev, then staging with smoke tests, then prod behind a manual approval gate. In prod I'd use a progressive rollout — canary or rolling update depending on how risk-sensitive the service is — gated by Azure Monitor watching error rate and latency, with automatic rollback on breach. [If the design has a store-edge fleet:] Because this isn't one cluster but potentially thousands of store clusters, I'd switch the deployment mechanism from push to pull — GitOps with Flux or Argo CD, so each store pulls its own config independently and one store's network issue doesn't stall the fleet. I'd roll a new version out to a small canary ring of stores first, bake it, then promote ring by ring."
