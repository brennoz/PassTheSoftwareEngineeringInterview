WebSockets Deep-Dive: Cashier Terminal ↔ POS Pod

Tesco Interview Prep · Tier 2 — Worked Example · File 5 of 12

The recalled hint was "heavy use of WebSockets." This file works out what that most plausibly means at the till, and — importantly — why the scaling story here is NOT the usual "millions of concurrent WebSocket connections" problem most system-design prep covers. That distinction is worth making explicit if it comes up, because it changes the right answer.

1. Why WebSocket over the alternatives, for THIS connection specifically

OptionWhy it loses here
REST polling (till polls POS pod every N ms for price/promo/stock updates)Either too slow (polling interval becomes checkout latency) or wasteful (polling fast enough to feel instant means near-continuous HTTP overhead for mostly-empty responses)
Server-Sent Events (SSE)One-directional (server→client only). The till needs to both push events (item scanned, payment initiated) AND receive pushes (price response, promo applied, "card declined") — SSE would need a second channel (HTTP POST) for the client→server direction, adding complexity WebSocket avoids with one connection
gRPC streamingViable alternative, genuinely — but WebSocket has simpler browser/kiosk-client tooling if the till UI is a web-based kiosk app (common for POS), and Spring's native STOMP-over-WebSocket support (below) gives pub/sub topic semantics for free
The actual justification, stated plainly A checkout needs low-latency, bidirectional, server-push-capable communication between the till and the local POS pod: scan an item → server looks up price/promo → pushes the result back → till updates the display, all without the till polling. WebSocket is the natural fit for exactly this shape of interaction, and it's a single persistent connection instead of a new HTTP request per scan.

2. Why this is NOT the "scale to millions of connections" problem

Most system-design material that covers WebSockets (chat apps, live sports odds, social feeds) focuses on the hard problem of sharding connection state across many WebSocket server instances, because a single popular server might need to hold millions of concurrent connections. That problem doesn't exist here, and saying so explicitly is a stronger answer than silently reciting a sharding strategy that doesn't apply:

  • A store has roughly 20–80 terminals (tills + self-checkouts) — file 0011 works the number out properly.
  • Every terminal in a store connects to that store's own local POS pod, not a shared central WebSocket server. Connection count per pod is in the dozens, not thousands or millions.
  • There is no cross-store connection sharing to worry about — Store A's tills never talk to Store B's POS pod. The "fleet" scaling problem (file 0002, 0008) is about deploying and managing 3,000 independent small pods, not about any single pod handling huge fan-out.
Where the real scale problem actually lives If asked "how does this scale," the honest answer redirects to the store-to-central sync path (file 0007) and the fleet deployment/observability story (file 0008) — that's where thousands-of-stores scale genuinely bites. The WebSocket layer itself is small-scale by design, precisely because it never leaves the store.

3. Connection lifecycle

Till boots │ ▼ Connect to LOCAL POS pod (never central — file 0003's boundary rule) │ ▼ Auth handshake — per-terminal token (issued at store setup, not per-session login) │ ▼ Subscribe to till-specific topic: /topic/till/{tillId}/* │ ▼ Heartbeat/ping-pong every ~10s (detects a silently-dead connection faster than TCP timeouts would) │ ├─ Connection drops (Wi-Fi hiccup, pod restart during a rolling update) │ │ │ ▼ │ Exponential backoff reconnect (1s, 2s, 4s... capped) │ │ │ ▼ │ Resume: re-subscribe, POS pod returns current basket state for that │ till (basket lives server-side, keyed by tillId — see Section 5) │ │ │ ▼ │ Till UI re-renders from server state — cashier sees no data loss, │ at most a brief "reconnecting" flicker │ ▼ Till shuts down / end of day → clean disconnect
Why basket state lives server-side, not just in the till's browser/kiosk memory If the till is "just a display" and the POS pod is the source of truth for basket state, a till reboot or browser crash mid-transaction is recoverable — reconnect, re-subscribe, get the basket back. If basket state lived only in the till's local memory, a crash mid-scan loses the whole transaction and forces a manual re-scan of everything, which is exactly the kind of visible, embarrassing failure a checkout system can't afford during a busy period.

4. Spring implementation shape — STOMP over WebSocket

Raw @ServerEndpoint WebSocket works, but Spring's STOMP-over-WebSocket support (spring-boot-starter-websocket + @EnableWebSocketMessageBroker) gives topic-based pub/sub semantics for free — a message published to /topic/till/{tillId}/price-update only reaches subscribers of that topic, rather than every connected till on the pod. This also matches how real-world Spring Boot WebSocket systems are typically built in production, so it's a defensible, well-trodden choice to name rather than inventing a bespoke protocol. 

// Illustrative shape, not literal Tesco code
@Controller
public class PosSocketController {

    @MessageMapping("/till/{tillId}/scan")
    @SendTo("/topic/till/{tillId}/basket-update")
    public BasketUpdate handleScan(@DestinationVariable String tillId, ScanEvent event) {
        // look up price (local Pricing Service), apply promos, update basket state
        // server is the source of truth — see Section 3
    }
}

JSON payloads, not a binary format like protobuf — bandwidth is not the constraint on a store's local LAN, and JSON's debuggability (reading raw WebSocket frames during development/incident response) is worth more here than the marginal size savings binary encoding would give at this connection count.

5. Security, even on a "local" connection

Being on the store LAN doesn't mean trusting it unconditionally — a till is close to the payment path (file 0009), so defense in depth applies even for local traffic: TLS on the WebSocket connection (WSS, not plain WS) even though it never leaves the building, and a per-terminal auth token checked on connect rather than assuming "if you're on this network, you're a legitimate till."
