Invented prompt for this rehearsal — not what you'll actually be asked "Design a system for how a Tesco store handles checkout, pricing, and stock — bearing in mind stores need to keep operating even if there's a network issue." Phase 1 — Clarifying questions0–10 min

Work through file 0001 Section 2's four categories, don't just ask one and move on:

Before I start drawing — a few questions. First, scope: are we designing just the checkout/till flow, or also how stock and pricing get INTO the store from a central system?
Let's say end-to-end — checkout, and how it stays in sync with the rest of the business.
Got it. On scale — roughly how many stores and how many tills per store should I be designing for? I'll assume a large multi-format estate, a few thousand stores, if you don't have an exact number in mind.
That's a reasonable assumption, go with it.
And on availability — you mentioned network issues. Should the store be able to keep SELLING if it loses its connection to head office, or is some downtime acceptable?
It needs to keep selling. That's actually the interesting part of this problem.
That's a strong signal — it tells me I need local compute in the store, not everything calling a central API directly. Last one: is card payment processing in scope, or should I treat that as an external black box?
You can treat the actual card network as external, but I want to see how you'd integrate with it.
Understood. I'll design the integration point and treat the payment network itself as a third party. Let me quickly estimate scale, then I'll start drawing.
Phase 2 — Capacity estimation (spoken, condensed from file 0011)10–15 min
Quick back-of-envelope: say ~3,000 stores, ~20 tills each on average — that's tiny per-store load, maybe a fraction of a transaction per second per store at peak, so the store's own local hardware doesn't need to be powerful. But aggregated nationally, at say 5x peak multiplier over an average day, that's a few hundred transactions a second hitting whatever central system aggregates all stores — THAT's where I need to think about real throughput, not any individual store. That split is going to shape the whole design: keep the store simple and self-sufficient, put the interesting scaling problem centrally.
Phase 3 — High-level design (drawing, narrated)15–40 min

Draw in this order, narrating each addition before moving to the next box — don't draw silently:

  1. Client layer — a box for cashier terminals.
    These are the tills and self-checkouts — I'll treat them as thin clients.
  2. Local store box — a bounded rectangle labelled "store-edge."
    Because we said the store must keep selling offline, I'm putting a local compute layer here — not everything talks straight to the cloud.
  3. Services inside it — POS, Pricing (local cache), Inventory (local), Payment.
    Each of these is its own service — POS owns the checkout flow, Pricing and Inventory are local read caches synced from a central source of truth, Payment is deliberately isolated since it touches card data.
  4. The sync bridge — a Store-Sync box with a dashed/async arrow to a central box.
    This is the ONLY component allowed to assume the network is up — it queues events locally and syncs when it can, so nothing else in the store depends on connectivity.
  5. Central box — Central Pricing, Inventory/Warehouse, Reporting.
    Central holds the source of truth for pricing and aggregates stock/sales across every store — this is also where the interesting scale numbers from a minute ago actually apply.
  6. External payment gateway — dashed border, outside everything.
    Card processing goes to a certified external payment gateway — I want as little of my own system touching raw card data as possible, for PCI-DSS reasons.

Phase 4 — Deep dive (interviewer-driven, two rehearsed examples)40–70 min

Example A — resilience (pulling from files 0007, 0010):

Tell me more about what actually happens if a store loses internet mid-trading day.
Nothing customer-facing breaks immediately — every service in the store box except Store-Sync was deliberately designed to not depend on that link. Checkout keeps working off the local price and stock cache. What DOES happen: Store-Sync can't publish its outbox anymore, so pending sale events queue up locally in a durable table — that's the outbox pattern, same transaction as the sale itself so nothing's lost. Card payments above a certain value might be affected since authorising those needs to reach an external gateway — that's really the one hard dependency. When the link comes back, Store-Sync drains the queue oldest-first, and the store does a full price resync rather than trying to replay potentially thousands of incremental changes, since that's simpler to reason about for correctness.

Example B — protocol design (pulling from file 0005):

Walk me through the actual protocol between a till and the local server.
WebSocket, not REST polling, because it needs to be bidirectional and low-latency — the till sends a scan event, the server pushes back a price/promo result without the till having to ask again. I'd use Spring's STOMP support over WebSocket specifically because it gives topic-based pub/sub for free — each till subscribes to its own topic so messages don't fan out to every connected till. On reconnect after a drop, the till re-subscribes and the server replays current basket state, because I'd keep basket state server-side precisely so a till crash mid-transaction doesn't lose the whole basket.
Phase 5 — CI/CD (condensed from file 0002)70–85 min
Can you give me an example of CI/CD for this?
Each service gets its own pipeline. On push: build, test, static analysis, then a container image goes to Azure Container Registry. Merge to main promotes through dev, staging, then a gated prod rollout. Here's the part specific to this domain: I'm not deploying to one cluster, potentially thousands of store clusters, so a central pipeline pushing to all of them synchronously doesn't scale well — one flaky store shouldn't stall the rollout. I'd switch to GitOps for that leg: each store's cluster pulls its own desired config independently via Flux, registered centrally through Azure Arc. I'd roll a new version to a small canary group of stores first, watch error rate for a bake period, then promote ring by ring — pilot stores, then a region, then everywhere.
Phase 6 — Wrap-up85–90 min
To summarise the key trade-offs: I chose local-first store compute over pure cloud-native for availability during network issues, at the cost of more operational complexity managing a fleet of edge clusters instead of one central system. I isolated payment into its own service specifically to shrink PCI-DSS scope. And I used a pull-based GitOps deployment model instead of push specifically because of the fleet scale, not because it's always the right default. With more time I'd want to dig into the offline card-payment story more — that edge case is genuinely partly a commercial/compliance question, not purely technical, and I'd want real numbers from Tesco's actual outage history before committing to a specific single-node-per-store hardware decision.
