Failure Modes & Resilience

Tesco Interview Prep · Tier 2 — Worked Example · File 10 of 12

This file is the reference answer to "what happens when X breaks" for every X raised so far in the folder — consolidated in one place because a live interview will very likely probe at least one of these, and having the blast radius memorised beats re-deriving it live.

1. Blast-radius table

FailureWhat stops workingWhat KEEPS working
WAN link down (store ↔ central) Price/promo updates stop arriving; card payments above the issuer floor limit (file 0009); central reporting for this store goes stale Everything else — checkout, local stock, cash/gift-card payments, till WebSocket sessions — all untouched, because they never depended on the WAN link (file 0003's boundary rule)
Single store-edge pod crashes (e.g. Pricing Service) That pod's function only, for the seconds it takes K8s to restart it (liveness probe failure → restart) Other pods on the same node — POS, Inventory, Payment — keep serving. K8s readiness probes stop routing traffic to the crashed pod specifically, not the whole node
Whole edge box hardware failure The entire store's local layer — tills fall back to a documented manual/paper contingency procedure until a replacement box is installed Every OTHER store — this is single-store blast radius by design (file 0004's single-node trade-off, accepted explicitly)
One till/terminal fails That till only — cashier moves the queue to another till Every other till at the same store, since each WebSocket session is independent (file 0005)
Central AKS outage/degradation Price/promo propagation stalls fleet-wide; cross-store reporting/analytics stalls; new fleet rollouts pause Every store's actual checkout operation — the whole point of the edge architecture is that stores don't need central to sell
External card payment gateway outage Card payments fleet-wide (this is genuinely outside Tesco's control) Cash and gift-card/loyalty-balance payments; everything non-payment-related
The pattern across every row Every failure in this table has a bounded, named blast radius — nothing cascades into "the whole estate is down." That's not an accident; it's the direct, provable consequence of the design decisions made earlier in this folder (local-first store-edge, single-writer sync, per-pod isolation, per-store hardware isolation). If asked "what's your availability story," pointing at this table row by row IS the answer — it's more convincing than quoting an abstract uptime percentage.

2. Recovering from a WAN outage — the reconnect sequence

WAN link restored │ ▼ Store-Sync Service resumes draining its outbox (file 0007) — oldest events first, preserving order per store │ ▼ Store pulls latest price/promo state from central (may be a full resync if the outage was long, not just a replay of missed deltas — simpler to reason about correctness than trying to replay a potentially huge backlog of incremental price-change events) │ ▼ Staleness indicator (last-synced timestamp) clears once caught up │ ▼ Store manager alert (if one was raised during the outage) resolves

3. Zero-touch recovery for a replaced edge box

A concrete payoff of the GitOps/Arc investment from files 0002 and 0008: when a failed edge box is physically replaced, the new hardware registers with Azure Arc and its local Flux agent pulls the exact desired-state configuration for that store from Git — no manual reinstall runbook, no "which version should this store be on" guesswork. The same mechanism that makes fleet-wide rollouts safe (ring-based promotion, file 0008) also makes single-store disaster recovery close to automatic once the physical hardware problem is fixed.

4. Circuit breakers on the calls that DO cross service boundaries

POS → Pricing, POS → Payment are synchronous calls inside the same edge cluster (file 0006). Even at sub-millisecond intra-cluster latency, a hung dependency shouldn't be allowed to hang the caller indefinitely — a circuit breaker (Resilience4j is the standard Spring Boot choice) with a short timeout and a defined fallback (e.g. Pricing Service unreachable → POS falls back to its own last-known-good local price cache rather than blocking the checkout entirely) keeps one degraded service from taking down the till experience with it.
