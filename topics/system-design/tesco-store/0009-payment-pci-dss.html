Payment & PCI-DSS

Tesco Interview Prep · Tier 2 — Worked Example · File 9 of 12

Not a recalled hint — this file exists because any real retail POS design has to address it, and an interviewer probing "go into more detail" would very plausibly land here given payment is the highest-stakes flow in the whole system.

1. The core principle: minimise PCI-DSS scope, don't just secure everything

The naive instinct is "encrypt everything, lock down everything." The stronger answer is narrower: PCI-DSS compliance cost and audit burden scale with how many systems touch raw card data (the PAN — Primary Account Number). The actual architectural goal is making that set of systems as small as possible, so the rest of the estate (POS, Inventory, Pricing, central reporting) never falls in scope at all.

2. Payment flow, and where tokenisation happens

Card presented at terminal (chip/contactless reader) │ ▼ Card reader hardware performs P2PE (point-to-point encryption) — raw PAN is encrypted at the physical reader, before it ever reaches any Tesco-operated software │ ▼ Payment Service pod receives the ENCRYPTED payload (never plaintext PAN) │ ▼ Forwards to external Payment Gateway (a PCI Level 1 certified processor) │ ▼ Gateway decrypts, authorises against the card network, returns: - approved / declined - a TOKEN representing this card (safe to store, useless if stolen) - last 4 digits (for the receipt) │ ▼ Payment Service relays ONLY {status, token, last4} back to POS pod │ ▼ POS pod updates basket/receipt — never sees, stores, or logs raw PAN
Why this shrinks PCI scope so much Because the card reader hardware encrypts at the point of capture (P2PE) and the gateway handles the actual decrypt+authorise, the ONLY Tesco-operated system that ever handles anything payment-related is the Payment Service pod — and even it only ever sees an encrypted blob going out and a token coming back, never plaintext PAN. POS, Inventory, Pricing, Store-Sync, and everything central are entirely out of PCI-DSS scope. This is the single highest-leverage decision in the whole payment design.

3. Network isolation at the store

Even though Payment Service never sees raw card data, defense in depth still applies — isolate it anyway, on the assumption that a design decision today doesn't guarantee no future engineer ever accidentally logs something sensitive.

ControlEffect
Kubernetes NetworkPolicy restricting ingress to Payment podOnly POS Service is allowed to call it — Pricing, Inventory, Store-Sync have no network path to Payment at all, even though they're on the same cluster
Separate physical/VLAN segmentation for card-reader traffic where feasibleThe card reader's own network path to the Payment pod is isolated from general store Wi-Fi/LAN traffic — reduces the blast radius if the general store network were ever compromised
No egress from Payment pod except to the certified gateway's known endpointsEven if compromised, the pod can't exfiltrate data anywhere except the one allow-listed destination

4. Logging discipline

A PCI-DSS requirement worth naming specifically, since it's a common real-world audit failure: Payment Service logs must NEVER contain PAN or CVV, even at debug level. Structured logging with an explicit allow-list of loggable fields (token, last4, status, amount, not the whole request object dumped wholesale) is the safe default — a generic log.debug(request) on a payment request object is exactly the kind of thing that silently leaks sensitive data into log aggregation systems that then themselves fall into PCI scope.

5. Honest limitation: payment during a WAN outage

Where to be honest about the edge of your design, rather than overclaiming File 0007/0010 establish that the store keeps SELLING during a WAN outage — but authorising a CARD payment specifically requires reaching the external gateway, which requires connectivity. Real payment terminals handle this via issuer-negotiated "store-and-forward" offline authorization for small amounts under a risk-managed floor limit — a specialised arrangement between the merchant, acquirer, and card networks, not something a from-scratch system design invents cleanly in an interview. The honest answer: "cash and any already-loaded gift-card/loyalty balance would still work offline; card payments above an issuer-agreed floor limit would need to queue or be declined until connectivity returns — the exact offline-authorization arrangement is a commercial/compliance negotiation with the payment processor, not purely an engineering decision." Naming that boundary honestly is stronger than inventing a fake technical solution to a problem that's actually partly-commercial.
