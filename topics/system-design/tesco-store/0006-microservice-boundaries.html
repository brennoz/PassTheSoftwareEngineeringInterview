Microservice Boundaries (Spring Boot)

Tesco Interview Prep · Tier 2 — Worked Example · File 6 of 12

File 0003 listed the services; this file justifies why they're split THAT way rather than some other way, and how they're built internally. "Microservices with Spring Boot" was one of the recalled hints — worth being ready to talk concretely about what that means beyond the name.

1. The boundary rule: bounded contexts, not technical layers

Each service boundary in file 0003 maps to a distinct business capability with its own data and its own reason to change independently — POS (checkout flow), Pricing, Inventory, Payment, Store-Sync. None of them are split by technical layer ("the database service", "the API service") — that's the classic anti-pattern this boundary rule explicitly avoids, since a layer-based split means almost every feature change touches multiple services anyway, which defeats the point of splitting at all.

The concrete test for "should this be its own service" Does it own data nothing else should directly touch, and does it change for a different reason than its neighbours? Payment changes when card-scheme/PCI requirements change. Pricing changes when the promotions team ships a new campaign. Those are different rates of change driven by different stakeholders — a real signal they belong in different services, not just a theoretical DDD exercise.

2. Internal shape of a store-edge service

Standard layered architecture inside each Spring Boot service — the same shape real production Spring Boot systems use, not something invented for this exercise:

Controller layer REST controllers (service-to-service calls) + WebSocket/@MessageMapping handlers (POS only, file 0005) │ ▼ Service layer Business logic — price calculation, promo application, stock decrement Owns the transaction boundary │ ▼ Repository layer Spring Data JPA (or JDBC for the smallest services) against this service's OWN schema only — never another service's tables

Data ownership at edge scale — a pragmatic compromise worth naming

"Pure" microservices usually means one database instance per service. On a resource-limited edge box running four or five small services, running five separate Postgres processes is wasteful for the actual data volume involved (one store's worth of stock/price cache is small). The pragmatic answer: one Postgres instance per store, one schema per service, with the ownership rule enforced in code, not by physical database separation — each service's repository layer only ever queries its own schema; no service is allowed to write SQL against another's tables, even though they're technically reachable on the same instance.

Be ready to defend this if pushed This is a genuine trade-off, not a free lunch — a determined future engineer COULD write a cross-schema join and quietly break the boundary, since the database itself doesn't enforce it the way separate instances would. The mitigation is discipline (code review, service accounts scoped per-schema if the DB engine supports it) rather than physical impossibility. Naming that honestly, rather than presenting it as risk-free, is the stronger answer.

3. Inter-service communication within the store

POS pod calling Pricing pod, or Pricing pod calling Inventory pod, all happen inside the same store-edge cluster — plain synchronous REST (or gRPC if you want stronger typed contracts), not WebSocket. WebSocket in this design is specifically the device-facing protocol (till ↔ POS pod, file 0005); pod-to-pod calls inside the cluster are ordinary short-lived HTTP calls over the cluster's internal network, since there's no need for a persistent connection or server-push semantics between two services that are both always co-located and reachable with single-digit-millisecond latency.

4. Why not split further, and why not merge

TemptationWhy resist it
Split Pricing further (e.g. separate "product pricing" vs "promo pricing" services)Nanoservice smell — at this scale (one store, small data volume) the extra network hop and deployment unit buys nothing; promo application is a query concern within Pricing, not a separate capability with its own stakeholders
Merge everything into one edge monolith podLoses independent restart/rollback (a Pricing bug shouldn't force a Payment pod restart), and specifically breaks the PCI-DSS isolation argument in file 0009 — Payment needs to be a separately network-policy-scoped workload, which requires it to be its own deployable

5. Central services differ — briefly

Central (file 0008) runs on real AKS with elastic compute, so the "keep it small, share a Postgres instance" compromise from Section 2 doesn't apply there — central services can each get their own dedicated datastore (and even different engines per service — Cosmos DB for the loyalty ledger's flexible schema, Azure SQL for structured warehouse data — true polyglot persistence), since resource constraints aren't the limiting factor centrally the way they are on a single edge box.
