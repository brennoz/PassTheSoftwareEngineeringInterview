Store-Edge Architecture

Tesco Interview Prep · Tier 2 — Worked Example · File 4 of 12

File 0003 established WHY a per-store edge cluster exists. This file goes into WHAT it actually is: the physical/logical stack running on "the machine in each store" the recalled hint referred to, and the choices that make a fleet of ~3,000 of them manageable rather than ~3,000 individual snowflakes.

1. Edge Kubernetes flavour — the actual decision

OptionFit for a single storeTrade-off
K3s (Rancher's lightweight, CNCF-certified K8s distro) Strong fit — single binary, ~512MB RAM footprint, designed for exactly this "edge/single-node" use case Not a managed Azure product itself — you register it into Azure's control plane via Arc separately (below) rather than getting fleet management for free
Azure IoT Edge Weaker fit — built around IoT device/module patterns (telemetry, device twins), not general-purpose stateless microservices Would fight the abstraction to run Spring Boot services as generic containers rather than IoT modules
Full AKS at the edge (Azure Stack / AKS Edge Essentials) Overkill for one store — AKS's control-plane overhead assumes a cluster with multiple nodes worth managing Higher resource cost per store for capability a single store doesn't need
Recommendation: K3s per store, fleet-managed via Azure Arc Run lightweight K3s locally for the actual workload, and register every store's cluster into Azure Arc-enabled Kubernetes — Arc gives you a single pane of glass in Azure for policy, monitoring, and GitOps config delivery across the whole fleet, without requiring the workload itself to run on "real" AKS. This is also what makes file 0002's GitOps fleet-rollout story (Flux via Arc) concrete rather than hand-wavy — Arc is the actual mechanism that lets a central Git repo drive config into thousands of independently-running K3s clusters.

3. Single-node vs redundant edge nodes — an assumption worth stating out loud

A real system-design decision, not a detail to skip: does each store get ONE edge box, or two for redundancy? This is exactly the kind of trade-off file 0001 says to surface explicitly rather than silently picking one.

OptionArgument forArgument against
Single node per storeCheaper (~3,000× the hardware cost of a second box adds up fast); a whole-store outage (power, till network) already takes the store down regardless of node count, so a second K8s node doesn't remove the real single point of failureA single box failure (not power/network, just the machine dying) takes the whole store's local layer down until it's replaced
Two nodes, active/passive or K3s HA modeSurvives a single hardware failure without a store visitDoubles edge hardware cost across the whole estate; added complexity (leader election, data replication) for a failure mode that's rare relative to power/network outages
Reasonable interview answer either way — the point is justifying it "I'd start with a single node per store, because the dominant failure mode for a shop (power cut, WAN drop) takes the whole store down regardless of node count, and doubling ~3,000 stores' worth of edge hardware for a comparatively rare pure-hardware failure isn't obviously worth it — though if Tesco's own outage data showed hardware failure was a bigger driver than I'd expect, I'd revisit that." Stating the reasoning, and that you'd revisit it given real data, matters more than which option you pick.

4. Resource discipline — why heavy services stay central

An edge box is deliberately small. That constrains what can run there: only the services that need to survive a WAN outage (file 0003's boundary rule) belong at the edge; everything else — reporting, analytics, the promotions rules engine, loyalty ledger — stays central, where compute is elastic and cheap. Container image size discipline matters more here than in a typical cloud deployment: a bloated image is a slow store-boot and a slow rollout across a fleet where bandwidth per store may be modest.
