Lesson 01 — Design Twitter

Category: System Design · Difficulty: Hard · Est. time: 25 min

Twitter is one of the most common hard system design questions. The central challenge is feed generation at scale: how do 300M users see a personalised timeline in under 200ms when a single celebrity tweet must reach 100M followers?

After this lesson you can: Explain fan-out on write vs fan-out on read, justify the hybrid approach for celebrities, design the timeline storage with Redis Sorted Sets, and map every component to AWS.

3. Data model

Tweets — Cassandra

-- Cassandra: write-heavy, time-series, wide rows, no joins needed
-- Partition key = user_id → all tweets by one user on one node
CREATE TABLE tweets (
    user_id    UUID,
    tweet_id   BIGINT,      -- Snowflake ID: encodes timestamp, sortable
    content    TEXT,
    media_url  TEXT,
    like_count COUNTER,
    created_at TIMESTAMP,
    PRIMARY KEY (user_id, tweet_id)
) WITH CLUSTERING ORDER BY (tweet_id DESC);
Why Cassandra, not PostgreSQL? 500M writes/day. Cassandra: tunable consistency, linear horizontal scale, append-only writes at O(1). PostgreSQL: vertical scale limit, index maintenance overhead on billions of rows, cross-shard complexity. Trade-off: Cassandra has no joins, no transactions — acceptable here since tweets are independent records.

Social graph — PostgreSQL or dedicated graph store

-- Follow relationship = directed edge. Simple adjacency list in Postgres works up to ~1B edges.
CREATE TABLE follows (
    follower_id  UUID NOT NULL,
    followee_id  UUID NOT NULL,
    created_at   TIMESTAMPTZ DEFAULT now(),
    PRIMARY KEY (follower_id, followee_id)
);
CREATE INDEX idx_follows_followee ON follows(followee_id);  -- "who follows X?"

Timeline — Redis Sorted Set per user

-- Key: timeline:{user_id}
-- Score: tweet_id (Snowflake — numerically encodes time, so ZRANGE gives chronological order)
-- Value: tweet_id (look up full tweet from Cassandra on render)

ZADD timeline:user123  1718000001  tweet_id_A
ZADD timeline:user123  1718000002  tweet_id_B

-- Serve timeline: newest 20 tweets
ZREVRANGE timeline:user123 0 19

-- Cap at 800 — remove oldest when exceeded
ZREMRANGEBYRANK timeline:user123 0 -801

4. Feed generation — the central design decision

Option A: Fan-out on Write (Push model)

Alice posts tweet │ ▼ Kafka topic: "new-tweets" │ ▼ Fan-out Workers (consumers) │ ├──► ZADD timeline:bob score=tweet_id (Bob follows Alice) ├──► ZADD timeline:carol score=tweet_id └──► ZADD timeline:dave score=tweet_id ... (one write per follower)
Fan-out on Write
Read latency✅ O(1) — timeline pre-built in Redis
Write cost❌ O(followers) writes per tweet
Celebrity problem❌ 100M followers × 1 tweet = 100M Redis writes → minutes of lag
Best forNormal users (≤ ~10K followers)

Option B: Fan-out on Read (Pull model)

Bob opens timeline │ ▼ Feed Service │ ├── SELECT followee_ids FROM follows WHERE follower_id = bob ├── For each followee: fetch latest tweets from Cassandra └── Merge + sort + return top 20
Fan-out on Read
Read latency❌ O(following_count × tweet_lookup) — slow, many Cassandra reads
Write cost✅ Zero — tweet stored once
Best forCelebrities (write once, read by many)

✅ Hybrid approach — what real Twitter uses

Alice posts tweet │ ├─ Alice has ≤ 10K followers? │ │ │ ▼ YES → Fan-out on Write → push to all follower Redis timelines │ └─ Alice is a celebrity (> 10K followers)? │ ▼ NO PUSH — tweet stored in Cassandra only Bob opens timeline │ ▼ Feed Service │ ├─ 1. Fetch Bob's pre-built Redis timeline (fan-out on write results) ├─ 2. Fetch latest tweets from Bob's celebrity followees (fan-out on read) └─ 3. Merge + deduplicate + sort → return top N
Celebrity threshold Typically ~10K–50K followers. Users above threshold are flagged in the user table (is_celebrity = true). Fan-out worker skips them; Feed Service handles them at read time. This is a configuration trade-off: lower threshold = more Redis writes, lower read latency; higher threshold = fewer writes, higher read latency for celebrity content.

5. Snowflake ID — why not UUID for tweet IDs

-- Snowflake: 64-bit integer
-- Bits: [timestamp 41] [datacenter 5] [machine 5] [sequence 12]
-- Encodes creation time → sortable by ID alone (no separate created_at index needed)
-- 4096 unique IDs per millisecond per machine

-- Redis sorted set score = tweet_id → chronological order for free
-- Cassandra clustering key = tweet_id DESC → newest-first for free
-- No UUID needed: UUIDs are random → scatter writes across Cassandra nodes → hot spots

7. Search and trending topics

Full-text tweet search — Elasticsearch

-- Tweet posted → Kafka → Search Indexer → Elasticsearch
-- Index: tweets { tweet_id, content, author_id, created_at, hashtags[] }
-- Query: full-text search on content + filter by date
-- Why not Cassandra for search? No full-text index. Cassandra = key/range lookup only.
-- Why Elasticsearch? Inverted index → O(1) term lookup regardless of corpus size.

Trending topics — sliding window + Redis Sorted Set

-- Every tweet published → extract hashtags → increment counter in Redis
-- Redis Sorted Set: key="trending", score=count, member=hashtag

ZINCRBY trending 1 "#WorldCup"    -- atomic increment
ZREVRANGE trending 0 9            -- top 10 hashtags

-- Problem: counts accumulate forever — need time decay
-- Solution: sliding window — bucket counts by minute, sum last 60 buckets
-- Key per minute: "trending:2026061512:34" (YYYYMMDDHHM)
-- TTL on each bucket: 61 minutes
-- Top trending = SUM of last 60 minute buckets for each hashtag

What breaks at scale without this design

  • Storing tweets in PostgreSQL → billions of rows → index scan latency, cross-shard JOINs
  • Fan-out on write for celebrities → 100M Redis writes per tweet → fan-out workers lag minutes behind
  • No Redis timeline cache → every feed load hits Cassandra for N followees → read storm
  • Media served from origin → no CDN → bandwidth saturated, global latency high
  • Single-region → AZ failure takes down all timelines → Multi-AZ ElastiCache + Aurora required

9. Retrieval quiz

Q1. Why is fan-out on write problematic for celebrity accounts (100M followers)?

  • A) Celebrity tweets are longer and require more storage per fan-out operation
  • B) One celebrity tweet triggers 100M Redis writes — fan-out workers lag far behind real-time; timeline updates take minutes not milliseconds
  • C) Redis Sorted Sets cannot hold more than 10M members per key
  • D) Fan-out on write requires a DB transaction per follower, which deadlocks at scale
O(followers) Redis writes per tweet. At 100M followers and even 100K writes/sec, one tweet takes 1000 seconds to propagate. The hybrid solution: don't push celebrity tweets at write time — merge them at read time from Cassandra instead.

Q2. Why use Cassandra for tweet storage instead of PostgreSQL?

  • A) Cassandra supports full-text search which PostgreSQL does not
  • B) PostgreSQL cannot store more than 1 billion rows
  • C) Tweets are append-only, require no joins, and need linear horizontal write scale — Cassandra's partition-per-user model gives O(1) writes and range reads without cross-node joins
  • D) Cassandra has ACID transactions making it safer for financial-grade tweet storage
PostgreSQL can store billions of rows but needs vertical scaling and complex sharding for 500M writes/day. Cassandra: partition key = user_id puts all tweets by one user on one node. Write = append to partition. Read recent tweets = range scan on one node. No joins, no cross-shard coordination. Trade-off: no transactions, no full-text search (that's Elasticsearch's job).

Q3. Why store tweet IDs (Snowflake IDs) in the Redis timeline sorted set rather than timestamps as the score?

  • A) Redis Sorted Sets only accept integer scores, not timestamps
  • B) Snowflake IDs are shorter and save memory in Redis
  • C) Timestamps are not unique — two tweets in the same millisecond would overwrite each other in the sorted set
  • D) Snowflake IDs encode the timestamp in their bits — so they sort chronologically by value, serve as unique identifiers, and are the key needed to fetch the full tweet from Cassandra — one field does three jobs
Snowflake ID: 41-bit timestamp prefix → numeric sort = chronological sort. Globally unique → no collision. Is the Cassandra lookup key. Using a separate timestamp score would require storing both the score and the tweet ID as separate fields, and two tweets at the same millisecond would have the same score — ambiguous sort order. Snowflake eliminates all three problems.

Q4. Bob follows 500 people: 490 normal users and 10 celebrities. How does the hybrid Feed Service build his timeline?

  • A) Fetch Bob's pre-built Redis timeline (tweets from 490 normal followees pushed at write time) + fetch latest tweets from 10 celebrity Cassandra partitions at read time → merge + sort → return top N
  • B) Fetch all 500 followees' latest tweets from Cassandra at read time and merge
  • C) Return only the Redis timeline — celebrities are excluded until their fan-out completes
  • D) Fan-out workers push celebrity tweets to a separate Redis key; Feed Service reads two sorted sets and merges
Hybrid: Redis gives O(1) access to normal-user tweets (already pushed). Celebrity tweets are pulled from Cassandra (one read per celebrity, bounded by following count). Merge is cheap — at most 10 Cassandra reads + one Redis read. Result: fast timeline with celebrity tweets included in real time. Option D would still require fan-out for celebrities, missing the point of the hybrid approach.
