Lesson 01 — Comment System Design

Category: System Design · Difficulty: Medium · Est. time: 20 min · Lesson 1 of N

Comment systems appear everywhere — YouTube, Reddit, Hacker News, blog platforms. They look simple but hide five hard problems: hierarchical storage, stable pagination, atomic like counters, read-heavy caching, and reply notifications at scale. This lesson covers each one with the tradeoff an interviewer expects you to articulate.

What you will be able to do after this lesson Given "design a comment system", produce a complete component diagram, justify every data model and storage choice, and explain what breaks at 10× load — in under 25 minutes.

1. Functional requirements (scope first)

Always state scope before touching components. Interviewers reward this habit.

In scopeOut of scope (state explicitly)
Post a comment on a resource (video, article, post)Real-time live updates (WebSocket)
Reply to a comment (one level of nesting minimum)Comment editing history / diffs
Like / dislike a commentMarkdown rendering (client concern)
Fetch comments with paginationFull-text search across comments
Notify author when their comment receives a replyCross-platform push (covered in Notification System)
Soft-delete (hide but retain for audit)

Scale assumptions to state: 100M DAUs, 10M comments/day written, 1B comment reads/day. Read:write ≈ 100:1. Comments per post follow a power law — top 1% of posts get 80% of comments.

2. Data model — the hard part

Nested comments are a tree. How you store a tree in a relational DB is the first decision interviewers probe.

Option A: Adjacency List

CREATE TABLE comments (
    id          BIGINT PRIMARY KEY,
    post_id     BIGINT NOT NULL,
    parent_id   BIGINT REFERENCES comments(id),  -- NULL = top-level
    author_id   BIGINT NOT NULL,
    body        TEXT NOT NULL,
    like_count  BIGINT DEFAULT 0,
    deleted     BOOLEAN DEFAULT FALSE,
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_comments_post_parent ON comments (post_id, parent_id, created_at);
Adjacency ListClosure Table
Write costO(1) — insert one rowO(depth) — insert ancestor rows
Read all descendantsRecursive CTE (slow for deep trees)Single JOIN — O(1)
Move subtreeUpdate one parent_idDelete + re-insert ancestor rows
Best forShallow nesting (Reddit: 2–3 levels max)Deep nesting (file systems, org charts)
Recommendation for interview Adjacency List + depth limit (e.g. max 3 levels). Most comment systems cap nesting. Mention Closure Table as the alternative for deep trees. Shows you know both.

3. Read path — pagination

Top-level comments for a post. 10K comments on a viral video. How to page through?

Why NOT offset pagination

-- BAD
SELECT * FROM comments WHERE post_id = 42 ORDER BY created_at LIMIT 20 OFFSET 200;
-- Problem 1: skips 200 rows on every DB node — O(N) work
-- Problem 2: new comment inserted at offset 50 → page 2 shows duplicate row

Cursor-based pagination

-- First page
SELECT * FROM comments
WHERE post_id = 42
ORDER BY created_at ASC, id ASC
LIMIT 21;   -- fetch 21, return 20 — 21st proves there's a next page

-- Next page: client sends back cursor = {created_at: '2026-01-15T10:23:00Z', id: 9001}
SELECT * FROM comments
WHERE post_id = 42
  AND (created_at, id) > ('2026-01-15T10:23:00Z', 9001)
ORDER BY created_at ASC, id ASC
LIMIT 21;

Cursor encodes position in the sorted order. New inserts don't shift positions. No skipped or duplicated rows. The compound (created_at, id) cursor handles the edge case where two comments arrive at the exact same millisecond.

4. Like counter — the race condition

-- BAD: read-modify-write in application code
long likes = commentRepo.findById(id).getLikeCount();   // read
commentRepo.update(id, likes + 1);                      // write — race!
-- Two concurrent requests both read 100, both write 101. One increment lost.

-- GOOD option 1: DB atomic increment
UPDATE comments SET like_count = like_count + 1 WHERE id = ?;
-- Serialised at DB level. Safe but hits DB on every like — expensive at scale.

-- GOOD option 2: Redis atomic counter + async flush
INCR comment:like:{commentId}          -- O(1), single-threaded Redis command
-- Background job flushes Redis counters → DB every 30s
-- Tradeoff: count may be slightly stale between flushes
Interview trap Using like_count + 1 in application code on a multi-replica service is a race condition that interviewers plant in code-review questions. Name it: optimistic lock or Redis INCR — never application-level read-modify-write.

5. Caching strategy

Read:write = 100:1. The top 1% of posts generate 80% of reads. Cache those threads aggressively.

Write path: Client → API → DB (write) → Redis DEL comment:page:{postId}:* ← invalidate cache Read path: Client → API → Redis GET comment:page:{postId}:{cursor} HIT → return cached page (TTL 60s) MISS → DB SELECT → Redis SET → return Cache key: comment:page:{postId}:{encodedCursor} TTL: 60 seconds (comments are mostly read-heavy, staleness acceptable)

Cache-Aside pattern. On write, invalidate all cached pages for that post (wildcard delete on Redis key prefix). On read, populate cache on miss. TTL of 60s means a write is visible within 1 minute even if invalidation fails.

6. Notifications — reply fan-out

When Alice replies to Bob's comment, Bob gets notified. At scale (celebrity post with 10K top-level comments), a single reply could trigger 10K notifications if you notify the whole thread. Scope it: notify only the direct parent comment's author.

Reply posted │ ▼ Comment Service → publishes ReplyEvent to Kafka topic: comment-events │ ┌───────────▼───────────┐ │ Notification Service │ │ (Kafka consumer) │ │ - look up parent │ │ author preference │ │ - send email / push │ └───────────────────────┘

Kafka decouples Comment Service from Notification Service. If notification is slow or down, comments still post. Kafka retains the event for retry.

Distributed failure modes to mention:

  • Redis down → fall through to DB; spike in DB load → add circuit breaker
  • Kafka consumer lag → notifications delayed, not lost (Kafka retains events)
  • Like counter flush fails → Redis and DB temporarily diverge; TTL on Redis key self-heals
  • DB write succeeds but Kafka publish fails → use Outbox Pattern (atomic write + event)

9. Retrieval quiz

Answer from memory — no scrolling.

Q1. Why is cursor-based pagination preferred over OFFSET for comments?

  • A) Cursor pagination requires fewer database indexes
  • B) OFFSET pagination only works with MongoDB, not PostgreSQL
  • C) Cursor pagination is simpler to implement on the client
  • D) OFFSET skips N rows on every query (expensive) and causes duplicates when new rows are inserted mid-page
OFFSET forces the DB to scan and discard N rows — O(N) cost that grows with page depth. Worse, a new comment inserted before your current offset shifts all subsequent rows, causing a row to appear on two consecutive pages. Cursor encodes a stable position in sorted order: no skips, no duplicates, O(log N) via index seek.

Q2. Why use Redis INCR for like counters instead of UPDATE comments SET like_count = like_count + 1?

  • A) Redis INCR is more accurate than a SQL UPDATE
  • B) At high like velocity, DB UPDATE on the same row creates lock contention; Redis INCR is atomic, single-threaded, and O(1) — no locking needed
  • C) PostgreSQL does not support atomic increments on BIGINT columns
  • D) Redis INCR automatically syncs the counter to the DB every second
Both SQL UPDATE and Redis INCR are atomic at their respective level. The difference is throughput. A DB row UPDATE acquires a row-level lock; 10,000 concurrent likes on a viral comment → 10,000 serialised lock acquisitions → bottleneck. Redis INCR is lock-free (single-threaded event loop) and handles millions of ops/sec. Async flush to DB every 30s trades perfect consistency for throughput.

Q3. A reply is posted. Kafka publish to comment-events fails, but the DB write succeeded. What pattern prevents the reply event from being permanently lost?

  • A) Retry the Kafka publish in a catch block with exponential backoff
  • B) Write the event to a dead-letter queue in SQS, then replay manually
  • C) Outbox Pattern — write the event row to an outbox table in the same DB transaction as the comment; a separate poller publishes to Kafka and marks it sent
  • D) Two-phase commit between the DB and Kafka broker
A catch-block retry still risks failure after the DB commits. 2PC with Kafka is not supported and introduces latency. The Outbox Pattern atomically co-locates the event with the business data in one DB transaction — if the comment lands, so does the outbox row. A poller (or Debezium CDC) publishes it reliably. This is the canonical distributed system answer for "DB write succeeded but event lost".

Q4. The comment cache is invalidated on write using a wildcard Redis key delete. What is the risk on a high-write post and how do you mitigate it?

  • A) Cache stampede — many readers hit the DB simultaneously after invalidation; mitigate with probabilistic early expiry or a distributed lock on cache population
  • B) Redis keyspace notifications are not supported for wildcard deletes
  • C) Wildcard deletes are O(N²) in Redis cluster mode and will crash the node
  • D) Write-through cache avoids this entirely — always write to cache and DB together
Cache stampede (thundering herd): invalidation clears the cache, then 1,000 concurrent readers all miss, all query the DB simultaneously, overloading it. Mitigations: (1) probabilistic early expiry — randomly refresh a small percentage of requests before TTL expires; (2) request coalescing — only one request rebuilds the cache while others wait; (3) short TTL instead of explicit invalidation — accept 60s of stale data. Write-through doesn't help here because it pre-populates one key, not all paginated pages.

🤖 AI Engineering Extension — Comment Moderation

Triggers: content moderation · spam detection. Classic implementation above is always the baseline. This section shows where an LLM integration changes the architecture.

Where AI fits

The write path. Before a comment is persisted to PostgreSQL, it passes through a Moderation Service that classifies it as safe / toxic / spam. Rule-based blocklists (regex, keyword lists) are fast but brittle — they miss context ("I want to kill this bug"), new slang, and multilingual abuse. An LLM classifier handles semantics a blocklist cannot.

Pattern — Classifier + Human-in-the-Loop

Comment write request │ ▼ Moderation Service │ ├─ STEP 1: Rule-based pre-filter (blocklist, regex) │ High-confidence block → reject immediately (free, <1ms) │ └─ STEP 2: LLM classifier (only if pre-filter passes) │ → score: [safe, toxic, spam, uncertain] │ ├─ score > 0.95 safe → write to DB, publish event ├─ score > 0.85 toxic → auto-reject, log for audit ├─ score > 0.80 spam → auto-reject, flag account └─ uncertain (0.4-0.80) → quarantine → Human Review Queue │ human reviewer approves / rejects

Architecture delta

New components added to the classic diagram:

  • Moderation Service — sits on the write path between API and DB
  • LLM Classifier API — Bedrock / Comprehend / external endpoint
  • Moderation Queue (SQS) — async call so comment write is not blocked on slow LLM
  • Human Review Queue (SQS + UI) — uncertain cases routed to moderators
  • Quarantine table — holds comments pending human decision (soft-hold, not rejected)
  • Prompt cache — identical system prompts cached at Bedrock level, reduces latency + cost

Interview angle Sync LLM on write path adds 50–200ms latency. At 10M comments/day that's real cost. Interviewers probe: "what if the LLM is down?" → circuit breaker → fall through to blocklist-only → queue for retroactive LLM scan. Never block the write path on an external API without a fallback.

AI-Q — Retrieval question

AI-Q1. A comment system uses a keyword blocklist for moderation. What problem does an LLM classifier solve that the blocklist cannot?

  • A) LLM classifiers run faster — blocklist lookups are O(N) per comment
  • B) Blocklists cannot handle Unicode characters; LLMs can
  • C) LLM classifiers understand context and semantics — "I want to kill this bug" is safe; a blocklist flags "kill". New slang and multilingual abuse are handled without rule updates.
  • D) LLM classifiers automatically retrain on new comments every hour
Blocklists are syntactic — they match strings, not meaning. LLMs are semantic — they understand that "kill" in "kill the process" is benign. This context-awareness is the core value. The tradeoff: LLMs cost $0.001–0.01 per call and add 50–200ms latency. The hybrid approach (blocklist first, LLM only for uncertain cases) gets accuracy without paying LLM cost on every comment.
