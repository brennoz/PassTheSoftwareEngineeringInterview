ExecutorService & ForkJoinPool

Java Concurrency Lesson 01 ~15 min Trading OMS context

Java's two main concurrency abstractions serve different shapes of work. Getting the choice wrong in an interview — or in production — means either deadlocked threads or idle CPUs. This lesson draws the line clearly.

Primary source Effective Java 3rd ed — Item 80: Prefer executors, tasks, and streams to threads and Java Concurrency in Practice (Goetz), Chapter 8 (thread pools).

1. The raw-thread problem

new Thread(() -> task.run()).start() creates an OS thread for every task. One OS thread costs ~1 MB of stack. A thousand tasks = a gigabyte of RAM just for stacks, plus ~1 ms of OS overhead per thread creation. At OMS scale (thousands of order validations per second) this collapses immediately.

A thread pool fixes this: create N threads once, reuse them forever, queue tasks to drain.

2. ExecutorService

ExecutorService is the standard thread-pool interface. You submit tasks; it returns Future<T> handles you can block on later.

Core pattern

ExecutorService pool = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors());
try {
    // submit returns Future — non-blocking
    Future<ValidationResult> f = pool.submit(() -> riskEngine.validate(order));

    // do other work here...

    ValidationResult result = f.get();             // blocks until done
    // f.get(500, TimeUnit.MILLISECONDS);           // with timeout
} finally {
    pool.shutdown();                               // stop accepting tasks
    pool.awaitTermination(10, TimeUnit.SECONDS);   // wait for in-flight tasks
}
Always shutdown. Forgetting shutdown() leaves threads alive — the JVM never exits. Java 19+ ExecutorService implements AutoCloseable, so try-with-resources works: try (var pool = Executors.newFixedThreadPool(4)) { ... }

Batch pattern — invokeAll

List<Callable<ValidationResult>> tasks = orders.stream()
    .map(o -> (Callable<ValidationResult>) () -> riskEngine.validate(o))
    .toList();

// submits all, blocks until ALL complete
List<Future<ValidationResult>> futures = pool.invokeAll(tasks);

List<ValidationResult> results = futures.stream()
    .map(f -> f.get())
    .toList();

3. ForkJoinPool

ExecutorService struggles with recursive divide-and-conquer tasks: a task that splits itself into subtasks and waits for them. With a fixed pool, the waiting thread holds a slot but does no work — pool exhaustion is likely.

ForkJoinPool solves this with work stealing: each thread has its own deque. Idle threads steal tasks from the top of busy threads' deques. No thread ever spins idle while work exists.

RecursiveTask — the pattern

class PnLTask extends RecursiveTask<BigDecimal> {
    private final List<Position> positions;
    private static final int THRESHOLD = 500;

    @Override
    protected BigDecimal compute() {
        if (positions.size() <= THRESHOLD) {
            // base case — compute directly
            return positions.stream()
                .map(Position::unrealisedPnL)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
        }
        int mid = positions.size() / 2;
        var left  = new PnLTask(positions.subList(0, mid));
        var right = new PnLTask(positions.subList(mid, positions.size()));

        left.fork();                        // submit left async to pool
        BigDecimal rightResult = right.compute();  // compute right on THIS thread
        BigDecimal leftResult  = left.join();      // block for left result

        return leftResult.add(rightResult);
    }
}

// invoke via commonPool
BigDecimal total = ForkJoinPool.commonPool()
    .invoke(new PnLTask(allPositions));
fork/compute order. Always fork() one half, compute() the other on the current thread, then join() the forked half. Never fork both — that wastes a thread doing nothing but joining.

4. Comparison

ExecutorService

  • Independent, uniform tasks
  • I/O-bound or CPU-bound
  • Tasks don't spawn subtasks
  • Results via Future
  • OMS use: parallel order validation

ForkJoinPool

  • Recursive, divide-and-conquer
  • CPU-bound only — no blocking I/O
  • Tasks fork subtasks
  • Results via join()
  • OMS use: P&L aggregation over millions of positions
commonPool starvation trap. CompletableFuture.supplyAsync() without a custom executor uses commonPool. A blocking call inside (DB, HTTP) starves all parallel streams in the JVM. Always pass a dedicated ExecutorService for I/O-bound CompletableFuture chains.
