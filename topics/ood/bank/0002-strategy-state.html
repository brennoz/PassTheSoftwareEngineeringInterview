Lesson 02 — Strategy Pattern (Interest) + Account State

Category: OOD  ·  Difficulty: Foundation  ·  Est. time: 15 min  ·  Lesson 2 of N

Lesson 01 built the domain skeleton. This lesson adds two new design moves: the Strategy Pattern for swappable interest calculation, and a state guard that prevents operations on closed accounts. Both appear directly in the q026 question requirements.

What you will be able to do after this lesson Add interest to SavingsAccount by injecting a strategy — and swap the algorithm at runtime without touching account code. Prevent operations on closed accounts with a clean state check.

1. The problem Strategy solves

Naïve approach: put the interest formula inside SavingsAccount. 

// BAD — algorithm hardcoded into account
public void applyInterest(int periods) {
    // What if we want compound instead? Edit this class. Now it violates Open/Closed.
    BigDecimal interest = balance.multiply(annualRate).multiply(BigDecimal.valueOf(periods));
    deposit(interest);
}

Problem: every time the bank changes its interest model (simple → compound → tiered), you modify SavingsAccount. Open/Closed Principle violated. Tests break. Regression risk.

Pattern: Strategy Extract the varying behaviour (the algorithm) into its own interface. The context class (SavingsAccount) holds a reference to the interface and delegates — it never knows which algorithm is running. Swap strategies at construction time or at runtime via a setter.

2. Structure

3. The interface + two implementations

// Pattern: Strategy — algorithm extracted to interface; context delegates
public interface InterestCalculationStrategy {
    BigDecimal calculate(BigDecimal balance, BigDecimal annualRate, int periods);
}

// Algorithm: Simple Interest — I = P * r * t (linear, no compounding)
// Why HALF_UP: banker's rounding is the regulatory default for financial calculations
public class SimpleInterestStrategy implements InterestCalculationStrategy {

    @Override
    public BigDecimal calculate(BigDecimal balance, BigDecimal annualRate, int periods) {
        return balance.multiply(annualRate)
                      .multiply(BigDecimal.valueOf(periods))
                      .setScale(2, RoundingMode.HALF_UP);
    }
}

// Algorithm: Compound Interest — I = P * (1+r)^t - P (exponential; interest earns interest)
// Why MathContext.DECIMAL128: pow() on BigDecimal needs explicit precision — default throws ArithmeticException
public class CompoundInterestStrategy implements InterestCalculationStrategy {

    @Override
    public BigDecimal calculate(BigDecimal balance, BigDecimal annualRate, int periods) {
        BigDecimal factor = BigDecimal.ONE.add(annualRate)
                                         .pow(periods, MathContext.DECIMAL128);
        return balance.multiply(factor)
                      .subtract(balance)
                      .setScale(2, RoundingMode.HALF_UP);
    }
}

4. SavingsAccount — delegate to strategy

class SavingsAccount extends BankAccount {

    private final BigDecimal minimumBalance;
    private final BigDecimal annualRate;
    // Strategy held by interface type, not concrete type — dependency inversion
    private InterestCalculationStrategy strategy;

    public SavingsAccount(BigDecimal initialBalance,
                          BigDecimal minimumBalance,
                          BigDecimal annualRate,
                          InterestCalculationStrategy strategy) {
        super(initialBalance);
        this.minimumBalance = minimumBalance;
        this.annualRate     = annualRate;
        this.strategy       = strategy;
    }

    @Override
    protected void validateWithdrawal(BigDecimal amount) {
        BigDecimal balanceAfter = balance.subtract(amount);
        if (balanceAfter.compareTo(minimumBalance) < 0)
            throw new IllegalStateException(
                "Withdrawal would breach minimum balance of " + minimumBalance);
    }

    public void applyInterest(int periods) {
        // Delegation — SavingsAccount has no idea which formula runs
        BigDecimal interest = strategy.calculate(balance, annualRate, periods);
        deposit(interest);
    }

    // Setter allows runtime strategy swap — e.g. promotional compound rate for 1 month
    public void setStrategy(InterestCalculationStrategy strategy) {
        this.strategy = strategy;
    }
}

Key: strategy is typed as InterestCalculationStrategy (the interface), not as SimpleInterestStrategy. This is Dependency Inversion — depend on the abstraction, not the concrete class.

5. Account state — ACTIVE / FROZEN / CLOSED

The question says: "closed accounts must reject all operations." The simplest correct implementation is an enum + guard. A full State Pattern (with separate state classes) is overkill here — name it correctly if you use it, but don't over-engineer.

Interview trap Using a boolean closed field works for two states, but fails as soon as you need FROZEN (reads OK, writes rejected) or DORMANT. Use an enum from the start. 
public enum AccountStatus { ACTIVE, FROZEN, CLOSED }

abstract class BankAccount {

    protected BigDecimal balance;
    private AccountStatus status = AccountStatus.ACTIVE;   // default
    private final List<Transaction> transactions = new ArrayList<>();

    // ...

    public final void deposit(BigDecimal amount) {
        requireStatus(AccountStatus.ACTIVE);   // guard
        if (amount.compareTo(BigDecimal.ZERO) <= 0)
            throw new IllegalArgumentException("Amount must be positive");
        balance = balance.add(amount).setScale(2, RoundingMode.HALF_UP);
        transactions.add(new Transaction(Transaction.Type.DEPOSIT, amount, balance, Instant.now()));
    }

    public final void withdraw(BigDecimal amount) {
        requireStatus(AccountStatus.ACTIVE);   // guard
        if (amount.compareTo(BigDecimal.ZERO) <= 0)
            throw new IllegalArgumentException("Amount must be positive");
        validateWithdrawal(amount);
        balance = balance.subtract(amount).setScale(2, RoundingMode.HALF_UP);
        transactions.add(new Transaction(Transaction.Type.WITHDRAWAL, amount, balance, Instant.now()));
    }

    public void close() { this.status = AccountStatus.CLOSED; }

    public void freeze() { this.status = AccountStatus.FROZEN; }

    // Centralised guard — one place to change when new rules added
    private void requireStatus(AccountStatus required) {
        if (status != required)
            throw new IllegalStateException("Account is " + status + ", expected " + required);
    }

    protected abstract void validateWithdrawal(BigDecimal amount);
}

6. SOLID checklist for this design

PrincipleHow it's applied here
Single ResponsibilityInterestCalculationStrategy owns only the formula. SavingsAccount owns only account rules.
Open/ClosedAdd a new interest model by implementing the interface — no existing class touched.
Liskov SubstitutionSavingsAccount and CheckingAccount are substitutable wherever BankAccount is expected.
Interface SegregationInterestCalculationStrategy has one method — not polluted with unrelated concerns.
Dependency InversionSavingsAccount depends on the interface, not the concrete strategy class.

7. Strategy vs Template Method — when to use which

Template MethodStrategy
MechanismInheritance — subclass overrides hookComposition — context holds interface reference

Q1. Strategy Pattern and Template Method Pattern both handle variable behaviour. What is the key structural difference?

  • A) Template Method uses interfaces; Strategy uses abstract classes
  • B) Template Method is for sorting algorithms; Strategy is for financial algorithms
  • C) Strategy uses composition (held reference); Template Method uses inheritance (subclass override)
  • D) There is no structural difference — they solve identical problems
Strategy: the context holds an interface reference and delegates — composition. Template Method: the base class defines the skeleton and subclasses override one step — inheritance. Prefer composition; it allows runtime swaps that inheritance cannot.

Q2. Which SOLID principle does the Strategy Pattern most directly enforce?

  • A) Liskov Substitution Principle
  • B) Open/Closed Principle
  • C) Single Responsibility Principle
  • D) Interface Segregation Principle
Open/Closed: the system is open to new interest algorithms (add a new class implementing the interface) but closed to modification (SavingsAccount never changes). You extend behaviour without editing existing code.

Q3. Why use an AccountStatus enum instead of a boolean closed field?

  • A) Enum scales to multiple states (ACTIVE / FROZEN / CLOSED) without adding new fields or conditionals
  • B) Booleans cannot be used as fields in abstract classes
  • C) Enums are faster than booleans at runtime due to JVM optimisation
  • D) Spring requires enum types for all entity status fields
A boolean covers two states. The moment you need FROZEN (reads allowed, writes rejected), you need a second boolean, which creates illegal combinations. An enum is mutually exclusive, self-documenting, and trivially extensible.

Q4. SavingsAccount holds InterestCalculationStrategy strategy typed as the interface, not as SimpleInterestStrategy. Which SOLID principle does this express?

  • A) Single Responsibility Principle — each class does one thing
  • B) Liskov Substitution Principle — subclasses replace base classes
  • C) Open/Closed Principle — closed to algorithm modification
  • D) Dependency Inversion Principle — depend on abstractions, not concretions
Dependency Inversion: high-level module (SavingsAccount) depends on the abstraction (the interface), not the concrete implementation. This is what makes the strategy swappable — SavingsAccount has zero knowledge of SimpleInterestStrategy or CompoundInterestStrategy.
