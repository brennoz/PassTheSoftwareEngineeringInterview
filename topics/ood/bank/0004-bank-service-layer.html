We built a bank account system in q026 (Rich Domain) and q027 (Observer). This lesson rebuilds it using the Service Layer pattern — same domain, different structure — and shows exactly why each choice matters in a production Java backend.

The two models at a glance

q026 — Rich Domain Model
  • Behavior lives inside the entity
  • account.withdraw(50)
  • Balance is a field on Account
  • synchronized on instance methods
  • Transfer needs deadlock-safe locking on two objects
  • Audit: manually fire events from within entity
q036 — Service Layer + Thin Records
  • Behavior lives in service classes
  • accountService.withdraw(id, 50)
  • Balance stored in repository (simulates DB column)
  • No sync needed on entity — repo is the lock boundary
  • Transfer is a single service method: TransferService
  • Audit: LedgerRepository records every transaction naturally

Entities and records

In the service layer model, domain objects are thin data containers. They carry identity and classification — no behavior.

q026 — Account as entity with behavior
abstract class Account {
  private BigDecimal balance;

  public synchronized void deposit(BigDecimal amount) {
    balance = balance.add(amount);
  }
  public synchronized void withdraw(BigDecimal amount) {
    if (balance.compareTo(amount) < 0)
      throw new InsufficientFundsException();
    balance = balance.subtract(amount);
  }
  abstract BigDecimal calculateInterest();
}
q036 — Account as thin record
// No behavior — just identity + classification
record Account(
    String        id,
    String        ownerId,
    AccountType   type,       // CURRENT / SAVINGS
    AccountStatus status      // ACTIVE / CLOSED
) {}

enum AccountType   { CURRENT, SAVINGS }
enum AccountStatus { ACTIVE, CLOSED }

The Transaction record replaces the audit log that had to be manually built in q026. It maps 1:1 to a ledger table row.

record Transaction(
    String          id,
    String          accountId,
    TransactionType type,         // CREDIT / DEBIT
    BigDecimal      amount,
    BigDecimal      balanceAfter,
    Instant         createdAt
) {}

enum TransactionType { CREDIT, DEBIT }

Where does the balance live?

This is the key structural difference between the two models.

Rich Domain (q026) Service Layer (q036)
Balance location Field inside Account Map<String, BigDecimal> balances in AccountRepository
DB equivalent accounts.balance column updated in-place Same accounts.balance column — but service writes it, not entity
Thread safety synchronized on Account instance Service calls repository — DB uses row-level locks; in-memory uses repo's single map
Can you query all accounts > £1000? Must iterate all accounts, call getBalance() balances.entrySet().stream().filter(e → e.getValue().compareTo(threshold) > 0)

The service layer approach shows how a real bank would structure it: AccountService is the only class allowed to read or write a balance. Nothing else touches the map directly.

class AccountService {

    private final AccountRepository  repo;
    private final LedgerRepository   ledger;
    private final InterestStrategy   interestStrategy;

    Transaction deposit(String accountId, BigDecimal amount) {
        Account account = repo.findById(accountId)
            .orElseThrow(() -> new AccountNotFoundException(accountId));
        if (account.status() == AccountStatus.CLOSED)
            throw new IllegalStateException("Account is closed");

        BigDecimal after = repo.addToBalance(accountId, amount);  // atomic in DB
        Transaction txn = new Transaction(
            UUID.randomUUID().toString(), accountId,
            TransactionType.CREDIT, amount, after, Instant.now());
        ledger.record(txn);
        return txn;
    }

    Transaction withdraw(String accountId, BigDecimal amount) {
        BigDecimal current = repo.getBalance(accountId);
        if (current.compareTo(amount) < 0)
            throw new InsufficientFundsException(accountId, current, amount);

        BigDecimal after = repo.subtractFromBalance(accountId, amount);
        Transaction txn = new Transaction(
            UUID.randomUUID().toString(), accountId,
            TransactionType.DEBIT, amount, after, Instant.now());
        ledger.record(txn);
        return txn;
    }
}
Interview check: In-memory AccountRepository must use new HashMap<>() for the balances map — never Map.of() or Map.copyOf(). Those are immutable and throw on put/remove. See the Set.of() trap from q035.

Transfer — the hardest operation

In q026, transferring between two accounts required locking both Account objects in a consistent order to prevent deadlock:

// q026 Rich Domain — deadlock-safe transfer
Account first  = id1.compareTo(id2) < 0 ? from : to;
Account second = id1.compareTo(id2) < 0 ? to : from;
synchronized (first) {
    synchronized (second) {
        from.withdraw(amount);
        to.deposit(amount);
    }
}

In the service layer, the concern is pushed to the transaction boundary — in production that is a single DB transaction. In the interview simulation, TransferService calls both operations in sequence and rolls back on failure:

class TransferService {

    private final AccountService accountService;

    Transfer transfer(String fromId, String toId, BigDecimal amount) {
        if (fromId.equals(toId))
            throw new IllegalArgumentException("Cannot transfer to self");

        // In production: single DB transaction wraps both operations
        accountService.withdraw(fromId, amount);   // throws if insufficient funds
        accountService.deposit(toId, amount);

        return new Transfer(UUID.randomUUID().toString(),
            fromId, toId, amount, Instant.now());
    }
}
Rich Domain (q026) Service Layer (q036)
Atomicity synchronized blocks — one JVM only DB transaction — atomic across any number of pods
Deadlock risk Must lock in consistent order (sort by id) None — one thread executes both ops sequentially in one DB txn
Rollback Manual compensating transaction ROLLBACK — DB undoes both ops automatically
Multi-region Impossible with synchronized Saga pattern — two-phase commit or compensating saga

Ledger and audit trail

Banking requires an immutable audit trail: every balance change must be recorded with who, when, how much, and balance after.

In q026 this was added on top via the Observer pattern. In the service layer it falls out naturally — AccountService creates a Transaction record on every deposit/withdraw and persists it to LedgerRepository.

class LedgerRepository {
    // append-only — no delete, no update — maps 1:1 to DB ledger table
    private final Map<String, List<Transaction>> byAccount = new HashMap<>();

    void record(Transaction txn) {
        byAccount.computeIfAbsent(txn.accountId(), k -> new ArrayList<>()).add(txn);
    }

    List<Transaction> history(String accountId) {
        return List.copyOf(byAccount.getOrDefault(accountId, List.of()));
    }
}
Banking rule: Ledger entries are append-only. No UPDATE, no DELETE on a posted transaction. This is not just good design — it is a regulatory requirement (SOX, Basel III). In production: ledger rows use a DB sequence ID; balanceAfter is stored for fast balance reconstruction without summing the entire history.

Production and AWS

In-memory structure Why it breaks on multi-pod Production fix AWS service
Map<id, BigDecimal> balances Balance on Pod A unknown to Pod B → race on concurrent withdrawals → overdraft PostgreSQL accounts.balance + UPDATE ... WHERE balance >= amount (atomic check-and-set) RDS Multi-AZ (PostgreSQL)
synchronized transfer Pods share nothing — sync within one JVM only DB transaction: BEGIN; debit; credit; COMMIT; RDS (ACID guaranteed)
LedgerRepository in memory Pod restart loses all history Append-only ledger table; sequence_id as PK; no UPDATE/DELETE RDS or DynamoDB with conditional writes
InterestStrategy in memory Strategy changes not visible across pods without restart Store strategy type on Account row; load at runtime via factory RDS config + feature flag (AppConfig)
Transfer (sequential ops) Crash between debit and credit → partial transfer Saga pattern — debit + credit as two steps with compensating transaction on failure Step Functions (Saga orchestration)
Idempotency in banking: A POST /transfer endpoint must accept an Idempotency-Key header. If the client retries after a network timeout, the second request must return the same result — not execute the transfer twice. Store the key in a idempotency_records table with the response payload.

Quiz

Q1. In the service layer bank model, AccountService.withdraw() finds that the balance is sufficient and calls repo.subtractFromBalance(). One millisecond later, on a different pod, another withdrawal also reads the same sufficient balance and proceeds. Both succeed. The account is now overdrawn. What is the correct fix?

  • Add synchronized to AccountService.withdraw()
  • Use ConcurrentHashMap for the balances map
  • Replace the read-then-write with an atomic DB conditional update: UPDATE accounts SET balance = balance - ? WHERE id = ? AND balance >= ?, check rows affected = 1
  • Add a ReentrantLock per account ID to the repository
Atomic conditional UPDATE. Options 1 and 4 only synchronize within one JVM. Option 2 is thread-safe within one JVM but not across pods. The only fix that works on a multi-pod cluster is pushing the atomicity to the database: the conditional UPDATE succeeds only if balance is still sufficient at the moment the DB executes it. If 0 rows are updated, throw InsufficientFundsException. In AWS: RDS PostgreSQL provides row-level locking that makes this safe across any number of ECS/Lambda instances.

Q2. You model Account as a Java record (immutable). A close() operation is needed that transitions status from ACTIVE to CLOSED. What must change?

  • Add a close() method to the record — records can have methods
  • Records are immutable — close() lives in AccountService: validate, create a new Account with status=CLOSED, save to repo, replacing the old one
  • Make Account a mutable class with a setter for status
  • Use the State Pattern inside the record to manage the status field
Service creates a new record instance. Records in Java are structurally immutable — you cannot change a field after construction. The service layer handles this by creating a replacement: Account closed = new Account(acc.id(), acc.ownerId(), acc.type(), AccountStatus.CLOSED), then repo.save(closed). This maps cleanly to a DB UPDATE accounts SET status = 'CLOSED' WHERE id = ?. Option 3 (mutable class) works but loses immutability guarantees. Option 4: State Pattern adds complexity without benefit when the state has only two values and the transition logic is simple.

Q3. The bank wants to calculate monthly interest differently for CURRENT (no interest) vs SAVINGS (compound). Where does the Strategy Pattern live in the service layer model?

  • Injected into AccountService as a field; selected based on account.type() at runtime using a factory or map-of-strategies
  • Implemented as a method on the Account record using a switch expression on type
  • Implemented in LedgerRepository when recording the interest credit transaction
  • Each subclass of Account (SavingsAccount, CurrentAccount) overrides the strategy
Strategy injected into AccountService, selected by account type. In service layer there is no Account subclass hierarchy — AccountType is an enum field. The Strategy is selected at runtime: Map<AccountType, InterestStrategy> strategies in the service. strategies.get(account.type()).calculate(balance, rate, days). Adding a new account type = new enum value + new strategy class, no existing code changes (Open/Closed Principle). Always use BigDecimal for the result — never double.

Q4. A customer closes an account with £0 balance. Six months later, a regulatory audit requires the full transaction history of that account. What design decision ensures this is possible?

  • Store all transactions as fields on the Account record so they travel with the account
  • Use the Observer Pattern to notify an audit service on each transaction at runtime
  • Reconstruct history by replaying balanceAfter values in reverse
  • LedgerRepository is append-only with no delete: every transaction row persists indefinitely, queryable by accountId at any future time
Append-only ledger. The LedgerRepository never deletes rows — not on close, not ever. This is the fundamental banking invariant: posted transactions are immutable. A closed account still has all its history. In production: the ledger table uses a sequence PK; closing the account sets accounts.status = 'CLOSED' but leaves the ledger rows untouched. GDPR "right to erasure" conflicts with this — the resolution is pseudonymisation (replace PII with a token) rather than deletion. AWS: RDS with point-in-time recovery; optionally S3 with Object Lock (WORM) for long-term regulatory archival.
