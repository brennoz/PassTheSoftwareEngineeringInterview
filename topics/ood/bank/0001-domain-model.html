2. The Account hierarchy — why abstract?

Account is abstract because you never instantiate a "plain account" — you always have a checking, savings, or loan. This forces subclasses to implement type-specific behaviour while sharing common logic (balance tracking, transaction history) in the base class.

Pattern: Template Method Account.withdraw() handles common guards (balance check, amount validation). Subclasses override canWithdraw() to inject type-specific rules (e.g. CheckingAccount allows overdraft to a limit; SavingsAccount does not). 
// Pattern: Template Method — common algorithm skeleton in base class,
// subclass hooks override the type-specific step
public abstract class Account {

    private final String id;
    private final Customer owner;
    private Money balance;
    private final List<Transaction> history = new ArrayList<>();

    // Why BigDecimal: floating-point arithmetic loses cents at scale
    // Money is a Value Object — immutable, compared by value not reference
    protected Account(String id, Customer owner, Money initialBalance) {
        this.id      = id;
        this.owner   = owner;
        this.balance = initialBalance;
    }

    // Template Method — subclasses override canWithdraw()
    public final synchronized void withdraw(Money amount) {
        if (amount.isNegativeOrZero()) throw new IllegalArgumentException("Amount must be positive");
        if (!canWithdraw(amount))       throw new InsufficientFundsException(id, amount, balance);
        balance = balance.subtract(amount);
        history.add(Transaction.debit(id, amount));
    }

    public final synchronized void deposit(Money amount) {
        if (amount.isNegativeOrZero()) throw new IllegalArgumentException("Amount must be positive");
        balance = balance.add(amount);
        history.add(Transaction.credit(id, amount));
    }

    // Hook — subclasses decide the rule
    protected abstract boolean canWithdraw(Money amount);

    // Why synchronized: balance is shared mutable state;
    // concurrent withdraw calls → race condition → overdraft
    public synchronized Money getBalance() { return balance; }

    public String getId()                  { return id; }
    public List<Transaction> getHistory()  { return List.copyOf(history); }
}

// Checking: allows overdraft up to a configured limit
public class CheckingAccount extends Account {

    private final Money overdraftLimit;

    public CheckingAccount(String id, Customer owner, Money initial, Money overdraftLimit) {
        super(id, owner, initial);
        this.overdraftLimit = overdraftLimit;
    }

    @Override
    protected boolean canWithdraw(Money amount) {
        // balance + overdraftLimit >= amount
        return getBalance().add(overdraftLimit).isGreaterThanOrEqualTo(amount);
    }
}

// Savings: no overdraft — balance must cover withdrawal
public class SavingsAccount extends Account {

    public SavingsAccount(String id, Customer owner, Money initial) {
        super(id, owner, initial);
    }

    @Override
    protected boolean canWithdraw(Money amount) {
        return getBalance().isGreaterThanOrEqualTo(amount);
    }
}

3. Transaction — always immutable

A Transaction is a value object: once created it never changes. This is not just style — in banking, posted transactions are legally immutable (the audit trail must survive). Use Java records (Java 16+). 

// Why record: immutable by default, equals/hashCode/toString auto-generated
// Why Instant not LocalDateTime: UTC always; LocalDateTime is timezone-naive
public record Transaction(
    String      id,
    String      accountId,
    TransactionType type,
    Money       amount,
    Instant     createdAt
) {
    public static Transaction debit(String accountId, Money amount) {
        return new Transaction(UUID.randomUUID().toString(), accountId,
                               TransactionType.DEBIT, amount, Instant.now());
    }

    public static Transaction credit(String accountId, Money amount) {
        return new Transaction(UUID.randomUUID().toString(), accountId,
                               TransactionType.CREDIT, amount, Instant.now());
    }
}

public enum TransactionType { DEBIT, CREDIT }

4. Money — value object

Money is the most important value object in any financial system. It wraps BigDecimal and Currency together so arithmetic is always currency-aware. Interviewers will explicitly watch for this. 

// Why BigDecimal not double: 0.1 + 0.2 = 0.30000000000000004 in floating point
// A 1-cent error across 100M transactions = $1M discrepancy in ledger
public record Money(BigDecimal amount, Currency currency) {

    public Money {
        Objects.requireNonNull(amount, "amount");
        Objects.requireNonNull(currency, "currency");
        if (amount.scale() > currency.getDefaultFractionDigits())
            throw new IllegalArgumentException("Too many decimal places for " + currency);
    }

    public Money add(Money other) {
        assertSameCurrency(other);
        return new Money(amount.add(other.amount), currency);
    }

    public Money subtract(Money other) {
        assertSameCurrency(other);
        return new Money(amount.subtract(other.amount), currency);
    }

    public boolean isGreaterThanOrEqualTo(Money other) {
        assertSameCurrency(other);
        return amount.compareTo(other.amount) >= 0;
    }

    public boolean isNegativeOrZero() {
        return amount.compareTo(BigDecimal.ZERO) <= 0;
    }

    private void assertSameCurrency(Money other) {
        if (!currency.equals(other.currency))
            throw new CurrencyMismatchException(currency, other.currency);
    }

    // Factory method — idiomatic Java
    public static Money of(String amount, String currencyCode) {
        return new Money(new BigDecimal(amount), Currency.getInstance(currencyCode));
    }
}

5. Customer — aggregate root

public class Customer {

    private final String id;
    private final String name;
    private final List<Account> accounts = new ArrayList<>();

    public Customer(String id, String name) {
        this.id   = id;
        this.name = name;
    }

    public void addAccount(Account account) {
        accounts.add(account);
    }

    public List<Account> getAccounts() { return List.copyOf(accounts); }
    public String getId()              { return id; }
    public String getName()            { return name; }
}

6. Transfer — the tricky operation

Transfer is the first place interviewers probe thread safety. Naive implementation: lock account A, lock account B, move money. Problem: if two transfers run concurrently in opposite directions (A→B and B→A), each thread acquires one lock and waits for the other — deadlock.

Deadlock scenario Thread 1: lock(A) → waiting for lock(B)
Thread 2: lock(B) → waiting for lock(A)
Both wait forever.

Fix: always acquire locks in a consistent global order (e.g. by account ID lexicographic order). Both threads agree on the order → no cycle. 

// Why ordered locking: prevents deadlock in concurrent transfers
// Algorithm: acquire both locks in consistent ID order → no circular wait
public class TransferService {

    public void transfer(Account from, Account to, Money amount) {
        // Determine lock order by account ID to avoid deadlock
        Account first  = from.getId().compareTo(to.getId()) < 0 ? from : to;
        Account second = first == from ? to : from;

        synchronized (first) {
            synchronized (second) {
                from.withdraw(amount);
                to.deposit(amount);
            }
        }
    }
}

8. Retrieval quiz

Q1. Why is Account declared abstract?

  • A) Java requires abstract for classes with synchronized methods
  • B) You never instantiate a plain "account" — always a specific subtype
  • C) Abstract classes run faster than concrete classes
  • D) To prevent the compiler from generating equals() automatically
You always have Checking, Savings, or Loan — never a generic Account. Abstract enforces that subclasses exist and implement the type-specific hook.

Q2. What design pattern does Account.withdraw() + canWithdraw() implement?

  • A) Strategy Pattern
  • B) Observer Pattern
  • C) Factory Pattern
  • D) Template Method Pattern
Template Method: the base class defines the algorithm skeleton (validate, check, debit, record). Subclasses override the hook step (canWithdraw) without changing the skeleton.

Q3. Two concurrent transfers A→B and B→A. What is the risk and how do you fix it?

  • A) Deadlock — fix by acquiring both locks in a consistent global order (e.g. by account ID)
  • B) Race condition — fix by wrapping both operations in a database transaction
  • C) Starvation — fix by using a fair lock (ReentrantLock with fairness=true)
  • D) Memory leak — fix by releasing locks in a finally block
Deadlock: each thread holds one lock and waits for the other → circular wait → both blocked forever. Fix: all threads agree on the same lock acquisition order → no cycle possible.

Q4. Why use BigDecimal for Money.amount instead of double?

  • A) BigDecimal is a primitive type and therefore faster for arithmetic
  • B) double does not support currency-aware formatting
  • C) double cannot store negative values, so withdrawals would break
  • D) Floating-point arithmetic loses precision — 0.1 + 0.2 ≠ 0.3 in binary
IEEE 754 floating point cannot represent 0.1 exactly in binary. At scale (millions of transactions), rounding errors compound. BigDecimal uses arbitrary-precision decimal arithmetic — every cent is exact.
