Lesson 03 — Observer Pattern (Account Notifications)

Category: OOD · Difficulty: Medium · Est. time: 15 min · Lesson 3 of N

Lessons 01 and 02 built the core account model. This lesson adds event notifications — when something happens to an account, interested parties (email system, fraud detector, audit logger) are told. The mechanism is the Observer Pattern.

What you will be able to do after this lesson Add unlimited listeners to BankAccount at runtime without touching any account code. Name the pattern, justify it, and explain the thread-safety gotcha that every interviewer waits for.

1. The problem — hardcoded notifications

// BAD — BankAccount knows about email AND fraud AND audit
public final void deposit(BigDecimal amount) {
    // ... balance update ...
    emailService.send("Deposit of " + amount);      // coupled
    fraudService.check(amount);                      // coupled
    auditLogger.log("DEPOSIT", amount);              // coupled
}

Every new notification target (SMS, Slack, regulatory log) means editing BankAccount. Open/Closed violated. Tests break. Circular dependencies grow.

2. Structure

«interface» AccountEventListener + onEvent(AccountEvent event): void ▲ ▲ ▲ │ │ │ EmailNotification FraudDetection AuditLogger Listener Listener Listener │ │ │ └───────────────┴───────────────┘ registered in ┌─────────────────┐ │ BankAccount │ ← Subject │ (Observable) │ │ listeners: List │ └─────────────────┘ fires on: deposit / withdraw / close

BankAccount knows only about the interface, never the concrete listeners. Adding a new listener = new class + one addListener() call. Zero changes to BankAccount.

3. The event — what gets passed to listeners

// Why a dedicated event record: listeners get typed context, not raw primitives
// Why record: immutable — listeners cannot mutate the event after the fact
public record AccountEvent(
    EventType     type,
    String        accountId,
    BigDecimal    amount,      // null for CLOSE events
    BigDecimal    balanceAfter,
    Instant       occurredAt
) {
    public enum EventType { DEPOSIT, WITHDRAWAL, CLOSE }

    public static AccountEvent deposit(String accountId, BigDecimal amount, BigDecimal balance) {
        return new AccountEvent(EventType.DEPOSIT, accountId, amount, balance, Instant.now());
    }
    public static AccountEvent withdrawal(String accountId, BigDecimal amount, BigDecimal balance) {
        return new AccountEvent(EventType.WITHDRAWAL, accountId, amount, balance, Instant.now());
    }
    public static AccountEvent close(String accountId) {
        return new AccountEvent(EventType.CLOSE, accountId, null, null, Instant.now());
    }
}

4. The listener interface

// Pattern: Observer — all listeners implement this single method
// Why a single onEvent() not separate onDeposit/onWithdrawal: fewer methods,
// listeners filter by EventType themselves — extensible without interface changes
public interface AccountEventListener {
    void onEvent(AccountEvent event);
}

5. BankAccount — the subject

abstract class BankAccount {

    // Why CopyOnWriteArrayList: listeners may be added/removed while an event fires
    // on another thread. Regular ArrayList → ConcurrentModificationException.
    private final List<AccountEventListener> listeners = new CopyOnWriteArrayList<>();

    public void addListener(AccountEventListener listener)    { listeners.add(listener); }
    public void removeListener(AccountEventListener listener) { listeners.remove(listener); }

    // Fire-and-forget: BankAccount does not care what listeners do
    private void fireEvent(AccountEvent event) {
        for (AccountEventListener listener : listeners) {
            listener.onEvent(event);
        }
    }

    public final void deposit(BigDecimal amount) {
        requireStatus(AccountStatus.ACTIVE);
        if (amount.compareTo(BigDecimal.ZERO) <= 0) throw new IllegalArgumentException("Amount must be positive");
        balance = balance.add(amount).setScale(2, RoundingMode.HALF_UP);
        transactions.add(new Transaction(Transaction.Type.DEPOSIT, amount, balance, Instant.now()));
        fireEvent(AccountEvent.deposit(accountId, amount, balance));  // ← after state change
    }

    public final void withdraw(BigDecimal amount) {
        requireStatus(AccountStatus.ACTIVE);
        if (amount.compareTo(BigDecimal.ZERO) <= 0) throw new IllegalArgumentException("Amount must be positive");
        validateWithdrawal(amount);
        balance = balance.subtract(amount).setScale(2, RoundingMode.HALF_UP);
        transactions.add(new Transaction(Transaction.Type.WITHDRAWAL, amount, balance, Instant.now()));
        fireEvent(AccountEvent.withdrawal(accountId, amount, balance)); // ← after state change
    }

    public void close() {
        this.status = AccountStatus.CLOSED;
        fireEvent(AccountEvent.close(accountId));
    }
}
Fire AFTER state change, not before If a listener reads getBalance(), it should see the updated value. Firing before the update means listeners see stale state. This is a common bug interviewers plant in code-review questions.

6. Two concrete listeners

public class EmailNotificationListener implements AccountEventListener {

    @Override
    public void onEvent(AccountEvent event) {
        switch (event.type()) {
            case DEPOSIT    -> System.out.printf("Email: £%.2f deposited. Balance: £%.2f%n",
                                    event.amount(), event.balanceAfter());
            case WITHDRAWAL -> System.out.printf("Email: £%.2f withdrawn. Balance: £%.2f%n",
                                    event.amount(), event.balanceAfter());
            case CLOSE      -> System.out.println("Email: Your account has been closed.");
        }
    }
}

// Threshold is configurable — different accounts may have different risk levels
public class FraudDetectionListener implements AccountEventListener {

    private static final BigDecimal DEFAULT_THRESHOLD = new BigDecimal("10000.00");
    private final BigDecimal threshold;

    public FraudDetectionListener() { this(DEFAULT_THRESHOLD); }
    public FraudDetectionListener(BigDecimal threshold) { this.threshold = threshold; }

    @Override
    public void onEvent(AccountEvent event) {
        if (event.type() == AccountEvent.EventType.WITHDRAWAL
                && event.amount().compareTo(threshold) > 0) {
            System.out.printf("FRAUD ALERT: Large withdrawal of £%.2f on account %s%n",
                    event.amount(), event.accountId());
        }
    }
}

7. Usage

SavingsAccount account = new SavingsAccount(
    "ACC-001",
    new BigDecimal("5000.00"),
    new BigDecimal("100.00"),
    new BigDecimal("0.03"),
    new SimpleInterestStrategy()
);

account.addListener(new EmailNotificationListener());
account.addListener(new FraudDetectionListener());

account.deposit(new BigDecimal("200.00"));
// → Email: £200.00 deposited. Balance: £5200.00

account.withdraw(new BigDecimal("15000.00"));
// → FRAUD ALERT: Large withdrawal of £15000.00 on account ACC-001
// → Email: £15000.00 withdrawn. Balance: £-9800.00  (if overdraft limit allows)

Q1. What does the Observer Pattern decouple?

  • A) The algorithm from its data structure
  • B) The constructor from its dependencies
  • C) The interface from its implementation
  • D) The subject (event source) from its observers (event handlers)
The subject fires events without knowing who receives them. Observers register themselves. Neither side depends on the other's concrete type — only on the shared event interface.

Q2. Why use CopyOnWriteArrayList for the listener list instead of ArrayList?

  • A) CopyOnWriteArrayList is faster for read-heavy workloads
  • B) A listener may be added or removed on another thread while fireEvent() is iterating — ArrayList throws ConcurrentModificationException
  • C) ArrayList does not support generic types in Java 21
  • D) CopyOnWriteArrayList prevents duplicate listeners from being registered
CopyOnWriteArrayList creates a fresh copy of the array on every write (add/remove). Iterators always read a stable snapshot, so concurrent modification during iteration is safe. Cost: writes are O(N) — acceptable when listeners are rarely changed but events fire frequently.

Q3. Should fireEvent() be called before or after the balance is updated? Why?

  • A) Before — so listeners can veto the operation before it commits
  • B) It does not matter — listeners receive the amount, not the balance
  • C) After — so listeners that call getBalance() see the updated value, not stale state
  • D) In a separate thread — so the account operation is not blocked by slow listeners
Fire after state change. A FraudDetectionListener or AuditLogger that reads getBalance() inside onEvent() must see the post-operation balance. Firing before the update gives listeners stale data — a classic planted bug in code-review questions.

Q4. Observer uses 1:N composition; Strategy uses 1:1 composition. What does this mean practically when adding a new notification target (e.g. SMS)?

  • A) Create a new SmsNotificationListener class, call addListener() — zero changes to BankAccount
  • B) Add an smsService field to BankAccount and call it in deposit() and withdraw()
  • C) Extend BankAccount into SmsBankAccount and override the fire methods
  • D) Replace InterestCalculationStrategy with a combined strategy that also sends SMS
This is the payoff of Observer. New listener = new class only. BankAccount is open to new observers (Open principle) and closed to modification (Closed principle). Options B and C both violate Open/Closed.
