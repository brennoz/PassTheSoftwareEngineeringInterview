Lesson 01 — ATM System Domain Model

Category: OOD · Difficulty: Medium · Est. time: 25 min · Lesson 1 of N

ATM System is a classic OOD interview question, and the classic reason it's asked is to see whether a candidate reaches for Command Pattern for transactions instead of just calling account.withdraw(amount) directly. This lesson builds the full solution: State Pattern for the card session lifecycle (same shape as q030/q043's State write-ups), and Command Pattern for transactions — the first time this project's OOD questions have used Command rather than Specification/State/Strategy.

What you will be able to do after this lesson Given "design an ATM," name State and Command correctly, explain why a transaction is an object rather than a method call, and say precisely where the authentication guard and the overdraft guard each belong — and why they don't belong in the same place.

2. State Pattern — the card session lifecycle

┌──────────┐ │ NO_CARD │◄───────────────────────┐ └────┬─────┘ │ │ insertCard() │ ┌────▼─────────┐ │ │CARD_INSERTED │────────────────────┤ ejectCard() └────┬─────────┘ │ (legal from either state) │ authenticate() │ ┌────▼─────────┐ │ │AUTHENTICATED │────────────────────┘ └──────────────┘
// Pattern: State — each status is an object; only the transition(s) legal from
// that status are implemented as a no-op, every other method throws IllegalStateException
public interface CardState {
    void insertCard(AtmSession session);
    void authenticate(AtmSession session);
    void ejectCard(AtmSession session);
    String name();
}

public class CardInsertedState implements CardState {
    @Override
    public void insertCard(AtmSession session)   { throw new IllegalStateException("Cannot insert card: a card is already inserted"); }
    @Override
    public void authenticate(AtmSession session) { session.setState(new AuthenticatedState()); }
    @Override
    public void ejectCard(AtmSession session)    { session.setState(new NoCardState()); }
    @Override public String name()               { return "CARD_INSERTED"; }
}

// NoCardState and AuthenticatedState follow the same shape. Notably, ejectCard() is legal
// from BOTH CardInsertedState and AuthenticatedState — a user can back out before or after
// entering a PIN, always landing back at NoCardState.
Why NOT model PIN correctness inside CardState A tempting design: CardInsertedState.authenticate(session, enteredPin) compares the PIN itself and only transitions on a match. Rejected — a state's job is transition legality (is authenticating even allowed right now), not the business decision of whether given credentials are correct. Credential checking belongs to whoever calls session.authenticate() after already verifying the PIN — same separation q043's SchedulingStrategy draws between "is this transition legal" and "which floor should we actually go to."

Q1. Why is ejectCard() legal from both CardInsertedState and AuthenticatedState, rather than only from one of them?

  • A) It isn't — only AuthenticatedState should allow it
  • B) A user must be able to take their card back whether or not they've entered a correct PIN yet — cancelling before authentication is a normal flow, not an error
  • C) Java interfaces require every method to be implemented identically across all implementing classes
  • D) It's a shortcut to avoid writing a fourth state class
A user who inserts a card and changes their mind before entering a PIN needs their card back without being forced through authentication first. Restricting eject to only AuthenticatedState would trap a hesitant user's card in the machine.

3. Command Pattern — transactions as objects

A withdrawal, deposit, or balance check is represented as an object with a single execute() method, submitted uniformly through AtmService. 

// Pattern: Command — a request is an object (which account, what amount),
// decoupled from when or by whom it's executed
public interface AtmCommand {
    void execute();
}

public class WithdrawCommand implements AtmCommand {
    private final Account account;
    private final BigDecimal amount;

    public WithdrawCommand(Account account, BigDecimal amount) {
        this.account = account;
        this.amount = amount;
    }

    @Override
    public void execute() {
        account.withdraw(amount);   // overdraft guard lives in Account, not here
    }
}

// DepositCommand follows the same shape. CheckBalanceCommand differs slightly — it
// captures its own result (getLastReadBalance()) since a balance check has nothing to
// mutate; its entire purpose IS the result.
Command vs Strategy — easy to conflate q043's SchedulingStrategy picks how to do one fixed kind of thing (dispatch a request). AtmCommand represents a specific request to do a specific thing, as a first-class object you could log, queue, or undo. Same "interface with one method" shape on the surface; different intent underneath.
Why bother with Command instead of AtmService.withdraw(account, amount)? A direct method call is simpler and passes every test in this question's scope. The Command form earns its place the moment a real ATM interview follow-up lands: a transaction log (each AtmCommand is already a loggable object), an undo/ reversal feature, or batching transactions for later processing — all natural once a transaction is an object you can store, not a call that's already finished. If no such follow-up were ever coming, the direct method call would be the right call — same "match the model to what the ticket needs" discipline as q041/q042's Specification-pattern discussion.

Q2. Why does Account.withdraw() throw InsufficientFundsException, rather than WithdrawCommand.execute() checking the balance before calling it?

  • A) Because Command objects cannot contain any conditional logic
  • B) Because InsufficientFundsException must extend a checked exception class
  • C) Because Account is the one place the overdraft rule is enforced; letting Command also check it would create two places that could disagree about what's allowed
  • D) Because BigDecimal doesn't support comparison operators
A Command's job is to encapsulate a request, not to own the business rule about whether it's allowed. If the guard lived in both Account and WithdrawCommand, a future third caller of Account.withdraw() (bypassing the command) could violate the rule the command enforced, or the two checks could drift out of sync over time.

4. AtmService — where the two guards actually live

public class AtmService {

    private final AtmSession session;

    public AtmService(AtmSession session) {
        this.session = session;
    }

    public void submitCommand(AtmCommand command) {
        if (!"AUTHENTICATED".equals(session.getStatus())) {
            throw new IllegalStateException("Cannot submit a transaction before authenticating");
        }
        command.execute();
    }
}

Two guards, two homes, on purpose: authentication is a session-level concern (can ANY command run right now), checked once in AtmService before execute() is even called. Overdraft is an account-level concern (can THIS specific withdrawal happen), checked inside Account regardless of how the withdrawal was triggered. Putting both guards in the same place — either both in AtmService, or both in the command — would mean testing WithdrawCommand in isolation always needs a fully set-up authenticated session just to exercise a balance check that has nothing to do with authentication.

Q3. What would break if the "must be authenticated" check moved from AtmService.submitCommand() into each AtmCommand implementation individually?

  • A) Nothing — it's exactly equivalent either way
  • B) BigDecimal arithmetic would start losing precision
  • C) The State pattern would no longer compile
  • D) Every new command type would need to remember to add the same guard itself, and unit-testing a command in isolation would require faking an authenticated session just to test logic unrelated to authentication
Centralising the guard in one place both commands pass through means new command types get it for free, and a command can be tested against its own actual responsibility without needing to also stand up session state.

5. What interviewers are actually probing

ProbeExpected answer
Why State Pattern for the card session?Adding a new status (e.g. CARD_RETAINED after failed PIN attempts) requires only a new class — no existing switch blocks to edit
Why is a transaction an object, not a method call?Command Pattern — makes transactions loggable/queueable/reversible without changing AtmService when a new transaction type is added
Where does the overdraft check live?Account.withdraw() — not the command, not the service, so it can't be bypassed by a different caller
Where does the authentication check live?AtmService.submitCommand() — the one place every command passes through
Why is ejectCard() legal from two different states?Cancelling before entering a PIN is a normal flow, not an error condition
