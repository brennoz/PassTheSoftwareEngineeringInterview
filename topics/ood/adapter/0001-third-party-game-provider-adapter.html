Adapter Pattern — Third-Party Game Provider Integration

Question this lesson prepares you for: q059 — integrate two third-party game providers with different SDK shapes behind one internal interface.

Why Adapter, specifically

You don't control the third party's API. SlotForgeClient is one blocking call, pence as long. ReelMasterXClient is a handshake + async poll loop, pounds as double. Every OTHER pattern (Strategy, Observer, Template Method) assumes the implementations you're switching between already share a compatible shape — Adapter is the one pattern whose entire job is reconciling shapes you don't control into one you do.

The structure

interface GameProviderAdapter {        // Target — the only contract callers see
    SpinResult spin(GameSession session, Money stake);
}

class SlotForgeAdapter implements GameProviderAdapter {   // Concrete Adapter #1
    private final SlotForgeClient client;                  // wraps the given SDK (Adaptee)
    // spin() converts Money -> pence(long), calls client.spin(), converts response back
}

class ReelMasterXAdapter implements GameProviderAdapter {  // Concrete Adapter #2
    private final ReelMasterXClient client;
    // spin() does authenticate -> submitSpin -> poll-until-COMPLETE, ALL hidden inside
    // this one method. Caller never sees a token, a ticket ID, or a poll loop.
}

The two traps this exercise plants

  1. Unbounded polling. If ReelMasterXAdapter polls in a while(true) with no attempt cap, one slow/broken provider hangs every spin that touches it — a resource leak disguised as "just waiting for a result." Bound the attempts; return a failed SpinResult once exhausted.
  2. Unsafe double→BigDecimal conversion. new BigDecimal(0.1) captures the double's actual binary value (0.1000000000000000055511151231257827021181583404541015625), not the "0.1" you think you typed. BigDecimal.valueOf(0.1) goes via Double.toString(0.1) first — exactly 0.1. Always valueOf when converting a third party's double-based money field.

System design angle

The adapter's polling loop currently blocks the calling thread with Thread.sleep. At scale this caps throughput at "however many threads you have," regardless of how fast the provider actually is. Two real fixes: (1) the provider pushes a webhook/event on completion instead of you polling it, or (2) you return immediately and the caller subscribes to a completion event (Kafka/SQS) — decoupling request from response. Both trade implementation complexity for not tying up a thread per in-flight spin.

Q1. Why does GameProviderAdapter expose zero provider-specific detail (no pollReelMasterX(ticketId) "just in case")?

  • Hiding provider-specific shape behind one interface is the entire point of Adapter — leaking one vendor detail back onto the Target forces every other adapter to fake-implement it or breaks the abstraction
  • Because polling is always slower than a synchronous call
  • Because ReelMasterX doesn't actually support polling
  • To reduce the number of HTTP requests made overall
Adding one vendor-specific method to the Target interface means every future adapter (SlotForge, and any third provider) must implement or no-op that method too — the interface stops being a true abstraction and starts leaking whichever provider was integrated first.

Q2. Why BigDecimal.valueOf(double) instead of new BigDecimal(double) when converting ReelMasterX's win amount?

  • valueOf is measurably faster at runtime
  • new BigDecimal(double) captures the double's exact binary value, not the decimal you'd expect — valueOf goes via Double.toString() first, giving the expected decimal
  • They're functionally identical; valueOf is just more idiomatic style
  • new BigDecimal(double) throws for negative values
Binary floating point can't represent most decimal fractions exactly. new BigDecimal(0.1) reveals that imprecision directly; valueOf avoids it by parsing the double's canonical string form instead.
