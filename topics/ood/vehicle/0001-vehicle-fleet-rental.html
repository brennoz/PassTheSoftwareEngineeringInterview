Vehicle Fleet Rental — State Machine + Strategy + Observer

Lesson prepares you for: q127 — implement a fleet rental system combining an enum state machine with transition guards, a pricing strategy with duration tiers, and a maintenance observer that fires exactly when a mileage threshold is crossed.

The domain in one paragraph

A fleet rental company manages vehicles through a lifecycle: available → reserved → in use → awaiting inspection → available (or maintenance → available or retired). Pricing differs by vehicle class (Economy/Standard/Premium/Luxury) and rental duration — 7+ days earns a 15% discount, 28+ days earns 25%. When a vehicle is returned and its odometer reading has crossed a configured threshold during this rental, a maintenance observer is notified.

Three classic OO patterns compose here without coupling: state machine governs what is allowed, strategy governs pricing, observer governs side effects. Each is independently testable; Vehicle is the aggregate root that wires them.

Pattern 1 — Enum state machine with canTransitionTo

Why not a String field?

Storing status as String means: (1) typos compile silently; (2) any method can set vehicle.setStatus("RETIRED") regardless of current state; (3) transition rules scatter across every caller. An enum encodes the rules where they belong — on the state itself.

canTransitionTo vs canTransitionFrom

Two equivalent choices:

  • Source-state guard current.canTransitionTo(next) — "what can I become?" reads naturally at the call site in transitionTo().
  • Target-state guard next.canTransitionFrom(current) — "who may enter me?" used in q081 (booking lifecycle).

Both work. This solution uses canTransitionTo so the enum constant owns an explicit list of valid successors rather than valid predecessors — the successor set is smaller and easier to reason about for most states.

public enum VehicleStatus {

    AVAILABLE {
        @Override public boolean canTransitionTo(VehicleStatus next) {
            // Direct path to IN_USE is blocked — RESERVED is mandatory so the system
            // records who holds the vehicle before keys change hands.
            return next == RESERVED || next == RETIRED;
        }
    },
    RESERVED {
        @Override public boolean canTransitionTo(VehicleStatus next) {
            return next == AVAILABLE || next == IN_USE;
        }
    },
    IN_USE {
        @Override public boolean canTransitionTo(VehicleStatus next) {
            // Every return triggers an inspection — no shortcut to AVAILABLE.
            // Skipping inspection would let hidden damage go undetected.
            return next == AWAITING_INSPECTION;
        }
    },
    AWAITING_INSPECTION {
        @Override public boolean canTransitionTo(VehicleStatus next) {
            return next == AVAILABLE || next == MAINTENANCE;
        }
    },
    MAINTENANCE {
        @Override public boolean canTransitionTo(VehicleStatus next) {
            return next == AVAILABLE || next == RETIRED;
        }
    },
    RETIRED {
        @Override public boolean canTransitionTo(VehicleStatus next) {
            return false; // terminal state
        }
    };

    public abstract boolean canTransitionTo(VehicleStatus next);
}
Open/Closed in practice: adding an UNDER_RECALL state requires one new enum constant and updating the constants whose successor sets should include it. No change to Vehicle.transitionTo() — it always delegates to status.canTransitionTo(next).

transitionTo in Vehicle

private void transitionTo(VehicleStatus next) {
    if (!status.canTransitionTo(next)) {
        throw new InvalidStateTransitionException(id, status, next);
    }
    this.status = next;
}

Every public state-change method calls transitionTo(). No caller can bypass the guard by writing this.status = VehicleStatus.RETIRED directly — the field is private.

Pattern 2 — Strategy: PricingStrategy with duration tiers

Why Strategy and not a switch in Vehicle?

A switch on VehicleClass inside Vehicle would hard-code four pricing blocks. Adding a corporate discount tier, a peak-season surcharge, or a subscription model requires editing Vehicle — a class that has nothing to do with pricing logic. Strategy isolates the concern.

public interface PricingStrategy {
    Money calculateCost(RentalPeriod period);
}

public class VehiclePricingStrategy implements PricingStrategy {

    private static final BigDecimal WEEKLY_MULTIPLIER  = new BigDecimal("0.85");
    private static final BigDecimal MONTHLY_MULTIPLIER = new BigDecimal("0.75");

    private final BigDecimal dailyRate;
    private final String currency;

    public VehiclePricingStrategy(BigDecimal dailyRate, String currency) {
        this.dailyRate = dailyRate;
        this.currency  = currency;
    }

    @Override
    public Money calculateCost(RentalPeriod period) {
        long days = period.durationDays();
        BigDecimal multiplier = discountMultiplierFor(days);
        BigDecimal total = dailyRate
            .multiply(BigDecimal.valueOf(days))
            .multiply(multiplier)
            .setScale(2, RoundingMode.HALF_UP);
        return new Money(total, currency);
    }

    private BigDecimal discountMultiplierFor(long days) {
        if (days >= 28) return MONTHLY_MULTIPLIER;
        if (days >= 7)  return WEEKLY_MULTIPLIER;
        return BigDecimal.ONE;
    }
}
Off-by-one trap: the boundary is >= 7, not > 7. A 7-day rental earns the weekly discount. Writing > 7 silently excludes exactly-one-week rentals — a pricing bug that's invisible in tests unless you test the exact boundary value.

Why one implementation, not four?

Economy, Standard, Premium, and Luxury use identical tier logic — only the base rate differs. Four separate classes would be DRY-violating duplication. The rate travels with the enum constant (VehicleClass.STANDARD.getDailyRateGbp()); the factory wires it to a single strategy implementation.

public enum VehicleClass {
    ECONOMY(new BigDecimal("30.00")),
    STANDARD(new BigDecimal("50.00")),
    PREMIUM(new BigDecimal("80.00")),
    LUXURY(new BigDecimal("130.00"));

    private final BigDecimal dailyRateGbp;
    VehicleClass(BigDecimal dailyRateGbp) { this.dailyRateGbp = dailyRateGbp; }
    public BigDecimal getDailyRateGbp()   { return dailyRateGbp; }
}

public final class PricingStrategyFactory {
    public static PricingStrategy forClass(VehicleClass vehicleClass) {
        return new VehiclePricingStrategy(vehicleClass.getDailyRateGbp(), "GBP");
    }
    private PricingStrategyFactory() {}
}

Money as an immutable record

public record Money(BigDecimal amount, String currency) {
    public Money multiply(BigDecimal factor) {
        return new Money(amount.multiply(factor).setScale(2, RoundingMode.HALF_UP), currency);
    }
    public Money add(Money other) {
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("Cannot add " + currency + " and " + other.currency);
        return new Money(amount.add(other.amount).setScale(2, RoundingMode.HALF_UP), currency);
    }
}
Test with compareTo, not assertEquals: BigDecimal.equals() is scale-sensitive — 150.00 and 150.0 are equal numerically but not by .equals(). Always use assertEquals(0, actual.amount().compareTo(new BigDecimal("150.00"))) in tests.

Pattern 3 — Observer: MaintenanceObserver

Why Observer and not a return value?

Returning boolean maintenanceRequired from returnVehicle() pushes dispatch responsibility to every caller — a controller, a service, a scheduled job. Each must check the flag and decide what to do. When a second listener is added (compliance logger, customer notification), every caller needs updating. Observer keeps the what happened inside the domain; the what to do about it belongs to the listeners.

public interface MaintenanceObserver {
    void onMaintenanceRequired(String vehicleId, BigDecimal currentMileageKm);
}

The threshold-crossing constraint

The observer must fire only when the threshold is crossed during this rental. If the vehicle was already past the threshold at checkout, a maintenance order was already raised — firing again creates a duplicate work order and may double-book a technician.

public void checkout(BigDecimal mileageAtStart) {
    transitionTo(VehicleStatus.IN_USE);
    this.mileageAtCheckout  = mileageAtStart;
    this.currentMileage     = mileageAtStart;
}

public void returnVehicle(BigDecimal mileageAtReturn) {
    transitionTo(VehicleStatus.AWAITING_INSPECTION);
    this.currentMileage = mileageAtReturn;
    boolean wasBeforeThreshold  = mileageAtCheckout.compareTo(maintenanceThresholdKm) < 0;
    boolean isAtOrPastThreshold = mileageAtReturn.compareTo(maintenanceThresholdKm) >= 0;
    if (wasBeforeThreshold && isAtOrPastThreshold) {
        notifyObservers();
    }
}

private void notifyObservers() {
    for (MaintenanceObserver observer : observers) {
        observer.onMaintenanceRequired(id, currentMileage);
    }
}
Test this with Mockito, not a boolean flag: verify(observer, times(1)).onMaintenanceRequired("V-001", new BigDecimal("50200")) asserts both that the observer was called and what arguments it received. A hand-rolled boolean[] called = {false} lambda only tells you whether the observer fired — not whether the correct vehicleId or mileage was passed.

Quiz

Q1. In VehicleStatus, why is the path AVAILABLE → IN_USE (skipping RESERVED) blocked?

  • To reduce the number of valid transitions and simplify unit tests
  • The RESERVED step records who holds the vehicle before keys change hands — skipping it would mean keys were handed over with no record of the customer
  • IN_USE cannot follow AVAILABLE because they share the same database table row
  • Only MAINTENANCE can follow AVAILABLE in a valid fleet lifecycle
The state machine encodes a business rule: hand-over accountability. RESERVED is not ceremony — it creates an explicit record linking the vehicle to a customer before any physical handover. A Vehicle going directly to IN_USE has no reservation record, so you can't determine who is responsible for it.

Q2. A vehicle has maintenanceThresholdKm = 50,000. It was checked out at 51,000 km (already past threshold) and returned at 52,000 km. How many times does the observer fire?

  • Zero — the threshold was already passed at checkout, so wasBeforeThreshold is false and the condition short-circuits
  • Once — the vehicle is still past the threshold so the observer fires on every return
  • Twice — once at checkout and once at return
  • It throws IllegalStateException because the mileage at checkout already exceeded the threshold
The guard is: mileageAtCheckout < threshold && mileageAtReturn >= threshold. If checkout mileage is already 51,000 and the threshold is 50,000, wasBeforeThreshold is false — the entire condition is false regardless of return mileage. Zero notifications. This prevents duplicate maintenance work orders for the same threshold crossing.

Q3. A test asserts assertEquals(new BigDecimal("476.00"), cost.amount()) for a 7-day LUXURY rental (£130/day × 0.85). The production code calculates 130 × 7 × 0.85 = 773.50 using PREMIUM (£80/day) by mistake, but the test still passes. What is the likely cause?

  • BigDecimal.equals() ignores the value when scale differs
  • RoundingMode.HALF_UP always returns 476.00 for three-digit inputs
  • The test was accidentally written against PREMIUM (£80/day) rate rather than LUXURY (£130/day), so 80 × 7 × 0.85 = 476.00 — the test matches the wrong implementation
  • multiply() on BigDecimal silently caps at four significant digits
This is a "tests pass but the spec is wrong" failure — the test was written for the wrong vehicle class (PREMIUM at £80 gives 80 × 7 × 0.85 = 476.00; LUXURY at £130 gives 773.50). The assertion and the production code agree with each other and both disagree with the requirement. Always pick test inputs that would distinguish the classes being tested — and assert on the correct expected value for the class under test.

🤖 AI Engineering Extension

Where AI fits

Two components in the vehicle fleet system are strong candidates for AI augmentation:

  • Predictive maintenance: instead of a fixed odometer threshold, a model predicts failure probability from mileage, vehicle age, usage pattern (daily vs long-haul), and past repair history. The MaintenanceObserver interface accepts this model as a listener without changing Vehicle.
  • Dynamic pricing: a model learns that a LUXURY vehicle rented on a Friday in a city during a major event commands a higher rate. The PricingStrategy interface can be swapped for an ML-backed implementation without touching Vehicle.

Pattern

Predictive maintenance: classification / regression model trained on historical inspection outcomes (pass/fail, what was replaced, at what mileage). Input: vehicle age, class, mileage since last service, usage intensity. Output: failure probability score. Observer fires when score exceeds a threshold, not when a raw odometer number does.

Dynamic pricing: real-time inference via an ML model (gradient boosting or a neural net) serving through a REST endpoint. MLPricingStrategy calls the endpoint with (vehicleClass, rentalPeriod, location, time-of-year) and returns a Money quote. Fallback to rule-based VehiclePricingStrategy if inference is unavailable.

Architecture delta

  • New: MLPricingStrategy implementing PricingStrategy — same interface, AI-backed
  • New: PredictiveMaintenanceObserver implementing MaintenanceObserver — calls inference endpoint instead of checking raw mileage
  • New: ML inference service (SageMaker endpoint or Bedrock hosted model)
  • New: feature store (ElastiCache) for real-time vehicle usage features
  • No changes to Vehicle, VehicleStatus, or any existing strategy/observer classes

AWS managed services

  • Amazon SageMaker Real-Time Inference — host the maintenance predictor and pricing model; auto-scales with fleet activity
  • Amazon Bedrock — if the pricing or maintenance advisory needs natural-language explanation ("why is this vehicle flagged?"), an LLM via Bedrock can generate a human-readable justification from the model's feature importance output
  • Amazon ElastiCache — feature store for real-time vehicle usage data (mileage per day, idle time, weather exposure) — low-latency features at inference time
  • Amazon S3 + SageMaker Pipelines — training pipeline: daily dump of inspection outcomes → feature engineering → model retrain → A/B deploy to the endpoint

AI-Q: Your MLPricingStrategy calls a SageMaker endpoint for every getRentalCost() call. During a promotional campaign, the fleet website generates 5,000 quote requests per second. What is the most operationally important addition to MLPricingStrategy?

  • Increase SageMaker instance size to handle the load
  • A fallback to VehiclePricingStrategy (rule-based) when the inference call times out or returns an error — the service must remain available even when the model is unavailable
  • Cache every model output in a local HashMap keyed by vehicle class
  • Run inference asynchronously and return a default price immediately
A fallback to the rule-based strategy is mandatory for production resilience. SageMaker endpoints can cold-start, throttle, or fail. Without a fallback, every pricing failure becomes a customer-visible outage. The HashMap cache (option C) causes stale prices during a campaign and is wrong per-instance on a multi-pod deployment — use ElastiCache for shared cache if caching is needed at all.
