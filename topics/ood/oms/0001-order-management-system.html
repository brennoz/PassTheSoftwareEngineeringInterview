Order Management System — OOD Walkthrough

TradingCo prep  ·  OOD Lesson 1  ·  ~25 min

An Order Management System (OMS) tracks the path of a trade order from submission to final outcome. It is the central object in a trading platform — every participant (risk engine, P&L calculator, audit trail) reacts to order state changes. This lesson walks through the three patterns required for q129: State Machine, Strategy, and Observer — applied to the trading domain.

1 — The Order Lifecycle

An order is not simply "open" or "closed". It moves through a precise sequence of states, each triggered by an external event (venue acknowledgement, execution report, cancel confirm). The state machine must enforce which transitions are legal — an order cannot jump from NEW to FILLED; it must travel through every intermediate step.

NEW  ──submit──▶  PENDING_ACK  ──ack──▶  ACKNOWLEDGED  ──partial fill──▶  PARTIALLY_FILLED
                      │                        │                                    │
                      ▼                        ├──── cancel ──────────────▶  CANCELLED  (terminal)
                  REJECTED (terminal)          ├──── expire ──────────────▶  EXPIRED    (terminal)
                                               └──── full fill ──────────▶  FILLED      (terminal)
                                               (PARTIALLY_FILLED also → FILLED / CANCELLED)
Key insight — partial fills: A single order can receive many execution reports before it is completely filled. Each partial fill adds to the running total. The order auto-transitions to FILLED only when remainingQuantity() == 0.

State Machine Implementation — enum with abstract method

// Pattern: guards live on the SOURCE state, not in a central switch statement.
// Adding a new status (e.g. PENDING_CANCEL) only requires editing that new constant.
public enum OrderStatus {

    NEW {
        @Override public boolean canTransitionTo(OrderStatus next) {
            return next == PENDING_ACK;
        }
    },
    PENDING_ACK {
        @Override public boolean canTransitionTo(OrderStatus next) {
            return next == ACKNOWLEDGED || next == REJECTED;
        }
    },
    ACKNOWLEDGED {
        @Override public boolean canTransitionTo(OrderStatus next) {
            return next == PARTIALLY_FILLED || next == FILLED || next == CANCELLED || next == EXPIRED;
        }
    },
    PARTIALLY_FILLED {
        @Override public boolean canTransitionTo(OrderStatus next) {
            return next == PARTIALLY_FILLED || next == FILLED || next == CANCELLED;
        }
    },
    FILLED    { @Override public boolean canTransitionTo(OrderStatus next) { return false; } },
    CANCELLED { @Override public boolean canTransitionTo(OrderStatus next) { return false; } },
    REJECTED  { @Override public boolean canTransitionTo(OrderStatus next) { return false; } },
    EXPIRED   { @Override public boolean canTransitionTo(OrderStatus next) { return false; } };

    public abstract boolean canTransitionTo(OrderStatus next);
}
What NOT to do: Put a big switch (currentStatus) inside Order.java. Adding a new state then requires finding and editing that switch — scattered logic, easy to forget a case, OCP violation. With the enum-per-constant approach, you edit one constant and nothing else changes.

2 — Data-Carrying Enums (OrderType, TimeInForce)

Order types and time-in-force map directly to FIX protocol tag values on the wire. Storing those values in the enum eliminates a translation lookup in the routing layer.

// FIX tag 40 — OrdType
public enum OrderType {
    MARKET("1"),  // execute at best available price; no limit price
    LIMIT("2"),   // execute only at limitPrice or better
    STOP("3");    // triggers as MARKET when stop price is hit

    private final String fixOrdType;
    OrderType(String fixOrdType) { this.fixOrdType = fixOrdType; }
    public String getFixOrdType() { return fixOrdType; }
}

// FIX tag 59 — TimeInForce
public enum TimeInForce {
    DAY("0"),   // cancel at market close
    GTC("1"),   // Good Till Cancelled
    IOC("3"),   // Immediate Or Cancel
    FOK("4");   // Fill Or Kill
    ...
}
Why data-carrying enums here? Without the FIX value stored on the enum, every routing strategy would need a separate mapping table (a Map<OrderType, String>). The enum owns its own wire representation — one less moving part to keep in sync.

3 — Value Objects: Price and Execution

// Why BigDecimal: double cannot represent 0.1 exactly.
// In a regulated trading environment, floating-point drift = wrong fills = regulatory breach.
public record Price(BigDecimal value, String currency) {
    public Price {
        if (value == null || value.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException("Price must be non-negative: " + value);
        value = value.setScale(6, RoundingMode.HALF_UP);  // normalise scale for .equals() safety
    }
    public static Price of(String currency, String value) {
        return new Price(new BigDecimal(value), currency);
    }
}

// Immutable record — a single fill event from the venue.
// An order may receive many Executions before reaching FILLED.
public record Execution(
        String executionId,
        Price executionPrice,
        BigDecimal filledQuantity,
        Instant timestamp          // UTC — never LocalDateTime for cross-venue reconciliation
) { ... }

4 — Strategy: Order Routing

Different order types route differently: a MARKET order sends no price; a LIMIT order must include the limit price. The Strategy pattern isolates each routing variant behind an interface, so adding a new order type is a new class, not an edit to existing code.

public interface OrderRoutingStrategy {
    // Contract: must call order.pendingAck() before returning.
    void route(Order order);
}

// MARKET strategy — guards against a limit price being present
public class MarketOrderRoutingStrategy implements OrderRoutingStrategy {
    @Override
    public void route(Order order) {
        if (order.getLimitPrice() != null)
            throw new IllegalArgumentException("MARKET order must not carry a limit price");
        order.pendingAck();   // NEW → PENDING_ACK
        // Production: serialise to FIX NewOrderSingle (tag 35=D, tag 40=1)
    }
}

// LIMIT strategy — guards against a missing limit price
public class LimitOrderRoutingStrategy implements OrderRoutingStrategy {
    @Override
    public void route(Order order) {
        if (order.getLimitPrice() == null)
            throw new IllegalArgumentException("LIMIT order requires a limit price");
        order.pendingAck();   // NEW → PENDING_ACK
        // Production: serialise to FIX NewOrderSingle (tag 35=D, tag 40=2, tag 44=limitPrice)
    }
}

// OrderManager wires the strategies — EnumMap for O(1) lookup by enum ordinal
public class OrderManager {
    private final Map<OrderType, OrderRoutingStrategy> strategies = new EnumMap<>(OrderType.class);

    public OrderManager() {
        strategies.put(OrderType.MARKET, new MarketOrderRoutingStrategy());
        strategies.put(OrderType.LIMIT,  new LimitOrderRoutingStrategy());
        strategies.put(OrderType.STOP,   new MarketOrderRoutingStrategy()); // STOP executes at market
    }

    public Order submit(Order order) {
        globalListeners.forEach(order::addListener);
        strategies.get(order.getOrderType()).route(order);  // NEW → PENDING_ACK
        globalListeners.forEach(l -> l.onOrderSubmitted(order));
        return order;
    }
}

5 — Observer: Order Events

Multiple downstream systems react to order state changes: a risk engine needs to know about fills, an audit logger needs every transition, a P&L calculator needs execution prices. The Observer pattern lets Order fire events without knowing who is listening.

public interface OrderEventListener {
    void onOrderSubmitted(Order order);
    void onExecutionReceived(Order order, Execution execution);
    void onOrderTerminated(Order order);  // FILLED, CANCELLED, REJECTED, or EXPIRED
}

// Inside Order.applyExecution():
public void applyExecution(Execution execution) {
    executions.add(execution);
    BigDecimal remaining = remainingQuantity();
    if (remaining.compareTo(BigDecimal.ZERO) == 0) {
        transitionTo(OrderStatus.FILLED);
        listeners.forEach(l -> l.onExecutionReceived(this, execution));
        listeners.forEach(l -> l.onOrderTerminated(this));  // fires BOTH callbacks on final fill
    } else if (remaining.compareTo(BigDecimal.ZERO) > 0) {
        transitionTo(OrderStatus.PARTIALLY_FILLED);
        listeners.forEach(l -> l.onExecutionReceived(this, execution));
    } else {
        executions.remove(executions.size() - 1);          // roll back overfill
        throw new IllegalStateException("Execution would overfill order " + id);
    }
}
Common bug to avoid: On a final fill (remaining → 0), you must fire BOTH onExecutionReceived AND onOrderTerminated. Only firing the terminal event loses the execution details (price, quantity) that the audit trail needs. Only firing the execution event means downstream systems never know the order is done.

6 — The Order Aggregate (core logic)

public class Order {
    // Static factory: order always starts NEW — no public constructor with status param
    public static Order create(OrderSide side, String instrument, OrderType orderType,
            TimeInForce timeInForce, BigDecimal requestedQuantity, Price limitPrice) {
        if (orderType == OrderType.LIMIT && limitPrice == null)
            throw new IllegalArgumentException("LIMIT order requires a limit price");
        return new Order(...);
    }

    // remainingQuantity: stream over all executions, sum filledQuantity, subtract from requested
    public BigDecimal remainingQuantity() {
        BigDecimal filled = executions.stream()
                .map(Execution::filledQuantity)
                .reduce(BigDecimal.ZERO, BigDecimal::add);
        return requestedQuantity.subtract(filled);
    }

    // Single private guard — all state changes go through here
    private void transitionTo(OrderStatus next) {
        if (!status.canTransitionTo(next))
            throw new IllegalStateException(
                "Order " + id + ": illegal transition " + status + " → " + next);
        this.status = next;
    }

    // pendingAck() is package-private — only OrderRoutingStrategy calls it
    void pendingAck() { transitionTo(OrderStatus.PENDING_ACK); }
}

7 — Interview Talking Points

QuestionStrong answer
Why a separate PARTIALLY_FILLED status rather than just tracking a quantity field? Explicit status makes the lifecycle readable in logs, dashboards, and MiFID II audit trails. A reader sees "partially filled then cancelled" without inspecting quantity fields — and it enforces correct transition logic: a PARTIALLY_FILLED order can cancel, but a FILLED one cannot.
Why EnumMap for strategy lookup? EnumMap uses the enum ordinal as an array index — O(1) with no hash computation or bucket collision. Correct here because OrderType is a fixed, compile-time-known set. Also communicates intent: this map is enum-keyed, not String-keyed.
What happens if two executions arrive simultaneously? The current design is single-threaded (correct for the OOD scope). In production, the OMS would process execution reports on a dedicated thread (or LMAX Disruptor event handler), so applyExecution() is always called by one thread — no synchronization needed in the core domain object. External synchronization at the messaging layer.
Why BigDecimal for price and quantity? double cannot represent 0.1 exactly — floating-point drift in accumulated fills produces wrong totals. At scale, being wrong by a fraction of a cent is a regulatory non-compliance issue under MiFID II best-execution rules. BigDecimal gives exact decimal arithmetic at the cost of verbosity.
How does this relate to Event Sourcing? The execution list in Order is an append-only event log — the current state (filled quantity, status) is derived by replaying executions. A fully event-sourced OMS stores each transition as an immutable event in a journal (Kafka, Chronicle) and rebuilds state on replay. This design is a step toward that: the executions list is the raw data, not just a running total.

Quiz — check your understanding

Q1. Where should the canTransitionTo() logic live in the state machine pattern?

  • On each enum constant — guards on the source state
  • In Order.java as a switch statement on currentStatus
  • In a separate OrderStatusValidator utility class
  • In OrderManager, before calling any state-change method
Guards on the source state (each enum constant) mean adding a new status only requires editing that constant. A central switch in Order.java forces you to find and edit that switch every time — a scattered, OCP-violating design that has caused real bugs when engineers added a new status and missed a case.

Q2. applyExecution() receives a fill for the remaining 40 shares of a 100-share order (60 already filled). What should happen?

  • Transition to PARTIALLY_FILLED and fire onExecutionReceived only
  • Transition to FILLED and fire both onExecutionReceived and onOrderTerminated
  • Transition to FILLED and fire onOrderTerminated only
  • Remain in PARTIALLY_FILLED until the caller explicitly calls complete()
When remaining quantity reaches zero, the order auto-transitions to FILLED and must fire BOTH callbacks. Firing only onOrderTerminated loses the execution details (price, quantity) needed by the audit trail and P&L calculator. Firing only onExecutionReceived means downstream systems never know the order is complete. The caller must not decide the terminal state.

Q3. Why does Order.create() validate that MARKET orders have no limit price?

  • FIX protocol requires tag 44 to be absent for OrdType=1
  • Market orders with a price are treated as limit orders by all venues
  • Venue behaviour for a MARKET with a limit price is undefined and inconsistent
  • The MarketOrderRoutingStrategy would null-pointer without the guard
Venue behaviour varies: some reject the order outright, some silently ignore the price, some treat it as a LIMIT order. All three outcomes are wrong — you get either a rejection or an unexpected fill type. The guard at construction time prevents the wrong combination from ever reaching the routing layer, regardless of which venue is connected.

Q4. What is the correct collection type for storing routing strategies keyed by OrderType?

  • HashMap<OrderType, OrderRoutingStrategy> — standard map, correct result
  • TreeMap<OrderType, OrderRoutingStrategy> — sorted, log(N) lookup
  • LinkedHashMap<OrderType, OrderRoutingStrategy> — insertion-order iteration
  • EnumMap<OrderType, OrderRoutingStrategy> — array-backed, O(1), enum-safe
EnumMap is purpose-built for enum keys: it uses the enum's ordinal as an array index, giving O(1) lookup with no hash computation or collision. For a fixed, compile-time-known key set like OrderType, it's strictly better than HashMap — and it communicates the intent (this is an enum-keyed map) more clearly than a generic Map.
