Command Pattern — Payment Transaction Log with Undo

Question this lesson prepares you for: q126 — implement a wallet payment processor using the Command pattern with execute, undo, and audit log.

The problem without Command

A naive payment service hard-codes operations directly:

public void debit(Wallet wallet, BigDecimal amount) {
    wallet.setBalance(wallet.getBalance().subtract(amount));
}

public void credit(Wallet wallet, BigDecimal amount) {
    wallet.setBalance(wallet.getBalance().add(amount));
}

Three problems: (1) undo is impossible — nothing records what happened, so reversing a transaction requires knowing which method was called with which arguments; (2) audit log requires manual plumbing — you must add logging to every new operation method; (3) operations are not first-class objects — you cannot queue them, delay them, retry them, or pass them around as data.

Command pattern — four roles

RoleWhoResponsibility
CommandPaymentCommand interfaceDeclares execute() and undo()
Concrete CommandDebitCommand, CreditCommandHolds receiver + amount; implements both methods
ReceiverWalletOwns the balance; performs the real work
InvokerPaymentProcessorExecutes commands; maintains history stack + audit log
Key insight: the Invoker knows nothing about what a command does. It only calls execute() and undo(). Adding a new operation (e.g. FreezeCommand) requires zero changes to PaymentProcessor.

The Command interface

// execute() performs the operation; undo() reverses it exactly
public interface PaymentCommand {
    void execute();
    void undo();
    String description(); // for audit log
}

Receiver — Wallet

public class Wallet {
    private BigDecimal balance;

    public Wallet(BigDecimal initialBalance) {
        this.balance = initialBalance;
    }

    // Raw balance mutations — no business logic here.
    // Validation (e.g. insufficient funds) belongs in the Command or Invoker.
    public void debit(BigDecimal amount) {
        balance = balance.subtract(amount);
    }

    public void credit(BigDecimal amount) {
        balance = balance.add(amount);
    }

    public BigDecimal getBalance() { return balance; }
}

Concrete Commands

public class DebitCommand implements PaymentCommand {
    private final Wallet wallet;
    private final BigDecimal amount;
    private final String description;

    public DebitCommand(Wallet wallet, BigDecimal amount, String description) {
        this.wallet = wallet;
        this.amount = amount;
        this.description = description;
    }

    @Override
    public void execute() { wallet.debit(amount); }

    // Undo a debit by crediting the same amount — compensation transaction
    @Override
    public void undo() { wallet.credit(amount); }

    @Override
    public String description() { return description; }
}

public class CreditCommand implements PaymentCommand {
    private final Wallet wallet;
    private final BigDecimal amount;
    private final String description;

    // ... same constructor pattern ...

    @Override
    public void execute() { wallet.credit(amount); }

    // Undo a credit by debiting the same amount
    @Override
    public void undo() { wallet.debit(amount); }

    @Override
    public String description() { return description; }
}
BigDecimal — never double for money. new BigDecimal(0.1) is 0.1000000000000000055511151231257827021181583404541015625. Always use new BigDecimal("0.10") or BigDecimal.valueOf(10, 2). Operations: add, subtract, multiply; for division always supply scale + RoundingMode.HALF_UP. Comparisons: compareTo, never equals (scale-sensitive: new BigDecimal("10.0").equals(new BigDecimal("10.00")) is false).

Invoker — PaymentProcessor

public class PaymentProcessor {
    // Deque used as a stack: push = addFirst, pop = removeFirst
    // Why not Stack? Stack extends Vector (synchronized, legacy); ArrayDeque is modern.
    private final Deque<PaymentCommand> history = new ArrayDeque<>();

    // All executed commands recorded here — including undone ones.
    // In production this would be a durable outbox / event log.
    private final List<String> auditLog = new ArrayList<>();

    public void execute(PaymentCommand command) {
        command.execute();
        history.addFirst(command);            // push
        auditLog.add("EXECUTED: " + command.description());
    }

    public void undoLast() {
        if (history.isEmpty()) throw new IllegalStateException("Nothing to undo");
        PaymentCommand last = history.removeFirst(); // pop
        last.undo();
        auditLog.add("UNDONE: " + last.description());
    }

    public List<String> getAuditLog() {
        return Collections.unmodifiableList(auditLog);
    }
}

Why Deque not Stack?

java.util.Stack extends Vector — which is synchronized on every method and considered legacy. ArrayDeque is the modern unsynchronized alternative and faster for single-threaded use. Use addFirst/removeFirst for stack semantics (LIFO).

Extension without modification

Open/Closed in practice: adding a FreezeCommand (locks the wallet, undo unlocks it) requires:

  • New class FreezeCommand implements PaymentCommand
  • New method on Wallet: freeze() / unfreeze()
  • Zero changes to PaymentProcessor

Command vs Strategy vs Template Method
Strategy: swaps how one algorithm is performed (e.g. discount calculation).
Template Method: fixes when steps run; subclasses fill in the steps.
Command: wraps an entire operation as an object — enabling undo, queuing, logging. The difference: Command is about what to do and when to reverse it.

Quiz

Q1. In the Command pattern, which class should contain the undo logic — the Invoker or the Concrete Command?

  • Invoker — it owns the history stack so it knows what to reverse
  • Concrete Command — it knows what it did and how to reverse exactly that operation
  • Receiver — it owns the state so it should also own reversal
  • A separate UndoManager class outside the pattern
The Concrete Command holds the receiver reference and the exact parameters used in execute(). Only it knows "I debited £30 from this wallet" — so only it can reverse that precisely. The Invoker just calls command.undo() blindly.

Q2. Why use ArrayDeque instead of Stack for the history stack in PaymentProcessor?

  • Stack extends Vector which is synchronized on every method — unnecessary overhead and legacy design; ArrayDeque is the modern unsynchronized replacement
  • ArrayDeque supports FIFO ordering which is required for correct undo sequencing
  • Stack doesn't support generics
  • ArrayDeque has O(1) random access which is needed for multi-level undo
java.util.Stack extends Vector — a synchronized, legacy class from Java 1.0. The synchronization is coarse-grained and unnecessary in single-threaded contexts. ArrayDeque (Java 6+) is faster, not synchronized, and explicitly recommended by the Javadoc as the stack/deque replacement. Use addFirst/removeFirst for LIFO.
