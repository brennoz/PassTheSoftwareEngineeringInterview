Payment Gateway OOD

Patterns: Builder · State Machine · Strategy (Value Object) · Service Layer

Domain: Fintech / UK card payments (Opayo / Sage Pay style)

Why this design matters

A payment gateway integration sits at the money boundary of your system. Three properties are non-negotiable here:

  • Precision — monetary amounts use BigDecimal, never double. One floating-point rounding error is a regulatory incident.
  • Valid state transitions — a payment must follow a strict lifecycle (Authorise → Capture → Settle). Accepting a capture on a voided payment is a financial loss.
  • Immutable audit trail — every status change is recorded. You cannot delete or update posted entries.

Value Object: Money Value Object

What: an immutable pair of (BigDecimal amount, Currency currency).
Why: grouping them prevents "£10 treated as $10" bugs. Immutability means arithmetic always produces a new Money, preventing accidental mutation of a transaction record. 

public record Money(BigDecimal amount, Currency currency) {

    public Money {
        Objects.requireNonNull(amount);
        Objects.requireNonNull(currency);
        if (amount.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException("Amount must be non-negative");
    }

    public Money add(Money other) {
        assertSameCurrency(other);
        return new Money(amount.add(other.amount), currency);
    }

    public Money subtract(Money other) {
        assertSameCurrency(other);
        BigDecimal result = amount.subtract(other.amount);
        if (result.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException("Insufficient amount");
        return new Money(result, currency);
    }

    private void assertSameCurrency(Money other) {
        if (!currency.equals(other.currency))
            throw new IllegalArgumentException("Currency mismatch");
    }
}
Never use double for money. 0.1 + 0.2 == 0.30000000000000004 in floating point. In fintech, that's a £0.000000000000004 rounding error per transaction — multiplied by millions of transactions and audited by the FCA.

Builder Pattern: PaymentRequest Builder

When to use Builder: when an object has >4 fields and several are optional, telescoping constructors become unreadable. Builder also gives you a validation hook before construction.

A payment request in Opayo style includes: card token (PAN never stored), amount, merchant ID, merchant reference (idempotency key), description, optional 3DS challenge flag. 

public record PaymentRequest(
        String  cardToken,
        Money   amount,
        String  merchantId,
        String  merchantReference,  // idempotency key
        String  description,
        boolean require3ds
) {
    public static Builder builder() { return new Builder(); }

    public static final class Builder {
        private String  cardToken, merchantId, merchantReference, description;
        private Money   amount;
        private boolean require3ds = false;

        public Builder cardToken(String t)            { cardToken = t;          return this; }
        public Builder amount(Money m)              { amount = m;             return this; }
        public Builder merchantId(String id)         { merchantId = id;        return this; }
        public Builder merchantReference(String ref) { merchantReference = ref; return this; }
        public Builder description(String d)         { description = d;        return this; }
        public Builder require3ds()                  { require3ds = true;     return this; }

        public PaymentRequest build() {
            Objects.requireNonNull(cardToken,          "cardToken required");
            Objects.requireNonNull(amount,             "amount required");
            Objects.requireNonNull(merchantId,         "merchantId required");
            Objects.requireNonNull(merchantReference,  "merchantReference required");
            return new PaymentRequest(cardToken, amount, merchantId, merchantReference, description, require3ds);
        }
    }
}
merchantReference = idempotency key. If the client retries the same payment (network timeout), the gateway checks this reference first. If a transaction with that reference already exists, return the existing result — don't charge twice. This is the most common fintech interview probe.

State Machine: PaymentStatus State Machine

Payment lifecycle has strict one-way transitions. Encode the valid transitions in the enum itself so no external caller can put a payment into an invalid state.

INITIATED ──authorise──▶ AUTHORISED ──capture──▶ CAPTURED ──settle──▶ SETTLED │ │ ▼ ▼ FAILED VOIDED CAPTURED ──refund──▶ REFUNDED
public enum PaymentStatus {
    INITIATED {
        @Override public boolean canTransitionTo(PaymentStatus next) {
            return next == AUTHORISED || next == FAILED;
        }
    },
    AUTHORISED {
        @Override public boolean canTransitionTo(PaymentStatus next) {
            return next == CAPTURED || next == VOIDED;
        }
    },
    CAPTURED {
        @Override public boolean canTransitionTo(PaymentStatus next) {
            return next == SETTLED || next == REFUNDED;
        }
    },
    SETTLED, VOIDED, REFUNDED, FAILED;

    public boolean canTransitionTo(PaymentStatus next) { return false; } // terminal

    public void assertCanTransitionTo(PaymentStatus next) {
        if (!canTransitionTo(next))
            throw new IllegalStateException(
                "Cannot transition from " + this + " to " + next);
    }
}
Why encode transitions in the enum? If transition logic lives in the service, every developer can accidentally add a new path ("let me just set VOIDED directly"). Embedding guards in the enum makes invalid transitions impossible to compile into the codebase quietly — the check is always there.

Gateway Interface: PaymentGateway Strategy

The actual card network call (Visa/Mastercard) is behind an interface. In production this calls Opayo's REST API. In tests, a StubPaymentGateway returns pre-configured responses. This is the Strategy pattern — the caller doesn't care which gateway handles the request. 

public interface PaymentGateway {
    GatewayResponse authorise(PaymentRequest request);
    GatewayResponse capture(String gatewayTransactionId);
    GatewayResponse voidPayment(String gatewayTransactionId);
    GatewayResponse refund(String gatewayTransactionId, Money amount);
}

public record GatewayResponse(
        String gatewayTransactionId,
        boolean success,
        String message
) {}

Service Layer: PaymentService

Service owns all state transitions. It delegates the actual card network call to PaymentGateway, then advances the payment's status. If the gateway returns failure, status → FAILED. 

public class PaymentService {
    private final PaymentGateway gateway;
    private final PaymentRepository repo;

    public Payment initiate(PaymentRequest request) {
        Payment payment = new Payment(UUID.randomUUID().toString(), request, PaymentStatus.INITIATED);
        repo.save(payment);
        return payment;
    }

    public Payment authorise(String paymentId) {
        Payment payment = findOrThrow(paymentId);
        payment.status().assertCanTransitionTo(PaymentStatus.AUTHORISED);
        GatewayResponse resp = gateway.authorise(payment.request());
        PaymentStatus next = resp.success() ? PaymentStatus.AUTHORISED : PaymentStatus.FAILED;
        return repo.updateStatus(paymentId, next, resp.gatewayTransactionId());
    }

    // capture / void / refund follow same pattern
}
Why service layer (not rich domain)? Payment is a thin record. Status-transition logic lives in PaymentStatus (the enum). Network calls live in PaymentGateway. This separation makes each piece unit-testable in isolation — you can test state machine logic without any gateway, and gateway behaviour with a stub, never touching the database.

Repository pattern

public class InMemoryPaymentRepository implements PaymentRepository {
    private final Map<String, Payment> store = new HashMap<>();

    public void save(Payment p)   { store.put(p.id(), p); }
    public Optional<Payment> findById(String id) {
        return Optional.ofNullable(store.get(id));
    }
    public Payment updateStatus(String id, PaymentStatus status, String gatewayTxId) {
        Payment existing = findOrThrow(id);
        Payment updated = existing.withStatus(status).withGatewayTxId(gatewayTxId);
        store.put(id, updated);
        return updated;
    }
}

Common Pitfalls (interview watch-outs)

  • double for amount — always BigDecimal; PCI-DSS requires exact amounts in audit logs
  • Storing raw PAN — card number must be tokenised by the gateway; never persisted in your DB (PCI-DSS scope)
  • Missing idempotency check — retry without checking merchantReference → double charge
  • Transition guard in service only — if guard is in service but state transitions can also happen via background jobs or events, the guard is bypassable
  • Mutable Payment record — if setStatus() exists, concurrent threads can corrupt state; produce new instances on update

Quiz

Q1: A client retries a payment request because the first response timed out. The payment was already authorised. What prevents a double charge?

  • The state machine — INITIATED can only transition to AUTHORISED once
  • The PaymentGateway interface — it is a no-op on retry
  • The merchantReference idempotency key — service checks for an existing payment with that reference before calling the gateway
  • The PaymentRepository — save() throws if the ID already exists
The state machine only prevents the same payment object from being authorised twice, but a retry creates a new payment object. The idempotency key (merchantReference) lets the service detect that this request was already processed and return the existing result instead of calling the gateway again.

Q2: Why should canTransitionTo() logic live inside the PaymentStatus enum rather than in PaymentService?

  • Enums are faster than service method calls at runtime
  • It allows the service to avoid switch statements
  • It co-locates the state machine contract with the state definition, making it impossible to bypass by adding a new code path in a service
  • Enum methods are automatically thread-safe
If guard logic is in the service, any developer adding a new endpoint or background job can bypass it. Placing canTransitionTo() in the enum means the check is inseparable from the status value itself — you cannot advance state without going through the guard.

Q3: You need to add a new payment method (Apple Pay token). What changes in the design?

  • A new PaymentGateway implementation for Apple Pay; PaymentRequest might add a paymentMethodType field; no other classes change
  • A new subclass of PaymentRequest and a new PaymentService subclass
  • A new enum constant in PaymentStatus for APPLE_PAY_PENDING
  • The state machine must be duplicated for Apple Pay flows
Strategy pattern: the PaymentGateway interface absorbs new payment methods without changing the service, repository, or state machine. The service calls gateway.authorise(request) regardless of method type — the gateway implementation handles the specifics. This is Open/Closed principle: open for extension (new gateway), closed for modification (existing service unchanged).
