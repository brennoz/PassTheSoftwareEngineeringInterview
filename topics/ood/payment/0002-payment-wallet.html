The problem — concurrent debit race condition

Two API pods each read a Wallet with balance £100. Both check: is 100 ≥ 80? Yes. Both approve an £80 withdrawal. Both commit. Balance becomes £-60.

This is a read-modify-write race condition — the most dangerous bug in any payment system. The consequence is money creation out of thin air: a regulatory violation, a direct financial loss, and an immediate audit trigger.

Why it happens: The check (balance ≥ amount) and the write (balance -= amount) are two separate operations. Without coordination, another pod can sneak its write in between them. In a single-pod system, synchronized on the method would prevent it. In a multi-pod cluster, synchronized does nothing — each pod has its own JVM heap.

Domain model diagram

Wallet (aggregate root) walletId : WalletId ← value object — no primitive obsession ownerId : String balance : BigDecimal ← NEVER double/float (see §5 for why) version : int ← optimistic lock counter; JPA manages this with @Version WalletTransaction (value object — idempotency record) transactionId : String ← idempotency key (UUID supplied by caller, not generated here) walletId : WalletId type : TransactionType (CREDIT / DEBIT) amount : BigDecimal createdAt : Instant

The WalletId value object wraps a raw string — it prevents mixing up wallet IDs with user IDs or transaction IDs in method signatures. The WalletTransaction record is the idempotency receipt: persisting it is what makes the debit replay-safe.

Optimistic vs pessimistic locking

Optimistic Pessimistic
Mechanism version field + Compare-And-Swap (CAS) in DB SELECT FOR UPDATE row lock
Throughput High — no lock contention in the happy path Low — debits on the same wallet are serialised
Failure mode OptimisticLockException → retry or 409 Deadlock if two threads acquire locks in different order
Best for Low contention — most debits succeed on first try High contention — many concurrent writes on the same row
JPA annotation @Version on the entity field LockModeType.PESSIMISTIC_WRITE on the query

Payment wallets are a classic optimistic locking use case: the vast majority of debits do not conflict. The rare conflict retries once and succeeds. Pessimistic locking would cap throughput to the rate at which the DB can release row locks — unacceptable during a flash sale or high-traffic event.

How optimistic locking works — step by step

  1. Thread A reads Wallet, gets balance=£100, version=5
  2. Thread B reads Wallet, also gets balance=£100, version=5
  3. Thread A calls debit(£80). Wallet produces a new instance with balance=£20, version=6. Service issues:
    UPDATE wallet SET balance=20, version=6 WHERE id=? AND version=5 → 1 row affected ✓
  4. Thread B also calls debit(£80). Wallet produces balance=£20, version=6. Service issues the same UPDATE — but version in DB is now 6, not 5 → 0 rows affected
  5. Service detects 0 rows affected → throws OptimisticLockException
  6. Caller catches it and either retries (re-reads wallet, re-checks balance) or returns 409 Conflict to client
Key insight: The version check turns a two-step read-then-write into an atomic single-step compare-and-swap at the database layer. The race window is eliminated because the DB only applies the write if the world still looks the same as when we read it.

Wallet record

// Pattern: Aggregate Root — Wallet owns its balance; no external class can mutate it directly.
// version field simulates @Version (JPA optimistic lock). In prod: JPA manages this automatically.
public record Wallet(WalletId walletId, String ownerId, BigDecimal balance, int version) {

    // Why withBalance not a setter? Records are immutable. withBalance creates a new
    // Wallet with bumped version — caller passes it to the repo which does the CAS check.
    public Wallet withBalance(BigDecimal newBalance) {
        return new Wallet(walletId, ownerId, newBalance, version + 1);
    }

    // Why BigDecimal not double?
    // double 0.1 + 0.2 = 0.30000000000000004 — wrong in a financial context.
    // BigDecimal("0.10") + BigDecimal("0.20") = BigDecimal("0.30") — exact.
    // Regulatory requirement: monetary amounts must be exact (FCA, PSD2).
    public boolean hasSufficientFunds(BigDecimal amount) {
        return balance.compareTo(amount) >= 0;
    }
}

Records bump the version on every withBalance() call. The repository's CAS check uses the old version to guard the UPDATE. If two threads call withBalance() on the same original Wallet, they both produce version=6 — but only the first one's CAS will match the DB which still has version=5; the second finds version already advanced and fails.

WalletRepository interface

public interface WalletRepository {
    void save(Wallet wallet);                    // INSERT — new wallet only
    Optional<Wallet> findById(WalletId id);

    // CAS (Compare-And-Swap): UPDATE WHERE version = expectedVersion
    // Returns false if version mismatch — caller handles conflict
    boolean updateIfVersionMatches(Wallet wallet);

    // Idempotency: has this transactionId already been processed?
    boolean transactionExists(String transactionId);
    void recordTransaction(WalletTransaction tx);
}

updateIfVersionMatches is the CAS gate. It issues the conditional UPDATE and returns true only when one row was affected. transactionExists and recordTransaction together provide idempotency: check before debit, record after debit. In production these two calls live inside the same DB transaction as the balance UPDATE to make the idempotency record and the balance change atomic.

WalletService.debit()

// Why: debit is the critical path — two concurrent calls on same wallet must not both succeed.
// Algorithm: optimistic CAS (read → check → CAS → throw on conflict; caller retries).
// Alternative (pessimistic lock) would serialise all debits on same wallet → lower throughput.
public WalletTransaction debit(WalletId walletId, BigDecimal amount, String transactionId) {

    // Idempotency: replay-safe. If this transactionId was already processed, return early.
    // In prod: network retry from client must not double-debit.
    if (walletRepo.transactionExists(transactionId)) {
        throw new DuplicateTransactionException(transactionId);
    }

    Wallet wallet = walletRepo.findById(walletId)
            .orElseThrow(() -> new WalletNotFoundException(walletId));

    if (!wallet.hasSufficientFunds(amount)) {
        throw new InsufficientFundsException(walletId, amount, wallet.balance());
    }

    Wallet updated = wallet.withBalance(wallet.balance().subtract(amount));

    // CAS: only succeeds if version still matches what we read.
    // If another thread committed first, version bumped → false → OptimisticLockException.
    if (!walletRepo.updateIfVersionMatches(updated)) {
        throw new OptimisticLockException("Concurrent debit conflict on wallet " + walletId);
    }

    WalletTransaction tx = new WalletTransaction(transactionId, walletId,
            TransactionType.DEBIT, amount, Instant.now());
    walletRepo.recordTransaction(tx);
    return tx;
}
Interview check: The idempotency check comes before the balance read, not after. If you check after the CAS, a race exists where two threads both pass the idempotency check and then race on the CAS — only one wins, which is correct, but you've added unnecessary round trips. Checking first eliminates duplicate work entirely.

Quiz

Q1. Two pods each read a Wallet with balance=£100, version=5. Pod A debits £80 — CAS succeeds, version advances to 6, balance is now £20. Pod B then attempts to debit £80 using the stale version=5 it read earlier. What happens with optimistic locking?

  • Both succeed — balance becomes £-60 because CAS does not protect across pods
  • Pod B's CAS issues UPDATE ... WHERE version=5, finds version is now 6, gets 0 rows affected, and throws OptimisticLockException — balance stays £20
  • Pod B waits for Pod A's lock to release before deducting
  • Pod B automatically re-reads the updated version before executing the debit
Pod B's CAS fails with OptimisticLockException. The CAS guard (WHERE version = 5) is evaluated atomically by the database. By the time Pod B issues its UPDATE, the DB already has version=6 from Pod A's committed write. 0 rows are affected, the service detects this, and throws OptimisticLockException. The caller either retries (re-reads wallet, re-checks balance — which now shows £20, insufficient for £80) or returns 409 Conflict to the client. Option 1 describes the bug that exists without optimistic locking. Options 3 and 4 describe pessimistic locking, which is a different mechanism.

Q2. A client sends the same debit request twice due to a network retry. Both requests carry the same transactionId (UUID generated client-side). With idempotency correctly implemented, what is the result?

  • Two debits are applied — the balance is deducted twice
  • The second request detects the existing transactionId, throws DuplicateTransactionException, and no second debit is applied
  • The second request throws 500 Internal Server Error because the UUID already exists in the DB
  • The first request is rolled back and only the second is applied
Second request is a silent no-op — balance deducted exactly once. walletRepo.transactionExists(transactionId) returns true on the second call. The service throws DuplicateTransactionException before touching the balance. The caller (REST controller) catches it and returns 200 with the original transaction record — to the client it looks identical to a successful first call. In production: the idempotency record stores the original response payload; the second call returns that payload without re-executing the debit. AWS: DynamoDB ConditionExpression: attribute_not_exists(transactionId) enforces uniqueness atomically — the INSERT fails on duplicate and the Lambda returns the previously stored response.

Q3. A junior developer changes BigDecimal balance to double balance in the Wallet record to "simplify arithmetic." Which failure scenario is possible?

  • Balance becomes negative — BigDecimal has the same precision problem
  • Balance rounds to whole pounds, losing pence precision entirely
  • 0.1 + 0.2 evaluates to 0.30000000000000004 in IEEE 754 double — small errors accumulate across millions of transactions, causing reconciliation failures and regulatory non-compliance (FCA, PSD2)
  • double is 64-bit and has enough precision for any monetary amount
Floating point precision errors accumulate and cause reconciliation failures. double uses IEEE 754 binary floating point — it cannot represent many decimal fractions exactly. 0.1 + 0.2 = 0.30000000000000004. Over millions of transactions, rounding errors accumulate into pence or pound discrepancies. This triggers end-of-day reconciliation failures, regulatory reports that don't balance, and potential FCA/PSD2 audit findings. BigDecimal uses arbitrary-precision decimal arithmetic — new BigDecimal("0.10").add(new BigDecimal("0.20")) returns exactly 0.30. Always initialise with a String constructor, not a double literal (new BigDecimal(0.1) has the same precision problem). Option 4 is the most common misconception — 64-bit width addresses magnitude, not decimal precision.

🤖 AI Engineering Extension

Where AI fits

The WalletService.debit() method is a natural insertion point for a fraud classifier. Before the CAS step commits money, an ML model evaluates whether the transaction looks fraudulent given the user's recent behaviour, merchant category, amount, location, and time-of-day.

Pattern

Binary classifier (approve / decline) trained on labelled transaction features. Features: debit amount, merchant category code, time since last debit, debits-in-last-hour velocity counter, device fingerprint, geolocation delta. Backed by a rule engine fallback for low-confidence predictions.

Architecture delta

New boxes inserted between the idempotency check and the CAS step:

  • FraudDetectionService — HTTP call to ML model endpoint (SageMaker real-time or Bedrock Claude) with transaction features as JSON; returns APPROVE / DECLINE / REVIEW
  • VelocityCounter — Redis INCR per (walletId, 1h window) — how many debits has this wallet executed in the last hour? Feeds the classifier as a feature
  • FraudDecisionCache — Redis cache on (walletId, amountBucket, merchantCategoryCode) for repeated identical patterns — avoids redundant ML calls at <20ms

Tradeoffs

AWS managed services

  • Amazon Bedrock — managed Claude/Titan inference; no model ops; pay-per-token; good for low-volume or complex reasoning tasks
  • Amazon SageMaker real-time endpoint — host custom XGBoost or neural fraud model; sub-50ms p99; auto-scales with traffic
  • ElastiCache (Redis OSS) — velocity counters (INCR + EXPIRE) and inference result cache
  • Amazon Kinesis Data Streams — stream every debit event to a feature store for model retraining; near-real-time feedback loop
  • Amazon Comprehend — classify merchant name strings into merchant category codes if the raw merchant string arrives from the acquirer unparsed

AI-Q: A fraud model runs before the CAS step. The model approves the transaction. Then the CAS fails (another pod's debit committed first, causing an OptimisticLockException). Your service re-reads the wallet and retries. Should you re-run the fraud check on the retry attempt?

  • Yes — transaction context may have changed: the velocity counter incremented (one more debit this hour), time has passed, the post-CAS balance is different, and the model may now produce a different signal. Always re-evaluate fraud on retry.
  • No — the model already approved once; re-running wastes latency and money; cache the decision against the transactionId
  • No — the CAS failure is a concurrency event, not a fraud signal; fraud check only needs to run once per transactionId
  • It depends on the model's confidence score — re-run only if confidence was below 95%
Re-run the fraud check. When the CAS fails and you retry, you re-read the wallet — which now has a lower balance, a higher version, and a higher velocity counter (because the intervening debit incremented it). These are new features the model has not seen. The model's approval on the first attempt was based on state that is now stale. In a fraud context, the velocity counter alone can tip a borderline transaction from APPROVE to REVIEW — and that counter just increased. The extra latency (~20ms) on a retry path (which is rare in low-contention systems) is acceptable given the regulatory consequence of approving a fraudulent transaction. Cache invalidation strategy: use the transactionId as cache key but set TTL to 0 on retry — force a fresh evaluation.
