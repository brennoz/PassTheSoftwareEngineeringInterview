Lesson 01 — Elevator System Domain Model

Category: OOD · Difficulty: Medium · Est. time: 25 min · Lesson 1 of N

Elevator System is a classic OOD interview question — a small state machine (idle, moving, door open) wrapped in a dispatch decision (which pending request to serve next). This lesson builds the full solution: State Pattern for the elevator's lifecycle, Strategy Pattern for the scheduling algorithm, and an orchestrator that ties both together — the same two-pattern shape as q030_library_system's BookCopy/Fine design, applied to a different domain.

What you will be able to do after this lesson Given "design an elevator system," name the State and Strategy patterns correctly, explain why the state objects — not the elevator — own transition legality, and swap a scheduling algorithm (FCFS vs SCAN) without touching the service.

2. State Pattern — the elevator lifecycle

┌─────────┐ │ IDLE │◄─────────────────────┐ └────┬────┘ │ │ move() │ ┌────▼────┐ │ │ MOVING │ │ └────┬────┘ │ │ arrive() │ closeDoor() ┌────▼─────┐ │ │DOOR_OPEN │─────────────────────┘ └──────────┘
// Pattern: State — each state is an object; only the transition(s) legal from
// that state are implemented as a no-op, every other method throws IllegalStateException
public interface ElevatorState {
    void move(Elevator elevator);
    void arrive(Elevator elevator);
    void closeDoor(Elevator elevator);
    String name();
}

public class IdleState implements ElevatorState {
    @Override
    public void move(Elevator elevator)      { elevator.setState(new MovingState()); }
    @Override
    public void arrive(Elevator elevator)    { throw new IllegalStateException("Cannot arrive: elevator is not moving"); }
    @Override
    public void closeDoor(Elevator elevator) { throw new IllegalStateException("Cannot close door: elevator door is not open"); }
    @Override public String name()           { return "IDLE"; }
}

// MovingState and DoorOpenState follow the same pattern — each allows exactly one
// transition (arrive() and closeDoor() respectively) and throws on the other two.

public class Elevator {

    private final String id;
    private int currentFloor;
    // State held as object, not enum — transitions are encapsulated in
    // the state itself, Elevator only delegates
    private ElevatorState state = new IdleState();

    public Elevator(String id, int currentFloor) {
        this.id = id;
        this.currentFloor = currentFloor;
    }

    public void move()      { state.move(this); }
    public void arrive(int newFloor) { state.arrive(this); this.currentFloor = newFloor; }
    public void closeDoor() { state.closeDoor(this); }

    void setState(ElevatorState state) { this.state = state; }   // package-private
    public String getStatus() { return state.name(); }
}
The mistake this exact question invites Same trap as q030's BookCopy: writing all three state classes correctly, then wiring Elevator to mutate state directly instead of delegating — elevator.state = new MovingState() inside Elevator.move() instead of state.move(this). Every guard you wrote in the state classes becomes dead code the moment Elevator bypasses them. Rule to say out loud: the state object controls the transition, the entity only delegates to it.

Q1. Elevator.closeDoor() is called while the elevator is IDLE. What should happen?

  • A) The door opens instead, since that's probably what was intended
  • B) IdleState.closeDoor() throws IllegalStateException — there's no open door to close from idle
  • C) Nothing happens, the call is silently ignored
  • D) The elevator transitions straight to DOOR_OPEN
Only DoorOpenState.closeDoor() is a legal no-op transition. Every other state's closeDoor() throws — that's the whole point of the guard. Silently ignoring it (C) would hide a real caller bug.

3. Strategy Pattern — which request to service next

Different dispatch policies exist: serve requests in the order they arrived (FCFS), or serve whichever pending floor is physically closest (a simplified SCAN). Swappable without touching ElevatorService. 

// Pattern: Strategy — the scheduling algorithm is injected, not hardcoded
public interface SchedulingStrategy {
    ElevatorRequest selectNext(int currentFloor, List<ElevatorRequest> pendingRequests);
}

public class FcfsSchedulingStrategy implements SchedulingStrategy {
    @Override
    public ElevatorRequest selectNext(int currentFloor, List<ElevatorRequest> pendingRequests) {
        return pendingRequests.get(0);
    }
}

public class ScanSchedulingStrategy implements SchedulingStrategy {
    @Override
    public ElevatorRequest selectNext(int currentFloor, List<ElevatorRequest> pendingRequests) {
        return pendingRequests.stream()
                .min(Comparator.comparingInt(r -> Math.abs(r.floor() - currentFloor)))
                .orElseThrow(() -> new IllegalStateException("No pending requests to schedule"));
    }
}
Why not just sort pendingRequests once and pop the front? Because "nearest" depends on the elevator's current floor at dispatch time, which changes after every trip — a one-time sort goes stale after the first request is served. Recomputing per call is the correct cost here, not a missed optimisation.

Q2. Why does ScanSchedulingStrategy take currentFloor as a parameter instead of reading it from a stored field?

  • A) Java requires all Strategy methods to take primitives as arguments
  • B) It's marginally faster than reading a field
  • C) The strategy object is stateless and reusable across elevators; passing the floor in keeps it that way rather than coupling one strategy instance to one elevator
  • D) It's required so `Comparator.comparingInt` can be used
A stateless strategy can be shared across every elevator in a building (one `ScanSchedulingStrategy` instance, many `ElevatorService`s) instead of needing one strategy instance per elevator. This is the same reason `FineCalculationStrategy` in q030 takes the `Loan` as a parameter rather than storing it.

4. ElevatorService — orchestrates dispatch

public class ElevatorService {

    private final Elevator elevator;
    private final SchedulingStrategy strategy;
    private final List<ElevatorRequest> pendingRequests = new ArrayList<>();

    public ElevatorService(Elevator elevator, SchedulingStrategy strategy) {
        this.elevator = elevator;
        this.strategy = strategy;
    }

    public void requestFloor(int floor, Direction direction) {
        pendingRequests.add(new ElevatorRequest(floor, direction));
        dispatchNextIfIdle();
    }

    public void closeDoor() {
        elevator.closeDoor();
        dispatchNextIfIdle();          // auto-dispatch chained requests
    }

    private void dispatchNextIfIdle() {
        if (!"IDLE".equals(elevator.getStatus()) || pendingRequests.isEmpty()) return;
        ElevatorRequest next = strategy.selectNext(elevator.getCurrentFloor(), pendingRequests);
        pendingRequests.remove(next);
        elevator.move();
        elevator.arrive(next.floor());
    }
}

TDD narrative: the reference implementation was built red→green exactly like every other question in this project — SolutionTest written first against interfaces that didn't compile yet, then IdleState/MovingState/ DoorOpenState filled in until the lifecycle test passed, then FcfsSchedulingStrategy/ScanSchedulingStrategy added and verified independently before wiring ElevatorService around them.

Why dispatchNextIfIdle() is called from two places Both requestFloor() (a new request arrives while idle) and closeDoor() (the elevator just freed up) can be the moment a pending request becomes dispatchable. Missing either call site is the single most likely bug in this question — an elevator that never picks up a second queued request after finishing the first one, because nothing re-triggered dispatch on door close.

5. What interviewers are actually probing

ProbeExpected answer
Why State Pattern instead of an enum + switch?Adding a new state (e.g. OUT_OF_SERVICE) requires only a new class — no existing switch blocks to edit
Why does Elevator delegate instead of mutating its own status?So the state object — not the entity — is the only place transition legality is enforced
How would you swap FCFS for SCAN without touching the service?Inject a different SchedulingStrategy implementation — ElevatorService's constructor already takes the interface
What happens to a second request queued while the elevator is busy?It waits in pendingRequests; closeDoor() re-triggers dispatch so it's picked up automatically
Ask your teacher Unclear on why the strategy takes currentFloor as a parameter instead of storing it? Or how this would extend to multiple elevators sharing one dispatcher? Ask before moving to the question.
