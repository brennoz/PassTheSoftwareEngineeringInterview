Lesson 01 — Card Authorization: Template Method

Category: OOD · Difficulty: Medium · Est. time: 25 min · Lesson 1 of 1

Card authorization is a fixed sequence of steps — validate the card, check risk, contact the card network, log the outcome — where every card network runs THAT SAME sequence, but one step (how you actually talk to Visa vs Mastercard) genuinely differs per network. That's the exact shape Template Method exists for: put the fixed skeleton in one place, force the varying step to be supplied by a subclass, and make it structurally impossible for a subclass to reorder or skip the fixed parts.

What you will be able to do after this lesson Explain why the template method itself should be final, correctly distinguish an abstract "primitive operation" (must override) from a "hook" (may override, has a sensible default), and say precisely why this is a different tool from Strategy (q043) even though both let you vary behaviour per subtype.

2. Why the template method itself must be final

public abstract class CardAuthorizationProcessor {

    // Pattern: Template Method — final so no subclass can reorder, skip, or duplicate
    // these steps. The discipline this pattern enforces IS the fixed sequence; a
    // non-final template method would let a subclass override authorize() itself and
    // do something completely different, which defeats the entire point of centralising
    // the skeleton here in the first place.
    public final AuthorizationResult authorize(Card card, BigDecimal amount) {
        validateCard(card);
        if (requiresManualReview(amount)) {
            return AuthorizationResult.pendingReview();
        }
        AuthorizationResult result = contactIssuerNetwork(card, amount);
        logResult(card, result);
        return result;
    }

    protected void validateCard(Card card) { /* shared validation */ }

    protected boolean requiresManualReview(BigDecimal amount) {
        return false; // hook: sensible default, override only if a network needs stricter policy
    }

    protected abstract AuthorizationResult contactIssuerNetwork(Card card, BigDecimal amount);

    protected void logResult(Card card, AuthorizationResult result) { /* shared logging */ }
}
What goes wrong without final If authorize() weren't final, nothing stops a future AmexAuthorizationProcessor from overriding it to skip validateCard() "just this once for a special partner integration." Six months later that's a silent compliance gap nobody remembers approving. final turns "please don't skip validation" from a code-review convention into something the compiler enforces.

3. Abstract primitive operations vs hooks — not the same thing

GoF's Template Method has two different kinds of "step a subclass can touch," and mixing them up is the most common mistake when applying this pattern:

Abstract primitive operationHook
Example herecontactIssuerNetwork()requiresManualReview()
Has a default body?No — abstract, compile error if not overriddenYes — base class supplies sensible behaviour
Must every subclass override it?Yes, by constructionNo — only if that subclass needs to deviate
What it's forThe one part of the algorithm that's genuinely different per subtype and has no sensible universal defaultAn optional extension point — most subclasses are fine with the default

In this exercise, MastercardAuthorizationProcessor overrides the hook (requiresManualReview) to flag larger amounts for manual review, while VisaAuthorizationProcessor leaves it at the default and never triggers manual review. Same fixed skeleton, same abstract step both must implement, but only one of them bothers to touch the hook — and that's fine, that's what a hook is for.

4. Template Method vs Strategy (q043) — genuinely different tools

Template Method (this lesson)Strategy (q043's SchedulingStrategy)
MechanismInheritance — subclass overrides specific stepsComposition — a whole algorithm object is injected/swapped
What variesOne or two steps within an otherwise-fixed sequenceThe entire algorithm, swappable at runtime
Can the caller change behaviour at runtime?No — the subclass is chosen at construction/compile timeYes — a new strategy object can be injected any time
Where does shared logic live?In the base class's concrete steps, shared automatically by every subclassNowhere automatically — each Strategy implementation must repeat any shared logic itself, or it's factored into a shared helper
The question to ask when choosing between them Is there a FIXED SEQUENCE most of which is identical across every variant, with only one or two steps genuinely differing? Template Method. Is the ENTIRE algorithm meaningfully different per variant, or does it need to be swappable at runtime without subclassing? Strategy. Card authorization is the first shape: validate → risk-check → contact-network → log is the same four steps for every card network, only step 3's implementation differs — that's why this lesson reaches for Template Method rather than Strategy.

Retrieval Quiz

Q1. Why is authorize() declared final?

  • A) Java requires all abstract class methods to be final
  • B) It makes the method run faster (JIT inlining)
  • C) It structurally prevents a subclass from reordering, skipping, or duplicating the fixed sequence of steps — the discipline the pattern is built around
  • D) So subclasses can call it via super.authorize()
The entire value of Template Method is that the sequence of steps is guaranteed identical across every subclass. If authorize() could be overridden, a subclass could silently skip validateCard() or reorder the steps, and nothing in the type system would catch it.

Q2. What's the actual difference between contactIssuerNetwork() (abstract) and requiresManualReview() (a hook)?

  • A) There's no real difference, both are just methods a subclass can override
  • B) The abstract method has no default and every subclass MUST supply one; the hook has a sensible default and a subclass only overrides it if it needs to deviate
  • C) Hooks can only be called from within the same package
  • D) Abstract methods must be static, hooks must be instance methods
This is the actual GoF distinction: primitive operations (abstract, no default, mandatory) vs hooks (concrete, sensible default, optional to override). Mixing them up — e.g. making contactIssuerNetwork() a hook with some arbitrary default network — would silently produce wrong behaviour for any subclass that forgot to override it.

Q3. Why is this Card Authorization example Template Method rather than Strategy?

  • A) Because the four-step sequence (validate → risk-check → contact network → log) is identical across every card network, and only one step's implementation genuinely differs — Strategy would be the right choice if the ENTIRE algorithm needed to vary or be swappable at runtime instead
  • B) Because Strategy can't be used with abstract classes
  • C) Because Template Method is always the better pattern for payment systems
  • D) Because there are only two subclasses (Visa, Mastercard)
The decision criterion is about how much of the algorithm varies, not the number of subtypes or the domain. A fixed sequence with one differing step fits Template Method; a fully swappable whole algorithm fits Strategy.

Q4. VisaAuthorizationProcessor never overrides requiresManualReview(). What happens when authorize() is called on it?

  • A) Compile error — every hook must be overridden
  • B) It uses the base class's default implementation (returns false), so manual review is never triggered for Visa
  • C) It throws UnsupportedOperationException at runtime
  • D) It silently skips the requiresManualReview check entirely
That's exactly what makes it a hook rather than an abstract method — a subclass that has no special requirement simply inherits the base class's default behaviour without needing to write any code for it.
