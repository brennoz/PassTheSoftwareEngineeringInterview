Lesson 01 — Shopping Cart Offers Decorator

Category: OOD · Difficulty: Medium · Est. time: 25 min · Lesson 1 of N

This is the classic "Tesco basket" checkout kata: a shopping cart's total must change when promotional offers are applied — Buy One Get One Free on a specific product, a percentage-off voucher on the whole basket — and a customer's receipt can carry any combination of these, applied in whatever order the retailer's rules say they should stack. That's exactly the shape the Decorator Pattern exists for: wrap a plain object in layers, each layer adding behaviour, without touching the object or the other layers. First Decorator-pattern question in this project (State x3, Command, Strategy, Specification, and Composite have all appeared before this).

What you will be able to do after this lesson Given "design a shopping cart with offers," reach for Decorator instead of a List<Offer> field on the cart, and explain precisely why construction order (which decorator wraps which) is allowed to change the final total — and why that's a feature of this design, not a bug.

1. The tempting wrong shape, first

The obvious first instinct: give Cart a List<Offer> field, loop over it in getTotal(), and let each Offer adjust the running total. It compiles, it's less code up front, and it works — right up until two offers need to apply in a specific sequence relative to each other, or a caller wants "just BOGOF, no voucher" for one customer and "voucher then BOGOF" for another.

Why the List<Offer> field falls over A single internal loop has one fixed iteration order, controlled by Cart, not by whoever is building a particular checkout. To express "apply BOGOF first, then take 10% off what's left" versus "take 10% off first, then apply BOGOF to the discounted total" as two different scenarios, the ordering decision has to live outside Cart entirely — in how the caller composes the pricing, not in a list Cart iterates internally.

Decorator solves this by making each offer a wrapper around whatever PricedCart it's given — which might be the plain cart, or might already be another offer wrapped around the plain cart. Nesting constructor calls (new PercentageOffOffer(new BuyOneGetOneFreeOffer(cart, "Baked Beans"), ...)) becomes the mechanism for expressing "this order, not that one" — something a List<Offer> field can't express as directly.

3. TDD, red → green: BasicCart and the component interface

// GREEN
public interface PricedCart {
    List<CartItem> getItems();
    BigDecimal getTotal();
}

public class BasicCart implements PricedCart {
    private final List<CartItem> items = new ArrayList<>();

    public void addItem(CartItem item) { items.add(item); }

    @Override
    public List<CartItem> getItems() { return Collections.unmodifiableList(items); }

    @Override
    public BigDecimal getTotal() {
        return items.stream().map(CartItem::getLineTotal).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}
Why getItems() returns an unmodifiable view Decorators need to inspect quantities (BOGOF has to count how many units of its target product are in the basket) — so getItems() has to exist on the interface, not just getTotal(). Returning the live, mutable list would let a decorator that's only supposed to be computing a price accidentally mutate the basket, corrupting getTotal() for every other decorator wrapped around the same cart.

Q1. Why does PricedCart need a getItems() method at all, given that the interface's whole purpose is pricing (getTotal())?

  • A) JUnit requires every interface under test to expose its internal state
  • B) BuyOneGetOneFreeOffer needs to find its target product's quantity, and it can only reach that data through the shared interface — however many decorator layers are wrapped in between
  • C) It doesn't — getItems() could be removed with no effect on any offer
  • D) BasicCart's getTotal() implementation internally calls getItems() so it must be public
Without getItems() on the interface, a decorator wrapping another decorator would have no way to inspect what's actually in the basket — it could only see whatever getTotal() the previous layer chose to report, which isn't enough information to compute a product-specific discount like BOGOF.

4. CartOfferDecorator and BuyOneGetOneFreeOffer

// Pattern: Decorator — the abstract base every concrete offer extends,
// so "pass getItems() through unchanged" is written exactly once.
public abstract class CartOfferDecorator implements PricedCart {
    protected final PricedCart wrapped;

    protected CartOfferDecorator(PricedCart wrapped) { this.wrapped = wrapped; }

    @Override
    public List<CartItem> getItems() { return wrapped.getItems(); }
}

public class BuyOneGetOneFreeOffer extends CartOfferDecorator {
    private final String targetProductName;

    public BuyOneGetOneFreeOffer(PricedCart wrapped, String targetProductName) {
        super(wrapped);
        this.targetProductName = targetProductName;
    }

    @Override
    public BigDecimal getTotal() {
        BigDecimal total = wrapped.getTotal();
        for (CartItem item : getItems()) {
            if (item.getProductName().equals(targetProductName)) {
                int freeUnits = item.getQuantity() / 2;
                BigDecimal discount = item.getUnitPrice().multiply(BigDecimal.valueOf(freeUnits));
                return total.subtract(discount);
            }
        }
        return total;
    }
}
Why integer division (quantity / 2), not quantity * 0.5 5 units of Baked Beans should give exactly 2 free units, not a fractional 2.5 that then needs a rounding rule nobody specified. Integer division makes "how many free units" an exact, unambiguous integer computation with no rounding-mode decision to get wrong later.

Q2. BuyOneGetOneFreeOffer.getTotal() calls getItems() (inherited from CartOfferDecorator) rather than reaching into a concrete BasicCart directly. Why does that matter?

  • A) It means this offer works correctly whether it's wrapping BasicCart directly or wrapping another decorator that's wrapping BasicCart — it never needs to know or care how deep the stack goes
  • B) Direct field access on BasicCart would be a compile error in Java
  • C) getItems() is faster than accessing a List field directly
  • D) It doesn't matter — casting to BasicCart would work identically in every case
If BuyOneGetOneFreeOffer cast its wrapped reference to BasicCart, it would break the moment another offer was wrapped in between it and the concrete cart — exactly the "stack offers in any order" requirement this whole exercise is built around. Depending only on the PricedCart interface is what makes arbitrary stacking possible.

5. PercentageOffOffer — where wrapping order becomes visible

public class PercentageOffOffer extends CartOfferDecorator {
    private final BigDecimal percentage;

    public PercentageOffOffer(PricedCart wrapped, BigDecimal percentage) {
        super(wrapped);
        this.percentage = percentage;
    }

    @Override
    public BigDecimal getTotal() {
        BigDecimal total = wrapped.getTotal();
        BigDecimal discountFraction = percentage.divide(BigDecimal.valueOf(100), 4, RoundingMode.HALF_UP);
        return total.multiply(BigDecimal.ONE.subtract(discountFraction));
    }
}

The test that actually justifies Decorator over the rejected List<Offer> design is this one — two offers, two different construction orders, two different totals: 

@Test
void wrappingOrderChangesTheFinalTotal() {
    PricedCart bogofThenPercent = new PercentageOffOffer(
            new BuyOneGetOneFreeOffer(cart, "Baked Beans"), new BigDecimal("10"));
    PricedCart percentThenBogof = new BuyOneGetOneFreeOffer(
            new PercentageOffOffer(cart, new BigDecimal("10")), "Baked Beans");

    // BOGOF first (7.40 - 2.00 = 5.40), then 10% off: 5.40 * 0.90 = 4.86
    assertEquals(0, bogofThenPercent.getTotal().compareTo(new BigDecimal("4.8600")));
    // 10% off first (7.40 * 0.90 = 6.66), then BOGOF's flat 2.00 off: 6.66 - 2.00 = 4.66
    assertEquals(0, percentThenBogof.getTotal().compareTo(new BigDecimal("4.66")));
}
Neither order is "wrong" Whether a percentage voucher applies before or after a BOGOF discount is a real business rule question (receipts genuinely differ between retailers and voucher terms) — Decorator doesn't decide that for you, it just makes both orders equally easy to construct, and makes the choice explicit at the call site instead of buried inside a loop.

Q3. Why does percentage.divide(BigDecimal.valueOf(100), 4, RoundingMode.HALF_UP) specify a scale and rounding mode, instead of a plain percentage.divide(BigDecimal.valueOf(100))?

  • A) BigDecimal.divide() without arguments always returns zero
  • B) It's purely stylistic — both forms behave identically for every possible percentage
  • C) RoundingMode is required syntax in Java 21 and has no effect on the actual result
  • D) An unscaled divide() throws ArithmeticException the moment a caller passes a percentage that doesn't divide 100 into a terminating decimal (e.g. 33.33...%) — a real crash risk, not a hypothetical
BigDecimal.divide(BigDecimal) with no scale/rounding arguments throws ArithmeticException whenever the exact quotient has a non-terminating decimal expansion. A percentage like one-third off would hit that immediately in production; specifying a scale and rounding mode sidesteps the crash entirely.
