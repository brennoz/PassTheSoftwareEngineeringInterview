Lesson 01 — Library System Domain Model

Category: OOD · Difficulty: Medium · Est. time: 15 min · Lesson 1 of N

Library Management is a classic OOD interview question. It looks simple but contains two rich design challenges: a BookCopy state machine (State Pattern) and swappable fine calculation (Strategy Pattern). This lesson builds the domain model from entities up to patterns.

What you will be able to do after this lesson Given "design a library system", produce a complete class diagram in under 5 minutes, name the State and Strategy patterns correctly, and explain why BookCopy is a separate entity from Book.

2. Why BookCopy is not Book

A library owns 5 copies of Clean Code. Each copy has its own status: copy #1 is BORROWED, copy #2 AVAILABLE, copy #3 RESERVED. The Book entity is the catalogue record (one per title). BookCopy is the physical item (many per title, each with its own state).

Interview trap Putting status on Book is the most common mistake. An interviewer immediately follows with: "what if you have 5 copies and 3 are borrowed?" You cannot answer without a BookCopy entity.

3. BookCopy state machine — State Pattern

┌─────────────┐ │ AVAILABLE │◄──────────────────────┐ └──────┬──────┘ │ │ reserve() │ ┌──────▼──────┐ │ │ RESERVED │ │ └──────┬──────┘ │ │ checkout() │ return() ┌──────▼──────┐ │ │ BORROWED │───────────────────────┤ └──────┬──────┘ │ │ due date passed │ ┌──────▼──────┐ │ │ OVERDUE │───────────────────────┘ └──────┬──────┘ │ reported missing ┌──────▼──────┐ │ LOST │ (terminal — no transitions out) └─────────────┘

Naïve approach: if (status == BORROWED && ...) { status = OVERDUE; } everywhere. This scatters transition logic across the codebase. State Pattern centralises it. 

// Pattern: State — each state is an object; transitions are methods on the state
public interface CopyState {
    void reserve(BookCopy copy);
    void checkout(BookCopy copy);
    void returnCopy(BookCopy copy);
    void markLost(BookCopy copy);
    String name();
}

public class AvailableState implements CopyState {
    @Override
    public void reserve(BookCopy copy)   { copy.setState(new ReservedState()); }
    @Override
    public void checkout(BookCopy copy)  { copy.setState(new BorrowedState()); }
    @Override
    public void returnCopy(BookCopy copy){ throw new IllegalStateException("Not borrowed"); }
    @Override
    public void markLost(BookCopy copy)  { throw new IllegalStateException("Not borrowed"); }
    @Override public String name()       { return "AVAILABLE"; }
}

public class BorrowedState implements CopyState {
    @Override
    public void reserve(BookCopy copy)   { throw new IllegalStateException("Already borrowed"); }
    @Override
    public void checkout(BookCopy copy)  { throw new IllegalStateException("Already borrowed"); }
    @Override
    public void returnCopy(BookCopy copy){ copy.setState(new AvailableState()); }
    @Override
    public void markLost(BookCopy copy)  { copy.setState(new LostState()); }
    @Override public String name()       { return "BORROWED"; }
}

// OverdueState and ReservedState follow the same pattern

public class BookCopy {

    private final String barcode;
    private final Book   book;
    // State held as object, not enum — transitions are encapsulated in the state itself
    private CopyState state = new AvailableState();

    public BookCopy(String barcode, Book book) {
        this.barcode = barcode;
        this.book    = book;
    }

    public void reserve()    { state.reserve(this); }
    public void checkout()   { state.checkout(this); }
    public void returnCopy() { state.returnCopy(this); }
    public void markLost()   { state.markLost(this); }

    void setState(CopyState state) { this.state = state; }   // package-private
    public String getStatus()      { return state.name(); }
}
State vs enum + switch Enum approach: switch(status) { case AVAILABLE: ... } in every service method. Adding a new state (e.g. MAINTENANCE) means editing every switch block. State Pattern: new state = new class. Existing states untouched. Open/Closed satisfied.
The single most common mistake on this exact question Defining all five state classes correctly, then wiring BookCopy wrong — reserve() directly mutating state = new ReservedState() instead of delegating with state.reserve(this). Every state class gets written correctly and is never actually reached — a LOST copy can still be "reserved" because the guard that would throw is dead code. The tell: if any BookCopy method contains the word new for a state class, delegation is broken — only CopyState implementations are allowed to call copy.setState(new X()). Rule to say out loud: the state object controls the transition, the entity only delegates to it.

4. Fine calculation — Strategy Pattern

Different libraries charge differently: flat rate per overdue loan, daily rate, tiered rate (cheap first week, expensive after). Swappable without touching Loan. 

// Pattern: Strategy — fine formula injected, not hardcoded
public interface FineCalculationStrategy {
    BigDecimal calculate(Loan loan);
}

public class DailyFineStrategy implements FineCalculationStrategy {
    private final BigDecimal ratePerDay;

    public DailyFineStrategy(BigDecimal ratePerDay) { this.ratePerDay = ratePerDay; }

    @Override
    public BigDecimal calculate(Loan loan) {
        long daysOverdue = ChronoUnit.DAYS.between(loan.getDueDate(), LocalDate.now());
        if (daysOverdue <= 0) return BigDecimal.ZERO;
        // BigDecimal not double — money arithmetic must be exact
        return ratePerDay.multiply(BigDecimal.valueOf(daysOverdue));
    }
}

public class FlatFineStrategy implements FineCalculationStrategy {
    private final BigDecimal flatAmount;

    public FlatFineStrategy(BigDecimal flatAmount) { this.flatAmount = flatAmount; }

    @Override
    public BigDecimal calculate(Loan loan) {
        long daysOverdue = ChronoUnit.DAYS.between(loan.getDueDate(), LocalDate.now());
        return daysOverdue > 0 ? flatAmount : BigDecimal.ZERO;
    }
}

5. Loan and Reservation

// Why record: Loan is immutable value once created; returnDate set via separate method
public class Loan {

    private final String     id;
    private final Member     member;
    private final BookCopy   copy;
    private final LocalDate  borrowedOn;
    private final LocalDate  dueDate;
    private LocalDate        returnedOn;   // null until returned

    public Loan(Member member, BookCopy copy, int loanDays) {
        this.id         = UUID.randomUUID().toString();
        this.member     = member;
        this.copy       = copy;
        this.borrowedOn = LocalDate.now();
        this.dueDate    = borrowedOn.plusDays(loanDays);
    }

    public boolean isOverdue()   { return returnedOn == null && LocalDate.now().isAfter(dueDate); }
    public void returnBook()     { this.returnedOn = LocalDate.now(); copy.returnCopy(); }
    public LocalDate getDueDate(){ return dueDate; }
}

6. LibraryService — orchestrates operations

public class LibraryService {

    private final FineCalculationStrategy fineStrategy;

    public LibraryService(FineCalculationStrategy fineStrategy) {
        this.fineStrategy = fineStrategy;
    }

    public Loan checkout(Member member, BookCopy copy, int loanDays) {
        if (member.hasReachedBorrowLimit())
            throw new BorrowLimitExceededException(member.getId());
        copy.checkout();                         // delegates to state
        Loan loan = new Loan(member, copy, loanDays);
        member.addActiveLoan(loan);
        return loan;
    }

    public Fine returnBook(Loan loan) {
        loan.returnBook();                       // state transition + returnedOn set
        BigDecimal amount = fineStrategy.calculate(loan);
        return amount.compareTo(BigDecimal.ZERO) > 0
                ? new Fine(loan, amount)
                : null;
    }
}
The second most common mistake on this exact question fine == BigDecimal.ZERO instead of fine.compareTo(BigDecimal.ZERO) == 0 (or > 0 for the check above). == on BigDecimal compares object identity, not numeric value — it works by accident when a strategy happens to return the exact static BigDecimal.ZERO constant, and silently breaks the moment any strategy returns new BigDecimal("0") or BigDecimal.valueOf(0) instead — a different object, same value, wrong answer. Compounding version of this bug seen in practice: the == check plus an inverted ternary — returning a real Fine object when the amount IS zero, and null when it isn't. Rule to say out loud: never ==/!= on BigDecimal — always .compareTo() or .equals(), and for a zero check specifically, .signum() == 0 reads even cleaner.

8. Retrieval quiz

Q1. Why is BookCopy a separate entity from Book?

  • A) A library owns multiple physical copies of the same title — each copy has its own independent status, barcode, and shelf location
  • B) Book is an interface; BookCopy is the concrete implementation of that interface
  • C) Java does not allow a single class to track both catalogue data and inventory status
  • D) BookCopy extends Book via inheritance to add the status field
Book is the catalogue record (one per title). BookCopy is the physical item (many per title). Copy #1 may be BORROWED while copy #2 is AVAILABLE — impossible to model without separating them. This is the single most important design decision in a library system question.

Q2. What is the key advantage of State Pattern over an enum + switch for BookCopy status?

  • A) State Pattern uses less memory than storing an enum value
  • B) Enums cannot be used as fields in JPA entities
  • C) Adding a new state (e.g. MAINTENANCE) requires only a new class — no existing switch blocks to edit, Open/Closed satisfied
  • D) State Pattern automatically persists status changes to the database
With enum + switch, every method that cares about status has a switch block. Add MAINTENANCE → edit every block → shotgun surgery. State Pattern: add MaintenanceState class, define its transitions, done. Existing states are untouched. This is the Open/Closed Principle in action.

Q3. Which pattern makes fine calculation swappable between daily rate and flat rate without changing LibraryService?

  • A) Template Method — LibraryService is abstract and subclasses override calculateFine()
  • B) Strategy — FineCalculationStrategy interface injected into LibraryService constructor
  • C) Observer — Fine events are published and a listener calculates the amount
  • D) Factory — a FineFactory decides which calculation class to instantiate
Strategy: the algorithm (fine formula) is extracted behind an interface and injected. LibraryService holds FineCalculationStrategy and delegates. Template Method would require subclassing LibraryService — one subclass per fine policy, which doesn't compose well. Observer would add unnecessary async complexity for a synchronous calculation.

Q4. A member tries to check out a book but has reached the borrow limit. Where should this guard live?

  • A) Inside BookCopy.checkout() — the copy decides if checkout is allowed
  • B) Inside Loan constructor — throw if member already has too many loans
  • C) Inside Member.addActiveLoan() — member enforces its own limit
  • D) Inside LibraryService.checkout() — the service orchestrates the rule before delegating to copy and member
BookCopy knows nothing about members — it only tracks its own state. Loan constructor shouldn't enforce business rules — it's a data record. Member.addActiveLoan() could work but mixes rule enforcement into a data method. LibraryService is the use-case orchestrator — it's the right place for cross-entity business rules like "member limit before copy state change".
