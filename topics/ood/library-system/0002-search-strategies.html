Lesson 02 — Library Search: Four Layers, One Interview

Category: OOD · Difficulty: Easy-Medium · Est. time: 25 min · Lesson 2 of N

This is the retro of a real NatWest take-home: a Library.search(String) stub that ignored its own argument. The fix itself is a one-liner. What this lesson actually covers is four different ways to build that one-liner — from "just make the tests pass" to "how would this search work if the catalogue had a million books" — so the next time a search ticket lands, the choice of approach is a decision, not a guess made under pressure.

What you will be able to do after this lesson Fix the given bug with a plain filter, then explain in one sentence each why you'd reach for a Specification pattern instead, when relevance ranking would matter, and when a linear scan stops being viable at all — and pick the right one for the ticket in front of you instead of over- or under-building. You'll also be able to read a given test file critically enough to spot a vacuous assertion, without touching a file you were told not to edit.

1. Baseline — plain Stream.filter

Given code:

public List<Book> search(String searchString) {
    return books;   // never reads searchString — always returns the whole catalogue
}

Minimal correct fix:

// Why StringUtils.containsIgnoreCase, not manual toLowerCase().contains():
// commons-lang3 was on the classpath and unused in the given code — a library visible
// in the pom and never imported is a hint toward the intended tool, not decoration
public List<Book> search(String searchString) {
    return books.stream()
            .filter(b -> StringUtils.containsIgnoreCase(b.getTitle(), searchString)
                    || StringUtils.containsIgnoreCase(b.getAuthor(), searchString))
            .collect(Collectors.toList());
}
This passes every given test. So why keep reading? Because the next ticket almost always adds a second criterion — filter by genre, exclude borrowed books, search by ISBN — and each one means going back into Library and editing this method again. That's fine once. By the third criterion it's an unreadable wall of ||.

Q1. The given pom.xml lists commons-lang3, unused in any given class. What should you conclude?

  • A) It's leftover, safe to ignore
  • B) A classpath-visible-but-unused library is a hint toward the intended solution, not decoration
  • C) It must be removed before the project compiles
  • D) It signals Lombok should be used instead
A curated pom in a take-home isn't padded randomly. An unused library sitting right there is one of the cheapest signals an interviewer can give — StringUtils.containsIgnoreCase here, not a hand-rolled case fold.

2. Specification pattern — the recommended answer

Each search criterion becomes its own class implementing one interface. Combining criteria is composition, not more || inside Library. 

// Pattern: Specification — each business rule (a search criterion) is an object
// with a single isSatisfiedBy(candidate) method, composable via And/Or/Not
public interface BookSpecification {
    boolean isSatisfiedBy(Book book);
}

public class TitleContainsSpecification implements BookSpecification {
    private final String fragment;

    public TitleContainsSpecification(String fragment) {
        this.fragment = fragment;
    }

    @Override
    public boolean isSatisfiedBy(Book book) {
        return StringUtils.containsIgnoreCase(book.getTitle(), fragment);
    }
}

public class AuthorContainsSpecification implements BookSpecification {
    private final String fragment;

    public AuthorContainsSpecification(String fragment) {
        this.fragment = fragment;
    }

    @Override
    public boolean isSatisfiedBy(Book book) {
        return StringUtils.containsIgnoreCase(book.getAuthor(), fragment);
    }
}

// Combinator — wraps two specifications, satisfied if either is
public class OrSpecification implements BookSpecification {
    private final BookSpecification left;
    private final BookSpecification right;

    public OrSpecification(BookSpecification left, BookSpecification right) {
        this.left = left;
        this.right = right;
    }

    @Override
    public boolean isSatisfiedBy(Book book) {
        return left.isSatisfiedBy(book) || right.isSatisfiedBy(book);
    }
}

public class Library {

    private final List<Book> books = new ArrayList<>();

    public List<Book> search(String searchString) {
        BookSpecification spec = new OrSpecification(
                new TitleContainsSpecification(searchString),
                new AuthorContainsSpecification(searchString));
        return books.stream()
                .filter(spec::isSatisfiedBy)
                .collect(Collectors.toList());
    }

    public void add(Book book) {
        books.add(book);
    }
}
This is more code for the same result — is that over-engineering? Only if no future ticket ever adds a criterion. In a real take-home, more tickets are coming. The tell that Specification earns its place here: the ticket says "search by title and author" — two criteria, combined — not "search by title." Two combinable criteria in the very first ticket is itself a signal more are coming. If the ticket were single-criterion with no hint of more, the baseline filter would be the right call — don't reach for this pattern reflexively, reach for it because the ticket's shape asked for it.

Q2. What's the actual justification for introducing the Specification pattern on this ticket, rather than treating it as premature abstraction?

  • A) Specification pattern is always correct for any filter, regardless of ticket shape
  • B) It makes the code shorter
  • C) It's required whenever Stream is used
  • D) The ticket already combines two criteria (title OR author) in its very first version — that's the signal more criteria are coming, which is what justifies paying the composition cost now instead of later
Patterns earn their place from what the ticket's shape implies, not from habit. A single-criterion ticket wouldn't justify this — a multi-criterion one, especially as ticket 1, does.

3. Relevance-ranked search

Both layers above are binary: a book matches or it doesn't, and the given tests never check order. A real search box needs "Lord of the Flies" to outrank "The Lord of the Rings" when you type "lord of the flies" — full-title matches should sort first. This layer is real, compiling, TDD'd code — RankedLibrary.java and RankedLibraryTest.java, alongside Library.java in the same package. It answers a different question than the ticket asked ("which result is most relevant?" instead of "does it match?"), so it's a sibling class, not a replacement. 

// Why a separate class, not a method added to Library: this answers
// "how relevant?" not "does it match?" — a different contract (ordered List, not a
// filtered set), so it earns its own class rather than overloading Library's meaning
public List<Book> searchRanked(String query) {
    return books.stream()
            .map(b -> new ScoredBook(b, score(b, query)))
            .filter(scored -> scored.score() > 0)
            .sorted(Comparator.comparingInt(ScoredBook::score).reversed())
            .map(ScoredBook::book)
            .collect(Collectors.toList());
}

// Why this tier order: an exact title match is almost certainly what the user meant;
// starts-with is the next-strongest signal (autocomplete-style); a mid-title substring
// is weaker; an author-only match is weakest but still relevant, matching the OR
// contract the plain search() honors.
private int score(Book book, String query) {
    if (book.getTitle().equalsIgnoreCase(query)) return 100;
    if (StringUtils.startsWithIgnoreCase(book.getTitle(), query)) return 50;
    if (StringUtils.containsIgnoreCase(book.getTitle(), query)) return 10;
    if (StringUtils.containsIgnoreCase(book.getAuthor(), query)) return 5;
    return 0;
}

RankedLibraryTest proves the tier order directly: five books, one per tier plus one non-match, asserting results.get(0) through get(3) land in exact → starts-with → contains → author-match order, and the non-match is excluded entirely — not just "some ordering," the specific ordering the scoring function promises.

Cost of this layer Every candidate gets scored even for a tiny catalogue — fine at hundreds of books, still a full scan under the hood. Ranking changes output order, not the fundamental scaling problem — that's what layer 4 addresses.

4. Index-based search at scale (system-design angle)

Every layer above scans the entire List<Book> per search call — O(n) per query. Fine for hundreds of books in memory. Not fine for a real catalogue of millions, or a service running on more than one instance. Real code again — IndexedLibrary.java / IndexedLibraryTest.java. It stores Book references directly in the index rather than inventing an ID field (the given Book class has none, and shouldn't need one just to demo indexing). 

// Inverted index — whole word (lowercased) -> the set of books containing
// it, in title or author. Lookup is O(1) average instead of an O(n) scan.
private final Map<String, Set<Book>> index = new HashMap<>();

public void add(Book book) {
    indexTokensOf(book.getTitle(), book);
    indexTokensOf(book.getAuthor(), book);
}

public List<Book> search(String token) {
    return new ArrayList<>(index.getOrDefault(token.toLowerCase(), Set.of()));
}

private void indexTokensOf(String text, Book book) {
    for (String token : text.toLowerCase().split("\\s+")) {
        index.computeIfAbsent(token, key -> new HashSet<>()).add(book);
    }
}
The tradeoff this layer actually costs you IndexedLibraryTest proves it directly: searching "lord" finds "Lord of the Flies" and "Lord of the Rings" but correctly excludes "Lordship Estates" — different whole word once split. A second test proves searching "lor" — a real substring of "Lord" — returns nothing at all. Every earlier layer (Library, RankedLibrary) matches "lor" via containsIgnoreCase; this one can't, because it only ever indexes whole tokens. O(1) lookup is not a strict upgrade over O(n) scan — it trades away substring matching to get there. A trie would serve prefix search ("type-ahead") better than this hash-based inverted index; the inverted index shown here serves whole-token lookups only.
In AWS / Distributed Environment This in-memory Map is the same trap as an in-memory rate limiter: it works on one instance and silently diverges the moment there's a second one — two replicas index independently, a book added via instance A is invisible to a search hitting instance B. AWS mapping: OpenSearch (managed Elasticsearch) — a shared, replicated inverted index every instance queries instead of maintaining its own. Failure mode this fixes: stale/inconsistent search results depending on which instance served the request.

Q3. Why does an in-memory Map<String, Set<Book>> index break on a multi-instance deployment even though it works perfectly in a single-instance test?

  • A) Each instance builds its own index from whatever books it's seen added locally — a book added via one instance never appears in another instance's index, so search results depend on which instance handled the request
  • B) HashMap is not thread-safe, causing a crash
  • C) Java's Map interface doesn't support Unicode book titles
  • D) The index would run out of memory immediately regardless of instance count
Same category of bug as an in-memory rate limiter or in-memory cache in a horizontally-scaled service: state that lives in one process's heap is invisible to every other process. The fix is always the same shape — move the state somewhere shared (Redis, OpenSearch, a database) instead of process-local memory.

5. Integration with the existing library system

This catalogue is deliberately the simplest version of the same domain already built out in q030_library_system (State Pattern, BookCopy) and ex4_library_borrowing (audit trail, Member). The Specification pattern from section 2 is exactly what makes that richer model a clean extension instead of a rewrite. 

// Sketch — once BookCopy/CopyStatus exists (q030), availability becomes another
// specification, composed with AND, without touching TitleContainsSpecification,
// AuthorContainsSpecification, or Library.search() at all
public class AvailableSpecification implements BookSpecification {
    @Override
    public boolean isSatisfiedBy(Book book) {
        return book.getCopies().stream().anyMatch(c -> c.getStatus() == CopyStatus.AVAILABLE);
    }
}

// search() becomes:
BookSpecification spec = new AndSpecification(
        new OrSpecification(titleSpec, authorSpec),
        new AvailableSpecification());
The bridge, stated plainly A boolean flag on Book or a scattered if/else would need editing every time a new filter criterion is added. Specification composes. That's the same Open/Closed argument as the State Pattern in Lesson 01 — different pattern, same underlying discipline: new requirement, new class, existing classes untouched.

6. The given test isn't perfect either

question.md marks the given LibraryTest "DO NOT edit; this is the spec" — for good reason, it's what any solution gets graded against. That doesn't mean it's well-written. Reading a given test critically, without touching it, is its own skill. 

@Test
void searchReturnsBookMatchingTitleOrAuthor() {
    var results = library.search("lord");
    assertEquals(3, results.size(), "matching books");
    assertTrue(results.contains(LORD_OF_THE_FLIES));
    assertTrue(results.contains(LORD_OF_THE_RINGS));
    assertTrue(results.contains(WAR_AND_PEACE));
    assertFalse(results.contains(HARRY_POTTER));   // ← HARRY_POTTER was never added in @BeforeEach
}
A vacuous assertion HARRY_POTTER is never library.add()-ed anywhere in this test class. assertFalse(results.contains(HARRY_POTTER)) passes unconditionally — a book that was never in the library can never be in the results, regardless of whether search() is correct, broken, or a no-op. It reads like it's proving exclusion works; it proves nothing. A version that actually tested exclusion would need library.add(HARRY_POTTER) in @BeforeEach first.

Separately, the first test bundles two unrelated behaviours — an exact-title match and a no-match-returns-empty check — into one method: 

@Test
void searchReturnsTheSingleBookThatMatchesTheEntireTitle() {
    var results = library.search("Lord of the Flies");
    assertEquals(1, results.size(), "matching books");
    var book = results.get(0);
    assertSame(LORD_OF_THE_FLIES, book);
    assertEquals("Lord of the Flies", book.getTitle());
    assertEquals(0, library.search("no book").size(), "matching books");   // ← different behaviour, same test
}

Not wrong — both assertions pass against a correct implementation — but if this test fails, the stack trace alone doesn't tell you which behaviour broke without reading closely. Read as a real interview artifact rather than a model to imitate, this tracks: a test written under the same time pressure as the code it's grading. Spotting these two issues — without editing the file, since it's the spec — is a legitimate thing to say out loud in the room; it demonstrates you're reading the test as carefully as the implementation.

Q4. assertFalse(results.contains(HARRY_POTTER)) in the third given test — what's actually wrong with it?

  • A) Nothing — it correctly proves non-matching books are excluded from results
  • B) assertFalse is deprecated in JUnit 5
  • C) HARRY_POTTER is never added to the library in this test, so the assertion passes regardless of whether search() works — it tests nothing
  • D) The book title contains a colon, which breaks string comparison
A useful exclusion test needs the excluded item to actually be present in the system under test — otherwise "it's not in the results" is true before the code under test even runs. This is worth spotting precisely because the given test is marked "DO NOT edit": you can't fix it, but naming the gap out loud shows you read it as carefully as you read the implementation requirements.

7. What interviewers are actually probing

ProbeExpected answer
Why did the given test fail?search() never read its argument — always returned the full catalogue
Why Specification over a plain filter?The ticket already combines two criteria (title OR author) — signal more are coming; Specification keeps Library untouched as criteria grow
How would you rank results, not just filter them?Score each candidate (exact > starts-with > contains), sort descending instead of a binary include/exclude
What breaks at catalogue scale?Linear scan over List<Book> — an inverted index or trie moves lookup from O(n) to near O(1)/O(k), at the cost of substring matching
What breaks on multiple instances?An in-memory index is per-process — needs a shared store (OpenSearch) or every instance sees a different catalogue
Is the given test itself above criticism?No — assertFalse(contains(HARRY_POTTER)) is vacuous (never added), and the first test bundles two behaviours. Spot it, don't edit it.
