Lesson 02 — Twitter: Service Layer vs Rich Domain Model

Category: OOD · Difficulty: Medium · Est. time: 20 min · Prerequisite: Lesson 01

In Lesson 01 we built Twitter with the Rich Domain Model: behavior lived inside User (Observer list, follow, post). In this lesson we rebuild it as a Service Layer + Explicit Entities: User is a thin data record, and separate service classes own all logic. We compare the two approaches from both a design and an Object-Oriented Design perspective.

1. The two models at a glance

q032 — Rich Domain Model 
User {
  id, username
  List<FeedObserver> observers  ← graph
  Feed feed                      ← timeline

  follow(User target)    ← behavior
  post(String content)   ← behavior
  notifyObservers(tweet) ← behavior
}

Feed implements FeedObserver {
  Deque<Tweet> timeline
  onTweetPosted(tweet)
}
q035 — Service Layer 
record User(id, username, bio) {}   ← data only

record Follow(followerId,
              followeeId,
              followedAt) {}           ← explicit edge

record Like(userId,
            tweetId,
            likedAt) {}               ← explicit edge

SocialGraph   { follow, unfollow,
                getFollowers,
                getFollowing }         ← service
FeedService   { getTimeline }          ← service
LikeService   { like, unlike,
                getLikeCount }         ← service

2. Explicit relationship entities — Follow and Like

In q032, "Alice follows Bob" was encoded as Bob's feed being registered as an observer on Alice. The relationship was implicit — encoded in object references, invisible to queries. Here, it's a first-class entity. 

// Follow: a directed edge in the social graph
// Maps directly to a DB row: (follower_id, followee_id, followed_at)
public record Follow(String followerId, String followeeId, Instant followedAt) {}

// Like: a many-to-many join between User and Tweet
// Maps directly to a DB row: (user_id, tweet_id, liked_at)
public record Like(String userId, String tweetId, Instant likedAt) {}
Records are ideal here Java records (Java 16+): immutable, auto-generate equals/hashCode/toString, zero boilerplate. Follow and Like are value objects — they have no identity beyond their fields. Records enforce immutability without effort.

3. In-memory repositories — simulating persistence

// Repository pattern: abstracts storage. Swap Map for JPA without touching services.
class TweetRepository {

    private final Map<String, Tweet>        byId       = new HashMap<>();
    // Secondary index: all tweets by one author — what a DB index would give us
    private final Map<String, List<Tweet>>  byAuthor   = new HashMap<>();

    Tweet save(Tweet tweet) {
        byId.put(tweet.id(), tweet);
        byAuthor.computeIfAbsent(tweet.authorId(), k -> new ArrayList<>()).add(tweet);
        return tweet;
    }

    Optional<Tweet> findById(String id) { return Optional.ofNullable(byId.get(id)); }

    List<Tweet> findByAuthorId(String authorId) {
        return byAuthor.getOrDefault(authorId, List.of());
    }
}

4. SocialGraph service — the queryable graph

// SocialGraph: owns follow/unfollow and all graph queries
// Internally: two maps (adjacency lists) for O(1) forward and reverse lookup
class SocialGraph {

    // follower → set of followee IDs  (forward: "who does Alice follow?")
    private final Map<String, Set<String>> following = new HashMap<>();
    // followee → set of follower IDs  (reverse: "who follows Alice?")
    private final Map<String, Set<String>> followers = new HashMap<>();

    Follow follow(String followerId, String followeeId) {
        if (followerId.equals(followeeId))
            throw new IllegalArgumentException("Cannot follow yourself");
        following.computeIfAbsent(followerId, k -> new HashSet<>()).add(followeeId);
        followers.computeIfAbsent(followeeId, k -> new HashSet<>()).add(followerId);
        return new Follow(followerId, followeeId, Instant.now());
    }

    void unfollow(String followerId, String followeeId) {
        following.getOrDefault(followerId, Set.of()).remove(followeeId);
        followers.getOrDefault(followeeId, Set.of()).remove(followerId);
    }

    // These queries were IMPOSSIBLE in the Observer model
    Set<String> getFollowing(String userId)  { return Set.copyOf(following.getOrDefault(userId, Set.of())); }
    Set<String> getFollowers(String userId)  { return Set.copyOf(followers.getOrDefault(userId, Set.of())); }
    boolean     isFollowing(String a, String b) { return following.getOrDefault(a, Set.of()).contains(b); }
    int         getFollowerCount(String userId)  { return followers.getOrDefault(userId, Set.of()).size(); }
}

5. FeedService — decoupled timeline assembly

// FeedService depends on SocialGraph + TweetRepository — no coupling to User
class FeedService {

    private final SocialGraph     socialGraph;
    private final TweetRepository tweetRepository;

    FeedService(SocialGraph socialGraph, TweetRepository tweetRepository) {
        this.socialGraph     = socialGraph;
        this.tweetRepository = tweetRepository;
    }

    // Fan-out on read: pull tweets from all followees and merge
    List<Tweet> getTimeline(String userId, int limit) {
        return socialGraph.getFollowing(userId).stream()
                .flatMap(followeeId -> tweetRepository.findByAuthorId(followeeId).stream())
                .sorted(Comparator.comparing(Tweet::createdAt).reversed())
                .limit(limit)
                .toList();
    }
}

6. Full comparison: Rich Domain Model vs Service Layer

From a design (architectural) perspective

ConcernRich Domain Model (q032)Service Layer (q035)
Behaviour locationInside domain objects (User.follow())Inside service classes (SocialGraph.follow())
CouplingUser coupled to Feed via CopyOnWriteArrayList of observersServices coupled to repositories; entities have zero coupling
Queryability"Who am I following?" — impossible without scanning all userssocialGraph.getFollowing(userId) — O(1)
Persistence mappingObserver list has no DB equivalent — transient stateFollow record maps directly to a DB row; swap Map for JPA repository
TestabilityMust create real User + Feed objects to test postingTest SocialGraph with empty maps; test FeedService by mocking both dependencies
Fan-out modelPush (Observer): post → synchronously notify each observerPull (Fan-out on read): timeline assembled on request from graph + tweets

From an OOD perspective

PrincipleRich Domain Model (q032)Service Layer (q035)
Single Responsibility❌ User manages: data + social graph + feed + notifications✅ User = data, SocialGraph = graph, FeedService = feed
Open/Closed✅ New observer types don't require changing User✅ New services added without touching entities
Dependency Inversion❌ User directly instantiates Feed — hard to swap✅ Services depend on interfaces/repos — easily swapped
Encapsulation✅ Observer list hidden inside User✅ Graph structure hidden inside SocialGraph
DDD alignmentRich Domain Model — entities are "smart"Thin entities + Domain Services — also valid DDD (domain services for cross-entity logic)
Pattern visibilityObserver Pattern clearly visible — good for textbook OODRepository + Service Layer — familiar to Spring Boot developers

Which is "better"?

Neither is universally better — context decides.
ContextUseWhy
OOD interview asking "show me a design pattern"Rich Domain ModelObserver Pattern is explicit; interviewer sees pattern knowledge immediately
OOD interview asking "design something production-ready"Service LayerQueryable graph, testable services, persistence-ready — shows senior thinking
Real Spring Boot applicationService LayerMaps naturally to @Service, @Repository, JPA entities, unit-testable
Small script / prototypeRich Domain ModelLess boilerplate; fewer classes

The Rich Domain Model shines when behaviour is complex and varies by subtype (e.g. State Pattern for BookCopy — each state IS a class). The Service Layer shines when relationships are complex and need to be queried (social graph, loan history, payment ledger). Twitter is relationship-heavy — Service Layer fits better at real scale.

7. Retrieval quiz

Q1. In the Service Layer approach, why does User not have a follow() method?

  • A) Java records cannot have methods
  • B) The follow action only needs to update the followee, not the follower, so it belongs on the followee
  • C) Following involves two users and creates a Follow entity stored in SocialGraph — it is a cross-entity operation that belongs in a service, not in one entity
  • D) Putting follow() on User would violate the Observer Pattern
follow() must update the following-set of the follower AND the follower-set of the followee — it touches two entities and creates a third (Follow). Embedding this in User violates SRP and couples User to SocialGraph internals. A service class is the correct home for cross-entity logic — this is what DDD calls a Domain Service.

Q2. What is the key advantage of storing Follow as an explicit entity vs encoding it as an Observer registration?

  • A) The Follow entity can be queried, counted, persisted to a DB, and used for "mutual follows" or "suggested follows" — none of which are possible when the relationship is just an object reference in a list
  • B) The Follow entity uses less memory than storing a FeedObserver reference
  • C) Observer registration requires the JDK Observer interface which is deprecated
  • D) Follow entities allow the follow date to be stored — impossible with Observer
The core win is queryability and persistence-readiness. A Follow entity maps to a DB row — it can be counted (follower count), queried in reverse (who follows me?), used for graph traversal (friends-of-friends), and given a TTL or soft-delete. Observer registration is a transient object reference — invisible to queries, lost on restart, and carries no metadata.

Q3. The Service Layer uses fan-out on read for the timeline. What is the trade-off vs the Observer (fan-out on write) approach?

  • A) Fan-out on read is always slower because it requires more database queries
  • B) Fan-out on write always produces stale timelines; fan-out on read is always fresh
  • C) Fan-out on read cannot support real-time feeds; fan-out on write can
  • D) Fan-out on write: timeline always ready in O(1) at read time but O(followers) writes per post — catastrophic for celebrities. Fan-out on read: zero write cost per post but O(following_count) reads per timeline load — slow for users following thousands
The trade-off is write amplification vs read amplification. Fan-out on write pre-builds the timeline (fast reads, expensive writes). Fan-out on read builds on demand (cheap writes, expensive reads). Neither is universally better — real Twitter uses a hybrid. For this OOD in-memory exercise, fan-out on read is simpler to implement correctly and avoids the celebrity fan-out problem entirely.
