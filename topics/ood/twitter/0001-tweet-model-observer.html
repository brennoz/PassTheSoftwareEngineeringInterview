Lesson 01 — Twitter OOD: Tweet Model & Observer Feed

Category: OOD · Difficulty: Medium · Est. time: 15 min

Twitter is a classic OOD question with two design challenges: a polymorphic tweet hierarchy (original / retweet / reply are structurally different) and an Observer-driven feed (post a tweet → all followers see it).

After this lesson you can: Design the Tweet hierarchy without putting tweetType switch-statements everywhere, wire follower feeds using Observer Pattern, and explain the fan-out trade-off in one sentence.

2. Tweet type hierarchy — why not a type enum?

Naïve approach: one Tweet class with a TweetType enum and nullable fields (sourceTweet is null unless it's a retweet, etc.). Every method that cares about type ends up with a switch block. Adding "Quote Tweet" means editing them all. 

// Pattern: polymorphism — tweet type is a class, not a flag
public abstract class Tweet {

    private final String    id;
    private final User      author;
    private final Instant   createdAt;
    private int             likeCount;

    protected Tweet(User author) {
        this.id        = UUID.randomUUID().toString();
        this.author    = author;
        this.createdAt = Instant.now();
    }

    // Template Method — each subclass defines what 'displayContent' means
    public abstract String displayContent();

    public void like()   { likeCount++; }
    public void unlike() { if (likeCount > 0) likeCount--; }

    public String  getId()        { return id; }
    public User    getAuthor()    { return author; }
    public Instant getCreatedAt() { return createdAt; }
    public int     getLikeCount() { return likeCount; }
}

public class OriginalTweet extends Tweet {
    private final String       content;
    private final List<String> hashtags;
    private final String       mediaUrl;   // nullable

    public OriginalTweet(User author, String content, List<String> hashtags, String mediaUrl) {
        super(author);
        this.content  = content;
        this.hashtags = List.copyOf(hashtags);
        this.mediaUrl = mediaUrl;
    }

    @Override public String displayContent() { return content; }
    public List<String> getHashtags()       { return hashtags; }
}

public class Retweet extends Tweet {
    private final Tweet sourceTweet;

    public Retweet(User author, Tweet sourceTweet) {
        super(author);
        this.sourceTweet = sourceTweet;
    }

    // Content belongs to the source — Retweet is just attribution
    @Override public String displayContent() {
        return "RT @" + sourceTweet.getAuthor().getUsername()
             + ": " + sourceTweet.displayContent();
    }
}

public class Reply extends Tweet {
    private final String content;
    private final Tweet  parentTweet;

    public Reply(User author, String content, Tweet parentTweet) {
        super(author);
        this.content     = content;
        this.parentTweet = parentTweet;
    }

    @Override public String displayContent() {
        return "@" + parentTweet.getAuthor().getUsername() + " " + content;
    }
}
Adding Quote Tweet in the future With polymorphism: add QuoteTweet extends Tweet, implement displayContent(). Zero changes to existing classes. Open/Closed Principle preserved. With the enum approach: add a case to every switch block — Shotgun Surgery.

3. Builder for OriginalTweet

OriginalTweet has optional fields (hashtags, mediaUrl). Builder eliminates telescoping constructors. 

// Pattern: Builder — optional fields with a readable, validated construction API
public class TweetBuilder {

    private final User         author;
    private final String       content;
    private List<String>       hashtags = new ArrayList<>();
    private String             mediaUrl;

    public TweetBuilder(User author, String content) {
        if (content == null || content.isBlank())
            throw new IllegalArgumentException("Tweet content cannot be blank");
        if (content.length() > 280)
            throw new IllegalArgumentException("Tweet exceeds 280 characters");
        this.author  = author;
        this.content = content;
    }

    public TweetBuilder hashtag(String tag)  { hashtags.add(tag); return this; }
    public TweetBuilder media(String url)    { this.mediaUrl = url; return this; }

    public OriginalTweet build() {
        return new OriginalTweet(author, content, hashtags, mediaUrl);
    }
}

// Usage:
Tweet tweet = new TweetBuilder(alice, "Just landed!")
        .hashtag("travel")
        .hashtag("NYC")
        .media("https://cdn.example.com/photo.jpg")
        .build();

4. Observer Pattern — fan-out on write

When Alice posts a tweet, all of Alice's followers should see it in their feed. Observer Pattern: Alice's account is the subject; followers' feeds are the observers. 

// Pattern: Observer — tweet posted → all follower feeds updated automatically
public interface FeedObserver {
    void onTweetPosted(Tweet tweet);
}

public class Feed implements FeedObserver {

    private static final int MAX_FEED_SIZE = 200;

    private final User         owner;
    // LinkedList for O(1) prepend; feed is chronological, always add at head
    private final Deque<Tweet> timeline = new LinkedList<>();

    public Feed(User owner) { this.owner = owner; }

    @Override
    public void onTweetPosted(Tweet tweet) {
        timeline.addFirst(tweet);
        if (timeline.size() > MAX_FEED_SIZE) timeline.removeLast();
    }

    public List<Tweet> getTimeline() { return List.copyOf(timeline); }
}

public class User {

    private final String           id;
    private final String           username;
    // CopyOnWriteArrayList — observers iterated on every post; rare writes, frequent reads
    private final List<FeedObserver> observers = new CopyOnWriteArrayList<>();
    private final Feed             feed;

    public User(String id, String username) {
        this.id       = id;
        this.username = username;
        this.feed     = new Feed(this);
    }

    public void follow(User target) {
        // Register this user's feed as observer of target's tweets
        target.addObserver(this.feed);
    }

    public void unfollow(User target) {
        target.removeObserver(this.feed);
    }

    public Tweet post(String content) {
        Tweet tweet = new TweetBuilder(this, content).build();
        notifyObservers(tweet);   // push to all follower feeds
        return tweet;
    }

    void addObserver(FeedObserver o)    { observers.add(o); }
    void removeObserver(FeedObserver o) { observers.remove(o); }

    private void notifyObservers(Tweet tweet) {
        observers.forEach(o -> o.onTweetPosted(tweet));
    }

    public Feed getFeed() { return feed; }
    public String getId() { return id; }
    public String getUsername() { return username; }
}
Fan-out on write — the scalability trade-off This in-memory model is correct for OOD. At Twitter scale (celebrity with 100M followers), notifying 100M observers synchronously on one post is too slow. Real Twitter uses a hybrid: celebrities use fan-out on read (pull on load); regular users use fan-out on write. For the OOD question, the in-memory Observer is the right answer — mention the scale caveat if the interviewer asks.

6. Retrieval quiz

Q1. Why is Retweet a subclass of Tweet rather than a flag on the same class?

  • A) Java does not allow enums inside entity classes
  • B) A subclass lets each tweet type define its own displayContent() without switch-statements — adding Quote Tweet later touches zero existing classes
  • C) Subclasses are required by the JPA @Inheritance annotation
  • D) Enums cannot hold nullable fields, so a class is needed
Each tweet type has different behaviour (display logic, data fields). Polymorphism encapsulates that per class. A tweetType enum forces every caller to switch — Shotgun Surgery on any new type. Subclass = Open/Closed satisfied.

Q2. Which collection is best for a feed's timeline, and why?

  • A) ArrayList — fast random access for pagination
  • B) TreeSet — keeps tweets sorted by timestamp automatically
  • C) LinkedList (used as Deque) — O(1) prepend for newest-first insertion, O(1) tail removal when feed is full
  • D) PriorityQueue — supports ranked feeds natively
Feed is always newest-first. Every post prepends. When capped at 200, tail is dropped. LinkedList gives O(1) for both operations. ArrayList.add(0, tweet) is O(N) due to element shifting. TreeSet would require a Comparator and doesn't give O(1) tail access. PriorityQueue doesn't maintain insertion order and has O(log N) ops.

Q3. Why use CopyOnWriteArrayList for the observer list rather than ArrayList?

  • A) Every post() iterates the observer list while concurrent follow/unfollow can modify it — CopyOnWriteArrayList prevents ConcurrentModificationException without blocking reads
  • B) CopyOnWriteArrayList is faster for all list operations
  • C) ArrayList cannot store interface types like FeedObserver
  • D) CopyOnWriteArrayList automatically deduplicates observers
post() calls forEach on observers (read). follow/unfollow add/remove (write). If both happen concurrently on ArrayList, iterating thread throws ConcurrentModificationException. CopyOnWriteArrayList: writes copy the array, iterators see a stable snapshot. Reads are fast (no lock); writes are slightly slower — fine here since follows are rare vs posts.

Q4. Alice (10M followers) posts a tweet. The Observer Pattern pushes to all 10M feeds synchronously. What's the problem and what's the mitigation?

  • A) No problem — Observer is designed for exactly this; synchronous fan-out is always correct
  • B) The observer list runs out of memory; fix by limiting followers to 1000
  • C) CopyOnWriteArrayList cannot hold 10M elements; use a database-backed list
  • D) Synchronous fan-out to 10M takes seconds; celebrity accounts should use fan-out on read — followers pull the feed lazily, merging celebrity tweets at query time
Synchronous fan-out to 10M observers on one post can take seconds — unacceptable latency. Real Twitter uses a hybrid: regular users (fan-out on write, push to follower feeds immediately); celebrities (fan-out on read, followers pull celebrity's timeline at query time and merge). For OOD, Observer is correct — add this caveat when asked about scalability.
