Lesson 03 — Twitter: Observer-Driven Notifications (Full Solution Walkthrough)

Category: OOD · Difficulty: Medium · Est. time: 30 min · Prerequisite: Lessons 01–02

This lesson is the full, TDD-ordered walkthrough for q035's current form: the Service Layer + explicit entities design from Lesson 02, extended with a second, independent use of the Observer Pattern — not for the timeline (that stays pull-based, as Lesson 02 argued it should), but for a notification feed: "bob followed you," "bob liked your tweet." Two different problems, two different fan-out strategies, living side by side in the same system on purpose.

What you will be able to do after this lesson Explain why the timeline and the notification feed use opposite fan-out strategies in the same codebase, correctly place a Subject's notifyObservers() call relative to its own state mutation, and — because this project builds solutions for real, not just describes them — recognise two genuine bugs this exact design produced during implementation, and why the fix for each was a null check, not a bigger abstraction.

2. Why two fan-out strategies in one system

Lesson 02 argued the timeline should be pull (fan-out on read): no write-time cost, and — the deciding factor — it supports arbitrary historical queries ("what did I miss since Tuesday") that a push-based cache can't answer without replaying every event. That argument doesn't apply to notifications. A notification inbox has no "arbitrary historical query" requirement — it's inherently an append-only, chronological event log: "here's what happened to you, in order." That's exactly what push (Observer) is good at, and there's no query the pull model would answer better here.

The decision rule, stated plainly Use push (Observer) when the consumer's job is "react to things that happened, in order." Use pull (query) when the consumer's job is "answer a question about current or historical state that could be asked in many different shapes." Timeline = the second. Notifications = the first.

3. The Observer contract — one interface, two events

// Pattern: Observer — one interface, two methods, not two segregated
// FollowObserver/LikeObserver interfaces. NotificationService is the only observer in this
// system and always needs both events; segregating them would only double the bookkeeping
// (two observer lists to maintain in two Subjects) for no behavioral gain.
// What NOT to do: don't collapse this into one onEvent(Object event) method — that
// reintroduces exactly the instanceof/type-switch this question's constraints forbid, since
// every observer would have to branch on the runtime type to know what happened.
public interface TwitterEventObserver {
    void onFollowed(Follow follow);
    void onLiked(Like like);
}

Follow and Like do double duty: they're the persisted graph edge and the event payload handed to observers. No separate FollowEvent type exists — reusing the entity means NotificationService resolves everything it needs (who to notify, who caused it, when) from data the Subject already had.

4. TDD narrative — building SocialGraph as a Subject, red → green

This section is the actual build history for this solution, not a cleaned-up retelling. Two real bugs surfaced while wiring the Subject/Observer machinery, and both are worth seeing exactly as they happened — the fix in each case is smaller than the instinct to reach for a bigger abstraction.

Step 1 — RED: the naive unfollow() throws on an absent relationship

// First implementation — looks reasonable, passes every test that follows a real relationship
public void unfollow(String followerId, String followeeId) {
    following.getOrDefault(followerId, Set.of()).remove(followeeId);
    followers.getOrDefault(followeeId, Set.of()).remove(followerId);
}

// A test exercising the untested path:
//   twitter.getSocialGraph().unfollow(bob.id(), alice.id());  // bob never followed alice
// throws java.lang.UnsupportedOperationException — NOT a no-op as the spec requires.
Why this breaks Map.getOrDefault(key, Set.of()) only substitutes the immutable Set.of() when the key is absent. Calling .remove() on that fallback throws unconditionally — Java's immutable collections reject every mutator, whether or not the target element would even have been present. The bug is invisible in code review because getOrDefault(...).remove(...) reads as an idiomatic one-liner; it's only wrong for the specific case of an absent key, which is exactly the case "unfollow someone you never followed" hits every time.

Step 2 — GREEN: null-check before mutating, don't rely on the immutable fallback

public void unfollow(String followerId, String followeeId) {
    Set<String> followeeSet = following.get(followerId);
    if (followeeSet != null) {
        followeeSet.remove(followeeId);
    }
    Set<String> followerSet = followers.get(followeeId);
    if (followerSet != null) {
        followerSet.remove(followerId);
    }
}
Why this is the right fix, not a bigger one The instinct might be "always initialize every user's Set eagerly on registration" so get() never returns null. Rejected: that couples SocialGraph to knowing about every registration event up front, and still doesn't fix the root cause — getOrDefault(key, ImmutableFallback).mutate() is the actual anti-pattern, and it would resurface the moment any other method used the same shortcut (which is exactly what happened next).

Step 3 — the same bug class, caught before it shipped: LikeService.unlike()

LikeService.unlike() was written against the same original (buggy) pattern in the initial plan: likesByTweet.getOrDefault(tweetId, Set.of()).remove(userId). Because the SocialGraph bug had already been found and fixed by the time LikeService was built, the identical fix — null-checked Map.get() — was applied proactively, before it ever failed a test: 

public void unlike(String userId, String tweetId) {
    String key = userId + ":" + tweetId;
    likes.remove(key);
    Set<String> likers = likesByTweet.get(tweetId);
    if (likers != null) {
        likers.remove(userId);
    }
}
The generalizable lesson Once you've found map.getOrDefault(key, ImmutableCollection.of()).mutate() is broken in one place, grep the rest of the codebase for the same shape before moving on — it's a pattern bug, not a one-off typo. (This is also why TweetRepository's read methods use getOrDefault(key, List.of()) safely — reading with a fallback is fine; the bug is specifically calling a mutator on the fallback.)

5. SocialGraph — the finished Subject

public class SocialGraph {

    private final Map<String, Set<String>> following = new HashMap<>();
    private final Map<String, Set<String>> followers = new HashMap<>();
    private final List<TwitterEventObserver> observers = new ArrayList<>();

    public void addObserver(TwitterEventObserver observer) {
        observers.add(observer);
    }

    public Follow follow(String followerId, String followeeId) {
        if (followerId.equals(followeeId)) {
            throw new IllegalArgumentException("A user cannot follow themselves: " + followerId);
        }
        following.computeIfAbsent(followerId, k -> new HashSet<>()).add(followeeId);
        followers.computeIfAbsent(followeeId, k -> new HashSet<>()).add(followerId);

        Follow event = new Follow(followerId, followeeId, Instant.now());
        // Notify AFTER both maps are consistent — an observer reacting to onFollowed()
        // must see a fully-updated graph, not a half-written one.
        for (TwitterEventObserver observer : observers) {
            observer.onFollowed(event);
        }
        return event;
    }

    // unfollow(), getFollowing(), getFollowers(), isFollowing(), getFollowerCount()
    // — unchanged from Lesson 02, except unfollow() carries the fix from Section 4.
}
Notice what unfollow() does NOT do It never calls notifyObservers, and it never tries to retract a past notification. "bob followed you" stays true as history even after bob unfollows — notifications are an append-only event log, not a live mirror of current graph state. Same reasoning as why Follow/Like are immutable entities instead of mutable relationship flags.

6. NotificationService — the concrete Observer

One class, subscribed to two Subjects. This is the entire reason TwitterEventObserver exists as a shared interface rather than two unrelated callback types. 

public class NotificationService implements TwitterEventObserver {

    private final UserRepository userRepository;
    private final TweetRepository tweetRepository;
    // Deque + addFirst: O(1) prepend for "newest first" ordering — same shape as
    // Lesson 01's Feed, applied to notifications instead of tweets.
    private final Map<String, Deque<Notification>> byRecipient = new HashMap<>();

    public NotificationService(UserRepository userRepository, TweetRepository tweetRepository) {
        this.userRepository = userRepository;
        this.tweetRepository = tweetRepository;
    }

    @Override
    public void onFollowed(Follow follow) {
        String actorName = userRepository.findById(follow.followerId())
                .map(User::username).orElse(follow.followerId());
        store(new Notification(UUID.randomUUID().toString(), follow.followeeId(),
                follow.followerId(), NotificationType.FOLLOW, actorName + " followed you",
                Instant.now()));
    }

    @Override
    public void onLiked(Like like) {
        Optional<Tweet> tweet = tweetRepository.findById(like.tweetId());
        if (tweet.isEmpty()) return;

        String recipientId = tweet.get().authorId();
        // Real product requirement, not a defensive guard: don't notify yourself for
        // liking your own tweet.
        if (recipientId.equals(like.userId())) return;

        String actorName = userRepository.findById(like.userId())
                .map(User::username).orElse(like.userId());
        store(new Notification(UUID.randomUUID().toString(), recipientId, like.userId(),
                NotificationType.LIKE, actorName + " liked your tweet", Instant.now()));
    }

    private void store(Notification notification) {
        byRecipient.computeIfAbsent(notification.recipientId(), k -> new ArrayDeque<>())
                .addFirst(notification);
    }

    public List<Notification> getNotifications(String userId) {
        return List.copyOf(byRecipient.getOrDefault(userId, new ArrayDeque<>()));
    }
}
Why ID resolution lives here, not in the Subjects Follow/Like only carry IDs. Turning "u-123 followed u-456" into "alice followed you" needs a username lookup; Like→recipient needs a tweet-author lookup. Doing that resolution in NotificationService (not in SocialGraph/LikeService) keeps the Subjects completely ignorant of what any observer does with their events — they just publish raw domain facts. Neither Subject imports Notification, UserRepository, or TweetRepository.
What NOT to do — the tempting shortcut that would break the pull-model timeline Don't have NotificationService prepend the new tweet into a cached FeedService timeline on every onFollowed/onLiked. That resurrects exactly the push-based staleness problem Lesson 02 spent a whole section arguing the pull model avoids. Timeline stays pull. Notifications stay push. They're solved separately on purpose — see Section 2.

7. TwitterService — wiring the subscription, once

public TwitterService() {
    this.userRepository = new UserRepository();
    this.tweetRepository = new TweetRepository();
    this.socialGraph = new SocialGraph();
    this.likeService = new LikeService();
    this.feedService = new FeedService(socialGraph, tweetRepository);
    this.notificationService = new NotificationService(userRepository, tweetRepository);

    // Subscribe once, here — the only place SocialGraph/LikeService and
    // NotificationService know about each other.
    socialGraph.addObserver(notificationService);
    likeService.addObserver(notificationService);
}
Rejected alternative — the facade publishes events itself A simpler-looking option: skip the observer machinery, and have TwitterService.follow() call socialGraph.follow(...) and then also call notificationService.onFollowed(...) directly. This compiles, passes every test — and isn't Observer at all, just two sequential method calls. It also doesn't scale: adding a second Subject later means editing TwitterService every time, instead of the new Subject just calling addObserver() on the same, already-built NotificationService.

10. Retrieval quiz

Q1. Why does this design use Observer (push) for notifications but stayed with pull (fan-out on read) for the timeline, instead of using Observer for both?

  • A) Observer can only be used once per system
  • B) Push is always slower than pull, so it's reserved for low-traffic features
  • C) The notification inbox has no "arbitrary historical query" requirement — it's inherently an append-only chronological log, which is exactly what push is good at. The timeline needs to answer many different possible queries, which push-built caches can't do without replaying every event
  • D) Because NotificationService and FeedService cannot both depend on TweetRepository
The deciding factor is what the consumer's job actually is. "React to things that happened, in order" fits push. "Answer a question about state that could be asked many different ways" fits pull. Notifications are the first; timelines are the second.

Q2. In SocialGraph.follow(), why does the observer notification loop run AFTER both the following and followers maps are updated, rather than before?

  • A) Java requires all field mutations before any method call in a constructor
  • B) An observer reacting to the event (e.g. NotificationService resolving a username) must see a fully-consistent graph, not a half-written one where only one of the two maps has been updated
  • C) It doesn't matter — the ordering is arbitrary
  • D) Because Follow is an immutable record and must be constructed last
If an observer ran mid-mutation, it could observe following updated but followers not yet updated (or vice versa) — a real consistency bug for any observer whose logic depends on graph state, even though NotificationService today doesn't happen to query the graph itself.

Q3. What was the actual root cause of the unfollow() bug found while building this solution?

  • A) Forgetting to check if the followerId equals the followeeId
  • B) Using a HashMap instead of a TreeMap for the adjacency lists
  • C) Not synchronizing access to the observer list
  • D) Calling .remove() on the immutable Set.of() fallback that getOrDefault() returns when the key is absent — Set.of() rejects every mutator unconditionally, regardless of whether the target element would even be present
The fix wasn't a bigger abstraction (like eagerly initializing every user's Set on registration) — it was recognizing that getOrDefault(key, ImmutableFallback).mutate() is unsafe by construction, and switching to a null-checked Map.get() before mutating.

Q4. Why does NotificationService — not SocialGraph or LikeService — hold the UserRepository/TweetRepository references needed to build a readable message like "bob followed you"?

  • A) Keeping ID-to-message resolution in the Observer means the Subjects stay completely ignorant of notifications — they publish raw Follow/Like facts and never import Notification, UserRepository, or TweetRepository at all
  • B) SocialGraph and LikeService are not allowed to depend on any repository
  • C) UserRepository and TweetRepository can only be instantiated once per application
  • D) It reduces the number of classes in the package
This is the entire point of Observer: the Subject knows a fact happened; only the Observer knows (and cares) what to do about it. If SocialGraph resolved usernames itself, it would need to know about notification message formatting — coupling a graph-mutation class to a presentation concern that has nothing to do with graph mutation.

🤖 AI Engineering Extension

Where AI fits

NotificationService currently fires a notification for every single Follow/Like event, unconditionally. At real scale (a user with 50,000 followers who all liked one viral tweet), that's 50,000 near-identical "X liked your tweet" notifications landing at once — a UX and infrastructure problem, not a correctness one. This is the natural seam for an AI-assisted notification ranking / batching layer sitting between the Observer's raw event stream and what actually gets shown to a user.

Pattern

Classification + ranking, not generation. A lightweight model (or even a rules-engine standing in for one) scores each incoming Notification for predicted engagement ("would this user open this?") and groups near-duplicate events ("bob and 47 others liked your tweet") before they're surfaced — closer to a recommender-system re-ranking step than a chatbot.

Architecture delta

NotificationService.store() stays exactly as-is (it's still the source-of-truth event log — never lossy). A new downstream consumer, NotificationRankingService, reads from the same append-only log and produces a separate, model-scored view for "what to actually push to the user's device right now." This keeps the Observer's job (durable, complete history) cleanly separate from the ranking job (best-effort, model-driven, allowed to be wrong or batch things).

Tradeoffs

Latency: ranking adds a scoring step between "event happened" and "user sees it" — acceptable for a notification (seconds of delay is fine) but would not be for the timeline path. Accuracy vs. rule-based: a simple "batch if >5 similar events in 10 minutes" rule solves the worst case cheaply; a model adds marginal engagement lift at real inference cost per event. Cold start: a new user with no engagement history gives the model nothing to rank on — fall back to chronological (today's actual behavior) until enough signal exists.

AWS / managed services

Amazon Personalize (managed recommendation/ranking models) or a lightweight rules engine on Lambda for the batching step; SQS between the Observer's event log and the ranking consumer so a slow/failed ranking pass never blocks NotificationService.store() itself; Bedrock only if notification text generation (not just ranking) is ever wanted — overkill for this system as designed.

AI-Q: Why should the ranking/batching layer read from NotificationService's existing log as a separate downstream consumer, rather than modifying NotificationService.store() to rank notifications before storing them?

  • A) Java doesn't allow two classes to read the same Map
  • B) Ranking is model-driven and best-effort — it can be wrong, slow, or temporarily unavailable without that being acceptable for the source-of-truth event log itself. Keeping them separate means a ranking outage never causes a lost or corrupted notification record
  • C) It reduces the total line count of NotificationService
  • D) AWS Personalize requires data to already be pre-sorted before ingestion
The same "keep the durable fact separate from the best-effort interpretation of it" principle that put ID resolution in the Observer rather than the Subject applies again one layer up: NotificationService's job is "record what happened, completely and correctly." Ranking's job is "guess what's worth surfacing right now." Mixing them means a model hiccup could corrupt or drop the historical record — never acceptable for an audit-style log.
