Lesson 01 — Odds Feed Observer

Category: OOD · Difficulty: Medium · Est. time: 20 min · Lesson 1 of N

This project has used Observer twice before — q027's BankAccount notifying an email listener and a fraud-alert listener, and q032's Twitter feed fanning out tweets to followers. This lesson applies the same pattern to a different real production shape: a live in-play sportsbook odds feed, where a price display board and a market-suspension monitor both need to react to every odds change, independently of each other and of the feed itself.

What you will be able to do after this lesson Given "design a live odds feed" or any "one source of truth, several independent reactions" problem, reach for Observer, explain why the Subject fires after its own state changes (not before), and justify CopyOnWriteArrayList over a plain list when listeners can register/unregister mid-notification.

1. Entities at a glance

2. TDD, red → green: the Subject fires after its own state changes

// GREEN
public interface OddsListener {
    void onOddsChanged(OddsChangedEvent event);
}

public record OddsChangedEvent(String eventName, String selectionName,
                                BigDecimal previousOdds, BigDecimal newOdds) {}

public class OddsFeed {
    private final Map<String, BigDecimal> currentOdds = new ConcurrentHashMap<>();
    private final List<OddsListener> listeners = new CopyOnWriteArrayList<>();

    public void addListener(OddsListener listener) { listeners.add(listener); }
    public void removeListener(OddsListener listener) { listeners.remove(listener); }

    public void publishOddsChange(String eventName, String selectionName, BigDecimal newOdds) {
        BigDecimal previousOdds = currentOdds.getOrDefault(selectionName, newOdds);
        currentOdds.put(selectionName, newOdds);   // state changes FIRST

        OddsChangedEvent event = new OddsChangedEvent(eventName, selectionName, previousOdds, newOdds);
        for (OddsListener listener : listeners) {   // notify SECOND
            listener.onOddsChanged(event);
        }
    }
}
Why previousOdds defaults to newOdds on a brand-new selection A selection's first-ever published price has no prior value to have moved from. Defaulting to newOdds gives a genuine zero-percent move on that first publish — treating a missing baseline as zero and calling it a "100% move" would falsely trip MarketSuspensionListener the instant any new market opened.

Q1. Why does OddsFeed.publishOddsChange() update currentOdds before looping over listeners, rather than after?

  • A) Java requires all field writes to precede any method call in the same method body
  • B) It doesn't matter — updating after would produce identical behaviour
  • C) A listener that reads OddsFeed's own state (rather than only the event object) — e.g. checking currentOdds for a different, correlated selection — must see the update already applied, not still pending
  • D) CopyOnWriteArrayList requires the backing map to be updated first or it throws
If a listener could observe OddsFeed mid-update (state changed, notification not yet sent, versus notification sent, state not yet changed), different listeners in the same list could see inconsistent pictures of "current" odds. Committing the state change first, then notifying, guarantees every listener sees the same already-applied fact.

3. MarketSuspensionListener — percentage, not raw difference

@Override
public void onOddsChanged(OddsChangedEvent event) {
    BigDecimal previousOdds = event.previousOdds();
    BigDecimal move = event.newOdds().subtract(previousOdds).abs();
    BigDecimal movePercentage = move
            .divide(previousOdds, 4, RoundingMode.HALF_UP)
            .multiply(BigDecimal.valueOf(100));

    if (movePercentage.compareTo(thresholdPercentage) >= 0) {
        suspendedSelections.add(event.selectionName());
    }
}
Why percentage-of-previousOdds, not the raw difference A move from 1.10 to 1.20 (raw difference 0.10) is a huge relative jump on very short odds. A move from 10.00 to 10.10 (same raw difference, 0.10) is close to irrelevant on long odds. A single "suspend if the difference exceeds 0.10" rule would either suspend constantly on short-odds markets or never suspend at all on long-odds ones. Dividing by previousOdds makes the threshold mean the same thing regardless of what range a selection's odds happen to sit in.

Q2. Why does MarketSuspensionListener take its threshold as a constructor parameter (BigDecimal thresholdPercentage) instead of a hardcoded constant, when the requirement only demonstrates one threshold value in tests?

  • A) Constructor parameters are required by JUnit for any class under test
  • B) Different markets in a real sportsbook need different suspension sensitivity — a football match-winner market and a tennis in-play market don't share one universal definition of "drastic move" — so the caller, not the class, must decide
  • C) BigDecimal fields cannot be declared as compile-time constants in Java
  • D) It doesn't actually need to be configurable — this is only a testing convenience
Hardcoding a single threshold would force every market that ever uses this listener to accept the same suspension sensitivity, which doesn't hold in a real sportsbook where different sports and bet types have very different normal volatility.

4. Why CopyOnWriteArrayList, not a plain ArrayList + synchronized

A listener can legitimately need to remove itself from inside its own onOddsChanged() callback — for example, a listener that only cares about one alert and then stops listening. That means OddsFeed can be iterating listeners at the exact moment a mutation to that same list happens, on the same thread, mid-iteration. 

// RED, then GREEN with CopyOnWriteArrayList already in place — no extra code needed
@Test
void listenerCanUnregisterItselfDuringNotificationWithoutBreakingTheFeed() {
    OddsListener selfRemoving = new OddsListener() {
        @Override
        public void onOddsChanged(OddsChangedEvent event) {
            feed.removeListener(this);
        }
    };
    feed.addListener(selfRemoving);
    feed.addListener(other);

    feed.publishOddsChange(...);   // selfRemoving fires once, removes itself mid-loop
    feed.publishOddsChange(...);   // selfRemoving does NOT fire again; other still does
}
What a plain ArrayList would do here Iterating an ArrayList with a standard for-each while another piece of code calls list.remove() on it throws ConcurrentModificationException — this project's feedback_teaching_explanations standing rule is exactly why this gets spelled out rather than silently choosing the "safe" collection type without explanation. CopyOnWriteArrayList's iterator works off a stable snapshot taken when iteration starts, so an in-flight removeListener() call is safe — the trade-off is that every add/remove copies the entire backing array, which is fine here (listener churn is rare; odds publish frequently, but listener registration doesn't) and would be the wrong choice for a list mutated as often as it's iterated.

Q3. What would happen if OddsFeed.listeners were a plain ArrayList, and a listener called feed.removeListener(this) from inside its own onOddsChanged(), mid-publish?

  • A) Nothing different — ArrayList and CopyOnWriteArrayList behave identically for this case
  • B) The removal would silently be ignored until the next publish
  • C) BigDecimal arithmetic elsewhere in the class would start failing
  • D) The for-each loop currently iterating listeners would throw ConcurrentModificationException, because a plain ArrayList detects structural modification during iteration and fails fast
ArrayList's iterator tracks a modification count and throws ConcurrentModificationException the moment it detects the list changed underneath it mid-iteration. CopyOnWriteArrayList's iterator instead works from an immutable snapshot taken at iteration start, which is exactly why it tolerates a listener modifying the list from within its own callback.

5. What interviewers are actually probing

ProbeExpected answer
Why Observer here?OddsFeed shouldn't need to know a price board or a suspension monitor exist — new reactions get added without touching OddsFeed
Why fire after updating state, not before?Every listener must see a consistent, already-applied picture of current odds, not a pending one
Why percentage, not raw odds difference, for suspension?A fixed raw threshold means wildly different things on short vs long odds; percentage-of-previousOdds normalises that
Why CopyOnWriteArrayList?Listeners can register/unregister — including from inside their own callback, mid-notification — without the iteration throwing
Why a record for OddsChangedEvent?An event is an immutable fact; a mutable event would let one listener silently change what later listeners in the same notification see
Ask your teacher Unclear on why the threshold is percentage-based, or want to talk through what a third listener (e.g. a settlement trigger, or an audit log writing every odds change to WORM-style storage) would need to look like? Ask before moving to the question.
