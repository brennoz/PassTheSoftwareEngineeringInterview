Lesson 01 — Bet Slip Composite

Category: OOD · Difficulty: Medium · Est. time: 25 min · Lesson 1 of N

"Design a bet slip" is a natural Composite Pattern question because a sportsbook already has the exact shape Composite exists for: a customer places single bets and accumulator (parlay) bets, mixes them freely on one slip, and the platform needs one uniform way to total stake and payout across the whole slip — without an instanceof chain anywhere. This is the first Composite-pattern question in this project (State x3, Command, Strategy, and Specification have all appeared before this).

What you will be able to do after this lesson Given "design a bet slip" or any tree-of-similar-things problem, identify which layer actually needs Composite's recursive uniformity and which layer would only be pretending to need it — and explain why those two answers are different in this design.

1. The tempting wrong shape, first

The obvious first instinct: give every bet-shaped thing a List<Wager> of children, all the way down. A SingleBet has zero children, an AccumulatorBet's children are its legs, a BetSlip's children are its bets. One recursive interface, total uniformity, done.

Why that's wrong for AccumulatorBet specifically An accumulator's legs are picks — an event and odds and an eventual result. They are not independently-staked bets. If AccumulatorBet held List<Wager> legs, nothing would stop a caller from building a leg out of a SingleBet that carries its own stake — implying that leg could be settled and paid out on its own, which is not how a real parlay works. Only the accumulator's own stake exists.

This is the actual design decision this lesson is about: Composite is genuinely earned at one level (BetSlip over Wager) and would be a false fit at another (AccumulatorBet over its legs). Knowing which is which — not just "can I draw a recursive tree here" — is what separates a correct Composite design from a pattern applied because it was available.

3. TDD, red → green: SingleBet first

Start at the leaf — no dependencies, cheapest thing to get right first. 

// RED — this doesn't compile yet, nothing exists
@Test
void singleBetWonPaysStakeTimesOdds() {
    Selection selection = new Selection("Team A win", new BigDecimal("2.50"));
    SingleBet bet = new SingleBet(selection, new BigDecimal("10.00"));
    selection.settle(SelectionResult.WON);

    assertEquals(0, bet.calculatePayout().compareTo(new BigDecimal("25.00")));
}

// GREEN — minimum to pass
public class Selection {
    private final String eventName;
    private final BigDecimal odds;
    private SelectionResult result = SelectionResult.PENDING;

    public Selection(String eventName, BigDecimal odds) {
        this.eventName = eventName;
        this.odds = odds;
    }
    public BigDecimal getOdds() { return odds; }
    public SelectionResult getResult() { return result; }
    public void settle(SelectionResult result) { this.result = result; }
}

public interface Wager {
    BigDecimal getStake();
    BigDecimal calculatePayout();
    boolean isWon();
}

public class SingleBet implements Wager {
    private final Selection selection;
    private final BigDecimal stake;

    public SingleBet(Selection selection, BigDecimal stake) {
        this.selection = selection;
        this.stake = stake;
    }
    @Override public BigDecimal getStake() { return stake; }
    @Override public boolean isWon() { return selection.getResult() == SelectionResult.WON; }
    @Override public BigDecimal calculatePayout() {
        return isWon() ? stake.multiply(selection.getOdds()) : BigDecimal.ZERO;
    }
}

A second test (lost selection pays zero) passes with no further changes — the isWon() guard already handles it. That's the signal SingleBet is done; move to the next layer instead of adding more tests that exercise the same branch.

Q1. Why must calculatePayout() check isWon() internally, rather than trusting the caller to check first and only call it when the bet has won?

  • A) BigDecimal.multiply() throws if called on a losing bet
  • B) JUnit requires every method under test to be side-effect free
  • C) BetSlip later sums calculatePayout() across a whole tree of children without inspecting each one individually — the method must be safe to call blindly, on anything, at any settlement state
  • D) It isn't required — checking outside would be equally correct
BetSlip.calculatePayout() (built later in this lesson) calls calculatePayout() on every child uniformly, with no isWon() check at the call site. If SingleBet or AccumulatorBet trusted the caller to pre-check, that contract would be silently violated the first time BetSlip sums a tree containing an unsettled bet.

4. AccumulatorBet — where the "legs are not Wagers" decision earns its keep

// Pattern: Composite — but composing Selection, not Wager. legs is
// List<Selection> on purpose: a leg is a pick, not an independently-staked sub-bet.
public class AccumulatorBet implements Wager {
    private final List<Selection> legs = new ArrayList<>();
    private final BigDecimal stake;

    public AccumulatorBet(BigDecimal stake) { this.stake = stake; }
    public void addLeg(Selection selection) { legs.add(selection); }

    @Override
    public boolean isWon() {
        return !legs.isEmpty() && legs.stream().allMatch(leg -> leg.getResult() == SelectionResult.WON);
    }

    @Override
    public BigDecimal calculatePayout() {
        if (!isWon()) return BigDecimal.ZERO;
        BigDecimal combinedOdds = legs.stream()
                .map(Selection::getOdds)
                .reduce(BigDecimal.ONE, BigDecimal::multiply);
        return stake.multiply(combinedOdds);
    }

    @Override
    public BigDecimal getStake() { return stake; }
}
Why !legs.isEmpty() in isWon(), not just allMatch() Stream.allMatch() on an empty stream returns true — vacuous truth. Without the explicit empty check, a freshly-constructed AccumulatorBet with zero legs added would report isWon() == true and pay out its full stake on settlement. This is a real production bug shape (an accumulator built but never populated before settlement runs), not a hypothetical edge case worth skipping.

Q2. Why does AccumulatorBet hold List<Selection> instead of List<Wager>, when BetSlip (built next) holds List<Wager> for the exact same "combine several things" purpose?

  • A) Java generics don't allow a class to implement an interface it also holds a list of
  • B) An accumulator leg is a pick (event + odds + eventual result), not an independently-staked bet — List<Wager> would let a leg carry its own stake, implying it could be settled and paid out on its own, which doesn't match how a real parlay works
  • C) Selection is faster to iterate over than Wager at runtime
  • D) BetSlip's children are always heterogeneous, so it needs Wager, while AccumulatorBet's legs are always the same type, so it doesn't
The type choice encodes a real domain rule: only the accumulator's own stake exists. Making legs Selection instead of Wager makes "a leg has its own stake" a compile error instead of something that has to be caught in code review or with a runtime instanceof guard.

5. BetSlip — the actual recursive Composite

// Pattern: Composite — the node that genuinely needs recursion. A Wager
// here can be a SingleBet, an AccumulatorBet, or another BetSlip.
public class BetSlip implements Wager {
    private final List<Wager> wagers = new ArrayList<>();

    public void addWager(Wager wager) { wagers.add(wager); }

    @Override
    public BigDecimal getStake() {
        return wagers.stream().map(Wager::getStake).reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    @Override
    public boolean isWon() {
        return !wagers.isEmpty() && wagers.stream().allMatch(Wager::isWon);
    }

    @Override
    public BigDecimal calculatePayout() {
        return wagers.stream().map(Wager::calculatePayout).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

The TDD-driving test for this class is the nested-slip case, not the flat-mix case — the flat mix (one SingleBet + one AccumulatorBet summed together) would already pass with a non-recursive List<SingleBet | AccumulatorBet> design. What actually forces BetSlip to implement Wager itself, rather than just being a container of leaf bets, is this: 

// RED, then GREEN with no extra code needed — BetSlip already implements Wager,
// so nesting one inside another just works
@Test
void nestedBetSlipPayoutIsSummedByParentSlip() {
    Selection wonSelection = new Selection("Nested single", new BigDecimal("2.00"));
    SingleBet nestedSingle = new SingleBet(wonSelection, new BigDecimal("10.00"));
    wonSelection.settle(SelectionResult.WON);

    BetSlip innerSlip = new BetSlip();
    innerSlip.addWager(nestedSingle);

    BetSlip outerSlip = new BetSlip();
    outerSlip.addWager(innerSlip);          // a BetSlip added as a Wager, not a special case

    assertEquals(0, outerSlip.getStake().compareTo(new BigDecimal("10.00")));
    assertEquals(0, outerSlip.calculatePayout().compareTo(new BigDecimal("20.00")));
}
Why no nesting guard on BetSlip, when AccumulatorBet has one (by type) There is no business rule against a slip containing another slip — grouping a customer's session-level wagers into one account-level rollup is a legitimate real reporting need. AccumulatorBet's restriction exists because bookmakers genuinely forbid "an acca of accas" as a product rule. Copying that restriction onto BetSlip would defend against a problem this domain doesn't have — the two classes look structurally similar (both hold a List of something bet-shaped) but the correct amount of restriction is different for each, because the underlying business rules differ.

Q3. What test would fail first if BetSlip were refactored to hold List<SingleBet> and List<AccumulatorBet> as two separate fields, instead of one List<Wager>?

  • A) nestedBetSlipPayoutIsSummedByParentSlip — there would be nowhere to put a BetSlip as a child anymore
  • B) singleBetWonPaysStakeTimesOdds — SingleBet's own payout logic doesn't depend on BetSlip's internal structure
  • C) accumulatorWithOneLostLegPaysZeroEvenIfOthersWon — AccumulatorBet doesn't reference BetSlip at all
  • D) None of them — all the existing tests would still pass unchanged
Two separate typed lists can each hold their own concrete type, but neither has room for "a BetSlip nested inside a BetSlip" — that's precisely the case that requires BetSlip's children to be typed as the shared Wager interface, not as specific leaf types.

6. What interviewers are actually probing

ProbeExpected answer
Why Composite here?BetSlip must total stake/payout across SingleBet and AccumulatorBet uniformly, with no instanceof/switch on wager type
Why doesn't AccumulatorBet hold List<Wager> too?An accumulator leg is a pick, not an independently-staked bet — List<Selection> makes that a type-level fact
Why can BetSlip nest BetSlip but AccumulatorBet can't nest itself?Different business rules: no rule bans nested slips; bookmakers do ban nested accumulators
Why does isWon() explicitly check for an empty collection?Stream.allMatch() on empty is vacuously true — an unpopulated accumulator or slip must not silently report as won
Where does BigDecimal.ZERO/ONE come in?Identity elements for the reduce() calls — sum starts at ZERO, product starts at ONE
Ask your teacher Unclear on why AccumulatorBet's legs aren't Wager, or want to talk through what a fourth Wager implementation (e.g. a "Free Bet" with a stake that isn't returned on a win) would need to change? Ask before moving to the question.
