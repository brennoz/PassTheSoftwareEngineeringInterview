Booking Lifecycle — State Machine with Enum Guards

Question this lesson prepares you for: q081 — implement a rail booking lifecycle with correct transition guards, BigDecimal money, and an exception on invalid transitions.

The problem with String status

The naive implementation stores status as a String:

booking.setStatus("CONFIRMED");
if (booking.getStatus().equals("CONFIRMED")) { ... }

Three problems: (1) a typo ("CONFIMED") compiles fine and fails silently at runtime; (2) nothing prevents cancel() being called on a TICKETED booking — a printed ticket can't be refunded, but the code doesn't know that; (3) the valid transitions are scattered across service methods rather than declared in one place.

Solution: enum that owns its transition rules

The key insight: put the state machine rules on the enum, not in the service. Each constant declares which states it can be reached from.

public enum BookingStatus {

    PENDING  (Set.of()),
    CONFIRMED(Set.of(PENDING)),
    TICKETED (Set.of(CONFIRMED)),
    CANCELLED(Set.of(PENDING, CONFIRMED));
    // TICKETED is deliberately absent from CANCELLED's predecessors —
    // a printed ticket cannot be cancelled

    private final Set<BookingStatus> validPredecessors;

    BookingStatus(Set<BookingStatus> validPredecessors) {
        this.validPredecessors = validPredecessors;
    }

    public boolean canTransitionFrom(BookingStatus current) {
        return validPredecessors.contains(current);
    }
}
Open/Closed principle in action Adding a new state (e.g. ON_HOLD) only requires adding one enum constant with its predecessors. BookingService does not change — its guard logic works for any state. Compare to the alternative: a Map<BookingStatus, Set<BookingStatus>> in BookingService — adding a state requires updating the map separately, easy to forget.

State diagram

The guard in BookingService

public class BookingService {

    private static final BigDecimal CANCELLATION_REFUND_RATE = new BigDecimal("0.80");

    private final BookingRepository repository;

    public BookingService(BookingRepository repository) {
        this.repository = repository;
    }

    public void confirm(String bookingId) {
        Booking booking = repository.findById(bookingId);
        transition(booking, BookingStatus.CONFIRMED);
        repository.save(booking);
    }

    public void cancel(String bookingId) {
        Booking booking = repository.findById(bookingId);
        transition(booking, BookingStatus.CANCELLED);
        repository.save(booking);
    }

    public void issue(String bookingId) {
        Booking booking = repository.findById(bookingId);
        transition(booking, BookingStatus.TICKETED);
        repository.save(booking);
    }

    public BigDecimal calculateRefund(String bookingId) {
        Booking booking = repository.findById(bookingId);
        if (booking.getStatus() == BookingStatus.CANCELLED) {
            return booking.getAmount()
                          .multiply(CANCELLATION_REFUND_RATE)
                          .setScale(2, RoundingMode.HALF_UP);
        }
        return BigDecimal.ZERO;
    }

    // Single guard — if this method is missing from ANY operation,
    // it's immediately obvious. Not inlined per-method.
    private void transition(Booking booking, BookingStatus target) {
        BookingStatus current = booking.getStatus();
        if (!target.canTransitionFrom(current)) {
            throw new InvalidStateTransitionException(booking.getId(), current, target);
        }
        booking.setStatus(target);
    }
}

Why BigDecimal, not double

Expressiondouble resultBigDecimal result
199.99 * 0.8159.99199999999998159.99
0.1 + 0.20.300000000000000040.3
1.005 * 100100.49999999999999100.50

double is IEEE 754 — it cannot represent most decimal fractions exactly. For money, use new BigDecimal("0.80") (string constructor) or BigDecimal.valueOf(0.80) — never new BigDecimal(0.80) (double constructor, inherits the imprecision).

BigDecimal comparison trap new BigDecimal("2.00").equals(new BigDecimal("2.0")) returns false — equals() compares scale too. Always use compareTo() == 0 to compare values, not equals().

Where to put the guard: enum vs service vs entity

ApproachProCon
Rules on the enum (this solution)Adding a state = one place to edit; Open/ClosedEnum has logic — slightly heavier than a plain value enum
Map in BookingServiceRules visible in one service methodAdding a state = edit both enum AND the map; easy to forget one
Full State pattern (separate classes)Each state object handles its own behaviourOverkill for a simple lifecycle — 5 classes for 4 states

For a simple lifecycle with no state-specific behaviour beyond transition rules, enum-with-predecessors is the cleanest choice. The full GoF State pattern earns its weight when each state has materially different behaviour (not just different allowed transitions).

Q1. Why is TICKETED absent from CANCELLED's valid predecessors set?

  • A ticket can always be cancelled if the passenger requests it
  • A printed ticket represents a committed physical document — cancellation after issue creates a financial/operational contradiction the system must prevent at the model level
  • TICKETED bookings are stored in a different database and cannot be looked up
  • To simplify the unit tests for the cancel() method
The state machine encodes a real-world constraint: once a ticket is printed, there is no reversing it without a separate refund process. Encoding this in the enum (not as a comment or documentation) means the system enforces it at every call site automatically.

Q2. A test asserts assertEquals(new BigDecimal("159.99"), service.calculateRefund("B1")) where the booking amount is £199.99. What subtle bug could make this test fail even with correct logic?

  • BigDecimal.multiply() always returns a scale-0 result
  • HALF_UP rounding rounds £159.992 up to £160.00
  • BigDecimal.equals() compares scale — 159.990 and 159.99 are not equal by equals(), only by compareTo()
  • new BigDecimal("199.99") cannot be multiplied by a two-decimal factor
BigDecimal.equals() is scale-sensitive. new BigDecimal("159.99").equals(new BigDecimal("159.990")) is false. Use compareTo() == 0 in tests. This is why the solution uses setScale(2, HALF_UP) — it normalises the scale — but tests should still use compareTo to be safe.
