A Dockerfile is not just a build script — it is a security boundary, a caching contract, and a deployment artifact all in one. Getting it wrong costs you 500 MB of Maven re-downloads on every commit, containers running as root, and Kubernetes pods that ignore shutdown signals. This lesson covers the canonical multi-stage Dockerfile for a Spring Boot service and explains every decision.

Where containers fit in the pipeline

Every push to GitLab triggers a chain. The multi-stage docker build is the step that converts compiled Java into a runnable, versioned artifact — the unit that Kubernetes actually deploys.

git push │ └─▶ GitLab CI │ ├─ mvn test ← unit tests fail fast, before image build │ ├─ docker build (multi-stage) ◀── YOU ARE HERE │ Stage 1 → eclipse-temurin:21-jdk-alpine (build) │ Stage 2 → eclipse-temurin:21-jre-alpine (runtime) │ └─ docker push ──────────────▶ ECR │ image:sha256-abc123 Helm chart updated (image tag) │ ArgoCD detects drift │ EKS rolling update (old pods → new pods) │ Datadog traces + logs stream (APM agent auto-injected via K8s) Underneath everything: Terraform provisioned ECR repository + EKS cluster + IAM roles

The image tag that flows from docker push through to ArgoCD must be a content-addressed identifier — a Git SHA or digest, never latest. We will see why in the "What breaks" section.

Why multi-stage — size and attack surface

A single-stage build that compiles and runs from the same image ships the entire JDK, Maven, and your source tree into production. Multi-stage builds let you throw all of that away — only the JAR crosses the boundary into the runtime image.

Single-stage JDK
Base: eclipse-temurin:21-jdk
Final size: ~600 MB

What's inside:
  • Full JDK (javac, jshell, jmap)
  • Maven binary + local repo (~200 MB)
  • Source code
  • Alpine build tools (wget, curl)

Attack surface: Compiler present — attacker can compile payloads inside the container. Maven credentials potentially on disk.
Multi-stage JDK → JRE
Build: eclipse-temurin:21-jdk-alpine
Runtime: eclipse-temurin:21-jre-alpine
Final size: ~200 MB

What's inside (runtime only):
  • JRE (java binary only — no javac)
  • Your JAR
  • Alpine minimal userland (sh, wget)

Attack surface: No compiler, no Maven, no src. Shell still present — an attacker can spawn a shell if they break out of the JVM.
Multi-stage → Distroless
Build: eclipse-temurin:21-jdk-alpine
Runtime: gcr.io/distroless/java21
Final size: ~120 MB

What's inside (runtime only):
  • JRE (from Google's curated image)
  • Your JAR
  • No shell, no package manager, no libc extras

Attack surface: Minimum possible. No shell to spawn, no package manager to install tools. Harder to debug — no exec into a shell.
Interview framing: In regulated environments (PCI-DSS, banking, betting), distroless is increasingly expected for production workloads. The tradeoff is debuggability — you cannot kubectl exec -it pod -- /bin/sh. The mitigation is ephemeral debug containers (kubectl debug) and shipping all diagnostics to Datadog/Splunk rather than doing ad-hoc shell work in prod.

Annotated Dockerfile

This is the canonical multi-stage Dockerfile for a Spring Boot service. Every line has a reason.

# ── Stage 1: Build ───────────────────────────────────────────────────────────
# Alpine variant: same JDK but stripped Alpine Linux base (~100MB smaller than Debian).
# AS build: names this stage so Stage 2 can reference it with --from=build.
FROM eclipse-temurin:21-jdk-alpine AS build

WORKDIR /workspace

# ── Layer caching trick: copy the dependency manifest FIRST ───────────────────
# Docker builds images as a stack of layers. A layer is only rebuilt when its
# inputs change. If pom.xml hasn't changed, the RUN below is a cache hit
# even when src/ changes. Without this ordering, a one-line src change would
# re-trigger mvn dependency:go-offline and re-download 200MB+ of JARs.
COPY pom.xml .

# Download all dependencies to the local Maven cache inside this layer.
# -B = batch mode (no progress bars in CI logs). This RUN is cached as long as
# pom.xml is unchanged — typical on 95% of commits (src changes only).
RUN mvn dependency:go-offline -B

# Copy source AFTER the dep-download layer. This way a change to src/
# only invalidates this COPY and the RUN below — NOT the dep download layer.
COPY src ./src

# Package the application. -DskipTests because unit tests run earlier in CI,
# not inside Docker. Running tests here would make the image non-deterministic
# (tests could pass or fail depending on env) and slow the build unnecessarily.
RUN mvn package -DskipTests -B

# ── Stage 2: Runtime ─────────────────────────────────────────────────────────
# Switch to JRE (not JDK). No compiler, no jshell, no jmap in production.
# Everything from Stage 1 (Maven cache, src, JDK tools) is left behind —
# it is NOT present in this final image. That is the whole point of multi-stage.
FROM eclipse-temurin:21-jre-alpine

# ── Non-root user ─────────────────────────────────────────────────────────────
# By default, containers run as root (UID 0). If an attacker exploits a
# vulnerability in the JVM or your app, they get root inside the container.
# In some misconfigured K8s clusters, container root = host root (no seccomp).
# Alpine uses addgroup/adduser (BusyBox), not useradd/groupadd (glibc/shadow).
# -S = system account (no login shell, no home dir by default).
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

WORKDIR /app

# ── Crossing the stage boundary ───────────────────────────────────────────────
# --from=build pulls files from Stage 1 into Stage 2. The glob *.jar matches
# the fat JAR produced by spring-boot-maven-plugin (e.g. myservice-1.0.0.jar).
# Only this JAR crosses — nothing else from /workspace is carried over.
COPY --from=build /workspace/target/*.jar app.jar

# EXPOSE is documentation, not a firewall rule. K8s NetworkPolicy and
# SecurityGroups control actual traffic. But it IS used by docker run -P
# to auto-assign host ports, and by K8s tooling that reads containerPort.
EXPOSE 8080

# Switch to non-root AFTER COPY (COPY as root is fine — file ownership can
# be set; USER only affects subsequent RUN/CMD/ENTRYPOINT).
USER appuser

# ── Exec form vs shell form ───────────────────────────────────────────────────
# Shell form:  CMD java -jar app.jar          → /bin/sh -c "java -jar app.jar"
# Exec form:   CMD ["java", "-jar", "app.jar"] → java is PID 1 directly
#
# K8s sends SIGTERM to PID 1 when a pod is terminated (rolling update, scale-down).
# Shell form: sh receives SIGTERM. sh does NOT forward it to java.
# Result: java keeps running for 30s until K8s sends SIGKILL → abrupt shutdown,
# in-flight HTTP requests dropped, connection pool not drained, DB transactions lost.
# Exec form: java IS PID 1, receives SIGTERM directly, Spring Boot's graceful
# shutdown hook fires, active requests drain before exit.
CMD ["java", "-jar", "app.jar"]
Spring Boot graceful shutdown: Set server.shutdown=graceful and spring.lifecycle.timeout-per-shutdown-phase=20s in application.properties. When the JVM receives SIGTERM (exec form), Spring Boot stops accepting new requests and waits up to 20 seconds for in-flight ones to complete. K8s terminationGracePeriodSeconds (default 30s) must be greater than this timeout. Together these give you zero-dropped-request rolling updates.

.dockerignore — what to exclude and why

The build context is the directory tree Docker sends to the daemon before executing the Dockerfile. Without .dockerignore, the entire project directory — including target/, .git/, and local .env files — is sent. This matters for three reasons: build context upload time, layer cache invalidation, and secret leakage.

# ── .dockerignore ─────────────────────────────────────────────────────────────

# Compiled output from local maven builds.
# If target/ is included, Docker sees stale JARs and the COPY pom.xml
# layer cache may compare file mtimes incorrectly → cache bust on every build.
# Also: target/ can be 200MB+ of downloaded JARs — no reason to send to daemon.
target/

# Git history. Adds tens of MB to context with zero benefit. Also: git objects
# contain every version of every file ever committed — potential secret exposure
# if a dev ever committed a key (even if subsequently removed from HEAD).
.git/
.gitignore

# Local environment files. These must NEVER enter the image.
# .env, .env.local, .env.production — all carry secrets (DB passwords, API keys).
# In production: inject via K8s Secrets → env vars, or AWS Secrets Manager.
.env
.env.*

# IDE metadata. Tens of MB of index files, caches, run configs.
# These change frequently → would bust Docker layer cache on every IDE save.
.idea/
*.iml
.vscode/

# Docker files themselves — no reason for the daemon to have them in context.
Dockerfile*
docker-compose*.yml

# Test and CI configuration — not needed at runtime, adds to context size.
*.md
*.sh
.gitlab-ci.yml
.github/

# macOS noise.
**/.DS_Store
Secret leakage via build context: Even if you never COPY .env app/ in your Dockerfile, if .env is not in .dockerignore, the file is still sent to the Docker daemon as part of the build context. The daemon stores it in a temporary directory. On a shared CI runner, another build or a compromised layer could read it. Always exclude secrets from build context — period.

What breaks without this

Pitfall 1: Using the latest tag

You push myservice:latest and Helm deploys it. Your K8s cluster has 3 nodes. Node 1 already has myservice:latest cached from two weeks ago (the old version). Node 2 and Node 3 have no cache. The pod scheduling pulls the image on Nodes 2 and 3 (new version), uses the cache on Node 1 (old version). With imagePullPolicy: IfNotPresent — the default — Kubernetes will NOT re-pull an image that exists locally under the same tag.

Result: 3 pods, 2 different versions, running simultaneously. User requests route to either version. You have no reliable way to tell which version a request hits. Symptoms look like random bugs. Rollback is impossible because you cannot reliably determine what version is running where.

Fix: Always tag with a content-addressed identifier — Git SHA (myservice:abc1234) or the image digest (myservice@sha256:...). Use imagePullPolicy: Always only if you genuinely need to force a pull, but the canonical answer is immutable tags.
Pitfall 2: Running as root inside the container

Without adduser + USER appuser, your JVM process runs as UID 0 (root). If an attacker exploits a Remote Code Execution (RCE) vulnerability in your app (for example, a deserialization gadget in a library), they get a root shell inside the container.

On clusters without securityContext.runAsNonRoot enforced by PodSecurityAdmission, and without strict seccomp profiles, container root can map to host root via namespace escape vulnerabilities. PCI-DSS and ISO 27001 audits will flag containers running as root as a critical finding.

Fix: addgroup -S appgroup && adduser -S appuser -G appgroup then USER appuser before CMD. Additionally set securityContext.runAsNonRoot: true and allowPrivilegeEscalation: false in the K8s Deployment spec.
Pitfall 3: No build cache layering — copying source before pom.xml

If your Dockerfile starts with COPY . . (copy everything at once), then RUN mvn package, then every commit to source code invalidates the COPY layer — which in turn invalidates the RUN mvn package layer — which re-downloads all Maven dependencies from the internet on every build.

A Spring Boot app with Spring Data, Spring Security, Kafka client, and Micrometer has ~150 transitive dependencies. Maven download is 200–500MB per build. On a shared CI runner with a slow NAT gateway, this is 3–5 minutes of pure network wait on every push.

Fix: COPY pom.xml . → RUN mvn dependency:go-offline -B → COPY src ./src → RUN mvn package -DskipTests -B. The dep download layer is cached as long as pom.xml is unchanged, which is true on 95%+ of commits.

Quiz

Q1. Your multi-stage Dockerfile copies the entire project before running mvn dependency:go-offline. A teammate changes one line in UserController.java and pushes. What happens on the CI build, and what is the correct fix?

  • Nothing unusual — Maven is smart enough to detect that pom.xml didn't change and skips the download.
  • The build fails because Docker detects that source changed after the dependency layer.
  • The build succeeds but the JAR is outdated because Docker uses the cached layer containing old source.
  • Docker invalidates the COPY . . layer (source changed), which cascades to invalidate the RUN mvn dependency:go-offline layer — all 200MB+ of Maven dependencies re-download from scratch. Fix: COPY pom.xml . then RUN mvn dependency:go-offline then COPY src ./src.
Layer cache cascade. Docker's cache key for a COPY instruction is the checksum of every file in the source set. Copying . (everything) means any changed file — including UserController.java — invalidates that layer. Every subsequent instruction is also invalidated. The correct fix is to copy only pom.xml first, run the dependency download as a separate layer, then copy source. The dependency layer's cache key is only pom.xml's checksum — unchanged on a pure source edit. In AWS CodeBuild, the same technique applies; CodeBuild also supports explicit S3 layer cache for cross-build persistence.

Q2. A Spring Boot service is deployed on EKS. During a rolling update, K8s terminates an old pod. Requests to that pod start returning connection resets immediately, even though active HTTP requests were in-flight. The Dockerfile uses shell-form CMD: CMD java -jar app.jar. What is the root cause and the fix?

  • The JVM takes too long to start — increase initialDelaySeconds on the liveness probe.
  • Shell form wraps the JVM in /bin/sh -c, making sh PID 1. K8s sends SIGTERM to PID 1 (sh), which does not forward it to the JVM child process. The JVM keeps running briefly but K8s stops routing traffic immediately. After terminationGracePeriodSeconds, SIGKILL fires and the JVM exits abruptly. Fix: exec form CMD ["java", "-jar", "app.jar"] so the JVM is PID 1 and receives SIGTERM directly, allowing Spring Boot's graceful shutdown hook to drain in-flight requests.
  • The pod is missing a preStop hook — add a sleep before termination.
  • The JVM ignores SIGTERM by default — add a JVM shutdown hook manually in main().
Exec form vs shell form SIGTERM forwarding. This is one of the most common K8s production bugs. Shell form (CMD java -jar app.jar) expands to /bin/sh -c "java -jar app.jar". The shell is PID 1; java is a child process. When K8s sends SIGTERM to PID 1, the shell exits immediately — it does not forward signals to children by default. The java process receives SIGTERM only indirectly (when the shell exits and the process group is cleaned up), but by then K8s has often stopped routing traffic. Exec form CMD ["java", "-jar", "app.jar"] makes java PID 1 directly. Combined with server.shutdown=graceful in Spring Boot, the JVM gracefully drains active connections on SIGTERM before exiting.

Q3. A team pushes myservice:latest after a critical hotfix. The EKS cluster has 3 nodes. Nodes B and C have never run this image. Node A has a cached image tagged myservice:latest from the previous week's deployment. imagePullPolicy is not explicitly set in the Deployment spec (so it defaults to IfNotPresent). What happens, and what is the correct tagging strategy?

  • K8s always pulls the latest digest when the tag is latest — no risk of stale images.
  • The cached image on Node A is automatically evicted when a new push to the same tag is detected.
  • All 3 pods will run the new version because Helm updates the Deployment spec, which triggers a rollout.
  • Nodes B and C pull the new image; Node A uses the cached (old) image — K8s does not check the registry if the tag already exists locally with IfNotPresent. Result: 3 pods, 2 different versions, running simultaneously with no visibility. Fix: tag with an immutable identifier (Git SHA: myservice:abc1234f) so the tag changes on every build. A new tag on the Deployment spec forces a pull on all nodes regardless of cache state.
Immutable image tags prevent silent version mixing. imagePullPolicy: IfNotPresent (the default when the tag is not latest) tells K8s: "if this tag exists locally, don't pull." When you reuse the latest tag, the tag is local on Node A but refers to a stale digest. K8s has no way to know the registry has a newer image under the same tag without pulling. Immutable tags solve this completely: a new Git SHA tag is always new to every node, so K8s always pulls. In GitLab CI: IMAGE_TAG=${CI_COMMIT_SHORT_SHA} → docker build -t myservice:${IMAGE_TAG} → pass IMAGE_TAG to Helm → Kubernetes spec changes → rollout happens. In AWS ECR: enable tag immutability to prevent overwriting an existing tag — any push attempt to an existing tag returns an error, enforcing the discipline at the registry level.

AI Engineering Extension

Where AI fits in the container story

Containers intersect AI engineering in two directions: AI workloads run inside containers (LLM inference services, embedding servers), and AI agents can operate on the container pipeline (reviewing Dockerfiles, generating release notes, flagging CVEs).

AI as workload — containerising an LLM inference service

An LLM inference service has different constraints from a Spring Boot app: the model weights are gigabytes, GPU memory limits are hard walls, and startup time is minutes, not seconds.

Key differences from a Java service:
  • Model weights NOT in the image — a 7B parameter model (fp16) is ~14GB. Baking it into the image means a 14GB push/pull on every code change, even if the weights are unchanged. Instead: weights live in S3, an init container downloads them to an EFS volume at pod start.
  • GPU base image — needs NVIDIA CUDA drivers. Use nvidia/cuda:12.2.0-cudnn8-runtime-ubuntu22.04. The CUDA version must match the host driver on the EKS node (GPU node group).
  • startupProbe, not livenessProbe for model load — model loading takes 60–120s. A liveness probe that fires too early will kill the pod before the model is loaded. startupProbe has its own failureThreshold * periodSeconds budget — set it to 180s total.
  • Memory limits are hard walls — unlike JVM heap which is configurable, GPU VRAM is a physical limit. OOM on the GPU kills inference silently. Set K8s resource limits: nvidia.com/gpu: 1 and test peak inference batch sizes before setting limits.
# ── Stage 1: Build Python dependencies ───────────────────────────────────────
FROM python:3.11-slim AS builder
WORKDIR /install
# venv ensures no system Python pollution; --no-cache-dir keeps layer small
RUN python -m venv /venv
COPY requirements.txt .
RUN /venv/bin/pip install --no-cache-dir -r requirements.txt

# ── Stage 2: CUDA runtime + inference service ────────────────────────────────
# cudnn8-runtime: includes cuDNN for transformer attention ops; not -devel
# (devel adds CUDA compiler — unnecessary in production, 2GB larger).
FROM nvidia/cuda:12.2.0-cudnn8-runtime-ubuntu22.04

RUN apt-get update && apt-get install -y python3 && rm -rf /var/lib/apt/lists/*

# Copy venv from builder — only Python packages, no build tools
COPY --from=builder /venv /venv
COPY inference_server.py .

# Model weights are NOT here. An init container (aws s3 cp) downloads them
# to a shared EFS volume (/models) mounted at pod start. The inference server
# reads /models/llama-3-8b/ at startup. This keeps the image at ~2GB, not 16GB.
ENV MODEL_PATH=/models/llama-3-8b

EXPOSE 8000

# Non-root even for GPU workloads — add user to 'video' group for GPU access
RUN groupadd -r inference && useradd -r -g inference -G video inferenceuser
USER inferenceuser

# Exec form for SIGTERM forwarding — same rule as Java services
CMD ["/venv/bin/python", "inference_server.py"]

The corresponding K8s Pod spec snippet:

# K8s Deployment — GPU inference pod config (abbreviated)
initContainers:
  - name: download-weights
    image: amazon/aws-cli:latest
    command: ["aws", "s3", "sync", "s3://my-models/llama-3-8b", "/models/llama-3-8b"]
    volumeMounts:
      - name: model-storage
        mountPath: /models

containers:
  - name: inference
    image: myrepo/inference:abc1234f
    resources:
      limits:
        nvidia.com/gpu: 1         # hard GPU reservation
        memory: "20Gi"           # VRAM + CPU RAM headroom
    startupProbe:                # budget: 30 checks × 6s = 180s for model load
      httpGet:
        path: /health
        port: 8000
      failureThreshold: 30
      periodSeconds: 6
    livenessProbe:               # only starts checking AFTER startupProbe passes
      httpGet:
        path: /health
        port: 8000
      periodSeconds: 30

AI as operator — agents in the Docker/CI pipeline

Claude in GitLab CI — Dockerfile review before build: Add a CI job that runs before docker build. The job sends the Dockerfile to Claude API with a prompt: "Review this Dockerfile for: running as root, shell-form CMD, missing .dockerignore, using mutable tags, and secrets baked in." Claude returns a structured list of findings. If severity is HIGH, the job fails and blocks the build. This catches the three pitfalls from this lesson automatically on every merge request.
AI-generated release notes after docker push: After a successful push to ECR, a GitLab CI job runs git log previous-tag..HEAD --oneline and sends the commit list to Claude with a prompt: "Summarise these commits as user-facing release notes for a fintech payment service. Flag any security fixes." The output is posted as a GitLab release note and a Slack message to #deployments. Zero manual authoring on every release.
Dockerfile linting agent on Merge Requests: An MR webhook fires a serverless function (Lambda) that pulls the changed Dockerfile from the GitLab API, runs hadolint (a static linter) and Claude analysis in parallel, merges findings, and posts inline comments on the MR diff via the GitLab API. The AI layer catches semantic issues (e.g. "this CMD won't forward SIGTERM") that hadolint's rule-based approach misses.
