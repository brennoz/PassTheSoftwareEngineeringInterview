Individual DevOps lessons treat each tool in isolation — a Dockerfile, a Helm chart, a Terraform module. Architecture questions test something different: can you trace one commit from a developer's laptop to a running pod, naming every tool that touches it and every failure mode at every handoff. This lesson is the connective tissue between the other eight clusters.

The end-to-end pipeline

Terraform state → S3 backend + DynamoDB lock table.
The one-sentence architecture answer: A commit becomes a running pod by moving through three separate control loops — GitLab CI (push-based, builds and publishes an artifact), ArgoCD (pull-based, reconciles cluster state to match a Git repo), and the Kubernetes controller (reconciles pod state to match the Deployment spec) — with Terraform as the substrate all three run on, and Datadog closing the loop with observability that feeds back into the next commit.

Push-based CI vs pull-based GitOps

The single most commonly missed architecture detail: GitLab CI does not deploy to Kubernetes. It builds an image and pushes a Git commit. ArgoCD is a separate control loop, running inside the cluster, that watches a Git repo and reconciles.

Push-based (CI runs kubectl/helm upgrade)
CI runner needs cluster-admin-adjacent credentials stored as a CI variable. Any compromised MR pipeline (e.g. a malicious dependency in a fork) has a path to prod credentials. No single source of truth — cluster state can drift from Git if someone runs kubectl edit by hand, and CI has no way to detect or reconcile that drift.
Pull-based GitOps (ArgoCD reconciles)
CI never holds cluster credentials — it only pushes to a Git repo. ArgoCD runs inside the cluster with a service account scoped to specific namespaces. ArgoCD continuously diffs live cluster state against Git and can auto-heal manual drift (kubectl edit gets reverted). Git history is the audit trail and the rollback mechanism — git revert triggers a real rollback.
Interview framing: "Why GitOps instead of CI running helm upgrade directly?" — answer with credential blast radius (CI never touches prod) and drift detection (Git is the single source of truth, not "whatever kubectl commands got run"). This is the most-asked question in this cluster.

Terraform underneath everything

Every tool above — GitLab runners, ECR, EKS, ArgoCD itself, the Datadog agent — runs on infrastructure that Terraform provisioned. Terraform is not part of the deploy pipeline; it is the substrate the pipeline runs on. It changes far less often (weekly/monthly) than application deploys (many times a day).

terraform/ ├─ modules/ │ ├─ vpc/ (subnets, NAT gateways, route tables) │ ├─ eks/ (cluster, node groups, IRSA roles) │ ├─ ecr/ (repo, immutability policy, lifecycle rules) │ └─ argocd-bootstrap/ (Helm release for ArgoCD itself — chicken/egg, │ solved by Terraform installing ArgoCD once, │ then ArgoCD manages everything AFTER that) ├─ envs/ │ ├─ staging/ (backend: s3://tfstate-staging, DynamoDB lock table) │ └─ prod/ (backend: s3://tfstate-prod, DynamoDB lock table — SEPARATE state) └─ backend.tf (remote state; local state = no team collaboration, no locking)
Why remote state + locking is non-negotiable at architecture scale: With local state, two engineers running terraform apply at the same time on the EKS module can corrupt state — one apply's plan is based on stale state, and the write clobbers the other's changes. The DynamoDB lock table makes the second apply block until the first completes. Losing state entirely means Terraform no longer knows what it manages — the practical fix is terraform import for every resource, which is a multi-day recovery, not a quick fix.

What breaks at each seam

Seam 1 — ArgoCD sync fails mid-rollout during a live sporting event

bet-settlement-service is mid-rollout (3 of 6 pods updated) when the new image crash-loops on a bad config value. ArgoCD's Progressing state means traffic is split across two versions right now, live, during an in-play match. Kubernetes readiness probes stop the crash-looping pods from receiving traffic, but 50% capacity is gone — settlement latency spikes, and if the SLO alert isn't wired to auto-page, this can run for minutes unnoticed.

Fix: ArgoCD syncPolicy.automated.selfHeal plus a progressDeadlineSeconds on the Deployment triggers automatic rollback if the new ReplicaSet never reaches Ready. For betting specifically: a canary step (Argo Rollouts, not plain Deployment) that shifts 10% traffic first and auto-aborts on error-rate threshold is the correct answer for anything liability-critical — never a big-bang rollout during live markets.
Seam 2 — GitLab CI has direct prod kubectl credentials (anti-pattern)

A CI variable holds a kubeconfig with cluster-admin. A dependency confusion attack or a malicious MR from a fork triggers a pipeline that exfiltrates the credential or runs kubectl delete directly. There is no GitOps audit trail for what happened — no Git commit corresponds to the change.

Fix: Push-based deploys should never hold cluster-wide credentials. GitOps (ArgoCD) is the correct boundary — CI's blast radius is capped at "can push a Git commit," which is reviewable and revertible.
Seam 3 — Terraform and Kubernetes both think they own the same resource

Someone adds an EKS node group change directly via eksctl or the console. The next terraform plan shows a diff and either reverts the manual change (destroying capacity mid-peak-traffic) or, worse, someone runs terraform apply without reading the plan output during an incident.

Fix: All infra changes go through Terraform, enforced by IAM policy (no console/CLI write access to EKS/VPC resources for humans, only through the Terraform CI role). terraform plan output is a required MR check before apply runs.

Quiz

Q1. A teammate proposes simplifying the pipeline: have the GitLab CI job run helm upgrade --install directly against the EKS cluster after docker push, removing ArgoCD entirely. What is the strongest architectural objection?

  • Helm is deprecated in favour of Kustomize, so this would not work regardless.
  • GitLab CI cannot authenticate to ECR and EKS in the same pipeline job.
  • CI would need long-lived, broad cluster credentials stored as a pipeline variable — expanding the blast radius of a compromised pipeline to full cluster access — and cluster state could drift from Git with no reconciliation loop to detect or heal it.
  • Helm charts cannot be templated inside a GitLab CI job, only inside ArgoCD.
Push vs pull deploy models. The core tradeoff is credential blast radius and drift detection. A push-based CI job needs credentials capable of deploying to prod, which means any pipeline compromise (malicious MR, compromised dependency, leaked CI variable) is a direct path to the cluster. GitOps controllers like ArgoCD run inside the cluster with scoped service accounts, continuously reconcile live state against Git, and can auto-heal drift from manual changes. CI's job is capped at "push a reviewable Git commit" — a much smaller blast radius.

Q2. During a live football match, ArgoCD begins rolling out a new version of bet-settlement-service. The new pods crash-loop due to a bad ConfigMap value. Readiness probes correctly keep the broken pods out of the Service endpoints, but the Deployment is stuck at 50% capacity for several minutes before anyone notices. What two changes prevent this from being a silent capacity loss during a liability-critical window?

  • progressDeadlineSeconds on the Deployment to trigger automatic rollback when the new ReplicaSet never reaches Ready, plus a canary rollout strategy (e.g. Argo Rollouts) that shifts a small percentage of traffic first and aborts automatically on an error-rate threshold — instead of a big-bang rollout to all replicas at once.
  • Increase replicas on the Deployment so there is always spare capacity regardless of rollout state.
  • Switch from readiness probes to liveness probes, since liveness probes trigger faster.
  • Disable rolling updates entirely and only deploy during scheduled maintenance windows.
Progressive delivery for liability-critical services. Readiness probes correctly stop bad traffic from reaching broken pods, but they don't stop the rollout itself from stalling silently. progressDeadlineSeconds makes a stuck rollout an explicit failure condition that can auto-rollback. Canary rollouts (Argo Rollouts, not a plain Kubernetes Deployment) cap the blast radius to a small percentage of traffic and abort automatically on metric thresholds — the correct pattern any time a deploy touches a service where downtime has direct financial/liability consequences, like in-play bet settlement. "No deploys during live matches" is not realistic for a 24/7 sports calendar, so the mitigation has to be in the rollout mechanics, not a freeze window.

Q3. Two engineers run terraform apply on the eks module within seconds of each other, from different laptops, against the same remote state. What prevents state corruption, and what would happen if that mechanism were missing?

  • Terraform automatically merges concurrent plans, similar to a Git merge — no special mechanism is required.
  • The DynamoDB lock table backing the S3 remote state acquires a lock for the first apply; the second blocks until it completes. Without it, both applies could read the same stale state, and the second apply's write can silently clobber the first's changes — producing a state file that no longer matches real infrastructure.
  • S3 versioning alone prevents corruption by keeping every previous state file.
  • Terraform Cloud is required for any locking to occur — the open-source CLI has no locking capability.
State locking is what makes concurrent Terraform usage safe. The S3 backend stores the state file itself; the paired DynamoDB table implements a distributed lock via conditional writes (the same primitive as an idempotency key). Without locking, two applies can both read state version N, compute independent plans, and the second write overwrites the first — the state file drifts from reality (e.g. a node group the first apply created is now "unknown" to Terraform). Recovery from silent state corruption is often a multi-day terraform import exercise per resource, far more costly than the lock table's cost.

Agentic AI Angle

AI as workload

If bet-settlement-service itself started calling an LLM — say, an AI-assisted fraud check on high-value settlements — the pipeline above needs new boxes: a GPU node pool provisioned by a new Terraform module, a token-rate limiting sidecar in the pod spec so a runaway loop cannot blow the LLM API budget, and a model_version label pinned in the Helm values (treated exactly like a dependency version — bumping it is a deploy, not a config tweak, and needs the same canary rollout as the code itself). Datadog gets a new metric class: cost-per-call and token throughput, not just latency and error rate.

AI as operator

Claude as automated MR reviewer in GitLab CI: A CI job (running before docker build) sends the diff to the Claude API with a prompt scoped to this course's known trigger list — hardcoded secrets, missing idempotency keys, double for money, mutable ledger rows. Findings above a severity threshold fail the pipeline, catching the exact categories this course's code-review rubric scores on, before a human reviewer even looks at the MR.
AI-triaged incident response: When the Datadog Monitor from this lesson's pipeline fires, instead of paging a human first, a Lambda function sends the trace, recent deploy history (from the GitOps repo's commit log), and the alert payload to Claude with a prompt: "Given this SLO breach and the last 3 deploys, what's the most likely cause and is auto-rollback appropriate?" High-confidence "yes, roll back" verdicts trigger argocd app rollback automatically; low-confidence verdicts page the on-call engineer with the AI's analysis attached as context, cutting mean-time-to-diagnosis.

Key differences from a standard service

  • GPU requirements — a new node group, new Terraform module, new node affinity rules in the pod spec; a standard Spring Boot service never needs this.
  • Non-deterministic output — CI tests can assert exact JSON for a settlement calculation; they cannot assert exact LLM output, only shape/schema and latency/cost bounds.
  • Model version = dependency — pin it in Helm values like a library version; an unpinned model can change behaviour silently on the provider's side with zero code change on yours.
  • Token cost = a runtime metric — belongs in the same Datadog dashboard as latency and error rate, not treated as a separate finance-only concern.
