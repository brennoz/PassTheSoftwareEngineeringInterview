Math for Developers

Powers of 2 · Logarithms · Modular arithmetic · Bit tricks · Float precision · Estimation · Percentiles
Why this matters You don't need a maths degree. You need seven patterns that appear constantly in system design, algorithm analysis, and production debugging — and a fast intuition for when each one is in play.

1. Powers of 2 — the developer's times table

Every capacity decision in software maps to a power of 2. Memorise this table cold.

TRICK: multiply by 2 = shift left by 1 bit

Every time you multiply by 2 you add 1 to the exponent. 210 = 1 KB → 220 = 1 MB → 230 = 1 GB. Each step is exactly ×1024 (≈×1000). Chain three steps: 1 byte × 1000 × 1000 × 1000 ≈ 1 GB.

Practical use: capacity estimation

A user profile record is 1 KB. 1 million users = 1 KB × 106 = 1 GB. 1 billion users = 1 TB. Instant, no calculator.

2. Logarithms — the key to understanding Big-O

log2(n) answers: "how many times do I have to halve n before I reach 1?" This is exactly what binary search and balanced trees do.

nlog2(n)Real meaning
10Already there
833 halvings: 8→4→2→1
1,0241010 comparisons to find one item in 1,024
1,000,000~20Binary search through 1M records = 20 comparisons
1,000,000,000~30Binary search through 1B records = 30 comparisons
The O(log n) intuition If doubling the input only adds ONE more step, the algorithm is O(log n). B-tree index lookup, binary search, balanced BST operations — all grow by 1 step per doubling. A billion-row table with a B-tree index requires ~30 comparisons. Without the index (O(n)): 1 billion comparisons.
TRICK: log₂(n) ≈ log₁₀(n) × 3.32

If you know the number of digits (log₁₀), multiply by ~3.3 to get log₂. 1 million has 6 digits → log₂(1M) ≈ 6 × 3.32 ≈ 20. ✓

3. Modular arithmetic — clocks, hashing, and ring buffers

a mod m is the remainder after dividing a by m. The answer is always in [0, m-1]. Intuition: a clock is mod 12.

Where it appears

  • Hash maps: bucket = hash(key) % numBuckets — maps any hash to a valid bucket index.
  • Consistent hashing: ring of 232 positions, node placed at hash(node) % 2^32.
  • Ring buffers: nextIndex = (currentIndex + 1) % capacity — wraps around without an if-statement.
  • Rate limiting (fixed window): window = timestamp / windowSize — divides time into slots.
TRICK: power of 2 modulo via bitwise AND
// x % 8  is expensive (division)
// x & 7  is free   (bitmask) — works when m is a power of 2
// General rule: x % 2^k  ==  x & (2^k - 1)
int bucket = hash & (numBuckets - 1);  // numBuckets must be a power of 2

This is why HashMap, ring buffers, and many caches require capacity to be a power of 2.

4. Bit manipulation tricks

Interviewers test these because they reveal whether you understand how computers actually represent numbers.

GoalCodeWhy it works
Check if n is even(n & 1) == 0Last bit is 0 for all even numbers

Set bit kn | (1 << k)OR with a mask that has only bit k set

Divide by 2k (integer)n >> kRight shift = floor divide by 2 per shift

Power-of-2 check in interviews (n & (n-1)) == 0 is a common interview question for "check if capacity is valid." Appears in HashMap resizing, allocator alignment, ring buffer implementation. Understand it — don't just memorise it: if n = 8 (1000₂), then n-1 = 7 (0111₂), AND = 0000₂. Any number with two or more bits set will leave a non-zero result.

5. Floating-point precision — why double breaks money

Computers store real numbers in IEEE 754 binary format. The mantissa is finite (52 bits for double), so most decimal fractions cannot be represented exactly.

// In Java / most languages:
System.out.println(0.1 + 0.2);        // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3); // false

// The actual stored value of 0.1 in binary is:
// 0.1000000000000000055511151231257827021181583404541015625

Why this matters in production

  • Money: £0.10 × 1,000,000 transactions. Double error accumulates → statement doesn't reconcile → regulatory issue.
  • Betting odds: payout = stake × odds. £10.00 × 3.25 with double arithmetic may yield £32.49999999... not £32.50.
  • Tax calculation: rounding errors in VAT or interest calculation cause audit failures.
FIX: use BigDecimal for anything financial
// Never:
double payout = stake * odds;

// Always:
BigDecimal payout = stake.multiply(odds);  // exact decimal arithmetic

// When constructing: use String constructor, not double
new BigDecimal("0.10")   // exact: 0.10
new BigDecimal(0.10)     // WRONG: captures the IEEE 754 approximation
Comparison gotcha BigDecimal.equals() is scale-sensitive: new BigDecimal("100.0") ≠ new BigDecimal("100.00"). Always use compareTo(): a.compareTo(b) == 0.

6. Back-of-envelope estimation

System design interviews require order-of-magnitude estimates. The goal is not precision — it's ruling out designs that don't fit the numbers.

Traffic estimates — useful constants

1 year~31.5 million ≈ 3×107
ESTIMATION TEMPLATE
1. Active users:           e.g. 100M daily active users
2. Requests per user/day:  e.g. 10 actions/day
3. Total requests/day:     100M × 10 = 1B/day
4. Requests/second:        1B / 86,400 ≈ 1B / 10^5 = 10,000 RPS
5. Storage per request:    e.g. 1 KB per event
6. Storage/day:            1B × 1 KB = 1 TB/day
Always state assumptions out loud. The interviewer is evaluating your reasoning, not the number.

7. Percentiles — reading p50 / p99 / p999

Mean latency lies. If 1% of requests take 10 seconds and 99% take 1ms, the mean is ~100ms — but users experience either 1ms or 10s, never 100ms. Percentiles tell the truth.

What they mean

  • p50 (median): 50% of requests completed in this time or less. The "typical" experience.
  • p95: 95% of requests. Catches the slower tail while ignoring outliers.
  • p99: 1 in 100 requests is at least this slow. The "almost worst case."
  • p999: 1 in 1,000. Matters when you process millions of requests/minute — thousands of users hit this every minute.
SLO definition pattern "p99 latency < 200ms over a 5-minute window." This means: in any 5-minute window, at most 1% of requests may exceed 200ms. Datadog, Prometheus, and every APM tool measure this. When defining an SLA with a payment partner, p99 is the standard contract metric — not mean.
CALCULATION: percentile from a sorted list
// Given N latency samples, sorted ascending:
p99 = sample at index ceil(0.99 × N)

// Practical example: 100 requests, sorted by response time
// p99 = the 99th value (the second-worst)
// p50 = the 50th value (the median)
In production: use histograms (Prometheus histogram_quantile) or pre-sorted structures (HdrHistogram), not sorted arrays — sorting 1M values per second is not feasible.

Quiz

Q1: A binary search through 1 billion records requires approximately how many comparisons?

  • About 1,000 comparisons — proportional to the cube root
  • About 1,000,000 comparisons — proportional to the square root
  • About 100 comparisons — based on log base 10
  • About 30 comparisons — log₂(1,000,000,000) ≈ 30
D is correct. log₂(10⁹) = log₂(2³⁰) ≈ 30. Each comparison halves the search space. 2³⁰ ≈ 1 billion, so 30 halvings reach 1 element. This is why B-tree indexes make billion-row tables fast — the depth is about 30 levels.

Q2: Why does new BigDecimal(0.1) not store the value 0.1 exactly?

  • BigDecimal has a precision limit of 15 significant digits by default
  • The double literal 0.1 is already an IEEE 754 approximation before BigDecimal sees it
  • Java's compiler rounds decimal literals to the nearest representable float
  • BigDecimal uses base-16 internally and 0.1 is not representable in hex
B is correct. The double value 0.1 is actually stored as 0.1000000000000000055511… before it is passed to the BigDecimal constructor. BigDecimal faithfully wraps that approximation. Use new BigDecimal("0.1") (String constructor) to get exact decimal 0.1.

Q3: Your service processes 100 million requests per day. What is the approximate requests-per-second rate?

  • Approximately 1,000–1,200 RPS
  • Approximately 100,000 RPS — dividing by minutes, not seconds
  • Approximately 100 RPS — 100M per day / 1M seconds per day
  • Approximately 10,000,000 RPS — dividing by 10 seconds
A is correct. 100M ÷ 86,400 ≈ 100M ÷ 10⁵ = 1,000 RPS. The approximation 86,400 ≈ 10⁵ is the key trick. This is a common system design interview calculation — memorise that 1 day ≈ 100,000 seconds.

Q4: (n & (n-1)) == 0 checks whether n is a power of 2. Why does this work?

  • Powers of 2 are always divisible by n-1 due to Fermat's little theorem
  • The AND operation extracts only the sign bit, which is 0 for powers of 2
  • n-1 is always odd when n is a power of 2, and AND with an odd number is 0
  • Powers of 2 have exactly one bit set; subtracting 1 flips that bit and all lower bits to zero, making AND equal zero
D is correct. n = 8 is 1000₂. n-1 = 7 is 0111₂. 1000 AND 0111 = 0000. Any number with two bits set (e.g. 12 = 1100₂) will have n-1 = 11 = 1011₂, and 1100 AND 1011 = 1000 ≠ 0. Also always check n > 0 — zero would satisfy the bit test but is not a power of 2.

Q5: A Datadog SLO says "p99 latency < 200ms." Your service handles 1 million requests per minute. In the worst compliant minute, how many requests may exceed 200ms?

  • 200 requests — p99 means 99.8% must be under the threshold
  • 100 requests — p99 means exactly 1 request per 100 may exceed it
  • 10,000 requests — p99 means 1% of 1 million may exceed the threshold
  • 1,000 requests — p99 is measured per thousand requests only
C is correct. p99 = 99th percentile means at most 1% of requests may exceed the threshold. 1% of 1,000,000 = 10,000 requests. At high volume this is still a lot of slow requests — which is why p999 matters too: at 1M RPS, p999 = 1,000 slow requests per minute.
