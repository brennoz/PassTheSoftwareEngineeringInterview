1 — What is Event Sourcing?

Event Sourcing — Core Idea

Frame 1 / 8

❌ Traditional CRUD

Store current state only. Past is gone.

order_idstatusqty
O-1PARTIAL500

How did we get here? Unknown.
Rollback? Impossible.

→

✅ Event Sourcing

Store every event. State = replay.

seqevent
1OrderPlaced(qty=1000)
2OrderFilled(qty=500)

State = apply events in order.
Full audit trail. Replayable.

Core axiom: currentState = fold(initialState, events) — the aggregate applies each event, left to right, to produce the present.
Key property: The event store is append-only — events are immutable facts. You never UPDATE or DELETE an event.

Optimistic Concurrency

Append at seq=N only if current max is N-1.
Conflict = another writer snuck in → retry.

INSERT WHERE seq = expected
Partitioned by Aggregate

Each aggregate (order-O1, account-A9) has its own stream. Parallel writes never contend with each other.

Why no UPDATE?

Immutability = no row-level locks on existing rows. Append = sequential write = cache-friendly = faster.

4 — Why Fast? The Low-Latency Argument

Why Event Sourcing is Fast — The Low-Latency Argument

Frame 4 / 8

Traditional UPDATE — slow path
  1. Acquire row-level lock on order row
  2. Read current state (SELECT … FOR UPDATE)
  3. Validate business rules in app
  4. Write updated row (UPDATE + redo log)
  5. Wait for fsync / WAL flush
  6. Release lock — other writers unblocked
Lock contention grows with throughput. At 10k orders/sec on same account → lock queue → latency spike.
Event APPEND — fast path
  1. Load aggregate from cache (or replay last N events)
  2. Validate business rules in-memory
  3. INSERT one row at next seq — no lock on existing rows
  4. WAL flush (async or group commit)
  5. Publish event to bus — done, return to caller
No contention on existing rows. Parallel aggregates never block each other. Throughput scales linearly with partitions.
Sequential I/O

Append = sequential disk write. Sequential writes are 10–100× faster than random UPDATE seeks on spinning disks, and cache-friendly on SSDs too.

In-Memory Aggregate

Hot aggregate stays in memory (last snapshot + delta events). Business logic runs at memory speed — no DB roundtrip for validation.

Async Projections

Write path doesn't wait for read models to update. Projection lag = milliseconds. Write latency = just the APPEND.

No thread blocks. flatMap suspends and releases the thread while waiting for I/O. At 10k concurrent orders, you need ~10 threads — not 10k.
CompletableFuture version (Java 8+)
CompletableFuture
  .supplyAsync(() -> repo.load(orderId))   // async load
  .thenApply(agg -> agg.place(cmd))        // pure — no I/O
  .thenCompose(events -> store.append(events)) // async write
  .thenAccept(bus::publish)                // fire & forget
Why thenApply not thenCompose on the aggregate?

thenApply: sync transform — returns T. Use when the step is pure (no I/O).
thenCompose: async transform — returns CompletableFuture<T>. Use when the step does I/O.
Mistake: wrapping a pure function in thenCompose → nested CompletableFuture<CompletableFuture<T>>.

OMS Example — Order Lifecycle in an Event-Sourced Aggregate

Frame 6 / 8 — Trading domain

Java Aggregate Skeleton
public class Order {
  private OrderStatus status;
  private int filledQty;

  // Command handler — produces events
  public List<DomainEvent> place(PlaceOrderCmd cmd) {
    if (status != null) throw new InvalidStateException();
    return List.of(new OrderPlaced(cmd.symbol(), cmd.qty()));
  }

  // Event applier — pure, no I/O
  public void apply(OrderPlaced e) {
    this.status = PENDING;
  }
  public void apply(OrderFilled e) {
    this.filledQty += e.qty();
    this.status = filledQty == totalQty ? COMPLETE : PARTIAL;
  }
}
Pattern: Command handler decides (can throw) → returns events. Apply method only mutates state — never throws, never does I/O. This split is what makes the aggregate testable and replayable.

7 — Snapshots: Solving Replay Cost

Snapshots — Solving the Replay Cost Problem

Frame 7 / 8

Problem: An order with 10,000 partial fills needs to replay 10,000 events every time it's loaded. At microsecond-latency targets, that's unacceptable.
Snapshot Strategy

Periodically serialize the aggregate's current state as a snapshot at sequence N.

On next load: load snapshot(N) + replay events from N+1 onward

streamseqtype
order-O10–999... events ...
order-O11000⚡ SNAPSHOT
order-O11001OrderFilled
order-O11002OrderFilled

Replay cost: 2 events, not 1002.

In-Memory Cache (hot aggregates)

For trading OMS: active orders stay in memory. No DB roundtrip at all for validation step.

  • Load on first command → cache in JVM heap
  • Each new event updates the cached aggregate in-place
  • Evict on order terminal state (COMPLETE / CANCELLED)
Caveat: Requires sticky routing (same node handles same order) OR distributed cache (Redis). Multi-pod without routing = stale cache.
Combined strategy: Hot aggregate in-memory (zero replay cost) + snapshot every N events (cold load fallback) + async projection lag accepted for reads. Write latency = memory + one APPEND.

8 — Trade-offs & When NOT to Use

Trade-offs — When to Use, When to Avoid

Frame 8 / 8

✅ Use Event Sourcing when
  • Audit trail is mandatory — financial, legal, regulatory (OMS, banking, betting)
  • Temporal queries — "what was the state at 09:32:14?" — replay to that point
  • High write throughput — append beats update at scale
  • Event-driven architecture — events are already the integration contract
  • Complex business rules — state machine with many transitions (order lifecycle)
  • Debugging & replay — reproduce any prod incident exactly from the event log
❌ Avoid Event Sourcing when
  • Simple CRUD — a user profile with 3 fields has no event complexity worth storing
  • Strong read consistency required — projections lag; if you can't tolerate 50ms stale reads, ES + CQRS is a bad fit without synchronous projections (costly)
  • Ad-hoc queries — "show me all orders where qty > 500 AND status = PARTIAL" needs a projection for every query shape — complex to maintain
  • Schema evolution is hard — once an event is in the store, changing its shape breaks replays unless you version events carefully
  • Small team, early stage — the operational complexity (snapshots, projections, schema versioning) has real cost
Interview-ready summary (say this out loud)

"Event sourcing replaces mutable state with an immutable, append-only event log. State is derived by replaying events. Paired with CQRS, the write path is a single INSERT — no row locks, no contention — giving low, predictable write latency. Read models are built asynchronously from projections, so query complexity is decoupled from write performance. The cost is eventual consistency on reads, operational overhead for snapshots and schema evolution, and sticky-routing or distributed cache requirements for hot aggregates in multi-pod deployments."
