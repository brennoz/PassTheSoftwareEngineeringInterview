Key problem: Every thread serialises through the lock. Work that takes 2ms per thread takes 6ms total for 3 threads. At 10 threads: 20ms. At 100 threads: 200ms. Latency grows linearly with concurrency.

UPDATE worst case = N × 2ms (last thread in queue waited for all N-1 before it). INSERT = always 2ms.

UPDATE: unpredictable tail latency

At 1 writer: fast. At 100 writers: 100× slower. The same code, the same DB, but traffic doubled → latency doubled. This is why it's called a scalability cliff.

In trading: a burst of 50 fills arrives in 1ms. P99 latency = 100ms. SLA breached. Ops paged. Customer sees stale position.

INSERT: flat latency curve

At 1 writer: 2ms. At 1000 writers: still 2ms. The curve is flat. This is "predictable" latency — your SLA holds regardless of burst size.

In trading: 50 fills burst in 1ms. All 50 append their event row in parallel. P99 = 2ms. SLA holds.

4 — The one real caveat

The One Real Caveat

Frame 4 / 4 — why it's not completely free

"No contention between different aggregates" is fully true. But same aggregate, same stream still has one coordination point: the sequence number.
Optimistic concurrency — the INSERT constraint
-- Thread A and Thread B both read current seq = 5
-- Both try to INSERT at seq = 6

Thread A: INSERT INTO events (stream_id, seq, ...) VALUES ('order-O1', 6, ...)
Thread B: INSERT INTO events (stream_id, seq, ...) VALUES ('order-O1', 6, ...)

-- DB has UNIQUE(stream_id, seq) constraint
-- One wins. One gets a unique-constraint violation → retry at seq = 7.
This is optimistic concurrency, not pessimistic locking. No thread blocks. The loser retries immediately — typically <1ms. Compare to pessimistic: loser waits for the winner to release, which may take 2ms, 50ms, or forever if the winner crashes.
Pessimistic lock (UPDATE)
  • Loser blocks — OS thread sleeps, context switch
  • Thread pool exhausts under load
  • Winner crash = loser waits forever (timeout needed)
  • Deadlock possible with multiple locks
Optimistic concurrency (INSERT)
  • Loser gets exception → retries immediately, no sleep
  • No thread blocked = thread pool stays healthy
  • Winner crash = no impact on others, they just retry
  • Deadlock impossible — no locks held
Summary in one sentence: UPDATE serialises writers through a lock queue → latency = N × work. INSERT lets writers race and retry on conflict → latency ≈ work + tiny retry overhead, regardless of N.
