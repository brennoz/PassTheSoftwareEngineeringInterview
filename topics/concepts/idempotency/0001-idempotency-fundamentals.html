Idempotency Fundamentals

Distributed systems, APIs, databases, AWS — the one guarantee that makes retries safe.

Related: System Design — Idempotent Payment API

1. The Definition

An operation is idempotent if applying it one time produces the same outcome as applying it any number of times.

f(f(x)) = f(x) Setting a light switch to ON is idempotent: doing it twice leaves the light on, exactly as doing it once. Toggling a switch is not idempotent: two toggles = net no change.

In software, this means: a client can safely retry a request without risking duplicate side effects. Every distributed system eventually needs retries — networks drop packets, timeouts fire, load balancers restart. Idempotency is what makes retries safe.

2. HTTP Methods — Which Are Idempotent?

MethodIdempotent?Safe?Why
GET✅ Yes✅ Yes Read-only. Same request returns same resource (until the resource changes).
HEAD✅ Yes✅ Yes Same as GET, no response body.
PUT✅ Yes❌ No Full replacement. PUT twice = same final state as PUT once.
DELETE✅ Yes❌ No Deleting an already-deleted resource → 404 or 204, but server state unchanged.
POST❌ No❌ No Creates a new resource each call. Retry = duplicate order, duplicate payment.
PATCH❌ Usually not❌ No Partial update. PATCH /balance {delta: -100} applied twice debits twice.
Interview trap: PATCH PATCH can be made idempotent if the payload is absolute ({"status": "CANCELLED"}) rather than relative ({"delta": -100}). The spec does not require it — the server author decides.

3. Why Networks Force This Conversation

In a distributed system, at-least-once delivery is the default — not exactly-once. When a client POSTs a payment and the TCP connection drops before the response arrives, the client does not know whether the server processed the request:

Client Network Server │ │ │ │──── POST /payments ───────▶ │ │ │ │ ← response lost → │ ← payment created ✅ │ │ │ │ timeout fires │ │ │──── POST /payments ───────▶ │ │ │ ← DUPLICATE payment ❌

The fix: the client includes an idempotency key in both requests. The server deduplicates using the key.

4. The Idempotency Key Pattern

Request shape

POST /payments
Idempotency-Key: 7f3a9b21-4c2e-4d1a-8e6f-1234abcd5678
Content-Type: application/json

{ "amount": 100, "currency": "GBP", "toAccount": "ACC-42" }

Server-side algorithm

Receive request with key K │ ├─ SELECT * FROM idempotency_records WHERE key = K │ │ │ ├─ FOUND and status = COMPLETED │ │ └─ Return cached response immediately (no re-processing) │ │ │ ├─ FOUND and status = IN_PROGRESS │ │ └─ Return 409 Conflict or wait/retry (concurrent duplicate) │ │ │ └─ NOT FOUND │ ├─ INSERT INTO idempotency_records (key, status=IN_PROGRESS) │ │ [UNIQUE constraint prevents race — second insert fails] │ ├─ Process the business operation │ ├─ UPDATE idempotency_records SET status=COMPLETED, response=... │ └─ Return response to client

Java skeleton

@Transactional
public PaymentResponse placePayment(String idempotencyKey, PlacePaymentRequest req) {
    // Step 1: check cache — returns immediately if already processed
    return idempotencyStore.find(idempotencyKey)
        .map(record -> record.getCachedResponse(PaymentResponse.class))
        .orElseGet(() -> {
            // Step 2: reserve the key — UNIQUE constraint prevents concurrent duplicates
            idempotencyStore.reserve(idempotencyKey);
            // Step 3: process
            PaymentResponse resp = paymentDomainService.execute(req);
            // Step 4: commit result alongside business data
            idempotencyStore.complete(idempotencyKey, resp);
            return resp;
        });
}
Why one transaction? Steps 2–4 run inside a single DB transaction. If the process crashes after inserting the payment but before marking the key COMPLETED, the whole transaction rolls back — the retry will find key NOT_FOUND and try again cleanly. Never commit the business record and the idempotency record in separate transactions.

5. Database-Level Idempotency

Three tools, from simplest to most powerful:

5a. UNIQUE constraint

-- Natural idempotency: duplicate INSERT → constraint violation, not duplicate row
CREATE TABLE bets (
    idempotency_key UUID PRIMARY KEY,
    bet_slip_id     UUID NOT NULL,
    amount          NUMERIC(10,2) NOT NULL
);

The DB itself rejects a second INSERT with the same key. No application logic needed.

5b. INSERT … ON CONFLICT DO NOTHING (PostgreSQL)

INSERT INTO payments (idempotency_key, amount, status)
VALUES (:key, :amount, 'PENDING')
ON CONFLICT (idempotency_key) DO NOTHING;

Silent deduplication — returns 0 rows affected on duplicate, no exception thrown.

5c. Optimistic locking with @Version

@Entity
public class Wallet {
    @Version
    private long version;   // JPA auto-increments; stale read → OptimisticLockException

    public void debit(BigDecimal amount) {
        if (balance.compareTo(amount) < 0) throw new InsufficientFundsException();
        this.balance = balance.subtract(amount);
    }
}

Not strictly idempotency — protects against concurrent writes to the same row (e.g. two simultaneous debit operations on the same wallet). If both threads read version=5, only the first commit succeeds; the second throws OptimisticLockException and retries at version=6.

6. Idempotency in Messaging (Kafka / RabbitMQ)

LayerProblemSolution
Producer Broker acks lost → producer retries → duplicate message in topic Kafka idempotent producer (enable.idempotence=true) — broker deduplicates within a session using sequence numbers
Consumer Consumer crashes after processing but before committing offset → message redelivered Consumer tracks processed message IDs in Redis/DB — skip if seen before (consumer-side deduplication)
Exactly-once Need both: no duplicates at producer AND consumer Kafka Transactions: producer + consumer in same transactional boundary; reads-process-writes atomically
Exactly-once is expensive. Kafka transactions add latency (~10–50 ms per batch). Most systems accept at-least-once with idempotent consumers rather than paying the transaction overhead.

7. Common Pitfalls

Pitfall 1: Idempotency key scope too wide Using the same key for different operations (e.g. same UUID reused by a buggy client for two different payments). The server returns the cached result of the first — wrong money moves. Fix: key is scoped per operation type + client + request content.
Pitfall 2: Request body changes on retry Client retries with same key but different amount. Server should hash the original request body, store it with the key, and return 422 Unprocessable Entity if the hash mismatches on retry.
Pitfall 3: No TTL on idempotency records Records accumulate forever → unbounded table growth. Set TTL (e.g. 24 hours for payments; 7 days for long-running sagas). After TTL, client must treat the request as new.
Pitfall 4: Idempotency key in application memory only Single-instance works. On a 4-pod ECS cluster, pod A deduplicates correctly, but pod B has never seen the key → processes duplicate. Fix: store keys in shared PostgreSQL or Redis.

Redis SET NX — the Swiss army knife

Boolean isNew = redisTemplate.opsForValue()

9. Decision Tree: Which Pattern to Use?

Is the operation naturally idempotent? (e.g. PUT full-replace, DELETE, SET) │ ├─ YES → No extra work needed. Document it. │ └─ NO (POST, PATCH with delta, multi-step saga) │ ├─ Single DB, single service? │ └─ UNIQUE constraint on idempotency_key column │ + INSERT ON CONFLICT DO NOTHING │ ├─ Multi-service / distributed? │ └─ Client-generated UUID in header │ + shared Redis SET NX (fast, TTL-based) │ + DB idempotency table as durable fallback │ └─ Event-driven / Kafka consumer? └─ Consumer deduplication table (message_id UNIQUE) or Redis SET NX per event

Quiz

Q1. A client POSTs a payment with Idempotency-Key: abc123. The server processes the payment successfully but crashes before sending the response. The client retries with the same key. What should the server return?

  • A 500 error — the server state is unknown
  • The cached response from the first (completed) request
  • A new payment — the first one may not have committed
  • A 409 Conflict — the key is already in use
The server completed the first request and stored the result alongside the idempotency record in one transaction. On retry it finds the key with status COMPLETED and returns the cached response. No new payment is created.

Q2. Which HTTP method is NOT idempotent by default?

  • DELETE
  • PUT
  • POST
  • GET
POST creates a new resource on each call. DELETE, PUT, and GET are idempotent: repeating them leaves server state the same as one application.

Q3. Your payment service runs on 4 ECS pods. An engineer stores idempotency keys in a local ConcurrentHashMap on each pod. What is the production failure mode?

  • A retry routed to a different pod finds no key and processes the payment again
  • The ConcurrentHashMap is not thread-safe across pods
  • The map fills up after high traffic and throws OutOfMemoryError
  • No failure — HTTP load balancers use sticky sessions by default
Each pod has its own map. A retry load-balanced to a different pod finds no record of the first request and creates a duplicate payment. Fix: use a shared Redis or database key store.

Q4. You store idempotency keys forever to guarantee deduplication. What is the primary operational risk?

  • Key collisions become more likely as the table grows
  • SELECT on idempotency_key becomes a full table scan over time
  • Old keys interfere with new requests that reuse the same UUID
  • Unbounded table growth leads to storage cost and query degradation
Without TTL, the table grows indefinitely. Add a TTL column and a periodic cleanup job (or use Redis with built-in expiry). UUID reuse is astronomically unlikely but TTL also guards against it.
