React + Redux — Overview

BillingCo prep  ·  Lesson 1 of ?  ·  ~20 min

You've already built the BillingCo backend: Invoice entity, state machine, REST endpoints (q128). This lesson maps that backend onto a React + Redux frontend — so when you're asked "describe a feature you built and how it interacted with the backend", you can walk through the full stack fluently.

1 — React in one paragraph

React is a JavaScript library for building UIs from components — small, reusable functions that return HTML-like JSX. Data flows down (parent → child via props); events flow up (child calls a callback passed as a prop). React re-renders a component when its state or props change — never by mutation, always by replacement.

Angular analogy (if Angular is stronger for you): React component ≈ Angular component. useState ≈ class field + ChangeDetectionStrategy. Props ≈ @Input(). Callback props ≈ @Output() EventEmitter. Redux ≈ NgRx.

Component anatomy

// InvoiceCard.jsx — a pure presentational component
// Receives data via props, emits events via callback props
function InvoiceCard({ invoice, onSelect }) {
  return (
    <div className="invoice-card" onClick={() => onSelect(invoice.id)}>
      <span>{invoice.id}</span>
      <span className={`badge badge--${invoice.status.toLowerCase()}`}>
        {invoice.status}
      </span>
      <span>£{invoice.amountDue.toFixed(2)} due</span>
    </div>
  );
}

// InvoiceList.jsx — composes InvoiceCard
function InvoiceList({ invoices, onSelect }) {
  if (invoices.length === 0) return <p>No invoices found.</p>;
  return (
    <ul>
      {invoices.map(inv => (
        <InvoiceCard key={inv.id} invoice={inv} onSelect={onSelect} />
      ))}
    </ul>
  );
}
Key rule — data down, events up: InvoiceList never modifies the invoice list — it only displays what it receives. When the user clicks, it calls onSelect (passed from the parent) which owns the decision. This is why React is "one-directional data flow."

State and effects

// Without Redux: local state for a simple case
function InvoiceDetailPage({ invoiceId }) {
  const [invoice, setInvoice] = useState(null);   // local state
  const [loading, setLoading] = useState(true);

  useEffect(() => {
    // useEffect fires after render — good place for API calls
    fetch(`/api/invoices/${invoiceId}`)
      .then(r => r.json())
      .then(data => { setInvoice(data); setLoading(false); });
  }, [invoiceId]);  // re-runs whenever invoiceId changes

  if (loading) return <p>Loading...</p>;
  return <InvoiceDetail invoice={invoice} />;
}
When NOT to use local state: If two unrelated components both need the invoice list (e.g. a sidebar summary AND a main table), you'd have to "lift state" to a common ancestor — and threading props down becomes painful. That's exactly when Redux earns its place.

2 — Redux: the pattern

Redux in one sentence: one global JavaScript object (the store) holds all shared state; components read from it via selectors and change it by dispatching actions that are processed by reducers.

The three pieces

PieceWhat it isBillingCo example
Store Single global JS object — the single source of truth { invoices: { list: [], loading: false }, selectedId: null }
Action Plain object: { type: "invoices/fetchAll/fulfilled", payload: [...] } User clicks "Load invoices" → action dispatched → reducer runs
Reducer Pure function: (currentState, action) => nextState. Never mutates — returns a new object. On fetchAll/fulfilled: return { ...state, list: action.payload, loading: false }

Old Redux (why it existed, why RTK replaced it)

// Old Redux — verbose, error-prone, lots of boilerplate
const FETCH_INVOICES_SUCCESS = "FETCH_INVOICES_SUCCESS"; // manual string constant

function invoicesReducer(state = { list: [], loading: false }, action) {
  switch (action.type) {
    case FETCH_INVOICES_SUCCESS:
      return { ...state, list: action.payload, loading: false }; // manual spread
    default:
      return state;
  }
}

// Problem: string typos compile silently, spread-or-mutate errors, 3 files per feature

3 — Redux Toolkit (RTK): modern Redux

Redux Toolkit is the official, recommended way to write Redux since 2020. It eliminates the boilerplate while keeping the same mental model.

createSlice — reducer + action creators in one call

import { createSlice, createAsyncThunk } from "@reduxjs/toolkit";

// createAsyncThunk: wraps an async operation, auto-dispatches
// pending / fulfilled / rejected actions
export const fetchInvoices = createAsyncThunk(
  "invoices/fetchAll",
  async (customerId) => {
    const res = await fetch(`/api/invoices?customerId=${customerId}`);
    return res.json(); // becomes action.payload on fulfilled
  }
);

const invoicesSlice = createSlice({
  name: "invoices",
  initialState: { list: [], loading: false, error: null, selectedId: null },

  // reducers: synchronous actions (no API calls)
  reducers: {
    selectInvoice(state, action) {
      state.selectedId = action.payload; // RTK uses Immer — looks like mutation, IS immutable
    },
    clearSelection(state) {
      state.selectedId = null;
    },
  },

  // extraReducers: handle async thunk lifecycle
  extraReducers: (builder) => {
    builder
      .addCase(fetchInvoices.pending,   (state)         => { state.loading = true; })
      .addCase(fetchInvoices.fulfilled, (state, action) => {
        state.loading = false;
        state.list    = action.payload;
      })
      .addCase(fetchInvoices.rejected,  (state, action) => {
        state.loading = false;
        state.error   = action.error.message;
      });
  },
});

// Slice auto-generates action creators from reducers:
export const { selectInvoice, clearSelection } = invoicesSlice.actions;
export default invoicesSlice.reducer;
Immer magic (the mutation illusion): Inside RTK reducers, state.loading = true looks like mutation but isn't — RTK wraps every reducer with Immer, which tracks changes and produces a new immutable object. You write imperative code; Redux receives pure functional output. Outside reducers, state is still read-only — mutating it directly will throw.

Store setup

// store.js
import { configureStore } from "@reduxjs/toolkit";
import invoicesReducer from "./invoicesSlice";

export const store = configureStore({
  reducer: {
    invoices: invoicesReducer,
    // add more slices here as the app grows
  },
});

// main.jsx — wrap the whole app
import { Provider } from "react-redux";
root.render(
  <Provider store={store}>
    <App />
  </Provider>
);

Reading and dispatching in components

// InvoiceDashboard.jsx
import { useSelector, useDispatch } from "react-redux";
import { fetchInvoices, selectInvoice } from "./invoicesSlice";

function InvoiceDashboard() {
  const dispatch = useDispatch();

  // useSelector: subscribes to a slice of the store, re-renders when it changes
  const { list, loading, error } = useSelector(state => state.invoices);

  useEffect(() => {
    dispatch(fetchInvoices("CUST-001")); // triggers pending→fulfilled→rejected cycle
  }, [dispatch]);

  if (loading) return <p>Loading invoices…</p>;
  if (error)   return <p>Error: {error}</p>;

  return (
    <InvoiceList
      invoices={list}
      onSelect={(id) => dispatch(selectInvoice(id))} // sync action
    />
  );
}

4 — BillingCo component tree

When asked "describe a feature you personally built", you can walk through this tree:

<App>
  <Provider store={store}>         {/* Redux store available everywhere below */}
    <InvoiceDashboard>             {/* reads invoices from Redux, dispatches fetchInvoices */}
      <InvoiceList>                {/* maps list → InvoiceCard items */}
        <InvoiceCard />            {/* presentational: invoice row, onSelect callback */}
      </InvoiceList>
      <InvoiceDetail>              {/* reads selectedId from Redux, shows detail */}
        <PaymentForm />            {/* dispatches recordPayment thunk → POST /api/invoices/{id}/payments */}
      </InvoiceDetail>
    </InvoiceDashboard>
  </Provider>
</App>

The Redux store shape that supports this tree:

{
  invoices: {
    list:       Invoice[],   // all invoices for the customer
    loading:    boolean,     // true while fetching
    error:      string|null, // set on fetch failure
    selectedId: string|null  // which invoice is open in detail panel
  }
}

5 — Interview talking points

QuestionStrong answer in one sentence
When would you use local state vs Redux? Local state for UI-only concerns (is this dropdown open?); Redux for data shared across multiple unrelated components or pages, or for data that persists across navigation.
What is a reducer? A pure function (state, action) => newState — same input always produces the same output, no side effects, returns a new object rather than mutating the old one.
What does createAsyncThunk do? Wraps an async function and auto-dispatches three actions — pending, fulfilled, rejected — matching the promise lifecycle, so you handle loading and error states in one place.
What does useSelector do? Subscribes a component to a specific slice of the Redux store; the component re-renders only when that slice changes — not on every store update.
What problem does Immer solve in RTK? It lets you write reducers that look like direct mutation but produce immutable state — eliminating the error-prone spread operators that made old Redux reducers verbose and fragile.

Quiz — check your understanding

Q1. In React, how does data flow between a parent and child component?

  • Parent passes data down to child via props
  • Child pushes data up to parent via props
  • Both share data through a direct ref object
  • State flows up from child to parent via hooks
Data flows one way: parent → child via props. Children communicate back by calling callback functions passed as props — they never directly push data to the parent. This is "one-directional data flow."

Q2. A Redux reducer must be:

  • A pure function: (currentState, action) => newState
  • An async function that calls the backend API
  • A class method that mutates the store directly
  • A React hook that reads from the global store
Reducers are pure functions: same input always produces the same output, no API calls, no mutations. Side effects (API calls) belong in thunks or middleware, not reducers. Hooks (useSelector) read from the store — they don't change it.

Q3. Which RTK function bundles a reducer and action creators together?

  • createSlice — bundles reducer and action creators
  • createStore — sets up the global Redux store
  • createReducer — generates reducer logic standalone
  • createAction — builds individual action types only
createSlice takes a name, initial state, and a map of reducer functions and auto-generates both the reducer AND typed action creators for each case. This is the RTK pattern that replaced writing separate action type constants, action creators, and switch-case reducers in three different files.

Q4. createAsyncThunk dispatches how many actions over its lifecycle?

  • One action: fulfilled when the promise resolves
  • Three actions: pending, fulfilled, and rejected
  • Two actions: loading-start and loading-end only
  • Four actions: start, retry, success, and failure
createAsyncThunk dispatches exactly three: pending (immediately on dispatch), fulfilled (on resolve), rejected (on error/reject). Your extraReducers handles all three. This is why you can set loading: true on pending and loading: false on both fulfilled and rejected — it always resolves to one of the two terminal actions.
