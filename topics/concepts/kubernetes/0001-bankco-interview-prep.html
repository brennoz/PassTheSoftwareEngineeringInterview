What K8s is, in one breath

What is Kubernetes and why not just run containers with Docker directly?
SAY THISKubernetes is a container orchestrator — it schedules containers onto a cluster of machines, restarts them when they crash, scales them up/down, routes traffic to healthy instances, and rolls out new versions with zero downtime. Plain Docker runs one container on one machine with no self-healing, no scaling, and no coordinated rollout — fine for a laptop, not for a bank running hundreds of services across many nodes.
▸ if pushed
The core loop underneath everything is the controller pattern: you declare desired state (e.g. "3 replicas of this image"), and a controller continuously reconciles actual cluster state toward that declaration. Every K8s object — Deployment, Service, HPA — follows this same declarative reconcile loop.

Core objects

What's a Pod?
SAY THISThe smallest deployable unit in K8s — one or more containers that share network namespace and storage, always scheduled together on the same node. Usually one container per Pod (your app); a second "sidecar" container (like a Datadog agent or an Envoy proxy) is the common exception.
What's a Deployment?
SAY THISA controller that manages a set of identical Pods via a ReplicaSet — you declare the desired replica count and Pod template (image, resources, probes), and the Deployment controller keeps that many healthy Pods running, handling rolling updates when you change the image tag.
▸ if pushed
Rolling update strategy is tunable: maxSurge (how many extra Pods above desired count during rollout) and maxUnavailable (how many can be down). maxUnavailable: 0 is the zero-downtime setting — a new Pod must be Ready before an old one is terminated.
What's a Service?
SAY THISA stable network endpoint (a fixed DNS name and virtual IP) in front of a set of Pods, selected by label. Pods are ephemeral — they get new IPs every time they restart — so nothing should ever talk to a Pod IP directly; everything talks to the Service, which load-balances across whichever Pods are currently Ready.
▸ if pushed
Types: ClusterIP (internal only, default), NodePort (exposes a port on every node, rarely used directly in prod), LoadBalancer (provisions a cloud load balancer — an AWS NLB/ALB on EKS). Most prod setups front everything with an Ingress instead of per-service LoadBalancers, to avoid provisioning a cloud LB per microservice.
Deployment vs Service — how do they relate?
SAY THISA Deployment manages the Pods (what's running, how many, how they update). A Service is the stable front door to those Pods (how traffic finds them). They're linked only by label selectors — the Service's selector matches labels on the Pod template inside the Deployment, not a direct reference. That decoupling is why you can swap Deployments (e.g. blue/green) without touching the Service at all.

Scaling, config, health

What's an HPA?
SAY THISHorizontalPodAutoscaler — watches a metric (CPU%, memory%, or a custom metric like request rate) and adjusts a Deployment's replica count automatically between a min and max, instead of a human scaling manually before a known traffic spike.
ConfigMap vs Secret?
SAY THISBoth inject configuration into Pods as env vars or mounted files. ConfigMap is for non-sensitive config (feature flags, timeouts, URLs). Secret is base64-encoded (not encrypted by default — encryption at rest needs to be explicitly enabled at the cluster level, or you use something like AWS Secrets Manager + External Secrets Operator to sync real secrets in rather than storing them as raw K8s Secrets).
Liveness vs readiness vs startup probes?
SAY THISLiveness answers "should this Pod be restarted" — fails, K8s kills and recreates it. Readiness answers "should this Pod receive traffic right now" — fails, it's pulled from the Service's endpoints but not restarted. Startup probe covers slow-starting apps — nothing else runs until it passes, preventing a liveness probe from killing a Pod that's just still booting.
▸ if pushed
Missing a readiness probe is a classic prod incident: a Pod that's still starting up (JVM warming, DB connection pool not ready) gets traffic immediately on creation and returns errors until it's actually ready. Missing a liveness probe means a hung/deadlocked Pod that's technically "running" but not serving anything just sits there forever, silently dropping capacity.

Banking angle — why this matters more here than elsewhere

Why does K8s rollout safety matter more for a bank than a typical web app?
SAY THISA ledger or payment service can't tolerate split-brain — two versions of business logic running simultaneously against the same DB during a rollout is how you get inconsistent balance calculations or a bug that only affects half of in-flight requests. Zero-downtime rolling updates (maxUnavailable: 0), strict readiness probes, and progressive delivery (canary via Argo Rollouts, not a big-bang rollout) aren't nice-to-haves here — they're the mechanism that keeps "correct" during a deploy, not just "available."
Why do resource limits matter on a shared banking cluster?
SAY THISWithout CPU/memory limits, one misbehaving service (a memory leak, a runaway batch job) can starve every other Pod on the same node — the "noisy neighbour" problem. On a cluster running multiple regulated services, that's not just a performance bug, it's a service running fine in isolation but failing in prod because of something unrelated on the same node. Requests/limits plus PodDisruptionBudget for critical services are the standard mitigation.

The bigger picture — one commit to a running Pod

If asked to sketch how a change actually reaches production, this is the shape (worth having as a mental model, not something to recite verbatim):

git push → GitLab CI (test, build, docker build/push to ECR) │ ▼ ArgoCD (GitOps controller inside the cluster, polls a Git repo holding the desired Helm values — NOT triggered by CI directly) │ ▼ EKS rolling update (readiness-gated, zero-downtime) │ ▼ Datadog (traces, metrics, SLO alerting → PagerDuty/Slack on breach) Terraform underneath: provisions the EKS cluster, node groups, ECR, IAM roles — infra, not application state.
Key point if asked "who deploys to prod?": Nothing in CI has direct cluster credentials — ArgoCD is the only thing with write access to the cluster, and it only acts on what's committed to Git. That boundary is deliberate: it caps a compromised CI pipeline's blast radius at "can push a Git commit," not "can run kubectl against prod."
