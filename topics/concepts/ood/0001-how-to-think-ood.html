Object-oriented design is not about picking the right pattern first. It is about asking the right questions in order — and letting the answers drive the structure. This lesson gives you a repeatable thinking process you can apply to any OOD problem, illustrated with two real implementations of the same system.

Running example: Twitter. We built it twice: q032 — Rich Domain / Observer and q035 — Service Layer / Thin Records. Both are correct OOD. They make different tradeoffs. This lesson explains how to choose.

Step 1 — Find the nouns

Read the problem statement and underline every noun. Group them into three buckets:

Bucket What it is Java representation Examples (Twitter)
Entity Has identity that persists over time. Two objects with same data are not the same if they have different IDs. class User, has an id User, Tweet, Conversation
Value Object Defined purely by its data. Two objects with same data are the same. Java record (immutable) MediaUrl, Location, Timestamp
Relationship Connects two entities. Has its own data (timestamp, role). Queryable in both directions. record Follow(String followerId, String followeeId, Instant at) Follow, Like, Retweet, Block
Common mistake: Treating a relationship as a field instead of an entity.
class User { List<User> followers; } — looks fine for one user. Ask yourself: Can I answer "who followed whom and when?" from this structure? If not, the relationship needs to be its own object.

Questions to ask at Step 1

  • Does this noun have an ID that survives updates? → Entity
  • Are two instances interchangeable if their data is equal? → Value Object → use record
  • Does this noun connect two other nouns and carry its own data? → Relationship entity
  • Is this noun only ever accessed through its parent? → Embed it, not a separate entity

Twitter example

Entities

  • User — has id, identity matters
  • Tweet — has id, immutable content

Relationships

  • Follow(followerId, followeeId, at)
  • Like(userId, tweetId, at)
  • These deserve their own class because they are queryable in both directions and carry a timestamp

Step 2 — Decide the model style

There are two fundamentally different ways to distribute behavior in an OOD system. You need to pick one early — mixing them is the most common source of confusion.

Rich Domain Model DDD style

  • Entities own their behavior
  • user.follow(other)
  • tweet.addLike(userId)
  • Logic lives inside the object
  • Good when: rules tightly couple to entity state

Service Layer + Thin Records Prod style

  • Entities are data containers only
  • socialGraph.follow(a, b)
  • likeService.like(userId, tweetId)
  • Logic lives in service classes
  • Good when: rules span multiple entities or need cross-cutting queries
Question Rich Domain Service Layer
"Who follows Alice?" (reverse lookup) Requires scanning all users for alice ∈ user.following socialGraph.getFollowers("alice") — O(1)
Serialize to DB Complex — need to extract embedded lists Each record maps 1:1 to a DB table row
Cross-entity transaction Entity must reach into other entities Service calls both repos in one transaction
Testing in isolation Easy — just create entity Need to inject service dependencies
Adding a new query New method on entity New method on service/repo — entity unchanged
Rule of thumb for interviews: If the relationship between two entities is itself a first-class concept with data (Follow has a timestamp, Like has a timestamp), model it as a relationship entity and use the Service Layer. That structure maps directly to a DB schema and scales to production.

Step 3 — Assign behavior with design patterns

Once you know your entities and model style, assign behavior using patterns. The key is to name the pattern — not just write code that happens to have the same shape.

Pattern Problem it solves OOD signal Example
Strategy Algorithm that varies at runtime Multiple ways to do the same thing FineCalculationStrategy — daily vs flat rate
State Object behavior depends on internal state Methods that throw "invalid in this state" BookCopy: AVAILABLE→RESERVED→BORROWED
Observer Multiple objects react to one event Fan-out: one action → N side effects User posts tweet → all followers' feeds update
Factory / Builder Complex object creation Constructor with many optional params TweetBuilder with 280-char validation
Command Encapsulate an operation as an object Undo/redo, queue operations, audit log Bank transfer: DebitCommand + CreditCommand
Template Method Algorithm skeleton, steps vary in subclasses Same sequence, different implementations Tweet.displayContent() — different for Original/Reply/Retweet
Decorator Add responsibilities without subclassing Wrap an object to add behavior at runtime LoggingRepository wraps real repo for audit
Facade Simplify a complex subsystem Many services, one entry point TwitterService — delegates to 4 sub-services
How to spot which pattern to use:
  • Object has a lifecycle / state machine → State
  • One event triggers many side effects → Observer
  • One algorithm, multiple implementations, swappable at runtime → Strategy
  • Complex construction, optional fields, validation on build → Builder
  • Multiple services behind one API → Facade
  • Steps fixed, implementation per subclass → Template Method

State Pattern — the most important for OOD interviews

Any entity with a lifecycle needs a State pattern. The invariant is:

// Entity delegates to state — state modifies entity
class BookCopy {
    private BookCopyState state;

    void reserve() {
        state.reserve(this);  // delegation: entity → state
    }
}

class AvailableState implements BookCopyState {
    public void reserve(BookCopy c) {
        c.setState(new ReservedState());  // state modifies entity
    }
}

class BorrowedState implements BookCopyState {
    public void reserve(BookCopy c) {
        throw new IllegalStateException("Already borrowed");
    }
}
Common State Pattern bug: Setting state directly in the entity method bypasses the guard.
Wrong: void reserve() { this.state = new ReservedState(); } — BorrowedState.reserve() (which throws) is never called.
Right: void reserve() { state.reserve(this); }

Step 4 — Think about persistence

Every entity eventually needs to be stored. Design your objects so that mapping to a DB table is obvious, even in an in-memory simulation.

Object type DB equivalent In-memory equivalent Key lesson
Entity Table row (users) Map<String, User> ID is always the map key
Relationship entity Join table (follows) Map<String, Set<String>> adjacency list Store in both directions for O(1) reverse lookup
Secondary index CREATE INDEX ON tweets(author_id) Map<String, List<Tweet>> byAuthor Keep in sync on every write — both maps updated together
Value Object Column(s) in parent row Field on parent record No separate storage needed

Repository pattern

In-memory repositories simulate a database. Always build them with the same interface you'd expose over JPA — this makes migration from in-memory → JPA trivial.

class TweetRepository {
    private final Map<String, Tweet>        byId     = new HashMap<>();
    private final Map<String, List<Tweet>> byAuthor = new HashMap<>();

    void save(Tweet t) {
        byId.put(t.id(), t);                                      // primary
        byAuthor.computeIfAbsent(t.authorId(), k -> new ArrayList<>()).add(t);  // secondary index
    }

    Optional<Tweet> findById(String id)          { return Optional.ofNullable(byId.get(id)); }
    List<Tweet>     findByAuthorId(String uid)    { return byAuthor.getOrDefault(uid, List.of()); }
}
Common persistence bug: computeIfAbsent(key, k -> Set.of())
Set.of() returns an unmodifiable set. Calling .add() on it throws UnsupportedOperationException.
Always use k -> new HashSet<>() or k -> new ArrayList<>().

Step 5 — Think about production and scale

Every in-memory OOD solution breaks at scale. Knowing exactly how it breaks — and what replaces it — is what separates a junior answer from a senior one.

What breaks first on a multi-pod deployment

In-memory structure Why it breaks on multiple pods Production replacement AWS service
HashMap (idempotency keys) Pod A stores key, retry lands on Pod B — key not found → duplicate PostgreSQL UNIQUE constraint on idempotency_key RDS Multi-AZ
Map<String, Set<String>> (SocialGraph) Follow on Pod A, timeline read on Pod B — follower missing PostgreSQL follows table or adjacency in Neo4j RDS / Neptune
List<Tweet> (timeline in memory) Timeline built per-pod from local data — incomplete Redis Sorted Set (score = timestamp); populated on write ElastiCache Redis
Like counter as Set.size() Concurrent likes on 2 pods → race → count wrong Redis INCR (atomic) or DB UPDATE ... SET count = count + 1 ElastiCache / RDS
synchronized on service method Only prevents race within one JVM — two pods share nothing DB-level lock (SELECT FOR UPDATE), optimistic lock (@Version), Redis SET NX RDS / ElastiCache

Observer pattern at scale

The Observer pattern works in-process. In production, the equivalent is an event broker.

OOD concept Production equivalent AWS service
subject.addObserver(obs) Consumer group subscribes to Kafka topic MSK (Kafka), SQS, SNS
subject.notifyObservers(event) Producer publishes event to topic Kafka producer / SNS publish
observer.update() Consumer polls and processes message Lambda trigger / ECS consumer
Synchronous notification in-process Async, durable, at-least-once delivery Kafka with consumer groups

State Pattern at scale

A state machine in-memory loses state when the pod restarts. In production:

  • Store current state as a column in DB: status VARCHAR on the entity row
  • Use UPDATE ... WHERE status = 'AVAILABLE' for atomic transitions (optimistic concurrency)
  • Use AWS Step Functions for long-running state machines that span services
  • Never allow invalid transitions — enforce at DB level with a CHECK constraint too

Key financial / domain rules (always relevant)

Never use double or float for money, odds, or fees. 0.1 + 0.2 == 0.30000000000000004 in IEEE 754. Use BigDecimal. Use compareTo() not == to compare.
  • Idempotency: any mutation endpoint (POST /bets, POST /payments) must accept an idempotency key. Duplicate request = same result, not double execution.
  • Optimistic locking: concurrent updates to the same entity (balance, like count) need @Version in JPA or a conditional write in DynamoDB.
  • Audit trail: financial entities (ledger entries, bets) must be append-only. No UPDATE on posted rows.

The decision tree

Apply this before writing any code:

Problem given
↓
1 Classify each noun — what kind of thing is it?
Has a stable identity that survives data changes? → Entity  ·  has an id field
Two instances are equal if their data is equal? → Value Object  ·  use Java record
Connects two entities and carries its own data? → Relationship entity  ·  record(aId, bId, at)
↓
2 Decide where behavior lives
Rules tightly bound to a single entity's own state? → Rich Domain Model  ·  entity.doX()
Rules span multiple entities, or need cross-queries? → Service Layer  ·  thin records + service classes
↓
3 Pick the right design pattern for each behavior
Entity has a lifecycle with guarded transitions (throw if invalid)? → State Pattern
Same operation, multiple swappable algorithms at runtime? → Strategy Pattern
One event triggers side effects in N other objects? → Observer Pattern
Object has many optional fields, validation on build? → Builder Pattern
Same sequence of steps, subclass varies each step? → Template Method
Many services hidden behind one clean entry point? → Facade Pattern
↓
4 Map to persistence (even in-memory)
Each entity → Map<String, T> keyed by id
Each relationship (Follow, Like, Loan…) → Adjacency maps in both directions
Query "all tweets by author"? → Secondary index  ·  Map<String, List<T>>
↓
5 Production sanity checks — ask these before you finish
Any in-memory state (Map, List, counter)? → Breaks on multi-pod  →  move to Redis / DB
Any synchronized method? → Breaks on multi-JVM  →  use DB lock / @Version
Money, odds, fees, interest in the domain? → Never double  →  use BigDecimal
Any POST/PUT that modifies state? → Idempotency key required  →  duplicate = same result

Quiz

Q1. You are designing a ride-sharing app. A Trip passes through states: REQUESTED → ACCEPTED → IN_PROGRESS → COMPLETED (or CANCELLED). Which pattern should control this lifecycle?

  • Strategy — because behaviour varies per state
  • State — because the object has a lifecycle with transitions that guard invalid moves
  • Observer — because multiple services react to each trip event
  • Template Method — because each phase has a fixed set of steps
State Pattern. The Trip entity has a finite lifecycle. Each state guards invalid transitions (e.g. CANCELLED cannot move to IN_PROGRESS). The delegation invariant: trip.cancel() → state.cancel(trip) → state either transitions or throws. Observer is also useful for notifying passengers/drivers, but the lifecycle management itself is State. At scale: the current state is stored as a status column; transitions use UPDATE WHERE status = 'IN_PROGRESS' to prevent concurrent race conditions.

Q2. You build a loyalty points service. Each user has a Map<String, Integer> pointsBalance in memory. In production on 4 ECS pods, a user makes two purchases simultaneously — both pods read 100 points, both add 50, both write back 150 instead of 200. Which fix is correct?

  • Add synchronized to the balance update method in the service class
  • Use ConcurrentHashMap instead of HashMap
  • Replace in-memory balance with DB row + optimistic lock (@Version), or Redis INCR
  • Use a thread-local copy of the balance per request
DB optimistic lock or Redis INCR. synchronized and ConcurrentHashMap only protect within one JVM. With 4 pods, each pod has its own heap — synchronization is meaningless across them. The fix: store balance in PostgreSQL with @Version — if two pods try to commit concurrently, one gets an OptimisticLockException and retries. Alternative: Redis INCR is atomic at the Redis level — safe across all pods. AWS: ElastiCache for Redis INCR, or RDS Multi-AZ for optimistic locking.

Q3. You are modelling a bank loan system. A Loan entity needs to support calculating interest. The bank offers two products: simple interest and compound interest, each a different formula. New products may be added. Which pattern is most appropriate?

  • Strategy — inject an InterestCalculationStrategy into the service; each product is one strategy implementation
  • State — because the loan changes state when interest is applied
  • Template Method — because both strategies share the same sequence of steps
  • Decorator — because interest calculation wraps the base loan object
Strategy. Multiple interchangeable algorithms (simple vs compound interest) that vary at runtime based on the loan product. Strategy: define InterestCalculationStrategy interface with calculate(principal, rate, days); inject the right implementation when creating the loan. Open/Closed Principle: adding a new product = new strategy class, no changes to existing code. Template Method could work if the steps are strictly shared — but here the formulas are entirely different, so Strategy fits better. Always use BigDecimal for the calculation — never double.

Q4. In your Twitter OOD, you model followers as class User { List<User> following; }. A product manager asks: "show me everyone who follows a given user, ordered by when they followed." Which statement is true?

  • This is easy — just call stream().filter() on the following list of each user
  • Add a List<User> followers field to User — symmetric data solves it
  • Add a Map<User, Instant> followerSince map to User to capture timestamps
  • Replace the embedded list with an explicit Follow(followerId, followeeId, followedAt) entity stored in a dedicated repository queryable in both directions
Explicit Follow entity. Option 1 requires scanning every user — O(N·M). Option 2 adds reverse data but still has no timestamp. Option 3 adds timestamp but data is embedded in User — breaks when you need to query "all follows for user X" across a large graph. The correct model: Follow is its own entity. In memory: two adjacency maps (following and followers). In production: a follows table with (follower_id, followee_id, followed_at) indexed in both directions. Query "followers ordered by followed_at" becomes a simple SELECT ... WHERE followee_id = ? ORDER BY followed_at DESC. At graph scale (Twitter): Neo4j or a dedicated social graph service backed by Aurora + ElastiCache.
