Sealed Interfaces & Pattern Matching for Switch

Category: Java · Topic: Java 17/21 Features · Est. time: 20 min · Lesson 8

Two features that only make sense discussed together: sealed types (Java 17) let you declare a closed, finite set of subtypes; pattern matching for switch with record deconstruction patterns (both finalized in Java 21) let the compiler prove you've handled every one of them. Individually they're modest syntax additions. Together they replace a whole category of runtime bugs — the "someone added a new subtype and forgot to update this switch statement six months later" bug — with a compile error at the exact line that needs updating.

1. The problem this solves — polymorphism without a shared method

Say you have a family of shapes and need to compute area. The textbook OOP answer is to put an area() method on each shape. But sometimes that's wrong — area might be a concern that belongs to a calculator, not the shape itself (single responsibility), or the shapes might be simple data records you don't want to load up with behaviour. The alternative before Java 21 was an instanceof chain, or the Visitor pattern to avoid it. Both have a shared weakness.

⛔ instanceof chain — compiles even when incomplete
double area(Shape shape) {
    if (shape instanceof Circle c) {
        return Math.PI * c.radius() * c.radius();
    } else if (shape instanceof Rectangle r) {
        return r.width() * r.height();
    }
    // Forgot Triangle entirely — this COMPILES.
    // Every call with a Triangle throws at runtime instead.
    throw new IllegalStateException("Unknown shape");
}
✅ sealed + switch pattern matching — won't compile if incomplete
double area(Shape shape) {
    return switch (shape) {
        case Circle(double radius) ->
            Math.PI * radius * radius;
        case Rectangle(double width, double height) ->
            width * height;
        // Missing "case Triangle" here is a
        // COMPILE ERROR, not a runtime surprise.
    };
}
Why the instanceof version is dangerous, specifically It's not that the code is wrong today — it's that it stays "correct" (compiles, passes existing tests) even after it becomes wrong, the moment a new subtype is added and this one switch/if-chain isn't updated. The bug is discovered by a user hitting the throw, not by the compiler. Sealed + exhaustive switch turns that into a build failure the person adding the new type sees immediately, at the exact call site that needs a new case.

2. Sealed types — declaring a closed hierarchy

sealed on an interface or class, plus a permits clause, tells the compiler "this is the complete list of implementations — nothing outside this list is allowed to implement/extend it."

public sealed interface Shape permits Circle, Rectangle, Triangle {}

public record Circle(double radius) implements Shape {}
public record Rectangle(double width, double height) implements Shape {}
public record Triangle(double base, double height) implements Shape {}

Every class named in permits must itself declare how it participates in the seal — final (no further subtyping, the common choice, and what a record implicitly is), sealed (has its own further-restricted permits list), or non-sealed (explicitly reopens the hierarchy to arbitrary subtypes from that point down — rare, and usually a sign the design should reconsider whether sealing was right here).

Modifier on the implementing classMeaning
finalNo further subtypes at all — the common case, and implicit for record
sealedHas its own permits list — the closed hierarchy continues one level deeper
non-sealedReopens to unlimited subtypes from here — use sparingly, it's an escape hatch that gives up the exhaustiveness guarantee for that branch

3. Record patterns — deconstruction, not just type-checking

case Circle c -> only binds the whole record to a name; you'd still call c.radius() yourself. case Circle(double radius) -> is a record pattern — it deconstructs the record's components directly into local variables, matching the record's own canonical constructor shape.

// Type pattern only — still need c.radius()
case Circle c -> Math.PI * c.radius() * c.radius();

// Record (deconstruction) pattern — radius is already a local double
case Circle(double radius) -> Math.PI * radius * radius;

Record patterns nest, which matters once your domain has records containing other records — you can reach into nested structure in one pattern rather than chaining accessor calls:

record Point(double x, double y) {}
record Line(Point start, Point end) {}

// Nested record pattern — pulls all four numbers out in one match
case Line(Point(double x1, double y1), Point(double x2, double y2)) ->
    Math.hypot(x2 - x1, y2 - y1);

4. Guarded patterns — adding a condition with when

Sometimes a case depends on more than just the type — e.g. "a Circle, but only if its radius is zero." A when clause adds a boolean condition to a pattern without breaking out into a separate if:

String describe(Shape shape) {
    return switch (shape) {
        case Circle(double radius) when radius == 0 -> "a point, not really a circle";
        case Circle(double radius) -> "a circle of radius " + radius;
        case Rectangle(double w, double h) when w == h -> "actually a square";
        case Rectangle r -> "a rectangle";
        case Triangle t -> "a triangle";
    };
}
Exhaustiveness still holds with guards, with one catch The compiler can't prove a when condition covers every value of that type (it's arbitrary boolean logic, not something it can statically reason about) — so when you use a guard, you generally still need an unguarded fallback case for that same type below it (as above: the guarded Circle case is followed by a plain case Circle catch-all for that type). The overall switch is still exhaustive across all sealed subtypes; it's just that a guarded case alone doesn't exhaust ITS type on its own.

5. instanceof pattern matching (Java 16) — the building block underneath

Before switch got pattern matching, instanceof did (Java 16, JEP 394) — this is what powered the if (shape instanceof Circle c) line back in Section 1's "old way" example. It's worth knowing as its own feature: useful for a single type check outside a switch, but it doesn't give you exhaustiveness checking the way a sealed-type switch does — the compiler has no way to know you've covered every case with a chain of independent if statements.

Retrieval Quiz

Q1. Why does the switch in Section 1's "new way" example NOT need a default branch?

  • Switch expressions never require a default in Java
  • Because Shape is a record, not an interface
  • Because Shape is sealed with a permits list of exactly Circle/Rectangle/Triangle — the compiler can enumerate every possible subtype and verify all are handled
  • Because record patterns automatically supply a default case
Exhaustiveness checking for switch only works this way against a sealed (or enum) type, where the compiler has the complete, closed list of possibilities. Against a plain (non-sealed) interface, the switch would need a default, since anyone anywhere could add a new implementation the compiler doesn't know about.

Q2. A teammate adds record Square(double side) implements Shape to the permits list. What happens to the exhaustive switch from Section 1 if no new case is added for it?

  • Nothing — it silently falls through and returns 0
  • The module fails to compile, pointing at the switch that's now missing a case
  • It throws a MatchException at runtime, the first time a Square is passed in
  • Java auto-generates a case that calls Square's toString()
This is the entire payoff of pairing sealed types with exhaustive switch: the failure moves from "a MatchException in production the day someone finally passes a Square" to "a compile error the moment the teammate adds Square," at the exact switch that needs updating. (Note: if the switch DID have a catch-all/default, it would compile fine and silently take the wrong branch instead — which is exactly why Section 1's callout warns against adding a default "just in case.")

Q3. What's the difference between case Circle c -> and case Circle(double radius) ->?

  • No difference, purely stylistic
  • The second is a record pattern that deconstructs radius into a local variable directly; the first only binds the whole record, and you'd still call c.radius() to get the value
  • The first only works on records, the second only works on regular classes
  • The second requires the when keyword
Both are valid pattern-matching forms. The plain type pattern (Circle c) just narrows the type and binds a name to the whole object. The record pattern additionally reaches into the record's components, matching its canonical constructor shape, and binds each component to its own local variable.

Q4. In the guarded-pattern example (Section 4), why does case Circle(double radius) when radius == 0 -> ... need a plain case Circle(double radius) -> ... below it, when the switch is already exhaustive over Shape?

  • It doesn't — that line is unnecessary and can be deleted
  • Guards are only legal on the last case in a switch
  • Java requires every record pattern to appear at least twice
  • A when guard is arbitrary boolean logic the compiler can't statically prove covers every value of that type — so a Circle where radius != 0 needs its own (unguarded) case to still be handled
Exhaustiveness checking works at the type level (has every sealed subtype got a case), not at the value level (has every possible input to a boolean guard been covered) — the latter is undecidable in general. So a guarded case for a type still needs a fallback, unguarded case for that same type, or the compiler will report the switch as non-exhaustive.

Q5. What does marking a permitted subclass non-sealed actually do?

  • Reopens the hierarchy from that point — arbitrary new subtypes of THAT class are now allowed, which means a switch that's exhaustive over the sealed parent may no longer be exhaustive if it also tries to pattern-match that non-sealed branch's own subtypes
  • It's a compile error — permitted subclasses must be final or sealed
  • It has no effect — non-sealed is a no-op modifier kept only for readability
  • It makes the class abstract
non-sealed is a deliberate escape hatch: it lets one branch of an otherwise closed hierarchy stay open to unknown future subtypes (useful for a plugin-style extension point), at the cost of giving up compiler-verified exhaustiveness for that branch specifically.
