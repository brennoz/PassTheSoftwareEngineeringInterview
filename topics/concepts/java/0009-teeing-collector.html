Collectors.teeing — Two Aggregations, One Pass

Category: Java · Topic: Collectors (Java 12) · Est. time: 15 min · Lesson 9

Most collector questions ask: collect this stream into one result. Collectors.teeing (introduced in Java 12) answers a harder question: what if I need two different results from the same stream, without iterating it twice? It splits every element into two independent downstream collectors simultaneously, then merges their results in one final step.

1. The Problem It Solves

Suppose you have a list of settled bets and you need two things: the total payout to winners, and the count of all bets processed. These two aggregations have different filtering criteria — payout sums only won bets, count includes everyone. Without teeing, you need two passes:

// Two-pass — iterates the list twice
BigDecimal totalPayout = settlements.stream()
    .filter(Settlement::won)
    .map(Settlement::payout)
    .reduce(BigDecimal.ZERO, BigDecimal::add);

long count = settlements.stream()
    .count();                                   // second pass

Or you collect to an intermediate list and re-stream — same cost, more code. teeing fuses both into one pass:

// Single pass — both collectors see every element once
SettlementReport report = settlements.stream()
    .collect(Collectors.teeing(
        Collectors.filtering(Settlement::won,
            Collectors.reducing(BigDecimal.ZERO, Settlement::payout, BigDecimal::add)),
        Collectors.counting(),
        SettlementReport::new          // BiFunction merger
    ));

2. Signature

static <T, R1, R2, R> Collector<T, ?, R> teeing(
    Collector<? super T, ?, R1> downstream1,
    Collector<? super T, ?, R2> downstream2,
    BiFunction<? super R1, ? super R2, R> merger
)
ParameterWhat it does
downstream1First collector — receives every element, produces R1
downstream2Second collector — receives every element, produces R2
mergerTakes R1 and R2, returns the final result R

The merger is a BiFunction<R1, R2, R>. A constructor reference like SettlementReport::new works when the record constructor matches the signature — SettlementReport(BigDecimal, long) matches BiFunction<BigDecimal, Long, SettlementReport>.

3. Collectors.filtering (Java 9)

Collectors.filtering(predicate, downstream) applies a Predicate inside a Collector pipeline. It is the collector equivalent of Stream.filter().

Why not just .filter() before the terminal collect? settlements.stream() .filter(Settlement::won) // only winners reach teeing .collect(teeing(reducing(...), counting(), SettlementReport::new)) Pre-filtering breaks settledCount: counting() now only sees winners, not all settled bets. When the two downstream collectors need different predicates, Collectors.filtering is mandatory inside teeing.
✓ filtering inside teeing — different predicates work
.collect(teeing(
  Collectors.filtering(
    Settlement::won,        // filter inside collector 1
    reducing(ZERO, payout, add)),
  counting(),              // no filter — counts all
  SettlementReport::new
))
⛔ pre-filter — breaks second collector
.filter(Settlement::won) // strips non-winners
.collect(teeing(
  reducing(ZERO, payout, add),
  counting(),              // now counts only winners!
  SettlementReport::new
))

4. Reducing — the Identity vs No-Identity Trap

Inside teeing you frequently need Collectors.reducing. There are two overloads that matter:

OverloadReturnsUse when
reducing(identity, mapper, combiner) T directly Empty partition must return a sensible default (e.g. BigDecimal.ZERO)
reducing(BinaryOperator) Optional<T> Empty case must be signalled explicitly as absent
Common mistake: 1-arg reducing inside teeing → type mismatch teeing( reducing(Settlement::payout), // returns Optional<BigDecimal> counting(), SettlementReport::new // constructor expects BigDecimal, not Optional ) The constructor reference fails to compile because R1 = Optional<BigDecimal>, not BigDecimal. Always use the 3-arg overload when you need T directly.

5. When to Use Teeing vs. Alternatives

ScenarioRight tool
Two aggregations, same predicate (or no predicate)teeing or pre-filter + teeing
Two aggregations, different predicatesteeing + Collectors.filtering inside each downstream
Two passes on a List — readability matters more than performanceTwo separate streams (simpler, still fine for small data)
Three or more aggregationsManual for-each or collect to intermediate + process (teeing only composes two)
Parallel stream — combining must be associativeteeing is parallel-safe; each downstream must be too

6. Domain Examples

Payment — reconciliation in one pass

record TxSummary(BigDecimal approvedTotal, long declinedCount) {}

TxSummary summary = transactions.stream()
    .collect(Collectors.teeing(
        Collectors.filtering(Transaction::approved,
            Collectors.reducing(BigDecimal.ZERO, Transaction::amount, BigDecimal::add)),
        Collectors.filtering(t -> !t.approved(), Collectors.counting()),
        TxSummary::new
    ));

Betting — payout vs stake ratio

record BookReport(BigDecimal totalPayout, BigDecimal totalStake) {}

BookReport book = bets.stream()
    .collect(Collectors.teeing(
        Collectors.reducing(BigDecimal.ZERO, Bet::payout, BigDecimal::add),
        Collectors.reducing(BigDecimal.ZERO, Bet::stake,  BigDecimal::add),
        BookReport::new
    ));

7. In AWS / Distributed Environment

Collectors.teeing is a local, in-JVM computation — there is no direct AWS equivalent. However, the pattern it represents — computing multiple aggregates in a single data scan — maps directly to distributed systems:

  • Kafka Streams / Flink: a single consumer reading a settlement topic can maintain two KTables (payout aggregate + count aggregate) from one consume loop, rather than spinning up two consumer groups.
  • AWS Athena / Redshift: SELECT SUM(payout) FILTER (WHERE won), COUNT(*) FROM settlements — the SQL FILTER clause is the exact relational equivalent of Collectors.filtering inside a downstream aggregate.
  • DynamoDB: no native multi-aggregate scan — you'd read the table once and compute locally, exactly what teeing enables.

Quiz

Q: You need two results from a stream: the sum of amounts for APPROVED transactions and the count of all transactions (approved + declined). Which code is correct?

  • .filter(Transaction::approved)
    .collect(teeing(reducing(ZERO, amount, add), counting(), TxSummary::new))
  • .collect(teeing(filtering(Transaction::approved, reducing(ZERO, amount, add)), counting(), TxSummary::new))
  • .collect(teeing(reducing(Transaction::amount), counting(), TxSummary::new))
  • .collect(teeing(groupingBy(Transaction::approved, reducing(ZERO, amount, add)), counting(), TxSummary::new))
Option 1 pre-filters to approved only — counting() then counts only approved, not all transactions. Wrong.
Option 2 is correct: Collectors.filtering scopes the predicate to downstream1 only; downstream2 (counting()) still sees every element.
Option 3 uses 1-arg reducing — returns Optional<BigDecimal>, which won't match a BigDecimal constructor parameter.
Option 4 passes a Map as R1 — incompatible with the record constructor.
