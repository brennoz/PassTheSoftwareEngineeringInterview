Ex1 — ThreadSafeLedger

A ledger where withdraw/deposit/transfer must be safe under real concurrent access. The interesting part isn't the single-lock case — it's transfer, which needs two locks at once.

The deadlock trap

If transfer(from, to) always locks from first then to, two threads transferring in opposite directions between the same two accounts can deadlock: Thread A holds account X waiting for Y, Thread B holds Y waiting for X. Neither ever proceeds.

SAY THISLock ordering — always acquire locks in the same global order regardless of transfer direction (e.g. compare account IDs), so both threads try to lock the SAME account first. One of them just waits its turn instead of the two deadlocking on each other. 
// Ledger.transfer() — from interview-prep/natwest/ex1_thread_safe_ledger/solution/Ledger.java
Account first  = account(fromId.compareTo(toId) <= 0 ? fromId : toId);
Account second = account(fromId.compareTo(toId) <= 0 ? toId : fromId);

lock(first);
try {
    lock(second);
    try { /* move the money */ }
    finally { second.getLock().unlock(); }
} finally { first.getLock().unlock(); }

Why ReentrantLock, not synchronized

tryLock(timeout, unit) is the reason. synchronized blocks forever with no way to bail out — in a production system that's how a thread-pool starvation incident happens (one stuck lock, every request thread eventually piles up behind it). ReentrantLock.tryLock lets you fail fast and let the caller retry.

Ex2 — TransactionFunctionalToolkit

thenApply vs thenCompose

SAY THISthenApply for a synchronous transform of an already-available value. thenCompose when the next step is ITSELF async — it flattens CompletableFuture<CompletableFuture<T>> down to CompletableFuture<T>. 
// thenApply: Account::getBalance is a plain synchronous getter, not async
public CompletableFuture<BigDecimal> fetchBalance(String accountId) {
    return accountFetcher.fetchAccount(accountId)
            .thenApply(Account::getBalance);
}

// thenCompose: validator.validate(...) ITSELF returns a CompletableFuture —
// thenApply here would produce CompletableFuture<CompletableFuture<ValidationResult>>
public CompletableFuture<ValidationResult> validateTransaction(Transaction transaction) {
    return accountFetcher.fetchAccount(transaction.getAccountId())
            .thenCompose(account -> validator.validate(account, transaction));
}

RxJava — filter / map / reduce

Same operator vocabulary as java.util.stream, but the source is async and push-based rather than an in-memory collection you pull from.

public Single<BigDecimal> totalOfValidTransactions(Observable<BigDecimal> amounts) {
    return amounts
            .filter(amount -> amount.compareTo(BigDecimal.ZERO) > 0)
            .filter(amount -> amount.compareTo(MAX_SINGLE_TRANSACTION) <= 0)
            .reduce(BigDecimal.ZERO, BigDecimal::add);
}

reduce vs Collectors — and the empty-input tell

SAY THISStream.reduce with no identity returns Optional — an empty stream has no result to fall back to. Collectors.joining is a mutable reduction purpose-built for strings (a StringBuilder under the hood) — an empty input just joins to "", never Optional.
parts.stream().reduce((a,b) -> a+"-"+b)parts.stream().collect(Collectors.joining("-"))
3 elementsOptional.of("NWB-2026-0042")"NWB-2026-0042"
0 elementsOptional.empty()""

And the literal "String reduce" reading — IntStream.reduce over a String's char codes, e.g. a simple checksum:

public int checksum(String input) {
    return input.chars().reduce(0, Integer::sum);
}

Ex3 — ConcurrentTransactionStream (combined)

Merges everything above into one gotcha: RxJava's own scheduler threads are just as real a concurrency source as an ExecutorService you spin up yourself. Observable.merge of several sources each subscribeOn(Schedulers.io()) means the subscriber's onNext callback genuinely fires from different threads.

The bug this catches: assuming RxJava "handles concurrency for you" and updating shared ledger state directly inside subscribe() with no lock. It compiles, it often even passes on a quiet machine, and it loses updates under real load — exactly the class of bug that's hard to catch outside a dedicated concurrency test with enough producers/events to force the race. 
// StreamMain.java — the lock-protected update still has to happen explicitly
events.subscribe(event -> {
    BigDecimal resultingBalance = ledger.apply(event);  // ConcurrentLedger: lock-protected
    gateway.persist(event.getAccountId(), resultingBalance).thenRun(done::countDown);
});

The test proves it deterministically: 4 producers × 25 events each, exact expected final balance, exact expected persisted-record count — not "probably fine," a hard assertion.

RxJava vs Spring WebFlux

If NatWest's actual codebase is Spring-based, there's a real chance the reactive question is really about Project Reactor (WebFlux's reactive library), not RxJava specifically — worth clarifying live if it comes up ("are we talking RxJava specifically, or reactive streams generally / WebFlux?").

RxJavaReactor (Spring WebFlux)Note
Observable<T> (0..N, no backpressure contract)Flux<T> (0..N, backpressure-aware)Both implement the same underlying Reactive Streams spec (Publisher/Subscriber) — they're interoperable at that boundary.
Single<T> / Maybe<T>Mono<T>Exactly-0-or-1 value. Reactor collapses RxJava's two types (Single always has a value, Maybe might not) into one Mono that can complete empty.
Flowable<T> (explicit backpressure)Flux<T> (backpressure always on)RxJava makes you choose Observable vs Flowable based on whether backpressure matters; Reactor's Flux just always supports it.
map / filter / reduce / flatMapsame names, same semanticsOperator vocabulary is close to identical — this is the part that transfers directly regardless of which library the interviewer actually meant.
Standalone library, works in any Java appNative to the Spring ecosystem — WebFlux controllers return Mono/Flux directlyIn a Spring shop, Reactor is the default choice specifically because the whole stack (WebClient, R2DBC, controller return types) is built around it — reaching for RxJava alongside Spring means bridging between two reactive libraries for no real benefit.

What Ex2/Ex3 would look like ported to WebFlux

// RxJava (this course's exercises)
public Single<BigDecimal> totalOfValidTransactions(Observable<BigDecimal> amounts) {
    return amounts.filter(a -> a.compareTo(ZERO) > 0)
                  .reduce(ZERO, BigDecimal::add);
}

// Same shape in Reactor / WebFlux
public Mono<BigDecimal> totalOfValidTransactions(Flux<BigDecimal> amounts) {
    return amounts.filter(a -> a.compareTo(ZERO) > 0)
                  .reduce(ZERO, BigDecimal::add);
}

// CompletableFuture -> Mono bridge, when wrapping existing async code
Mono<Account> account = Mono.fromFuture(accountFetcher.fetchAccount(id));
// thenCompose's equivalent in Reactor is flatMap:
Mono<ValidationResult> result = account.flatMap(a -> Mono.fromFuture(validator.validate(a, tx)));
Key talking point if pushed: the operator-level knowledge (filter/map/reduce/flatMap, sync-transform vs async-chain distinction) transfers directly between RxJava and Reactor — what changes is the type names (Observable→Flux, Single→Mono) and that Reactor is what a Spring WebFlux controller actually returns natively, so in a Spring-first codebase Reactor is the more idiomatic choice over pulling in RxJava as a second reactive library.
