Java Streams — Pipeline, Collectors & Optional

Category: Java · Topic: Streams & Collectors · Est. time: 30 min · Lesson 3 of 3

The Streams API, introduced in Java 8, is a declarative way to process sequences of data. You describe what you want — filter, transform, group, aggregate — and the API handles iteration internally. Streams eliminate most hand-written for-loops, remove mutable accumulators, and make the logic of a data transformation visible in one expression. This lesson also covers Optional, the companion type that replaces nullable returns, and the primitive stream variants that avoid boxing overhead.

1. What Is a Stream?

A Stream<T> is a lazily-evaluated pipeline over a sequence of elements. It is not a data structure — it does not store elements. Intermediate operations describe transformations; nothing executes until a terminal operation is called.

Three parts: source → intermediate operations → terminal operation accounts.stream() // source: Collection .filter(Account::isActive) // intermediate: lazy .map(Account::getBalance) // intermediate: lazy .reduce(BigDecimal.ZERO, // terminal: triggers ONE pass through the data BigDecimal::add);
⛔ Imperative — mutable accumulator, iteration explicit
BigDecimal total = BigDecimal.ZERO;
for (Account account : accounts) {
    if (account.isActive()) {
        total = total.add(
            account.getBalance());
    }
}
// Who owns the loop? Who owns the filter?
// Logic and iteration are tangled.
✅ Stream pipeline — no variables, pure expression
BigDecimal total = accounts.stream()
    .filter(Account::isActive)
    .map(Account::getBalance)
    .reduce(BigDecimal.ZERO,
            BigDecimal::add);
// Read left to right: take accounts,
// keep active ones, get balances, sum them.
// No mutable state, no loop variable.
Streams are single-use Once a terminal operation runs, the stream is consumed and cannot be reused. To process the same data twice, call .stream() on the source again. Attempting to reuse a stream throws IllegalStateException: stream has already been operated upon or closed.

2. Creating Streams

// From a Collection (most common)
List<Bet> bets = betRepository.findAll();
Stream<Bet> stream = bets.stream();

// From an array
String[] currencies = {"GBP", "EUR", "USD"};
Stream<String> currencyStream = Arrays.stream(currencies);

// From known values
Stream<String> statuses =
    Stream.of("PENDING", "APPROVED", "DECLINED");

// Ranges — returns IntStream, not Stream<Integer> (no boxing)
IntStream range     = IntStream.range(0, 100);         // 0..99 (exclusive end)
IntStream inclusive = IntStream.rangeClosed(1, 12);    // 1..12 (months)

// Infinite stream — generate (stateless, each element independent)
Stream<UUID>       ids    = Stream.generate(UUID::randomUUID).limit(10);
Stream<BigDecimal> zeroes = Stream.generate(() -> BigDecimal.ZERO);

// Infinite stream — iterate (each element derived from previous, like a loop)
Stream<Integer> powers  = Stream.iterate(1, x -> x * 2).limit(10); // 1,2,4,8,...
Stream<Long>    seconds = Stream.iterate(0L, n -> n + 1);           // 0,1,2,...

// Java 9+ iterate with predicate (bounded; avoids limit())
Stream<Integer> nTo99 =
    Stream.iterate(0, n -> n < 100, n -> n + 1); // like for(int n=0;n<100;n++)

// Empty stream (useful as a no-op fallback)
Stream<Bet> empty = Stream.empty();

3. Intermediate Operations

Intermediate operations return a new stream. They are lazy — calling them does not process any elements. Processing only happens when a terminal operation pulls elements through the pipeline.

OperationEffectType change
filter(Predicate)Keep elements matching predicateStream<T> → Stream<T>
map(Function)Transform each element T → RStream<T> → Stream<R>
flatMap(Function)Map each element to a stream, flatten all into oneStream<T> → Stream<R>
distinct()Remove duplicates (uses equals/hashCode)Stream<T> → Stream<T>
sorted()Natural order or custom ComparatorStream<T> → Stream<T>
limit(n)Take only the first n elementsStream<T> → Stream<T>
skip(n)Drop the first n elementsStream<T> → Stream<T>
peek(Consumer)Inspect each element without modifying itStream<T> → Stream<T>

filter — keep matching elements

⛔ Imperative
List<Transaction> approved =
    new ArrayList<>();
for (Transaction tx : all) {
    if (tx.getStatus() == APPROVED
            && tx.getAmount()
               .compareTo(BigDecimal
                   .valueOf(100)) > 0) {
        approved.add(tx);
    }
}
✅ filter
List<Transaction> approved = all.stream()
    .filter(tx -> tx.getStatus() == APPROVED)
    .filter(tx -> tx.getAmount()
        .compareTo(BigDecimal.valueOf(100)) > 0)
    .toList();
// Two predicates composed as chained filters
// Each is readable independently

map — transform each element

// Extract one field from each object
List<String> ibans = accounts.stream()
    .map(Account::getIban)        // Account -> String
    .toList();

// Apply a calculation
List<BigDecimal> netPayouts = bets.stream()
    .filter(Bet::isWon)
    .map(bet -> bet.getStake().multiply(bet.getOdds()))
    .toList();

flatMap — flatten nested collections

⛔ Imperative — nested loops
// Each Customer has multiple Accounts
List<Account> all = new ArrayList<>();
for (Customer c : customers) {
    for (Account a : c.getAccounts()) {
        all.add(a);
    }
}
// Two loops, one accumulator
✅ flatMap — one expression
// map would give Stream<List<Account>>
// flatMap flattens to Stream<Account>
List<Account> all = customers.stream()
    .flatMap(c -> c.getAccounts().stream())
    .toList();
// Think: map each to a stream, then flatten
flatMap vs map: the rule If your mapping function returns a Stream (or a Collection you want to treat as one), use flatMap. map gives Stream<List<Account>>. flatMap gives Stream<Account>. It is analogous to Optional.flatMap — both "flatten" a nested container.

distinct, sorted, limit, skip

// distinct — deduplication by equals()/hashCode()
List<String> currencies = transactions.stream()
    .map(Transaction::getCurrency)
    .distinct()        // unique currencies only
    .sorted()          // alphabetical order
    .toList();         // ["EUR", "GBP", "USD"]

// sorted with Comparator
List<Bet> topBets = bets.stream()
    .sorted(Comparator.comparing(Bet::getStake).reversed())
    .limit(10)         // top 10 highest-stake bets
    .toList();

// skip + limit — pagination
int page = 2;
int pageSize = 20;
List<Transaction> page2 = transactions.stream()
    .sorted(Comparator.comparing(Transaction::getTimestamp).reversed())
    .skip((long) page * pageSize)   // skip first 2 pages
    .limit(pageSize)                // take next 20
    .toList();

peek — inspect without modifying

// peek is for debugging mid-pipeline — NOT for side effects in production
List<Bet> result = bets.stream()
    .filter(Bet::isHighValue)
    .peek(bet -> log.debug("high-value: {}", bet.getId())) // log before transform
    .map(riskEngine::assess)
    .peek(bet -> log.debug("after risk: {}", bet.getRiskScore()))
    .filter(bet -> bet.getRiskScore() < 0.9)
    .toList();
peek is for debugging only Never use peek for real side effects (saving, publishing). It may not execute at all — the runtime can optimise away intermediate ops if the terminal doesn't need them. Use forEach for intentional side effects.

4. Terminal Operations

Terminal operations consume the stream and produce a result or side effect. After a terminal operation, the stream is closed. These are the only operations that actually trigger processing.

OperationReturnsUse for
collect(Collector)VariesAccumulate into List, Map, Set, String, etc.
forEach(Consumer)voidSide effects on each element
reduce(identity, BinaryOp)TFold into a single value (sum, product, max)
count()longNumber of elements
min(Comparator)Optional<T>Smallest element
max(Comparator)Optional<T>Largest element
findFirst()Optional<T>First element (respects order)
findAny()Optional<T>Any element (parallel-friendly)
anyMatch(Predicate)booleanShort-circuits on first match
allMatch(Predicate)booleanShort-circuits on first non-match
noneMatch(Predicate)booleanTrue if no element matches
toList() (Java 16+)List<T>Shorthand for collect(Collectors.toUnmodifiableList())

reduce — fold into a single value

⛔ Imperative sum
BigDecimal total = BigDecimal.ZERO;
for (Account account : accounts) {
    if (account.isActive()) {
        total = total.add(
            account.getBalance());
    }
}
✅ reduce
BigDecimal total = accounts.stream()
    .filter(Account::isActive)
    .map(Account::getBalance)
    .reduce(BigDecimal.ZERO,   // identity (start value)
            BigDecimal::add);  // accumulator
// reduce with no identity — returns Optional (empty stream is handled)
Optional<BigDecimal> maxStake = bets.stream()
    .map(Bet::getStake)
    .reduce(BigDecimal::max);

// anyMatch / allMatch / noneMatch — short-circuit early
boolean anyLarge = transactions.stream()
    .anyMatch(tx -> tx.getAmount()
        .compareTo(BigDecimal.valueOf(10_000)) > 0);
// Stops at the first match — never reads the whole list

boolean allSettled = bets.stream()
    .allMatch(bet -> bet.getStatus() == BetStatus.SETTLED);

// count + findFirst
long pending = transactions.stream()
    .filter(tx -> tx.getStatus() == PENDING)
    .count();

Optional<Bet> earliestOpen = bets.stream()
    .filter(bet -> bet.getStatus() == BetStatus.OPEN)
    .min(Comparator.comparing(Bet::getPlacedAt));

5. Collectors Deep-Dive

Collectors is a factory class for the most common accumulation strategies. You pass a Collector to collect() — it defines how elements are folded into a result container.

toList, toSet, toUnmodifiableList

// Java 16+ shorthand — always unmodifiable
List<String> ibans = accounts.stream()
    .map(Account::getIban)
    .toList(); // unmodifiable, null-hostile

// Pre-Java 16 / mutable list needed
List<String> ibans = accounts.stream()
    .map(Account::getIban)
    .collect(Collectors.toList()); // mutable ArrayList

// Set (deduplication)
Set<String> currencies = transactions.stream()
    .map(Transaction::getCurrency)
    .collect(Collectors.toSet());

toMap — key/value pairs, requires unique keys

// Simple: each Account maps to itself by IBAN
Map<String, Account> byIban = accounts.stream()
    .collect(Collectors.toMap(
        Account::getIban,           // key extractor
        Function.identity()         // value extractor (the Account itself)
    ));
// Throws IllegalStateException on duplicate key — fail-fast is intentional

// With merge function — handle duplicates (keep higher balance)
Map<String, BigDecimal> maxBalanceByType = accounts.stream()
    .collect(Collectors.toMap(
        Account::getType,           // key: account type
        Account::getBalance,        // value: balance
        BigDecimal::max             // merge: called when two accounts share a type
    ));

groupingBy — partition into groups

// Basic: Map<K, List<V>>
Map<BetStatus, List<Bet>> betsByStatus = bets.stream()
    .collect(Collectors.groupingBy(Bet::getStatus));
// betsByStatus.get(PENDING) → List of all pending bets

// With downstream collector — count per group
Map<BetStatus, Long> countByStatus = bets.stream()
    .collect(Collectors.groupingBy(
        Bet::getStatus,
        Collectors.counting()
    ));

// Sum stakes per market type
Map<String, BigDecimal> totalStakeByMarket = bets.stream()
    .collect(Collectors.groupingBy(
        Bet::getMarketType,
        Collectors.reducing(
            BigDecimal.ZERO,
            Bet::getStake,
            BigDecimal::add)
    ));

// Nested grouping: first by status, then by market type
Map<BetStatus, Map<String, List<Bet>>> nested = bets.stream()
    .collect(Collectors.groupingBy(
        Bet::getStatus,
        Collectors.groupingBy(Bet::getMarketType)
    ));

partitioningBy — exactly two groups (true/false)

// Split transactions into high-value and normal
Map<Boolean, List<Transaction>> partitioned = transactions.stream()
    .collect(Collectors.partitioningBy(
        tx -> tx.getAmount().compareTo(BigDecimal.valueOf(1000)) > 0
    ));

List<Transaction> highValue = partitioned.get(true);
List<Transaction> normal    = partitioned.get(false);

// With downstream: count each partition
Map<Boolean, Long> counts = bets.stream()
    .collect(Collectors.partitioningBy(
        Bet::isWon,
        Collectors.counting()
    ));
long wonCount  = counts.get(true);
long lostCount = counts.get(false);

joining — concatenate strings

// IBAN list as comma-separated string with brackets
String ibanList = accounts.stream()
    .map(Account::getIban)
    .collect(Collectors.joining(", ", "[", "]"));
// → "[GB29NWBK60161331926819, GB56BARC20031253243859, ...]"

// Audit log line
String betSummary = settledBets.stream()
    .map(b -> b.getId() + ":" + b.getPayout().toPlainString())
    .collect(Collectors.joining(" | "));
// → "bet-001:120.00 | bet-002:45.50 | ..."

counting, summingInt, averagingDouble, summarizingInt

// counting — equivalent to .count() but usable as a downstream collector
long total = bets.stream()
    .collect(Collectors.counting());

// summingInt
int totalOddsNumerator = bets.stream()
    .collect(Collectors.summingInt(Bet::getOddsNumerator));

// averagingDouble
double avgStake = bets.stream()
    .collect(Collectors.averagingDouble(
        bet -> bet.getStake().doubleValue()));

// summarizingInt — count + sum + min + max + average in ONE pass
IntSummaryStatistics stakeStats = bets.stream()
    .collect(Collectors.summarizingInt(
        bet -> bet.getStake().intValue()));

stakeStats.getCount();    // number of bets
stakeStats.getSum();      // total stakes (pence)
stakeStats.getMin();      // smallest stake
stakeStats.getMax();      // largest stake
stakeStats.getAverage();  // mean stake

6. Optional — Eliminating Null Checks

Optional<T> is a container that either holds a value or is empty. It makes nullable returns explicit in method signatures and forces callers to decide what to do when no value is present — instead of crashing with NullPointerException.

// Creating
Optional<Account> found    = accountRepo.findById(id); // repo returns Optional
Optional<Account> present  = Optional.of(account);      // throws NPE if account is null
Optional<Account> nullable = Optional.ofNullable(maybeNull); // empty if null
Optional<Account> empty    = Optional.empty();
Anti-pattern: isPresent() + get() — just use orElse // WRONG — defeats the purpose of Optional if (found.isPresent()) { return found.get().getBalance(); } // RIGHT — declarative chain return found.map(Account::getBalance).orElse(BigDecimal.ZERO); 
// map — transform the value if present
BigDecimal balance = accountRepo.findById(id)
    .map(Account::getBalance)         // Optional<Account> -> Optional<BigDecimal>
    .orElse(BigDecimal.ZERO);         // default if empty

// orElseGet — lazy supplier, only called when empty
Account account = accountRepo.findById(id)
    .orElseGet(() -> createGuestAccount()); // expensive call deferred

// orElseThrow — throw a specific exception if empty
Account account = accountRepo.findById(id)
    .orElseThrow(() -> new AccountNotFoundException(id));

// filter — empty the Optional if condition fails
Optional<Account> activeWithBalance = accountRepo.findById(id)
    .filter(Account::isActive)
    .filter(a -> a.getBalance().compareTo(BigDecimal.ZERO) > 0);

// flatMap — when map would produce Optional<Optional<T>>
// getPrimaryAddress() returns Optional<Address>
Optional<String> city = accountRepo.findById(id)
    .flatMap(Account::getPrimaryAddress) // flatMap: no double-wrapping
    .map(Address::getCity);

// ifPresent — side effect when present, nothing when empty
accountRepo.findById(id)
    .ifPresent(acct -> auditLog.recordAccess(acct.getId()));

// ifPresentOrElse (Java 9+) — both branches in one call
accountRepo.findById(id)
    .ifPresentOrElse(
        acct -> auditLog.recordAccess(acct.getId()),
        ()   -> log.warn("Account not found: {}", id)
    );

// or (Java 9+) — provide an alternative Optional when empty
Optional<Account> result = primaryRepo.findById(id)
    .or(() -> archiveRepo.findById(id)); // fallback to archive
MethodInput typeUse for
map(Function)T → RTransform value, stay in Optional
flatMap(Function)T → Optional<R>Chain methods that return Optional
filter(Predicate)T → booleanDiscard if condition fails
orElse(T)default valueEager default (always evaluated)
orElseGet(Supplier)() → TLazy default (only if empty)
orElseThrow(Supplier)() → ExceptionMandatory value, fail fast
ifPresent(Consumer)T → voidSide effect when present
ifPresentOrElseConsumer + RunnableBoth branches explicit (Java 9+)
Optional rules Never use Optional as a field type (not serialisable). Never use Optional as a method parameter (forces callers to wrap). Never use Optional for collection returns (return empty collection instead). Only use Optional as a method return type to signal that the result may be absent.

7. Primitive Streams — Avoiding Boxing Overhead

For numeric work, Stream<Integer> boxes each int into an Integer object. On millions of elements, that creates millions of short-lived objects and GC pressure. IntStream, LongStream, and DoubleStream work directly with primitives — no boxing, and they carry built-in aggregate methods.

// Creating primitive streams
IntStream ages   = IntStream.of(25, 30, 45, 22);
IntStream range  = IntStream.range(1, 13);       // months 1..12
LongStream ids   = LongStream.rangeClosed(1L, 1_000_000L);

// Convert from object stream — mapToInt avoids autoboxing
IntStream stakePennies = bets.stream()
    .mapToInt(bet -> bet.getStake()
        .multiply(BigDecimal.valueOf(100)).intValue());

// Aggregate operations available directly (no Collectors needed)
int  totalPennies = stakePennies.sum();          // sum
long betCount     = bets.stream()
    .mapToLong(bet -> 1L).sum();                 // count via sum
OptionalDouble avg = IntStream.range(1, 100).average();
OptionalInt    max = IntStream.of(10, 30, 20).max();
IntSummaryStatistics stats = IntStream.of(10, 30, 20).summaryStatistics();

// DoubleStream for odds / probabilities
DoubleStream odds = DoubleStream.of(1.5, 2.0, 3.75, 1.1);
double impliedProbSum = odds.map(o -> 1.0 / o).sum();
// If > 1.0 it is the bookmaker overround (margin)

// mapToObj — back to object stream
Stream<String> labels = IntStream.rangeClosed(1, 5)
    .mapToObj(n -> "Round " + n);  // "Round 1" .. "Round 5"

// boxed() — back to Stream<Integer>
List<Integer> list = IntStream.range(0, 5).boxed().toList();
LongStream for IDs and epoch timestamps Use LongStream when working with IDs, epoch millis, or any counter where int overflows are possible. Snowflake IDs, Unix timestamps, sequence numbers — all require long. A Stream<Long> adds boxing overhead; LongStream does not.

8. Parallel Streams

Parallel streams split the data across multiple threads in ForkJoinPool.commonPool(). You get parallelism in one method call. The catch: it is only faster for the right workloads, and it is actively harmful for the wrong ones.

// Enable parallelism with one call
List<RiskDecision> decisions = bets.parallelStream()
    .map(riskEngine::evaluate)   // runs on ForkJoinPool threads
    .toList();

// Or from a sequential stream
List<RiskDecision> decisions = bets.stream()
    .parallel()
    .map(riskEngine::evaluate)
    .toList();
Use parallel when…Avoid parallel when…
Data set is large (> ~10,000 elements)List is small — thread overhead exceeds gain
Each element operation is CPU-bound and expensiveEach operation is I/O-bound (use CompletableFuture instead)
Operations are stateless (no shared state)Operations share mutable state (race conditions)
Element order in result does not matterOrdered output required — use forEachOrdered or collect then sort
No external side effects per elementOperations add to a shared list — use collect() instead
Race condition with parallelStream() + ArrayList 
// BAD — ArrayList is not thread-safe
List<RiskDecision> results = new ArrayList<>();
bets.parallelStream()
    .map(riskEngine::evaluate)
    .forEach(results::add);  // multiple threads calling add() concurrently
                              // ConcurrentModificationException or silent data loss

// GOOD — let collect() handle thread-safe accumulation
List<RiskDecision> results = bets.parallelStream()
    .map(riskEngine::evaluate)
    .collect(Collectors.toList()); // Collectors are thread-safe internally
// Parallel + CPU-bound: risk scoring a large batch (good use case)
List<ScoredBet> scored = largeBetList.parallelStream()
    .map(riskEngine::scoreWithMachineLearning) // expensive CPU work
    .sorted(Comparator.comparing(ScoredBet::getScore).reversed())
    .limit(100)
    .toList();

// For I/O bound work: use CompletableFuture, not parallelStream
// parallelStream blocks ForkJoinPool threads on I/O — wrong tool
List<PriceDto> prices = marketIds.stream()
    .map(id -> CompletableFuture.supplyAsync(
        () -> priceService.getPrice(id), ioExecutor))
    .toList()
    .stream()
    .map(CompletableFuture::join)
    .toList();

Quiz

Q1. When does the Java Streams pipeline actually process elements?

  • When stream() is called on the collection — the pipeline starts immediately
  • When a terminal operation is called — intermediate ops are lazy and only described, not executed, until then
  • When filter() is called — it is the first operation that touches elements
  • Elements are processed continuously as intermediate ops are chained
Streams use lazy evaluation. Calling filter() or map() does not process any elements — it builds a pipeline description. Processing happens in a single pass only when a terminal operation (collect, reduce, forEach, count, etc.) is invoked. This allows optimisations like short-circuiting: anyMatch stops at the first match without reading the rest of the stream.

Q2. You have Stream<Customer> where each Customer has a List<Account>. Which operation produces a single Stream<Account> from all customers?

  • .map(Customer::getAccounts) — transforms each customer into its account list
  • .filter(c -> !c.getAccounts().isEmpty()) — removes customers with no accounts
  • .flatMap(c -> c.getAccounts().stream()) — maps each customer to a stream of accounts then flattens all into one
  • .reduce(Stream.empty(), Stream::concat, Stream::concat)
flatMap applies a function that returns a Stream and then flattens all the resulting streams into one. map(Customer::getAccounts) would give Stream<List<Account>> — one list per customer, still nested. flatMap(c -> c.getAccounts().stream()) gives Stream<Account> — all accounts in one flat sequence.

Q3. What type does bets.stream().collect(Collectors.groupingBy(Bet::getStatus)) return?

  • Map<BetStatus, List<Bet>> — each status maps to the list of bets with that status
  • Map<BetStatus, Bet> — each status maps to a single representative Bet
  • List<BetStatus> — the distinct statuses found in the stream
  • Map<String, List<Bet>> — status toString() is used as the key
Collectors.groupingBy(classifier) returns a Map<K, List<V>> where K is the classifier's return type and List holds all elements that produced that key. Here K is BetStatus (return type of Bet::getStatus), so the result is Map<BetStatus, List<Bet>>. The enum itself is used as the key — not its toString().

Q4. What happens when you call Optional.of(null)?

  • Returns an empty Optional — of() treats null as absent
  • Throws NullPointerException immediately — of() requires a non-null value
  • Returns Optional.empty() silently after logging a warning
  • Throws IllegalArgumentException — null is not a valid Optional value
Optional.of(T value) requires a non-null argument and throws NullPointerException immediately if null is passed. Use Optional.ofNullable(T value) to safely wrap a potentially null value — it returns Optional.empty() for null inputs. The distinction enforces that of() is for values you know are non-null; ofNullable() is for uncertain ones.

Q5. You have Stream<Bet> and want to sum the stakes as primitive int values, avoiding autoboxing. Which is correct?

  • bets.stream().mapToInt(bet -> bet.getStake().intValue()).sum() — converts to IntStream, no boxing, sum() available directly
  • bets.stream().map(Bet::getStake).sum() — sum() is available on Stream<BigDecimal>
  • bets.stream().toIntStream(Bet::getStake).sum() — toIntStream() is the correct conversion method
  • bets.stream().collect(Collectors.summingInt()) — summingInt() needs no argument
mapToInt(ToIntFunction) converts a Stream<T> to IntStream, which holds primitives — no autoboxing. IntStream has sum(), average(), min(), max(), and summaryStatistics() directly. Stream<T> has none of these — you'd need Collectors.summingInt() which requires the function argument. toIntStream() does not exist.

Q6. Which thread pool does parallelStream() use by default?

  • A dedicated parallel pool sized to the number of parallel stream operations currently active
  • The main application thread, blocking until all parallel tasks complete
  • ForkJoinPool.commonPool() — a shared pool sized to available CPU cores minus one
  • Executors.newCachedThreadPool() — an unbounded thread pool managed by the JVM
parallelStream() uses ForkJoinPool.commonPool() by default. This pool is shared across the entire JVM and sized to Runtime.getRuntime().availableProcessors() - 1. On a 2-vCPU instance (e.g. t3.small) that is 1 thread — minimal parallelism. Consequence: a slow parallel stream operation can starve other parallel work in the same JVM (e.g. completable future chains also using the common pool). For production use, pass a custom ForkJoinPool if you need isolation.
