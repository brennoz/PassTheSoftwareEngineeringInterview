How this maps to the real exercise format

NatWest's own description: you're handed a project with some existing basic code and asked to add functionality, finish it, and make tests pass. That's not quite blank-slate (this practice exercise) and not quite the course's usual full-skeleton — it's "read someone else's partial code, understand its shape, extend it." The skill that actually transfers from this practice isn't the specific class names here — it's TDD discipline under time pressure and a coherent object model. Read the code in solution/ once cold, as if you'd just opened it in an unfamiliar IDE, before reading the explanations below — that's the closer rehearsal.

The object model

Book (record) — isbn, title, author. Immutable value, no identity beyond its data. BookCopy — ONE physical copy. Owns its own availability + lock. Several BookCopy instances can share the same isbn. Member — owns its own borrowed-copy list (information-expert). Library (orchestrator) — coordinates the above + AuditTrail. Holds NO business state of its own beyond the catalog/copies/members maps. AuditTrail (interface) — side-effect seam. InMemoryAuditTrail is the real implementation.
SAY THISAvailability lives on BookCopy, not Book — a library can hold several physical copies of the same title, and each copy is independently on the shelf or on loan. Putting a mutable flag on Book would conflate "what the book is" with "where a specific copy currently is."

Why Library is thin

Library doesn't hold "is this copy available" or "what has this member borrowed" as its own fields — it asks BookCopy and Member, who own that state. This is the same information-expert principle this course's other OOD questions push (see topics/ood/) — and it's precisely what let the Part B lock get added to BookCopy alone, with zero changes to Library.borrowBook()'s logic.

Why author is a single String — and where that stops being true

Book.author() is one String, not a list, not a domain type. That's a real simplification — plenty of books have co-authors — kept deliberately, because nothing in this exercise ever queries, sorts, or filters by author. Worth being ready to walk through the two escalation steps live, rather than defending the String as permanently correct:

ModelWhat it buys youWhat triggers reaching for it

List<String> authorsCorrectly represents multiplicity — a book CAN have 2+ authors — without inventing identity or behavior nothing needs yet.The moment a co-authored book is a real input the system must accept, even if nothing queries by author individually.

Rowling" and "JK Rowling" silently fail to match as the same person with strings, but an Author entity with its own id does not have that problem. Once that query exists, Library would also need an author index (e.g. Map<AuthorId, List<Book>>) to answer it without scanning the whole catalog.
The interview-ready answer if pushed: "I kept author as a single String because nothing here needs multiplicity or identity yet. If co-authored books were a real input, I'd widen it to List<String> — that's a data-shape fix, not a new concept. I'd only promote to a full Author entity once there's an actual query or behavior that needs author identity, like 'list all books by this author' — at that point a plain string can't reliably tell two authors apart from a typo, and that's the real trigger, not just 'authors are a thing in the domain.'"

TDD order — six tests, in the order they were written

The order is itself a signal graders look for — not just "are there tests." Each test below only makes sense once the previous one's model exists.

1borrowing an available copy marks it unavailable
The simplest possible case. Forces the core decision immediately: borrowBook must return the BookCopy (not void, not a boolean) — later tests and Part B's race need to know which copy was actually lent.
2borrowing with zero available copies throws
Needs Test 1's model to exist first — "no copies available" only means something once "a copy can become unavailable" is implemented. Zero copies is the simplest way to set up the precondition.
3returning a borrowed copy makes it available again
The round trip — only testable once borrow works, since you need a borrowed copy to return.
4returning a copy never borrowed throws
The "real use / user journey" case rejected-candidate feedback explicitly flags as often missed — without this, returnBook would silently free up someone else's book on a typo'd copy id.
5borrowing records an audit event (Mockito @Spy)
Layered on AFTER the core flow is proven — auditing a broken borrow flow tests the wrong thing. See the spy section below for why this is a spy, not a mock.
6(Part B) exactly one concurrent borrower wins the last copy
Only makes sense once single-threaded correctness is solid. Against a naive/unlocked BookCopy this test is flaky, not reliably red — worth saying out loud live, since that's exactly what makes race-condition bugs dangerous in production: they don't fail every run.

The race condition, and why the lock goes where it goes

The naive implementation of "borrow if available" is two separate statements:

if (status == CopyStatus.AVAILABLE) {
    status = CopyStatus.BORROWED;
    return true;
}
return false;
The race: two threads can both execute the if (status == AVAILABLE) check and both see true, BEFORE either one reaches status = BORROWED. Both threads then proceed to "successfully" borrow the same physical copy. This is a classic check-then-act race — the exact same shape as the account-balance race in Ex1's ThreadSafeLedger. (The field started as a plain boolean available and was swapped for a CopyStatus enum — see below — but the race is identical either way; a boolean and a two-value enum are the same bug wearing different clothes.)
SAY THISFold the check AND the flip into one atomic operation, under a lock owned by the specific BookCopy — not a library-wide lock, which would serialize borrowing of completely unrelated books for no reason. 
// BookCopy.tryBorrow() — check-and-flip as ONE atomic step under this copy's own lock
public boolean tryBorrow() {
    lock.lock();
    try {
        if (status != CopyStatus.AVAILABLE) return false;
        status = CopyStatus.BORROWED;
        return true;
    } finally { lock.unlock(); }
}
Why an enum here, not a plain boolean or a full State pattern: a boolean available works but reads poorly at call sites (if (!available) vs if (status != AVAILABLE)) and can't grow past two values. A full GoF State pattern (separate AvailableState/BorrowedState classes, each implementing borrow()/returnCopy()) would be premature — both states do the exact same lock-then-transition, no per-state behavior diverges. CopyStatus is the right-sized middle ground: readable, and a natural seed for a third value (RESERVED, LOST) later, without committing to a class hierarchy until behavior — not just the label — actually diverges per state.

Why a lock per copy, not a single lock on Library: a library-wide lock would make borrowing "Effective Java" block someone borrowing "Clean Code" at the same instant, even though they touch completely unrelated state — correct, but needlessly slow. Locking at the smallest scope that actually needs protecting (one physical copy's availability) is the same principle as Ex1's per-account locks, not one lock for the whole ledger.

Mockito: spy vs mock vs fake

BehaviourWhen to reach for it here
@MockEvery method no-ops / returns null unless stubbedYou only care THAT a call happened, not what real storage would do — would need when(mock.allEvents()).thenReturn(...) stubbed by hand to fake "it actually stored the event," which is testing your stub, not your code.
@SpyReal object, real methods run, unless individually overriddenWhat Test 5 uses. InMemoryAuditTrail's real record()/allEvents() genuinely run — the test verifies both the interaction (verify(auditTrail).record(...)) AND that the resulting state is actually correct (allEvents() really contains the event), from one object.
Hand-written fakeA second, simplified real implementation you write yourselfReasonable alternative to a spy for this exact case — but Mockito's spy gets you the same real-behaviour guarantee AND `verify()`'s interaction-checking for free, without writing and maintaining a second implementation.
Interview framing if pushed on this: "spy wraps a real instance so its real code runs — I use it when I want to assert on both what actually happened to the object's state, and that a specific method was called, in one test. A mock is for when I only care about the interaction, and don't want the collaborator's real logic running at all (e.g. it would hit a real database or a real external API)."

What the rejected-candidate feedback actually maps to

Feedback quoteWhat this exercise rehearses against it
"rusty in the IDE... lots of problems with setup"Not something a doc fixes — practice this exercise IN IntelliJ, from a truly blank file, timed.
"no coherent approach to the model"The five-class split (Book/BookCopy/Member/Library/AuditTrail) — each with ONE reason to change — is the coherent-model answer. Cramming borrow/return/availability/audit into one Library class is the incoherent one.
"not really test focussed enough... where to put the logic"The TDD-order table above — tests aren't an afterthought bolted on at the end, each one drives the next design decision.
"lack of forethought to how the implementation would stand up to real use"Test 4 (returning a copy you never borrowed) and Part B (the concurrent race) are exactly this — going one step past "the given tests pass" to "what breaks this in practice."
"didn't consider how the solution would fit together as a user journey"Walk the interviewer through register → borrow → (attempt to borrow when unavailable) → return → (attempt to return twice) as one continuous story, not four disconnected methods.
