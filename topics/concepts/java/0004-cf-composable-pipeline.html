CompletableFuture — Composable Async Pipeline

Category: Java · Topic: Async programming · Lesson 4 of 4

This lesson answers one specific question that trips up many developers: why return CompletableFuture<T> from a service instead of blocking inside and returning T directly? The short answer is delegation — the service should not decide when to block. Different callers have different strategies.

1. Return the Promise — Don't Cash It In

A CompletableFuture<T> is a promise of a future result. When a service method returns a CF instead of blocking, it hands the promise to the caller. The caller then decides what to do with it: block, chain further, combine with other CFs, or never block at all.

BAD — service blocks itself (wrong) 
// Service collapses the CF internally. Caller has no choice.
@Service
public class SubscriptionService {
    public EnrichedSubscription enrich(String id) {
        Subscription sub = subscriptionRepo.findById(id).get();    // thread BLOCKS here
        Account acc      = accountRepo.findById(sub.accountId()).get(); // thread BLOCKS again
        return new EnrichedSubscription(sub, acc);
    }
}
GOOD — service returns CF (caller decides) 
// Service returns a promise. No blocking anywhere inside.
@Service
public class SubscriptionService {
    public CompletableFuture<EnrichedSubscription> enrich(String id) {
        return subscriptionRepo.findById(id)          // CF<Subscription>
            .thenApply(pricingService::applyDiscount)  // sync transform, no IO
            .thenCompose(d ->
                accountRepo.findById(d.accountId())    // CF<Account>
                    .thenApply(acc -> new EnrichedSubscription(d, acc))
            );
        // No .get() anywhere — promise returned to caller
    }
}

2. What Happens to the Calling Thread

When a Spring MVC controller handles an HTTP request, Tomcat assigns a thread from its pool (default: 200 threads). That thread runs your controller → service → returns response. If the service blocks internally, that Tomcat thread is pinned — sleeping while waiting for a DB or HTTP response — unable to serve other requests.

Without CF (blocking): Tomcat thread ──── controller ──── service.enrich() ───┐ │ SLEEPING 50ms (DB call) │ SLEEPING 30ms (DB call) └──── response Thread is pinned for 80ms. On 200 threads → 200 concurrent requests max. With CF (non-blocking, Spring MVC): Tomcat thread ──── controller ──── service.enrich() ──── .get() ──┐ returns CF immediately │ waits at edge Virtual threads run DB calls concurrently │ Tomcat thread resumes when CF completes ◄───────────────────────────┘

In standard Spring MVC the Tomcat thread still blocks at the edge (the controller's .get()), but the work inside the service is now parallelisable. The real non-blocking story comes with WebFlux — covered in section 4.

3. Three Callers — Three Strategies

The same service method enrich(String id) returning CompletableFuture<EnrichedSubscription> can be called from three different contexts, each handling the CF differently.

Strategy A — Spring MVC controller (block once at the HTTP edge) Spring MVC

@RestController
public class SubscriptionController {

    @GetMapping("/subscriptions/{id}/enriched")
    public EnrichedSubscription enrich(@PathVariable String id)
            throws ExecutionException, InterruptedException, TimeoutException {

        // Block ONCE at the HTTP boundary — not deep inside the service
        // If you later want a timeout, change this one line only
        return subscriptionService.enrich(id).get(500, TimeUnit.MILLISECONDS);
    }
}

// If blocking were inside the service, you'd have to dig through
// business logic to add or change a timeout. Here it is one call.
Idiom: block at the boundary, not inside the domain The service has zero knowledge of HTTP, timeout policies, or SLAs. The controller owns those decisions. This keeps services reusable across different callers with different timeout requirements.

Strategy B — WebFlux reactive controller (never blocks) WebFlux

@RestController
public class SubscriptionController {

    @GetMapping("/subscriptions/{id}/enriched")
    public Mono<EnrichedSubscription> enrich(@PathVariable String id) {
        // Mono.fromFuture wraps the CF — no .get() anywhere
        // Netty event loop never blocks; response is sent when CF completes
        return Mono.fromFuture(subscriptionService.enrich(id));
    }
}

// Same service method. Zero code change in SubscriptionService.
// WebFlux handles 10k concurrent requests on ~10 threads because no thread
// ever sits idle waiting for a CF — they return to the event loop immediately.
Why this scales Netty's event loop threads never block. When Mono.fromFuture(cf) is returned, Netty registers a callback on the CF. The thread is immediately free to accept another request. When the CF completes, the callback fires and Netty writes the response. 10k open connections, 10 threads — possible because no thread sleeps.

Strategy C — Kafka consumer (block before offset commit) Kafka

// Kafka consumer: must finish all async work BEFORE committing the offset
// If we return without joining, the offset commits but the work might still fail
@KafkaListener(topics = "subscriptions.events")
public void onSubscriptionCreated(SubscriptionCreatedEvent event) {

    // Fan out to two independent services in parallel
    CompletableFuture<EnrichedSubscription> enrichCf =
        subscriptionService.enrich(event.getSubscriptionId());

    CompletableFuture<Void> auditCf = CompletableFuture.runAsync(
        () -> auditService.recordCreation(event), ioExecutor
    );

    // Block until both complete — BEFORE Kafka commits the offset
    // If either fails, exception propagates, offset is NOT committed,
    // Kafka retries the message — at-least-once delivery preserved.
    CompletableFuture.allOf(enrichCf, auditCf)
        .exceptionally(ex -> {
            log.error("Processing failed for subscriptionId={}",
                event.getSubscriptionId(), ex);
            throw new RuntimeException(ex); // forces offset NOT to commit
        })
        .join(); // block here — this is intentional in a Kafka consumer
}
Kafka consumers must join before returning If you fire async work but return from the listener method without joining, Kafka commits the offset assuming success. If the async work later fails, the message is lost — no retry. In Kafka consumers, always .join() at the end of the listener method. This is the one place where blocking intentionally is correct.

4. Sequential Chain vs Parallel Fan-out

Two different CF shapes exist. Knowing which to use is key to getting the performance benefit.

Sequential chain — result of A feeds into B

Use when the second call depends on data from the first. No parallelism possible — and that is correct. thenCompose is the tool.

// q001 pattern: account fetch needs accountId from the subscription
public CompletableFuture<EnrichedSubscription> enrich(String subscriptionId) {
    return subscriptionService.findById(subscriptionId)   // 1. fetch subscription
        .thenApply(pricingService::applyDiscount)          // 2. apply discount (sync)
        .thenCompose(discounted ->
            accountService.findById(discounted.accountId()) // 3. fetch account (needs accountId from step 2)
                .thenApply(account -> new EnrichedSubscription(discounted, account))
        );
}
// Total time: t(subscription) + t(account) — sequential, unavoidable here
// CF still adds value: non-blocking, composable, timeout-friendly

Parallel fan-out — A, B, C are independent

Use when all calls can start simultaneously. allOf is the tool. This is where CF delivers real latency savings.

// q002 pattern: subscription, billing address, and payment method are independent
public CompletableFuture<Invoice> buildInvoice(String subscriptionId, String accountId) {
    // All three start at the same instant
    CompletableFuture<Subscription> subCf = subscriptionService.getSubscription(subscriptionId)
        .completeOnTimeout(Subscription.empty(), timeoutMs, MILLISECONDS)
        .exceptionally(ex -> Subscription.empty());   // broken service → fallback

    CompletableFuture<BillingAddress> addrCf = billingAddressService.getBillingAddress(accountId)
        .completeOnTimeout(BillingAddress.unknown(), timeoutMs, MILLISECONDS)
        .exceptionally(ex -> BillingAddress.unknown());

    CompletableFuture<PaymentMethod> pmCf = paymentMethodService.getDefaultPaymentMethod(accountId)
        .completeOnTimeout(PaymentMethod.unknown(), timeoutMs, MILLISECONDS)
        .exceptionally(ex -> PaymentMethod.unknown());

    // allOf waits for all three — total time = max(t_sub, t_addr, t_pm)
    return CompletableFuture.allOf(subCf, addrCf, pmCf)
        .thenApply(ignored -> new Invoice(subCf.join(), addrCf.join(), pmCf.join()));
}
// Sequential equivalent: t_sub + t_addr + t_pm = e.g. 20+30+15 = 65ms
// Parallel with allOf:  max(20, 30, 15) = 30ms — 2× faster, same code complexity

5. The Double-Safety Pattern — completeOnTimeout + exceptionally

These two methods handle completely different failure modes. Combined, they cover every way a remote service can fail.

Failure modeWhat happensWhich method fires
Slow service (no response in time)CF is still pending after deadlinecompleteOnTimeout
Broken service (throws exception)CF completes exceptionally before deadlineexceptionally
Fast successCF completes normally before deadlineNeither — result passes through
 
// Double-safety: chain order matters
// completeOnTimeout MUST come before exceptionally
CompletableFuture<BillingAddress> addrCf = billingAddressService.getBillingAddress(accountId)
    .completeOnTimeout(BillingAddress.unknown(), 200, MILLISECONDS)
    // ↑ slow service: CF still pending at 200ms → complete with fallback (normal completion)
    .exceptionally(ex -> BillingAddress.unknown());
    // ↑ broken service: CF completed exceptionally (e.g. network error) → catch, return fallback

// WHY order matters:
// completeOnTimeout on a CF that ALREADY completed exceptionally is a no-op.
// So: broken service fires before 200ms → completeOnTimeout is ignored → exceptionally fires.
// Slow service still pending at 200ms → completeOnTimeout fires (normal completion) →
//   exceptionally does NOT fire (result is now normal, not exceptional).

// Testing the two paths separately (Mockito):
// Path 1 — slow service (never-completing CF):
when(service.get()).thenReturn(new CompletableFuture<>()); // pending forever → completeOnTimeout fires

// Path 2 — broken service (immediately failed CF):
when(service.get()).thenReturn(CompletableFuture.failedFuture(new RuntimeException("down")));
// completes exceptionally before timeout → exceptionally fires

6. Composability Across Layers

The real power of returning CF from services emerges when services call each other. Each layer composes the promise without blocking. Only the outermost caller (HTTP edge, Kafka listener) decides when to collect.

// Three service layers — each returns CF, none blocks internally

// Layer 3: data access
@Service
public class SubscriptionRepository {
    private final ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor();

    public CompletableFuture<Subscription> findById(String id) {
        return CompletableFuture.supplyAsync(() -> jdbc.queryForObject(...), exec);
    }
}

// Layer 2: domain service — composes layer 3, adds business logic
@Service
public class SubscriptionService {
    public CompletableFuture<EnrichedSubscription> enrich(String id) {
        return subscriptionRepository.findById(id)   // CF from layer 3
            .thenApply(pricingService::applyDiscount)
            .thenCompose(d -> accountRepository.findById(d.accountId())
                .thenApply(acc -> new EnrichedSubscription(d, acc)));
    }
}

// Layer 1: controller — only place that blocks (or doesn't, in WebFlux)
@RestController
public class SubscriptionController {
    // Spring MVC: block once at edge
    @GetMapping("/subscriptions/{id}/enriched")
    public EnrichedSubscription get(@PathVariable String id) throws Exception {
        return subscriptionService.enrich(id).get(500, MILLISECONDS);
    }

    // WebFlux: never block — wrap CF in Mono
    @GetMapping("/subscriptions/{id}/enriched")
    public Mono<EnrichedSubscription> get(@PathVariable String id) {
        return Mono.fromFuture(subscriptionService.enrich(id));
    }
}
Mental model CF flows upward through layers like a baton. Each layer can transform it (thenApply), chain more async work (thenCompose), or combine it with others (thenCombine, allOf). The baton is only "opened" (blocked on) at the top — the HTTP edge or message consumer. Deep inside the domain, no thread ever sleeps waiting for I/O.

7. Spring @Async — CF Without Explicit Executor

Spring can manage the executor for you via @Async. The method runs on Spring's configured executor, and the calling thread returns immediately with a CF.

// Config: replace default SimpleAsyncTaskExecutor with virtual threads
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean(name = "virtualThreadExecutor")
    public Executor taskExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor(); // Java 21
    }
}

// Service: annotated method runs on the executor, returns CF to caller
@Service
public class SubscriptionServiceImpl implements SubscriptionService {

    @Async("virtualThreadExecutor")
    @Override
    public CompletableFuture<Subscription> findById(String id) {
        // This method body runs on a virtual thread, not the caller's thread
        Subscription sub = jdbc.queryForObject(...); // blocking JDBC — OK, virtual thread
        return CompletableFuture.completedFuture(sub);
    }
}

// Caller: does not need to pass an executor — Spring handles it
subscriptionService.findById("sub-1")
    .thenApply(pricingService::applyDiscount)
    .thenCompose(d -> accountService.findById(d.accountId())
        .thenApply(acc -> new EnrichedSubscription(d, acc)));

// Spring AOP wraps the @Async method:
// 1. Caller invokes findById() on the proxy
// 2. Proxy submits the real method body to virtualThreadExecutor
// 3. Caller gets a CF back immediately
// 4. CF completes when the virtual thread finishes the JDBC call
@Async pitfall: self-invocation Calling this.findById() from inside the same bean bypasses Spring's proxy — the method runs on the caller's thread, not the executor. Always inject the service and call through the injected reference, not this.

Quiz

Q1. A service method currently does Subscription sub = repo.findById(id).get(); inside its body and returns EnrichedSubscription. A teammate suggests changing it to return CompletableFuture<EnrichedSubscription> and removing the inner .get(). The REST controller would then call .get(500, MILLISECONDS). What is the main benefit of this change?

  • The DB query now runs faster because CompletableFuture uses a faster JDBC driver internally
  • The calling code (controller) now owns the decision of when and how long to block. The service becomes reusable by callers with different timeout policies — a Kafka consumer, a WebFlux controller, or a batch job — without changing the service. The controller can add or change a timeout in one line instead of modifying business logic.
  • The change eliminates all thread blocking in the application — no thread ever waits after this change
  • The DB query now runs in parallel with the pricing calculation automatically
The benefit is delegation of the blocking decision, not eliminating it. In Spring MVC the controller's .get() still blocks a Tomcat thread — but that's the correct boundary. The service is now usable by WebFlux (Mono.fromFuture — no block at all) or Kafka (join before offset commit) without any changes to the service. Option D is wrong: the CF chain in this example is sequential (account fetch depends on subscription result), so no parallelism is gained — but the composability benefit is still real.

Q2. You have this code: service.getBillingAddress(id).completeOnTimeout(BillingAddress.unknown(), 200, MILLISECONDS).exceptionally(ex -> BillingAddress.unknown()). The address service immediately throws a RuntimeException (response time: 5ms). Which method fires?

  • completeOnTimeout fires because it is declared first in the chain
  • Both fire: completeOnTimeout provides the fallback, then exceptionally transforms it again
  • exceptionally fires. The service threw at 5ms — the CF completed exceptionally before the 200ms deadline. completeOnTimeout only fires when the CF is still pending at deadline; a CF that already completed (even exceptionally) is unaffected by completeOnTimeout. exceptionally catches the exception and returns the fallback.
  • Neither fires — the chain re-throws the RuntimeException to the caller
completeOnTimeout checks: "is this CF still pending after 200ms?" If the CF already completed (normally or exceptionally) before 200ms, completeOnTimeout is a no-op. The CF completed exceptionally at 5ms, so completeOnTimeout does nothing. exceptionally then fires because the CF is in a failed state. This is the key distinction: completeOnTimeout = slow services (timeout), exceptionally = broken services (errors). Together they cover all failure modes.

Q3. A WebFlux controller method returns Mono.fromFuture(subscriptionService.enrich(id)). The service internally uses supplyAsync with a virtual thread executor and chains thenApply / thenCompose. The request arrives on Netty's event loop thread. Is that event loop thread ever blocked while the DB calls run?

  • No. The event loop thread returns the Mono to Netty immediately. Netty registers a callback on the CF. The DB calls run on virtual threads (the executor passed to supplyAsync). When the CF completes, Netty's event loop picks it up and writes the HTTP response — the event loop thread was never sleeping. This is how WebFlux serves thousands of concurrent requests on a small thread pool.
  • Yes. Mono.fromFuture calls CompletableFuture.get() internally to bridge the two async models, which blocks the event loop
  • No, but only because virtual threads eliminate all blocking — the same result would occur with a fixed thread pool
  • Yes. Netty's event loop must hold an OS thread open for each pending Mono until it completes
Mono.fromFuture subscribes to the CF's completion callback — it does NOT call get() or join(). The Netty event loop thread sets up the subscription and immediately returns to accept more connections. Option C is incorrect: virtual threads eliminate blocking from OS thread pinning, but the event loop is never blocked regardless — that is a property of the reactive model (Mono/CF callbacks), not of virtual threads. Virtual threads benefit the executor doing the DB calls, not the event loop.

Q4. A Kafka listener calls subscriptionService.enrich(event.getSubscriptionId()) and returns immediately without calling .join() or .get(). The CF is still running when the listener returns. What is the consequence?

  • Kafka suspends the consumer partition until the CF completes, then commits the offset
  • Kafka commits the offset immediately when the listener method returns (before the CF completes). If the CF later fails, the message is lost — Kafka has no knowledge of the outstanding CF. The failure produces no retry. To preserve at-least-once delivery, always call .join() (or CompletableFuture.allOf(...).join()) at the end of a Kafka listener, so the offset is only committed after all async work succeeds.
  • Kafka retries the message automatically after detecting the CF was not awaited
  • The listener thread blocks in the background until the CF completes, then Kafka commits the offset
Kafka's offset commit is tied to the listener method's return, not to any CF running in background threads. Kafka has no awareness of CompletableFuture. When the listener returns, Spring Kafka considers the message processed and commits the offset. Any async work that fails after that point is silently lost — no DLQ, no retry. Kafka consumers are one of the few places where intentionally blocking (.join()) at the end of the method is the correct design.
