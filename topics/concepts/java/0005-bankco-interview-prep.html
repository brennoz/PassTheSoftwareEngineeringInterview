Java Core

What's the difference between a primitive and an object reference in Java?
SAY THISA primitive (int, boolean, long...) holds its value directly on the stack — fixed size, no identity, compared with == by value. An object reference holds a pointer to heap memory; the variable itself is the reference, and == compares reference identity, not content, which is why we use .equals() for objects.
▸ if pushed
Autoboxing (Integer caching -128 to 127) is the classic gotcha — Integer a = 200; Integer b = 200; a == b is false outside the cache range. Wrapper types also mean null is a valid "value" for a boxed primitive, which primitives can never be — a common NPE source when a DB column is nullable and mapped to an int instead of Integer.
ArrayList vs LinkedList?
SAY THISArrayList is backed by a resizable array — O(1) random access, O(n) insert/remove in the middle because elements shift. LinkedList is a doubly-linked list — O(1) insert/remove once you have the node, O(n) to get there by index. I default to ArrayList; LinkedList only wins with heavy head/tail churn and no random access need.
▸ if pushed
ArrayList's resize is amortized O(1) (grows by 50%, copies old array). LinkedList's per-node overhead (two pointers + object header, ~40 bytes extra per element) plus poor cache locality means in practice ArrayList often outperforms LinkedList even for insert-heavy workloads at moderate size — CPU cache misses dominate over the theoretical shift cost. ArrayDeque beats LinkedList for stack/queue use cases entirely.
What's a functional interface?
SAY THISAn interface with exactly one abstract method — that single-method shape is what lets a lambda or method reference be assigned to it. @FunctionalInterface is optional but documents intent and makes the compiler enforce the single-method rule. Runnable, Comparator, and the whole java.util.function package (Function, Predicate, Supplier, Consumer) are examples.
▸ if pushed
Default and static methods don't count against the single-abstract-method rule — an interface can have many default methods and still be functional as long as only one method is unimplemented. Function.andThen/compose and Predicate.and/or/negate are default methods that let you chain functional interfaces without extra boilerplate.

Multithreading & Concurrency

Callable vs Runnable?
SAY THISBoth represent a unit of work to hand to a thread or executor. Runnable.run() returns void and can't throw checked exceptions. Callable<V>.call() returns a value and can throw checked exceptions — that's why ExecutorService.submit(Callable) gives you a Future<V> you can actually get a result from, versus submit(Runnable) which gives you a Future<?> that's only useful for knowing when it's done.
▸ if pushed
In a Spring Boot service, @Async methods returning CompletableFuture<T> have mostly replaced raw Callable submission for business logic — but Callable is still what you reach for with a plain ExecutorService when you need the checked-exception propagation without wrapping in a RuntimeException.
What's the Lock interface?
SAY THISjava.util.concurrent.locks.Lock is an explicit alternative to synchronized — ReentrantLock is the main implementation. It gives you things synchronized can't: tryLock() with a timeout instead of blocking forever, interruptible locking, and fairness policies. You must manually unlock() in a finally block, which is the main risk versus synchronized's automatic release.
▸ if pushed
ReadWriteLock (via ReentrantReadWriteLock) lets multiple readers hold the lock concurrently while writers get exclusive access — useful for a cache that's read-heavy. In a banking context I'd reach for optimistic locking (@Version on a JPA entity) over explicit Locks for balance updates, since Locks are per-JVM and don't help across multiple pod replicas — that needs a DB-level or Redis-level lock instead.
What's a CompletableFuture?
SAY THISA Future that supports composition and callbacks instead of just blocking get(). You can chain with thenApply/thenCompose for sequential async steps, fan out and join with allOf, and handle errors with exceptionally or handle — all without manually managing threads.
▸ if pushed
Common pitfall: default thenApply/thenAccept run on the same thread that completed the previous stage, which can be a shared ForkJoinPool.commonPool() thread — a slow callback there starves unrelated parallel streams elsewhere in the JVM. Use the Async variants with an explicit Executor for anything non-trivial. get() throws checked ExecutionException; join() throws unchecked CompletionException — join() is usually cleaner inside lambdas.
What's an Observable?
SAY THISDepends on context — classic GoF Observer pattern is one-to-many: subjects notify registered observers on state change. In reactive programming (RxJava, or Project Reactor's Mono/Flux in Spring WebFlux), an Observable is an async stream of 0..N values over time that you subscribe to, with operators like map/filter/flatMap composed declaratively — same shape as a Java Stream but push-based and async instead of pull-based and synchronous.
▸ if pushed
Spring's own idiom is Mono<T> (0 or 1 value) and Flux<T> (0..N values) rather than RxJava's Observable/Single directly, though they're conceptually the same reactive-streams contract underneath (backpressure included). I'd mention I've used CompletableFuture more than full reactive pipelines day-to-day, and would ramp on WebFlux specifics if the role needs it.

Spring

What's the context in Spring?
SAY THISThe ApplicationContext is Spring's IoC container — it reads configuration (annotations, XML, or Java config), instantiates beans, wires their dependencies, manages their lifecycle, and publishes application events. When people say "the Spring context" they mean this container and everything it's holding.
▸ if pushed
@SpringBootTest boots a real (sliced or full) context for integration tests — expensive, which is why unit tests with Mockito that don't load any context are preferred for fast feedback. Context refresh order matters for @PostConstruct/bean lifecycle bugs — a bean depending on another that isn't fully initialized yet is a classic circular-dependency or ordering issue.
Mock vs Spy bean?
SAY THISA Mockito @Mock is a fully fake object — every method returns a default/stubbed value unless you tell it otherwise. A @Spy wraps a real object — real methods actually run unless you explicitly stub them with doReturn().when(). Spring's @MockBean/@SpyBean do the same thing but also replace the bean inside the Spring context for that test.
▸ if pushed
Spy is riskier because it can trigger real side effects (a real DB call, a real HTTP call) if you forget to stub a method that gets invoked — I default to full mocks unless I specifically need to verify interaction with real logic on part of the object. @MockBean triggers a context reload if used inconsistently across test classes, which slows the suite — worth being consistent about which tests need it.
Prototype bean vs singleton bean?
SAY THISSingleton (Spring's default scope) means one shared instance per container — reused everywhere it's injected. Prototype means a new instance is created every time the bean is requested/injected. Singleton is the right default for stateless services; prototype is for anything that holds per-use mutable state.
▸ if pushed
The gotcha: injecting a prototype bean into a singleton via field injection only resolves it once, at the singleton's construction — you get the same prototype instance forever, defeating the point. Fix is a ObjectProvider<T>/ObjectFactory<T> or a lookup-method injection so a fresh instance is fetched on every call.
What is @ControllerAdvice?
SAY THISA cross-cutting exception handler for @Controller/@RestController classes — instead of try/catch in every endpoint, you centralize error handling in one class with @ExceptionHandler methods per exception type, mapping domain exceptions to consistent HTTP status codes and error response bodies.
▸ if pushed
In a banking API this is where I'd map, say, InsufficientFundsException → 422, OptimisticLockingFailureException → 409 with a retry hint, and a catch-all handler that logs the full exception server-side but returns a generic message to the client — never leaking stack traces or internal exception messages externally, which matters for PCI-DSS-adjacent APIs.

Testing / TDD

JUnit annotations — what does @ExtendWith do?
SAY THIS@ExtendWith is JUnit 5's extension mechanism — it registers a class that hooks into the test lifecycle. @ExtendWith(MockitoExtension.class) is the common one — it initializes @Mock fields automatically, replacing JUnit 4's MockitoJUnitRunner. Other core annotations: @Test, @BeforeEach/@AfterEach (per-test setup/teardown), @BeforeAll/@AfterAll (static, once per class), @ParameterizedTest with @ValueSource/@CsvSource/@MethodSource for data-driven tests.
▸ if pushed
@ExtendWith composes — you can stack multiple extensions (e.g. Mockito + a custom clock-freezing extension) rather than being locked into one Runner like JUnit 4. @Nested lets you group related tests in an inner class for readability, sharing outer setup.
How would you efficiently test a method that validates a string?
SAY THIS@ParameterizedTest with @CsvSource or @MethodSource — one test method, many input/expected-output rows, instead of copy-pasting a test per case. I'd cover: valid input, empty string, null, whitespace-only, max-length boundary, one-over-max-length, and any format-specific edge case (e.g. a sort code needing exactly 6 digits).
▸ if pushed
Per this course's own test-count convention: 2–4 focused tests, not 8 — group boundary cases into one parameterized test rather than one test method per case, keep the happy path and one meaningful failure path separate and named clearly. I'd explicitly avoid asserting internal implementation details (e.g. exact regex used) — assert behavior (accepted/rejected), not mechanism.
Talk to me about TDD.
SAY THISRed-green-refactor: write a failing test that describes the behavior you want, write the minimum code to pass it, then refactor with the safety net of a passing test. For a bank, TDD's real value isn't ceremony — it's that a ledger or payment method has one shot to be correct, and a test written first forces you to define "correct" before you're tempted to special-case your way to green.
▸ if pushed
I'd distinguish unit tests (fast, Mockito-only, no real infra) from integration tests (Testcontainers/real DB) — unit tests dominate the pyramid for fast feedback in CI, integration tests cover the seams (a real JPA query, a real Kafka round-trip) where mocks would hide a bug. For money-handling code specifically I'd always test rounding/precision behavior explicitly, since that's where BigDecimal misuse hides.

Streams

map vs flatMap?
SAY THISmap transforms each element one-to-one, so Stream<List<T>>.map(x -> x) stays a stream of lists. flatMap transforms each element into its own stream and flattens all of them into one — so mapping a list of orders to their line items with flatMap gives you one flat Stream<LineItem> instead of a Stream<List<LineItem>>.
▸ if pushed
Same distinction shows up in Optional — Optional.map on a function returning another Optional gives you a nested Optional<Optional<T>>; flatMap unwraps one level, which is exactly why chained lookups (find account → find owner → find address, each returning Optional) use flatMap to stay flat instead of nesting.

AWS / Cloud

How would you access S3 from a Java service?
SAY THISAWS SDK v2 (software.amazon.awssdk:s3) — inject an S3Client bean, call putObject/getObject/listObjectsV2. Credentials should never be hardcoded — in production the pod/EC2 instance gets an IAM role (via IRSA on EKS or an instance profile on EC2), and the SDK's default credential chain picks that up automatically. For giving a client temporary direct access without proxying through your service, I'd generate a presigned URL with a short expiry instead of exposing the bucket.
▸ if pushed
For large files, multipart upload (S3TransferManager) instead of a single putObject call. Bucket policies should deny public access by default (S3 Block Public Access) with access scoped via IAM role + bucket policy, not bucket ACLs, which AWS itself now recommends against for new buckets.
What's a VPC?
SAY THISVirtual Private Cloud — your own logically isolated network inside AWS, with its own IP address range, route tables, and gateways. Everything else (subnets, EC2 instances, EKS nodes, RDS) lives inside a VPC, which is what gives you network-level isolation between, say, your prod environment and anyone else's on AWS.
▸ if pushed
A VPC spans a region but is split into subnets per Availability Zone for fault tolerance. Peering or Transit Gateway connects separate VPCs (e.g. a shared-services VPC talking to an app VPC) without traffic going over the public internet.
What's a subnet?
SAY THISA subdivision of a VPC's IP range, tied to a single Availability Zone. Public subnets have a route to an Internet Gateway (for anything that needs a public IP — a load balancer, a bastion). Private subnets route out through a NAT Gateway instead — no inbound internet access, which is where app servers and databases should live.
▸ if pushed
In an EKS setup, worker nodes typically sit in private subnets; only the load balancer (ALB/NLB) sits in a public subnet, terminating TLS and forwarding into the private network — minimizes what's directly internet-reachable.
Different types of EC2 instances?
SAY THISInstance families are optimized for different resource ratios: general purpose (t3/m5 — balanced CPU/memory), compute-optimized (c5 — CPU-heavy workloads), memory-optimized (r5 — in-memory caches, large JVM heaps), storage-optimized (i3 — high IOPS, local NVMe). Purchase models matter too: On-Demand (pay per use), Reserved/Savings Plans (committed discount), Spot (cheap but interruptible — good for CI runners, bad for prod ledger services).
▸ if pushed
t3/t4g are burstable — cheap baseline CPU with credits that spike, can throttle hard if you sustain high CPU (a bad fit for a consistently loaded prod service, fine for low-traffic internal tools). t4g/m6g (Graviton, ARM) are typically 20% cheaper for the same performance if your Docker images are built multi-arch.
Security groups vs Network ACLs?
SAY THISSecurity groups are stateful and attached to instances/ENIs — if you allow inbound traffic, the response is automatically allowed out, and you can only write "allow" rules. Network ACLs are stateless and attached to a subnet — you need explicit rules for both directions, and you can write both "allow" and "deny" rules. I default to security groups for per-service access control; NACLs are for coarse subnet-level blocking, like explicitly denying a known-bad IP range.
▸ if pushed
Because NACLs are stateless and evaluated in rule-number order (lowest first, first match wins), misconfiguring one can silently block return traffic that a security group would have allowed automatically — a classic "service works from one subnet but not another" debugging trap.

If BankCo-specific angles come up

Not explicitly asked, but likely follow-ups given the domain — worth having the one-liner ready.

Why not use double for monetary values?
SAY THISFloating point can't represent most decimal fractions exactly in binary — 0.1 + 0.2 != 0.3 — which silently loses cents at scale. BigDecimal with an explicit scale and rounding mode is the standard for money, always constructed from a String or unscaled long, never from a double literal.
How do you prevent a double-charge on a payment retry?
SAY THISIdempotency key — client generates a unique key per logical operation, sent with the request. Server checks a table/cache for that key before processing; if seen before, returns the original result instead of processing again. Usually backed by a unique DB constraint so even a race between two concurrent retries can't both succeed.
How do you stop two concurrent requests from causing an account overdraft?
SAY THISOptimistic locking with @Version on the account entity — the second concurrent write fails with OptimisticLockingFailureException because the version it read is stale, and the caller retries or fails cleanly. Pessimistic row locks are the alternative but hold DB connections longer under contention — I'd default to optimistic unless the domain shows very high contention on the same row.
