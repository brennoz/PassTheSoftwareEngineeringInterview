Java CompletableFuture

Category: Java · Topic: Async programming · Lesson 1 of 1

CompletableFuture<T> is Java's primary tool for non-blocking async composition. It extends Future<T> (Java 5) with chainable transformations, combining, error recovery, and manual completion. Understanding it is essential for any Spring Boot backend — every HTTP client, JDBC call, and external API call can be run concurrently and composed without blocking threads.

1. The Problem with Future

// Java 5 Future — blocking only, no composition
ExecutorService pool = Executors.newFixedThreadPool(4);
Future<EventDto> future = pool.submit(() -> eventClient.getEvent(id));

// .get() blocks the calling thread — you waste a thread waiting
EventDto event = future.get();       // blocks here
List<BetDto> bets = betFuture.get(); // can't even start bets until event is done

// You CANNOT chain: "when event is done, fetch bets" — no callback mechanism
// You CANNOT recover from exceptions without try/catch around every .get()
// You CANNOT combine two futures without blocking one
// CompletableFuture solves all of this
CompletableFuture<EventDto> eventCf = CompletableFuture.supplyAsync(() -> eventClient.getEvent(id));
CompletableFuture<List<BetDto>> betsCf = CompletableFuture.supplyAsync(() -> betClient.getBets(id));

// Both fire simultaneously. Combine without blocking either.
CompletableFuture<EventSummary> summary = eventCf.thenCombine(betsCf, EventSummary::new);

// Chain error recovery
summary.exceptionally(ex -> EventSummary.empty());

2. Creation

// --- Already-done value (tests, cached results) ---
CompletableFuture<EventDto> cf = CompletableFuture.completedFuture(cachedEvent);
CompletableFuture<EventDto> failed = CompletableFuture.failedFuture(new RuntimeException("not found"));

// --- Async computation on ForkJoinPool.commonPool() (default) ---
// WARNING: ForkJoinPool is sized to CPU cores (e.g. 4 on t3.large).
// Good for CPU-bound. BAD for I/O — 4 threads max.
CompletableFuture<EventDto> cf = CompletableFuture.supplyAsync(
    () -> eventClient.getEvent(id)
);

// --- Async computation on explicit executor (correct for I/O) ---
ExecutorService ioExecutor = Executors.newVirtualThreadPerTaskExecutor(); // Java 21
CompletableFuture<EventDto> cf = CompletableFuture.supplyAsync(
    () -> eventClient.getEvent(id),
    ioExecutor
);

// --- Async with no result (Runnable, returns CF<Void>) ---
CompletableFuture<Void> cf = CompletableFuture.runAsync(
    () -> auditLog.record(event),
    ioExecutor
);

// --- Manual completion (you control when/what completes) ---
CompletableFuture<String> cf = new CompletableFuture<>();
// somewhere else, when result is ready:
cf.complete("result");
cf.completeExceptionally(new RuntimeException("failed"));
// if cf is already completed, these calls are no-ops
cf.completeAsync(() -> expensiveComputation(), executor); // complete async

3. Transform — thenApply / thenCompose

The key distinction thenApply — transform is synchronous (pure function, returns plain value). thenCompose — transform is asynchronous (calls another service, returns CF). Without thenCompose you'd get CF<CF<T>> — nested futures. 
// thenApply — sync transform (like Stream.map)
// runs on the thread that completed the upstream CF (or calling thread if already done)
CompletableFuture<String> eventName = CompletableFuture
    .supplyAsync(() -> eventClient.getEvent(id), ioExecutor)  // CF<EventDto>
    .thenApply(event -> event.getName().toUpperCase());         // CF<String>

// thenApplyAsync — transform on new thread from executor pool
// use when the transform itself is CPU-heavy or you want to avoid thread-starvation
CompletableFuture<String> name = eventCf
    .thenApplyAsync(event -> heavyTransform(event), executor);

// thenAccept — consume result, return CF<Void> (no further chaining of result)
CompletableFuture<Void> done = eventCf
    .thenAccept(event -> log.info("Event loaded: {}", event.getId()));

// thenRun — run after completion, no access to result, return CF<Void>
CompletableFuture<Void> done = eventCf
    .thenRun(() -> metrics.increment("events.loaded"));
// thenCompose — async transform (like Stream.flatMap)
// fn RETURNS a CF — thenCompose flattens CF<CF<T>> → CF<T>
CompletableFuture<List<BetDto>> bets = CompletableFuture
    .supplyAsync(() -> eventClient.getEvent(id), ioExecutor)      // CF<EventDto>
    .thenCompose(event ->
        CompletableFuture.supplyAsync(                             // CF<List<BetDto>>
            () -> betClient.getBetsForEvent(event.getId()),
            ioExecutor
        )
    );
// Result: CF<List<BetDto>>   ← flat

// What thenApply would produce instead (wrong for this case):
CompletableFuture<CompletableFuture<List<BetDto>>> nested = CompletableFuture
    .supplyAsync(() -> eventClient.getEvent(id), ioExecutor)
    .thenApply(event ->
        CompletableFuture.supplyAsync(() -> betClient.getBetsForEvent(event.getId()), ioExecutor)
    );
// CF<CF<List<BetDto>>>  ← double-wrapped, useless

4. Combine Multiple Futures

// thenCombine — combine exactly TWO CFs when BOTH complete
// biFunction receives both results
CompletableFuture<EventDto>  eventCf = CompletableFuture.supplyAsync(() -> eventClient.getEvent(id), exec);
CompletableFuture<PriceDto>  priceCf = CompletableFuture.supplyAsync(() -> priceClient.getPrice(id), exec);

CompletableFuture<String> display = eventCf.thenCombine(
    priceCf,
    (event, price) -> event.getName() + " @ " + price.getOdds()
);

// allOf — wait for ALL CFs to complete, returns CF<Void> (no direct result)
CompletableFuture<EventDto>     eventCf  = CompletableFuture.supplyAsync(() -> eventClient.getEvent(id), exec);
CompletableFuture<List<BetDto>> betsCf   = CompletableFuture.supplyAsync(() -> betClient.getBets(id), exec);
CompletableFuture<PriceDto>     priceCf  = CompletableFuture.supplyAsync(() -> priceClient.getPrice(id), exec);

// All 3 fire simultaneously. Total time = max(t_event, t_bets, t_price).
EventSummary summary = CompletableFuture.allOf(eventCf, betsCf, priceCf)
    .thenApply(ignored -> {
        // .join() here is INSTANT — allOf guarantees all 3 are done before this runs
        return new EventSummary(eventCf.join(), betsCf.join(), priceCf.join());
    })
    .join(); // block once for the final result

// anyOf — completes when FIRST finishes (Object type — you lose type safety)
CompletableFuture<Object> first = CompletableFuture.anyOf(cf1, cf2, cf3);
// Useful for: fallback to fastest data source, race between replicas
Real pattern: parallel fetch in sportsbook-service Sequential: 20ms (event) + 30ms (bets) + 15ms (price) = 65ms total.
Parallel with allOf: max(20, 30, 15) = 30ms total. 2× speedup, zero extra code complexity.

5. Error Handling

// exceptionally — recover on failure, return fallback value
// ONLY runs if upstream failed
CompletableFuture<PriceDto> price = CompletableFuture
    .supplyAsync(() -> priceClient.getPrice(id), exec)
    .exceptionally(ex -> {
        log.warn("Price fetch failed eventId={}: {}", id, ex.getMessage());
        return PriceDto.stale();  // fallback
    });

// handle — ALWAYS runs whether success or failure
// receives (result, throwable) — exactly one will be null
CompletableFuture<PriceDto> price = CompletableFuture
    .supplyAsync(() -> priceClient.getPrice(id), exec)
    .handle((result, ex) -> {
        if (ex != null) {
            log.warn("Price unavailable: {}", ex.getMessage());
            return PriceDto.stale();
        }
        metrics.recordSuccess("price.fetch");
        return result;
    });

// whenComplete — side effect only, CANNOT change the result
// always runs, result/exception pass through unchanged
CompletableFuture<PriceDto> price = CompletableFuture
    .supplyAsync(() -> priceClient.getPrice(id), exec)
    .whenComplete((result, ex) -> {
        if (ex != null) log.error("Price fetch failed", ex);
        else metrics.record("price.fetch.ok", result.getLatency());
        // return value here has no effect — result passes through as-is
    });

// Chaining recovery then continuing
CompletableFuture<EventSummary> summary = eventCf
    .exceptionally(ex -> EventDto.empty())           // recover event
    .thenCombine(
        betsCf.exceptionally(ex -> List.of()),       // recover bets
        (event, bets) -> new EventSummary(event, bets)
    );
MethodRuns whenCan change result?Use for
exceptionally(fn)Failure onlyYes (provides fallback)Fallback value on error
handle(biFunc)AlwaysYesTransform or recover in one step
whenComplete(biConsumer)AlwaysNo (side effects only)Logging, metrics, cleanup

6. Timeout (Java 9+)

// orTimeout — completes exceptionally with TimeoutException after deadline
CompletableFuture<AdvisoryResult> advisory = CompletableFuture
    .supplyAsync(() -> advisoryClient.check(bet), exec)
    .orTimeout(500, TimeUnit.MILLISECONDS)
    .exceptionally(ex -> {
        // ex is TimeoutException or original exception
        log.warn("Advisory timeout — defaulting to APPROVE");
        return AdvisoryResult.APPROVED;
    });

// completeOnTimeout — provide default value instead of exception (cleaner)
CompletableFuture<AdvisoryResult> advisory = CompletableFuture
    .supplyAsync(() -> advisoryClient.check(bet), exec)
    .completeOnTimeout(AdvisoryResult.APPROVED, 500, TimeUnit.MILLISECONDS);
// If advisory responds in time → use its result
// If 500ms exceeded → complete with APPROVED, no exception needed

// Combining: timeout + circuit breaker + fallback
public CompletableFuture<PriceDto> getPriceSafe(Long eventId) {
    return CompletableFuture
        .supplyAsync(() ->
            CircuitBreaker.decorateSupplier(priceCircuitBreaker,
                () -> priceClient.getPrice(eventId)
            ).get(),
            ioExecutor
        )
        .completeOnTimeout(PriceDto.stale(), 200, TimeUnit.MILLISECONDS)
        .exceptionally(ex -> {
            log.warn("Price unavailable eventId={}", eventId);
            return PriceDto.stale();
        });
}

7. Blocking — get() vs join()

// get() — throws checked exceptions — use in normal methods
try {
    EventDto event = eventCf.get();                              // blocks indefinitely
    EventDto event = eventCf.get(5, TimeUnit.SECONDS);          // blocks up to 5s
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw new RuntimeException(e);
} catch (ExecutionException e) {
    throw new RuntimeException(e.getCause()); // unwrap the actual exception
} catch (TimeoutException e) {
    throw new ServiceTimeoutException("event-service", e);
}

// join() — throws unchecked CompletionException — use in CF chains and streams
EventDto event = eventCf.join();           // throws CompletionException(unchecked)

// join() preferred in CF chains — already done when called after allOf:
CompletableFuture.allOf(eventCf, betsCf)
    .thenApply(v -> new Result(eventCf.join(), betsCf.join())); // instant, not blocking

// join() preferred in streams:
List<EventDto> events = ids.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> eventClient.getEvent(id), exec))
    .toList()        // collect all CFs first — so all start before any join()
    .stream()
    .map(CompletableFuture::join) // then join — all already running in parallel
    .toList();
// WARNING: do NOT .map(id -> cf).map(cf -> cf.join()) in one stream
// That starts cf1, waits for cf1, starts cf2, waits for cf2 — SEQUENTIAL, not parallel

// getNow() — non-blocking, returns default if not done
EventDto event = eventCf.getNow(EventDto.empty()); // returns empty if CF not yet done
Stream parallel fetch — the order matters Collect all CFs into a list FIRST (so all start), then join in a second pass. A single stream that maps and immediately joins runs SEQUENTIALLY — no parallelism.

8. Executor Choice

// ForkJoinPool.commonPool() — DEFAULT when no executor passed
// Sized to available CPU cores (Runtime.getRuntime().availableProcessors())
// On t3.large (2 vCPU): pool has 1 thread (max(1, processors - 1))
// PROBLEM: fire 100 I/O calls — only 1-2 run concurrently, 98 queue up

// --- Option 1: Fixed thread pool (classic I/O pool) ---
ExecutorService ioPool = Executors.newFixedThreadPool(
    50,                                    // 50 concurrent I/O tasks
    new ThreadFactory() {
        private final AtomicInteger n = new AtomicInteger();
        public Thread newThread(Runnable r) {
            Thread t = new Thread(r, "io-pool-" + n.incrementAndGet());
            t.setDaemon(true);
            return t;
        }
    }
);

// --- Option 2: Virtual thread per task (Java 21, best for I/O) ---
ExecutorService ioExecutor = Executors.newVirtualThreadPerTaskExecutor();
// Each task gets own VT. No pool ceiling. JVM schedules on carrier threads.
// Correct for HTTP calls, JDBC, Redis, any I/O-bound supplyAsync.
// DO NOT use for CPU-bound (no benefit, extra scheduling overhead).

// --- Option 3: Spring's @Async executor (configured in app context) ---
@Configuration
@EnableAsync
public class AsyncConfig {
    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        return Executors.newVirtualThreadPerTaskExecutor(); // Java 21
    }
}

// Usage in service
@Async("taskExecutor")
public CompletableFuture<EventDto> getEventAsync(Long id) {
    return CompletableFuture.completedFuture(eventClient.getEvent(id));
}
// Calling thread is not blocked — Spring MVC dispatches to VT executor

9. Real-World Patterns

Pattern 1 — Parallel service calls with independent fallbacks

// Each service fails independently — the others still return
public EventSummaryDto buildEventSummary(Long eventId) {
    var exec = Executors.newVirtualThreadPerTaskExecutor();

    CompletableFuture<EventDto> eventCf = CompletableFuture
        .supplyAsync(() -> eventService.getEvent(eventId), exec)
        .completeOnTimeout(EventDto.empty(), 200, MILLISECONDS)
        .exceptionally(ex -> EventDto.empty());

    CompletableFuture<List<BetDto>> betsCf = CompletableFuture
        .supplyAsync(() -> betManager.getBets(eventId), exec)
        .completeOnTimeout(List.of(), 300, MILLISECONDS)
        .exceptionally(ex -> List.of());

    CompletableFuture<PriceDto> priceCf = CompletableFuture
        .supplyAsync(() -> pricingService.getPrice(eventId), exec)
        .completeOnTimeout(PriceDto.stale(), 150, MILLISECONDS)
        .exceptionally(ex -> PriceDto.stale());

    return CompletableFuture.allOf(eventCf, betsCf, priceCf)
        .thenApply(v -> EventSummaryDto.of(
            eventCf.join(),
            betsCf.join(),
            priceCf.join()
        ))
        .join();
}

Pattern 2 — Sequential fan-out (result of first feeds into second)

// Use thenCompose: result of getEvent feeds into getBets
public CompletableFuture<List<BetDto>> getBetsForLatestEvent(Long raceId) {
    return CompletableFuture
        .supplyAsync(() -> eventService.getLatestEvent(raceId), ioExecutor)
        .thenCompose(event ->
            CompletableFuture.supplyAsync(
                () -> betManager.getBetsForEvent(event.getId()),
                ioExecutor
            )
        )
        .exceptionally(ex -> {
            log.error("Failed to load bets for race {}", raceId, ex);
            return List.of();
        });
}

Pattern 3 — Batch parallel processing

// Process N items in parallel, collect all results
public List<PriceDto> getPricesForMarkets(List<Long> marketIds) {
    // Step 1: start ALL CFs (fire all requests simultaneously)
    List<CompletableFuture<PriceDto>> futures = marketIds.stream()
        .map(id -> CompletableFuture
            .supplyAsync(() -> priceService.getPrice(id), ioExecutor)
            .completeOnTimeout(PriceDto.stale(), 200, MILLISECONDS)
        )
        .toList(); // collect BEFORE joining — critical for parallelism

    // Step 2: join all (all are already running)
    return futures.stream()
        .map(CompletableFuture::join) // instant if all done, waits for slowest
        .toList();
}

Pattern 4 — Fire-and-forget async notification

// Bet accepted — notify audit log async, don't block the response
public BetSlipResponse createSlip(CreateSlipCommand cmd) {
    BetSlip slip = betRepository.save(BetSlip.from(cmd));

    // Non-blocking: response goes back to client immediately
    CompletableFuture.runAsync(
        () -> auditService.recordBetPlacement(slip),
        ioExecutor
    ).exceptionally(ex -> {
        log.error("Audit notification failed slipId={}", slip.getId(), ex);
        return null; // must handle — swallowed exceptions are silent bugs
    });

    return BetSlipResponse.from(slip);
}

Pattern 5 — Async enrichment in Kafka consumer

// Kafka consumer receives event, enriches from two services, publishes result
@KafkaListener(topics = "arm-dev.event-service.json")
public void processEvent(EventUpdateEvent event) {
    // Enrich in parallel from two services
    CompletableFuture<TenantDto>    tenantCf  = CompletableFuture.supplyAsync(
        () -> tenantService.getTenant(event.getTenantId()), ioExecutor);
    CompletableFuture<SportsbookDto> sbookCf   = CompletableFuture.supplyAsync(
        () -> sportsbookService.getConfig(event.getTenantId()), ioExecutor);

    tenantCf.thenCombine(sbookCf, (tenant, sbook) ->
            enrichedEventPublisher.publish(event, tenant, sbook)
        )
        .exceptionally(ex -> {
            log.error("Enrichment failed eventId={}", event.getId(), ex);
            deadLetterPublisher.publish(event, ex);
            return null;
        })
        .join(); // Kafka consumer must wait for async work to finish before committing offset
}

10. Common Pitfalls

Pitfall 1 — Exception silently swallowed 
// BAD — exception disappears if nobody calls get()/join()
CompletableFuture.supplyAsync(() -> {
    throw new RuntimeException("service down");
}); // fire-and-forget — RuntimeException is lost forever

// GOOD — always attach error handling
CompletableFuture.supplyAsync(() -> priceClient.getPrice(id), exec)
    .exceptionally(ex -> { log.error("Failed", ex); return PriceDto.stale(); });
Pitfall 2 — Blocking inside a CF chain (nested blocking) 
// BAD — get() inside thenApply blocks the pool thread
CompletableFuture.supplyAsync(() -> eventClient.getEvent(id))
    .thenApply(event -> {
        List<BetDto> bets = betsCf.get(); // BLOCKS the thread running thenApply
        return new EventSummary(event, bets);
    });

// GOOD — use thenCombine, never block inside a chain
eventCf.thenCombine(betsCf, (event, bets) -> new EventSummary(event, bets));
Pitfall 3 — Sequential stream instead of parallel 
// BAD — starts cf1, joins cf1, starts cf2, joins cf2 — SEQUENTIAL
List<EventDto> events = ids.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> eventClient.getEvent(id), exec))
    .map(CompletableFuture::join) // immediate join defeats parallelism
    .toList();

// GOOD — collect first (all start), then join
List<CompletableFuture<EventDto>> cfs = ids.stream()
    .map(id -> CompletableFuture.supplyAsync(() -> eventClient.getEvent(id), exec))
    .toList();                // all running now
List<EventDto> events = cfs.stream()
    .map(CompletableFuture::join) // join all — already in flight
    .toList();
Pitfall 4 — ForkJoinPool for I/O tasks 
// BAD — ForkJoinPool.commonPool() has 2 threads on a 2-core machine
// 100 concurrent I/O calls → 98 tasks queue, latency explodes
CompletableFuture.supplyAsync(() -> jdbcTemplate.query(...)); // default pool

// GOOD — explicit I/O executor
ExecutorService ioExec = Executors.newVirtualThreadPerTaskExecutor();
CompletableFuture.supplyAsync(() -> jdbcTemplate.query(...), ioExec);

Quiz

Q1. You call eventClient.getEvent(id) which itself returns CompletableFuture<EventDto>. You want to chain it with another async call betClient.getBets(event.getId()) that also returns a CF. Which method gives you CF<List<BetDto>> rather than CF<CF<List<BetDto>>>?

  • thenApply — it maps the result of the first CF to the second CF and flattens automatically
  • thenCompose — the function returns a CF<List<BetDto>>, and thenCompose flattens CF<CF<List>> into CF<List>. thenApply would return CF<CF<List>> — double-wrapped and unusable without nested join()
  • thenCombine — merges both CFs into one result using a BiFunction
  • thenAccept — consumes the first CF result and triggers the second
thenCompose is CF's equivalent of flatMap. Rule: if your transform function returns a CF, use thenCompose. If it returns a plain value (String, DTO), use thenApply. thenCombine is for merging two INDEPENDENT CFs that both start at the same time — not for chaining where result of first feeds second.

Q2. You fire 3 parallel calls with allOf(eventCf, betsCf, priceCf).thenApply(v -> new Result(eventCf.join(), betsCf.join(), priceCf.join())). What does eventCf.join() do inside the thenApply callback?

  • Blocks the calling thread for up to 30ms waiting for the event response
  • Starts a new async operation on ForkJoinPool to fetch the event
  • Returns immediately without blocking — allOf guarantees all three CFs are complete before thenApply runs. join() on a completed CF returns the cached result instantly. This is the correct pattern: allOf waits for all, then join() inside thenApply extracts the results without blocking.
  • Throws CompletionException if the event CF encountered an exception during execution
allOf's contract: the CF returned by allOf completes only after ALL input CFs complete. thenApply runs only after allOf completes. So when thenApply runs, all three CFs are already done — join() is a no-op (returns cached result). This is why you always call allOf first, then collect results with join() inside thenApply. Option D is wrong because exceptions in the input CFs are propagated through allOf — if any CF failed, thenApply would not run (allOf itself completes exceptionally).

Q3. You write CompletableFuture.supplyAsync(() -> priceClient.getPrice(id)) with no explicit executor. The server has 2 CPU cores. You fire 200 concurrent requests each making this call. What is the performance bottleneck?

  • ForkJoinPool.commonPool() defaults to max(1, processors-1) = 1 thread on a 2-core machine. Only 1 I/O task runs at a time; 199 tasks queue. Price fetches that should take 20ms in parallel now take 200 × 20ms = 4 seconds serially. Fix: pass an explicit I/O executor — Executors.newVirtualThreadPerTaskExecutor() in Java 21, or a fixed thread pool sized for concurrency.
  • CompletableFuture has a built-in concurrency limit of 16 tasks per JVM
  • Each supplyAsync call creates a new OS thread — 200 threads × 1MB stack = 200MB memory exhaustion
  • The default timeout on supplyAsync is 100ms — tasks taking longer are cancelled
ForkJoinPool.commonPool() is CPU-sized, not I/O-sized. On a 2-core machine it typically has 1 worker thread. This is the correct default for CPU-bound work (math, compression) where you want at most cores-worth of parallelism. For I/O-bound work (HTTP, JDBC, Redis) you want many more threads because they spend most time waiting, not using CPU. Always pass an explicit executor to supplyAsync for I/O-bound tasks.

Q4. A supplyAsync task throws a RuntimeException. Nobody calls get() or join(). Nobody attaches exceptionally() or handle(). What happens to the exception?

  • The JVM logs the exception to stderr and shuts down the thread that ran the task
  • The exception is silently swallowed — stored inside the failed CF but never surfaced. If no code ever calls get()/join()/handle() on that CF, the exception is lost with zero logging, zero indication of failure. This is the most dangerous CompletableFuture pitfall. Always attach error handling: .exceptionally(ex -> { log.error(…); return fallback; })
  • ForkJoinPool's UncaughtExceptionHandler logs it to Datadog automatically
  • The CF retries the supplier up to 3 times before storing the exception
Unlike Thread where an uncaught exception goes to UncaughtExceptionHandler, CompletableFuture stores the exception inside the CF in a failed state. If nothing ever observes that state (no get/join/handle/exceptionally), the exception is permanently lost. This commonly causes fire-and-forget audit log calls, notification sends, or cache updates to silently fail in production with no trace in logs. Rule: every CompletableFuture chain that produces no result for the caller (runAsync, void thenAccept) must still have .exceptionally() or .whenComplete() to log failures.
