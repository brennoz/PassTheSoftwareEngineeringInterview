Collectors.mapping — Extract Before You Collect

Category: Java · Topic: Collectors (Java 8) · Est. time: 15 min · Lesson 10

Collectors.mapping is the simplest downstream adapter: it applies a mapper function to each element before feeding it into another collector. You've probably used .map(f).collect(...) hundreds of times. mapping does the same thing but works inside a downstream position — inside a groupingBy, inside teeing, inside collectingAndThen.

1. The Problem It Solves

You have a list of bets and want to group them by market, collecting just the bet reference strings — not the whole Bet object.

The naive two-pass approach:

// Two passes: group first, then transform each group
Map<String, List<Bet>> byMarket = bets.stream()
    .collect(Collectors.groupingBy(Bet::marketId));

Map<String, List<String>> result = new HashMap<>();
byMarket.forEach((market, marketBets) ->
    result.put(market, marketBets.stream()
        .map(Bet::betRef)
        .toList()));

Collectors.mapping collapses this into one stream pass, one collect call:

Map<String, List<String>> result = bets.stream()
    .collect(Collectors.groupingBy(
        Bet::marketId,
        Collectors.mapping(Bet::betRef, Collectors.toList())
    ));

mapping(Bet::betRef, toList()) reads as: "for every bet in this group, extract betRef, then collect those strings into a list." The extraction happens before the downstream toList ever sees the element.

2. Signature

// java.util.stream.Collectors
public static <T, U, A, R> Collector<T, ?, R> mapping(
    Function<? super T, ? extends U> mapper,
    Collector<? super U, A, R>       downstream
)
ParameterMeaning
TInput element type (e.g. Bet)
UMapped type (e.g. String — the bet reference)
mapperTransforms T → U before the downstream sees it
downstreamAny collector that accepts U — toList, toSet, joining, counting…

3. Common Patterns

3a. groupingBy + mapping + toList

The most common shape — extract one field per group:

// marketId → list of bet references in that market
bets.stream().collect(groupingBy(
    Bet::marketId,
    mapping(Bet::betRef, toList())
));

3b. groupingBy + mapping + toSet (deduplication)

// marketId → set of unique bettors
bets.stream().collect(groupingBy(
    Bet::marketId,
    mapping(Bet::bettor, toSet())
));

3c. groupingBy + mapping + joining

// marketId → comma-separated bet refs
bets.stream().collect(groupingBy(
    Bet::marketId,
    mapping(Bet::betRef, joining(", "))
));

3d. mapping + collectingAndThen (sort the result)

Wrap the downstream with collectingAndThen to post-process — here, sort the collected list:

bets.stream().collect(groupingBy(
    Bet::marketId,
    collectingAndThen(
        mapping(Bet::betRef, toList()),
        refs -> refs.stream().sorted().toList()
    )
));
Why not .sorted() before .collect()?

Sorting the outer stream before groupingBy sorts elements globally — not per-group. The finisher in collectingAndThen runs after a group is fully accumulated, so it sorts each bucket independently. That's the correct hook for per-group ordering.

4. Imperative Counterpart: Map.computeIfAbsent

The imperative version of groupingBy + mapping uses computeIfAbsent to lazily create the accumulator list on first encounter of a key:

Map<String, List<String>> result = new HashMap<>();
for (Bet bet : bets) {
    result.computeIfAbsent(bet.marketId(), k -> new ArrayList<>())
          .add(bet.betRef());
}
result.values().forEach(Collections::sort);
return result;
MethodWhen it firesReturns
computeIfAbsent(k, fn)Key absent — calls fn and stores resultThe existing or newly-created value
computeIfPresent(k, fn)Key present — calls fn(key, existing) and stores resultUpdated value, or null if fn returns null
compute(k, fn)Always — calls fn(key, existingOrNull)New value
merge(k, v, fn)Always — absent uses v; present calls fn(existing, v)New value
Why computeIfAbsent beats get + put

get(k) + putIfAbsent(k, new ArrayList<>()) allocates a new list even when the key already exists — the put just discards it. computeIfAbsent only calls the factory when the key is genuinely missing, so no wasted allocation on hot keys.

Quiz

Q1: You call groupingBy(Bet::marketId, mapping(Bet::bettor, toList())). What is the return type?

  • Map<String, List<Bet>>
  • Map<String, List<String>>
  • Map<String, Set<String>>
  • Compile error — mapping cannot be a groupingBy downstream
mapping(Bet::bettor, toList()) produces Collector<Bet,?,List<String>>. The outer groupingBy key is String (marketId), the downstream result is List<String>, so the map is Map<String, List<String>>.

Q2: computeIfAbsent(k, fn) vs get(k) + putIfAbsent(k, new ArrayList<>()) — which is preferable and why?

  • They are equivalent — both do one map lookup.
  • putIfAbsent is better — it is an atomic CAS operation, safe for concurrent use.
  • computeIfAbsent is better — it only calls the factory when the key is absent, so hot keys incur no allocation. putIfAbsent always allocates a new list, which is immediately discarded when the key already exists.
  • computeIfAbsent is better only for ConcurrentHashMap; for HashMap they are identical.
computeIfAbsent(k, fn) calls fn only when k is absent. putIfAbsent(k, new ArrayList<>()) always evaluates new ArrayList<>() — the allocation is unconditional, the reference is just discarded if the key exists. For a map with many repeated keys this is measurable GC pressure. Note: neither is safe for concurrent use without ConcurrentHashMap.
